# Общий кэш компиляции (sccache) для флота

Короткая справка по `scripts/rustc-wrapper.sh` и переменной `RUSTC_WRAPPER`.
Файл намеренно честный: ниже отдельно сказано, чего общий кэш **не** даёт.

## Что даёт

- **Разделяемый кэш объектных файлов.** Обёртка `scripts/rustc-wrapper.sh`
  запускает `sccache` вместо голого `rustc`; результат компиляции кладётся в
  общий кэш `~/.cache/sccache` (или `SCCACHE_DIR`). Разные ворктри флота
  (агент `A`, агент `B`, гейты) при одинаковых входных данных получают
  готовый объект — повторная компиляция не выполняется.
- **Кэш переживает `target/`.** Кэш живёт вне дерева; `cargo clean` его не
  трогает, поэтому уборка целевого каталога не обнуляет ускорение.
- **Работает ВНЕ дерева репозитория.** Обёртка подставляется в окружение
  процесса-исполнителя и процессов гейтов (см. ниже), поэтому фабричные
  ворктри `worktrees/<slug>-<hash>` — которые лежат вне репозитория — тоже
  получают кэш. Именно ради них `.cargo/config.toml` не годится: cargo ищет
  конфиг вверх по дереву от cwd, а ворктри вне дерева.

## Чего он НЕ даёт

- **Не разделяет `target/`.** Инкрементальная сборка cargo по-прежнему
  локальна для каждого ворктри: линковка, финальный бинарь и метаданные
  пересобираются. Экономия — только на компиляции единиц крейта.
- **Не отменяет эксклюзивную блокировку `target/`.** Это главная причина,
  почему общий `CARGO_TARGET_DIR` намеренно НЕ вводится: cargo берёт
  исключительную блокировку каталога сборки, и ворктри, делящие один
  `target/`, выстраиваются в очередь вместо параллельной работы — флот
  сериализуется. Общий кэш даёт разделение труда без этой блокировки.
- **Не ускоряет первый прогон.** Холодный кэш пуст: первую компиляцию
  платит тот, кто запустился первым; выигрыш появляется со второй.
- **Ничего не даёт без `sccache`.** Если `sccache` нет в `PATH` и не задан
  `SCCACHE_PATH`, обёртка прозрачно передаёт аргументы реальному `rustc`
  (`exec "$@"`) — сборка идёт как обычно, просто без кэша. Отсутствие
  `sccache` ломает ровно ничего.

## Как включить

Зависит от того, кто запускает сборку.

1. **Исполнители флота и командные гейты — автоматически.** Движок сам
   подставляет `RUSTC_WRAPPER` в окружение дочернего процесса
   (`src/harness.rs::apply_rustc_wrapper`, вызов в `run_harness_inner` и в
   `src/fleet_gate.rs::run_command`). Путь считается от расположения бинаря
   (`current_exe`), а не от cwd и не от домашнего каталога, поэтому ворктри
   вне репозитория получают ту же обёртку. Подстановка идёт ПОСЛЕ
   `env_clear`/`env`, поэтому доходит и до изолированного окружения.
   Если `scripts/rustc-wrapper.sh` не существует — подстановки нет, сборка
   идёт как раньше.

2. **Вручную (своя оболочка).**
   ```sh
   export RUSTC_WRAPPER="$PWD/scripts/rustc-wrapper.sh"
   cargo build
   ```
   Либо через конфиг (для СВОЕЙ машины, не для ворктри флота):
   ```toml
   # .cargo/config.toml
   [build]
   rustc-wrapper = "scripts/rustc-wrapper.sh"
   ```
   **В репозитории такого файла СОЗНАТЕЛЬНО нет.** `.cargo/` в
   `.gitignore`, а обёртка untracked: оставленный конфиг создаёт ловушку —
   `git clean -fd` удаляет скрипт, конфиг остаётся и ссылается на
   несуществующий файл, после чего ЛЮБАЯ команда cargo в репозитории падает.
   Подстановка из окружения движка этой ловушки не создаёт: нет скрипта —
   нет ссылки.

## Как выключить

- **Убрать автоподстановку**: переименовать или удалить
  `scripts/rustc-wrapper.sh`. Движок тихо перестанет подставлять обёртку,
  сборка пойдёт обычным `rustc`. Ничего не падает.
- **Свой wrapper**: выставьте `RUSTC_WRAPPER` заранее — движок НЕ
  переопределяет уже заданное значение (приоритет пользователя) и переносит
  его в дочернее окружение. Пустое значение считается невыставленным.
- **Только кэш off, wrapper on**: пустой результат даёт
  `sccache` с отключённым кэшем, но проще убрать скрипт (см. выше).

## Ограничения детектора самооценки

Детектор (`src/fleet_gate.rs::detect_self_assessment`) ищет случай, когда
гейт зовёт судью `arch-ml`, СОБРАННОГО ИЗ ОЦЕНЯЕМОЙ ВОРКТРИ, — тогда зачёт
себе ставит сам оцениваемый код. Это **детектор, а не барьер**, и он
намеренно узкий:

- **По умолчанию `Warn` НЕ останавливает узел.** Движок флота прерывает узел
  только на `Fail` (`GateReport::failed`), а `Warn` проходит. То есть в
  штатном режиме срабатывание детектора защищает ровно никак — только
  оставляет след в отчёте. Эскалация:
  `ARCH_ML_SELF_ASSESSMENT=fail` (`1`/`true`) превращает самооценку в
  `Verdict::Fail`. По умолчанию оставлен `Warn` — решение владельца, менять
  его без явного слова нельзя.
- **Видит только позицию программы.** Токены берутся как первый и следующие
  за `&&`, `||`, `;`, `|`, `&`; имя сверяется по basename целиком и без
  регистра. Поэтому `echo ./target/debug/arch-ml` и
  `arch-ml-wrapper.sh` — не судья.
- **Не ловит обёртки.** Вызов через переменную (`$JUDGE`, `"$BIN"`),
  Makefile/`make`, `cargo run --bin arch-ml`, переименованную копию бинаря
  (`cp arch-ml judge`) детектор не видит — путь судьи в команде не назван.
- **Сборка «своего» судьи.** Если бинарь ещё не собран (`cargo build --bin
  arch-ml && ./target/debug/arch-ml …`), путь назван внутри ворктри —
  детектор сообщает об этом (`missing = true`), но не разбирает, кто именно
  вызовет будущий бинарь.
- **Не видит содержимого гейта.** Гейт может звать `arch-ml` через
  промежуточный скрипт, который сам лежит вне ворктри.

## Числа

Проверяемого артефакта замера эффекта `debug = "line-tables-only"` в
репозитории нет, поэтому в комментарии `Cargo.toml` число СОЗНАТЕЛЬНО не
записано. Ранее там стояло «257 → 201 МБ (−22 %)» — эта цифра ничем не
подтверждалась и удалена. Отдельный разовый прогон уборки `target/` дал около
**−13.6 %** на диске, но это наблюдение на одной машине, а не воспроизводимая
методика; приведено лишь как ориентир порядка величины и не должно
тиражироваться как факт. Экономию собственно кэша (hit rate) смотрите в
`sccache --show-stats`.
