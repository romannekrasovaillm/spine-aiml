# ADR-042. Движок оркестрации флотов по паттернам: план как артефакт, детерминированный судья, resume из журнала

- Date: 2026-09-12
- Status: Accepted

## Context

Передача архитектуры в работу кодовым харнессам сегодня имеет ровно один
режим — плоский веер: handoff-пакет декомпозируется в work-items, и все items
гонятся одной волной (`src/fleet_run.rs::run_fleet`). Живой кейс
(`кейсы/fleet-of-ten`: 10 параллельных Claude Code, 10/10 `complete`, 42/42
тестов, 60/60 fitness) доказал, что веер работает. Но он же показал границы:

- **топология только одна.** Конвейер «спека → скелет → тесты → интеграция»,
  склейка N результатов, выбор лучшего из N попыток, пара «реализатор +
  независимый ревьювер» — выразить нечем: `WorkItem` (`src/router.rs:55`) не
  знает ни зависимостей, ни ролей, ни гейтов;
- **нет потолка конкурентности.** `run_fleet` делает `tokio::spawn` на каждый
  item без ограничения (`src/fleet_run.rs:562`): десять процессов — нормально,
  сотня — упор в память и в rate-limit провайдера, причём молча;
- **нет гейтов внутри прогона.** Проверки (`control check`, линт спайна,
  delta guard) запускает человек или сам агент после прогона; оркестратор о
  них не знает и не может остановить масштабирование по отказу;
- **нет возобновления.** `FleetLog` — append-only журнал событий
  (`src/fleet_run.rs:124`), но `fleet resume` не существует: упавший на
  середине прогон флота повторяется целиком.

При этом «умность» уже есть в правильном месте — в детерминированном слое:
роутер без LLM (`src/router.rs:1-4`), fitness-функции (`src/control.rs`),
owner-гейт мерджа («агент не аппрувит свой код», ADR-001/`docs/fleet.md`).
Не хватает одного слоя между декомпозицией пакета и запуском процессов.

## Decision

**1. Паттерн — сахар над одним DAG, а не восемь исполнителей.**
Восемь паттернов (`fanout`, `pipeline`, `map_reduce`, `tournament`,
`review_pair`, `ralph`, `walking_skeleton`, `dag`) компилируются в одну модель
`FleetPlan { nodes, edges, policy }`: компилятор достраивает недостающие узлы и
рёбра (`map_reduce` → узел `integrator` с `depends_on` = все worker;
`tournament` → узел `judge`; `review_pair` → узел `reviewer`;
`walking_skeleton` → `depends_on = [skeleton]` у остальных), после чего идёт
общий волновой прогон по топологическим уровням. `dag` — супермножество,
отдельного исполнителя не имеет.

**2. План — версионируемый артефакт передачи архитектуры в работу.**
TOML-канон (`<repo>/.arch-fleet/<plan-id>.plan.toml`), JSON/YAML принимаются.
Не в `.arch-handoff/`: тот перезаписывается `handoff_create` и по контракту не
коммитится, а план должен ревьюиться в PR. Состояние прогона — в доме
(`paths.state_dir/fleet/`), как журналы сейчас; рядом с журналом лежит снимок
резолвнутого плана, поэтому resume самодостаточен.

**3. Паттерн предлагает Spine, утверждает человек.**
`fleet plan propose` читает `.arch-handoff/MANIFEST.json` (route,
`recommended_timeout_secs`, sources) и CONSTRAINTS пакета, пересчитывает
значимость (`control::significance_score_with_limits`) и пишет план с
обоснованием. Автозапуска нет: топология — архитектурное решение, а не вывод
эвристики.

**4. Судья детерминированный.**
Гейт узла — механическая проверка после прогона: контракт результата
(`parse_result_contract`), fitness (`control::check`), линт спайна
(`control::lint_spine`), delta guard (`delta::guard`), объявленные артефакты,
детерминированная команда. LLM-вердикт принимается только как
`ReviewVerdict` (READY/NOT-READY) и только для **блокировки** мерджа — никогда
для выбора «лучшего кода». `tournament` выбирает первый узел группы, прошедший
все гейты; tie-break — лексикографически меньший id. Воспроизводимо и без
LLM в контуре решения.

**5. Конкурентность — пул с потолком, не «спавн на item».**
`tokio::sync::Semaphore(max_parallel)`; узлы сверх потолка ждут слота (событие
`NodeQueued`). Потолок — осознанное решение владельца (план/конфиг): флот из
сотен узлов исполняется, одновременных процессов может быть много меньше.
Отказ провайдера по лимиту (`retry::classify` → `RateLimit`) приостанавливает
выдачу слотов: реальный регулятор — провайдер, а не число воркеров.

**6. Resume — из журнала событий, идемпотентно по построению.**
`FleetEvent` только расширяется аддитивными вариантами (`PlanStarted`,
`WaveStarted`, `NodeQueued`, `NodeCompleted`, `NodeSkipped`, `NodeRetry`,
`NodeGated`, `RunResumed`, `RunHalted`); существующие варианты и поля не
меняются, старые журналы читаются. `FleetLog::read_tolerant` не роняет разбор
на неизвестном `type` или битой последней строке (процесс убит посреди
дописки). `fleet resume <run-id>` исключает завершённые узлы из расписания;
идемпотентность обеспечивается детерминированным именем worktree
`<run-id>-<node-id>`, а не «надеждой на удачу». Для прогонов без worktree
resume помечает узел небезопасным и требует явного `--force-rerun`.

**7. Ноль новых зависимостей.**
Топологическая сортировка (алгоритм Кана), детект цикла с путём и развёртка
паттернов пишутся вручную (~60 строк). `petgraph` не добавляется: в контуре с
`SECURITY.md`, `supply-chain.md` и `vendor/` зависимость ради одной операции
не оправдана.

## Alternatives Considered

**Отдельный исполнитель на каждый паттерн.** Проще написать первый, дальше —
восемь копий одного волнового цикла, восемь леджеров и восемь resume. Отказ:
дублирование логики в восьми местах — главный риск задачи, а `dag` всё равно
требует общего исполнителя.

**Автовыбор паттерна движком без человека.** Убрало бы шаг утверждения.
Отказ: топология зависит от границ компонентов и риска, которые знает
архитектор, а не эвристика по route; ошибка топологии дороже одного ревью
файла.

**Взять `petgraph`.** Меньше своего кода. Отказ: одна операция не окупает
зависимость в репозитории, который держит `vendor/` и SBOM.

**Хранить план в `.arch-handoff/`.** Рядом с задачей. Отказ: пакет
перезаписывается генератором и не коммитится — план будет затёрт и потерян
при ревью.

**Гейт как LLM-судья (`judge`-инструмент).** Гибче на «качестве». Отказ:
недетерминированный судья в контуре принятия решения о мердже противоречит
оси «принуждение, а не знание» и не воспроизводится между прогонами.

## Consequences

- Появляется единая точка передачи архитектуры в работу флоту:
  `fleet plan propose|validate|show` → `fleet run --plan` → `fleet resume` →
  `fleet merge --owner-approve`.
- `fleet run --items-file` (legacy-веер) и формат существующих журналов
  сохраняются: старый путь не ломается, регрессия зафиксирована золотым
  журналом в тестах.
- Гейты узла делают отказ видимым внутри прогона: `stop_on_gate_fail`
  останавливает масштабирование (walking skeleton), а не выясняется постфактум.
- Сотни узлов требуют дисциплины диска: worktree-на-узел переиспользуются по
  имени (`worktree::get_or_create`), чистка — через существующий `fleet audit`
  (рекомендация prune старше `PRUNE_AGE_DAYS`).
- Цена: `fleet_run.rs` (1530 строк) не растёт — новые модули `fleet_plan.rs`,
  `fleet_gate.rs`, `fleet_exec.rs`; в `fleet_run.rs` остаются события и ридер.

**Честные границы (не делает):** не декомпозирует пакет на узлы (это
архитектор/модель), не мержит в main (только `fleet merge --owner-approve`),
не судит качество LLM-судьёй, не enforce'ит область чтения ревьювера на уровне
ОС для subprocess-харнессов (для in-process субагента — whitelist
инструментов), не считает деньги (харнессы не рапортуют токены/₽ — бюджет
только в наблюдаемых единицах: `max_node_secs`, `max_attempts`,
`max_parallel`), не заменяет `fleet audit` как SSOT-аудит, не гарантирует
бесконфликтный resume (повторный прогон узла накапливает коммиты в ту же
ветку — конфликт решает владелец).

## Reversibility

Обратимо: план — надстройка, `run_fleet` и CLI-путь `--items-file` остаются
рабочими и не меняют сигнатур. Откат — удаление `fleet plan|resume` из CLI и
трёх модулей; журналы, записанные с новыми событиями, читаются старым кодом
толерантно только вперёд, поэтому откат версии безопасен для уже завершённых
прогонов (неизвестные события в новых журналах старый `read_all` не разберёт —
инвариант «журнал пишет и читает одна версия» зафиксирован в тестах).
