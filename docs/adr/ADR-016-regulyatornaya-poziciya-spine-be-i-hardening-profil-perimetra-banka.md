# ADR-016. Регуляторная позиция Spine BE и hardening-профиль периметра банка

- Date: 2026-08-31
- Status: Accepted

## Context

Владелец: «проверить нормативку ЦБ РФ для Spine и усилиться, чтобы
регулятор нас не взломал» — т.е. продукт должен (а) не создавать банку
нарушений на проверке, (б) помогать банку проходить надзор.

Ограничение честности: веб-доступ к первоисточникам (cbr.ru, консультант)
в сессии проектирования недоступен (поиск и fetch не отдают контент).
Поэтому нормативная база фиксируется как **гипотезы с протоколом
верификации** (`banking/compliance/reg-map.md`), а не как проверенные
факты. Ничего регуляторного не утверждается по памяти.

Факты самопроверки продукта (машина, grep по коду, 2026-08-31):

- Исходящие каналы ровно два: LLM-провайдеры (`src/llm/openai_compat.rs`,
  base_url из `[models.*]`) и веб-поиск/феч (`src/web.rs`,
  `html.duckduckgo.com` по умолчанию + произвольные URL web_fetch).
- Телеметрии, бэконов и автообновлений **нет** (grep пуст).
- MCP — локальные stdio-процессы; образец `examples/mcp.example.json`
  тянет серверы из публичных регистров (npx/uvx) — образец, не продукт.
- **GAP-C1**: у `[web]` нет флага выключения — веб-инструменты
  доступны агенту всегда; в контуре ДИТ это периметр-риск.
- **GAP-C2**: ГОСТ TLS (криптография по ГОСТ, часто обязательна в
  контуре банка к внутренним сервисам): reqwest с rustls-tls ГОСТ-TLS
  не поддерживает — потенциальный блокер для GigaChat on-prem, если
  шлюз требует ГОСТ-TLS [ТРЕБУЕТ ПРОВЕРКИ: требования конкретного
  контура заказчика].

## Decision

**1. Регуляторная позиция**: Spine BE — инструмент проектирования ДИТ,
не банковская информационная система и не объект прямого надзора ЦБ.
Надзор проверяет банк; наш продукт обязан (а) не создавать банку
новых нарушений (периметр данных, egress, аудит), (б) давать банку
evidence-артефакты для надзорных вопросов (трассируемость, ADR,
fitness, журнал — сильная сторона ядра). Формула для ДИТ: «инструмент,
который не выводит ничего за периметр и документирует каждое решение».

**2. Hardening-профиль периметра банка** — продуктовый артефакт
`banking/presets/bank-profile/`:

- `config.toml` — шаблон: только внутренние LLM base_url
  (placeholder), веб-канал не используется (search_base заглушен
  внутренним адресом, домены поиска исключены), MCP только внутренние
  серверы, политика автономии консервативная.
- `mcp.json` — шаблон без публичных регистров (никаких npx/uvx —
  только вендоренные/внутренние серверы).
- README — что профиль закрывает, что НЕ закрывает (GAP-C1: полное
  выключение веб-инструментов требует кодовой правки — backlog через
  handoff, T1-конвейер ADR-015), как применять.

**3. Регуляторная карта** `banking/compliance/reg-map.md` — живой
артефакт: документ → гипотеза применимости → ответ Spine BE →
evidence → владелец верификации → статус `[ТРЕБУЕТ ПРОВЕРКИ]`.
Ни одна строка не считается фактом до верификации по первоисточнику;
верификация — обязательный шаг волны 2 (T2) и предпродажной подготовки.

**4. Инвариант AD-BE5 (egress-дисциплина)**: в продуктовых пресетах
banking/ — только внутренние endpoint'ы; веб-канал по умолчанию
заглушен в банк-профиле; появление внешнего URL в пресете — error
фитнес-правилом. GAP-C1 закрыт 2026-08-31: флаг `[web].enabled`
(реализация — theseus через handoff-конвейер, гейты прогнаны
архитектором: fmt/clippy -D warnings/612 тестов зелёные) — при false
веб-инструменты не регистрируются в сессии; банк-профиль переведён на
флаг. Открыт GAP-C1b: CLI/слэш-команды веб-канала минуют реестр
(находка theseus) — в handoff-очереди.

- Update 2026-08-31 (вечер): регуляторное ядро верифицировано и
  скорректировано субагентской разведкой — 683-П утратил силу (замена
  **851-П** от 30.01.2025, карта `cbr-851p.md`, официальный скан в
  `banking/compliance/evidence/`); «682-П» не существует (конфабуляция,
  R-03 закрыт); 152-ФЗ и материалы ЦБ об ИИ верифицированы (R-01/R-07);
  PAY-27 мигрирован на 851-П. См. ADR-017.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Позиция «не объект надзора» + hardening-профиль (принято)** | честно и проверяемо; закрывает реальные риски (egress, регистры, телеметрия); evidence-сила ядра — готовый аргумент для ДИТ | регуляторика остаётся гипотезами до верификации волны 2 |
| Спроектировать полный compliance-контур ЦБ сейчас | максимум готовности к проверке | первоисточники недоступны; любое утверждение по памяти — риск фабрикации; нарушает дисциплину честности |
| «Регулятор проверяет банк, не нас — ничего не делать» | ноль затрат | вендорский инструмент, создающий утечки/риски, — репутационная мина первой продажи; отвергнуто владельцем («усилимся») |
| Перенести всё на заказчика (в спросе: «банк сам обеспечит контур») | вендор не отвечает | слабая продажная позиция: ДИТ ждёт от вендора готовый безопасный профиль |

## Consequences

### Positive

- Периметр закрывается конфигом уже сейчас (данные, без кода):
  внутренние LLM, заглушенный поиск, внутренние MCP-серверы,
  консервативная автономия.
- Отсутствие телеметрии — проверяемый факт (grep) — продающий
  аргумент для ДИТ.
- Reg-map делает регуляторную работу измеримой: каждая строка имеет
  владельца верификации и статус.

### Negative

- GAP-C1 (выключатель веб-инструментов) до кодовой правки —
  профили закрывают канал конфигом частично; риск: агент в контуре
  попытается позвонить наружу и получит таймаут (шум в журнале, не
  утечка). Кодовая правка — в очереди handoff (после ADR-015 T1
  конвейера).
- GAP-C2 (ГОСТ TLS) — если контур заказчика требует ГОСТ-канал к
  LLM-шлюзу, потребуется другой TLS-стек или прокси-решение —
  архитектурное решение откладывается до реального требования
  [ТРЕБУЕТ ПРОВЕРКИ].
- Регуляторные гипотезы (682-П, 187-ФЗ, 152-ФЗ, 115-ФЗ, ГОСТ-СКЗИ)
  не верифицированы — пока не верифицированы, в продажных материалах
  не цитируются как требования, только как «карта для совместной
  проработки с вашим ИБ».

## Reversibility

**reversible**: позиция и профиль — документы и конфиг-шаблоны; кодовые
GAP'ы закрываются инкрементально через handoff. Смена позиции (например,
сертификация СКЗИ) — отдельное решение при реальном требовании рынка.
