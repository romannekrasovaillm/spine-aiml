# ADR-013. Open-core лицензирование: src/ — MIT-ядро, banking/ — проприетарная надстройка по договору

- Date: 2026-08-31
- Status: Accepted

## Context

Spine BE — форк MIT-проекта (ADR-010), продаваемый ДИТ банков. Модель
монетизации — лицензии на проприетарную часть + услуги внедрения. Выбор
лицензионной модели сделан владельцем продукта: **open-core (dual)**.

Ограничения, с которыми считаемся:

- **Переносы патчей апстрима** (ADR-010): чем больше proprietary-правок
  в унаследованных файлах, тем дороже каждый перенос и выше риск
  лицензионной ошибки.
- **Дисциплина Fast-маршрута** (POLICY.md апстрима): данные/конфиги
  архитектор правит сам, исполняемый код — только через кодовый харнесс.
- **Дифференциация продукта** — не код адаптеров, а методика:
  compliance-рубрики (152-ФЗ, КИИ, требования ЦБ), пресеты CONSTRAINTS
  под банковские домены, поставочная документация.
- ADR-011: идентификаторы кода не переименовываем, crate/binary `arch`.

## Decision

**Open-core dual licensing с границей по директориям**:

- **Ядро (MIT, файл `LICENSE` — унаследованный)**: вся `src/`, `tests/`,
  `benches/`, `docs/`, `кейсы/`, `examples/`, `assets/` — унаследованные
  файлы + патчи апстрима + новый Rust-код (включая будущий GigaChat-адаптер,
  ADR-012). Весь исполняемый код остаётся открытым.
- **Банковская надстройка (proprietary, файл `LICENSE.banking`)**: новая
  директория `banking/` — compliance-рубрики, пресеты CONSTRAINTS под
  регуляторику, методика внедрения в ДИТ, демо-кейсы поставки,
  коммерческая документация. Только данные и документы, без Rust-кода.
  Поставляется банкам по лицензионному договору; исходники надстройки —
  заказчику по договору поставки.

Гигиена границы — двумя проверяемыми правилами (кандидаты в CONSTRAINTS
форка при заведении продуктового контура):

1. Каждый файл `banking/**` несёт заголовок proprietary-лицензии
   (машино-проверяемо: must_contain regex).
2. `src/` не импортирует/не читает `banking/` на этапе сборки — ядро
   собирается и работает без банковской зоны (проверка сборкой в CI).

До первой продажи текст `LICENSE.banking` — рабочий шаблон; обязателен
юридический обзор перед подписанием первого лицензионного договора.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Open-core: src/ MIT + banking/ proprietary (принято)** | патчи апстрима падают в MIT-зону без лицензионных конфликтов; граница совпадает с код/данные (Fast-дисциплина); ядро открытости — доверие ДИТ; GigaChat-адаптер в ядре упрощает интеграцию заказчика | GigaChat-адаптер и весь код открыты — копируемы конкурентами (ценность смещена в banking/-методику); нужен CI-контроль границы |
| Полностью закрытая поставка | максимальный контроль | пофайловая лицензия внутри src/ (апстрим-MIT + proprietary) запутывает переносы патчей и NOTICE-гигиену; ниже доверие |
| MIT на всё + монетизация услугами | нулевая лицензионная работа | банк разворачивает сам без вендора; лицензии ДИТ не продаются — модель отвергнута владельцем |
| Proprietary-код в src/ (GigaChat-адаптер закрыт) | техническая дифференциация кодом | ломает чистую границу: переносы патчей апстрима в закрытые файлы конфликтуют; адаптер API — слабая коммерческая ценность против методики |

## Consequences

### Positive

- Чистая, проверяемая граница: лицензия определяется путём файла,
  никаких пофайловых смешений внутри директорий.
- Перенос улучшений апстрима (ADR-010) затрагивает только MIT-зону —
  механически дёшево.
- Ядро можно показывать на демо и аудитах ДИТ без NDA на исходники;
  коммерческая ценность (banking/) защищена.
- Граница совместима с Fast-дисциплиной: banking/ — данные/документы,
  правятся архитектором напрямую.

### Negative

- Конкурент может собрать «Spine + своя банковская надстройка» на
  открытом ядре; защита — бренд, методика, актуальность compliance-зоны,
  первенство на рынке (принятый риск, владелец продукта в курсе).
- Дисциплина CI-границы обязательна: забытый proprietary-файл в src/
  (или наоборот) — лицензионная дыра; митигируется fitness-функциями
  из Decision.
- `LICENSE.banking` до юр-обзора — шаблон, не договор: первая продажа
  блокируется на юр-обзор (календарный риск, назначить сразу при первом
  лиде).

## Reversibility

**costly**: после первых продаж смена модели лицензирования —
пересогласование с клиентами. Смена границы (перемещение файла между
зонами) — reversible до продажи, с проверкой истории файла.
