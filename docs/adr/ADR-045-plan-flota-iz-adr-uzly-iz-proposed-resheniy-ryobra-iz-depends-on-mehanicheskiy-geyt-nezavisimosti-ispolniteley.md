# ADR-045. План флота из ADR: узлы из proposed-решений, рёбра из depends_on, механический гейт независимости исполнителей

- Date: 2026-09-13
- Status: Accepted

## Context

Дисциплина spine требует проверяемого правила: «могут ли две единицы уровнем ниже, построенные независимо, разойтись несовместимо?» Если да — это связывает (AD-n), если нет — Deferred. Сегодня этот вопрос решает человек, глядя на список работ.

Цена видна на факте 13.09.2026: два потока независимо правили один и тот же TUI-слой и одни и те же документы (`src/tui/app.rs`, `src/tui/render.rs`, `docs/tui.md`) — 62 файла оказались в основном дереве одновременно, версии разошлись, и расхождение нашлось глазами (сравнением хешей и текстов), а не гейтом. Ни один существующий механизм этого не поймал: `fleet audit` ловит дубли **копий спайна** между worktree, `delta guard` — прямые правки спайна мимо дельты, `control spine` — структуру инвариантов.

Что уже есть в харнессе и переиспользуется:
- `FleetPlan` (ADR-042): узел несёт `spec`, `spec_files` (источники epic-context), `outputs` (ожидаемые артефакты-выходы), `depends_on` (рёбра), `route`, `domain`, `effort`; паттерн `dag` — «произвольный граф зависимостей»;
- `validate_plan` — механический гейт плана (сейчас: пустой план, `max_parallel = 0`, компиляция графа, ёмкость);
- `arch-ml fleet plan propose` — черновик плана из одного handoff-пакета (`.arch-handoff/MANIFEST.json`);
- типизированная модель (ADR-003): карточки `model/**/*.md` с YAML-frontmatter `id`, `type`, `status`, `depends_on`, `affects`, `verified_by`.

Не хватает двух вещей: (1) способа вывести план работ **из набора решений**, а не из одного пакета; (2) механического критерия «эти две работы нельзя вести параллельно, они разойдутся».

## Decision

1. **Новый режим предложения плана:**
   `arch-ml fleet plan propose --from-adrs [--adr-dir <каталог>] [--status proposed|accepted|all] [--pattern dag] [--out <каталог>]`

   - Источник по умолчанию — `docs/adr`; отбор по статусу — по умолчанию `proposed` (реализованные решения планировать не нужно; `all` — для аудита и ретроспективы).
   - Один узел на один ADR: `id` — нормализованный `adr-NNN`; `spec` — задание «реализовать решение» с заголовком и ссылкой на файл; `spec_files` — путь самого ADR плюс объявленные в frontmatter источники; `outputs` — объявленные `affects` (затрагиваемые идентификаторы/пути); `route`/`domain` — из frontmatter, иначе дефолты маршрута.
   - `depends_on` узла — из одноимённого поля frontmatter ADR (нормализация: `ADR-005` → `adr-005`); ссылка на ADR вне отбора не ошибка (зависимость может быть уже принята), но даёт предупреждение «зависимость вне плана».
   - Паттерн по умолчанию для режима — `dag`; `--pattern` переопределяет.

2. **Формат метаданных ADR.** Читается YAML-frontmatter; поля: `id`, `title`, `status`, `depends_on`, `affects`, `spec_files`, `route`, `domain`. Для ADR без frontmatter допускается фолбэк: `id`/`title` из строки `# ADR-NNN. <title>`, `status` из строки `- Status:`; в этом случае узлу выдаётся предупреждение «ADR без frontmatter: зависимости не видны» — деградация не должна быть тихой.

3. **Механический гейт независимости** — правило плана, исполняется в `validate_plan` для **любого** плана (не только собранного из ADR), потому что рукописные планы правятся людьми и обязаны проходить тот же контроль:
   для любой пары узлов, между которыми нет пути в графе зависимостей (достижимость в неориентированном смысле — прямой или транзитивный `depends_on` в любую сторону):
   - непустое пересечение **затрагиваемых путей** (`outputs`, они же объявленные `affects`) → **error** плана: «два независимых исполнителя затрагивают один путь»; диагностика называет обе стороны, пересечение и подсказку (добавить `depends_on` либо развести пути);
   - непустое пересечение **путей чтения** (`spec_files`) → **warn** (совместное чтение одного источника к расхождению не ведёт).

4. Критерий самоприменим: на этом репозитории `--from-adrs --status proposed` обязан построить план из ещё не принятых решений (например, ADR-044/ADR-045), а гейт — отказать, если два независимых решения объявили запись в один путь.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Режим `--from-adrs` + правило в `validate_plan` (принято)** | один контракт для выведенных и рукописных планов; критерий проверяем механически; переиспользует `dag`, `depends_on`, `outputs` | требует актуального frontmatter у ADR; трактовка `affects` как путей записи нуждается в явной фиксации |
| Проверять пересечения только в момент `propose` | дешевле | план правят руками после генерации — гейт обходится по умолчанию; критерий перестаёт быть инвариантом |
| Считать строгим и пересечение `spec_files` | проще формулировка, единое правило | два решения, опирающиеся на одну спеку/стандарт, — частый и безопасный случай; ложные отказы обесценивают гейт |
| Новое поле узла `affected_paths` | точное имя под смысл | дубль `outputs`, ещё один способ объявить одно и то же; расхождение определений — источник ошибок |
| Парсить зависимости из тела ADR (проза) | работает без frontmatter | зависимости, выведенные регуляркой из прозы, — выдумывание связей; ложные рёбра хуже их отсутствия |
| Статус-кво: решает человек по списку работ | ноль работы | факт 13.09.2026: два потока разошлись на 62 файлах, расхождение нашлось глазами |

## Consequences

### Positive

- Механический критерий независимости: пара работ без общего предка, пишущая в один путь, не может стартовать параллельно — расхождение ловится **до** прогона, а не глазами после.
- Набор proposed-решений превращается в граф работ: план перестаёт зависеть от того, собран ли handoff-пакет.
- Гейт стоит на плане (а не на генераторе), поэтому рукописные планы контролируются тем же правилом.

### Negative

- Появляется обязанность держать frontmatter ADR актуальным: без него зависимости не видны, узлы вырождаются в не связанные — гейт слабеет (митигация: предупреждение «ADR без frontmatter»).
- `affects` в модели означает «затрагивает сущность» (например, `CMP-004`), а не обязательно файл; трактовка «затрагиваемые пути» — соглашение, а не факт (митигация: фиксируется в этой ADR и в `docs/fleet.md`; сравнение по строкам).
- Возможны ложные срабатывания: два независимых решения legitimately затрагивают один агрегат, не записывая в один файл. Цена выбрана сознательно: пропущенное расхождение дороже лишнего ребра.
- Ещё один режим в CLI и ещё одно правило валидации — рост поверхности `fleet`, требующий строки в README и `docs/fleet.md`.

## Reversibility

**reversible**: режим — аддитивный флаг `propose`; правило живёт в `validate_plan` и снимается одним коммитом без миграций. Уже построенные планы остаются валидными (правило касается только пар без пути с общими путями).
