# ADR-034. Калибровка значимости: механический floor, anti-bypass, пороги в конфиг, статус гипотезы

- Date: 2026-09-04
- Status: Accepted

## Context

Маршрутизатор значимости (Fast/Standard/Critical) работает с момента
введения `significance_score`, но два разрыва видны механически:

1. **Пороги захардкожены.** Границы «0–1 → Fast, 2–4 → Standard, 5+ →
   Critical» — эвристика из обзора AI-Disrupt PDLC (`docs/SOURCE_BRIEF.md`
   §C.3), зашита в код. Калибровка под профиль банка (например, более
   осторожная граница Fast/Standard для платёжного домена) требовала правки
   `src/control.rs` — то есть изменения детерминированного слоя ради
   политики, которая по природе своя у каждого периметра.
2. **Заявленные триггеры — только честность автора.** `control score
   --trigger …` принимает ответы на веру: автор изменения может занизить
   множество триггеров (случайно или осознанно) и увести изменение на Fast
   Path мимо гейта A3. Ни одного механического сигнала «дифф противоречит
   заявленному» не было.

При этом статус самих порогов 1/2/5 честно неизвестен: это рабочая гипотеза,
не калиброванная на данных. Любая «настройка по месту» без разметки кейсов
рискует стать подгонкой под вкус.

## Decision

**1. Пороги — в конфиг, статус «рабочая гипотеза».** Секция
`[significance]` в `config.toml` (`src/config.rs::SignificanceConfig`):
`fast_max` (дефолт 1), `standard_max` (дефолт 4). Маршрут: score ≤
`fast_max` → Fast, ≤ `standard_max` → Standard, выше → Critical. Дефолты
воспроизводят историческое поведение 1/2/5 — обратная совместимость тестов
и всех потребителей (`significance_score` делегирует в
`significance_score_with_limits` с дефолтами). Значения 1/2/5 фиксируются
как **рабочая гипотеза с пересмотром при первых данных пилота**, а не как
калиброванная константа. Валидация мягкая: `fast_max >= standard_max` —
понятная ошибка при чтении в `control score` / инструменте
`significance_score`, а не при загрузке конфига (конфиг с временно
невалидной секцией не ломает остальные команды).

**2. Форсирующие critical-триггеры — вне конфигурации (fail-safe).**
`security_boundary_change`, `irreversible_migration`,
`criticality_or_exception` дают Critical при ЛЮБЫХ порогах и не
конфигурируются: границу безопасности и необратимость нельзя
«откалибровать вниз» ни политикой, ни ошибкой конфига.

**3. Anti-bypass floor: `control score --from-diff [GIT_REF]` (S-1).**
Механический вывод триггеров из git-диффа (`git diff --name-status` +
патч; без значения — рабочее дерево против `HEAD` включая untracked, со
значением — `GIT_REF...HEAD`): новый компонент (манифест/`src/` в новом
каталоге), новый вендор (строка зависимости в манифесте), смена
API-контракта (файл `openapi`/`asyncapi`), необратимая миграция
(`DROP TABLE`/`TRUNCATE`/`DROP COLUMN` в `migrations/`/`*.sql`), новое
хранилище (строка подключения в конфиге). Семантика fail-safe: детектор
**только добавляет** триггеры к заявленным `--trigger` (объединение
множеств), маршрут считается по объединённому. Расхождение «заявлено vs
видно по диффу» печатается warn-секцией с источником каждого триггера
(`(declared)`/`(diff)`/`(declared+diff)`) — на exit code не влияет:
floor — сигнал, а не новый гейт.

**4. Формат разметки кейсов зарезервирован.** Для будущей калибровки
порогов по данным резервируется формат `significance-cases.yaml` (кейс →
триггеры → ожидаемый маршрут → источник решения A3). В этой итерации
**не реализуется**: нет размеченного корпуса, а пороги уже объявлены
гипотезой — преждевременный формат зафиксировал бы структуру до первых
реальных данных.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Пороги в `[significance]` + from-diff floor (принято)** | политика отделена от детерминированного слоя; дефолты = статус-кво; механический сигнал против занижения триггеров | детекторы диффа — текстовые эвристики с ложными срабатываниями (принимаем: fail-safe только расширяет множество) |
| Пороги в CONSTRAINTS.yaml | единый файл правил | CONSTRAINTS — реестр fitness-проверок репозитория, а пороги значимости — политика периметра/пользователя; смешение зон |
| LLM-оценка диффа для триггеров | семантика глубже текстовых эвристик | нарушает AD-2 (детерминированный слой контроля — без LLM); недетерминизм в маршрутизации |
| Реализовать significance-cases.yaml сразу | формат готов к пилоту | нет разметки; структура файла зафиксировалась бы до данных |
| from-diff как гейт (exit 1 при расхождении) | жёсткий anti-bypass | ложные срабатывания эвристик блокировали бы легитимные изменения; warn-сигнал дешевле и безопаснее для внедрения |

## Consequences

### Positive

- Пороги маршрутизации — данные конфига, а не код: банк калибрует
  Fast/Standard под свой риск-профиль без патча ядра.
- Занижение триггеров автором впервые видно механически — warn-секция
  «заявлено vs дифф» годится для аудита и разборов.
- Дефолты 1/2/5 прозрачно объявлены гипотезой: пересмотр по данным
  пилота — ожидаемое событие, а не признание ошибки.
- Обратная совместимость полная: без `[significance]` и `--from-diff`
  поведение идентично прежнему (тесты на дефолты это фиксируют).

### Negative

- Эвристики дифф-детекторов ложно срабатывают (добавление файла в
  существующий `src/` читается как `new_component`; любая `kafka`-строка в
  конфиге — как `new_datastore`). Цена — шум в warn-секции; маршрут при
  этом смещается только в более строгую сторону (fail-safe), что и требуется.
- Пороги теперь различаются между инсталляциями: сравнение маршрутов
  между периметрами требует учёта их `[significance]`.
- Зарезервированный `significance-cases.yaml` — обещание, а не механика:
  калибровка гипотезы зависит от дисциплины разметки кейсов пилота.

## Reversibility

**reversible.** Удаление `[significance]` из конфига возвращает дефолты
1/4; отказ от `--from-diff` не меняет существующий CLI-контракт (флаг
опциональный, вывод без него побайтово прежний). Форсирующие
critical-триггеры и fail-safe объединение не имеют «обратного хода вниз»
по замыслу — это свойство, а не ограничение.
