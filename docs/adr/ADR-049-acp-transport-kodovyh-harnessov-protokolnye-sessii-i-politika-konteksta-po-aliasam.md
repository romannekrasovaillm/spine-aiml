# ADR-049. ACP-транспорт кодовых харнессов: протокольные сессии вместо «чёрного ящика», продолжение контекста только по имени-алиасу

- Date: 2026-09-23
- Status: Accepted

## Context

Процессный транспорт прогона кодового харнесса (`run_harness`) видит
исполнителя как чёрный ящик: задача уходит через argv/stdin, ответ читается
из stdout по итогу. Два системных последствия:

- **Мутность.** Во время прогона (минуты) не видно, что исполнитель делает:
  ни tool-вызовов, ни плана, ни расхода контекста. Живой «хвост» stdout —
  сырой поток без структуры, у части харнессов в headless он пуст до конца.
- **Потеря контекста.** Каждый прогон — новый процесс с нулевой памятью:
  многошаговая работа (разбор → правка → ревью) вынужденно передаёт контекст
  через файлы репозитория, а не через диалог.

Оба пробела закрывает Agent Client Protocol v1 (ndjson JSON-RPC 2.0 поверх
stdio): живые `session/update` (текст, мысли, tool_call, plan, usage_update),
`session/resume` (контекст между прогонами), структурные
`session/request_permission`. Поддержка подтверждена живым handshake:
`kimi acp` отвечает `initialize` полным набором
`sessionCapabilities{list,resume,close,delete,fork}`.

При этом «всегда сохранять контекст» — не цель: независимые проверки
(ревью, повторная оценка) обязаны стартовать с чистым листом, иначе
субагент-ревьювер наследует предвзятость автора. Нужна явная политика,
когда контекст продолжается, а когда нет.

## Decision

1. **Новый транспорт адаптера: `transport = "acp"` в `[harnesses.*]`.**
   Запуск: `binary` + `args` как есть (для kimi — `["acp"]`); задача уходит
   `session/prompt`, `prompt_mode` в ACP-режиме не применяется. Прогон =
   один ход сессии: `initialize` → `session/new`|`session/resume` →
   `session/prompt` → (по исходу) `session/close` + гашение процессной
   группы. Код возврата проецируется из `stopReason` хода, а не из статуса
   убитого сервера. Клиент hand-rolled (tokio process + serde_json) —
   новых зависимостей нет (fitness `no-new-dependencies`).

2. **Входящие запросы агента — fail-closed.** Агент вправе спрашивать
   клиента (`session/request_permission`, `fs/*`, `terminal/*`) и ЖДАТ
   ответа; молчание — дедлок. Клиент декларирует fs/terminal
   неподдерживаемыми; неизвестные входящие запросы получают JSON-RPC
   ошибку `-32601`. Разрешения — политикой `acp_permission`:
   `readonly_auto` (дефолт: `read`/`search`/`think`/`fetch` — allow_once,
   остальное и неизвестное — reject_once), `deny`, `allow_all`.

3. **Политика контекста: свежая сессия — дефолт, продолжение — только по
   имени-алиасу.** Без `acp_session` каждый прогон открывает `session/new`.
   С `acp_session = "<алиас>"` — семантика «возобновить-или-создать»:
   первый прогон открывает новую сессию и запоминает её за алиасом
   (карта `харнесс/алиас → {sessionId, runs}` в
   `state/acp-sessions.json`, атомарная запись tmp+rename), следующие —
   `session/resume`. Мёртвая/чужая сессия или агент без
   `sessionCapabilities.resume` — НЕ ошибка прогона, а новая сессия с
   явной пометкой в логе. Факт выбора виден всегда: строка
   `[acp] session: <id> (свежая | возобновлена, алиас '<a>', прогон #N |
   новая вместо недоступной …)`. TTL и автоочистки нет: алиас живёт, пока
   агент помнит сессию; смена алиаса — осознанный сброс.

4. **Проекция обновлений без смешения каналов.** Текст ответа
   (`agent_message_chunk`) собирается в `stdout` прогона — разбор
   контракта результата, отчёты и авто-коммит работают без изменений.
   Tool-вызовы, план, usage_update, мысли (усечённо) — в `stderr` прогона
   (per-agent лог флота): stdout остаётся чистым для контракта.

5. **Таймауты и отмена зеркалят процессный режим.** Абсолютный потолок
   `timeout_secs`, тишина `idle_timeout_secs` (активность = любой входящий
   ACP-кадр ИЛИ свежие mtime репозитория). Прерывание: `session/cancel` →
   грейс 5 с → уничтожение процессной группы (сирот нет, как у
   процессного транспорта).

## Alternatives Considered

- **Крейт `agent-client-protocol`.** Отклонён: новая зависимость запрещена
  fitness-правилом `no-new-dependencies`; нужный поднабор (initialize,
  session/*, диспетчер входящих запросов) — ~300 строк на tokio+serde_json.
- **MCP.** Направление не то: MCP — сервер инструментов, ACP — клиентский
  протокол управления агентом (сессии, ход, разрешения).
- **Флаги resume конкретных CLI** (`claude --continue` и т.п.) поверх
  процессного транспорта. Отклонено: у каждого харнесса своё имя флага и
  своя семантика идентификатора сессии, единой политики алиасов не
  получить; живой видимости хода это не даёт вовсе.
- **Resume по сырому sessionId, подставляемому в конфиг вручную.**
  Отклонено как UX: id длинный и немнемоничен, перепутать чужую сессию —
  типовая ошибка. Алиас — человекочитаемое имя, привязка к sessionId —
  механическая (карта в state).

## Consequences

Плюсы: живой структурный ход прогона (tool/plan/usage в логе флота и
TUI-хвосте); продолжение контекста многошаговых задач по имени; свежие
субагенты остаются дефолтом — предвзятость между независимыми прогонами не
наследуется; разрешения агента отвечаются детерминированной политикой,
дедлока на промпте нет.

Минусы/стоимость: ручная поддержка подмножества протокола (новые варианты
`session/update` попадают в `Other` без потери хода); ACP умеет не каждый
харнесс (адаптеры без `transport` продолжают работать процессным режимом);
метрик KV-кэша в протоколе нет — `usage_update` несёт лишь used/size/cost.
Дополнение 2026-09-23: кэш-метрика своих агентов реализована через
`_meta.cached_tokens`/`_meta.prompt_cache_hit_tokens` в `usage_update` —
клиент показывает `кэш N (NN% hit)` в строке usage.

## Reversibility

Транспорт опционален и включается per-адаптер одной строкой конфига;
удаление — обратимая операция (модуль `src/acp.rs`, ветка в
`run_harness_inner`, три поля `CodingHarnessConfig`). Карта сессий —
данные в `state/`, удаление файла равносильно сбросу алиасов.
