# ADR-047. Роутинг гипотез по фактам проекта: доменные хуки плагинов, карточки HYPOTHESIS.md, поля skills/hypotheses в MANIFEST и сенсор hypothesis_hit

- Date: 2026-09-13
- Status: Accepted

## Context

Библиотека домена растёт (~1000 скиллов, ~170 плагинов). Отбор по
`description` работает для активных наборов и не работает для латентных
личных: им не с чем конкурировать в общем поиске, а контекстная инженерия
решает, что положить в окно, но не решает, из чего выбирать и когда
вспомнить. Не хватает двух вещей: памяти о намерении с жизненным циклом и
**роутинга по фактам проекта** — карточка должна всплывать не потому, что
модель угадала по описанию, а потому что в репозитории лежит нужный файл,
ключ конфига, зависимость или слово задачи (свидетельство в репо уже есть).

Что уже есть в харнессе и что показал разбор исходного артефакта
(`aiml/plugins/hypothesis-router` + `aiml/plugins/laguna-gb10-skills`):

- **Механизм хуков привязан к событиям инструментов.** `hooks/hooks.json`
  объявляет команды `PreToolUse`/`PostToolUse`/… и исполняется при
  `plugins.include_hooks = true`. Доменных событий (`intent`,
  `pre_handoff`, `post_accept`, `library_changed`) в ядре нет.
- **Манифест плагина** (`src/plugin.rs`, `PluginManifest`) знает только
  `name`/`version`/`description`/`keywords`; поля `hooks` в схеме не было.
- **`Manifest` handoff-пакета** (`src/harness.rs`) не имеет полей `skills` и
  `hypotheses`; `generate_handoff` хуков не зовёт.
- **Детектор значимости** `detect_diff_triggers` (`src/control.rs`) — пять
  захардкоженных эвристик; внешнюю таблицу триггеров он не читает.
- **Fitness-контур плагина не совпадает со схемой движка**: артефакт
  объявляет `description` + `check: {command_succeeds: …}`, движок ждёт
  `name` + `type: command_succeeds` + `command:`, подстановок
  `{handoff_dir}`/`{project_name}` в движке нет.

Следствие для исходного артефакта: тезис черновика «через **существующий**
механизм плагин-хуков» неверен — существующий механизм привязан к событиям
инструментов, а доменные события вводятся этим решением впервые, как
отдельный канал. Также зафиксирован дефект артефакта: фраза намерения
«хочу обучить 3B на Spark» **не поднимает** карточку — слова матчатся по
границе токена (`(?<!\w)…(?!\w)`), а в списке слов карточки нет ни «3B», ни
«Spark». Критерий приёмки требует, чтобы эта фраза карточку поднимала.

## Decision

1. **Новый модуль `src/hypothesis.rs`** (объявлен в `src/lib.rs`) —
   доменные хуки плагинов, отдельный от инструментного канала `src/hooks.rs`:

   ```rust
   pub struct DomainHook { pub plugin: String, pub event: String,
                           pub program: PathBuf, pub prefix: Vec<String> }
   pub struct DomainHookOutcome { pub plugin: String, pub event: String,
                                  pub code: i32, pub line: String }
   pub fn domain_hooks(plugin_dirs: &[PathBuf]) -> Vec<DomainHook>;
   pub fn run_hook(hook: &DomainHook, args: &[&str], cwd: &Path,
                   env: &[(String, String)]) -> DomainHookOutcome;
   pub fn run_event(plugin_dirs: &[PathBuf], event: &str, args: &[&str],
                    cwd: &Path) -> Vec<DomainHookOutcome>;
   ```

   `domain_hooks` читает `<plugin>/plugin.json` → `hooks:
   {"<event>": "<команда с аргументами>"}`; первый токен резолвится от
   каталога плагина, остальные становятся `prefix`; хук берётся, только если
   файл существует. `run_hook` запускает `program + prefix + args` в `cwd` с
   унаследованным окружением плюс `env`, таймаут 5 с, stdout усекается до
   **первой** строки. Ненулевой код, таймаут и сбой запуска **не блокируют**
   вызывающего: они возвращаются в `DomainHookOutcome` (`code = -1` при
   таймауте/сбое запуска, причина в `line`). `run_event` исполняет все хуки
   события с окружением процесса харнесса (`std::env::vars`). Обход
   детерминирован: каталоги и имена плагинов — по возрастанию пути, события —
   по алфавиту (`BTreeMap`).

2. **Манифест плагина получает поле `hooks`** (`BTreeMap<String, String>`).
   Это единственная правка схемы `PluginManifest`; `fitness`, `commands`,
   `env`, `skills`, `deterministic`, `requires_llm` из артефакта ядром не
   читаются и в схему не входят.

3. **Доменному слою — три точки вызова** (без LLM, без зависимости ядра от
   плагина): `intent` (на входе первого контура, текст намерения),
   `pre_handoff` (при `handoff_create`, до записи MANIFEST — пишет
   `<handoff>/HYPOTHESES.json`), `post_accept` (при принятии worktree —
   касание карточек из HYPOTHESES.json), `library_changed` (пересборка
   `$HYPOTHESES_DIR/routing.json`). Контракт кода выхода — 0/2/3; ядро его не
   интерпретирует, а возвращает наружу.

4. **`MANIFEST.json` получает поля** `skills: Option<Vec<String>>`
   (`skip_serializing_if = "Option::is_none"`) и
   `hypotheses: Vec<HypothesisRef>` (`skip_serializing_if = "Vec::is_empty"`),
   где `HypothesisRef { card: String, state: String, score: u32,
   skills: Vec<String> }`. Источник — `hits[]` файла
   `<handoff>/HYPOTHESES.json`, который создал хук события `pre_handoff`:
   ядро читает результат хука, но не выполняет матчинг само.

5. **Сенсор значимости `hypothesis_hit`**: `detect_diff_triggers` получает
   шестую эвристику — по `$HYPOTHESES_DIR/routing.json` (появление файла по
   маске из `rows[]`). Триггер **не форсирует** Critical (в
   `FORCING_CRITICAL_TRIGGERS` не входит) и даёт **+1** к счёту
   Fast/Standard/Critical, то есть попадает в существующий контур
   `score_with_sources` как обычный найденный диффом триггер и может быть
   заявлен флагом (`TriggerSource::Both`).

6. **Fitness-правила плагина остаются вне схемы движка.** Артефакт
   `fitness/hypothesis-routing.yaml` — декларативный референс; чтобы правило
   заработало как гейт движка, его форму нужно привести к контракту
   `name` + `type: command_succeeds` + `command:` (без подстановок
   `{handoff_dir}`/`{project_name}`). Это не скрытая правка: расхождение
   фиксируется здесь и в документации.

7. **Дефект матчинга слов исправляется в артефакте, не в ядре.** Карточка
   дополняет список `words` токенами, по которым критерий приёмки должен
   срабатывать («3B», «Spark»), либо использует триггер-файл/ключ, вес
   которого ≥ порога. Ядро семантику матчинга не знает: веса даны
   артефактом — файлы 3, ключи конфигов/env 3, зависимости 2, слова 1;
   порог по умолчанию 2 (одно слово карточку поднять не может).

## Consequences

### Positive

- Латентные наборы всплывают по свидетельствам в репозитории, а не по памяти
  модели: роутинг становится детерминированным и воспроизводимым.
- Доменные события отделены от инструментных: `src/hooks.rs` не трогается,
  регрессии существующего канала исключены.
- Неблокирующий контракт хука: падение или зависание плагина не рушит
  handoff — таймаут 5 с и `code = -1` едут в outcome для диагностики.
- Зависимость ядра от плагина не появляется: ядро резолвит путь и запускает
  процесс, но не знает семантики событий (направление зависимостей
  `dependency_direction` проходит).
- MANIFEST становится носителем свидетельств: пакет несёт, какие гипотезы
  подняты и какие скиллы к ним привязаны (`card/state/score/skills`).
- Сенсор `hypothesis_hit` встроен в существующий механизм значимости, а не
  во второй параллельный счётчик: +1 к счёту, без форсирования Critical.

### Negative

- **Честное ограничение:** тело хука — внешний процесс (Python) из плагина.
  Ядро от него не зависит и не проверяет его корректность: неверный матчинг,
  медленный старт, отсутствие интерпретатора Python или недостача
  `HYPOTHESES.json` — зона плагина. Ядро лишь доносит код и первую строку
  stdout до вызывающего слоя.
- Схема `PluginManifest` расширяется полем `hooks`, которое ядро раньше не
  читало; смысл доменных событий не валидируется по значениям — опечатка в
  имени события даёт молча неисполненный хук (митигация: обход детерминирован,
  событие — узкая строка, документируется).
- Расхождение fitness-контура артефакта со схемой движка не устранено
  автоматически: правило остаётся референсом, пока его не приведут к
  `type: command_succeeds`.
- Словесные триггеры шумны: ложный подъём карточки смягчён весами и порогом,
  но не исключён.
- Ещё два поля в `MANIFEST.json` (обратная совместимость сохранена
  `skip_serializing_if`).
- Артефакт по-прежнему требует исправления списка слов карточки — критерий
  приёмки («3B на Spark» поднимает карточку) достигается правкой карточки, а
  не ядра, и это надо держать в приёмке.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Отдельный канал `src/hypothesis.rs` + поле `hooks` (принято)** | доменные события не смешаны с инструментными; ядро не зависит от плагина; неблокирующий таймаут | новая схема манифеста и новая точка вызова в handoff/accept |
| Переиспользовать `hooks/hooks.json` и события инструментов | ноль новой схемы | доменных событий (`intent`/`pre_handoff`/…) у инструментного канала нет; пришлось бы лгать о `PreToolUse`; семантика теряется |
| Вызвать Python-скрипт напрямую из `generate_handoff` | короче путь | жёсткая зависимость ядра от конкретного плагина и Python — прямое нарушение `dependency_direction` (ADR-029) |
| Матчинг гипотез внутри ядра (по routing.json) | нет внешнего процесса | ядро узнаёт доменную семантику карточек и весов; критерий «ядро не зависит от домена» (ADR-040) нарушается |
| Description/эмбеддинг-поиск вместо фактов проекта | не требует триггеров | не решает «когда вспомнить» и не различает латентное/активное; исходная проблема именно в этом |
| Теги проектов вручную | просто | не поддерживаются без дисциплины; факты в репо уже есть |
| Сенсор `hypothesis_hit` форсирует Critical | громче сигнал | форсирование снижает чувствительность порогов (`FORCING_CRITICAL_TRIGGERS` неконфигурируем, ADR-034); карточка — не граница безопасности |

## Reversibility

**reversible**: `src/hypothesis.rs` — новый модуль, поле `hooks` —
аддитивное (`#[serde(default)]`), поля `MANIFEST.json` — опциональные
(`skip_serializing_if`), сенсор — аддитивная эвристика `detect_diff_triggers`.
Откат — снятие вызовов `run_event` из точек handoff/accept и удаление
модуля; уже собранные пакеты с `hypotheses` остаются читаемыми (поле
игнорируется при отсутствии потребителя).
