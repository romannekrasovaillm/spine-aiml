# ADR-030. Границы контекстов как fitness-функция: context_boundary и code_roots CMP-сущностей

- Date: 2026-09-04
- Status: Accepted

## Context

Вторая часть находки внешнего ревью о «потолке fitness-функций»: границы
bounded contexts не проверяются нигде. Модель архитектуры (ADR-003) знает
компоненты (`CMP-*`) и их связи (`depends_on`, циклы — `error`), но живёт
отдельно от кода: ни одна сущность не знает, какие файлы её реализуют, и
импорт через границу контекста не виден ни модели, ни fitness-гейту.
`dependency_direction` (ADR-029) проверяет направление зависимостей по
статическим спискам модулей, но не связывает их с архитектурной моделью:
дублирование границ в CONSTRAINTS и в модели — антипаттерн «одно правило в
трёх источниках» (ADR-019, прил. Б).

Сочленение уже заложено: `verified_by` ссылается на правила `C-NNN`
(ADR-003 §3), `depends_on` между CMP фиксирует разрешённые направления.
Не хватает обратной связи: модель → код.

## Decision

**1. Поле `code_roots` у CMP-сущностей** (`src/model/parse.rs`; список
префиксов путей от корня репозитория; опциональное, старые модели валидны —
`deny_unknown_fields` допускает его как известное поле):

```yaml
---
id: CMP-002
type: cmp
title: Billing
status: adopted
code_roots: [services/billing]
depends_on: [CMP-003]
---
```

**2. Новый тип правила `context_boundary`** в `src/control.rs`:

```yaml
- name: context_boundaries
  type: context_boundary
  model_dir: model        # дефолт "model"
  severity: error
```

- Контекст файла — CMP, чей `code_root` префиксно покрывает путь файла
  (граница сегмента). Файлы вне всех корней пропускаются (инфраструктура,
  тесты вне контекстов).
- Контекст импорта (извлечение — общее с ADR-029): прямое префиксное
  совпадение с `code_roots` в координатах импортов (Python/Java: путь
  пакета == путь файла); TS/JS-относительный путь — от каталога файла;
  иначе — разрешение модуля в существующий файл репозитория (базы `""`,
  `src/`, `src/main/java/`, `src/main/kotlin/`, `crates/*/` + модульные
  суффиксы `.rs`/`mod.rs`/`.py`/`__init__.py`/`.java`/`.kt`/`.ts`/…).
  Путь импорта включает имя элемента (`crate::beta::core::Engine` →
  `beta/core/Engine`), поэтому файл ищется по префиксам от длинного к
  короткому. Неразрешённый импорт — внешняя зависимость, пропускается.
- Нарушение: импорт из файла CMP-A разрешается в CMP-B, и `B ∉
  A.depends_on`. Находка `file:line` с парой CMP — годится для evidence
  bundle.
- Пересекающиеся `code_roots` разных CMP — ошибка конфигурации правила
  (`HarnessError::Control`): владение файлом неоднозначно.
- Отсутствующий `model_dir` и модель без единого `code_roots` — находки
  «правилу нечего проверять» (мёртвая конфигурация видна, как мёртвый
  glob).

**3. Без dogfood на собственном коде**: у `src/` харнесса нет модели CMP
(слои зафиксированы правилами C-23…C-27 ADR-029 — для монолитного крейта
слои точнее контекстов). Применение к кейсам — когда у кейса появится код
рядом с `model/`; первым кандидатом зафиксирован `кейсы/payment-processing-platform`.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **code_roots в CMP + context_boundary (принято)** | границы живут в одном источнике (модель); разрешение через depends_on ревьюится как часть архитектуры; сочленяется с trace check (ADR-006) | разрешение импортов — эвристика с базами каталогов; без dogfood на своём коде |
| Границы списками forbid в dependency_direction (без модели) | проще, уже работает | дублирование границ в модели и CONSTRAINTS; разрешённые направления не видны архитектору в графе модели |
| Разрешение импортов по индексу пакетов/крейтов (cargo metadata, tsconfig paths) | точное | стек-специфичные конфиги у каждого потребителя; тяжёлые зависимости; против AD-1 |
| Поле code_roots у всех типов сущностей (SYS, CAP) | полная карта кода | раздувает схему; владение кодом — атрибут компонента, не системы |
| Сканирование только явно объявленных расширений (поле languages) | строже | лишнее поле; экстрактор и так игнорирует неподдерживаемые расширения |

## Consequences

### Positive

- Граница контекста становится исполняемой: импорт через границу без
  `depends_on` ломает CI; добавление зависимости между контекстами —
  изменение модели, проходящее архитектурное ревью (AD-9).
- Модель ADR-003 получает недостающее звено «сущность → код»: та же
  карта `code_roots` пригодна для будущих потребителей (покрытие
  компонентов тестами, владение при fleet-аудите).
- Семантика разрешения мультистекова из коробки: Python/Java — по
  координатам пакетов, Rust — через `src/` и `crates/*`, TS — относительные
  пути.

### Negative

- Разрешение «модуль → файл» — эвристика с конвенциональными базами;
  экзотические layout'ы (переопределённые source roots, path-алиасы
  bundler'ов) потребуют внешнего инструмента (ArchUnit/depcruise через
  `command_succeeds`) — граница применимости задокументирована в
  `docs/control.md`.
- Тесты внутри `code_roots` подчиняются тем же запретам (тест,
  импортирующий чужой контекст, — находка); осмысленные исключения — через
  `exclude_glob` правила.
- Без dogfood на собственном репозитории: корректность подтверждена
  фикстурными тестами (python/rust/depends_on/overlap/пустая модель), а не
  живым прогоном по коду харнесса.

## Reversibility

**reversible** для поля `code_roots` (опциональное; удаление не трогает
прочие потребители модели) и правил; **costly** для типа
`context_boundary` после появления в CI заказчиков — старые типы
декларативно сохраняются (прецедент ADR-019/ADR-029).
