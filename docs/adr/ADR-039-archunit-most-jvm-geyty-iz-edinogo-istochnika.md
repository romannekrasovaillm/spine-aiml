# ADR-039. ArchUnit-мост: JVM-гейты из единого источника (CONSTRAINTS.yaml → настоящий ArchUnit)

- Date: 2026-09-04
- Status: Accepted

## Context

ADR-029 закрыл замечание внешнего ревью «класс ArchUnit не показан»
нативными структурными проверками (`dependency_direction`,
`context_boundary`) и эталонным скриптом `deps-check.py`, сохранив
философию делегирования: ArchUnit-класс проверок — стек-нативным
инструментам, а не переизобретение в тонком ядре (AD-1). Оставшийся зазор:
для JVM-проектов «стек-нативный инструмент» — это настоящий ArchUnit, и
его подключение требовало ручной возни в каждом Java-репо (написать
JUnit-тесты, продублировать правила из CONSTRAINTS.yaml на Java, настроить
зависимости). Правила при этом жили в двух местах и неизбежно расходились:
архитектор правит CONSTRAINTS.yaml, а ArchUnit-тесты в репо команды про
это не знают.

Нативные проверки ADR-029/030 остаются полезными (мультистек, ноль
зависимостей рантайма), но это текстовая эвристика по импортам: она не
видит зависимости через сигнатуры полей/методов без импорта (same-package,
fully-qualified) и разбирает исходник, а не байткод. ArchUnit анализирует
скомпилированные классы — другой, более сильный уровень доказательности.

Ограничения среды: машина архитектора имеет JDK (`java`/`javac`), Maven
Central доступен; тонкое ядро не должно получать новых crate-зависимостей
(AD-1, dogfood-правила); живой Java-прогон в юнит-тестах недопустим
(конвенция детерминированных тестов).

## Decision

**1. Спек правил (`ArchUnitSpec`, `src/archunit.rs`).** Стек-нейтральная
модель: `ForbiddenDeps` (noClasses…dependOnClassesThat), `AllowedDepsOnly`
(classes…onlyDependOnClassesThat), секция `unsupported` (правила, которые
не смаплись, — с причиной; генерацию не роняют). Источник — правила
`dependency_direction`/`context_boundary` из CONSTRAINTS.yaml, чей glob
целится в `**/*.java`, плюс CMP модели (`--model-dir`, дефолт `model`) для
`context_boundary`. Эвристики маппинга (file-glob → пакетный паттерн,
forbid/allow-запись → пакетный паттерн, `code_roots` → пакет)
задокументированы в модульном комментарии `src/archunit.rs` и в
`docs/archunit.md`. Allow-списки CONSTRAINTS описывают внутренние модули,
поэтому в `AllowedDepsOnly` автоматически добавляются собственный пакет и
JDK-белый список (`java..`, `javax..`, `jakarta..`, …).

**2. Два пути исполнения из одного спека.**

- **Встраиваемый**: `arch-be archunit gen <repo>` рендерит
  `ArchFitnessTest.java` (идиоматичный JUnit 5 + ArchUnit:
  `@AnalyzeClasses` с выведенным базовым пакетом, `@ArchTest`-поля) и
  `archunit-rules.json`. Имя каждого правила и текст `.as(...)` содержат
  id правила CONSTRAINTS (C-12) — трассировка нарушения в источник.
- **Standalone (бесшовный, главная ценность)**: `arch-be archunit check
  <repo>` — без единой правки Java-репо: авто-детект классов
  (`target/classes`, `build/classes/java/main`, `out/production`,
  `classes`), jar'ы из `--jar-dir` / `ARCHUNIT_HOME` /
  `~/.arch-ml/archunit/lib`, одноразовая компиляция сгенерированного
  `ArchGateRunner.java` (main без JUnit, правила захардкожены из спека —
  JSON на стороне Java не парсится) javac'ом в кэш
  `~/.arch-ml/archunit/runner` (пересборка только при смене
  исходника, ключ — SHA-256), запуск `java -cp … ArchGateRunner` с
  таймаутом (дефолт 300 с). Вывод (`VIOLATION|<id>|<detail>`, `SUMMARY`)
  парсится в отчёт; exit 1 при error-нарушениях.

**3. `arch-be archunit fetch`** — скачивает пинnutые jar'ы (archunit
1.5.0, slf4j-api 2.0.19, slf4j-nop 2.0.19; slf4j-api обязателен в runtime
— проверено живьём: `ClassFileImporter` без него падает с
`NoClassDefFoundError`) с Maven Central в `~/.arch-ml/archunit/lib` с
проверкой SHA-256 против пинов в коде (supply-chain фиксация; те же
хэши — в `docs/archunit.md`). SHA-256 реализован в `src/archunit.rs`
(FIPS 180-4, safe Rust) — новых crate-зависимостей ноль (AD-1).

**4. Тип правила `archunit` в control.rs.** Правило
(`classes_dir`/`jar_dir` опционально, `timeout_secs` дефолт 300,
`severity`) исполняется `arch-be control check` через тот же
`run_gate`/`spec_from_constraints`: нарушения — находки общего отчёта с id
исходного правила и его severity, unsupported — warn-находки,
инфраструктурный сбой — error-находка (fail-closed, как пустой glob у
прочих типов). Единый JSON/текст отчёта и exit-код гейта сохранены.

**5. Fail-closed диагностика.** Нет `java`/`javac`, нет jar'ов (подсказка
`arch-be archunit fetch`), нет скомпилированных классов (подсказка
`mvn compile`/`javac`), пустой спек, таймаут — всё это понятные ошибки,
а не молчаливый PASS.

**6. Кейс 009 `кейсы/jvm-archunit-gate/`** — механический (без LLM):
трёхслойное java-приложение с намеренным нарушением, эталоны `expected/`
сняты живыми прогонами (fetch → compile → gen → check FAIL → фикс →
PASS → control check).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Спек + gen + standalone runner + тип `archunit` (принято)** | один источник правил; ноль правок Java-репо на standalone-пути; настоящий ArchUnit (байткод); нарушения в едином отчёте гейта; fail-closed; пины SHA-256 | требует JDK и разовый fetch; эвристики маппинга приблизительны; кэш раннера — состояние вне репо |
| Только `gen` (JUnit-тест в репо команды) | нет рантайм-зависимостей у харнесса; идиоматично для JVM-команд | ручная возня возвращается (встроить файл, добавить archunit-junit5, гонять в CI репо); правила снова живут отдельно от гейта архитектора; замечание ревью «бесшовности» не закрыто |
| Только standalone runner (без gen) | минимум кода | команды, предпочитающие тесты в своём CI (JVM-нативный контур), не получают артефакт; spec JSON нечем потребить |
| Импорт ArchUnit-правил → YAML (обратное направление) | единый YAML даже для существующих репо | парсинг Java-DSL правил — ненадёжен и бесконечен (свободные предикаты ArchUnit); направление «YAML → исполнение» уже закрывает потребность |
| Встроить парсер class-файлов в ядро (свой «ArchUnit на Rust») | ноль внешних зависимостей | переизобретение ArchUnit в тонком ядре — прямо против философии ADR-029 и AD-1; месяцы работы и вечное отставание от семантики JVM |

Отклонённые дополнения при реализации (зафиксированы для прозрачности):
`slices()…should().beFreeOfCycles()` не генерируется — из типов правил
CONSTRAINTS проверка циклов не выводится, а безусловное добавление дало бы
расхождение «JUnit-тест строже standalone-гейта»; `layeredArchitecture()`
не эмитится — семантика `dependency_direction` точнее выражается
примитивами `noClasses/classes`, а слоистость модели (уровни) в
типизированной модели отсутствует (есть только CMP и depends_on).

## Consequences

### Positive

- Замечание ревью закрыто на уровне реального инструмента: правила из
  CONSTRAINTS.yaml исполняются настоящим ArchUnit 1.5.0 по байткоду —
  включая зависимости через сигнатуры полей/методов, невидимые текстовой
  эвристике ADR-029 (в кейсе 009 ArchUnit даёт 6 находок против 2
  текстовых на том же нарушении).
- Бесшовность: на JVM-репо гейт ставится тремя командами (`fetch` один
  раз, `javac`/`mvn compile`, `archunit check`) без единой правки репо.
- Единый отчёт: тип `archunit` кладёт находки в общий `FitnessReport`
  (текст/JSON, exit-код) — CI читает один контракт (ADR-020).
- Трассировка: id правила (C-12) — в имени @ArchTest, в сообщении
  `.as(...)`, в каждой строке `VIOLATION|<id>|…` и в находке отчёта.
- Supply-chain: версии и SHA-256 jar'ов запинены в коде и
  `docs/archunit.md`; fetch отказывается писать файл при расхождении хэша.
- Нативные проверки ADR-029/030 не тронуты: мост — дополнительный
  исполнитель того же источника, а не замена (мультистек остаётся на
  нативных; JVM получает более сильный уровень).

### Negative

- Эвристики маппинга приблизительны: glob `src/**/domain/**/*.java` →
  `..domain..` может захватить чужой одноимённый пакет; allow-режим
  ArchUnit строже текстового (видит ВСЕ зависимости байткода, включая
  не-импортированные) — возможны неожиданные находки на legacy.
- Состояние вне репо: кэш `~/.arch-ml/archunit/{lib,runner}` и
  `ARCHUNIT_HOME` — разработчик CI обязан воспроизвести fetch.
- Нет проверки циклов slices и layeredArchitecture (см. отклонённые
  дополнения) — кандидат на отдельный тип правила, если появится спрос.
- Живой Java-прогон не покрыт юнит-тестами (конвенция): регрессии
  рантайм-пути ловятся кейсом 009 вручную/в dogfood-сценарии, не в
  `cargo test`.
- Агентный инструмент (`Tool`) для archunit-гейта не добавлен: CLI и
  control-правило закрывают контур; сопряжение с policy/R-уровнями
  осознанно отложено.

## Reversibility

**reversible**: новый модуль, новая подкоманда, новый тип правила и кейс
аддитивны; старые CONSTRAINTS.yaml парсятся без изменений (обратная
совместимость по прецеденту ADR-019/029). Удаление модуля и типа
возвращает прежний контур; тип `archunit` становится «costly» только
после того, как CONSTRAINTS заказчиков начнут использовать его в CI.
