# ADR-008. MCP-серверный режим (`arch mcp serve`)

- Date: 2026-08-17
- Status: Accepted
- Expiry review: при появлении второго транспорта (HTTP/SSE) или запроса на
  конкурентную обработку запросов — пересмотреть однопоточный цикл и набор
  инструментов.

## Context

Ревью `SPINE-REVIEW.md` (находка F-5, задача P1-2): `src/mcp.rs` — только
stdio JSON-RPC **клиент**. Архитектурный контроль (линтер spine, fitness
functions, трассируемость, значимость, модель, рубрики) доступен внутри TUI
архитектора и по приёмке handoff-пакета, но **не доступен кодовому агенту
(Claude Code и др.) в момент написания кода** — нарушение `AD-*` узнаётся
постфактум, на гейте, а не в точке принятия решения.

DoD P1-2: кодовый агент с этим сервером в конфиге MCP получает
структурированный verdict (`passed` + находки) и может **отказать**
изменению, нарушающему `AD-*`, в момент написания кода. Сервер — read-only
по отношению к репозиторию клиента: verdict — это данные, не side-effect.

## Decision

1. **Новый модуль `src/mcp_server.rs`** (клиент `src/mcp.rs` не трогаем,
   переиспользуем его константы протокола): `arch mcp serve` — stdio
   MCP-сервер, JSON-RPC 2.0 поверх NDJSON (одно сообщение — одна строка,
   как у клиента, без `Content-Length`-фрейминга).
2. **Методы**: `initialize` (echo известной версии протокола из
   `{"2025-06-18", "2024-11-05"}`, иначе — наша `2025-06-18`;
   `capabilities.tools`, `serverInfo arch-harness`), `tools/list`,
   `tools/call`, `ping` (→ `{}`), `notifications/initialized` и любые
   `notifications/*` — игнор без ответа. Неизвестный метод с `id` →
   `-32601`; строка, не разобранная как JSON, → `-32700` (`id: null`);
   валидный JSON без `method` → `-32600`. Сервер **не падает ни на каком
   вводе**: любая строка даёт либо ответ-ошибку, либо игнор; цикл живёт
   до EOF stdin.
3. **Инструменты** (6, имена — как у агентских аналогов; все помечены
   `annotations.readOnlyHint = true`):

   | Инструмент | Аргументы | Оборачивает |
   |---|---|---|
   | `spine_lint` | `path` (обяз.) | `control::lint_spine` |
   | `fitness_check` | `repo` (обяз.), `constraints?` (дефолт `<repo>/.arch-handoff/CONSTRAINTS.yaml`) | `control::check` |
   | `significance_score` | `triggers` (map str→bool) | `control::significance_score` |
   | `trace_check` | `case` (обяз.; корень кейса с `model/`) | `trace::trace_check` |
   | `model_query` | `dir?` (дефолт `model`), `id?`, `type?` | `model::{load_model, card}` |
   | `rubric_run` | `rubric`, `target?` | `target_text?`, `model?` (ровно один из target/target_text) | `rubric::evaluate_with_options` |

   Пути — **только аргументами вызова**; глобального «текущего кейса» нет.
   Относительные пути резолвятся от cwd процесса сервера (его задаёт
   клиент при запуске) — это дефолт аргумента, не состояние.
4. **Структурированный verdict**: успешный `tools/call` возвращает
   `structuredContent` (машиночитаемый объект) и тот же объект pretty-JSON
   в `content[0].text` — читается и нашим же клиентом (разбирает text), и
   кодовыми агентами. Контракт verdict'ов контроля:
   `{passed: bool, summary, issues: [{severity, rule, file?, line?, message}], …}`
   — `passed = false` означает блокирующую находку (`error`), клиентский
   агент обязан трактовать её как отказ изменению. `spine_lint.passed` =
   «нет находок severity error» (у `lint_spine` своего вердикта нет).
   `trace_check` и `rubric_run` дополнительно несут `report_markdown`
   (готовый отчёт для evidence bundle).
5. **Ошибки**: невалидные аргументы (нет обязательного поля, не тот тип,
   оба target/target_text) → `-32602`; неизвестный инструмент → `-32602`;
   доменный сбой выполнения (файл не читается, битый YAML, сущность не
   найдена) → **не** protocol error, а `result` с `isError: true` и текстом
   (MCP-стиль, как у агентских инструментов); сервер продолжает работу.
6. **`rubric_run` без API-ключа** — единственный protocol error выполнения:
   предпроверка доступности ключа (env `api_key_env` задана или файл
   `api_key_file` существует; содержимое не читается и не печатается) →
   `-32603` с понятным русским сообщением, какой env/файл настроить.
   Обоснование: недоступность capability — это не «инструмент поработал и
   упал», а отказ обслуживания; DoD требует именно JSON-RPC ошибку.
7. **Модель выполнения**: один процесс, последовательный цикл
   read-line → dispatch → write-line (flush на каждый ответ).
   Конкурентность запросов не поддерживается: stdio-клиенты (Claude Code)
   сериализуют вызовы, а длинный `fitness_check` (command_succeeds)
   уводится в `spawn_blocking`, чтобы не держать worker runtime.
   Входная строка длиннее 16 МиБ → `-32600` (лимит `MAX_LINE_BYTES`;
   оцениваемый документ рубрикой ограничен 24k символов — запас 600×).
8. **Логи — только stderr** (tracing уже настроен туда в `main`); stdout —
   чистый протокол.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Свой модуль `mcp_server.rs`, Value-диспетчер, последовательный цикл (выбрано) | 350 строк без новых зависимостей; тестируется процессно; симметрия с клиентом | нет batch-запросов и server→client запросов (sampling) |
| Готовый SDK (`rmcp`) | типизированный протокол, progress/cancellation из коробки | тяжёлая зависимость ради 5 методов; NDJSON-стиль проекта пришлось бы ломать; версия протокола SDK ≠ нашей |
| HTTP/SSE транспорт | несколько клиентов к одному серверу | сеть/порты/авторизация — лишняя поверхность; DoD просит stdio |
| Отдавать только текст (как агентские ToolOutput) | проще | кодовый агент не может надёжно отличить PASS от FAIL — весь смысл P1-2 |
| Конкурентный dispatch (spawn на запрос) | параллельные tools/call | гонки за stdout, out-of-order ответы; не нужно stdio-клиентам |

## Consequences

### Positive

- Кодовый агент получает `fitness_check`/`trace_check`/`spine_lint` verdict
  в момент написания кода: `passed: false` + поимённые находки — основание
  отказать изменению до коммита, а не на приёмке пакета (закрывает F-5).
- Ноль новых зависимостей; протокол симметричен существующему клиенту
  (NDJSON, те же версии), сервер проверяется нашим же `McpManager`.
- Read-only гарантия: сервер ничего не пишет в репозиторий клиента
  (в отличие от `arch rubric run`, серверный `rubric_run` не сохраняет
  отчёт на диск — возвращает данные).
- Сервер устойчив к мусору на входе: битый JSON, неизвестные методы и
  уведомления не роняют процесс (контракт тестируется).

### Negative

- Последовательная обработка: долгий `fitness_check` (command_succeeds с
  таймаутом 60 с) блокирует последующие запросы клиента. Приемлемо для
  stdio (клиенты сериализуют вызовы); конкурентность — кандидат при первом
  реальном запросе.
- Дублирование адаптации аргументов с агентскими инструментами
  (`control::SpineLintTool` и др.): схемы похожи, но не переиспользованы —
  агентские инструменты завязаны на `ToolContext`/текстовый вывод, а
  сервер отдаёт структуру. Цена — две точки обновления описаний.
- `rubric_run` наследует стоимость LLM-судьи: кодовый агент может
  неосознанно инициировать платные вызовы. Смягчается тем, что инструмент
  явно описан как LLM-оценка, а без ключа даёт понятную ошибку.

## Reversibility

reversible. Модуль — чистый читатель доменных API; его удаление не трогает
`mcp.rs`-клиента, форматы spine/CONSTRAINTS/model и CLI. Имена инструментов
и контракт verdict — опубликованный интерфейс: переименование — breaking
change для клиентских конфигураций, потребует мажорной пометки.
