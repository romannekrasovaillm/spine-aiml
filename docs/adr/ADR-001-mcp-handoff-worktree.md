# ADR-001. MCP-handoff пакета + параллельная передача независимым агентам в worktree

- Date: 2026-08-16
- Status: Accepted
- Expiry review: при первом прогоне харнесса, где MCP-доставка или параллельные
  worktree дадут расхождение (см. Reversibility), либо при замене лёгкого
  MCP-сервера штатным (npx/uvx) — пересмотреть решение.

## Context

Нужен способ передачи handoff-пакета кодовому агенту, который не ограничивается
чтением файлов `.arch-handoff/` из репозитория: пакет должен быть доступен по
протоколу (MCP), чтобы агент мог запросить его точечно, и чтобы несколько
независимых агентов могли работать параллельно по разным под-пакетам без
общего изменяемого состояния.

Наблюдения теста (полигон `arch-mcp-parallel`, 2026-08-16):

- Штатные MCP-серверы (filesystem/fetch/memory через npx/uvx) зависают при
  конкурентном handshake в `arch mcp list` (EXIT=124) и в изолированном конфиге.
- Лёгкий stdio MCP-сервер на чистом python (JSON-RPC 2.0 NDJSON) поднимается
  мгновенно и детерминированно.
- Кодовый агент (Claude Code) в headless-режиме успешно вызвал
  `mcp__arch-handoff__read_packet {id: p4-mcp}` и получил полный пакет
  (TASK.md + ARCHITECTURE.md + CONSTRAINTS.yaml + spine).
- Три агента в параллельных worktree по spine-границам (AD-1/AD-2/AD-3)
  реализовали независимые модули, все тесты зелёные, fitness PASS,
  интеграционный гейт «валидация→лог→отчёт» — OK.
- Idle-таймаут харнесса по умолчанию (600 с) убивает агентов при медленном
  LLM-провайдере: между tool-вызовами модель думает дольше 10 минут.
  Фикс: `idle_timeout_secs = 0` в конфиге харнесса.

## Decision

1. Для доставки handoff-пакета агенту по протоколу использовать лёгкий
   stdio MCP-сервер (python, JSON-RPC 2.0 NDJSON), раздающий содержимое
   пакета через `tools/call read_packet(id)` / `list_packets()`.
   Сервер регистрируется в `mcp.json` как `arch-handoff` и в
   `~/.claude.json` клиента кодового агента.
2. Для параллельной передачи независимых под-пакетов использовать по одному
   git-worktree на агента (`arch worktree new`), разнесённых по spine-границам
   (Binds/Prevents/Rule в ARCHITECTURE-SPINE.md), с единым интеграционным
   гейтом после завершения всех агентов.
3. Прогоны кодовых харнессов выполнять только через `harness_run`
   (потолок 7200 с + idle-таймаут), НЕ через bash: bash режет промпт о
   квотинг, таймаут короткий, env-scrub прячет ключи авторизации.
   При медленном LLM-провайдере выставлять `idle_timeout_secs = 0`
   (отключение таймаута тишины), контролируя прогресс по heartbeat/логам.
4. Каждый под-пакет получает свой `.arch-handoff/` с CONSTRAINTS.yaml,
   переписанными под spine-инварианты (AD-n), а не стековую заготовку
   генератора.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Штатные MCP-серверы (npx/uvx: filesystem, fetch, memory) | нет своей разработки | зависают при конкурентном handshake (EXIT=124), тяжеловесны, недетерминированы в этом окружении |
| Передача пакета только файлами `.arch-handoff/` (без MCP) | просто, без протокола | нет точечного запроса по id, нет проверки MCP-стека, агент обязан читать файлы репо |
| Один агент на все под-пакеты последовательно | нет конфликтов worktree | не проверяет spine-инвариант «независимо построенные единицы не расходятся», медленнее |
| Прогон харнесса через `bash`/tmux | обход env-scrub | промпт ломается о квотинг, таймаут обрезается, теряется управление процессной группой (сироты) |

## Consequences

### Positive

- MCP-handoff проверен сквозным прогоном: агент получил пакет по `tools/call`,
  что доказывает работоспособность протокольной доставки, а не только файлов.
- Параллельные worktree по spine-границам дали 3 совместимых модуля
  (5/6/4 passed, интеграционный гейт OK) — подтверждён spine-инвариант.
- Лёгкий python MCP-сервер не зависит от npx/uvx и не таймаутит.

### Negative

- Idle-таймаут 600 с по умолчанию убивает агентов при медленном провайдере;
  отключение (`idle_timeout_secs = 0`) оставляет только абсолютный потолок —
  нужен внешний мониторинг прогресса. Второй прогон p4-mcp показал, что даже
  потолок 1800 с может не хватить: на медленном proxy агент потратил весь
  бюджет на исследование кода (17 tool-use: 9 Read, 7 Bash, 1 MCP) и не дошёл
  до реализации — для сложных задач повышать потолок (`timeout_secs` до 7200).
- Агенты склонны завершать текстом «Готово» без финального git-commit и без
  JSON-контракта результата; требуется явный шаг «git add/commit» в TASK.md
  и проверка парсера контракта.
- MCP-сервер архитектора (процесс `arch`) держит старый конфиг в памяти:
  правки `config.toml` (idle=0) не применяются до перезапуска сервера —
  в тесте пришлось использовать `--config test-config.toml` в обход.
- Каждый worktree с большим `.git` замедляет `git status/log` (20с+ на вызов)
  — гейты точечные.

## Reversibility

reversible. Схема «лёгкий MCP-сервер + worktree на агента» локальна для
хендофф-стека, не меняет продуктовые контракты; откат — вернуться к файловой
доставке и последовательным прогонам без потери состояния (пакеты и spine
остаются в репозитории).
