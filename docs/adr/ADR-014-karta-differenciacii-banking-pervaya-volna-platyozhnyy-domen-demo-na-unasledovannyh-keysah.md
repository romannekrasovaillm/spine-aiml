# ADR-014. Карта дифференциации banking/: первая волна — платёжный домен (демо на унаследованных кейсах)

- Date: 2026-08-31
- Status: Accepted

## Context

`banking/` — проприетарная зона Spine BE (ADR-013), сейчас пуста кроме
маркера зоны. План зон в `banking/README.md` (compliance, presets,
playbooks, delivery) — backlog. Владелец продукта выбрал первую волну:
**платёжный домен** — она определяет демо для первого лида ДИТ.

Фактический актив (проверено, MIT-зона `кейсы/`):

- `кейсы/sbp-gateway` — платёжный шлюз СБП (C2B-приём): Critical 11/15,
  solutioning, NFR, контракты TSP-API и ОПКЦ-адаптера, статусная машина
  платежа, RFP по вендору транспорта, ADR-001..007, spine AD-001..008,
  handoff на walking skeleton; честно размеченные gaps (протокол
  участника НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`).
- `кейсы/payment-processing-platform` — центральный процессинг платежей
  (Мир/Visa/MC, СБП, SWIFT, БЭСП): 27 инвариантов спайна, 34
  fitness-правила, типизированная модель на 96 сущностей, трассируемость
  REQ→NFR→AD→CMP→fitness 100% PASS (`arch trace check`), ADR-001..016,
  handoff на walking skeleton H0.

Конкурентное поле: ИТ-консалтинг продаёт банкам слайды и PDF; ДИТ не
получает машино-проверяемой связи «требование → решение → правило →
доказательство». Это и есть дифференциация Spine BE.

## Decision

**Первая волна наполнения `banking/` — платёжный домен**: превращаем
унаследованные кейсы в продуктовую демонстрацию и доменные пресеты.

Состав волны 1:

1. `banking/demos/payments/` — демо-сценарий для ДИТ на двух кейсах:
   скрипт показа (проблема → решение → evidence → гейты), реперная
   точка: машина проверяет, слайды не врут.
2. `banking/presets/payments/` — доменный пресет: выжимка обязательных
   fitness-правил платёжного контура из 34 правил кейса
   payment-processing-platform (идемпотентность, защита от двойного
   списания, сага/outbox, RTO/RPO) + spine-шаблон платёжного домена для
   новых проектов ДИТ.

Роадмап последующих волн (порядок фиксируется, пересматривается
владельцем):

- Волна 2 — **compliance**: рубрики и пресеты 152-ФЗ/ПДн + КИИ (187-ФЗ),
  позиции ЦБ. Сквозная обязательная тема каждой закупки.
- Волна 3 — **playbooks**: методика внедрения Spine BE в ДИТ (онбординг,
  гейты A0–A5, критерии готовности команды).
- Волна 4 — **delivery**: коммерческая упаковка (ведётся параллельно по
  мере лидов: прайс-листы, пресейл-материалы, договорная база).

Правило волн: каждая волна — это данные (md/yaml) в `banking/`, без
Rust-кода (AD-BE1), контент волн старше первой не начинается, пока волна
текущая не имеет проверяемого артефакта (демо-сценарий отрепетирован /
пресет прогнан fitness_check на референс-кейсе).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Первая волна — платежи (принято)** | кейсы уже готовы (дёшево и быстро до демо); платёжный домен — витрина тяжёлой архитектуры (саги, консистентность, RTO/RPO); «вау-эффект» трассируемости на знакомом ДИТ материале | compliance-гэп остаётся открытым до волны 2 — первый лид столкнётся с вопросами 152-ФЗ/КИИ (митигация: волна 2 стартует сразу после сценария волны 1; в демо честно заявить роадмап) |
| Первая волна — compliance | формальная обязательность для любой закупки | до живого демо дольше всего; регуляторика требует выверки по актуальным редакциям; без демо продукт не осязаем |
| Первая волна — playbooks | монетизация услуг сразу | выглядит generic-консалтингом; теряем главное отличие — машино-проверяемые артефакты |
| Все волны параллельно | максимум покрытия | распыление; ни одна волна не доходит до проверяемого артефакта — отложено |

## Consequences

### Positive

- Быстрый путь к демо: оба кейса уже прошли полный цикл проектирования,
  включая PASS трассируемости — демо строится на реальных прогонах
  (`arch trace check`, `arch model graph`), не на макетах.
- Демонстрация сильнейшей стороны продукта (evidence, fitness,
  трассируемость) на самом сложном банковском домене.
- Пресет волны 1 — переиспользуемый актив: каждый платёжный проект ДИТ
  стартует с готового набора обязательных правил.

### Negative

- Демо-сценарий опирается на кейсы с честно размеченными gaps
  (протокол НСПК `[ТРЕБУЕТ ПРОВЕРКИ]`) — в демо нужно показывать это
  как дисциплину честности, а не прятать; риск: ДИТ-скептик увидит
  «незакрытый» кейс (митигация: сценарий прогоняет проверяемую часть,
  gaps — слайд «открытые вопросы», это сильнее, чем притворство).
- Пресет-выжимка из одного кейса — риск переноса частных решений как
  универсальных; каждый элемент пресета получает ссылку на
  источник-инвариант, эволюция — через использование в следующих кейсах.
- Сдвиг compliance-волны: первый лид может запросить 152-ФЗ/КИИ-контур
  раньше волны 2 (митигация: роадмап в ADR виден, волна 2 — следующая).

## Reversibility

**reversible**: состав волн и их порядок — продуктовый план, смена
приоритета не ломает архитектуру; артефакты волн независимы друг от
друга.
