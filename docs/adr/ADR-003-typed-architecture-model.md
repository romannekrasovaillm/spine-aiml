# ADR-003. Типизированная модель архитектуры с трассируемостью ссылок

- Date: 2026-08-17
- Status: Accepted
- Expiry review: при появлении второго потребителя графа (P0-2 `arch trace check`,
  P1-1 NFR-расчёты, P1-3 экспорт в Structurizr) — пересмотреть минимальность
  схемы frontmatter и набора видов связей.

## Context

Ревью `SPINE-REVIEW.md` (находка F-1, задача P0-1): все архитектурные сущности
существуют только как проза в markdown; связи между ними не представлены в коде
и не проверяются. Рубрика `solution_architecture` требует «полной двусторонней
трассировки без сирот» (критерий `sdd_contract`, вес 8), но харнесс отдаёт её
проверку LLM-судье вместо детерминированного кода. В кейсе 002 ADR лежат в двух
каталогах (`docs/adr/` и `.arch-handoff/adr/`) побайтово идентичными копиями —
дублирование, а не проекция из модели.

При этом ценность текущего формата — markdown в git: diff-ы, ревью,
переносимость. Модель добавляется **над** markdown, а не вместо него
(запрет из раздела 5 ревью).

## Decision

1. **Хранение**: каталог `model/` целевого проекта; одна сущность = один
   `.md`-файл с YAML-frontmatter и прозаическим телом. Frontmatter:
   `id`, `type`, `title`, `status` (обязательные), `date` (опционально),
   связи — списки ID: `depends_on`, `implements`, `affects`, `verified_by`
   (опциональные); для `NFR` — поле `verification` (способ проверки).
   Frontmatter разбирается вручную (маркеры `---`/`---`) + `serde_yaml`;
   новых зависимостей нет.
2. **Стабильные типы ID**: `CAP-`, `SYS-`, `CMP-`, `INT-`, `NFR-`, `REQ-`,
   `AD-`, `ADR-`, `RISK-`, `OWNER-`. Разбор ID — один regex
   (`model::ID_PATTERN` → `model::id_re()`), переиспользуется в
   `control::adr_new` вместо локального `^ADR-(\d+)`.
3. **Валидация** (`arch model validate <dir>`, exit 1 при `error`):
   битая ссылка на несуществующий ID — `error`; дубль ID — `error`;
   цикл в `depends_on` — `error`; `ADR` без затронутых `CMP` — `warn`;
   `NFR` без `verification` — `warn`. Цели `verified_by` могут быть либо
   ID сущностей, либо ссылками `C-NNN` на правила `CONSTRAINTS.yaml`
   (файл ищется рядом с `model/`; отсутствует — такие ссылки не проверяются;
   есть, а правила нет — `error`). Это закладывает сочленение с
   fitness-правилами, не дублируя их в модели.
4. **CLI**: `arch model validate <dir>`, `arch model show <id> [--dir]`,
   `arch model graph [--dir] [--format text|mermaid]`,
   `arch model project <dir>`. Инструмент агента `model_query`
   (`model::tools()`, регистрация в `tools::domain_tools`).
5. **Проекция**: `arch model project <dir>` рендерит сущности `ADR-*` из
   модели в `<dir>/../.arch-handoff/adr/` под теми же именами файлов
   (`# ADR-NNN. <title>` + `- Date:`/`- Status:` + тело). Проекция зеркальная:
   файлы `ADR-*.md` в целевом каталоге без соответствующей сущности удаляются
   (каталог полностью генерируемый). Дублирующий каталог
   `кейсы/payment-processing-platform/.arch-handoff/adr/` заменяется
   проекцией из `model/` кейса; `docs/adr/` кейса остаётся авторским
   прозаическим чтивом (миграция его на рендер из модели — отдельное решение).
6. **Модуль**: `src/model.rs` + `src/model/{parse,graph,validate,project}.rs`.
   (`project.rs` — четвёртый подмодуль сверх минимального списка P0-1:
   проекция — отдельная обязанность, держать её в `parse.rs` нелогично.)

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Markdown + YAML-frontmatter (выбрано) | человекочитаемо, git-diff-friendly, одна сущность = один файл, не ломает дисциплину артефактов | схему дисциплинирует только валидатор |
| Единый `model.yaml` на проект | один файл, дешёвый разбор | конфликты при параллельной правке, diff нечитаем, против духа «markdown first» |
| База (SQLite) | запросы из коробки | теряется git-ревью и переносимость; прямо запрещено ревью (раздел 5) |
| Fitness-правила как сущности модели (новый префикс `FIT-`) | полная трассировка в одном графе | раздувает стабильный список типов ID; правила уже живут в `CONSTRAINTS.yaml` и исполняются `control check` — дублирование |
| Проекция в `docs/adr/` вместо `.arch-handoff/adr/` | единый источник ADR | ломает авторский цикл (ADR пишутся людьми/агентом как проза до фиксации в модели); вне объёма P0-1 |

## Consequences

### Positive

- Ссылочная целостность проверяется кодом: битая ссылка, дубль ID, цикл
  `depends_on` ломают сборку (`arch model validate`, exit 1).
- `model_query` даёт агенту детерминированный доступ к сущностям и связям —
  основа для P0-2 (`arch trace check`), P1-1 (NFR-расчёты), P1-3 (экспорт).
- `.arch-handoff/adr/` кейса 002 — генерируемая проекция, а не копия:
  дрейф копий исключён по построению.
- `control::adr_new` и модель делят один regex ID — новые префиксы
  добавляются в одном месте.

### Negative

- Дважды записанная правда в переходный период: `docs/adr/` кейсов —
  авторские файлы, `model/ADR-*.md` — их типизированное отражение; синхронность
  поддерживается руками до решения о рендере `docs/adr/` из модели.
- Схема frontmatter не навязана редактором — опечатку в имени поля ловит
  только валидация (serde `deny_unknown_fields` в разборе frontmatter
  частично компенсирует).
- Циклы ловятся только по `depends_on`; смысловые циклы других видов связей
  (`implements`/`affects`) не проверяются — их семантика допускает петли.

## Reversibility

reversible. Модель — надстройка над markdown: удаление `model/` и команд
`arch model …` возвращает репозиторий к прозаической дисциплине без потери
артефактов (проекция `.arch-handoff/adr/` при этом перестаёт обновляться —
каталог либо возвращается к ручной копии, либо удаляется).
