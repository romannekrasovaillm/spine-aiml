## A. Фреймворки: суть и что полезно перенять

### A.1. AI-Disrupt PDLC (Сбер, White Paper 2.0, июнь 2026)

**Суть.** Наиболее целостная публичная концепция перестройки жизненного цикла под агентную модель. Жизненный цикл делится на петлю намерения (Intent Loop, человек, такт — дни) и петлю реализации (Implementation Loop, агент, такт — минуты); сквозь обе проходят Validation Spine и Governance Mesh. Это целевая архитектура инженерной организации, а не исполнимая методика команды; явной accountable-роли Solution Architect нет.

**Что полезно перенять в харнесс архитектора:**
- **Две петли с разным тактом**: вероятностный исполнитель не получает права определять цель и риск — человек владеет проблемой, гипотезой результата, инвариантами, критериями приёмки.
- **R-уровни автономности R0–R5**: автономность калибруется риском действия (обратимость, blast radius, деньги/клиент, security boundary, новизна паттерна), а не брендом модели.
- **HITL Decision Map**: человек включается в decisions, а не в events; если одобряется >95–99% однотипных запросов — границу автономии пересматривают (детектор approval theater).
- **Evidence Bundle как условие выпуска** — аудиторский след не «отчёт после», а гейт релиза.
- **Context Supply Chain**: контекст — производственный актив со владельцем, версией, freshness SLA, правами и отзывом; запрет «всю Wiki в RAG».
- Метрики перехода: **I/V Tempo Ratio, Cost per Validated Outcome**.

### A.2. AWS AI-DLC 2.0 + Amazon Kiro

**Суть.** Наиболее формализованный исполнимый agentic SDLC (awslabs/aidlc-workflows, MIT-0): 5 фаз, 32 стадии, 14 специализированных агентов, 9 адаптивных масштабов (enterprise…workshop), approval gate на каждой стадии, аудит из 82 типов событий, детерминированная state machine с checkpoint/resume, идентичная между harness'ами (Claude Code, Kiro, Codex CLI, opencode, Copilot). Спринты заменены Bolt'ами (часы–дни), декомпозиция — через Unit of Work с DAG зависимостей. Kiro — IDE-воплощение: requirements в нотации EARS → design.md → tasks.md, spec check на противоречия, hooks, steering-файлы, admin-контроль моделей и MCP.

**Что полезно перенять:**
- **Architect Agent как design authority**: ADR, DDD-декомпозиция, NFR с измеримыми целями, DAG единиц работ; при этом corporate accountability остаётся у названного человека.
- **Состязательный architecture-reviewer**: отдельный агент с установкой «я не проектировал эту систему, моя работа — найти, что сломается»; вердикт READY/NOT-READY; находки обязаны опираться на проверяемое свидетельство, а не на вкус; ограниченная область чтения (запрет читать соседние единицы, кроме точечной проверки точки интеграции).
- **Walking skeleton**: первый Bolt — минимальный сквозной срез, эмпирически доказывающий архитектуру до массовой генерации; после него один «лестничный вопрос» — дальше автономно или гейт на каждый Bolt; отказ всегда останавливает Construction.
- **Слоистое проектирование**: Functional Design технологически нейтрален → NFR Design оперирует логическими компонентами → Infrastructure Design привязывает к конкретным сервисам. Прослеживаемость требование → компонент → метод → единица → инфраструктура.
- **Машиночитаемые контракты стадий** (execution/lead_agent/reviewer/produces/consumes/requires_stage/sensors/scopes) + детерминированные **сенсоры** артефактов: required-sections, upstream-coverage (артефакт, не ссылающийся на входы из consumes, считается непокрывающим).
- **ADR-дисциплина**: запись до реализации; статусы Proposed/Accepted/Deprecated/Superseded; обязательные альтернативы, отрицательные последствия и оценка обратимости; номера не переиспользуются; ревью в PR вместе с кодом; ежеквартальный пересмотр.
- **Цикл обучения**: человеческие исправления превращаются в правила memory/{org,team,project}.md и новые сенсоры; файлы стадий при этом неизменяемы.
- Из Kiro: **EARS-нотация** требований (машиночитаемые, проверяемые) и анализ требований на противоречия; Quick Spec как fast path.
- Reverse engineering brownfield: 9 артефактов со **сроком годности** (карта системы пересобирается при устаревании).

### A.3. BMAD Method v6 (~50–52 тыс. звёзд, MIT)

**Суть.** Открытая методология с ролевой моделью (аналитик, PM, архитектор, разработчик, UX) и четырьмя фазами: анализ → планирование → Solutioning → реализация (все пути сходятся в bmad-build). Это дисциплина с человеком в контуре, а не мультиагентный оркестратор. Лучшая публичная механика фиксации архитектурных инвариантов для параллельных агентов.

**Что полезно перенять:**
- **ARCHITECTURE-SPINE.md — «позвоночник» инвариантов**: фиксируется только то, в чём независимые исполнители могут разойтись несовместимо, что неочевидно и является компромиссом. Тест принадлежности: «могут ли две единицы уровнем ниже, построенные независимо, выбрать несовместимо?» — если нет, в Deferred.
- **Блок решения AD-n с полями Binds / Prevents / Rule** («что связывает / какое расхождение предотвращает / проверяемое правило»); стабильные ID без перенумерации и переиспользования; метка [ADOPTED] для ратифицированной реальности.
- **Высота (altitude) и наследование**: initiative → feature → epic; родительский spine — read-only связывающее ограничение; локальное переопределение запрещено, конфликт выносится наверх.
- **Seed vs spine**: структурное (стек, дерево каталогов) — «посев», истинный на холодном старте, дальше владелец — код; spine не дублирует выводимое из репозитория.
- **Readiness-гейт PASS/CONCERNS/FAIL** перед реализацией: «сможет ли разработчик реализовать, не изобретая отсутствующих решений?»; двусторонняя прослеживаемость требование↔история, «сироты» помечаются с обеих сторон.
- **Ревью-гейт**: детерминированный линтер (lint_spine: заглушки, дубли AD, пустые Binds/Prevents/Rule, непиннутые версии) + параллельные **линзы-субагенты**, включая состязательную («построй две единицы, соблюдающие все AD, но несовместимые») и линзу веб-проверки фактов (версии/применимость названных технологий — не из памяти модели). Родительский контекст получает только сводку.
- **Компиляция epic-context (800–1500 токенов)** вместо загрузки сырых планировочных документов; кеш инвалидируется, если планировочный документ новее.
- **Headless-контракт с JSON-статусом** complete/partial/blocked + assumptions[], open_questions[], conflicts_with_prior_decisions[].
- **Корпоративная кастомизация через TOML-слои без форка навыка**: persistent_facts, external_sources, finalize_reviewers, external_handoffs, spine_template.
- Режимы coaching vs fast path ([ASSUMPTION]-теги); memlog — append-only журнал прогона, из которого spine дистиллируется в конце (воспроизводимость, возобновление от журнала).

### A.4. GitHub Spec Kit (v0.16.x, ~128 тыс. звёзд)

**Суть.** Самый распространённый SDD-набор 2026 года, де-факто lingua franca взаимодействия с агентом через артефакты. Цепочка Constitution → Specify → Clarify → Plan → Checklist → Tasks → Analyze → Implement. Класс spec-first: после начала генерации спека дрейфует от кода, ролей и валидации почти нет.

**Что полезно перенять:**
- **Project constitution**: неизменяемые принципы проекта, наследуемые каждой спецификацией; писать как executable standards, а не манифест ценностей.
- Простую короткую цепочку Spec→Plan→Tasks→Implement, реально стандартизируемую на сотнях команд.
- Опциональные гейты clarify/checklist/analyze как risk-based quality gates.
- Enterprise distribution: private catalogs, offline/air-gap, extensions с compliance-гейтами, role-based bundles; лучшая портируемость (30+ агентов) — процесс не прибит к одному агенту.

### A.5. OpenSpec (v1.9.0, ~65 тыс. звёзд, MIT)

**Суть.** Легковесный SDD-слой, живущий в репозитории без внешнего runtime. Центр — change-центричные **дельта-спецификации**: каждое изменение — proposal со структурой ADDED/MODIFIED/REMOVED относительно текущей истины; цикл propose → apply → archive, после чего дельта вливается в живой источник истины. Философия: fluid not rigid, iterative not waterfall, brownfield not just greenfield. Полевое испытание: 12 минут до PR (против 90 мин Spec Kit и 5,5 ч полного BMAD).

**Что полезно перенять:**
- **Дельта-спеки** — описывать только изменение, а не систему целиком; естественно для legacy/потока мелких изменений (основной ландшафт банка).
- Явное разделение **текущей истины и предлагаемого изменения** — аудиторский след намерения до реализации.
- CLI-валидацию структуры (openspec validate) и жёсткую state-машину изменения как лёгкий гейт согласования.
- Роль: **Fast Path** корпоративного стандарта; не применять на Critical Path (платежи, КИИ, необратимые миграции, смена security boundary).

### A.6. Spec Kitty (~1,5 тыс. звёзд, MIT)

**Суть.** Редкий SDD-набор, добавляющий не шаблон markdown, а контур исполнения: изолированные git worktree, пакеты работ, человеческие контрольные точки до слияния, локальный Kanban. В таксономии Macedo 9–10 из 12 (в документах расхождение: главный и agentnye дают 10 и «первое место с BMAD», записка по Macedo — 9; источник — разные версии подсчёта по ролям).

**Что полезно перенять:**
- Паттерн **«worktree + review/accept/merge»**: изоляция worktree снижает коллизии параллельных агентов на одном репозитории; обязательный accept-гейт до merge; полный цикл spec → plan → tasks → next → review → accept → merge.
- Видимый Kanban-прогресс factory-контура. Сам инструмент — не стандарт (малая экосистема), паттерн заимствуется в собственный харнесс/IDP.

### A.7. Tessl и Agent OS (смежные платформы SDD-контура)

**Суть.** Tessl ($125 млн) сместился от радикального spec-as-source к **Agent Enablement Platform**: реестр навыков (3000+), сканирование безопасности, политики установки, evals на сами инструкции агента; Spec Registry — 10+ тыс. спецификаций корректного использования open-source библиотек против галлюцинаций API. Критика Thoughtworks — параллели с провалом Model-Driven Development. Agent OS (Builder Methods, открытый) — система **«инъекции стандартов»**: Discover (извлечение соглашений из кодовой базы) → Deploy (избирательное подмешивание релевантных стандартов агенту под задачу) → Shape Spec.

**Что полезно перенять:**
- **Skill Supply Chain**: инвентарь и policy на навыки/MCP/промпты, evals на инструкции агента, сканирование безопасности — ответ на skill sprawl и supply-chain риск агентных расширений (подпись, манифесты, скоупинг прав, аудит обновлений).
- **Избирательную инъекцию доменных стандартов в контекст** под задачу (не «все стандарты сразу») — слой контекста, комбинируемый с любым SDD.
- Урок Tessl: не жёсткая связка spec↔код 1:1 (spec-as-source) — ловушка MDD на неудобном уровне абстракции.

### A.8. Superpowers (~140–214 тыс. звёзд, MIT; в marketplace Anthropic с января 2026)

**Суть.** Дисциплинарный execution-фреймворк Джесси Винсента: «проблема в дисциплине». Конвейер из семи фаз: сократический Brainstorm → Spec → Plan → TDD → Subagent Dev → Review → Finalize. Строгий red-green-refactor (тест обязан упасть до реализации), четырёхфазная отладка через root-cause, двухступенчатый самообзор (соответствие спецификации → качество кода).

**Что полезно перенять:**
- Запрет прыжка в код; **подпись дизайна** перед реализацией; YAGNI/DRY как проверяемые правила.
- TDD-петлю и двухступенчатое ревью (spec-compliance отдельно от code quality).
- Реализацию в свежих субагентах (чистый контекст на задачу).
- Роль: личный стандарт качества инженера / junior academy, не корпоративный SDLC.

### A.9. GSD — Get Shit Done (~51–64 тыс. звёзд)

**Суть.** Метапромптинговый фреймворк, атакующий деградацию контекста (context rot): «проблема в контексте». Отдельный оркестратор на фазу, удержание окна ниже 50% заполнения, волновое параллельное исполнение, передача состояния через markdown-файлы на диске. Жёсткая привязка к Claude Code, портируемость 0.

**Что полезно перенять:**
- **Бюджет контекста как инженерное правило** (окно <50%); контекст — расходный ресурс, измерять объём на одну историю.
- Свежий контекст на фазу + файловая передача состояния (агенты забывают, файлы — нет).
- Волновое (wave-based) параллельное исполнение крупных фич.

### A.10. Reversa и living-spec платформы (Augment Cosmos)

**Суть.** Reversa (~1,1 тыс. звёзд; конфликт интересов — автор Macedo) — единственный заметный фреймворк обратного направления: извлекает операционные спецификации из legacy-кода, **честно помечая уверенность и пробелы** (противоядие от automation bias на сгенерированных спеках). Augment Cosmos (май 2026) представляет класс **living specs**: спецификации обновляются вместе с кодом, event-driven триггеры из GitHub/Linear/Slack/PagerDuty — ответ на главный дефект статических SDD, дрейф.

**Что полезно перенять:**
- Режим **reverse discovery** перед высокоавтономной работой с legacy: карта системы с метками confidence/gaps; reverse-spec не заменяет владельца домена.
- **Drift-детекцию spec↔код** как непрерывный процесс (living spec), а не разовый аудит.
- Пять из шести фреймворков решают greenfield; для банка с 20–30-летним ядром обратное направление критично.

### A.11. IBM ADLC (Agent Development Lifecycle)

**Суть.** Соседний класс: жизненный цикл бизнес-AI-агента как производственного актива — Plan → Code & Build → Test & Release → Deploy → Operate → Monitor. Акценты: evals, red teaming, sandboxing, MCP gateway, progressive rollout, мониторинг дрейфа, governed catalog агентов и инструментов, version control промптов/моделей/оркестрации. Дополняет agentic PDLC, не заменяет.

**Что полезно перенять:**
- Если харнесс архитектора сам порождает/управляет агентами — отдельный **Agent Product Lifecycle**: каталог с ownership/versioning, behavioral evals, progressive rollout, drift monitoring, kill switch.
- Не дублировать существующие MLOps/SDLC-контроли — нужна common control taxonomy.

## B. Рекомендуемая гибридная модель (из главного документа, полностью)

**Принцип.** Корпоративная ошибка — заставить каждую задачу проходить одинаковый процесс. Изменения маршрутизируются по трём режимам в зависимости от **Architecture Significance Score**: риска, обратимости и blast radius.

### Три режима

- **Fast Path** (низкий риск, готовый паттерн): Intent Lite → дельта OpenSpec (propose/apply/archive) или Spec Kit Tasks → агентная реализация → автоматизированная валидация → release. Человек-архитектор не требуется; constitution/golden path/policy hooks работают автоматически.
- **Standard Path**: + Discovery (AI-Disrupt) → контракт Spec Kit (constitution + spec/plan) → автоматический Architecture Fit / Impact (A0–A1) → реализация в harness с **worktree-изоляцией по паттерну Spec Kitty** → Evidence Bundle → release → outcome check. Solution Architect подключается **по триггеру**, не по умолчанию.
- **Critical Path** (архитектурно/регуляторно значимое): Discovery → полный SDD → **BMAD Solutioning со spine-инвариантами** + **Architect Agent из AI-DLC** (варианты, ADR, NFR, DAG) → **человеческое архитектурное решение** → threat/risk analysis → **walking skeleton** → агентная реализация под независимыми evidence-проверками → controlled release → усиленное наблюдение. Human Solution Architect обязателен.

Все режимы разделяют **объектный минимум артефактов** (проблема/гипотеза результата, спецификация или дельта, уровень риска, ссылка на паттерн или ADR, критерии приёмки, план отката) и платформенный control plane.

### Что брать из каждой методологии (консолидация таблиц главного документа и обзора 12 фреймворков)

| Источник | Взять в стандарт | Оставить снаружи |
|---|---|---|
| AI-Disrupt | Две петли, Discovery, Validation Spine, Governance Mesh, R-уровни, Evidence Bundle, Context Supply Chain, IDP, AgentOps, антипаттерны, метрики I/V и cost/outcome | Tiny Teams как стартовую цель; перегруженную роль Product Engineer; Zero Friction как отмену независимого контроля |
| AWS AI-DLC | Architect Agent, детерминированные стадии, ADR с обратимостью, reverse engineering, walking skeleton, сенсоры, цикл обучения org/team/project | Обязательный mob на весь поток; вендорские 10× как KPI; Kiro как единственную IDE |
| BMAD | Solutioning, Architecture Spine, Binds/Prevents/Rule, наследование инвариантов, readiness-гейт, epic-context, customize.toml, adversarial-линза | Полный цикл на каждую историю; неконтролируемый расход токенов; генерацию документов без решения |
| Spec Kit | Constitution, цепочку Spec→Plan→Tasks→Implement, портируемость, пресеты/bundles | Веру, что конституция заменяет архитектора; статичную спеку без drift-детекции |
| OpenSpec | Дельта-спеки, propose/apply/archive, brownfield-first, низкий порог Fast Path | Применение на Critical Path; Stores до их зрелости как единственный контрактный реестр |
| Spec Kitty | Worktree-изоляцию и review/accept/merge, видимый factory-контур | Сам инструмент как стандарт до проверки устойчивости |
| Superpowers / GSD | TDD-петлю, подпись дизайна, свежий контекст, запрет прыжка в код | Статус корпоративного SDLC; привязку к одному агенту/IDE-плагину |
| Reversa | Reverse discovery с метками уверенности и пробелов | Ожидание, что reverse-spec заменяет владельца домена |
| Tessl / Agent OS | Инвентарь и policy навыков, evals на skills; инъекцию стандартов в контекст | Замену PDLC платформой управления навыками |
| Kiro | EARS как нотацию требований; spec check на противоречия | Как обязательную среду, если нет сознательного AWS-контура |

### Красные флаги при внедрении (главный документ + расширенный список)

- Число PR резко растёт, а Change Failure Rate ухудшается.
- Validation lead time растёт быстрее implementation lead time.
- Спецификации создаются формально **после** кода (задним числом).
- Более 90–95% HITL-утверждений проходят без замечаний (approval theater / резиновый штамп).
- Библиотека паттернов растёт при низком reuse; растёт architecture exception rate.
- Растёт зоопарк технологий/библиотек/хранилищ; команды обходят approved harness (shadow AI).
- Инцидент нельзя воспроизвести из audit trail.
- Стоимость inference растёт быстрее delivered value.
- Сотрудники не могут объяснить сгенерированное решение без агента (деградация junior-конвейера).
- Product Engineers систематически работают сверх WIP limits.
- Контрольные функции создают ручные параллельные очереди ревью.

Дополнительно из обзора agentic-фреймворков (анти-паттерны): framework monoculture (один тяжёлый процесс на всё), «runtime = governance» fallacy (guardrails в SDK ≠ enterprise-контроль), spec bureaucracy (markdown растёт, качество решений — нет), architecture vacuum, framework zoo, lock-in под маской портируемости, validation bottleneck, context sprawl, premature Tiny Teams.

## D. Таксономия Macedo (arXiv:2606.04967, июнь 2026)

**Метод:** направленный поиск по первичным источникам; единица анализа — фреймворк как «структурированный набор артефактов, команд, ролей, шаблонов и политик поверх агента разработки». Фильтры: функция поддержки процесса (не точечная генерация), надстройка над агентом (не сам агент/IDE/платформа — исключены Claude Code, Kiro, Antigravity), не SDK оркестрации (исключены CrewAI, LangGraph, ADK…), трекшен ≥1000 звёзд + активность за 6 мес.

**Шесть измерений с направляющими вопросами и индикаторами (рубрика 0–2: 0 — отсутствует, 1 — частично, 2 — сильно/центрально):**

| Измерение | Направляющий вопрос | Индикаторы |
|---|---|---|
| Спецификация | Как намерение становится рабочим контрактом? | Спеки, PRD, планы, stories, задачи, критерии приёмки |

**Структурные выводы для классификации инструментов:**
- Спецификация — общий знаменатель (почти у всех 2), не различает; **наиболее дискриминирующие измерения — роли и валидация**.
- Устойчивый обмен **«глубина процесса ↔ портируемость»**: переносимые Spec Kit/OpenSpec жертвуют ролями и валидацией; глубокий BMAD теряет портируемость; контекстно-сфокусированный GSD обнуляет остальное. Выбор фреймворка — выбор точки на кривой обмена под риск изменения.
- Конвергенция механизмов: изолированный промпт теряет центральную роль; персистентные артефакты, рабочие контракты, трассируемость и человеческое ревью становятся стандартом.
- Спектр «жёсткости» SDD (из обзоров, дополняет таксономию): **spec-first → spec-anchored → spec-as-source** — положение на этом спектре информативнее перечня функций.
- Четырёхэтажная классификация ландшафта (из главного документа и обзоров): A — операционная модель организации; B — исполнимый lifecycle с гейтами; C — спецификация как исполнимый контракт; D — дисциплина сессии агента. Сравнение корректно только внутри этажа. Обзор agentic-фреймворков добавляет этаж «Agent product lifecycle» (IBM ADLC) и «Runtime/orchestration».

## E. Итог: идеи фич для доменного харнесса solution-архитектора (must/should/could)

Документы языко-нейтральны; на Rust естественно ложатся детерминированные части (state machine, линтеры, сенсоры, валидаторы, CLI) — всё, что в источниках названо «детерминированным/механическим слоем». Банковских доменных схем артефактов (платежи, КИИ) в документах нет — есть только перечни триггеров риска.

### MUST (ядро харнесса)

1. **Маршрутизатор режимов Fast/Standard/Critical по Architecture Significance Score** — 15 признаков из §10.2 анализа AI-Disrupt (новый компонент/datastore/vendor, смена контракта, security boundary, необратимость, RTO/RPO и т.д.); превышение порога автоматически запускает Solutioning и human SA review.
2. **Architecture Spine как центральный артефакт**: блоки AD-n с обязательными полями Binds/Prevents/Rule; стабильные ID (без перенумерации/переиспользования); тест принадлежности «могут ли две единицы ниже разойтись несовместимо»; раздел Deferred с причиной и условием возврата; метка [ADOPTED] для ратифицированной реальности.
3. **Наследование инвариантов по высоте** (initiative → feature → epic): родительский spine read-only, секция Inherited Invariants с оригинальными ID, запрет локального переопределения, конфликт эскалируется наверх.
4. **ADR-реестр по образцу AI-DLC**: создаётся до реализации; Status/Context/Decision/Consequences (вкл. отрицательные)/Alternatives Considered/References; оценка обратимости; индексный файл; Superseded-связки; ревью в PR вместе с кодом.
5. **Readiness-гейт PASS/CONCERNS/FAIL** перед массовой реализацией: двусторонняя прослеживаемость требование↔история, поиск «сирот», вердикт с местами пробелов и указанием чинящего навыка.
6. **Независимое состязательное ревью архитектуры**: отдельный агент/субагент со свежим контекстом («не проектировал — ищу, что сломается»), вердикт READY/NOT-READY, находки только с проверяемым свидетельством, ограниченная область чтения; плюс параллельные линзы (рубрика, безопасность/комплаенс, стыки, целостность данных) по образцу BMAD finalize_reviewers — как обязательный пол, не опция.
7. **Детерминированный механический слой**: линтер spine/спек (заглушки, дубли ID, пустые поля, непиннутые версии), сенсоры required-sections и upstream-coverage, верификационные гейты на границах фаз (наличие артефактов, целостность ссылок). Это чистый Rust-слой.
8. **Детерминированная state machine процесса с checkpoint/resume и append-only аудитом** (аналог audit.md/memlog: ISO-метки, запросы на утверждение, ответы; событие SENSOR_FAILED и т.п.) — воспроизводимость инцидента из журнала.
9. **Evidence Bundle как условие выпуска**: спецификация/дельта, риск-уровень, ссылка на паттерн/ADR, критерии приёмки, план отката, snapshot контекста, доказательства валидации — собирается до release, а не после.
10. **NFR с измеримыми целями и слоистость**: functional design (технологически нейтральный) → NFR design (логические компоненты) → infrastructure (привязка); NFR-бюджеты (latency, RTO/RPO, cost, data locality) как часть спеки.
11. **HITL decision-level, не event-level**: единственная обязательная человеческая точка — A3 Human Architecture Decision (короткий machine-readable результат: choice, rationale, constraints, rejected options, expiry); встроенный мониторинг approval rate с порогом 95% как сигналом пересмотра границы автономии.
12. **Handoff-пакеты кодовым агентам**: компиляция эпик-контекста 800–1500 токенов (по смыслу, не по источнику; без дословных цитат; кеш инвалидируется при обновлении входов); headless JSON-контракт complete/partial/blocked + assumptions[]/open_questions[]/conflicts_with_prior_decisions[].
13. **Walking skeleton как первый Bolt**: минимальный сквозной срез, доказывающий архитектуру до массовой генерации; «лестничный вопрос» (автономно или гейт на каждый Bolt) фиксируется в состоянии; отказ останавливает конвейер.

### SHOULD (сильные усилители)

14. **Дельта-спеки для brownfield-потока** (ADDED/MODIFIED/REMOVED; propose/apply/archive; вливание в живой источник истины) + CLI-валидация структуры.
15. **Reverse discovery для legacy**: извлечение операционных спек из кода с метками уверенности/пробелов (Reversa) + 9 артефактов обследования AI-DLC со **сроком годности** и пересборкой при устаревании.
16. **Fitness functions + drift detection**: исполняемые архитектурные проверки (dependency rules, allow-lists, contract checks), post-deploy drift check A5 по телеметрии и графу архитектуры; living-spec обновление спек вместе с кодом (event-driven триггеры).
17. **Policy-as-code с Policy Registry**: каждое правило с owner/scope/version/expiry и measurable control objective; executable standards вместо PDF; exception workflow (time-bound).
18. **Веб-верификация названных технологий** (линза проверки фактов BMAD): версии и применимость — из внешних источников, не из памяти модели.
19. **Конфигурационная кастомизация без форка**: TOML-слои persistent_facts / external_sources / finalize_reviewers / external_handoffs / шаблон spine; файлы методологии неизменяемы, версии пинуются.
20. **Context Supply Chain**: доменно-ограниченный, версионированный контекст с provenance, freshness SLA, правами и отзывом; снимок контекста в Evidence Bundle; запрет «всей Wiki в RAG»; бюджет контекста (окно <50%) как измеримое правило.
21. **Модель ролей и допуска**: human SA/DA accountable только на high-significance; Architect Agent — design authority в workflow без corporate accountability; уровни допуска команд A0–A4 / R0–R5 по измеренному качеству.

### COULD (верхний слой, по мере зрелости)

22. **Worktree-фабрика + review/accept/merge** (паттерн Spec Kitty) для параллельных агентов на одном репозитории + Kanban-видимость factory-контура.
23. **Цикл обучения организации**: исправления человека → правила org/team/project + новые сенсоры; обязательный вопрос «что добавить на будущее?» на каждом гейте.
24. **Метрики харнесса**: Intent/Implementation/Validation Lead Time, I/V Tempo Ratio, First-pass Validation Rate, Agent-introduced Regression Rate, Architecture Drift Rate, Pattern Reuse Rate, Cost per Validated Outcome, доля решений, зафиксированных до реализации.
25. **EARS-нотация требований + spec check на противоречия** (из Kiro) для машиночитаемости intent; при желании — Quick Spec-режим для понятных изменений.
26. **Skill Supply Chain**: инвентарь навыков/промптов/MCP с политиками установки, сканированием безопасности и evals на инструкции (Tessl) + избирательная инъекция доменных стандартов в контекст под задачу (Agent OS Discover/Deploy).

**Чего в документах нет (не выдумываю):** конкретики реализации на Rust; готовых банковских доменных шаблонов спецификаций; независимых бенчмарков полного процесса (Macedo прямо фиксирует этот пробел — SWE-bench не меряет промежуточные артефакты); расхождение в балле Spec Kitty у Macedo (9 vs 10) между запиской и сводными документами.
