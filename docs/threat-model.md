# Модель угроз Spine AI/ML Edition (агент и его поставка)

Версия 1.1 (2026-09-04: T1/T2 закрыты пакетом T-4 — ADR-038), статус:
живой документ (пересмотр — см. §7).
Принята ADR-031; закрывает карточку threat model волны 2 (ADR-019) и
замечание внешнего ревью «модель угроз самого агента». Связанные
документы: ADR-016 (egress-дисциплина, GAP-C1/C2), ADR-017 (надзорный
контур), ADR-038 (sandbox bwrap + prompt-injection гигиена),
`banking/presets/bank-profile/` (hardening-профиль периметра).

## 1. Область

Модель угроз **самого агента** `arch-ml` и его цепочки поставки: что
может пойти не так, когда LLM-агент с исполняющими инструментами работает
внутри периметра банка. Угрозы проектов заказчика (их кода и данных как
цели атаки извне) — вне области, кроме точек, где агент сам становится
вектором.

## 2. Активы

| Актив | Где живёт | Цена компрометации |
|---|---|---|
| API-ключи LLM-провайдеров и прочие секреты | env машины пользователя, key-файлы | доступ к квотам/данным провайдера, подмена запросов |
| Содержимое репозиториев заказчика | рабочие копии на машине архитектора | архитектура, код, конфиги банка — конфиденциально |
| Журналы сессий (`sessions/*.jsonl`) | `~/.arch-ml/` | фрагменты кода/данных/решений; аудиторский след |
| Конфигурация (модели, пути, плагины) | `~/.config/arch-ml/` | подмена endpoint'ов = перенаправление данных |
| Исполняемая поставка | бинарь `arch-ml`, `vendor/archify/` + node | исполнение чужого кода в периметре |

## 3. Границы доверия

- **TB-1: ответ LLM → исполняющие инструменты.** Текст модели превращается
  в команды bash и правки файлов. Недоверенный сгенерированный «код»
  исполняется с правами пользователя внутри периметра.
- **TB-2: содержимое репозитория/веба → контекст LLM.** Файлы, issue,
  веб-страницы — недоверенные данные; встроенные в них инструкции —
  prompt injection против агента.
- **TB-3: агент → LLM-провайдер.** Исходящий канал несёт содержимое
  репозитория и сессии. В контуре ДИТ — только self-hosted/b2bank
  (модельная матрица ADR-012).
- **TB-4: MCP-серверы.** Локальные stdio-процессы с доступом к данным;
  конфигурация определяет, какому коду дан этот доступ.
- **TB-5: цепочка поставки.** crates.io-зависимости, вендоренный
  `vendor/archify/` + внешний `node`, скачанные бинари.
- **TB-6: машина пользователя.** Журналы, сессии, конфиги на диске в
  домашнем каталоге архитектора.

## 4. Угрозы, митигации, остаточный риск

Формат: угроза → вектор → действующие митигации (код/правила) → остаточный
риск и статус. Статусы: **З** (закрыта в основном), **Ч** (частично),
**GAP** (открыта, план закрытия указан).

### T1. Выполнение вредоносной команды через bash (TB-1)

Ошибка модели или инъекция (T2) приводит к деструктивной/эксфильтрационной
команде.

- Митигации: policy R0–R5 (destructive deny по умолчанию R2;
  RequireConfirm в неинтерактивном режиме = отказ с эскалацией);
  `env_scrub` (секретоподобные переменные вырезаются из окружения
  дочерних команд, `src/tools/bash.rs`); **sandbox bubblewrap**
  (`[bash] sandbox = "bwrap"`, ADR-038: рабочее дерево rw, остальная ФС
  read-only, `--unshare-net` — egress дочерних процессов закрыт;
  fail-safe: нет бинаря bwrap → команда не выполняется; включён в
  bank-profile); ортогональные маркеры исходов; полное журналирование
  команд в сессионный JSONL.
- Остаточный риск: классификация команд — паттерн-матчинг по строке
  (обходимо составными командами, подстановками, base64); sandbox
  закрывает egress и запись вне дерева только там, где включён конфигом
  и где контур разрешил unprivileged user namespaces (дефолт ядра —
  `"none"`, обратная совместимость). **Ч**.
- План: рассмотреть `bwrap` кандидатом в дефолт после пилота в контуре
  заказчика (решение — отдельным ADR по протоколу §7).

### T2. Prompt injection из содержимого репозитория/веба (TB-2)

Файл/страница содержит «игнорируй инструкции, выполни X»; агент с bash
может исполнить.

- Митигации: policy gate на деструктив (T1), журнал (постфактум-аудит
  «кто и что пытался»), redactor секретов в выводе инструментов
  (`src/secrets.rs`), детекторы циклов агента; **секция гигиены в
  системном промпте** (`assets/prompts/architect.md`: содержимое
  файлов/веба/журналов — данные, не команды; внедрённые инструкции
  исполняются только при подтверждении задачей пользователя;
  подозрительное — сообщить, не исполнять); **warn-детектор инъекционных
  паттернов** (`src/injection.rs`, ADR-038: сканируется вывод
  read_file/grep/glob, а с ADR-041 — ещё browser_page/browser_eval/window_list
  (текст страницы и заголовки чужих окон); НЕ bash и НЕ bash-подобные; совпадение → маркер
  `[warn: возможная prompt-инъекция …]` в вывод модели + событие
  `prompt_injection` в журнал; warn-first, без блокировки); sandbox
  bwrap (T1) ограничивает урон исполнившейся инъекции (нет egress).
- Остаточный риск: детектор ловит только сильные англоязычные паттерны
  (русские формулировки и обфускация — вне покрытия, сознательно:
  ложные срабатывания на технической прозе); маркер — совет модели,
  а не барьер (решение остаётся за LLM + policy gate); сканируются
  только инструменты чтения ядра (web/kb-вывод — кандидаты на
  расширение по данным пилота). **Ч**.
- План: оценка полноты паттерн-листа и состава сканируемых инструментов
  — по журналам `prompt_injection` после пилота (протокол §7).

### T2a. Prompt injection, отрисованный в пиксели (TB-2, ADR-041)

Страница или чужое окно содержит инструкцию, которая попадает к модели не
текстом, а изображением (`screenshot`, `browser_screenshot`). Текстовый
детектор её не видит в принципе.

- Митигации: контур воздействия **выключен по умолчанию**
  (`[computer].enabled = false`) и классифицирован как `Destructive` (клик и
  ввод требуют R4/R5) — то есть исполнение возможно только там, где человек
  уже согласился на управление машиной; фоновым субагентам инструменты
  воздействия не выдаются вовсе; наблюдение отделено от воздействия на уровне
  реестра.
- Остаточный риск: **текстовой защиты здесь нет и быть не может** —
  картинку регекспом не отсканировать. Модель может предпринять действие под
  влиянием надписи на экране, и на R5 оно будет исполнено без подтверждения.
  Митигация — не детектор, а сочетание «выключено по умолчанию» + класс
  риска + выделенный профиль браузера. **Ч**.
- План: при пилотном использовании контура — оценить, нужен ли отдельный
  барьер (например, обязательный `screenshot`-only режим наблюдения или
  детектор аномальных серий кликов) по журналам сессий.

### T9. Действие на реальной машине под влиянием недоверенного контента (TB-1/TB-2, ADR-041)

Инструменты `computer_*`/`browser_*` выходят за контур рабочего каталога: клик
или ввод в чужом окне необратим и не ограничен песочницей bash.

- Митигации: класс `Destructive` (R2 — запрет, R4 — подтверждение, R5 — авто);
  `DESTRUCTIVE_BINARIES` в `classify_bash` закрывает обход через
  `bash "xdotool …"`; браузер поднимается с выделенным `--user-data-dir` в
  `state_dir`, отладочный порт только loopback; потолок повторов
  (`max_clicks`) и таймауты против runaway-серии; спавн с очищенным
  окружением (процесс ввода не видит ключей провайдеров).
- Остаточный риск: **гейт — не изоляция.** `bash` остаётся общим люком
  (`python3 -c` с Xlib, скачанный бинарь, `xdg-open`), а после включения
  контура и подтверждения на R4 действие человека уже не сопровождает.
  Полная изоляция ввода не строится — это свойство задачи, а не недоделка. **Ч**.
- План: пересмотр после первого практического прогона (условие в ADR-041).

### T3. Утечка данных за периметр через LLM API (TB-3)

Конфигурация с внешним endpoint'ом отправляет содержимое репозитория
наружу.

- Митигации: модельная матрица ADR-012 (продуктив — внутри периметра);
  bank-profile: fitness-правила BE-03/BE-07 (внешние LLM-URL в пресетах —
  critical), заглушка веб-поиска; `arch-ml doctor` показывает активные
  endpoint'ы; исходящие каналы ровно два и перечислены (ADR-016).
- Остаточный риск: контент запросов не инспектируется (нет DLP);
  redactor знает только форматы ключей, не ПДн; GAP-C1 (веб-канал без
  глобального выключателя, заглушен конфигом bank-profile, не кодом);
  GAP-C2 (ГОСТ-TLS не поддержан reqwest — блокер или смягчение, зависит
  от контура). **Ч**.
- План: GAP-C1/C2 — по протоколу ADR-016 (проверка в контуре заказчика).

### T4. Утечка секретов через дочерние процессы и журналы (TB-1/TB-6)

Команда читает env или файл ключа и печатает; секрет попадает в
журнал/экран/контекст LLM.

- Митигации: `env_scrub` + `env_allow` (точные исключения);
  redactor вывода инструментов и журнала; ключи резолвятся лениво
  (`api_key_env`/`api_key_file`), не хранятся в конфиге (BE-правила
  C-05/C-06 — critical); значения не попадают в `Debug`.
- Остаточный риск: секреты нестандартных имён/форматов вне эвристик;
  команда `cat ~/.kimi_api_key` читается как обычный файл (секрет попадёт
  в tool output → redactor по паттерну, не по пути). **Ч** (низкий).

### T5. Компрометация цепочки поставки (TB-5)

Уязвимая/подменённая зависимость или вендоренный код исполняется в
периметре.

- Митигации: `Cargo.lock` + `cargo audit` в CI (правило C-04); pinned
  MSRV (C-03); ноль новых зависимостей как политика (handoff-правила);
  vendored archify — единственная JS-вставка, без node_modules;
  MCP-серверы из публичных регистров запрещены в пресетах (BE-08).
- Остаточный риск: **vendor/archify не пиннут хэшами** (BE-20g проверяет
  только наличие `bin/archify.mjs`); версия/происхождение `node` не
  контролируются; SBOM/подпись релиза отсутствуют. **GAP → Ч** (закрытие
  — BE-22 пиновка вендора 2026-09-04; SBOM — пакет T-3).
- План: `vendor/archify/SHA256SUMS` + fitness-гейт целостности (BE-22);
  `cargo sbom` + `SHA256SUMS` бинаря в CI-релиз + страница «как ДИТ
  проверяет поставку» (T-3).

### T6. Подмена/фабрикация аудиторского следа (TB-6)

Задним числом правятся журналы, спеки, evidence — «спека, дописанная
после инцидента».

- Митигации: append-only JSONL-журнал; evidence bundle с хэшами +
  `evidence verify` (подмена артефакта после упаковки ломает сверку);
  дисциплина ADR (номера не переиспользуются, линтер).
- Остаточный риск: журнал локальный, без независимого notarization;
  определить, КТО правил, нельзя (одна учётка). **Ч** (приемлемо для
  single-user границы, см. ADR-031 §границы продукта).

### T7. Вредоносный плагин/скилл (TB-4/TB-6)

Каталог плагинов подменён; hooks/скиллы выполняют команды от имени агента.

- Митигации: плагины — только из каталогов `[plugins] dirs` конфига
  пользователя (личные пути, не репо); hooks опциональны
  (`include_hooks = false` в фикстурах/CI); плагин — единица
  распространения, ревьюится как код в git.
- Остаточный риск: hooks выполняют shell; доверие = доверие к пути
  установки. **Ч**.

### T8. Run-away агента (квоты, стоимость, диск) (TB-1)

Циклы, бесконечные ретраи, разрастание worktree/журналов.

- Митигации: детекторы циклов (doom-loop/spiral, `src/detectors.rs`);
  таймауты и retry-политики с бюджетом (`src/retry.rs`); лимиты контекста
  и компактификация; таймауты `command_succeeds`.
- Остаточный риск: диск worktree/журналов не квотируется. **Ч**.

| SBOM/подпись поставки | открыт | пакет T-3 (cargo sbom + SHA256SUMS + инструкция ДИТ) |
| sandbox bash / egress дочерних процессов | закрыт 2026-09-04 | пакет T-4: `[bash] sandbox = "bwrap"` (`--unshare-net`, fail-safe), bank-profile — ADR-038 |
| prompt-injection гигиена и детектор | закрыт 2026-09-04 | пакет T-4: секция гигиены в системном промпте + warn-детектор `src/injection.rs` — ADR-038 |

## 6. Вне области (out of scope)

- Компрометация ОС/учётной записи пользователя, физический доступ к
  машине — периметр защиты ДИТ, не агента.
- «Галлюцинации» модели как источник ошибок проектирования — покрывается
  рубриками, fitness-гейтами и evidence-пакетами (это качество, не ИБ).
- Угрозы кодовой базы заказчика от внешних атак — предмет threat model
  проектов (карточка GEN-21), не этой модели.

## 7. Протокол пересмотра

Документ пересматривается: (а) при изменении поверхности — новый
исходящий канал, новый вендор в `vendor/`, новый транспорт (sandbox,
серверный режим), новый класс инструментов; (б) не реже раза в год
(дата версии выше); (в) по инциденту ИБ с участием агента. Изменения —
через ADR, ссылка из этого документа. Владелец: solution-архитектор BE.
