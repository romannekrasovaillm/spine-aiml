# Карточки гипотез и роутинг по фактам проекта

> Референс по механизму «память о намерении»: плагин
> `aiml/plugins/hypothesis-router` (скилл `hypothesis-card`, хук, правила)
> и библиотека `aiml/library/fitness/hypothesis-routing.yaml`.
> Все команды и числа ниже проверены живым прогоном 2026-09-13; там, где
> что-то не проверялось, это сказано прямым текстом.

## 1. Что такое карточка гипотезы

Карточка — каталог `~/hypotheses/<id>/HYPOTHESIS.md`: YAML-фронтматтер
(машиночитаемая часть) + короткое тело на русском (человеческая часть).
Фронтматтер — единственное, что читают скрипты.

Что она фиксирует:

- **намерение** одной фразой («хочу уметь прогонять лесенку CPT → SFT → RL
  на GB10»);
- **состояние** (`state`) и **триггеры** — факты, по которым намерение
  должно всплыть без поиска;
- **что выведено** (скиллы/плагины) и **что сделало бы это проектом**
  (`promote_when`);
- **журнал** касаний.

Зачем это нужно: скилл отвечает на «как», карточка — на «зачем и когда».
Скилл без карточки через полгода неотличим от тысячи соседей, и поиск по
`description` его честно не находит — не с чего предпочесть.

Схема фронтматтера — `aiml/plugins/hypothesis-router/skills/hypothesis-card/references/card-schema.md`,
живой пример — `.../references/example-laguna.md`.

## 2. Состояния и переходы

| Состояние  | Смысл                          | Где живут скиллы                          |
|------------|--------------------------------|-------------------------------------------|
| `fleeting` | мимолётный интерес, триггеры набросаны | теплица (не в общем поиске)        |
| `latent`   | пригодится, триггеры выверены  | теплица (поднимается триггером или явно)  |
| `active`   | применяется в текущей работе   | доменный ярус (грузится профилем проекта) |
| `project`  | выросло в отдельный проект     | репо проекта; карточка хранит ссылку      |
| `archived` | давно не трогали               | теплица, исключено из роутинга по умолчанию |

```
fleeting ──(вспомнил / триггер сработал)──► latent ──(использовал в задаче)──► active
   │                                          │                                   │
   └──(не трогал ~6 мес.)──► archived ◄───────┘(~12 мес.)        (условие «проект» выполнено)
                                                                                    ▼
                                                                                 project
```

Переходы **предлагают** скрипты (`card_review.py --touch/--promote`), а
**выполняет** человек. Архив — только вниз по ярусу, не удаление: удалённое
нельзя повысить обратно (см. `skills/hypothesis-card/SKILL.md`, §4–5).

## 3. Как поднять карточку

### 3.1 По фактам проекта (детерминированно)

Карточки всплывают не потому, что модель угадала по описанию, а потому что
в проекте лежит нужный файл. `card_match.py --project <dir>` обходит проект
и считает балл по совпавшим триггерам с весами: **файлы 3, ключи конфигов/env 3,
зависимости 2, слова намерения 1**. Порог по умолчанию — `--min-score 2`.

```bash
python3 aiml/plugins/hypothesis-router/skills/hypothesis-card/scripts/card_match.py \
    --dir ~/hypotheses --project ~/work/spark-run --min-score 2
```

**Что именно поднимается.** Порог абсолютный, а триггеров на карточку со
временем становится много (8–12), поэтому одного совпадения файла (вес 3)
достаточно, и на большом реестре поднимались все карточки. Отсюда три
надстройки над баллом (без изменения `--min-score` и весов):

| Что | Как |
|---|---|
| Нормированный балл | `norm = score / max_possible`, где `max_possible = 3*\|files\| + 3*\|keys\| + 2*\|deps\| + 1*\|words\|` — потолок балла карточки. Печатается в отчёте и в `--json`; в `routing.json` не попадает (формат таблицы прежний). |
| Число поднятых | `--max-cards N` (0, по умолчанию, — без ограничения). Порядок: балл убыв., при равенстве — `id` по возрастанию. |
| Диверсификация | `--dedupe J` (по умолчанию 0 — выключено). Если множества **совпавших** триггеров двух карточек дают Jaccard ≥ J, остаётся карточка с большим баллом (при равенстве — с меньшим `id`), вторая уходит в `suppressed` с причиной («перекрытие с <id> = <jaccard>») и в набор не входит. Диверсификация идёт **до** усечения: в top-N не остаётся дублей. |

```bash
# пятёрка самых сильных карточек без почти-дублей
python3 .../card_match.py --dir ~/hypotheses --project ~/work/spark-run \
    --max-cards 5 --dedupe 0.5
```

### 3.2 По намерению

Тот же матчинг, но по тексту задачи (`--intent "<фраза>"`):

```bash
python3 aiml/plugins/hypothesis-router/skills/hypothesis-card/scripts/card_match.py \
    --dir ~/hypotheses --intent "хочу обучить 3B на Spark"
```

Проверено живым прогоном на карточке `example-laguna.md`:

```
Подходящие гипотезы (1 из 1):
  [ 3] laguna-gb10-ladder — Лесенка маленьких моделей на GB10  (latent) norm=0.075
       по: words: Spark, 3B, обучить
```

Балл 3 при пороге 2 — карточка поднимается; `norm=0.075` — это 3 из 40
возможных баллов карточки (у неё 4 файла, 3 ключа, 3 зависимости, 13 слов),
то есть сработал слабый, словесный слой. Слова в триггерах
`words` матчатся по границам токенов (`(?<!\w)слово(?!\w)`, регистр
не важен), поэтому «3B», «Spark» и «обучить» попали в фразу, а,
например, «обучение» — нет.

### 3.3 Завести новую

```bash
python3 .../scripts/card_new.py --dir ~/hypotheses --id <slug> \
    --title "..." --state latent --source "..." \
    --trigger-file 'eval_results_*.json' --trigger-key LAGUNA_MEM_FRACTION \
    --trigger-word GB10 --skill laguna-ladder-run
```

Тело карточки скрипт оставляет заготовками — дописать руками.

## 4. `routing.json`

Детерминированный слой читает не карточки, а плоскую таблицу триггеров,
которую собирает `card_match.py --emit-routing <файл>` (по умолчанию
`$HYPOTHESES_DIR/routing.json`):

```json
{"min_score": 2,
 "rows": [
   {"trigger": "rollouts_log.jsonl", "kind": "files", "weight": 3,
    "card": "laguna-gb10-ladder", "state": "latent",
    "skills": ["laguna-ladder-run", "ood-stage-eval", "..."]}
 ]}
```

На карточке-примере таблица вышла в **23 строки**, `min_score: 2`.
Правило подъёма: сумма весов совпавших триггеров карточки ≥ `min_score`.
Формат и состав таблицы отбором не затрагиваются: `--max-cards`/`--dedupe`
влияют только на отчёт и `--json`, `routing.json` — по-прежнему
`{"min_score": N, "rows": [...]}` со всеми триггерами реестра.
Пересобрать после правки карточек:

```bash
aiml/plugins/hypothesis-router/hooks/hypothesis-hook.sh refresh
```

## 5. Что делает хук на каждом событии

`hooks/hypothesis-hook.sh <событие> ...` — тонкая обёртка над
`hooks/hypothesis_hook.py` (stdlib Python 3, без LLM). Коды выхода:
**0** ок, **2** ошибка аргументов/окружения, **3** проверка не пройдена.

| Событие       | Аргументы                              | Что делает |
|---------------|----------------------------------------|------------|
| `intent`      | `"<текст>" [project_dir]`              | Подбирает карточки по намерению (+фактам проекта, если дан каталог) и печатает одну строку для TUI; `--json` — полный список. Отбор: до 5 карточек, диверсификация при перекрытии ≥ 0.5 (`HYPOTHESES_MAX_CARDS`/`HYPOTHESIS_DEDUPE`). Каталога `HYPOTHESES_DIR` нет → exit 2. |
| `pre-handoff` | `<project_dir> [handoff_dir]`           | Считает совпадения по `TASK.md`/`ARCHITECTURE.md` пакета (до 8 карточек, диверсификация ≥ 0.5), пишет `<handoff>/HYPOTHESES.json` (`hits` — только поднятые, у каждого `norm`, плюс `suppressed`), добавляет в `MANIFEST.json` ключ `hypotheses` и собирает `skills` только с поднятых карточек. С `HYPOTHESIS_ANNOTATE=1` дописывает в `TASK.md` блок ≤ 400 символов. Нет каталога handoff → exit 2. |
| `post-accept` | `<handoff_dir> <project_name>`         | Делает `--touch` карточкам из `HYPOTHESES.json` — фиксирует факт использования (данные для повышения/понижения, не мнение). |
| `refresh`     | —                                      | Пересобирает `$HYPOTHESES_DIR/routing.json`. |
| `check`       | `<handoff_dir>`                        | exit 0, если `HYPOTHESES.json` есть и `routing.json` не старее карточек; иначе exit 3 с причиной. Это цель fitness-правил. |

Окружение: `HYPOTHESES_DIR` (по умолчанию `~/hypotheses`),
`HYPOTHESIS_MIN_SCORE` (по умолчанию 2), `HYPOTHESES_MAX_CARDS`
(по умолчанию 8 для `pre-handoff` и 5 для `intent`, 0 — без ограничения),
`HYPOTHESIS_DEDUPE` (по умолчанию 0.5; 0 — диверсификация выключена).
Неразобранное значение — предупреждение в stderr и дефолт события, не падение
хука. Подавленные карточки не теряются: они в `suppressed` и в строке вывода
(«подавлено перекрытием: N — …»), причина — пара и коэффициент Jaccard.

`HYPOTHESES.json` потребители читают как раньше: `min_score` и `hits[]`
(`card`, `state`, `score`, `skills`) на месте, добавлены `norm` у каждого
попадания, `suppressed` и эхо отбора (`max_cards`, `dedupe`). Ядро Spine
разбирает `hits[]` с `#[serde(default)]` и лишние поля игнорирует.

Проверено: `check` на каталоге без `HYPOTHESES.json` →

```
FAIL: в handoff-пакете нет HYPOTHESES.json (pre-handoff не выполнен)
exit 3
```

а с приложенным `HYPOTHESES.json` — `OK`, exit 0.

## 6. Fitness-правила

`aiml/library/fitness/hypothesis-routing.yaml` — 4 правила в схеме движка
(`constraints:` + `command_succeeds`), исполнимые из корня репо:

| id     | name                          | severity     | Проверка |
|--------|-------------------------------|--------------|----------|
| HYP-01 | `hypothesis_handoff_attached` | warn         | есть `.arch-handoff` → в нём обязан быть `HYPOTHESES.json` (проверяется прямо в пакете, без захода в плагин — поэтому правило работает в любом репозитории) |
| HYP-02 | `hypothesis_routing_fresh`    | warn         | `routing.json` существует и не старее `HYPOTHESIS.md`; нет карточек → pass |
| HYP-03 | `hypothesis_card_has_triggers`| **error**    | в `card_review.py` есть строка «нет триггеров»; нет каталога карточек → pass; скрипт не найден → правило **пропускается** с сообщением |
| HYP-04 | `hypothesis_touch_on_accept`  | warn, `unverifiable: true` | не исполняется (post-accept пишет в журнал — побочный эффект на каждом `control check` недопустим) |

Проверено живым прогоном
`arch-ml control check . --constraints aiml/library/fitness/hypothesis-routing.yaml`:

- каталог карточек с карточкой без триггеров → `error: 1`, **Итог: FAIL, exit 1**;
- здоровый каталог + `.arch-handoff` без `HYPOTHESES.json` → `error: 0,
  warn: 1`, **Итог: PASS, exit 0**.

Во втором случае red нет намеренно: warn не блокирует гейт (значимость
`passed` считает только `severity: error`), а `hypothesis_handoff_attached`
специально не `error` — репозиторий с собранным handoff-пакетом, но без
гипотез, не должен уходить в красный.

**Путь к плагину в правилах.** Движок исполняет команду правила через
`bash -c` с cwd = корень ПРОВЕРЯЕМОГО репозитория, поэтому репо-относительный
путь `aiml/plugins/...` разрешается только внутри spine-aiml. Отсюда две меры:
HYP-01 вообще не ходит в плагин (проверяет файл в пакете), а HYP-03 берёт
путь к скрипту из `$HYPOTHESIS_PLUGIN` (абсолютный путь к каталогу плагина),
иначе из репо-относительного, и при отсутствии скрипта пропускается с явным
сообщением. Без этого чужие репозитории получали бы провал по причине
«файл не найден» — то есть правило обвиняло бы за то, что его же скрипт не
лежит в чужом дереве.

**Копии правил в плагине нет.** В исходном артефакте
`aiml/plugins/hypothesis-router/fitness/hypothesis-routing.yaml` написан в
собственном формате плагина (вложенный `check:`, `description:`,
плейсхолдеры `{handoff_dir}`/`{project_name}`) — движок такой файл
отвергает, а из манифеста ядро читает только
`name/version/description/keywords/hooks`. Держать в репозитории вторую,
нерабочую копию правил значило бы заводить два источника правды, поэтому
здесь правила живут ровно в одном файле — этом.

## 7. Чего механизм НЕ делает

- **Не выбирает по смыслу.** Матчинг — по именам файлов, ключам, строкам
  зависимостей и словам. «Похожая по духу» карточка не всплывёт, если
  триггеры не совпали.
- **Не заменяет дисциплину.** Хук вызывается явно; сам он ничего не
  поднимает и не превращает в проект. Касания (`post-accept`) — единственные
  данные для смены состояний; без них теплица только растёт.
- **Словесные триггеры шумные.** Вес 1, порог по умолчанию 2: одно слово
  карточку не поднимает, но два частых — уже могут дать ложное срабатывание.
  Лучше один точный файл (`weight 3`), чем пять общих слов.
- **Не проверяет семантику триггеров.** `card_review.py` ловит только
  пустой список триггеров, не «плохие» триггеры.
- **`card_review.py` предлагает переходы, а не выполняет их.**
- **Не трогает удаление карточек.** Только `archived` (понижение яруса).

## 8. Как отключить

Механизм opt-in — по умолчанию не работает ничего:

1. **Хук** запускается только явным вызовом
   `hooks/hypothesis-hook.sh <событие>` (из скрипта/CI/хука вашего агента).
   Нет вызовов — нет роутинга. Не задан `HYPOTHESES_DIR` или в нём нет
   карточек — `intent` вернёт exit 2, `check`/`refresh` ничего не найдут.
2. **Fitness-файл не подключён к гейту репозитория.** `CONSTRAINTS.yaml`
   на него не ссылается: живой `arch-ml control check .` в этом репо даёт
   «Правил: 7, нарушений: 0» — правил HYP там нет. Чтобы правила
   участвовали, их передают явно:
   `--constraints aiml/library/fitness/hypothesis-routing.yaml`.
3. **Отключить одно правило** можно записью верхнего уровня `overrides:`
   (в том же constraints-файле) с тремя обязательными полями — `rule`,
   `adr`, `until`; неполный override = error-находка и игнорируется,
   просроченный — правило снова действует (см. `docs/corp-spine.md`).
4. **HYP-01 самоотключается** вне каталога `.arch-handoff`
   (`test -d .arch-handoff || exit 0`), HYP-02/HYP-03 — когда в
   `HYPOTHESES_DIR` нет ни одной карточки, HYP-04 не исполняется никогда
   (`unverifiable`).

## 9. Что не проверено

- Реальная интеграция хуков в ядро (`harness.rs` / точка `accept`) не
  сделана — в `docs/spine-integration.md` это раздел «с правкой ядра», а
  Rust здесь не трогался. Работает только явный вызов хука.
- Перенос `routing.json` в сенсор значимости (`detect_diff_triggers`-подобный)
  — предложение, не реализация.
- На живом большом наборе карточек точность `words`-триггеров не измерялась;
  вывод «шумно» опирается на веса/порог и на разовое наблюдение.

См. также: `docs/plugins_and_skills.md` (установка плагинов), `docs/control.md`
(fitness-функции), заметку о карточке примера —
`aiml/plugins/hypothesis-router/skills/hypothesis-card/references/example-laguna.md`.
