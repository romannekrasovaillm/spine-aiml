# SPEC H0.3: дистиллят с адресным следом (address trace)

Статус: проект. Домен: AI/ML-исследователь (`arch-ml`). Затрагивает `src/control.rs`,
`src/distill.rs`, `src/adr_registry.rs`, `assets/prompts/skill_distiller.md`,
`CONSTRAINTS.yaml`, `docs/control.md`.

## 1. Проблема (что закрываем)

Рецензия §3.5: дистиллят требует «писать без дословных цитат», но это противоречит
источнику как `path:line` — знание теряет проверяемую связь с инвариантом и
превращается в пересказ. Нужен **адресный след**: дистиллят несёт *ссылку* на
инвариант (`ADR-014:rule-7`, `spine:AD-3`, `rule:ML-SKILL-1`), а не его
парафраз, и готовность дистиллята проверяется **механически** — каждая ссылка
резолвится в существующий узел (ADR-запись, spine-блок, fitness-правило).

Это харнесс-сторона H0.3: она делает наблюдаемым то, что бенчмарк
`benchmarks/spine-vs-claude/SPEC.md` §6 называет `trace_coverage`
(`<AC-id> -> <ADR-id>`), а §9 — H0.3 `eval_bar_ok`. В гейте LLM не участвует;
резолюция ссылок детерминирована.

## 2. Формат ссылки (грамматика адреса)

Адрес — токен без пробелов. Канонический вид в frontmatter — элемент списка
`trace:`; в теле — в квадратных скобках `[<адрес>]` (не Markdown-ссылка:
скобка `()` запрещена, чтобы не конфликтовать с `upstream_coverage`).

```
spine:AD-<n>          # заголовок `## AD-<n>:` в ARCHITECTURE-SPINE.md
spine:AD-BE<n>        # заголовок `## AD-BE<n>:` в ARCHITECTURE-SPINE-BE.md
ADR-<nnn>             # запись реестра ADR (docs/adr/*.md | model/ADR-*.md)
ADR-<nnn>:rule-<m>    # именованное правило №m внутри ADR-<nnn> (см. §3)
rule:<id>             # fitness-правило с `id: <id>` в CONSTRAINTS.yaml (C-04, ML-SKILL-1)
```

Регулярка извлечения (одна на обе формы):

```regex
(?m)(?P<a>spine:AD-(?:BE)?\d+|ADR-\d{1,4}(?::[A-Za-z0-9][A-Za-z0-9_-]*)?|rule:[A-Za-z][A-Za-z0-9_-]*)
```

Нормализация при сравнении множеств: `ADR-014` ≡ `ADR-14` → к `ADR-%03d`;
номера spine — десятичные без ведущих нулей.

### 2.1 Резолюция `ADR-<nnn>:rule-<m>`

Фрагмент после `:` резолвится в **объявленный анкер** файла `ADR-<nnn>`; порядок
пунктов не важен (ссылка не ломается от вставки пункта). Анкер объявляется одним
из двух способов:

```markdown
### rule-7 Идемпотентность реестра        <!-- заголовок: slug = rule-7 -->
- **rule-7** — продвижение только по явному аппруву   <!-- жирный ярлык пункта -->
```

Резолюция = файл содержит строку, чей slug-заголовка или жирный стартовый ярлык
совпадает с фрагментом:

```regex
(?m)^#{2,6}\s*rule-(?P<m>\d+)\b | ^\s*[-*]\s*\*\*rule-(?P<m>\d+)\*\*
```

Если ADR не объявляет `rule-<m>` — ссылка **невалидна**, а не «примерно та».
Автор, желающий адресовать пункт, обязан его пометить. Это осознанная цена:
гейт честен, а не угадывает.

## 3. Где в дистилляте живёт след

Оба артефакта дистилляции несут `trace:` во frontmatter (пишется существующим
`upsert_fm_field`/`stamp_playbook`, `src/distill.rs`):

```markdown
---
name: gpu-quota-admission
description: ... (триггерная формулировка)
source: sessions/2026-09-11-gpu-quota.md
trace:
  - ADR-014:rule-7
  - spine:AD-3
  - rule:ML-SKILL-1
---
```

- **SKILL.md** (`DistillRoute::Skill`) — frontmatter обязателен, `trace:`
  обязателен.
- **playbook** (`DistillRoute::Playbook`) — `trace:` добавляется рядом с
  `stamp_playbook` (`type/status/uses/skill_candidate/steps_sha256/created`).
- **Md** (`DistillRoute::Md`) — свободный документ; правило на него не
  распространяется по умолчанию (glob исключает), `trace:` допустим вручную.

Тело скилла содержит **адресные ссылки вместо пересказа**:
`Продвижение только по аппруву [ADR-014:rule-7].` Парафраз инварианта без адреса
не запрещён синтаксически, но адресный след — обязателен, и он же аудиторский.

## 4. Fitness-правило

Отдельный `RuleKind` (резолвится и по `type:`, и по `as_str()`):

| Поле | Значение |
|---|---|
| имя | `address-trace` (пример в `CONSTRAINTS.yaml`: `id: ML-TRACE-1`) |
| тип | `address_trace` (`RuleKind::AddressTrace`) |
| glob (дефолт) | `["**/distillate/**/*.md", "**/skills/*/SKILL.md"]` |
| `pattern` (опц.) | regex-фильтр: анализируются только адреса, матчащие паттерн (напр. `^ADR-`) |
| `require` (**новое поле** `Vec<String>`, опц.) | адреса, **обязательные** в файле (покрытие-надмножество) |
| `path` (опц.) | корень резолюции (дефолт — корень репозитория) |
| `severity` | по умолчанию `error` (не `critical`: не валит hard_fail, но и не зелёный) |

Семантика (нарушение → `LintIssue` на файл, по одной находке на адрес):

1. **пустой след** — в файле нет ни одного адреса → `address_trace: пустой след`
   (дистиллят без следа = «ничего не делать» … не даёт зелёного гейта);
2. **нерезолвленный адрес** — каждая ссылка из `trace:` ∪ inline `[…]` обязана
   резолвиться; иначе `address_trace: ADR-014:rule-9 не резолвится (нет анкера в ADR-014)`;
3. **непокрытый required** — при непустом `require` каждый его адрес обязан
   присутствовать: `address_trace: обязательный AD-3 не покрыт`;
4. при заданном `pattern` — адреса вне паттерна игнорируются (позволяет,
   например, требовать резолюцию только `ADR-*`, не трогая `rule:*`).

Адрес в квадратных скобках в теле, отсутствующий в `trace:` — не ошибка, но
учитывается в множестве (гейт видит обе формы).

### 4.1 Резолюция адреса (детерминированно)

```
spine:AD-<n>       → в ARCHITECTURE-SPINE*.md есть `^##\s*AD-(BE)?<n>\s*:`
ADR-<nnn>          → adr_registry::build_registry(root).entries содержит number == nnn
ADR-<nnn>:rule-<m> → (1) есть entry nnn; (2) в его файле — анкер §2.1
rule:<id>          → в CONSTRAINTS.yaml есть правило с `id == <id>`
```

Реестр строится **один раз** на прогон правила (не на файл).

## 5. Реализация

### 5.1 `src/control.rs`

```rust
/// Адрес инварианта/правила в дистилляте (H0.3).
pub(crate) struct Address { pub raw: String, pub kind: AddressKind, pub frag: Option<String> }

/// Индекс резолвируемых узлов репозитория (строится один раз).
pub(crate) struct AddressIndex {
    pub spine: BTreeSet<String>,   // "AD-3", "AD-BE1"
    pub adr: BTreeMap<u64, String>, // nnn -> путь к файлу ADR
    pub rules: BTreeSet<String>,   // "C-04", "ML-SKILL-1"
}

pub(crate) fn build_address_index(root: &Path) -> Result<AddressIndex>;
pub(crate) fn extract_addresses(text: &str) -> Vec<Address>;      // чистая
pub(crate) fn address_trace_violations(
    text: &str, index: &AddressIndex, require: &[String], pattern: Option<&str>,
) -> Vec<String>;                                                  // чистая
```

- `RuleKind::AddressTrace` (+ `as_str() -> "address_trace"`), arm `eval` рядом с
  `SkillContract`/`PlaybookGraduation` (сбор файлов по glob минус `exclude_glob`,
  построение индекса, per-file вердикт).
- `FitnessRule` — новое поле `#[serde(default)] pub require: Vec<String>`
  (обратно совместимо: старые конфиги десериализуются).
- Резолюция `spine:*` переиспользует разбор заголовков из spine-линтера;
  `ADR:*` — `adr_registry::build_registry` (`RegistryEntry.number`/`.file`);
  `rule:*` — существующий парсер правил из `CONSTRAINTS.yaml`.

### 5.2 `src/distill.rs`

- После генерации текста и ДО `write_atomic` — прогон
  `address_trace_violations`; непустой результат → `ToolOutput::err` с перечнем
  (тот же паттерн, что уже применяется к `skill_contract_violations`).
- Playbook: `stamp_playbook` дополнительно проставляет/сохраняет `trace:`
  (после `steps_sha256`, до `created`).
- Мок-LLM в тестах возвращает frontmatter с `trace:`; проверяется, что адреса
  не потеряны при записи и что нерезолвленный адрес → ошибка инструмента.

### 5.3 `src/adr_registry.rs`

- `pub(crate) fn anchor_present(file: &Path, frag: &str) -> Result<bool>` (или
  переиспользование чтения записи): проверка анкера §2.1 внутри ADR-файла.

### 5.4 `assets/prompts/skill_distiller.md`

- В формат frontmatter обоих маршрутов добавляется обязательный `trace:`
  (список адресов).
- Правило: «инвариант не пересказывай — сошлись адресом; если адрес не
  резолвится, НЕ выдумывай его, а пометь `unverifiable` в тексте».
- Шпаргалка грамматики §2 и требование объявлять анкер `rule-<m>` в ADR, если
  на пункт ссылаешься.

### 5.5 `CONSTRAINTS.yaml` и `docs/control.md`

## 6. Тесты

`src/control.rs` (`#[cfg(test)] mod tests`, стиль соседних sensor/skill-тестов):

- `extract_addresses` — `spine:AD-3`, `ADR-014:rule-7`, `rule:ML-SKILL-1`,
  inline `[…]`, мусор вне грамматики не ловится;
- `address_trace_violations` на собранном из структур `AddressIndex` (без fs):
  - все адреса резолвятся → пусто;
  - `ADR-014:rule-9` без анкера → находка; `spine:AD-99` → находка;
    `rule:ZZZ` → находка;
  - пустой след → «пустой след»;
  - `require = ["AD-3"]` при отсутствии → «обязательный AD-3 не покрыт»;
  - `pattern = "^ADR-"` гасит находку по `rule:*`;
- `RuleKind` round-trip: serde `type: address_trace` ↔ `as_str()`;
- интеграционный: временный каталог + `CONSTRAINTS.yaml` + fixture-скилл с
  валидным/битым следом → зелёный/красный вердикт `check`.

`src/distill.rs`:

- `SkillDistillTool` с mock-LLM, вернувшим `trace: [spine:AD-3]` и `ADR-014:rule-7`
  (ADR создан в temp-репо) → артефакт содержит `trace:`;
- mock вернул нерезолвленный адрес → `ToolOutput::err`, файл не записан
  (`produced_files` пуст);
- playbook: `trace:` переживает `graduate_playbook` (не затирается `stamp_playbook`).

## 7. Связь с бенчмарком и белыми пятнами

- H0.3/§3.5: `address_trace` — детерминированный гейт покрытия; в бенчмарке ему
  соответствует `trace_coverage` (`AC-<nn> -> <ADR-id>`), в дистилляте —
  `trace:` + резолюция. Один и тот же принцип: адресный след, сверяемый машиной.
- Белое пятно (а) подотчётность: адрес `rule:<id>`/`ADR-<nnn>` привязывает
  дистиллят к версии инварианта — база для `spec_binding`/журнала решений.
- Белое пятно (б) независимый eval-бар: `require:` фиксирует обязательные
  адреса заранее (человеком), а не постфактум моделью.
- EU AI Act — только фрейминг; комплаенс-чеклистов правило не вводит.

## 8. Ограничения

- Анкерная разметка `rule-<m>` — новое авторское соглашение; существующие ADR
  без неё цитируются лишь до уровня файла (`ADR-014`) или заголовка-слага.
- Гейт не оценивает *семантическую* верность выбора адреса (правильный ли ADR
  процитирован) — только его существование. Это осознанная граница H0.3:
  механически проверяемо существование, не истинность.
