# Флот прогонов: изоляция worktree и гейт мерджа владельца

Мотив — сравнительный разбор «Харнесс vs Anthropic SDLC» (AI-native SDLC
playbook Anthropic): у Anthropic «агент не аппрувит свой код и не имеет пути
в main» — enforced платформой, а не дисциплиной промптов. Здесь то же
закрывается конфигурацией поверх существующей worktree-фабрики
(`src/worktree.rs`).

## Два переключателя: `[fleet]`

```toml
[fleet]
require_worktree = true    # прогоны харнессов — только в изолированном worktree
merge_gate = "owner"       # мерж результата — только с подтверждением владельца
```

Оба дефолта выключены/совместимы с прежним поведением: `require_worktree =
false` (прогон в рабочем дереве как раньше), `merge_gate = "owner"` (гейт
включён для `arch fleet merge`; прямые `arch worktree accept` им не
затрагиваются).

## Enforcement: нет пути в main (`require_worktree`)

Когда `require_worktree = true`, прогон кодового харнесса — инструмент
`harness_run` и CLI `arch harness-run` — обязан идти в изолированном git
worktree:

1. Создаётся worktree фабрики: ветка `arch/<харнесс>-<timestamp>` (run-id,
   напр. `claude-code-20260825143000`), каталог — вне репозитория
   (`~/.arch-ml/worktrees/<repo-slug>/<run-id>`).
2. Handoff-пакет `.arch-handoff/` по контракту в git не коммитится, поэтому
   копируется в worktree автоматически — исполнитель получает TASK.md и
   MANIFEST.json как обычно.
3. Харнесс работает с `cwd` = worktree; авто-коммит хвоста (если включён)
   фиксирует работу в ветке worktree. Основное дерево не изменяется ни на
   байт.
4. Каталог не git-репозиторий — понятная ошибка ДО запуска харнесса.

Сводка прогона сообщает run-id и дальнейшие шаги; merge — только через гейт
владельца (см. ниже), отклонение — `arch worktree drop <run-id>`.

## Гейт мерджа: `arch fleet merge <run-id>`

Интеграция результата прогона в основную ветку — решение владельца:

```bash
arch fleet merge claude-code-20260825143000                 # review: сводка, мерж ОТКЛОНЁН (exit 1)
arch fleet merge claude-code-20260825143000 --owner-approve # влить (merge --no-ff + уборка worktree)
```

Без подтверждения человека (ни `--owner-approve`, ни `--approver`; при
`merge_gate = "owner"`; неизвестные значения трактуются как `owner` —
безопасная интерпретация) печатается сводка для решения человеком:

- коммиты ветки и `git diff --stat` против основного дерева;
- состояние worktree (незакоммиченные изменения подсвечиваются — merge их
  не подхватит);
- статус контракта результата (`status=complete|partial|blocked`) из лога
  прогона `reports/harness/*.log`, если лог с этим run-id найден (evidence).

С подтверждением выполняется accept-семантика worktree-фабрики: merge
`--no-ff` в текущую ветку основного дерева, удаление worktree и ветки.
Подтверждений два:

```bash
arch fleet merge <run-id> --owner-approve                 # флаг владельца
arch fleet merge <run-id> --approver "roman"              # именной аппрувер + журнал приёмки
```

`--approver` — тот же именной обход, что у `worktree accept --approver`
(ADR-046, п. 2): он закрывает и гейт владельца, и блокирующий вердикт
ревьювера `NOT-READY`, а решение уходит в append-only журнал приёмки
(`state_dir/accept/decisions.jsonl`) — той же записью, что у accept.
`--owner-approve` именным обходом НЕ является: без `--approver` вердикт
`NOT-READY` блокирует и его. Отказ при незакоммиченных изменениях — как у
`arch worktree accept`. `merge_gate = "none"` отключает гейт (мерж без
подтверждения).

## Гейт приёмки: вердикт ревьювера блокирует merge (ADR-046, п. 2)

`NOT-READY` ревьювера — не украшение журнала, а блокировка интеграции.
Перед merge `arch worktree accept <name>` (и `arch fleet merge`, который
идёт через ту же accept-семантику) читает журналы прогонов флота
(`state_dir/fleet/*.jsonl`) и ищет вердикты гейта `review`, относящиеся к
ветке `arch/<name>`:

- последний вердикт — `NOT-READY` → **отказ** с текстом находок ревьювера
  (из лога узла `state_dir/fleet/<run-id>-<node-id>.log`) и подсказкой
  обхода; основное дерево не трогается;
- последний вердикт — `READY` → merge без вопросов;
- вердиктов по ветке нет → merge, но в выводе явная пометка
  «вердиктов ревью не найдено — не проверено» (отсутствие проверки ≠ успех:
  журнал мог быть очищен).

Связь «вердикт ↔ ветка» берётся из СТРУКТУРНЫХ полей журнала, без догадок и
без разбора текста: событие вливания зависимости
(`gate = "dependency:<узел>"`) несёт поле `branch` с именем влитой ветки,
поэтому вердикт ревьювера относится к веткам, влитым в дерево его узла
(паттерн `review_pair`); плюс прямое совпадение `node_id` с именем
принимаемого worktree. Текст `detail` не читается — формулировка не
контракт. Нет ни одного признака — вердикт к этой ветке не относится;
журнал старого формата (без поля `branch`) даёт честное «вердиктов по ветке
не найдено».

Обход блокировки — **только** явным именным аппрувером:

```bash
arch worktree accept impl-20260913120000 --approver "roman"   # merge + запись решения
arch fleet merge impl-20260913120000 --approver "roman"       # то же для гейта мерджа
```

Решение уходит в append-only журнал приёмки
(`state_dir/accept/decisions.jsonl`: аппрувер, ветка, вердикт, находки,
время). Запись фиксирует решение, но не «закрывает» вердикт: журнал флота
append-only и не переписывается, поэтому обход требуется каждый раз.
Автоматического merge нет — приёмка остаётся рукой человека.

Связанное: `arch fleet audit` — SSOT-аудит дублей/дрейфа копий спайна
(см. README и `кейсы/fleet-spine-drift`); для каждого worktree показывает
размер на диске (`du -sh`, недоступен — «—») и возраст последнего коммита
(`git log -1`, не-git — «—»), а для worktree старше 30 дней — рекомендацию
prune (`git worktree remove`); `arch worktree …` — ручная
фабрика worktree (`docs/slash_commands.md`, `/worktree`).

## Планы флота: паттерны оркестрации (ADR-042)

Веер — не единственная топология передачи архитектуры в работу. Команда
`arch-ml fleet plan|run|resume` исполняет **план флота**: паттерн оркестрации
(`fanout`, `pipeline`, `map_reduce`, `tournament`, `review_pair`, `ralph`,
`walking_skeleton`, `dag`) разворачивается в граф узлов, узлы идут волнами по
топологическим уровням, конкурентность ограничена пулом (`max_parallel`),
результат каждого узла проходит механические гейты, а интеграция в main
остаётся за владельцем (`fleet merge --owner-approve`).

- каталог паттернов, схема плана, гейты и resume — [fleet_patterns.md](fleet_patterns.md);
- `arch-ml fleet plan propose --repo .` — черновик плана по
  `.arch-handoff/MANIFEST.json` (паттерн по маршруту значимости);
- `arch-ml fleet plan propose --from-adrs [--adr-dir <D>] [--status proposed|accepted|all]`
  — план работ из набора решений `docs/adr/*.md` (ADR-045): один узел на ADR,
  рёбра — из frontmatter `depends_on`, `outputs` — объявленные `affects`;
  ссылка на ADR вне отбора даёт предупреждение «зависимость вне плана»;
- `arch-ml fleet plan validate <plan>` — механический гейт для CI;
- журнал прогона — `state/fleet/<run-id>.jsonl`, рядом снимок плана
  (`<run-id>.plan.toml`), поэтому `fleet resume` самодостаточен.

## Гейт независимости исполнителей (ADR-045)

Мотив — факт 13.09.2026: два независимых потока правили один TUI-слой,
расхождение нашли глазами. Правило живёт в `validate_plan` и действует на
**любой** план (рукописный тоже — план правят после генерации):

- для пары узлов **без пути в графе зависимостей** (неориентированная
  достижимость: прямой или транзитивный `depends_on` в любую сторону)
  непустое пересечение `outputs` — **ошибка**: «независимые узлы … затрагивают
  один путь» (подсказка: добавить `depends_on` либо развести пути);
- непустое пересечение `spec_files` — **предупреждение**: совместное чтение
  одного источника к расхождению не ведёт, усиливать до ошибки нельзя.

Пустые элементы списков путей игнорируются; сравнение — по строкам. В режиме
`--from-adrs` ошибка гейта останавливает команду (exit 1), черновик плана при
этом записан — владелец правит рёбра, а не генерирует заново. Метаданные ADR
читаются из YAML-frontmatter (`id`, `title`, `status`, `depends_on`,
`affects`, `spec_files`, `route`, `domain`); без frontmatter работает фолбэк
по заголовку `# ADR-NNN. <title>` и строке `- Status:`, но узел получает
предупреждение «ADR без frontmatter: зависимости не видны» — тихая деградация
запрещена.

## Baseline-судья гейтов (ADR-046)

Гейт `command` вида `./target/debug/arch-ml control check .` исполняется
бинарём, который собрал сам исполнитель: дельта, меняющая проверки в `src/`,
судила бы себя сама. Поэтому `fleet run` фиксирует **baseline-судью ДО запуска
узлов**:

1. `arch-ml fleet run --plan <файл> --judge <путь>` — явный бинарь (приоритет);
2. `[fleet] judge_binary = "<путь>"` в `config.toml`;
3. иначе — бинарь, запустивший флот (`current_exe`), если он вне ворктри узла.

Политика `command`-гейта, зовущего судью (`arch-ml` или путь к нему):

- судья **вне** ворктри узла — поведение прежнее (`ok`), в отчёт гейта идут
  путь судьи и `sha256` его файла;
- судья **внутри** ворктри, baseline задан — токен судьи в команде подменяется
  baseline-путём (аргументы и структура команды не меняются), в отчёте —
  фактический судья;
- судья **внутри** ворктри, baseline не задан (или сам внутри ворктри) —
  гейт **падает**: «самооценка запрещена: укажите baseline-судью».

Проверка идёт по границам токенов, поэтому `cat notes/arch-ml.md` судьёй не
считается. В CI baseline надо собирать явно — при его отсутствии гейт падает,
а не проходит тихо.

Фактический судья виден не только в отчётах узлов: событие старта прогона
`plan_started` в журнале `state/fleet/<run-id>.jsonl` несёт структурные поля
`judge_path` и `judge_sha256` (путь и хеш файла baseline-судьи; `null` —
судья не задан). Аудит уровня прогона отвечает на вопрос «кто судил», не
собирая отчёты узлов.

## Самоулучшение ядра: `evolve` (ADR-046, п. 3)

Протокол H2.2 (предложение → именной аппрувер → журнал → применение) раньше
работал только с managed-блоками доменного слоя: в файлах `src/` таких блоков
нет, поэтому правка КОДА ЯДРА шла мимо протокола — руками. Теперь у
предложения есть режим:

| Режим | Цель | Применение | Гейт |
|---|---|---|---|
| `block` (дефолт) | md-артефакты доменного слоя | managed-блок (upsert, сверка хеша блока) | не исполняется (как раньше) |
| `file` | файлы ядра `src/**` | замена файла целиком, атомарно (`tmp` + `rename`), сверка `base_sha256` | обязателен: baseline-судья, зелёный до фиксации |

Порядок для `mode=file` — «применить → судить → зафиксировать или откатить»:
контент вносится атомарно, гейты исполняются **на вносимом содержимом**
baseline-судьёй (приоритет `--judge` → `ARCH_ML_JUDGE` → `[fleet] judge_binary`;
резолв через `PATH` не делается — иначе «судья внутри дерева» неотличим).
Зелёный гейт → статус `committed`; красный → полный откат к исходному
состоянию файла (или к его отсутствию), статус остаётся `proposed`, в отчёте —
хвост находок. Частично применённого состояния быть не может.

Защищённые цели (`docs/adr/**`, `CONSTRAINTS.yaml`, `ARCHITECTURE-SPINE*.md`)
закрыты в обоих режимах — и на предложении, и на применении: это зона
архитектора, её меняет человек, а не протокол самоулучшения.

Журнал — append-only `state/evolve/proposals.jsonl`; статусы
`proposed|committed|rejected`. Резолв `mode` толерантен: строки старого
журнала без поля читаются как `block`.

Два эксплуатационных ограничения (осознанные):

- **UTF-8-цель.** Откат восстанавливает исходный *текст* через
  `managed::atomic_write`, поэтому не-UTF-8 цель отклоняется **до любой
  записи**: побайтовое восстановление произвольных байт протоколом не
  предусмотрено;
- **таймаут гейта** — 600 с на команду (`DEFAULT_GATE_TIMEOUT_SECS`); без него
  зависший судья оставлял бы правку применённой навсегда, а не «красной».
  Переопределение — через `GatePlan::with_timeout` (в конфиг не вынесено:
  потребности нет, а лишняя ручка — лишний способ обойти гейт).
