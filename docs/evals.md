# Eval-сьюты конфигурации харнесса (continuous evals)

Регрессионный контур конфигурации самого харнесса (`src/eval.rs`, команда
`arch eval run`): сьют реальных задач прогоняется по расписанию и в CI, гейт
pass-rate ломает сборку при деградации конфига. Мотивация — практика
Anthropic SDLC (20–50 реальных задач с гейтом pass-rate на каждое изменение
CLAUDE.md/skills/hooks): без сьюта деградация конфигурации замечается поздно.

Два слоя проверок:

1. **Детерминированные** (всегда, офлайн): regex/exit-code/JSON-проверки
   вывода задачи — та же механика, что у fitness-правил `CONSTRAINTS.yaml`
   (`docs/control.md`), но предмет проверки — вывод задачи, а не файлы репо.
2. **LLM-судья по рубрике** (опционально, `--judge`): prompt-задачи и поле
   `rubric` оцениваются полным контуром судьи ADR-004
   (`docs/rubrics_and_benchmarks.md`) через текущий реестр моделей.

## Запуск

```bash
arch eval run                                   # встроенный сьют agent-config (герметично, офлайн)
arch eval run --gate 100                        # явный гейт pass-rate, %
arch eval run --judge                           # + слой LLM-судьи (нужен API-ключ)
arch eval run --judge --model glm               # судья/испытуемая — glm
arch eval run --suite ~/.arch-ml/assets/evals/agent-config   # против живой установки
arch eval run --suite ./my-suite --gate 80      # свой сьют, мягче гейт
```

- Без `--suite` прогон **герметичен**: ассеты и конфиг разворачиваются во
  временный каталог (`prepare_builtin_home`), команды получают бинарь с явным
  `--config` — живой `~/.arch-ml` и пользовательский `config.toml` не
  читаются и не трогаются. Поэтому встроенный сьют зелёный и в CI без
  `arch init`.
- С `--suite` прогон идёт против **живой установки**: реальный конфиг,
  реальные каталоги плагинов, реальный `ARCH_ML_HOME` — это и есть проверка
  «моя текущая конфигурация харнесса ещё здорова».
- Результат: текстовая сводка в stdout + JSON-отчёт
  `eval-<suite>-<yyyymmdd-hhmmss>.json` в `~/.arch-ml/evals/`
  (`paths.evals_dir()`, следует за `reports_dir`).
- **Гейт**: pass-rate ниже `--gate` (дефолт 100%) → exit code 1. Ошибка
  загрузки сьюта (битый YAML, невалидная задача, пустой сьют) — тоже ненулевой
  код: молчаливо потерянная задача завышала бы измеренный pass-rate.

## Формат задачи (YAML в каталоге сьюта)

```yaml
id: mermaid-render                 # уникальный id (kebab-case)
title: Mermaid рендерится          # что проверяет задача
command: |                         # bash -c; плейсхолдеры {arch} и {home}
  printf 'flowchart TD\n  A[Клиент] --> B[Шлюз]\n' | {arch} mermaid -
timeout_secs: 120                  # дефолт 120
checks:                            # слой 1: детерминированные (офлайн)
  - type: command_succeeds         # exit 0 до таймаута (только command-задачи)
  - type: must_contain             # regex найден в выводе
    pattern: "Клиент"
  - type: must_not_contain         # regex НЕ найден в выводе
    pattern: "panic"
  - type: json_field               # вывод — валидный JSON; указатель RFC 6901
    pointer: "/status"
    equals: "ok"                   # опционально: точное значение
```

Задача с `prompt` вместо `command` — слой судьи: промпт уходит в модель,
детерминированные проверки применяются к ответу. Без `--judge` такая задача
**пропускается** (в знаменатель pass-rate не входит).

Слой судьи на любой задаче (и command, и prompt):

```yaml
rubric: adr_quality                # имя в assets/rubrics или путь
pass_threshold: 3.5                # порог взвешенного итога (дефолт 3.0)
```

Задача проходит, когда зелёные все детерминированные проверки **и** судья не
ниже порога (если рубрика задана и `--judge` включён).

## Встроенный сьют `agent-config`

8 офлайн-задач smoke-уровня (`assets/evals/agent-config/`, деплоятся
`arch init`): реестр моделей отвечает, библиотека скиллов читается, рубрики и
бенчмарки перечисляются, mermaid рендерится, significance score
маршрутизирует Fast/Critical, политика R2 отклоняет деструктив. Гейт 100% —
все задачи обязаны быть зелёными.

Slash-команды в сьют не входят осознанно: у них нет headless-поверхности
(живут внутри TUI-цикла), а сьют обязан работать в CI.

## Триггер-политика (когда гонять)

Прогон при любом изменении, способном деградировать конфигурацию харнесса:

- правки `config.toml` (модели, политика, пути, хуки);
- изменение библиотеки скиллов/плагинов (`[plugins] dirs`, `arch init`);
- правки `POLICY`/политики автономии и хуков жизненного цикла;
- обновление бинаря (новая сборка `arch`).

Расписание: сьют детерминированный и не требует LLM, поэтому вешается на
**системный cron** напрямую (мимо `cron.toml` — там md-задачи исполняются
моделью):

```cron
20 7 * * * arch eval run >> ~/.arch-ml/evals/eval.log 2>&1
```

(закомментированный пример — в `cron.example.toml`). В CI сьют гейтит каждый
push/PR — джоба `eval-suite` в `.github/workflows/ci.yml`.

## Как расширять сьют

1. Добавьте `<nn>-<name>.yaml` в `assets/evals/agent-config/` (или в свой
   каталог для `--suite`).
2. Подключите файл в `src/assets.rs` (константа `include_str!` + запись в
   `DEFAULT_FILES` + массив в тесте `builtin_suite_assets_are_valid_offline_commands`).
3. Правила для встроенного сьюта: только офлайн-команды через `{arch}`,
   обязательна проверка `command_succeeds`; prompt/рубрики — в
   пользовательские сьюты (герметичность CI без ключей важнее).
4. Локальная проверка перед коммитом: `cargo build && ./target/debug/arch-ml eval run`.

## Ограничения

- Сьют проверяет **конфигурацию и механики** харнесса, а не качество моделей
  (для моделей — `arch bench run` и golden-гейт судьи, ADR-004).
- Команды сьюта — доверенная конфигурация (как правила CONSTRAINTS.yaml):
  окружение наследуется, `bash env_scrub` не применяется.
- Live-режим `--suite` зависит от состояния машины (установленные плагины,
  конфиг) — для CI используйте герметичный встроенный прогон.
