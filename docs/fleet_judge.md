# Судья флота и честность самоулучшения

Гейты узла плана флота бывают двух родов (ADR-042):

* **механические** — детерминированный вызов уже существующей проверки
  (`arch-ml control check`, линтер спайна, JSON-контракт результата, `cargo test`
  …);
* **состязательное ревью** — вердикт LLM-ревьювера READY / NOT-READY.

LLM-вердикт принимается только для БЛОКИРОВКИ и никогда для выбора «лучшего
кода»: выбор в турнире делает детерминированный порядок гейтов. Поэтому тот,
кто СУДИТ прогон, обязан быть независим от того, кого судят. Этот документ —
про одну конкретную форму зависимости: судью, собранного из оцениваемой
ворктри.

## 1. Почему судья должен быть собран из main

Гейт может не считать проверку сам, а позвать бинарь-судью:

```sh
arch-ml control check --policy gate.json --node node-7
```

Команда исполняется через `sh -c` с `current_dir(worktree)`. Если при этом
`arch-ml` разрешается в бинарь, лежащий ВНУТРИ той же ворктри
(`./target/debug/arch-ml`, `target/release/arch-ml`, …), получается
**самооценка**: агент правит код движка, из этого кода собирается движок, и
этот же движок выносит вердикт по своей правке. Такой зачёт ничего не значит —
подопытный подменил экзаменатора.

Ключевое: сравнивать надо **не строки, а канонизированные пути**. Симлинк,
`..`, относительный путь от ворктри — всё это обходит наивное сравнение строк
(`starts_with` по тексту команды), но не обходит `std::fs::canonicalize` +
`Path::starts_with`. Детектор устроен именно так.

## 2. Как задать эталонный судью

Приоритет разрешения (`resolve_judge` в `src/fleet_gate.rs`):

1. **`ARCH_ML_JUDGE`** — переменная окружения с путём к эталонному судье.
   Задана — берётся она. Относительный путь трактуется **от каталога ворктри**
   (там исполняется гейт), а не от каталога запуска движка. Явно заданный, но
   несуществующий путь НЕ откатывается на `PATH`: пин судьи должен падать
   громко, а не подменяться случайным бинарём из окружения.
2. **`PATH`** — если переменная не задана, ищется `arch-ml` в `PATH`
   (`find_in_path`), путь канонизируется.

Конфигурация через переменную окружения, а не через `[fleet]` в конфиге,
выбрана намеренно: это минимальный срез, не требующий правки общей схемы
конфигурации, и он одинаково работает в CI и на машине разработчика.

```sh
# эталонный судья — из чистого main, вне любой оцениваемой ворктри
export ARCH_ML_JUDGE=/home/user/arch-ml-main/target/release/arch-ml
arch-ml fleet run --plan plan.json
```

## 3. Что значит предупреждение о самооценке

Перед исполнением гейта движок разрешает судью и проверяет, указывает ли
канонизированный путь ВНУТРЬ каталога ворктри. Ловятся три формы:

1. заданный эталон (`ARCH_ML_JUDGE`) внутри ворктри;
2. путь, названный прямо в команде (`./target/debug/arch-ml …`) —
   абсолютный или относительный;
3. голое `arch-ml`, разрешённое через `PATH`, если оно внутри ворктри.

При срабатывании гейт **не исполняется вовсе** и возвращает вердикт
`Warn` с явной причиной:

```
судья собран из оцениваемой ворктри — самооценка: <канонизированный путь> (источник: <ARCH_ML_JUDGE=… | PATH>); гейт не исполнен, вердикт понижен до warn
```

Подробность несёт **именно путь**, а не только факт: в журнале узла
(`NodeGated`) видно, какой бинарь сработал бы.

### Warn, а не Fail — и почему

Выбор сделан осознанно:

* **`Fail` останавливает узел** (`GateReport::failed()` реагирует только на
  `Fail`). Самооценка — это подозрение на недостоверный зачёт, а не доказанный
  дефект кода узла; рубить из-за эвристики весь прогон означало бы ломать уже
  существующие планы, где гейт просто гоняет `cargo test` и никогда не зовёт
  `arch-ml`.
* **`Warn` громкий**: он попадает в журнал событиями `NodeGated` и виден
  человеку, но не превращает самоулучшение в стоп-кран.
* Гейт не исполняется — это делает предупреждение детерминированным и заодно
  не запускает потенциально скомпрометированный бинарь.

Если политика флота требует жёсткости, `Warn` можно повысить до `Fail`
решением владельца — это осознанная точка настройки, а не случайность.

### Чего детектор НЕ ловит

`cargo run --bin arch-ml …` в детектор не входит: путь судьи там вычисляет
карго, а не движок, и до запуска он неизвестен. Такой гейт следует записывать
явным путём к бинарю (пункт 2), иначе самооценка останется незамеченной.

## 4. Централизация бинаря: предложение владельцу, НЕ реализовано

Чтобы судья был гарантированно один на все флоты и собран из одной ревизии,
предлагалось централизованное хранилище:

```
~/.arch-ml/bin/arch-ml@<sha>
```

Идея: движок разрешает судью не из ворктри и не из `PATH`, а из этого
хранилища по пину ревизии (`@<sha>`), проверяя, что бинарь собран из
ожидаемого коммита. Варианты и их последствия:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Не централизовать** (текущее) | Ноль новой инфраструктуры; гейты, не зовущие `arch-ml`, не меняются | Судья у каждого свой; пин ревизии — на совести человека; `PATH` может подсунуть бинарь из ворктри |
| **`~/.arch-ml/bin/arch-ml@<sha>`** | Один судья на все флоты; пин ревизии воспроизводим; самооценка структурно невозможна (хранилище вне ворктри) | Новая инфраструктура: сборка и укладка бинарей, утилизация старых, доверие к содержимому каталога; вопрос «кто и когда собирает» |
| **Только жёсткий пин `ARCH_ML_JUDGE`** в CI/скриптах | Без нового хранилища; уже поддержано сегодня | Человек может забыть выставить переменную — тогда сработает `PATH` и, возможно, самооценка (но детектор её поймает) |

**Решение о централизованном хранилище бинарей остаётся за ВЛАДЕЛЬЦЕМ.** В
этой итерации реализован только честный детектор и разрешение судьи по
`ARCH_ML_JUDGE` / `PATH`; самого хранилища `~/.arch-ml/bin/…` в коде НЕТ и быть
не должно, пока владелец не выберет вариант.

## 5. Гарантия неизменности существующих прогонов

Если команда гейта вообще не упоминает `arch-ml` (частый случай: `cargo test`,
`pytest -q`, `true`), детектор возвращает `None` и вердикт гейта не меняется.
Судья за пределами ворктри — тоже `None`, вердикт как раньше. Меняется ровно
один случай: судья, канонизированный внутрь оцениваемой ворктри.
