# ADR-001. Двухконтурная доменная модель закупок 44-ФЗ и 223-ФЗ

- Date: 2026-08-15
- Status: Proposed

## Context

Платформа обслуживает заказчиков обоих закупочных контуров: госорганы (44-ФЗ, жёсткая регламентация, обязательная публикация в ЕИС, план-графики, НМЦК, ЕАТ, РНП) и госкомпании (223-ФЗ, собственное Положение о закупке, частичная публикация, свобода процедур). Процедуры, документооборот, сроки и состав публикуемых данных различаются, но ядро сущностей (извещение, лот, заявка, протокол, контракт) общее. Решение на уровне доменной модели принимается один раз и дёшево не меняется.

## Decision

Единое доменное ядро сущностей закупки; правовой режим (`procurement_regime: FZ44 | FZ223`) — обязательный атрибут арендатора (заказчика) и наследуется процедурами. Различия контуров реализуются не ветвлением кода по `if regime`, а конфигурируемым workflow-движком: набор состояний, переходов, обязательных документов и правил публикации описывается декларативной конфигурацией контура (versioned, хранится в БД, изменения — через миграции с аудитом). Правила, общие для обоих контуров (неизменяемость протоколов, аудит, УКЭП на ключевых действиях), — инварианты ядра, не подлежат конфигурации.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Два отдельных модуля-контура с собственными моделями | Полная изоляция правил; проще верифицировать каждый контур | Дублирование ~70% домена; рассинхрон сущностей (контракт, поставщик) между контурами; двойная стоимость изменений НСИ |
| Только 44-ФЗ на старте, 223-ФЗ потом | Быстрее MVP | Позднее добавление 223-ФЗ потребует переделки модели процедур — риск необратимых миграций данных; потеря рынка госкомпаний |
| Только 223-ФЗ (мягкий контур) | Максимальная свобода дизайна | Не закрывает госорганы — основной объём госзакупок; обязательная интеграция с ЕИС всё равно нужна |
| Статус-кво (не строить) | Нулевые затраты | Задача поставлена: платформа нужна |

## Consequences

### Positive

- Один контракт данных для смежных систем (НСИ, отчётность, интеграция с ЕИС) независимо от контура.
- Изменения регламента (поправки в 44-ФЗ выходят регулярно) меняют конфигурацию workflow, а не код ядра — короче time-to-compliance.
- Арендатор-госкомпания может вести часть закупок по 44-ФЗ-подобным правилам без смены платформы.

### Negative

- Workflow-движок — дополнительная сложность и скрытая точка отказа: ошибка в конфигурации контура = юридически значимый сбой. Митигация: версионирование конфигураций, обязательный прогон контрольных сценариев контура на гейте перед применением версии, запрет правки продуктивной версии in-place.
- Конфигурируемость размывает «очевидность» процедур: аналитикам и ревьюерам нужно читать конфигурацию, а не код. Митигация: генерация человекочитаемой спецификации процедур из конфигурации (docs-as-code).
- Риск «переусложнённого движка» под гипотетические процедуры. Митигация: реализуем только процедуры из утверждённого каталога (начальный набор — в дельта-спеке эпика), расширение — отдельным ADR.

## Reversibility

**costly.** Модель данных ядра и накопленный реестр процедур/документов мигрируются дорого; отказ от workflow-движка после запуска означает переписывание процедурного слоя. До первого продуктивного арендатора решение обратимо.
