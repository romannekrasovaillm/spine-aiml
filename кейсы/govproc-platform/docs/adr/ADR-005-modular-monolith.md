# ADR-005. Модульный монолит как стартовая архитектура ядра

- Date: 2026-08-15
- Status: Proposed

## Context

Команда и домен новые; границы модулей (извещения, заявки, протоколы, контракты, НСИ, пользователи, интеграции) на старте известны лишь приблизительно. Нагрузки на ядро умеренные (закупочные процедуры — не high-frequency); пиковые профили — подача заявок к дедлайнам. On-prem контур ограничен по ресурсам и эксплуатации (ADR-002). Микросервисы на старте дадут распределённую сложность без соответствующей выгоды; классический «большой ком грязи» — убьёт сопровождаемость регуляторно нагруженного домена.

## Decision

Ядро платформы — **модульный монолит**: один деплой-юнит, строгие границы модулей внутри (каждый модуль — свой пакет верхнего уровня, своя схема БД, публичный API модуля через интерфейс, прямые межмодульные импорты запрещены — только через API или доменные события). Отдельными сервисами с первого дня выделяются только: `eis-adapter` (ADR-003 — другой релизный цикл и внешняя изменчивость), `signing` (ADR-004 — изоляция СКЗИ), `notification` (email/лкабинет — иной нагрузочный профиль). Правила границ модулей проверяются автоматически (fitness function: архитектурные тесты на запрет кросс-импортов и кросс-схемных запросов).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Микросервисы с первого дня | Независимое масштабирование и релизы | Распределённые транзакции по юридически значимому workflow (saga по протоколу) — неподъёмная сложность для новой команды; оверхед эксплуатации в on-prem |
| Слоистый монолит без границ модулей | Быстрее всего стартовать | В регуляторном домене границы размываются за месяцы; выделение сервисов потом — боль |
| Serverless/функции | Минимум эксплуатации | Неприменимо в on-prem госконтуре без зрелой serverless-платформы; холодные старты недопустимы на дедлайнах |

## Consequences

### Positive

- Транзакционная целостность workflow закупки в одной БД: протокол либо зафиксирован целиком, либо нет — критично для аудита.
- Один деплой-пайплайн, один контур мониторинга — посильно для стартовой команды эксплуатации.
- Границы модулей, выверенные на практике, станут честной картой для выделения сервисов позже.

### Negative

- Масштабирование — только всего юнита: пик подачи заявок грузит и отчётность. Митигация: read-реплики для чтения/отчётности; приоритизация очередей.
- Дисциплина границ держится на автоматических проверках, а не на изоляции процессов — риск эрозии. Митигация: fitness functions в CI, блокирующие нарушения (см. CONSTRAINTS.yaml).
- Выделение модуля в сервис потребует работы над событиями/транзакциями. Митигация: межмодульное взаимодействие с первого дня через контракты и события, а не через БД.

## Reversibility

**reversible→costly**: выделение сервисов из дисциплинированного модульного монолита — плановая операция; обратный путь (сборка микросервисов в монолит) был бы дороже. Решение не закрывает путь к микросервисам.
