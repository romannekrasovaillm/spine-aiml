# ADR-004. УКЭП и ГОСТ-криптография для юридически значимых действий

- Date: 2026-08-15
- Status: Proposed

## Context

В госзакупках юридически значимые действия (подача заявки, подписание протокола, контракта) требуют усиленной квалифицированной электронной подписи (63-ФЗ). ГОСТ-криптография обязательна (ФСБ); для защищённого контура — сертифицированные СКЗИ. Архитектурный вопрос: где живут ключи и как подписание встроено в workflow, чтобы не превратить его в блокирующий шаг и не размазать криптографию по коду.

## Decision

1. Подписание серверное, через КриптоПро DSS (или аналогичный сертифицированный сервер подписи): ключи участников не покидают HSM/сервер DSS, пользователь подтверждает подписание вторым фактором. Локальные токены (Рутокен и т.п.) поддерживаются как опция для поставщиков через браузерный плагин, но не являются основным сценарием.
2. Подпись — отдельный модуль (`signing`) с узким контрактом: `sign(document_hash, signer_id, purpose) → signed_document_ref`. Остальной код платформы криптографии не содержит.
3. Подписывается каноническая форма документа (детерминированная сериализация + хеш ГОСТ Р 34.11-2012). Хеш и ссылка на подписанный документ фиксируются в аудит-логе (AD-4).
4. Подписание — обязательный переход workflow на ключевых точках контура (конфигурация ADR-001); протокол/контракт без валидной УКЭП не существует как юридический факт.
5. Проверка подписи при приёме документов от поставщиков — синхронно на границе (отклонить невалидное сразу), проверка цепочки до УЦ — с кэшем CRL/OCSP.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Только локальные токены + браузерный плагин | Классическая схема ЭТП; ключ у пользователя | Поддержка зоопарка ОС/браузеров у тысяч поставщиков; блокирует мобильные сценарии; поддержка — ад |
| Собственный крипто-модуль на библиотеке | Нет лицензий КриптоПро | Несертифицированное СКЗИ недопустимо в контуре; самостоятельная сертификация — годы |
| Подписание пакетно, по расписанию | Разгружает DSS | Юридически значимое действие должно совершаться волеизъявлением в моменте; пакетность ломает сроки и аудит |

## Consequences

### Positive

- Сертифицированный стек снимает риск отказа в аттестации и оспаривания подписи в суде/ФАС.
- Единая точка криптографии: смена СКЗИ или алгоритмов (переход на новые ГОСТ) локализована в модуле `signing`.
- Серверное подписание резко снижает нагрузку на поддержку поставщиков.

### Negative

- DSS — лицензионная стоимость и единая точка отказа для подписания. Митигация: кластер DSS, graceful degradation (приём документов продолжается, подписание в очередь с алертом).
- Зависимость от дорожной карты вендора СКЗИ. Митигация: контракт модуля `signing` позволяет заменить реализацию.
- Производительность подписания ограничена HSM/DSS: пиковые подачи заявок в дедлайн извещений. Митигация: нагрузочные тесты по NFR (пиковый профиль), шедулер пиков.

## Reversibility

**reversible** на уровне модуля (контракт узкий); **irreversible** на уровне выданных подписей — подписанные документы и их проверка должны сохраняться весь срок хранения (сроки по 44-ФЗ/223-ФЗ и архивному законодательству `[ТРЕБУЕТ ПРОВЕРКИ]: конкретные сроки по видам документов`).
