# ADR-004. Сегментация доверенных зон (4 зоны)

- Date: 2026-08-15
- Status: Accepted

## Context

Платформа процессинга обрабатывает финансовые транзакции, персональные данные (152-ФЗ), данные платёжных карт (PCI DSS), и интегрируется с критической информационной инфраструктурой (КИИ, 187-ФЗ). Без сегментации — компрометация DMZ-компонента даёт атакующему доступ к финансовым данным и ядру банка.

## Decision

**4 изолированные доверенные зоны** с network segmentation, mTLS и data flow control.

### Зона 1 — DMZ (публичный периметр)
- Компоненты: API Gateway, Tokenization Service, Channel Adapters.
- Сетевой доступ: извне (HTTPS), исходящий — только в Зону 2.
- PAN (номер карты) токенизируется здесь и не покидает зону. Вглубь — только токен.

### Зона 2 — Application (бизнес-логика)
- Компоненты: Payment Gateway, Orchestrator, Authorization, Fraud, AML.
- Сетевой доступ: входящий — из Зоны 1 (mTLS), исходящий — в Зоны 3 и 4.
- Не хранит сырые пан-данные. Работает с токенами.

### Зона 3 — Data (финансовые данные)
- Компоненты: Ledger, Clearing & Settlement, Payment Events (audit log).
- Сетевой доступ: входящий — из Зоны 2 (mTLS), исходящий — в Зону 4 (Core Banking).
- Строгий доступ: audit logging на каждом запросе, encryption at rest (TDE).

### Зона 4 — Integration (внешние системы)
- Компоненты: NSPK Connector, CBR Connector, SWIFT Connector, Core Banking Adapter.
- Сетевой доступ: входящий — из Зон 2 и 3 (mTLS), исходящий — во внешние сети (NSPK, CBR, SWIFT, Core).
- Каждый коннектор — отдельный deployment с собственным network policy.
- Исходящий трафик — через dedicated egress proxy с allowlist.

### Общие правила
- Междузонный трафик — mTLS (сертификаты от внутреннего PKI, rotation 90 дней).
- Network policies в Kubernetes: default-deny, явные allow rules.
- Синхронный вызов через зону — только через service mesh (Istio/Linkerd).
- Логирование межзонных вызовов: кто, куда, когда, что (для аудиторского следа).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **2 зоны** (DMZ + backend) | Простота. | Backend — единая зона, компрометация даёт доступ ко всему. Не соответствует PCI DSS. |
| **3 зоны** (DMZ + app + data) | Меньше сложности. | Integration-коннекторы в app-зоне — внешний доступ из app. Нарушение изоляции. |
| **Zero trust без зон** (каждый сервис изолирован) | Максимальная гранулярность. | Экспоненциальная сложность network policies. Избыточно. |

## Consequences

### Positive

- Соответствие PCI DSS (сегментация CDE), КИИ (изолированные контуры).
- Ограничение blast radius: компрометация DMZ не даёт доступа к финансовым данным.
- Чёткий data flow: PAN не покидает Зону 1, финансовые данные — в Зоне 3.

### Negative

- Операционная сложность: 4 набора network policies, mTLS-сертификаты, мониторинг.
- Задержка: межзонный трафик через service mesh добавляет ~1–2ms per hop.
- Развертывание новых сервисов требует явного network policy review.

## Reversibility

**Costly.** Сегментация — фундаментальная сетевая архитектура. Изменение количества зон требует перенастройки всей сетевой инфраструктуры.
