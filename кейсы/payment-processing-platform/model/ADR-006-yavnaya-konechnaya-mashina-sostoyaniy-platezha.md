## Context

Платёж проходит через 8+ состояний. Без явной state machine: переходы разбросаны по коду (if/else в разных сервисах), невозможность проверить корректность перехода, race conditions (два потока переводят платёж в разные состояния), невозможность ответить «в каком состоянии платёж и что дальше». Для банка — недопустимо: регулятор требует реконструкции жизненного цикла.

## Decision

**Явная конечная машина состояний (FSM)** в Payment Orchestrator.

### Состояния

```
INITIATED
  → VALIDATED          (схема, аккаунт, канал проверены)
  → FRAUD_PASSED       (фрод-скоринг < порога)
  → AML_PASSED         (санкционный скрининг пройден)
  → AUTHORIZED          (лимиты, баланс, холд)
  → RAIL_SENT          (запрос отправлен на рельс)
  → RAIL_CONFIRMED     (ответ от рельса получен)
  → LEDGER_POSTED      (проводка по ledger выполнена)
  → COMPLETED          (платёж завершён, событие опубликовано)
```

### Терминальные состояния

- `COMPLETED` — успешное завершение.
- `FAILED` — неуспех на валидирующем шаге (fraud, AML, limits).
- `REJECTED_BY_RAIL` — отказ внешней системы.
- `CANCELLED` — отменён клиентом/оператором (только до RAIL_SENT).
- `COMPENSATED` — сага откатана (компенсации выполнены).

### Правила переходов

- Переход допустим только по явной таблице переходов (transition table). Недопустимый переход → 409 Conflict + лог.
- Каждый переход — запись в `payment_events` (AD-7, append-only).
- Single-writer per payment_id (AD-4): только оркестратор меняет статус.
- Семантическая блокировка: `PENDING_*` статусы запрещают конфликтующие операции.

### Точка невозврата

- `RAIL_SENT` — точка невозврата: после отправки на рельс отмена невозможна, только компенсация (возврат).
- До `RAIL_SENT` — отмена возможна (CANCELLED).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Свободные статусы** (if/else) | Гибкость. | Хаос. Невозможность валидации. Race conditions. |
| **Event Sourcing (full)** | Полная реконструкция из событий. | Избыточно для MVP (snapshotting, projections). DEF-1 в spine. |

## Consequences

### Positive

- Корректность переходов гарантирована таблицей.
- Реконструкция жизненного цикла — из payment_events.
- Race conditions предотвращены (single-writer + optimistic locking).
- Чёткая точка невозврата для компенсаций.

### Negative

- Жёсткость: добавление нового состояния/перехода — изменение таблицы + деплой.
- Single-writer — потенциальное bottleneck. Митигация: партиционирование по payment_id.

## Reversibility

**Costly.** Переход на свободные статусы — потеря гарантий. Но таблица переходов расширяется без ломки (additive).
