## Context

Платёж — это многошаговый процесс (5–8 шагов): валидация → фрод-проверка → AML → авторизация → отправка на рельс → ответ рельса → проводка по ledger → уведомление. Каждый шаг — отдельный сервис со своей БД (AD-3 database-per-service). Распределённые транзакции (2PC) запрещены в микросервисной архитектуре (блокировки, единая точка отказа координатора XA, недоступность для Kafka).

Без явного оркестратора: участники слушают события и решают сами (хореография). Для 8 участников поток становится невидимым — нет единого места, где видна последовательность. Циклы событий, невозможность реконструкции «где застрял платёж». Для банка это неприемлемо: состояние платежа должно быть явным и аудируемым (AD-7).

## Decision

Жизненный цикл платежа управляется **сагой с оркестрацией** (Saga Execution Coordinator в Payment Orchestrator).

- Состояние саги персистентно: таблица `payment_saga(payment_id, current_state, step_results, version, created_at, updated_at)`.
- Явная конечная машина состояний (state machine): `INITIATED → VALIDATED → FRAUD_CHECKED → AML_CHECKED → AUTHORIZED → RAIL_SENT → RAIL_CONFIRMED → LEDGER_POSTED → COMPLETED`.
- При сбое шага Ti — компенсирующие транзакции C(i-1)…C1 в обратном порядке.
- Компенсации — семантические: сторно проводки, снятие холда, отмена авторизации. Запрещено удаление записей (аудиторский след, AD-7).
- Таймауты шагов + эскалация застрявших саг в операционную очередь (ручное вмешательство).
- Изоляционные аномалии: семантическая блокировка через статус `PENDING` (запрещает конфликтующие операции с тем же payment_id).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Choreography** (участники слушают события) | Нет единой точки отказа. Простые потоки ≤3 участников. | 8 участников — поток невидим. Циклы событий. Невозможно реконструировать состояние. Запрещено для платёжного потока банка. |
| **2PC / XA** | Атомарность. | Блокировки. Единая точка отказа координатора. Недоступно для Kafka. Запрещено риск-аппетитом. |
| **Status quo** (монолит с распределённой транзакцией) | Простой код. | Невозможно масштабировать. Связанность. Не соответствует требованиям throughput и time-to-market. |

## Consequences

### Positive

- Явное, видимое состояние платежа на каждом шаге.
- Аудируемый жизненный цикл (реконструкция для регулятора/суда).
- Скоординированные компенсации (нет «частично выполненных» платежей без плана отката).
- Возможность операционного мониторинга и ручного вмешательства.

### Negative

- Orchestrator — единственная точка координации. Митигация: персистентное состояние, restart с последнего шага, несколько реплик (leader election).
- Риск «умного центра» — бизнес-логика концентрируется в оркестраторе. Митигация: оркестратор только координирует, бизнес-логика — в сервисах.
- Дополнительная задержка (state persistence + event publish). Митигация: latency-бюджет саги в NFR, асинхронные шаги где возможно.

## Reversibility

**Costly.** Переход на хореографию потребует переработки всех участников и потери явного состояния. Но архитектурно возможно — интерфейсы сервисов остаются теми же, меняется только модель координации.
