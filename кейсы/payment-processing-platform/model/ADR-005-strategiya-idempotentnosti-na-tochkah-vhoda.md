## Context

At-least-once доставка — норма: Kafka гарантирует at-least-once (дубли при ребалансах, ретраях). Клиенты (мобильный банк, партнёрские API) ретраят при таймаутах. Повторная обработка команды списания без защиты = двойное списание. В банке это — финансовый ущерб, клиентский комплаенс, репутационный риск.

## Decision

**Многоуровневая идемпотентность** на каждой точке входа.

### Уровень 1: API (Payment Gateway)
- Каждый mutating endpoint принимает HTTP-заголовок `Idempotency-Key`.
- Ключ хранится в Redis (TTL = 24ч + буфер) с привязкой к результату.
- Повторный вызов с тем же ключом → возврат ПЕРВОГО результата (не «уже сделано», а полное тело ответа с payment_id и статусом).
- Если ключ отсутствует — 400 Bad Request (для mutating endpoints).

### Уровень 2: Consumer (обработчики событий/команд)
- Inbox-таблица: `processed_messages(message_id, processed_at, result)` в **той же транзакции**, что и бизнес-изменение.
- Дубль → вернуть сохранённый результат, не выполнять логику.
- message_id из Kafka header (Kafka offset не подходит — меняется при ребалансе).

### Уровень 3: Естественная идемпотентность
- State machine: переход `PAID → PAID` = no-op (вернуть 200), не повторное списание.
- Оптимистичная блокировка: версия сущности (optimistic concurrency) — конфликт версий → 409.

### TTL и очистка
- TTL ключей идемпотентности = окно ретраев канала + буфер (минимум 24ч, для партнёров — 72ч).
- Inbox-записи: retention 30 дней, затем архивация.

### Мониторинг
- Метрика: `idempotency_duplicates_total` — количество отклонённых дублей. Аномальный рост = симптом зацикленного producer'а → алерт.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Только Redis** (без inbox) | Быстро, просто. | Redis не в транзакции с БД — гонка: «ключ записан, БД упала» → второй вызов пройдёт. |
| **Только inbox** (без Redis) | Транзакционно. | Медленнее (БД-lookup на каждый запрос). Redis быстрее для hot path. |
| **Exactly-once Kafka** | Гарантии внутри Kafka. | Сквозной exactly-once не существует. Не покрывает API-вызовы и cross-system. |

## Consequences

### Positive

- Двойное списание невозможно (при корректной реализации всех 3 уровней).
- Поведение при ретраях предсказуемо для клиента (тот же результат).
- Естественная идемпотентность через state machine — бесплатная защита.

### Negative

- Дополнительный Redis-lookup на каждый запрос (~1ms).
- Inbox-таблица растёт — нужно партицирование/архивация.
- Сложность тестирования: нужно проверять все 3 уровня (fitness: тест повторной доставки).

## Reversibility

**Reversible.** Уровни независимы. Снятие уровня ослабляет гарантию, но не ломает систему.
