## Context

Kafka гарантирует at-least-once доставку. Consumer может получить сообщение, которое не может обработать: невалидный формат, отсутствие обязательного поля, бизнес-ошибка (например, payment_id не найден). Без DLQ-стратегии: poison message повторяется бесконечно, блокирует партицию, останавливает обработку всех последующих сообщений в ней. В банке это = стоп процессинга.

## Decision

**Многоуровневая стратегия обработки ошибок: retry → DLQ → ручная обработка.**

### Retry-топики
- Каждый consumer имеет retry-топик: `payments.commands.retry` (и т.д.).
- Политика: 3 попытки с задержкой 1s → 5s → 25s (экспоненциальный backoff, AD-10).
- Реализация: Kafka consumer ловит ошибку → публикует в retry-топик с меткой `next_attempt_at`. Отдельный retry-consumer читает по достижении времени.

### DLQ
- После 3 неудачных попыток → запись в `payments.commands.dlq`.
- Сообщение в DLQ содержит: оригинальное сообщение, error message, stack trace, original topic, original offset, attempt count, timestamp.
- DLQ-топик мониторится: `dlq_messages_total` (counter) + `dlq_queue_depth` (gauge). Алерт при depth > 0.

### Ручная обработка
- Оператор открывает DLQ-инструмент: просмотр, replay (после исправления), reject (с причиной).
- Replay: повторная публикация в исходный топик с новым message_id (старый lifecycle закрывается).
- Reject: запись в `operator_audit` (AD-26), маркировка сообщения как `REJECTED`.
- Dual control: replay требует двух подписей (AD-26).

### TTL
- Retry-топики: TTL 24ч (сообщение старше 24ч → автоматически в DLQ).
- DLQ: retention 90 дней (аудит), затем архивация.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Бесконечный retry** | Сообщение не теряется. | Блокирует партицию. Стоп процессинга. |
| **Молчаливое удаление** | Не блокирует. | Потеря данных. Недопустимо для платёжных сообщений. |
| **In-place error table** (без Kafka DLQ) | Просто. | Нет стандартизованной обработки. Сложнее мониторить. |

## Consequences

### Positive

- Poison message не блокирует партицию.
- Полный аудиторский след ошибок.
- Оператор может исправить и переотправить.

### Negative

- Дополнительные топики и consumer'ы (операционная сложность).
- Окно 24ч для ручной обработки (retention retry).
- Риск накопления DLQ при систематической ошибке (например, ломающая изменение схемы — AD-15, AD-14 предотвращают).

## Reversibility

**Reversible.** Переход на другую стратегию — замена retry/DLQ-топиков и consumer'ов. Бизнес-логика не меняется.
