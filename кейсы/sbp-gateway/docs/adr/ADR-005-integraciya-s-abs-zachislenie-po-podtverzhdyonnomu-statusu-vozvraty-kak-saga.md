# ADR-005. Интеграция с АБС: зачисление по подтверждённому статусу, возвраты как сага

- Date: 2026-08-15
- Status: Proposed
- Owner: solution-architect (платёжный контур) + владелец АБС
- Related: ADR-002, ADR-004, AD-005

## Context

АБС банка-эквайера ведёт счета ТСП. Для C2B-приёма АБС выполняет два типа финансовых действий: **зачисление** средств по подтверждённому платежу СБП на счёт ТСП и **возврат** (refund) — обратное списание со счёта ТСП в пользу плательщика. АБС — унаследованияя система, её контракты простые (документ: сумма, счёт, реквизиты), понятия «платёж СБП» и «нотификация НСПК» в ней нет. Согласованность между шлюзом и АБС — в конечном счёте, с обязательной сверкой.

Силы: зачисление должно происходить **только** по подтверждённому НСПК статусу (не по факту создания QR); возврат — компенсирующая операция, не должна выполняться дважды; АБС не идемпотентна по своей природе — идемпотентность обеспечивает шлюз; сроки зачисления регулируются (НПС, правила НСПК).

## Decision

1. **Зачисление — только из состояния `PAID`** (подтверждённый НСПК статус платежа). Триггер — обработанная нотификация/сверка (ADR-004). Из `CREATED`/`QR_ISSUED` зачисление невозможно — инвариант AD-005.
2. **Вызов АБС идемпотентен на уровне шлюза**: документ АБС формируется с уникальным внешним ключом = `paymentId` шлюза; повторный вызов с тем же ключом не создаёт второй проводки (АБС либо поддерживает идемпотентность, либо шлюз хранит `absDocId` результата и повторно не вызывает).
3. **Порядок**: шлюз → очередь → адаптер АБС → подтверждение прихода в АБС → статус `CREDITED` → outbox-нотификация ТСП (`COMPLETED`). Если АБС недоступна — ретраи (не теряем операцию), платёж остаётся `PAID` и виден в сверке.
4. **Возврат — сага**: ТСП инициирует возврат → шлюз проверяет, что платёж был зачислен (`CREDITED`/`COMPLETED`) → вызывает АБС (списание со счёта ТСП) → регистрирует возврат в НСПК → по подтверждению НСПК → статус `REFUNDED`, нотификация ТСП. При сбое на любом шаге — компенсирующие действия (отмена АБС-списания, повтор регистрации в НСПК, DLQ + runbook). Возврат — отдельная операция со своей идемпотентностью (`refundId`).
5. **Сверка шлюз↔АБС**: ежедневная (и по запросу) сверка «зачислено в АБС» vs «PAID по НСПК»; расхождения — в отчёт незавершённых операций, эскалация. Двойная проводка при расхождении исключается идемпотентностью (п.2).
6. **Читающие запросы к АБС** (проверка счёта ТСП, остатков) — через выделенный read-адаптер, без прямого доступа шлюза к БД АБС.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Зачислять сразу при создании QR (до подтверждения НСПК) | Мгновенный «успех» для ТСП | Платёж может не состояться — незаконное зачисление, кассовый разрыв, нарушения НПС |
| Прямой SQL-доступ шлюза к БД АБС | Просто, быстро | Нарушение границ владения, риск целостности АБС, не проходит аудит |
| Возврат без саги, «просто вызвать АБС и НСПК» | Меньше кода | Частичное выполнение (АБС списала, НСПК не узнала) — зависшие деньги, диспуты |

## Consequences

### Positive

- Зачисление строго по подтверждённому статусу — соответствие НПС и исключение «платежей из воздуха».
- Идемпотентность защищает от двойных проводок при ретраях АБС.
- Сага возвратов даёт согласованное состояние (АБС + НСПК + шлюз).

### Negative

- АБС — внешняя зависимость для завершения операции: доступность АБС влияет на SLA зачисления (митигируется очередью и приоритетами).
- Два источника истины (шлюз, АБС) требуют постоянной сверки — эксплуатационная нагрузка.
- Возвраты как сага — сложная логика, нужны тесты на все сценарии сбоя.
- Если АБС не поддерживает идемпотентность — шлюз вынужден хранить маппинг `paymentId → absDocId` и делать компенсации при расхождениях.

## Reversibility

**costly.** Изменить «зачисление только из PAID» на другую модель нельзя без пересмотра финансовой модели и регуляторного согласования. Замена конкретного адаптера АБС — reversible.
