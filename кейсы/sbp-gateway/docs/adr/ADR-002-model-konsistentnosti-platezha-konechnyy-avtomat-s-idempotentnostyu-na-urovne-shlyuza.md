# ADR-002. Модель консистентности платежа: конечный автомат с идемпотентностью на уровне шлюза

- Date: 2026-08-15
- Status: Proposed
- Owner: solution-architect (платёжный контур)
- Related: ADR-001, ADR-004, ADR-005, AD-002, AD-003

## Context

Платёж C2B проходит через три системы: ТСП → шлюз → ОПКЦ СБП → (банк плательщика) → уведомление обратно. Канал к НСПК не даёт ровно-один раз: сообщения могут повторяться, ответы приходить позже таймаута, нотификации дублироваться. При этом финансовое последствие ошибки — двойное зачисление или потерянный платёж — недопустимо. АБС не имеет понятия «платёж СБП» — ей нужен простой идемпотентный документ.

Силы: at-least-once доставка от внешнего оператора, необходимость согласованного состояния между шлюзом, АБС и НСПК, аудируемость каждого перехода (требования НПС, отчётность).

## Decision

1. **Платёж — конечный автомат в БД шлюза.** Канонические состояния (детализация — по документации НСПК на этапе контракта):
   `CREATED → QR_ISSUED → PAID (подтверждён НСПК) → CREDITED (зачислен на счёт ТСП в АБС) → COMPLETED`, плюс терминальные `FAILED`, `EXPIRED`, `REVERSED`, `REFUNDED`. Промежуточные технические состояния (`NOTIFY_SENT`, `ABS_IN_PROGRESS`) допустимы как подсостояния.
2. **Переходы только атомарные**: смена статуса + запись в outbox + аудит-лог — в одной локальной транзакции (см. ADR-001). Никакого «обновить статус, потом отправить».
3. **Идемпотентность по явному ключу**: входящие запросы ТСП идут с `Idempotency-Key` (или коррелируются по `qrId`/`paymentId`). Повторный запрос с тем же ключом возвращает ранее созданный ресурс, не создавая новый.
4. **Обработка нотификаций НСПК — идемпотентна по `eventId`** (см. ADR-004): повторная нотификация не меняет уже завершённый переход.
5. **Правило «одна сумма, один плательщик, один ТСП»**: сумма и реквизиты платежа иммутабельны после создания QR; расхождение в нотификации (сумма/получатель) → статус `FAILED` + алерт, зачисление запрещено.
6. Консистентность между шлюзом и АБС — «согласованность в конечном счёте» с обязательной сверкой (ADR-005); консистентность внутри шлюза — строгая (ACID на уровне статусной машины).

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| Полагаться на «ровно один раз» от НСПК и АБС | Проще код | Наружно: НСПК/АБС не гарантируют ровно-один раз; риск двойного зачисления при ретрае |
| Event-sourcing полный (события как единственное хранилище) | Полная аудируемость | Избыточная сложность для 5-6 состояний, дороже эксплуатация, сложнее сверка с АБС |
| Хранить только «последний статус», без автомата | Максимально просто | Нельзя доказать корректность переходов регулятору, сложно отлаживать расхождения |

## Consequences

### Positive

- Доказуемая корректность: каждый финансовый переход — атомарный и аудируемый.
- Повторные доставки безопасны: идемпотентность на входе и на нотификациях.
- Единая модель для отчётности ЦБ/НСПК и для сверки.

### Negative

- Нужна строгая дисциплина транзакций: ошибка «запись вне транзакции» — источник двойных зачислений (контролируется AD-003 и ревью).
- Автомат состояний требует формальной спецификации переходов и тестов на каждый переход (fitness-функции).
- Дополнительные технические состояния усложняют модель — нужно держать канонический список в одном месте (spine).

## Reversibility

**reversible.** Модель можно расширять новыми состояниями (C2C, выплаты) и упрощать; данные уже накоплены в структурированном виде. Полный отказ от автомата — costly, но не требуется.
