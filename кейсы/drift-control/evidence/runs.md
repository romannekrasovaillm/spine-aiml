# Фактические исходы дрейф-эксперимента (2026-08-17)

Стенд: реальный Claude Code 2.1.233 headless (`claude -p
--dangerously-skip-permissions`, бэкенд `deepseek-v4-pro[1m]`), запуск через
`arch-be harness-run`, каждая рука — в изолированном git-репозитории
(полигон `/tmp/drift-lab`). Машина и сеть — одни, прогоны последовательные.

## Дизайн

Контролируемый эксперимент «удерживает ли handoff-пакет кодовый харнесс от
архитектурного дрейфа». Одна и та же базовая задача — Rust-библиотека
платёжного ядра (Payment: сумма/валюта/статус, authorize/capture/refund,
журнал событий, ошибки, тесты) — отдана исполнителю в двух руках:

- **Рука A (контроль)** — голый текст задачи (секция «Задача» из TASK.md).
  Никаких инвариантов, правил, критериев приёмки. Решения «как сделать»
  исполнитель принимает сам.
- **Рука B (спайн)** — та же задача + handoff-пакет `.arch-handoff/`:
  `ARCHITECTURE-SPINE.md` (AD-1 деньги в minor units, AD-2 ошибки через
  thiserror, AD-3 идемпотентный authorize по ключу) и `CONSTRAINTS.yaml`
  (6 fitness-правил C-01…C-06, все severity critical).

Судья один и механический для обеих рук: `arch-be control check <рука>
--constraints CONSTRAINTS.yaml` — правила руки B применяются и к руке A
именно как внешний гейт (дрейф = нарушение орг-инвариантов, о которых
исполнитель A не знал).

## Результаты

| Рука | Код | Стена | Тесты | Fitness (6 правил) | Гейт |
|---|---|---|---|---|---|
| A (голая задача) | 0 | 371.9 с | 32/32 зелёные | **FAIL: 2 нарушения** (C-02 thiserror, C-05 идемпотентность) | exit 1 |
| B (спайн + правила) | 0 | 360.4 с | 19/19 зелёные | **PASS: 0 нарушений** | exit 0 |

Выводы гейта дословно — `armA-fitness.txt` / `armB-fitness.txt`.

**Дрейф руки A — ровно по орг-специфичным инвариантам.** Модель без пакета
написала добротную библиотеку (6 модулей, 32 теста, аккуратный коммит): f64
для денег не выбрала сама (C-01 PASS), anyhow не притащила (C-03/C-04 PASS),
тесты зелёные (C-06 PASS). Но: ошибки оформила рукописным enum с ручным
`Display`/`Error` вместо thiserror (C-02 FAIL) и **вообще не реализовала
идемпотентность** (C-05 FAIL) — обобщённая модель не может угадать
организационный стандарт «ошибки через thiserror» и продуктовый инвариант
«authorize идемпотентен по ключу». Это и есть архитектурный дрейф: код
качественный, тесты зелёные — а ландшафт разошёлся.

**Рука B прошла не формально.** Идемпотентность реализована настоящим
inbox'ом: `PaymentProcessor::authorize` дедуплицирует повторы по ключу
(успех — клон первого платежа, ошибка — та же ошибка), а не строкой
«idempotency» под линтер; `thiserror 2.0.20` — реальная зависимость в
`Cargo.toml` и `Cargo.lock`. Исполнитель сам сверился с критериями приёмки
(таблица C-01…C-06 в его отчёте — `armB.log`) и сослался на план отката.

## Воспроизведение из репозитория

```bash
# из корня репозитория Spine:
arch-be control check кейсы/drift-control/armA-solution \
  --constraints кейсы/drift-control/handoff-example/CONSTRAINTS.yaml
# → FAIL, exit 1 (C-02, C-05)
arch-be control check кейсы/drift-control/armB-solution \
  --constraints кейсы/drift-control/handoff-example/CONSTRAINTS.yaml
# → PASS, exit 0
```

(C-06 `cargo test --quiet` требует сборки: armB тянет thiserror из
cargo-кэша/сети; обе руки — edition 2021, без прочих зависимостей.)

## Замечания о честности

- Промпт руки B содержал секцию «Критерии приёмки» со ссылкой на правила —
  исполнитель B знал гейт заранее, рука A — нет. Это не перекос, а сама
  проверяемая гипотеза: инварианты должны доезжать до исполнителя явно.
- Обе руки получили инструкцию «Финализация» (финальный коммит) — обе
  закоммитили (`commits.txt`); дисциплина коммита на результат не влияет.
- Различие 32 vs 19 тестов — следствие свободы дизайна (у A богаче
  статусная модель: 7 статусов, частичные capture/refund, void); мерой
  эксперимента являются только fitness-правила, не объём.
- Контракт результата (```json со status) ни одна из рук в stdout не
  напечатала — `harness_run` честно пометил «⚠ контракт не найден» и свёл
  прогон по коду выхода и git log. Отдельный урок: текстовая инструкция
  в TASK.md без механического разбора — слабый контракт (P0-разрыв,
  зафиксирован в журнале харнесса ранее).
