# tools/ — стражи S0/S1 (walking skeleton контроля)

Инструменты делают инварианты `ARCHITECTURE-SPINE.md` (AD-1…AD-8) механически
проверяемыми. Каждый вызывается правилом `CONSTRAINTS.yaml` через
`command_succeeds` (кроме `check_gb10_serialization.sh` — AD-5 пока
`[PENDING-EVIDENCE]`), поэтому выход ограничен **60 секундами** (таймаут
`fitness_check`) и печатает диагностику в stdout, даже если её не видно из гейта.

|---|---|---|---|---|---|

`check_sft_rl_overlap.py` **не привязан к правилу**: пересечение SFT↔RL само по
себе не нарушение (RL-задачи и SFT-примеры домена частично об одном и том же), а
факт, который обязан быть измерен до прогона. Exit 1 — сигнал архитектору, а не
вердикт гейта; фильтрация данных — решение следующей дельты (AD-7: состав
заморожен). Кросс-проверка `--expect-matched 39` защищает от тихого «перемерил и
разошёлся»: расхождение с известным числом даёт тот же exit 1 и печатается явно.

Общие принципы (соблюдены в каждом инструменте):

1. **Нет зелени по умолчанию.** Отсутствие входа — `NOT-VERIFIED` (exit 2), а не
   exit 0. Вакуумные исключения объявлены явно и напечатаны: `no runs yet`
   (C-012 — «каждый каталог прогона» при нуле каталогов), `gb10 not reachable`
   (AD-5 — стенд недоступен, проверка не состоялась).
2. **Честный красный лучше зелёного.** Нарушения называются поимённо (индекс
   задачи, slug, поле, pid), а не сворачиваются в счётчик.
3. **Только чтение.** Ни один инструмент не убивает процессы, не перезаписывает
   данные и не пишет в родительский контур `~/gb10-shared` (кроме
   `write_run_manifest.py`, который пишет только внутрь `runs/<id>/` кейса, и
   `check_sft_rl_overlap.py`, который пишет только поле в `evidence/`).
4. **Данные не копируются** (AD-4): входы подключаются симлинками на
   `/home/user/gb10-shared` — `datasets/`, `data/tok/`, `laguna_pipeline_v8.py`,
   `cpt_corpus_v12r.txt`.

## Политика C-008 (ADR-004): три уровня, а не «все 8 токенов»

Буквальная редакция правила требовала ненулевых вхождений всех 8 спецтокенов в
кэше. Замер S0 показал, что критерий **неисполним на замороженном корпусе**:
`<reasoning>`/`</reasoning>` дают 0 вхождений во всех 42 кэшах контура — не из-за
дефекта токенизации, а потому что тега нет в исходных текстах. ADR-004 разделил
проверку на три уровня:

| Уровень | Что проверяется | Обязательность |
|---|---|---|
| 1. Токен-пространство | все 8 спецтокенов → **один id** (не сабтокены) | **всегда** |
| 2. Вхождения формата v12 | `<think>`, `</think>`, `<tool_call>`, `</tool_call>`, `<tool_response>`, `</tool_response>` | **всегда** (дефолт `--occurrences chat-format`) |
| 3. Неиспользуемые | `<reasoning>`, `</reasoning>` | вхождений **не требуем** |

Дополнять корпус парными `<reasoning>`-тегами **запрещено** — это фабрикация
данных в обход заморозки ADR-003. Значения уровня 3 печатаются как справка, но
гейтом не являются.

`--occurrences all8` (буквальная формулировка прежней редакции) остаётся
доступным **явным флагом** для разовых проверок и дефолтом не является: гейт,
красный на замороженном корпусе по причине, которую нельзя устранить иначе как
правкой данных, обесценивает сигнал.

Приоритет выбора кэша закреплён тем же ADR: `LAGUNA_TOK_CACHE` →
`cpt_corpus_v12r_8192_qwen25.npy` (рабочий кэш ревизии, ADR-002) → первый
`*.npy|*.npz` в `datasets/tok/`. Выбранный путь и причина выбора печатаются.
«Первый кэш в каталоге» без приоритета запрещён: он может оказаться посторонним
(`cpt_1024.npy`, август) и дать красный гейт по чужой причине.

Правило C-008 передаёт `--dataset ${LAGUNA_TOK_CACHE}`; при невыставленной
переменной bash убирает слово, поэтому `--dataset` объявлен с `nargs="?"`: без
значения (или с литералом `${...}`) инструмент переходит к автоопределению.

## Стенд GB10 (AD-5): выбор хоста и что считается нагрузкой

Порядок выбора стенда: `--host H` → `$GB10_HOST` → локальный GB10 (nvidia-smi) →
список кандидатов `--hosts "H1 H2"`/`$GB10_HOSTS` → по умолчанию `gb10-fast`,
затем `gb10`. Локальная проверка идёт перед ssh: в контуре Лагуны GB10 — это и
есть рабочая машина. Кандидатов несколько, потому что алиасы неравноценны: факт
14.09.2026 — `gb10` (192.0.2.50) из рабочей сети недоступен, рабочий
`gb10-fast` (192.0.2.2, прямой 10GbE). Берётся первый ответивший; если не
ответил никто — `gb10 not reachable — check skipped`, exit 0: «стенд недоступен»
не равно «инвариант нарушен».

Нагрузка опознаётся по имени эксперимента (`--exp_name`), а не по процессу: один
прогон стадии — это дерево `tmux → bash -c → run_v12_ladder.sh → safe_start.sh →
docker run → python laguna_pipeline_v8.py`, и подсчёт «по процессам» объявил бы
ОДНУ нагрузку нарушением AD-5 (замер 14.09.2026: 6 процессов = 1 нагрузка). Если
`--exp_name` в командных строках нет вовсе, нагрузкой считается корень совпавшего
дерева. Предел точности назван честно: два одновременных прогона с ОДНИМ
`--exp_name` не различаются.
