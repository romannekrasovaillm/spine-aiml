# laguna-compact — ревизия доменной лесенки Лагуны (кейс архитектурных решений)

> **Что это.** Ревизия существующего контура «Лагуна» (обучение компактной доменной
> LLM циклом **CPT → SFT → Agentic-RL** на русскоязычном корпусе концептов ML/AI)
> с целью получить **доказуемый и воспроизводимый** результат без известных дефектов
> контура. Не «новая модель с нуля» и не новый домен: та же ось, та же метрика,
> узкий протокол, но с дисциплиной решений.
>
> **Статус:** фаза 1 (пилот, один сид) идёт на стенде GB10. Точка решения — по
> `docs/specs/S4-PROTOCOL.md`. Артефактов на текущий момент: **21 ADR, 19 правил,
> 20 инструментов (+ тесты), 8 evidence-файлов, 5 каталогов прогонов**.
>
> **Владелец:** Роман Некрасов. **Стенд:** `gb10-fast` (DGX Spark GB10, 121 ГБ unified).
> **Данные и веса:** `/home/user/gb10-shared` (в кейсе — симлинки, AD-4).

## Порядок чтения (для человека и для агента)

1. **`docs/specs/REVISION.delta.md`** — что делаем, границы, стадии S0…S4,
   критерии приёмки, стоп-условия, план отката. Начинать отсюда.
2. **`ARCHITECTURE-SPINE.md`** (AD-1…AD-9) — инварианты: что связывают, какое
   расхождение предотвращают, каким правилом проверяются.
3. **`docs/adr/`** — 18 решений. Если нужен только контекст, читать по порядку
   номеров; если конкретный вопрос — см. карту ниже.
4. **`CONSTRAINTS.yaml`** — 18 механических правил (стражи). Их можно запустить:
   `arch-ml control check .` или `fitness_check`.
5. **`evidence/`** — доказательства по стадиям (см. таблицу ниже).
6. **`docs/specs/S4-PROTOCOL.md`** — как принимается решение о результате.
7. **`docs/HYPOTHESES-WATCH.md`** — реестр гипотез: какое событие в прогоне
   поднимает какую отложенную карточку и что по ней делать (чтобы не искать
   решение под давлением).

## Практика передачи работы кодовому харнессу (обновлено 16.09.2026)

Дельта передаётся пакетом `.arch-handoff/`: `TASK.md` (дельта-спека: цель, шаги,
критерии приёмки, «чего НЕ делать», JSON-контракт отчёта, требование финального коммита),
`ARCHITECTURE.md` (эпик-контекст), `CONSTRAINTS.yaml` (19 правил), `MANIFEST.json`
(маршрут, таймаут, baseline-коммит, план отката, подобранные скиллы), `ROLLBACK/RUBRIC`,
копии ADR.

**Изменение практики:** в аргумент `spec` теперь включается **`ARCHITECTURE-SPINE.md`**
вместе с профильными ADR. Причина: спайн раньше в пакет не попадал, и инварианты,
не покрытые механическим стражем (например, «кредит бинарный; градуированный — только
по доказательствам» с пометкой PENDING-EVIDENCE), доходили до задания только потому,
что архитектор писал запрет руками. Теперь инварианты идут в контекст напрямую,
а в TASK дополнительно перечисляются инварианты без стража, релевантные дельте.

**Процедура приёмки дельты (ADR-024) — шесть шагов, три из них обязательные новые:**
1. **До приёмки (в ветке):** гейт + тесты + наличие артефактов + `git log`/`git status`.
2. **Сверка редакции правил (новое):** `sha256` `CONSTRAINTS.yaml` в ветке против `main`; расхождение — сначала `merge main` в ветку, потом проверять (иначе гейт зелёный по устаревшей редакции).
3. **Чистота дерева (усилено):** незакоммиченных изменений нет; изменения **исторических `evidence/*`** завершённых стадий откатываются до приёмки.
4. **Мерж** (`accept`).
5. **Post-merge гейт обязателен (новое):** сразу после мержа прогнать гейт на `main`; красное — немедленный разбор.
6. **Проверка после конфликта (новое):** если мерж был с конфликтом — после ручного разрешения повторный прогон гейта **и** тестов.

**Чек-лист завершённости дельты (ADR-023, AD-12) — дельта принимается только при всех четырёх:**
1. заявленные артефакты **существуют** и проверяемы;
2. есть **финальный git-коммит** (результат берётся из истории, не из пересказа);
3. гейт (`fitness_check`) и тесты прогнаны, результат зафиксирован;
4. отчёт несёт **JSON-контракт** (`status: complete | partial | blocked`).

Не выполнен любой пункт → статус `blocked`, а не `complete`. **Код возврата харнесса
не является доказательством** (нулевой не подтверждает результат). Фоновые ожидания
запрещены, кроме автономных прогонов на стенде — там обязательны подтверждение старта
и идентификаторы (tmux-сессия, контейнер, шаги, манифест стадии). Размер дельты сверяется
с бюджетом **до** запуска: не влезает — разбить или сократить, зафиксировав ограничение.

## Как возобновить прогон после сбоя
1. Проверить, что цепочка не жива: `tmux ls` на стенде, `var/status/*`.
2. **Не запускать `run_pilot.py` при живой цепочке** — он перезаписывает
   `stages.tsv` под читателем (риск R2, ADR-016).
3. Возобновление идемпотентно: цепочка пропускает стадии с готовым артефактом
   (`checkpoints/<stage>_final.pt`), SFT/RL продолжают с последнего
   `*_checkpoint_N.pt`.
4. Перед стадией страж проверит хозяина ресурса и память; при отказе — причина
   печатается в лог цепочки.
5. После завершения — **вернуть стенд лесенке v12** (ADR-012 п.4): снять флаг
   `REVISION-WINDOW.lock`, `chmod +x` сторожу, восстановить crontab из бэкапа.

## Границы протокола (что этот кейс НЕ утверждает)

- Один сид фазы 1 **не даёт** статистики: `std` и `k-из-k` — `null`, pass@k не
  экстраполируется (`S4-PROTOCOL.md` §2).
- Выводы не переносятся на другие семейства и размеры моделей (ADR-001).
- Прогон в обычном режиме **бит-в-бит не воспроизводим**; воспроизводимость кода
  доказывается 20–50-шаговой детерминированной пробой (ADR-014).
- Публикация артефактов запрещена при `license_status: internal_only` (ADR-005).
