# laguna-compact — ревизия доменной лесенки Лагуны (кейс архитектурных решений)

> **Что это.** Ревизия существующего контура «Лагуна» (обучение компактной доменной
> LLM циклом **CPT → SFT → Agentic-RL** на русскоязычном корпусе концептов ML/AI)
> с целью получить **доказуемый и воспроизводимый** результат без известных дефектов
> контура. Не «новая модель с нуля» и не новый домен: та же ось, та же метрика,
> узкий протокол, но с дисциплиной решений.
>
> **Статус:** фаза 1 (пилот, один сид) идёт на стенде GB10; CPT завершён (LR×0.035,
> ADR-032), идёт стадия SFT. Точка решения — по `docs/specs/S4-PROTOCOL.md`.
> **Счётчиков артефактов в тексте нет — ни «N ADR», ни «M правил».** Рукописные числа
> расходились с деревом дважды: «18 ADR / 19 правил» против факта (решение архитектора
> 20.09.2026, `evidence/s3z2-canonization.json`) и «76 инструментов» против фактических
> (что стояло в тексте — `git log -p -- README.md`). Число читается командой из раздела
> «Числа артефактов»: **носитель числа — само дерево** (ADR-023 п.10).
> Состав `runs/` — прогоны с манифестом AD-2 и каталоги-непрогоны с маркером
> `NOT_A_RUN` (C-012), а не «сколько получилось».
>
> **Владелец:** Роман Некрасов. **Стенд:** `gb10-fast` (DGX Spark GB10, 121 ГБ unified).
> **Данные и веса:** `/home/user/gb10-shared` (в кейсе — симлинки, AD-4).

## Числа артефактов — командой, а не по памяти

Счётчики README расходились с деревом дважды, поэтому чисел артефактов в тексте нет:
**носитель числа — само дерево** (ADR-023 п.10 — у числа один носитель), а читается оно
командой из корня кейса:

```bash
ls docs/adr/*.md | wc -l                    # ADR (номер выдаёт канон — ADR-046 п.2)
grep -cE '^\s*- id: C-' CONSTRAINTS.yaml    # правила C-NNN
ls tools/*.py tools/*.sh | wc -l            # инструменты (без tools/tests/)
find evidence -type f | wc -l               # evidence-файлы
ls -d runs/*/ | wc -l                       # каталоги в runs/ (AD-2, маркер NOT_A_RUN — C-012)
```

Где счётчик нужен читателю по смыслу, рядом стоит команда: состав правил читает гейт
(`arch-ml control check .` или `fitness_check`), число проверок печатает сам прогон
тестов (`bash tools/tests/run_tool_tests.sh`, строка `итого: PASS=…`), каталоги `runs/`
разбирает `tools/check_run_manifest.py --runs runs/`.

Индекс артефактов — карты ниже («Карта решений (ADR)», «Карта доказательств (evidence)»,
«Инструменты (`tools/`)»): они отвечают, что где лежит, а числа к ним берутся командами
выше, а не из текста.

## Порядок чтения (для человека и для агента)

1. **`docs/specs/REVISION.delta.md`** — что делаем, границы, стадии S0…S4,
   критерии приёмки, стоп-условия, план отката. Начинать отсюда.
2. **`ARCHITECTURE-SPINE.md`** — инварианты (число — командой, см. «Числа артефактов»):
   что связывают, какое расхождение предотвращают, каким правилом проверяются.
3. **`docs/adr/`** — решения (число — командой, см. «Числа артефактов»). Если нужен
   только контекст, читать по порядку номеров; если конкретный вопрос — см. «Карту
   решений» ниже: там команда, печатающая индекс. Нумерация глобальна **внутри
   каталога кейса** и **выдаётся только каноном** (ADR-028 п.3 с уточнением
   ADR-046 п.2); следующий свободный номер читается по индексу решений
   (`arch-ml adr registry .`), а не из текста README.
4. **`CONSTRAINTS.yaml`** — механические правила-стражи (число — командой; номера
   C-021/C-022 зарезервированы предложениями). Их можно запустить:
   `arch-ml control check .` или `fitness_check`.
5. **`evidence/`** — доказательства по стадиям (см. таблицу ниже).
6. **`docs/specs/S4-PROTOCOL.md`** — как принимается решение о результате.
7. **`docs/HYPOTHESES-WATCH.md`** — реестр гипотез: какое событие в прогоне
   поднимает какую отложенную карточку и что по ней делать (чтобы не искать
   решение под давлением).

## Карта решений (ADR) — индекс печатает команда

Перечня ADR в README нет: рукописный список расходился с деревом (последний раз —
таблица кончалась на ADR-047, когда в `docs/adr/` уже лежали 048, 049 и 050), поэтому
решением архитектора 20.09.2026 числа и перечни артефактов в README не хранятся: рядом
стоит команда, которой они читаются. Индекс решений собирает реестр ADR (ADR-036) —
он читает **обе грани** каждого решения (прозу `docs/adr/ADR-NNN-*.md` и сущность
`model/ADR-NNN.md`) и печатает номер, тему, статус, дату и источник. Из корня кейса:

```bash
arch-ml adr registry .        # индекс решений: номер, тема, статус, дата, источник
```

Указатель на индекс — сам каталог `docs/adr/` (проза) вместе с `model/ADR-*.md`
(типизированные сущности): отдельного файла-индекса нет, его собирает команда, поэтому
дописывать список при новом решении не нужно — достаточно завести документ. Тема в
индексе — заголовок решения, а не пересказ: «когда обращаться» даёт сам документ
(разделы `Context` и `Alternatives Considered`). Чем решения проверяются механически —
`CONSTRAINTS.yaml` и раздел «Состояние правил (гейт)» ниже.

- **S3ar** — откуда петли SFT-состояния: петли размечены блоками (≥ 8 слов, ≥ 2 раз) по сегментам
  хода и найдены в обучающем наборе — 6 блоков из 409 (1.47 %), и все шесть оказались узорами из
  знаков (дефисы, цифры), а среди содержательных блоков в наборе нет **ни одного** (0 из 120) при
  контроле 3.86 % (`same_generation`) — вердикт «собственная дегенерация», а не воспроизведение
  выученного; ось кратности не измерена (0 строк-источников) и структурно не могла сработать:
  на шаге 21 500 прогон прошёл 0.97 файла при `shuffle=True` — ни одна строка не показана дважды ✅
- **S3at** — кривая зарождения петель: склейка ранних точек (S3ap, 19.09, локальная 4080) с точками тренда (S3as, 21.09, стенд GB10) в один ряд. - **rl-env-probe-gb10** — проба предусловий RL **на стенде** (ADR-049 п.10, Proposed; сам ADR
  живёт в ветви `arch/laguna-control-arms`): контейнерный механизм изоляции, детерминизм, цена
  шага и G1–G3 на пяти задачах заземлённого скелета. **Изоляция работает**: все обязательные
  пробы назвали ожидаемое (непривилегированный пользователь, read-only корень, нулевой `CapEff`,
  скрытые пути хоста, недоступный docker-сокет, закрытая сеть), 84 rollout'а в 4 батч-контейнерах
  по одному на сетевой профиль, откат состояния подтверждён на каждом (`seed_matches_pristine`),
  следов предыдущей задачи не остаётся (`residue_absent`). **Цена шага RL** (пересчёт формулы
  аудита на измеренных слагаемых, база 123.87 с): среда стоит **0.045 с на шаг инструмента**,

  проверены попыткой их нарушить: процессы — `can't fork` на 31-м при `pids-limit 32`, память —
  `awk_rc=137` при 256 МиБ, tmpfs — `No space left on device` при 16 МиБ. **Лимит шагов**

## Состояние правил (гейт)

`fitness_check` считает все правила `CONSTRAINTS.yaml` (`grep -cE '^\s*- id: C-' CONSTRAINTS.yaml`);
их состав — C-001…C-020 и C-023…C-032. Живое состояние гейта — не этот текст, а прогон
(`arch-ml control check .`): на 22.09.2026 красное — **C-018** (AD-9 читает
живую память стенда и мерцает по занятости стадии; на приёмке информационен —
решение архитектора 20.09.2026, обязателен как предусловие старта).

**C-014 зелёное и больше не «ждёт S4».** Двумя дельтами (S3bd, S3be) правило приведено
к предмету: сначала glob — к каноническому имени отчёта
(`evidence/result-report.json`; прежний `evidence/result-report-*.json` не увидел бы
сданный отчёт), затем тип — на **фазу**. Пока правило было `each_file_must_contain`,
оно краснело **по построению**: пустой набор по glob — находка движка, а отчёт до замера
не создаётся (S4-PROTOCOL §5: заранее созданный сделал бы правило ложно зелёным, поэтому
шаблон отчёта живёт в `docs/specs/`, а не в `evidence/`). Теперь правило зовёт
`tools/check_result_report.py` и различает три состояния: `PENDING-EVIDENCE` (фаза не
наступила → `warn`), `MISSING-REPORT` (точка решения пройдена, а отчёта нет → `error`,
долг) и `INCOMPLETE` (отчёт есть, но обязательные поля схемы выведены не все →
`error`, поимённо). Полнота проверяется **конъюнкцией** полей
`docs/specs/result-report.schema.json`, а не дизъюнкцией подстрок: отчёт с одним словом
«axis» полным больше не считается.

Зелёные: C-001…C-020 (включая **C-018** — страж хозяина ресурса,
который 14.09 корректно отказал в старте при активном `@reboot` лесенки, и **C-020**
(S3p, следствие ADR-025 п.2): evidence PPL несёт `leak_check` либо `leak_check_ref`;
из правила точечно исключена база S3h — её `sha256` прибит в 6 артефактах, и правка
метаданных разорвала бы привязку числа к версии файла).

**C-029** — запрет сна во время GPU-нагрузки (вторая грань AD-9, дельты
`sleep-guard-in-launch` и `sleep-guard-masked-stand`, 21.09.2026). Обвязка
`tools/guard_cuda_run.sh` существовала,
но **её не применял ни один запуск**: защита держалась на памяти человека. Правило
превращает «не рекомендовано» в находку — тем же способом, что C-025 сделал для стража
реестра приборов (страж, живущий только в тестах, гейтом не является). Класс риска тот
же, что у C-018: ресурс достаётся нагрузке, которая может быть уничтожена извне; только
там внешний конкурент — чужой прогон, а здесь — сон машины.

Что стало механическим (и где граница):

| Где | Что мешает запуску без защиты сна |
|---|---|
| обвязка `guard_cuda_run.sh` | **не стартует** без доказанной защиты: инхибит берётся с самопроверкой **либо** доказывается структурная недостижимость сна; `--no-inhibit` означает «уже взята снаружи» и проверяется стражем, а не объявляется (`refused_no_inhibit`, код 2) |
| раннер `launch_sft_stage.py` | `--do launch\|all` **отказывается** стартовать без доказанной защиты (exit 2); `build`/`check`/`facts` нагрузки не ставят и защиты не требуют |
| стадия SFT | защита стоит **в записанной команде цепочки** (`chain_command.txt`), перед самой цепочкой, а не вокруг запускающего её `ssh`: тот возвращается сразу, и снятая с него защита не защитила бы ничего. Первым идёт `tools/chain_sleep_guard.sh`: он решает **на площадке прогона**, каким из двух способов защищаться (инхибит берётся сам; где нечем — требуется доказанная недостижимость сна), и отказывает **закрыто** — без защиты цепочка не стартует (проверено) |
| прибор `probe_language_split.py` | тронуть нельзя (пиннут хешем, ADR-041). Обход ловится живьём: нагрузка без запрета — находка с pid и командной строкой; плюс у прогона, начатого после момента вступления правила в силу (2026-09-21 14:22:35 MSK), обязано быть доказательство (расписка либо защита в записанной команде); прогоны старше этого момента печатаются поимённо как `legacy-not-checked` («старше правила, защита сна НЕ доказана») и находкой не выставляются (ADR-053) |

Проверяются три источника, все — факт, а не декларация: **живые** нагрузки (обе
площадки), **доказательства** прогонов, начатых после момента вступления правила в силу (2026-09-21 14:22:35 MSK, ADR-053), и **состояние защиты** на
каждой площадке. Прогоны, начатые раньше порога, — не находка, а поимённо названные
исторические `legacy-not-checked` («старше правила, защита сна НЕ доказана»):
ADR-028 п.4 (история не переписывается), ADR-053 п.2 (порог — момент вступления
правила в силу, а не начало суток).

**Защита площадки — два способа, оба доказательством** (дельта
`sleep-guard-masked-stand`, 21.09.2026). Инхибит — не единственный способ удержать
сон. На `gb10-fast` его взять неоткуда — `systemd-inhibit` отвечает `Failed to
inhibit: Access denied` (у пользователя нет logind-сессии), — но сон там
**структурно недостижим**: `/etc/systemd/system/{sleep,suspend,hibernate,hybrid-sleep}.target
→ /dev/null` (переживает перезагрузку), и это доказано **попыткой**:
`sudo -n systemctl start suspend.target` → `Unit suspend.target is masked.`. Флаг без
провала попытки доказательством не считается, провал без причины о маскировке — тем
более (`Interactive authentication required` даёт и незамаскированная площадка), а
попытка не может усыпить площадку по построению: она делается только после того, как
все четыре цели прочитаны `masked`. Прежде такая площадка отдавалась **блокером**, и
старт стадии на ней был невозможен, хотя фактическая защита там **сильнее** инхибита.

Красное при этом осталось красным: площадка, **измеренная** и не защищённая ни одним
из двух способов, — находка (exit 1), «маскировка прочитана, а попытка прошла» —
тоже, расписка без имени способа (`protection: inhibit | masked_targets`) —
доказательством не считается. Различие «не измерено» и «измерено и не защищено»
названо: недоступный стенд остаётся NOT-VERIFIED, потому что красить гейт чужой
занятостью нельзя, а выдавать неизмеренное за проверенное — тем более.

**C-023/C-024** — карточка обучающего набора SFT (дыра G3 плана стадии): набор
зафиксирован карточкой, карточка несёт полный хеш и долю дубликатов с эквивалентом эпох.
**Номера выданы при сведении веток (S3z-2), а не в ветке:** в `arch/laguna-control-arms`
эти два правила были выданы локальным счётом как C-020/C-021 и столкнулись с занятыми
номерами канона (C-020 — `leak_check`, ADR-025 п.2; C-021 — предложение AD-12 из
`docs/specs/HANDOFF-CONTRACT-PROPOSAL.md`; C-022 зарезервирован за стражем agentic-доли,
ADR-035 п.5). Номер выдаёт канон (ADR-046 п.2), поэтому правила ветки уехали на следующие
свободные номера, тексты правил не менялись. Ссылки «C-020/C-021» в артефактах стадии SFT
(`evidence/s3aa-sft-launch.json`, `runs/sft-20260916-2246/HANDOFF.md`) означают **эти два
правила** — как исторический факт они не переписываются (ADR-028 п.4).

**C-025** — реестр редакций приборов в гейте (дельта `followup-instruments`, 20.09.2026):
страж `tools/check_instrument_versions.py` держал соответствие «прибор ↔ редакция ↔ sha256»,
но вызывался только секцией 31 набора тестов, а тест гейтом не является — страж, живущий
в тестах, не попадал ни в `fitness_check`, ни в трассируемость (ровно та обратная проверка,
которую AD-10 держит как pending evidence). Правило называет стража в гейте; заодно реестр
стал вести **два** прибора — `tools/ppl_probe.py` (P-1…P-4) и
`tools/probe_pool_v2_reachability.py` (R-1, прибор пробы п.5 ADR-021).

**C-026/C-027** — страж заземления (ADR-049 п.5/п.11, заземлённая ось RL): успех без
`tool_call` → красное; **отсутствие** заземлённого артефакта — `PENDING-EVIDENCE` (warn),
а не error, иначе повторяется класс «тест, красный by construction» (ADR-023 п.12).
**Номера выданы при сведении веток, а не в ветке:** в `arch/laguna-control-arms` эти два
правила были выданы локальным счётом как C-022/C-023 и столкнулись с занятыми номерами
канона (C-022 зарезервирован за стражем agentic-доли, ADR-035 п.5; C-023/C-024 — карточка
SFT-набора выше). Номер выдаёт канон (ADR-046 п.8), поэтому правила ветки уехали на
следующие свободные номера, тексты правил не менялись. Ссылка «C-022» в артефакте стадии
S3aq (`evidence/s3aq-acceptance-reds.json`) означает **первое из этих правил** — как
исторический факт она не переписывается (ADR-028 п.4). **Краснота C-026 снята
20.09.2026:** правило было красным *по построению* — карточка набора хешировала
пересобираемый байткод (`__pycache__/*.pyc`), часть которого удалена с диска, поэтому
`sha256_full` из git не воспроизводился. Исправлена **политика**, а не артефакт:
байткод исключён из канонической карты в обоих инструментах
(`tools/grounded_runner.py`, `tools/check_grounded_pool.py`), карточка пересобрана, а
прежнее объявление идентичности сохранено рядом (`previous_sha256_full` и соседние
поля, ADR-028 п.1). Доказательство S4-skeleton **не переписывалось** — страж опознаёт
его по прежней идентичности, восстанавливая её из текущей карты и объявленных отличий.
Разбор прежней красноты и предписанный порядок — `evidence/s3aq-acceptance-reds.json`
(`grounded_card_stale`, статус `resolved`).

**Контракт среды доказан пробой (20.09.2026, набор `67a80be4…`).** Правка *измеренных*
артефактов набора — пять `task.json` получили `max_steps` и схему `grounded-task/2`, а
задача с моком переехала из дефолтной `bridge` в свою `internal`-сеть с канарейкой —
снимает опознание по прежней идентичности: содержательная часть изменилась, и
доказательство прежней редакции становится фактом **другой** редакции, а не устаревшей
записью текущей. Аудиторский след **не переписан** (ADR-023 п.9): прежний файл сохранён
поимённо (`evidence/grounded-skeleton-r1-2026-09-20.json`), новый прогон записан на
канонический путь `evidence/grounded-skeleton.json`. Прогон вёлся раннером с пробами
контракта (`--step-probe --timeout-probe --teardown-probe --repeat 2`) на стенде
`gb10-fast`; поля контракта воспроизвелись дважды в один день (17:22Z и 16:50Z, второй
артефакт — вне дерева, каталог прерванной попытки; совпадение по всем полям контракта,
различаются только имена прогона и тайминги). Это была проба **на хосте стенда**;
редакция на каноническом пути сменилась в тот же день ещё раз — пробой внутри
контейнера стадии (следующий абзац), и предметом смены был механизм мока.

**Мок переехал в sidecar, и проба изоляции стала исполнимой из контейнера стадии
(20.09.2026, поправка ADR-049 п.10).** Требование «повторить пробу внутри
контейнера стадии» в буквальном виде было неисполнимо: мок поднимался **слушателем
на шлюзе сети прогона**, а этим адресом владеет хост — из контейнера раннер падал в
`OSError: [Errno 99] Cannot assign requested address`. Мок стал **контейнером в той
же внутренней сети**, что и песочница: достижимость больше не зависит от топологии.
Админ-операции (ротация журнала, чтение выборки) идут **через демон** — у раннера
нет своего сетевого пути к моку, поэтому механизм один и там, и там. Канарейка
выхода — тоже контейнер, но на дефолтной bridge (её живость подтверждается
self-check'ом: недостижимость мёртвого слушателя ничего не доказывает), а страж
требует от доказательства **следа механизма** — имя, образ, адрес в сети прогона,
`in_run_network`, — поэтому доказательство прежнего механизма краснеет
(`mock-mechanism-unnamed`), а не проходит по инерции. Цена: **+1 контейнер на батч,
0.77 с** (подъём 0.65 с + снятие 0.12 с) — меньше grace-периода `docker stop -t 1`
(1.09 с), который снятие уже не платит, и 0.097 с на rollout при R = 8. Проба
исполнена **внутри контейнера стадии** на `gb10-fast`: sidecar достижим, G1–G4
выполнены, страж изнутри зелёный, его зубы краснеют; вложенной сети не обнаружено.

**Контракт среды — попыткой, а не флагом.** `tools/check_env_contract.py` не читает
профиль сети вообще: он поднимает контейнер и пробует выйти тремя независимыми
способами. Зубы проверены обратным ходом — на дефолтной `bridge` страж **краснеет**
(`--probe-network bridge` → `egress-open`: публичный IP `rc=0` и канарейка `rc=0`), на
`internal` — зелёный с нулём находок. Страж требует от доказательства и **следа
механизма** мока (sidecar-контейнер в сети прогона, живая канарейка): без этого
«мок достижим» не отличает контейнер от процесса на адресе хоста, а такой процесс
из контейнера стадии неисполним. Страж подключён к гейту правилом **C-028**
(severity error, `timeout_secs: 300` — проба живая, на холодном хосте тянет ДВА образа):
канон кейса требует, чтобы страж жил **в гейте, а не только в тестах** (AD-10;
`docs/specs/INSTRUMENT-VERSIONS.md` §5 называет эту дыру ровно на примере C-025).
**Номер предварительный:** номера правил выдаёт канон при сведении (ADR-046 п.8) — в
этой же ветке самовыданные C-022/C-023 столкнулись с занятыми номерами и на сведении
уехали на C-026/C-027. При коллизии правило уезжает на следующий свободный, текст не
меняется. Граница названа в самом правиле, а не умолчана: на хосте без docker проба
невыполнима (exit 2 NOT-VERIFIED), и правило краснеет — молчание доказательством не
является (ADR-023 п.12).

**Чего проба не доказала — и что изменилось 20.09.2026.** Первый повтор пробы
**внутри контейнера стадии** (ADR-049 п.10) не состоялся: раннер изнутри контейнера
был неисполним — HTTP-мок поднимался на шлюзе сети прогона, а этим адресом владеет
хост, не контейнер (проверено: `OSError: [Errno 99] Cannot assign requested address`
на образе стадии `nvcr.io/nvidia/pytorch:26.07-py3-vllm` с примонтированным сокетом
docker), и проба шла на **хосте** стенда. Причина устранена не обходом, а механизмом:
мок стал **sidecar-контейнером в той же внутренней сети** (поправка ADR-049 п.10),
поэтому достижимость перестала зависеть от топологии. Проба повторена **внутри**
контейнера стадии и **прошла** (sidecar достижим, G1–G4 выполнены, страж изнутри
зелёный, его зубы краснеют; вложенной сети не обнаружено). Цена механизма —
+1 контейнер на батч, 0.77 с, — измерена, а не предположена.

**Граница переносимости чисел: стенд прогрет — и это названо, а не умолчано.**
Числа сняты там, где оба образа — песочницы (`alpine:3.20`) и sidecar'ов
(`python:3.12-alpine`) — уже лежали в хранилище демона: тяга в замере не было
вовсе. Время скачивания на **холодном** стенде **не наблюдалось и не измерено**, и
оценкой оно не подставляется — оценка не замер (ADR-023 п.13): пустое место
названо пустым. С этой дельты тяг стал наблюдаемым (`host.images[].pull_s` отчёта
прибора: `null` — образ лежал, число — стоил столько секунд), поэтому следующий
прогон на чистом стенде даст цену сам; к числам 20.09.2026 такого замера нет и
появиться не может — замороженное доказательство не переписывается (ADR-028 п.4).
Границы объявлены машинно: `evidence/grounded-portability.json`; числа прибора —
`docs/specs/INSTRUMENT-VERSIONS.md` §2.3 (редакция G-4).

Побочно проба нашла дефект, который на хосте не проявлялся: раннер внутри контейнера
стадии работает от root, и скопированное им состояние `/work` (и журнал мока)
принадлежало root'у, а песочница работает под uid 1000 — задача падала на
`mv: Permission denied` не потому, что не решена, а потому, что среда не дала писать.
Владение передаётся контейнерам прогона явно, свойство проверяется пробой
(`state_writable`) и входит в G4.

**Несовпадение путей перестало быть косвенным (20.09.2026).** Тот же класс дефекта,
что владение файлами: «среда не дала» выглядело как «задача не решена». Невидимый
демону каталог прогона давал ровно одну улику — «мок не отметился готовым», — и по
ней нельзя было отличить невидимый каталог от нерешаемой задачи. Теперь **до**
прогона идёт предпроверка: маркер-контейнер читает по названному пути nonce
каталога прогона, состав дерева набора и размер карточки; расхождение
останавливает прогон явным сообщением с путём и причиной (`--mount-preflight-only`
даёт ту же проверку без прогона). Два лица дефекта — «демон пути не видит» и «демон
видит ДРУГОЙ каталог» — проверены **живыми мутантами** (раннер запускается внутри
контейнера, где у демона и у раннера разные виды на один путь); дерево набора
проверяется тогда, когда прогон будет его монтировать, — иначе проба краснела бы на
наборе без мока (ADR-023 п.12).

Порядок сведения веток (S3z) снял два давних красных теста: расхождение пула v2
с карточкой (S3p) и отсутствие секций приборов в `tools/tests/run_tool_tests.sh`
(объединение секций вместо выбора одной редакции). Сведение `arch/laguna-control-arms`
(S3z-2) сохраняет оба: секции приборов объединены уже по семи редакциям, к ним добавлены
секции стадии SFT (20–28).

## Практика передачи работы кодовому харнессу (обновлено 16.09.2026)

Дельта передаётся пакетом `.arch-handoff/`: `TASK.md` (дельта-спека: цель, шаги,
критерии приёмки, «чего НЕ делать», JSON-контракт отчёта, требование финального коммита),
`ARCHITECTURE.md` (эпик-контекст), `CONSTRAINTS.yaml` — редакция правил в пакете
сверяется при каждой передаче (ADR-024 шаг 2), а число правил кейса читается
командой (`grep -cE '^\s*- id: C-' CONSTRAINTS.yaml`, см. «Числа артефактов» —
числа в тексте не держим), `MANIFEST.json` (маршрут, таймаут, baseline-коммит, план отката,
подобранные скиллы), `ROLLBACK/RUBRIC`, копии ADR.

**Изменение практики:** в аргумент `spec` теперь включается **`ARCHITECTURE-SPINE.md`**
вместе с профильными ADR. Причина: спайн раньше в пакет не попадал, и инварианты,
не покрытые механическим стражем (например, «кредит бинарный; градуированный — только
по доказательствам» с пометкой PENDING-EVIDENCE), доходили до задания только потому,
что архитектор писал запрет руками. Теперь инварианты идут в контекст напрямую,
а в TASK дополнительно перечисляются инварианты без стража, релевантные дельте.

**Процедура приёмки дельты (ADR-024) — шесть шагов, три из них обязательные новые:**
1. **До приёмки (в ветке):** гейт + тесты + наличие артефактов + `git log`/`git status`.
2. **Сверка редакции правил (новое):** `sha256` `CONSTRAINTS.yaml` в ветке против `main`; расхождение — сначала `merge main` в ветку, потом проверять (иначе гейт зелёный по устаревшей редакции).
3. **Чистота дерева (усилено):** незакоммиченных изменений нет; изменения **исторических `evidence/*`** завершённых стадий откатываются до приёмки.
4. **Мерж** (`accept`).
5. **Post-merge гейт обязателен (новое):** сразу после мержа прогнать гейт на `main`; красное — немедленный разбор.
6. **Проверка после конфликта (новое):** если мерж был с конфликтом — после ручного разрешения повторный прогон гейта **и** тестов.

**Чек-лист завершённости дельты (ADR-023, AD-12) — дельта принимается только при всех четырёх:**
1. заявленные артефакты **существуют** и проверяемы;
2. есть **финальный git-коммит** (результат берётся из истории, не из пересказа);
3. гейт (`fitness_check`) и тесты прогнаны, результат зафиксирован;
4. отчёт несёт **JSON-контракт** (`status: complete | partial | blocked`).

Не выполнен любой пункт → статус `blocked`, а не `complete`. **Код возврата харнесса
не является доказательством** (нулевой не подтверждает результат). Фоновые ожидания
запрещены, кроме автономных прогонов на стенде — там обязательны подтверждение старта
и идентификаторы (tmux-сессия, контейнер, шаги, манифест стадии). Размер дельты сверяется
с бюджетом **до** запуска: не влезает — разбить или сократить, зафиксировав ограничение.

**Практика от 21.09.2026 (ADR-051): решение, меняющее вход, без доказательства
исполнения не принимается.** Проверка, стоящая на артефакте («файл создан»,
«манифест есть»), не отвечает на вопрос, дошло ли решение до потребителя: ADR-042 был
исполнен полностью, а перезапуск прочёл прежний набор — и правило было зелёным. Поэтому
решение, меняющее вход, артефакт-потребитель или контракт, несёт раздел «Доказательство
исполнения» — **чем** доказано, что решение дошло до потребителя (носитель: поле
манифеста, строка лога, sha прочитанного файла, число; потребитель: носитель возник у
читающей стороны). Раздел проверяется механически правилом C-031
(`tools/check_execution_proof.py`); решение, которое не меняет ни вход, ни потребителя,
ни контракт, обязано назвать неприменимость с причиной — это названное исключение,
а не пропуск. Образец заполнения — раздел в **ADR-051**.

**Два дополнения ADR-023 от 20.09.2026 (по инциденту S3aq), пп.12–13.** Разбор идёт
не только по «есть результат / нет результата», но и по **фазе**: пока замер жив
(liveness по `pid` из `resume_confirmed.json`), проверка «свод против каталога прогона»
не выполняется — она возвращает `active`/`skipped`, а не красное; строгая проверка
обязательна, когда процесс мёртв или отчёт существует. Красное теста, который во время
живого прогона красный **by construction**, сигналом не является. И второе: артефакт,
который пересобирается целиком (свод состояния), **не хранит долговечные поля** — они
идут sidecar-файлом рядом (`resume_confirmed.json` рядом с `run_state.json`), потому что
пересборка затрёт всё, чего нет в сырье.

## Как возобновить прогон после сбоя
1. Проверить, что цепочка не жива: `tmux ls` на стенде, `var/status/*`.
2. **Не запускать `run_pilot.py` при живой цепочке** — он перезаписывает
   `stages.tsv` под читателем (риск R2, ADR-016).
3. Возобновление идемпотентно: цепочка пропускает стадии с готовым артефактом
   (`checkpoints/<stage>_final.pt`), SFT/RL продолжают с последнего
   `*_checkpoint_N.pt`.
4. Перед стадией страж проверит хозяина ресурса и память; при отказе — причина
   печатается в лог цепочки.
5. После завершения — **вернуть стенд лесенке v12** (ADR-012 п.4): снять флаг
   `REVISION-WINDOW.lock`, `chmod +x` сторожу, восстановить crontab из бэкапа.
6. **Остановить живой прогон по решению** (смена конфигурации, остановка стадии) —
   только штатным путём ADR-016 п.2: `python3 tools/run_full_cpt.py --stop --ts <ts>`
   (маркер `var/STOPPED` того же формата, что пишет страж цепочки, + `docker stop`).
   `docker kill` и `tmux kill-session` в обход этого пути запрещены: без маркера
   цепочка запишет стадии `failed` вместо `stopped`, и остановленный по решению
   прогон станет неотличим от упавшего.
