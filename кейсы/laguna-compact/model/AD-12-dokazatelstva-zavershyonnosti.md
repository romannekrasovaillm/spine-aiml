- **Binds**: формулировка TASK ↔ отчёт исполнителя ↔ проверка приёмки ↔ факты в git и артефактах
- **Prevents**: класс «зелёный без результата». Зафиксированные случаи: отчёт «успешно» без коммитов и файлов в git (запуск пилота); **код возврата 0 при отсутствии evidence**, работа отложена в фон (`hr-33`: скрипт 45 КБ создан, результатов нет, процессов не осталось, GPU свободна); 8 прогонов из 30 завершились без JSON-контракта. Код возврата харнесса **ничего не доказывает**: ненулевой сигнализирует о сбое, нулевой не подтверждает результат
- **Rule**: дельта принимается только при всех четырёх условиях: (1) артефакты существуют и проверяемы; (2) есть финальный git-коммит; (3) гейт и тесты прогнаны; (4) отчёт несёт JSON-контракт (`complete | partial | blocked`). Не выполнен любой → `blocked`, а не `complete`. Фоновые ожидания запрещены, кроме автономных прогонов на стенде (там обязательны подтверждение старта и идентификаторы: tmux, контейнер, шаги, манифест). Размер дельты сверяется с бюджетом **до** запуска: не влезает — разбить или сократить с фиксацией ограничения.
- **Pending evidence**: [PENDING-EVIDENCE: правила в CONSTRAINTS.yaml нет — проверка ручная (git + артефакты + гейт), хотя страж-инструмент для условия 4 существует и проверен (`tools/check_handoff_contract.py`, 89/89 совпадений с вердиктом харнесса): предложение C-021 (`docs/specs/HANDOFF-CONTRACT-PROPOSAL.md`) внесено не было. Условие снятия: C-021 внесено по §4 предложения (окно `--latest` и изоляция по кейсу — решение архитектора), после чего условие 4 проверяется механически. Кандидат на автоматизацию остальных условий: правило, требующее в каждом `runs/<id>/` одновременно манифест (C-012) и evidence-файл]
