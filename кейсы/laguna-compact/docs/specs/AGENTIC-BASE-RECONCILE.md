# Аудит коллизии двух agentic-баз (45.1 % vs «0 на 700»)

> Read-only сверка двух чисел, приписываемых «CPT-состоянию», по первоисточникам
> артефактов. Вывод — только со ссылками файл:строка. Дата аудита: 2026-09-25.

## 1. Коллизия и её суть

В кейсе ходят два несовместимых числа «доли самостоятельных вызовов инструмента»,
оба на момент написания приписывались CPT-состоянию:

* **45.1 % (158 из 350)** — `docs/specs/AGENTIC-GUARD.md:14` и
  `docs/adr/ADR-033-*.md:32` (правка 17.09.2026 по замеру `hr-68`).
* **«0 на 700 задач»** — `docs/reports/CPT-report-20260917.md:184`
  («на текущем чекпойнте самовызовов не зафиксировано вовсе») и исходная посылка
  `docs/adr/ADR-033-*.md:24` («на текущем (CPT) чекпойнте … ноль на 700 задач»).

Коллизия снимается так: **это разные приборные конфигурации на разных чекпойнтах.**
«45.1 %» снят на CPT-финале без форсирования; «0 на 700» — на SFT-финале с
форсированием вызова (`toolcall_force`). Ни одно число не является «неправильным
замером того же» — они измеряют разное, и только одно из них (45.1 %) относится к
CPT. Подробнее — таблица §3.

## 4. Вердикт

**База 45.1 % НЕ сопоставима с будущим замером на SFT-финале** — даже при флагах
`--no-toolcall-force --no-hint`.

Флаги `--no-toolcall-force --no-hint` у базы 45.1 % **соблюдены**
(`toolcall_force=false`, `prefill="<think>\n"` без `<tool_call>`), но этого
недостаточно: между замером базы и будущим SFT-замером лежит **третья ортогональная
ось — режим декодирования**. База снята в legacy-режиме (без запрета повторов
n-грамм), а SFT-замер по `ADR-041` обязан идти в штатном режиме
(`no_repeat_ngram=4`). `ADR-041:23` формулирует это явно: сравнивать агентность
«до/после» с уже снятой базой 45.1 % (158/350) **нельзя — база получена в
legacy-режиме**. `ADR-041:31` (Decision п.3): «Agentic-база переснимается в штатном
режиме (прежние 45.1 % — 158/350 — сохраняются как исторические, но выходят из
критерия)».

Действующая (штатная) база для сравнения с SFT-финалом — **36.6 % (128/350)** из
`s3am-agentic-cpt-standard.json` (переснятие по ADR-041), а не 45.1 %.

## 5. Обязательные условия для будущего сравнения

Для корректного сравнения SFT-финала с базой должны выполняться **все** условия
(проверяются по полям отчёта, а не по описанию):

1. **Пул тот же** — `sha256` пулов совпадает: v2
   `e678eb680d5abba0825f81d3e84cda3f680a51850f683fa6f1a3aa22de91d4da`, v1
   `06b95b2f3b62d2f8b24a458ca49ff13232b9fc7a00c5390e4354d6b2956a5eb3`
   (`s3aa-agentic-cpt.json:77,407`; закреплены в `--expect-pool-sha256`,
   `AGENTIC-GUARD.md:72-73`).
2. **Без форсирования** — `toolcall_force=false` (`--no-toolcall-force`).
3. **Без hint** — `prefill="<think>\n"`, без вложенного `<tool_call>`
   (`--no-hint`).
4. **Штатный режим декодирования** — `protocol.decoding.no_repeat_ngram=4`,
   `standard=true`, `legacy_decoding=false` (ADR-041 п.1, п.4). Это условие
   **отсутствует** в тексте правила C-022 в `AGENTIC-GUARD.md:95-102`, который
   пингует legacy-базу 45.1 % — текст правила устарел относительно ADR-041.
5. **Та же выборка** — `--per-type 50 --seed 42` → v1 n=150 (3 типа), v2 n=200
   (4 типа), итого 350 (`s3aa`/`s3am` strata; `AGENTIC-GUARD.md:66`).
6. **Тот же протокол** — `max_turns=5`, `n_attempts=1`, `temperature=1.0`,
   `top_k=20`, `max_new_tokens=4096`, `batch=32`, один system prompt/tool/verifier.
7. **Сравнение только на совпавшем составе** — по каждому пулу (v1↔v1, v2↔v2) и
   сводно только при том же составе подвыборок (`AGENTIC-GUARD.md:49-52`).

## 7. Прочие находки (не блокируют вывод, но требуют правок)

1. **`AGENTIC-GUARD.md` устарел относительно ADR-041.** Документ (и текст правила
   C-022, `:95-102`) пингует базу 45.1 % и не содержит условия о штатном режиме
   декодирования; ADR-041 (18.09) вывел 45.1 % из критерия и требует переснятия.
   Спека `SFT-POINT-CHAIN.md:30` (25.09) это уже фиксирует: «штатный режим
   декодирования; … сначала сверить сопоставимость базы».
2. **Остаточная коллизия внутри ADR-033:** `ADR-033:24` (Context) всё ещё
   утверждает «ноль на 700 задач» на CPT, правка добавлена только в `:32`
   (Decision), а не в исходную посылку.
3. **Метка `weights_kind="sft_checkpoint"`** в `s3aa:56` и `s3am` противоречит
   идентичности чекпойнта (CPT-финал `080c3ab6…`) — см. §2.1.
4. **Сводная доля по двум пулам не является type-matched** (у v1 и v2 совпадает
   только `explain_relation`, `s3aa-agentic-cpt.json` `delta_v2_minus_v1`), поэтому
   агрегат 158/350 (или 128/350) — это сравнение «пул целиком», а не
   покомпонентное; построчно сопоставим только тип `explain_relation`.
