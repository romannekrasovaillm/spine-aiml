## 0. Предмет: два дефекта адресации, один класс

| # | Что не так | Чем доказано |
|---|---|---|
| D1 | §1 адресует eval-артефакты по имени **пилота** (`runs/pilot-compact-s42-*/logs/`), тогда как носитель SFT-базы — **другой прогон**: `sft-v13-2e6-20260921-2054` | `runs/pilot-compact-s42-20260914-1626/logs/` содержит **только `cpt.log`**; ни одного `eval_results*.json` нет ни в репозитории, ни в `gb10-shared`/`experiments`; `stages.tsv` пилота объявлял `logs/eval_results_{base,sft}.json`, но `chain-check.log` фиксирует «стадия не запускается: `--check-only`» |
| D2 | Критерий домена читается «по набору v3», но без явного запрета на **калибровочную шкалу монитора** (`DOMAIN_ratio ≈ 0.348`), которая печатается рядом и выглядит как «то же число» | `runs/full-cpt-ppl-20260916-2149/trend.json` → `.DOMAIN = 0.3482`; `runs/sft-20260916-2246/HANDOFF.md` → `×0.3485`; `evidence/s3aa-sft-launch.json` → `DOMAIN_ratio: 0.35427`. Решающая мера — `ppl/13.559193` по `domain_eval_v3.txt` (`evidence/s3ao-domain-v3.json`, `runs/s3ao-domain-v3-20260919/ppl_cpt_final.json`) |

Оба дефекта — **один класс** (ADR-051 п.4/п.3): объявлен один носитель — прочитан другой. В D1 это путь, в D2 — шкала одного и того же слова «домен».

**Следствие для текущей ветки.** Приборная цепочка `runs/sft-point-chain-20260925-1000/` (`SFT-POINT-CHAIN.md`) — это и есть новый носитель eval-артефактов SFT-стадии. Протокол обязан уметь адресовать **её**, а не только пилота.

## 1. Точное место правки и предлагаемая формулировка

### 1.1 `S4-PROTOCOL.md` §1, таблица (строки 9–16), в первую очередь строки 11–13

**Было (строки 9–16):**

```
| Артефакт | Где | Что берём |
|---|---|---|
| `eval_results_sft.json` | `runs/pilot-compact-s42-*/logs/` | `judge_mean` **SFT-базовой** (на том же чекпойнте) |
| `eval_results.json` | там же | `judge_mean` после RL |
| `eval_results_base.json` | там же | база до SFT (ориентир) |
...
```

**Стало (предлагается):**

```
| Артефакт | Где (носитель — имя прогона, не пилота) | Что берём |
|---|---|---|
| `eval_results_sft.json` | `runs/<носитель SFT-стадии>/logs/` — для текущей ветки носитель стадии `sft-v13-2e6-20260921-2054`; у него стадий замера в цепочке **не было**, поэтому артефакт создаёт приборная цепочка `runs/sft-point-chain-<ts>/` (`SFT-POINT-CHAIN.md` §3 п.2) | `judge_mean` **SFT-базовой** (на том же чекпойнте) |
| `eval_results.json` | `runs/<носитель RL-стадии>/logs/` — **сейчас отсутствует**: RL не запускался | `judge_mean` после RL |
| `eval_results_base.json` | тот же носитель, что RL-стадия; при отсутствии — `runs/sft-point-chain-<ts>/` | база до SFT (ориентир) |
```

**Правило адресации (новый абзац сразу под таблицей, после строки 16):**

```
**Адрес артефакта — имя прогона-носителя, а не имя пилота.** `runs/pilot-compact-s42-*/`
— исторический адрес прогона 14.09; eval-артефактов там нет (каталог `logs/` содержит только
`cpt.log`), и объект другой: SFT-стадия пилота обучена на `v12` при объявленном `v13`
(ADR-051). Прогон, чей чекпойнт стоит на оси, обязан быть назван поимённо — вместе с путём
артефакта и sha256 набора/чекпойнта (ADR-051 п.2/п.4). Отсутствие артефакта по объявленному
адресу — **находка**, а не «нет данных».
```

### 1.2 `S4-PROTOCOL.md` §3 критерий 3, строка 44 (домен)

**Было (строка 44):**

```
   - **Домен** (`domain_eval_v3`, 200 док): отношение к базе **< 1** = домен выучен (ADR-044 п.1/п.6; правило чтения — ADR-031 п.4).
```

**Стало (предлагается):**

```
   - **Домен** — решающая мера: `ppl` на наборе `domain_eval_v3` (200 док, sha256 `a0b35f3f…`),
     отношение к базе **13.559193** < 1 = домен выучен (ADR-044 п.1/п.6; правило чтения — ADR-031 п.4).
     **Калибровочная шкала монитора (`DOMAIN_ratio ≈ 0.348`) решающей не является** — это
     контроль тренда по своей калибровке, а не доменное отношение на v3; число из монитора
     в критерий 3 не подставлять (ADR-044 п.1: исторические шкалы v1/v2 с решающей роли сняты).
```

### 1.3 `S4-PROTOCOL.md` §5 (строки 59–81): носители базовых констант

Пример JSON (строки 64–77) содержит константы `7.504686` / `15.009373` / `6.159936` / `12.319871` / `13.559193`, но **не называет, откуда они**. Предлагается добавить к §5 абзац (после строки 60, перед примером):

```
**Носители базовых констант** (читаются сами артефакты, а не их описание):

| Компонента | База / потолок | Артефакт-носитель | Набор (sha256) |
|---|---|---|---|
| K1 (`general_eval_v3`) | 7.504686 / 15.009373 | `evidence/s3q-baseline-v3.json` | `general_eval_v3.txt` — `6fa8e00f…` |
| K2 (`general_eval_k2`) | 6.159936 / 12.319871 | `evidence/s3t-baseline-k2.json` | `general_eval_k2.txt` — `723daeaf…` |
| домен v3 | 13.559193 | `runs/s3ao-domain-v3-20260919/ppl_cpt_final.json` (+ сводка `evidence/s3ao-domain-v3.json`) | `domain_eval_v3.txt` — `a0b35f3f…` |

База домена — состояние `base` в том же приборе, что дал замер SFT-финала
(`ppl_sft_fresh.json` того же прогона): числа переносятся как свойства набора, а не как
замеры стенда.
```

И в текст под примером (строка 80–81) добавить: `limits` обязан нести имя носителя и версию набора, по которому считались K1/K2/домен.

## 2. Что это затрагивает в `result-report.schema.json`

Схема (`docs/specs/result-report.schema.json`) уже запрещает лишние поля (`additionalProperties: false`), поэтому адресация в ней выражается **теми же** полями — важно, что их значения берутся по носителю:

| Поле схемы | Строки схемы | Что затрагивает |
|---|---|---|
| `generation.k1.ppl` / `.baseline` / `.ceiling` | 9–19, 30, 52–61 | замер K1 обязан быть с набора v3 (sha `6fa8e00f…`) и сверен с носителем `evidence/s3q-baseline-v3.json` |
| `generation.k2.ppl` / `.baseline` / `.ceiling` | 31, 52–61 | то же для K2 (sha `723daeaf…`, носитель `evidence/s3t-baseline-k2.json`) |
| `generation.domain_v3.ppl` / `.baseline` / `.relation` | 32, 63–72 | `baseline` = 13.559193 из `runs/s3ao-domain-v3-20260919/ppl_cpt_final.json`; `relation` = `ppl/13.559193`, **не** `DOMAIN_ratio` монитора |
| `limits` | 50 | обязана назвать носителя и версию наборов (v3/k2/domain v3) и границу «1 сид» |

**Предлагаемая аддитивная дельта схемы** (отдельным решением, потому что `additionalProperties: false` — это ломающая правка):

- `generation.k1.set_sha256`, `generation.k2.set_sha256`, `generation.domain_v3.set_sha256` — тождество набора доказывается хешем, а не именем;
- `axis.sft_artifact` / `axis.carrier_run` — имя прогона-носителя SFT-базы (ADR-051 п.2);
- `generation.domain_v3.measure_id` (`"domain_eval_v3"`) при необходимости явного контраста с мониторной шкалой.

До принятия дельты эти сведения живут в `limits` строками, чтобы отчёт не терял адрес.

## 3. Риски, если адрес оставить как есть

| # | Риск | Механика |
|---|---|---|
| R1 | **Артефакта нет по объявленному адресу** — тихая дыра вместо находки | `runs/pilot-compact-s42-*/logs/` содержит только `cpt.log`; читатель либо не находит ничего (и «нет данных» выглядит как норма), либо берёт первый подходящий файл |
| R2 | **Класс дефекта ADR-051: «объявлен один вход — прочитан другой»** | Пилот обучался на `v12` при объявленном `v13` (ADR-051); его `judge_mean` — про другую модель. Плюс шаги SFT не совпадают: пилот 67 423 против носителя 66 157 — разные объекты, на одной оси их числа несравнимы |
| R3 | **Подмена шкалы домена** | `DOMAIN_ratio ≈ 0.348` (монитор, калибровочная шкала) и `ppl/13.559193` — разные величины; при чтении по монитору критерий 3 проходит («0.348 < 1») там, где решающая мера не снята. ADR-044 п.1 уже снимал исторические шкалы v1/v2 с решающей роли — здесь та же ошибка под другим именем |
| R4 | **Базовые константы без носителя** | `7.504686` / `6.159936` / `13.559193` в §5 и схеме невозможно проверить: непонятно, к какому набору и какой версии карточки они относятся. При пересборке набора константа молча остаётся старой |
| R5 | **Glob-адрес `pilot-compact-s42-*`** | Маска совпадёт и с будущим каталогом того же шаблона; «где» перестаёт быть однозначным адресом, а `run_manifest.json` — свидетельство **объявленного**, не прочитанного (ADR-051 п.4) |
| R6 | **Отчёт примет не тот объект** | `evidence/result-report.json` (правило C-014) будет построен на числах чужого чекпойнта; вердикт `phase2/stop` окажется решением про другую сущность — и решение владельца (порог SE, фаза 2) примется на ложном основании |

## 4. Границы предложения

- Не меняет `S4-PROTOCOL.md` — это дельта; принятие правки протокола и аддитивной дельты схемы — за архитектором.
- Не трогает пороги, состав критериев и правило C-014 («отчёт только по факту»).
- Не пересчитывает задним числом прошлые прогоны (ADR-051 п.5, §6 S4-протокола).
- Не запускает замеры и не создаёт `evidence/result-report.json` (точка не пройдена: RL не было).

## 5. Как проверяется принятая правка (механика)

1. Адрес в §1 обязан разрешаться в существующий файл: `test -f runs/<носитель>/logs/eval_results_sft.json` или явное `runs/sft-point-chain-<ts>/` — иначе страж краснеет (класс ADR-051).
2. `judge` в артефакте = `GLM-API` (`slug-verifier` — не засчитывается; §1 S4-протокола, `SFT-POINT-CHAIN.md` §6).
3. Шаг/чекпойнт артефакта совпадает с объявленным носителем (sha256, `SFT-POINT-CHAIN.md` §2).
4. Домен: в отчёте стоит `baseline = 13.559193` и `relation` из набора `a0b35f3f…`; `DOMAIN_ratio` монитора в критерии не появляется (grep по отчёту).
5. `limits` называет носителя и версии наборов.
