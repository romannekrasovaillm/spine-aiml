## 3. Механический сторож `tools/check_handoff_contract.py`

Реализован и покрыт тестами (раздел 19 `tools/tests/run_tool_tests.sh`).

- Читает лог прогона (или голый stdout), вырезает stdout-область (между
  `--- stdout ---` и `--- stderr ---`), заново извлекает и валидирует контракт —
  тот же алгоритм, что `parse_result_contract` харнесса (fenced ```` ```json ````-блоки
  с конца + голый JSON-объект в хвосте 4 КБ).
- Три исхода: **valid** (status ∈ complete|partial|blocked), **missing** (нет `"status"`),
  **invalid** (блок есть, но JSON бит или схема нарушена).
- Коды: `0` — все логи с контрактом; `1` — есть лог без/с невалидным контрактом;
  `2` — NOT-VERIFIED (нет входа / файл нечитаем) — «не зелёный», а не «чисто».
- Интерфейс: позиционные пути (с `~` и glob) либо `--log-dir DIR [--glob GLOB] [--latest N]`
  (свежайшие N логов каталога харнесса).

**Валидация верности реимплементации:** прогнан по всем 89 логам — вердикт стража
совпал с вердиктом харнесса в заголовке во **всех 89** (0 расхождений).
Примеры: `hr-43`/`hr-55` → FAIL «контракт не найден», `hr-56` → OK `status=complete`,
`hr-14` → FAIL «status='done' вне complete|partial|blocked».

## 4. Предлагаемый текст правила C-021 (для CONSTRAINTS.yaml — НЕ внесено)

```yaml
  - id: C-021
    name: "AD-12/ADR-023: последний прогон харнесса несёт JSON-контракт результата (status ∈ complete|partial|blocked) — «код 0 без результата» ловится механически"
    type: command_succeeds
    command: "python3 tools/check_handoff_contract.py --log-dir \"${LAGUNA_HARNESS_LOGS:-$HOME/.arch-ml/reports/harness}\" --glob 'hr-*.log' --latest 1"
    severity: critical
    scope: case
    kind: behavioural
    evidence: "tools/check_handoff_contract.py → exit 0; свежайший hr-*.log несёт валидный контракт. Класс дефекта: фоновое ожидание без контракта (hr-43, hr-55; 9/31 прогонов сессии 16.09 без контракта)"
```

Замечания для архитектора (поэтому правило *не* внесено сразу):

1. **Какие логи смотреть.** `--latest 1` — минимальная форма «последняя дельта с контрактом».
   Альтернативы: `--latest 30` (окно ADR-023 «30 последних») — жёстче, но на
   общем каталоге харнесса заденет и чужие кейсы; явный путь к логу конкретной
   дельты — точнее всего, но требует подстановки на каждую приёмку. Выбор окна —
   решение архитектора.
2. **Общий каталог.** `~/.arch-ml/reports/harness/` — общий для всех контуров
   (не только laguna-compact). Правило уровня кейса, проверяющее общий каталог,
   будет краснеть и по чужим дельтам. Если нужна изоляция — фильтр по дельте
   (префикс/тег в логе) или отдельный каталог логов кейса.
3. **Путь.** Использован `$LAGUNA_HARNESS_LOGS` с фолбэком на `$HOME/.arch-ml/…` —
   без жёсткого `/home/user` (конвенция «никаких персональных путей»). См. прецедент C-008 (`LAGUNA_TOK_CACHE`).
4. **C-020 свободен.** Следующий свободный id после C-019 — C-020; в постановке
   заказан C-021. Оставлен C-021 как заказано; при желании перенумеровать — это правка одной строки.

Правило **совместимо с AD-10 / C-019** (гейт ссылается только на `tools/check_*`, не на раннеры).

## 5. Предлагаемый текст напоминания в TASK.md (НЕ внесено)

Добавить в `render_task_md` после «## Контракт результата» (перед чеклистом):

```markdown
## Долгие процессы: не уходи в фон без контракта

- Доведи работу до конца **в этом же прогоне**: если запустил сборку/прогон —
  дождись завершения опросом (`ps`, лог, `test -f`), а не фразой «ответ пришлёт watcher».
  Не влезает в бюджет — уменьши объём дельты, а не откладывай.
- Исключение — автономный прогон на стенде: вернуть управление можно, но обязательно
  подтверди старт и оставь идентификаторы (tmux-сессия, контейнер, шаги, манифест
  стадии) — чтобы следующая дельта продолжила, а не выясняла состояние заново.
- Завершение прогона без JSON-контракта = статус `blocked`, дельта возвращается.
```
