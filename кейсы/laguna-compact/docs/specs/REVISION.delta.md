## 1. Что делаем

Ревизия существующей лесенки CPT → SFT → Agentic-RL на компактном семействе ≤1B:
тот же домен (концепты ML/AI), те же метрики (`judge_mean`, `slug_accuracy`),
узкий протокол. Цель ревизии — не «новый рекорд», а **доказуемый и
воспроизводимый результат без известных дефектов контура**.

## 1a. Версионирование контура (факт, зафиксирован 14.09.2026)

Версия **прогона** и версия **кода** в контуре расходятся, и это не ошибка
нумерации, а сложившаяся практика:

| Сущность | Файл | sha256 (префикс) |
|---|---|---|
| Пайплайн (последний существующий) | `laguna_pipeline_v8.py` | `8fe7ac7b…` |
| Раннер прогона v12 | `run_v12_ladder.sh` | `3447b203…` |
| Корпус | `cpt_corpus_v12r` (9776×8192, домен 75% / replay 25%) | см. `data/corpus-card.json` |

Пайплайнов `v9…v12` **не существует** (проверено: `ls laguna_pipeline*.py`
даёт максимум v8, сен 10). «Прогон v12» = раннер `run_v12_ladder.sh` +
пайплайн `v8` + корпус `v12r`; раннер сам указывает на пайплайн
(`run_v12_ladder.sh:11`). Копии пайплайна и раннера на этой машине и на GB10
идентичны по sha256 — сетевой диск действительно единый источник.

Следствие для артефактов ревизии: в манифестах и отчётах указываются **обе**
версии (`pipeline_version` и `run_version`, AD-2); формулировка «запускаем v12»
без указания пайплайна запрещена — она неоднозначна.

## 2. Границы

**Входит:**
- стадии CPT → SFT → RL, полный цикл по 3 сида (решение R3, 14.09.2026);
- целевое семейство ≤1B, 3 сида;
- инструменты стражей (walking skeleton) и манифесты прогонов;
- карточка корпуса, механический аудит утечек eval.

**Не входит (Deferred, см. спайн):**
- лесенка 12 моделей × 5 сидов, сравнение семейств и размеров;
- собственная архитектура и претрейн с нуля;
- квантизация и инференс-оптимизация;
- изменение домена и метрик (ось наследуется без смягчения).

1. **Порог памяти ADR-007 (30 ГБ) оказался ниже фактической потребности.**

2. **Собственный `tok/s` пайплайна включает eval.** `laguna_pipeline_v8.py:760,778`
   считает `(step+1)*batch_tokens/(time-t0)` при `t0` перед циклом, то есть с
   GEN-EVAL и probes в знаменателе; для смоука GEN-EVAL дёшев (~11 с на 4 прогона),
   и число почти совпало с замером обвязки (3189 против исторических 3325 для той
   же модели и конфигурации). Сравнивать конфигурации по этому числу нельзя —
   `tok/s` в evidence считается по интервалам между обучающими forward'ами.

Четыре замера, которые меняют чтение решений:

1. **Порог памяти ADR-010 п.4 (≥40 ГБ) откалиброван впритык и ниже фактического
   прироста.** Старт — 79.4 ГБ свободных, но за стадию занятая память выросла на
   **+42.78 ГБ** (38.99 → 81.77), и свободная опускалась до **39.92 ГБ** — один сэмпл
   из 1787 ниже порога. То есть старт ровно с 40 ГБ на этой конфигурации упёрся бы в
   unified-память; запас ADR-008 п.2 («~15 % к измеренному приросту») дал бы ≈49 ГБ.
   Это та же калибровка, что S2 сделал для SFT (30 → 50 ГБ): RL-стадия под правило
   запаса не подведена. **Возврат открытым вопросом — ADR не правится в этой дельте.**
2. **Энтропия политики вышла из коридора сверху, а не снизу.** ADR-008 п.3 задаёт
   `1.0–2.0` как здоровую полосу (мониторинг mode collapse). Измерено 2.17 в среднем,
   **91 шаг из 100 выше 2.0**, ни одного ниже 1.0, до пола 0.5 — далеко. Стоп-условие
   ADR-010 п.5 (энтропия < 0.5 два шага подряд) не срабатывало ни разу. Угрозы
   коллапса нет; вопрос обратный — считать ли выход сверху отклонением.
3. **Признак «упор в потолок хода» считается по величине, которая не является числом
   токенов ассистента.** `n_assistant_tokens = len(tokenizer.encode(responses[g]))`
   включает prefill и **текст `<tool_response>`** (`laguna_pipeline_v8.py:1261,1283-1284`),
   поэтому систематически завышен (наблюдаемый максимум 4623 при потолке вызова 4096) и
   даёт **верхнюю границу** доли: 709 из 800 (88.6 %) против 69 из 800 (8.6 %) у
   исторического прогона. Точная проверка — по `gen_tokens` обвязки
   (`outputs[].token_ids`): **3997.8 токена на траекторию против потолка 4096 = 97.6 %**,
   то есть генерация действительно идёт до потолка. Цифра «92/96» (≈96 %) из
   промежуточного среза по финальным артефактам **не воспроизводится**; финальное
   значение — 709/800.
4. **Накладные расходы измерения названы явно.** `t_probe` (пробы пайплайна
   `run_probes`, `laguna_pipeline_v8.py:1547`) — **14.975 с однократно = 0.119 % стены
   стадии**, не на шаг: пайплайн зовёт пробы один раз после цикла шагов, и в разбивку
   закрытых шагов они не попадают вовсе (там 0.0 с). Инструментация обвязки —
   ≈0.04 с за прогон (оценка сверху: 3953 перехваченных вызова × 10 мкс). Деление
   `t_probe` на хвостовой блок («≈10–12 % шага») описывает хвост, а не шаг — у
   незакрытого блока нет следующего старта, по которому он стал бы шагом. Удешевлять
   нечего; цифра названа, решение — за владельцем.

**Экстраполяция — двумя границами, без усреднения.** 500 шагов: **12.27 ч** (прямой
замер 500 шагов той же конфигурации из лога `v12_qwen25-05b_s42`: 88.1 с/шаг, тренд
первая/вторая половина −2.9 %) — нижняя; **17.26 ч** (экстраполяция от 123.87 с/шаг +
186.19 с старта) — верхняя. **Три сида: 36.8–51.66 ч (1.53–2.15 суток).** Оговорка
обязательна: верхняя граница получена на политике, которая договаривает ход до потолка
(88.6 % против 8.6 % у исторического прогона при длине ответа ×2.55) — политика,
завершающая ход раньше, стоит дешевле. С календарём ADR-008 (CPT+SFT ≈8.5 суток на три
сида) полный цикл ≈ **10.0–10.7 суток**; eval-стадия в обе величины не входит.

Гейт: `fitness_check` — **единственное красное C-014** (отчёт результата, ждёт S4);
тесты инструментов — **151 проверка, PASS=151**. Стенд после прогона: контейнер
разведки закрыт, `llm-platform-*` живы (4), свободно 78.1 ГБ.

Проба данных: два манифеста прогона дают **разные** sha256 одного и того же пула
(`run_manifest.json` — `06b95b2f…`, `pipeline_run_manifest.json` — `7ba116ae…`).
Это не расхождение данных, а две разные методики под одним именем: манифест AD-2
хеширует файл целиком, пайплайн — только **первые 1 МиБ** (`_sha256_head`,
`laguna_pipeline_v8.py:1754-1758`, «lineage датасетов»), и в его манифесте это нигде
не сказано. Проверено: sha256 первых 1 МиБ = `7ba116ae…`, sha256 файла целиком =
`06b95b2f…`, оба — про один и тот же `/home/user/gb10-shared/datasets/rl_tasks_revpool_v1.jsonl`
(симлинки `datasets/rl_tasks_revpool_v1.jsonl` и `runs/rev-pool/rl_pool_filtered.jsonl`
ведут туда же). **Прогон действительно шёл по пулу ревизии**; но сверка манифестов
без этой оговорки выглядит как подмена датасета — стоит назвать методику в AD-2.

**S3 — прогон ревизии. Фаза 1: пилот (ADR-013), затем точка решения.**
**Статус 15.09.2026: CPT исполнен, SFT идёт.**
CPT: 9776 шагов, **6.7 ч** (прогноз ADR-008 — 7.0 ч, точность 4 %), финальный loss 1.4949,
`ppl_domain` 6.8–7.1 (лучше базовой модели на ~41 %), `ppl_general` 151–165 (+18…29 % к базе).
Переход CPT→SFT: ≈4 с, страж прошёл (78.3 ГБ при пороге 50), входной чекпойнт загружен
явной строкой (`Loaded CPT ckpt`) — риски R1/R3 ADR-016 сняты фактом.
SFT: 3.10 с/шаг, остаток ≈53 ч, прогноз финиша ≈2026-09-17 07:00Z; `ppl_general` 101.9
(ниже базовой модели), `ppl_domain` 4.7.
Пилот идёт **в обычном режиме контура** (ADR-014: детерминированный режим применяется
к пробам-доказательствам, а не к полному циклу — цена +79…85 %, смысла платить её
на 3.5 суток нет). A5-drift выполняется отдельной 20–50-шаговой детерминированной
пробой (сверка пошаговых loss и sha256 чекпойнтов).
Пилот: **один сид (42), полный цикл** — CPT 9776 шагов (≈7 ч) → SFT 3 эпохи
(≈61 ч) → RL 500 шагов (12.3 … 17.3 ч) → eval (192 задачи) + `eval_results_sft.json`
на том же SFT-чекпойнте; SFT-данные — замороженный `sft_train_v12` (замкнутый цикл
синтеза — отдельной дельтой после подтверждения направления). Итого ≈3.5 суток.
Точка решения (ADR-013 п.3): направление оси (RL > SFT на этом сиде), отсутствие
дегенерации, общий язык без роста PPL > 15 %, полнота доказательств. Положительно —
**фаза 2**: ещё два сида (≈7 суток) и полная ось AD-1 со статистикой; отрицательно —
стоп с формулировкой «эффект на одном сиде не обнаружен».
Перед стадиями (ADR-006, ADR-009, ADR-010, ADR-012):
- **RL-разведка (ADR-010) — первый шаг S3, до полного протокола**: 50–100 шагов RL
  с одного сида на существующем `sft_checkpoint_final.pt` (2.8 ГБ, 30.07),
  пул — `rl_pool_filtered` (27 992 задачи, положен на `gb10-shared` по ADR-4).
  Замеряется: время шага, доля роллаутов, пик памяти, число ресников, энтропия
  политики (коридор 1.0–2.0 применим здесь), pass_rate/reward как фон →
  `evidence/s3-rl-probe.json`. Сходимость — не критерий: цель — цена шага.
  **Выполнено отдельной стадией S3-pre 14.09.2026 (см. выше);** выбор протокола
  A/B/C по цене шага остаётся за владельцем — это отдельное решение, не эта дельта;
- **детерминизм-проба** (ADR-009): два прогона CPT по 20 шагов с одним сидом в
  детерминированном режиме (`torch.use_deterministic_algorithms(True)`,
  `CUBLAS_WORKSPACE_CONFIG=:4096:8`), замер расхождения loss и хешей чекпойнтов,
  цена во времени → `evidence/s3-determinism.json`. Исход пробы определяет
  формулировку A5-drift;
- **порог памяти по стадии** (ADR-008, ADR-011): CPT ≥35 ГБ, SFT ≥50 ГБ, RL ≥49 ГБ
  свободной unified-памяти на старте стадии;
- **RL-пул калибруется по полосе pass-rate** (не берётся как есть): задачи с
  pass-rate у пола и у потолка отсеиваются, перекос `multi_hop_search`
  (7/1507) снимается или фиксируется явно (`verifiable-rl-recipes`);
- **SFT-данные ревизии собираются замкнутым циклом** generate → verify →
  refine вместо конкатенации без фильтра (`closed-loop-tool-traj-synthesis`;
  известный факт: `build_sft_v12.sh:17` — чистая конкатенация);
- **план Б при вырожденной награде** (симптом `0 passed / 4 failed`,
  `reward_mean 0.0`): closed-form шаговый кредит из механических per-gate
  вердиктов, а не LLM-судья (`rubric-credit-long-horizon-rl`). Переход на план
  Б — решение архитектора по факту первых N шагов RL, фиксируется в отчёте.

Выход: `runs/rev-<model>-s{seed}/` с манифестами.

**S3d — финализация пилота и дефекты отчётности** (после завершения ≈3.5 суток):
снять со стенда артефакты стадий в `runs/pilot-compact-s42-*/`, собрать
`evidence/s3-result.json` (точка решения ADR-013 п.3 + чек-пойнты ADR-015), исправить
три дефекта отчётности раннера, найденные прогоном: (а) `status=launched` при уже
мёртвой tmux-сессии → отдельный статус `stage_failed`; (б) при резюме
`var/status/<стадия>` и манифест несут статус прошлой попытки (`failed` для идущей
стадии) → сбрасывать в `running` при старте; (в) метка `stage` в evidence следует
стадии дельты, а не метке раннера (S3b → S3c).
Дополнительно (найдено мониторингом, ADR-015): **починить прибор GEN-EVAL** —
`base` снимать на модели до первого шага (сейчас base = первый успешный вызов
на шаге 50, `pipeline:1589-1590`), а наборы `domain_eval.txt` (5 документов!) и
`general_eval.txt` (24) расширить до объёмов, при которых разброс прибора не
превышает измеряемый эффект. Без этого флаг FORGETTING не различает состояния,
а решения ADR-015 стоят на шуме.
Дополнительно (ADR-016, разбор цепочки перед переходом CPT→SFT): починить шесть
дефектов цепочки и стража — (R1) страж проверяет память **сразу** после выхода
предыдущей стадии, без ожидания освобождения unified-памяти; (R2) файлы стенда
(`stages.tsv`, `pilot_chain.sh`) перезаписываются in-place под живым читателем —
писать рядом и переключать атомарно; (R3) пайплайн молча учится **с базовых весов**,
если входной чекпойнт отсутствует (`pipeline:806`, `if exists()` без `else`) —
добавить явный отказ; (R4) `CHAIN_PID_FILE` не удаляется → ложный отказ при
переиспользовании pid; (R5) `--check-only` не проверяет GLM-ключ и входные
чекпойнты для eval; (R6) статус стадии не сбрасывается в `running` при старте и
может остаться `failed` от прошлой попытки.
**Ограничение по времени правки (важно):** `laguna_pipeline_v8.py` читается
**на старте каждой стадии** — новый контейнер берёт текущую версию файла. Поэтому
правка прибора **недопустима, пока пилот не завершён**: изменение методики GEN-EVAL
в середине прогона сделает SFT/RL-стадии несопоставимыми с CPT-стадией того же
пилота. Порядок: сначала пилот целиком, потом правка прибора, потом фаза 2 (если
она состоится) — уже с исправленным замером.

**S4 — отчёт результата.**
`evidence/result-report.json`: ось (AD-1), `judge_mean`/`slug_accuracy`
mean ± std, min/max по сидам, **k-из-k** (доля задач, решённых во всех трёх
сидах) отдельно от per-run, **явное число попыток n**, анти-метрики
(`entropy`, `clip_frac`, `kl`), явное указание, какие выводы протокол **не**
покрывает (в т.ч.: pass@k не экстраполируется за пределы n;
`consistency-gap` и `passk-identifiability`).

## 5. Критерии приёмки (A4 — conformance evidence)

1. Все стражи `CONSTRAINTS.yaml` зелёные либо явно помечены «ждёт S<k>».
2. На каждый прогон есть `run_manifest.json` с хешами данных, базы, пайплайна,
   образа и сидом (AD-2).
3. Eval-набор прошёл аудит утечек; отчёт аудита в evidence (AD-7).
4. Смоук-прогон сходится: loss убывает; для CPT/SFT действует порог дегенерации
   (энтропия не падает к < 0.5), а коридор `1.0–2.0` применяется **только** к
   энтропии политики RL (ADR-008 п.3) — к токенной энтропии ЯМ он не относится;
   нет OOM/NVRM-инцидентов, не превышен бюджет шага.
5. Отчёт S4 содержит ось, статистику по сидам и анти-метрики.
6. Данные и веса подключены симлинками; в дереве кейса нет копий > 50 МБ.

## 6. Стоп-условия (kill criteria)

- `entropy < 0.5` два шага подряд на смоуке при `kl_coef=0.01` → остановка,
  разбор политики (рецепт `kl_coef ×1.5` из контура — только через ADR-дельта).
- Аудит утечек находит > 5% задач eval → стоп S1, пересборка eval-набора,
  фиксация в отчёте; прогон по «подчищенному» набору без решения — запрещён.
- NVRM 0x51 storm дважды за прогон → пауза, `storm_gap.sh`, проверка
  `GPU memory utilization` per-size; третий инцидент — эскалация владельцу.
- Расхождение «reward растёт, `judge_mean` падает» на RL-стадии → остановка
  как сигнал reward hacking (AD-6).

## 7. План отката

- Якорь: baseline-коммит кейса (все артефакты — в git `spine-aiml`).
  Откат документации и конфигов — `git revert`/возврат на baseline.
- Чекпойнты и логи прогонов **не удаляются** при откате решений: они остаются
  доказательной базой в `~/gb10-shared/checkpoints` и `runs/`.
- Освобождение ресурса: при остановке S2/S3 — завершение стадии до
  чекпойнта (идемпотентные раннеры контура), затем `mem_hygiene.sh`.
- Откат выбора базы (R1) после старта S2 — costly: сравнение с прошлыми
  прогонами теряется, требуется новый манифест и новый смоук (см. ADR-001,
  Reversibility).
