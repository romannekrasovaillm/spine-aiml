# ADR-023. Практика handoff

- Date: 2026-09-16
- Status: **Accepted** (решение владельца после разбора трёх инцидентов)

## Context

> **Уточнение 16.09.2026 (инцидент `hr-39`, тишина 2400 с).** Прогон был прерван по таймауту
> тишины (40 минут без вывода и без изменений файлов), но **запущенный исполнителем процесс
> остался жив**: `nohup … python tools/passrate_probe.py … &` продолжал работать и занимать
> GPU **54 минуты** после прерывания. Инструмент сообщил «сирот нет» — и это верно только
> для дочерних процессов группы: **`nohup`-детачи выживают**.
>
> Следствия, которые вводятся этим уточнением:
> 1. **После любого прерывания проверять процессы пробы руками** (`ps`): «сирот нет» в отчёте
>    инструмента не означает, что работа остановлена.
> 2. **Длинная проба обязана писать прогресс инкрементально** (дописывать JSONL каждые N задач):
>    тогда таймаут тишины не срабатывает — файлы меняются, — и прерывание не теряет работу.
>    Проба без промежуточной записи на часы работы — это дельта, спроектированная неверно.
> 3. **Объём пробы согласуется с окном молчания** (по умолчанию 10 минут): либо объём меньше,
>    либо запись прогресса чаще. «200 задач на тип» без инкрементальной записи — прямое
>    нарушение правила размера дельты (п.4 Decision).

Разбор показал три класса сбоев, которые нельзя смешивать, потому что лечатся они по-разному.
Статистика по 30 последним прогонам кодовых харнессов:

| Класс | Число | Причина | Лечение |
|---|---|---|---|
| Отказ инфраструктуры | **3** | `502 Upstream request failed: Temporary failure in name resolution` — шлюз к модели | проверка шлюза + перезапуск (уже применяется) |
| Отчёт без JSON-контракта | **8** | исполнитель не выдал машиночитаемый статус | требование в TASK + пометка «отчёт неполный» |
| «Код 0 без результата» | минимум 2 | работа отложена или не зафиксирована | **этот ADR** |

**Живые случаи, на которых видно суть:**

1. **Запуск пилота.** Отчёт гласил «выполнено», а в git не было ни коммитов, ни созданных
   файлов — работа фактически не состоялась. Обнаружено проверкой `git log`/`status`, а не чтением отчёта.
2. **S3j (baseline pass-rate, `hr-33`).** Харнесс завершился с **кодом 0**, скрипт создан (45 КБ),
   манифест создан — но **evidence с результатами отсутствует**, процессов не осталось,
   GPU свободна. Дословная причина в отчёте: «дальше не опрашиваю: фоновые ожидания пришлют
   уведомление» — то есть исполнитель **отложил** работу и закрыл прогон, оформив это как нормальный ход.
3. **Таймаут по абсолютному лимиту** (ранние дельты): задача «подготовить и запустить цепочку
   стадий» не влезала в час; после сужения до «только запустить» прошла.

**Ключевой вывод: код возврата харнесса ничего не доказывает.** Ненулевой сигнализирует о сбое,
нулевой **не подтверждает** результат. Доказательство — только артефакты, git и прогон гейта.

**Признанная часть ответственности архитектора** (моя): в пакетах не было требования
«довести до конца или уменьшить объём»; не был задан признак завершённости (evidence + коммит + гейт);
размер дельты не сверялся с бюджетом до запуска; отсутствие JSON-контракта не имело последствий.

## Decision

1. **Чек-лист завершённости в каждом TASK** — дельта принимается только при **всех четырёх** пунктах:
   (а) заявленные артефакты существуют; (б) есть **финальный git-коммит**; (в) гейт и тесты прогнаны
   с результатом; (г) отчёт несёт JSON-контракт (`complete | partial | blocked`).
   Не выполнен любой — статус **`blocked`**, а не `complete`, и дельта возвращается.
2. **Код возврата не является доказательством.** Приёмка идёт по `git log`/`git status`,
   содержимому артефактов и результату гейта. Строка «выполнено» в отчёте — не основание.
3. **Запрет фоновых ожиданий по умолчанию.** Исключение — автономные прогоны на стенде
   (там правильно «вернуть управление, не ожидая»), но с обязательным подтверждением старта
   и идентификаторами: tmux-сессия, контейнер, шаги, манифест стадии.
4. **Размер дельты проверяется до запуска.** Если объём не влезает в бюджет прогона —
   дельта разбивается или сокращается, и это фиксируется **до** старта. Внутри TASK допускается
   «уменьшить выборку, но закончить с результатом» (так закрыт S3j).
5. **Отчёт без контракта — неполный, но не отбрасывается.** Машинная приёмка невозможна,
   содержательная часть читается человеком; в журнале это помечается как дефект формата,
   чтобы не путать с содержательным результатом.
6. **Практика handoff обновлена в части контекста:** в `spec` включаются
   `ARCHITECTURE-SPINE.md` и `CONSTRAINTS.yaml` (не только профильные ADR), а в TASK —
   раздел «инварианты, релевантные дельте», в том числе **инварианты без механического стража**
   (пример: AD-11 «кредит бинарный» с `PENDING-EVIDENCE`). До этого такой инвариант доходил
   до задания только потому, что архитектор вписывал запрет руками.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Чек-лист + запрет фона + контроль размера** (принято) | Класс «зелёный без результата» закрыт; приёмка обоснована; дельты дробятся там, где нужно | TASK удлиняется; число прогонов растёт (дельта мельче); «код 0» перестаёт быть сигналом → больше ручной проверки |
| **B. Полагаться на текстовый отчёт исполнителя** | Ноль работы | 8 из 30 без контракта; «выполнено» при отсутствии файлов — уже случалось |
| **C. Увеличить таймауты прогонов** | Проще | Не лечит «отложил в фон»: проблема не во времени, а в критерии завершённости |
| **D. Автоматический перезапуск при «code 0 без артефактов»** | Меньше ручной работы | Скрывает причину; перезапуск при «отложил» повторит то же поведение, а стоило бы вернуть дельту с диагнозом |

## Consequences

### Positive

- Класс «зелёный без результата» получает правило: нет артефактов и коммита — нет приёмки.
- Дельты дробятся до размера, который реально доводится до конца в одном прогоне.
- Инварианты без стражей (AD-11 и подобные) попадают в задание механически, а не по памяти архитектора.

### Negative

- **Число прогонов растёт**: мелкая дельта — меньше работы за прогон, но больше накладных (пакет, гейт, приёмка).
- **Приёмка дороже по вниманию**: проверять git и артефакты каждый раз — это осознанная плата за отказ доверять коду возврата.
- **Часть «нулевых» прогонов — нормальна** (автономные на стенде возвращают управление с промежуточным статусом), и это приходится различать вручную: правило не может быть абсолютным.
- **Формальные требования не гарантируют содержания**: исполнитель может выполнить чек-лист, но сделать не то — от этого защищает только предметная постановка задачи, а не список пунктов.

## Reversibility

**reversible.** Практика — правила в TASK и ADR; уже выполненные дельты не пересматриваются.
Единственное необратимое — потраченное время прогонов, которые завершились без результата
(минимально два; плюс 12 ч остановленного пилота по отдельному решению).
