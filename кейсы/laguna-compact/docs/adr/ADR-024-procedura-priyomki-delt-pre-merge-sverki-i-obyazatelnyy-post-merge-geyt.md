# ADR-024. Процедура приёмки дельт

- Date: 2026-09-16
- Status: Proposed
- Основание: разбор процедуры гейтов (документ «Гейты в контуре кодовых харнессов», ДКА) — целевая процедура TO-BE, три новые обязательные проверки

## Context

Сейчас гарантированно работает **одна** точка контроля — гейт в ветке перед приёмкой. Всё остальное держится на дисциплине архитектора: в практике этой сессии было **два конфликта при мерже** (`tools/tests/run_tool_tests.sh`, `tools/README.md`), которые я разрешал вручную и **после разрешения гейт не прогонял**; приёмка **отклонялась** из-за перезаписи исторического `evidence/s1-data-audit.json`; гейт в ветке проверял **копию** `CONSTRAINTS.yaml`, которая может быть старее, чем в `main`.

**Пять пробелов (из разбора, с отметкой подтверждения):**

| № | Пробел | Подтверждён |
|---|---|---|
| П1 | гейт не проверяется на шаге мержа | да |
| П2 | разрешение конфликта не проверяется | да (два конфликта разрешены без гейта) |
| П3 | редакция правил в ветке может расходиться с `main` | потенциально |
| П4 | нет post-merge проверки по умолчанию | да |
| П5 | нет проверки, что `evidence` завершённых стадий не переписаны | да (случай был, откатил вручную) |

Ключевое: **мерж — единственная операция, меняющая `main`, и её результат никем не проверяется**, при стоимости проверки в секунды (19 правил ≈ 3 с).

## Decision

**Процедура приёмки становится шестишаговой; шаги 2, 5, 6 — новые обязательные.**

1. **До приёмки (в ветке):** гейт + тесты + наличие заявленных артефактов + `git log`/`git status`.
   (Без изменений — это делалось.)
2. **Сверка редакции правил (новое):** `sha256` файла `CONSTRAINTS.yaml` в ветке против `main`. Расхождение → сначала синхронизировать (`merge main` в ветку), **затем** проверять; иначе гейт зелёный по устаревшей редакции. Закрывает **П3**.
3. **Проверка чистоты дерева (усилено):** незакоммиченных изменений нет; изменения **исторических `evidence/*`** завершённых стадий обнаруживаются и выводятся **предупреждением** — инструмент **не мутирует рабочее дерево** и не откатывает их сам; решение об откате принимает владелец (ADR-024 п.5: красное состояние не откатывается автоматически). Закрывает **П5** (в AS-IS проверялось только «незакоммиченное»).
4. **Мерж** (`accept`).
5. **Post-merge гейт обязателен (новое):** сразу после мержа прогон гейта на `main`; красное — немедленный разбор, а не «запишем в долг». Закрывает **П1, П4**.
6. **Проверка после конфликта (новое):** если мерж был с конфликтом, после ручного разрешения — **повторный прогон гейта и тестов**. Закрывает **П2**.

**Автоматизация — в инструменте приёмки, а не в кейсе** (иначе работает только там, где архитектор помнит чек-лист):
- `accept` после merge сам прогоняет `fitness_check` и печатает вердикт; при красном — не откатывает мерж, но помечает приёмку как `CONSTRAINTS-FAILED` и требует решения владельца;
- в отчёт приёмки добавляются `sha256` правил из ветки и из `main` (П3);
- предупреждение, если в ветке изменены файлы `evidence/*` (П5).
Эти три доработки — **дельты платформы** (Rust-инструмент `arch-ml`), оформляются отдельными пакетами; в этом ADR фиксируется требование, а не реализация.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Шестишаговая процедура + автоматизация в инструменте** (принято) | Закрывает все пять пробелов; цена проверки — секунды; работает для всех дельт, а не только при моей памяти | Требует правки платформенного инструмента (отдельные дельты) |
| **B. Оставить как есть (гейт только в ветке)** | Ноль работы | Красное состояние может попасть в `main`; конфликтные разрешения не проверяются; причина ошибки ищется задним числом |
| **C. Гейт только перед мержем (без post-merge)** | Проще | Не закрывает главную дыру: результат мержа (единственного изменения `main`) остаётся непроверенным |
| **D. Запретить конфликты (мелкие дельты, один исполнитель за раз)** | Конфликтов не будет | Параллельность уже даёт экономию; запрет снижает пропускную способность и не отменяет П1/П4/П5 |

## Consequences

### Positive

- `main` перестаёт быть непроверяемым: post-merge гейт ловит расхождение в момент мержа, а не через день.
- Разрешение конфликта перестаёт быть «на честном слове» — повторный прогон после ручной склейки.
- Расхождение редакций правил (П3) видно до приёмки, а не после.

### Negative

- **Шесть шагов вместо трёх — больше времени на приёмку** (секунды на гейт, но плюс сверка хешей и чистоты дерева; при многих дельтах это заметно).
- **Post-merge гейт может показать красное состояние, которое было и до мержа** — тогда нужно понять, чей это долг; без этого шага вопрос просто не возникал.
- **Автоматизация требует правки платформы**: пока она не сделана, шаги 2, 5, 6 остаются ручными и, значит, забываемыми — то есть ADR фиксирует цель, а не гарантию.
- **Дополнительное требование к владельцу**: при красном post-merge гейте решение (откатывать мерж или чинить поверх) принимается человеком, что добавляет точку вмешательства.

## Reversibility

**reversible.** Процедура — правила приёмки; уже принятые ветки не пересматриваются. Автоматизация — отдельные дельты платформы, каждая откатывается независимо. Необратимо только уже потраченное время на разборы инцидентов, которые эта процедура предотвращала бы.
