# Walking skeleton заземлённого RL (ADR-049 пп.1–12)

Пять задач, на которых проверяется **каждое** условие заземления по отдельности —
до массовой сборки пула. Размер выбран сознательно: скелет доказывает механику и
измеряет цену, а не трудность (полоса `p*` из ADR-049 п.12 измеряется на реальных
rollout политики, отдельной дельтой).

| Задача | Инструмент | Действие-цель | Бинарный критерий (по состоянию) |
|---|---|---|---|
| `gs-shell-01` | shell | вычислить сумму столбца `value` из `in/series.csv` → `out/total.txt` | файл существует, одно целое, равно независимому пересчёту по исходным данным |
| `gs-shell-02` | shell | починить `bin/aggregate.sh` | предъявленный скрипт запускается верификатором на **удержанном** наборе: код 0 и верная сумма |
| `gs-fs-01` | файловая система | собрать `app/config/service.json` из трёх источников | строгий JSON, ровно три ключа, значения сверены с исходными файлами |
| `gs-fs-02` | файловая система | разложить `inbox/*` по адресатам из первой строки | дерево в точности равно эталонному, `inbox` пуст, содержимое по sha256 |
| `gs-http-01` | HTTP-мок | получить выборку и отправить принятый отчёт `POST /v1/report` | в журнале **сервера** есть запись `accepted=true`, числа сверены с генератором выборки |

## Четыре условия и чем каждое подтверждается

- **G1 — награда по состоянию.** Верификатор читает артефакт/журнал/дерево и
  пересчитывает эталон сам. Текст ответа агенту недоступен по построению: у
  верификатора нет аргумента с транскриптом. Проба усиливает это эмпирически:
  текстовый ответ пробы `no-action` подставляет **точное ожидаемое значение**
  (`expected_public`), и вердикт от этого не меняется.
- **G2 — no-action = 0.** Проба `--no-action`: ни одного вызова инструментов,
  только состязательный текст. Ожидание — 0 на каждой задаче. Ту же роль играет
  вырожденная проба `--empty-action` (`true`): «действие без последствий» тоже 0.
- **G3 — бинарный внешний верификатор.** Верификатор — отдельный файл набора,
  в контейнер не монтируется, живёт вне песочницы; возвращает строго 0/1; два
  вызова на одном снимке дают один балл; третий вызов с удалённым транскриптом —
  тот же балл. Для `gs-http-01` образец правильный: **журнал ведёт сервер** (мок
  на хосте, файл вне контейнера), агент может писать в `/work` что угодно. Для
  `gs-shell-02` критерий ещё строже: верификатор не читает результат агента, а
  **исполняет** предъявленную программу на удержанном входе — зашитое число и
  подделка артефакта не проходят (приём `execution-grounded-benchmark-gen`).
- **G4 — изоляция и откат.** Контейнер (`docker`, read-only корень,
  непривилегированный пользователь, лимиты памяти и pid), один контейнер на батч
  задач с откатом состояния (ADR-049 п.10). Задача с моком исполняется в **своей
  внутренней сети** (`docker network create --internal`), мок поднят на **её шлюзе**:
  выхода наружу нет, DNS не резолвится, мок — единственный достижимый эндпоинт.
  Это не украшение: на дефолтной `bridge` контейнер достаёт до `http://1.1.1.1/`
  (проба 20.09.2026), то есть награду можно получить внешним вызовом, а не
  состоянием, — и ось ADR-049 перестаёт что-либо значить. Каждая проба изоляции
  названа числом/фактом (`host_paths_hidden`, `rootfs_readonly`, `nonroot`,
  `external_unreachable`, `dns_unresolvable`, `mock_reachable`, `journal_invisible`);
  **выход проверяется попыткой выхода, а не флагом сети** — живой страж
  `tools/check_env_contract.py` (C-028) сам пробует выйти (публичный IP, DNS,
  канарейка на шлюзе дефолтной bridge) и требует, чтобы каждая попытка провалилась.
  Между прогонами состояние возвращается к исходному, следы предыдущей задачи
  проверяются на отсутствие.
- **G4, лимит шагов — из задачи.** `task.json` несёт `max_steps` (схема
  `grounded-task/2`), и исполняет его **среда**: исчерпанный бюджет отказывает в
  действии, не исполняя его, поэтому награда падает через состояние. Внешний
  потолок харнесса (`--max-steps N`) применяется как минимум и не может поднять
  бюджет выше объявленного задачей. Число объявлено с запасом на разведку и правку
  (эталонное действие задачи — один шаг), доказывается пробой `--step-probe`:
  бюджет 0 → награда 0, бюджет 1 → 1.
- **G4, шаг под супервизором.** Измерено пробой 20.09.2026: клиентский таймаут
  `docker exec` процесс внутри контейнера **не убивает** и оставляет частичный след.
  Поэтому среда держит шаг в своей группе процессов, по таймауту снимает её сама
  (`kill -9 -<pgid>`) и откатывает след; проба `--timeout-probe` показывает, что
  убитый шаг не влияет на следующий rollout (та же награда, то же состояние, что
  у чистого прогона).
  Пространства имён в этом окружении недоступны (`bwrap`/`unshare` → `Permission
  denied`), поэтому подтверждён только контейнерный путь.

## Как запускать

```bash
python3 tools/grounded_runner.py --card            # пересобрать карточку набора (AD-2)
python3 tools/grounded_runner.py --run --no-action --empty-action --repeat 2 \
    --step-probe --timeout-probe \
    --out evidence/grounded-skeleton.json          # прогон + доказательство
python3 tools/grounded_runner.py --no-action --json # только проба G2
python3 tools/grounded_runner.py --step-probe      # лимит шагов: бюджет 0 → 0, 1 → 1
python3 tools/grounded_runner.py --timeout-probe   # убитый шаг не влияет на следующий
python3 tools/grounded_runner.py --teardown-probe  # снятие батча: -t 0 против -t 1
python3 tools/check_grounded_pool.py               # страж ADR-049 п.5 (правило C-026)
python3 tools/check_grounded_pool.py --mode pending # состояние PENDING (правило C-027)
python3 tools/check_env_contract.py                # контракт среды: egress/шаги/супервизор (C-028)
```

Контейнеры и сети прогона несут префикс `gs-<метка прогона>` и снимаются по
**точному** префиксу, а не по широкому шаблону: docker и `/tmp` на хосте делят
параллельные дельты. Что осталось — отчёт называет сам (`cleanup`).

Каталог прогона (`--run-dir`) обязан лежать в `$HOME`: docker на этом хосте
(snap-конфайнмент) не видит `/tmp` и молча отдаёт в контейнер пустой каталог
вместо bind-mount. Метка стенда в отчёте (`--stand`) по умолчанию — имя хоста:
цена и пробы изоляции не переносятся между стендами (ADR-049 п.10), и называть
чужую машину в кадре замера нельзя.

`sha256_full` набора покрывает **все содержательные файлы** набора, включая этот
README: любая правка внутри `data/grounded-skeleton/` (кроме `card.json`) делает
доказательство устаревшим, и страж (C-026) это назовёт. Порядок после правки —
`--card`, затем прогон раннера.

Пересобираемые артефакты (`__pycache__/`, `*.pyc`) в каноническую карту **не
входят** (решение архитектора 20.09.2026): байткод производен от исходников, в git
не хранится и появляется от одного импорта на машине, поэтому хеш с ним из чистого
клона не воспроизводится — правило краснело бы по построению (ADR-023 п.12).

**Цепочка идентичностей не затирается** (ADR-028 п.1). При пересборке карточки
прежняя пара уходит в `previous_*`, а более ранняя — в `previous_history`: у цепочки
нет «одного слота», третья пересборка не стирает вторую. Прежнее объявление несёт
**полную каноническую карту** (`previous_files`), а отличия от текущей разложены по
трём классам: `previous_files_excluded` (пересобираемый байткод),
`previous_files_doc_delta` (документы корня набора) и `previous_files_measured_delta`
(измеренные артефакты задач и мока). Страж по этой записи опознаёт доказательство,
записанное до пересборки, как описание **той же** содержательной части набора — но
только пока измеренные артефакты не менялись: изменилась задача — доказательство
устарело и пересобирается (ADR-012), даже если запись честно объявила это классом.
Необъявленное отличие — красное (`card-previous-inconsistent`).

## Схема

`card.json` — карточка набора (AD-2): полный `sha256_full` по канонической карте
`{путь: sha256 файла}` (без усечения), объём, состав, хеши верификаторов, схема
`task.json`. Файлы задачи описаны в `card.json → task_schema`. Кратко:

- `task.json` — `id` (без ожидаемого ответа, ADR-049 п.9), `tool`, `network`,
  **`max_steps`** (лимит шагов задачи: исполняет среда, ADR-049 п.1/G4),
  `prompt`, начальное состояние, действие-цель, критерий, пробы, `seed_dir`,
  `solution` (эталонное действие), `verifier`, `verifier_reads`, `timeout_s`;
- `seed/` — начальное состояние (монтируется в `/work` контейнера);
- `holdout/` — удержанный вход верификатора-ре-execution (в контейнер не попадает);
- `verify.py` — внешний верификатор: `{score: 0|1, reason, expected_public, reads}`;
- `mock/mock_server.py` — HTTP-мок и генератор выборки (журнал ведёт сервер).

## Границы

- Раннер не запускает модель: `--run` — положительный контроль (эталонное
  действие), `--no-action`/`--empty-action` — пробы контура награды. Доля успехов
  скелета ничего не говорит о трудности задач для политики.
- «Шаг» здесь — одно действие среды (один `exec`); эталонное действие задачи —
  один шаг, поэтому бюджет 1 достаточен, а объявленные `max_steps` — потолок для
  агента, а не измеренное число его действий.
- Цена измерена только для среды (контейнер, состояние, действие, верификация);
  рост длины генерации взят из аудита как допущение — см. `cost.assumptions` в
  `evidence/grounded-skeleton.json`.
- Замер сделан на стенде, названном в `host.stand` отчёта; цифры цены и пробы
  изоляции не переносятся на другой стенд без повторного прогона (ADR-049 п.10).
