# Queue-Based Load Leveling + Competing Consumers

**Проблема.** Пики нагрузки (зарплатный день: ×40 к медиане) перегружают сервис и его зависимости; синхронный вызов заставляет клиента ждать и ретраить.

**Решение.** Очередь как буфер: производитель кладёт задачу и получает приёмку (202 Accepted + id), сервис обрабатывает в СВОЁМ темпе. Competing Consumers: N экземпляров потребителя разбирают одну очередь — масштабирование без изменения производителя.

## Железные правила

- Приёмка ≠ выполнение: клиенту — честный асинхронный контракт (статус по событию/опросу; Azure: Asynchronous Request-Reply).
- Потребитель идемпотентен (at-least-once; навык `idempotent-consumer`), ядовитые сообщения → DLQ с алертом и процедурой разбора.
- Backpressure честен: глубина очереди — метрика с порогами; переполнение → отказ на входе (503 + Retry-After), а не молчаливая потеря.
- Заказ сообщений — только там, где нужен (ключ партиции); «вся очередь строго по порядку» убивает конкурентных потребителей.
- Lag (время ожидания в очереди) включён в сквозной NFR платежа (навык `nfr-design`).

## Когда НЕ применять

- Запрос требует немедленного ответа с результатом (авторизация у банкомата) — буфер неуместен, смотри `circuit-breaker-retry` и `bulkhead`.
- Задачи с жёстким realtime-дедлайном: устаревшая задача должна отбрасываться (TTL сообщения), иначе обрабатываем мусор.

## Композиция (Azure)

Queue-Based Load Leveling + Competing Consumers = буфер + масштаб обработки; + Priority Queue, если платежи зарплатного реестра важнее фоновых выписок.
