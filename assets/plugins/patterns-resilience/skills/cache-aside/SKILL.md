# Cache-Aside

**Проблема.** Частые чтения бьют в медленное/дорогое хранилище; данные меняются редко относительно чтений.

**Решение.** Читающий код: (1) ищет в кэше; (2) промах — читает хранилище, кладёт в кэш с TTL, возвращает. Записи идут в хранилище напрямую + инвалидация кэша.

## Железные правила

- TTL обязателен и осмыслен (справочник валют — часы; лимиты клиента — секунды/минуты; баланс для платежа — НЕ кэшируется никогда).
- Инвалидация при записи: запись в БД → invalidate (или event-driven инвалидация через шину). «Протухание по TTL» как единственный механизм — только для некритичных данных.
- Stampede-защита: при промахе один запрос идёт в БД, остальные ждут (single-flight) или stale-while-revalidate.
- Кэш — не источник истины: потеря кэша (flush) не ломает корректность, только latency.
- Персданные в кэше: шифрование, TTL, контур размещения (data locality) — согласовано с безопасностью.

## Когда НЕ кэшировать

- Данные, где устаревшая копия — финансовый риск (баланс списания, курс сделки) — strong read у владельца.
- Данные с соотношением чтение:запись ~1:1 — кэш только добавит сложности.

## Чек-лист

- [ ] Hit rate измеряется (кэш с hit rate 5% — мёртвый груз)
- [ ] TTL + стратегия инвалидации задокументированы (в ADR)
- [ ] Stampede-защита на тяжёлых ключах
- [ ] Тест: запись → чтение не возвращает старое (в рамках задокументированного окна)
- [ ] Персданные/ПДн — отдельное решение с безопасностью
