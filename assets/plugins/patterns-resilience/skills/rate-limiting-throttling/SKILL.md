# Rate Limiting / Throttling

**Проблема.** Потребление ресурса вне контроля: один агрессивный клиент/партнёр забирает capacity всех; пиковые волны; злоупотребления.

**Решение.** Контроль потребления на границе: лимиты (RPS/единицу времени, конкурентные вызовы, объём) по измерениям — tenant, клиент, операция.

## Приёмы

- **Token bucket / leaky bucket**: RPS + всплеск (burst) явно; sliding window для точности.
- **Измерения лимитов**: per-client, per-tenant, per-operation (дорогие операции — отдельный лимит), системный потолок.
- **Честный отказ**: `429 Too Many Requests` + `Retry-After`; для критичных партнёров — Priority Queue вместо отказа.
- **Throttling зависимостей**: уважай чужие 429 (навык `circuit-breaker-retry` — ретраи с Retry-After).
- **Шлюз — точка правды**: лимиты на API Gateway (Gateway Offloading), не распределённые «надежды» на каждый сервис.

## Банковские акценты

- Open Banking/партнёрские API: лимиты — часть договора (SLA-тарифы); превышение — биллинговое событие.
- Антифрод-стыки: rate limit — не замена антифроду (и наоборот).
- Зарплатные дни: приоритеты важнее отказов — платежи зарплатных реестров > фоновых выписок (Priority Queue, `queue-load-leveling`).

## Чек-лист

- [ ] Лимиты по измерениям задокументированы (таблица: кто/что/сколько)
- [ ] 429 + Retry-After возвращается всегда, не connection reset
- [ ] Метрики отказов по лимитам (рост 429 = повод пересмотреть квоты, а не «у клиентов проблемы»)
- [ ] Приоритетные классы нагрузки определены
- [ ] Лимиты зависимостей учтены в наших ретраях
