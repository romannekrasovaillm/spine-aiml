# Bulkhead

**Проблема.** Общий пул ресурсов: одна деградирующая зависимость (или шумный tenant) забирает все потоки/соединения → умирают даже здоровые направления. Название — от переборок корабля: пробоина топит отсек, не судно.

## Приёмы

- **Пул на зависимость**: отдельный connection/thread pool на каждый внешний вызов (шлюз ≠ справочник ≠ ядро) + CB на каждый пул (навык `circuit-breaker-retry`).
- **Семафоры/лимитеры конкурентности** на направление: max N одновременных вызовов к X; остальные — очередь с отказом (load shedding).
- **Tenant-букеты**: пулы/квоты на класс клиентов (VIP-канал не тонет вместе с массовым).
- **Критичность**: критичный путь (авторизация платежа) изолирован от отчётности и витрин — отдельные пулы, отдельные БД-роли.

## Чек-лист

- [ ] Карта «зависимость → её пул → её лимит» (таблица в дизайне)
- [ ] Нет shared nothing-иллюзии: общий пул БД/веб-сервера найден и оценён
- [ ] Лимиты имеют отказ-by-design (503+Retry-After), не зависание
- [ ] Изоляция покрыта тестом: стоп зависимости X → направление Y работает
- [ ] Метрики занятости каждого пула (saturation — 4 золотых сигнала)

## Цена

Избыточность ресурсов (пулы простаивают), сложность настройки лимитов. Trade-off принимаем сознательно: для некритичных направлений общий пул допустим — зафиксируй решение в ADR.

## Антипаттерны

- Один глобальный пул «на весь сервис».
- Bulkhead без CB: изоляция замедляет смерть, не предотвращает.
- Лимиты «на глаз» без замера профиля нагрузки.
