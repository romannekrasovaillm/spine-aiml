# Circuit Breaker + Retry

**Проблема.** Зависимость деградировала (медленно/падает). Вызывающие ждут таймауты → пулы потоков/соединений исчерпаны → каскадный сбой всего контура. Фалласи «сеть надёжна».

## Retry — только транзиентные сбои

- Ретраим: сетевые обрывы, 502/503/504, таймауты, throttling (429 — с Respect Retry-After).
- НЕ ретраим: 4xx (кроме 429), бизнес-отказы (недостаток средств!), ошибки валидации.
- Стратегия: экспоненциальная задержка + джиттер (иначе синхронные стаи ретраев добьют зависимость), максимум 2–3 попытки, общий дедлайн на попытки меньше таймаута вызывающего.
- Ретрай только идемпотентных операций (навык `idempotent-consumer`) — иначе двойное списание.

## Circuit Breaker

Прокси-автомат на вызов зависимости:
- **closed**: вызовы проходят; счётчик сбоев (доля за окно, напр. 50% за 20 вызовов).
- **open**: мгновенный отказ (fail fast) без вызова; таймер cool-down (напр. 30 с).
- **half-open**: N пробных вызовов; успех → closed, сбой → open.

Параметры — от критичности: платёжный шлюз — быстрый open (дорогой простой пула), справочник — терпеливее. Состояние CB — метрика + алерт (open CB = инцидент зависимости).

## Композиция (Azure): Retry ВНУТРИ Circuit Breaker

Ретраи маскируют транзиентные сбои; CB останавливает ретраи, когда сбой устойчив. Fallback на open: кэш, деградированный ответ, очередь — но НЕ молчаливый «успех».

## Чек-лист

- [ ] Каждый внешний вызов: таймаут + ретрай-политика + CB (или обоснование)
- [ ] Ретраи только транзиентных и только идемпотентных
- [ ] Джиттер на месте; Retry-After уважается
- [ ] Open CB имеет fallback и алерт
- [ ] Тест: зависимость молчит 60 с → наш сервис НЕ истощает пулы (chaos-проверка)
