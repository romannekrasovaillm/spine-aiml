# Статическая стабильность (Becky Weiss, Mike Furr, AWS)

**Определение**: система продолжает делать всё, что делала до деградации зависимости, — пусть без обновлений, но работает. Ключ: готовность к отказу ДО отказа, а не реакция на него.

## Два паттерна на зонах

- **Active-active (stateless)**: флот за LB в 3 зонах, избыточное провижинирование — каждая зона на 66% от нагрузочного предела (при отказе одной две несут всё). Отказ зоны → ноль действий: health checks уводят трафик сами. Работает и для консьюмеров очередей.
- **Active-standby (stateful)**: тёплый standby в другой зоне (RDS primary/standby), фейловер управляемый (DNS repoint). Новый лидер — ИЗ standby-кандидатов, не «догнать just-in-time».

Общее: capacity на случай отказа провижинируется ЗАРАНЕЕ. Восстановление, требующее control plane (запуск инстансов, скачивание конфигурации, регистрация в discovery), — анти-паттерн: control plane сложнее и вероятнее сломан именно во время аварии.

## Зональная арифметика (главный аргумент)

Серый сбой в зоне: regional-calls-regional: шанс запроса миновать битую зону = (2/3)^N для N сервисов в цепочке. Zonal-calls-zonal (запрос остаётся в своей зоне): константные 2/3 независимо от N. Поэтому фундаментальные data-plane сервисы (NAT gateway) — зональные: трафик не пересекает границ зон, деплой — по зональному календарю (одна зона в день).

- Простой паттерн: regional→regional (для большинства сервисов).
- Сложный: regional→zonal / zonal→zonal — для фундаментальных data-plane компонентов в критичном пути. Цена: управление N зональными средами.
- Данные: жёсткое состояние реплицируется через зоны (durability), но реплики не нужны зоне для работы.

## Банковский маппинг

- Запас на отказ ЦОДа: N+1 с готовой мощностью, а не «поднимем при пожаре»; RTO из учения, не из расчёта.
- Платёжный контур: восстановление не зависит от контура деплоя/конфигурации.
- Деплой платёжного ядра — по одному контуру/зоне в окно (blat: blast radius = одна зона).
