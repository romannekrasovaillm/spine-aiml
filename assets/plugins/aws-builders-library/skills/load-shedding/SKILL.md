# Load shedding: сбрасывай лишнее, сохраняй goodput (David Yanacek, AWS)

## Анатомия перегрузки

- Под нагрузкой latency растёт (контекст-свитчи, GC, I/O contention); после точки перегиба **goodput** (полезная работа) падает к нулю, хотя throughput ещё высок.
- Позитивная обратная связь: таймаут клиента → работа сервера впустую → ретрай → ещё больше нагрузки. Перегрузка становится устойчивым состоянием.
- Цель: держать latency принятых запросов низкой — отказывать ИЗБЫТОЧНЫМ дёшево и рано.

## Техники Amazon

- **Дешёвый отказ**: дроп запроса обязан быть почти бесплатным (затаившийся лог-вызов или сокет-настройка делают отказ дорогим — тестируй!). Если дроп дороже удержания — замедляй отказ до latency успешных (иначе least-outstanding балансировщик засыплет «быстрый на отказы» сервер).
- **Приоритизация**: ping балансировщика — важнейший запрос (не ответил → выкинут из пула в разгар шторма). `end()` важнее `start()`: завершение начатой работы приоритетнее новой (иначе недоделанная работа = впустую). Пагинация: следующие страницы приоритетнее первых.
- **Timeout hints**: клиент передаёт дедлайн; сервер выбрасывает обречённые запросы (после дедлайна ответ бесполезен). Дедлайн транзитивно пробрасывается по цепочке вызовов («remaining time» на каждом хопе). Часы — только монотонные локальные длительности.
- **Очереди**: ограничивай размер И время в очереди (выбрасывай старые); LIFO там, где протокол позволяет (HTTP/2 да, HTTP/1.1 pipelining нет). Surge queues у балансировщика — ловушка (Classic ELB → spillover/fast-fail в ALB). «Предполагай, что очередь есть там, где ты её не видишь».
- **Bounded work**: пагинация вместо безразмерных ответов — admission control требует оценки стоимости запроса.
- **Слоистая защита**: WAF/API Gateway/LB снаружи (самое дешёвое место для сброса), сервер внутри (видимость: кто и что дропнули). Тензия: ранний сброс дёшев, но слеп — логируй.
- **Внимание на автoscaling**: load shedding по CPU-таргету гасит сигнал реактивного скейлинга — согласуй пороги. Запас на отказ зоны считай по нагрузочным тестам, не по CPU.

## Тестирование и метрики

- Грузи до слома и ДАЛЬШЕ: идеал — плато goodput при росте throughput. Если не тестировал — сломается наихудшим образом.
- Метрики: НЕ загрязняй latency-метрики быстрыми отказами (медиана будет «отличной» при 60% сброшенного); false positive rate сбросов держи на нуле.
