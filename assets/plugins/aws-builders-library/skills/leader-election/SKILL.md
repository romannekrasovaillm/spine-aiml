# Выборы лидера (Marc Brooker, AWS)

## Плюсы и цена

Плюсы: проще думать, консистентность из одной точки, единый кэш, эффективность. Цена: единая точка отказа, единая точка масштабирования (рост за пределы одного лидера = реархитектура), единая точка доверия (плохой лидер = большой blast radius), сложные частичные деплои. Сначала рассмотри альтернативы: идемпотентные API, optimistic locking, workflow-движки — часто лидер не нужен.

## Leases — основной механизм Amazon

- БД хранит текущего лидера; лидер heartbeat'ит; замолчал — кандидаты занимают.
- Время — только локальные монотонные длительности, НЕ синхронизированные часы (время в распределённых системах — для людей).
- Бери battle-tested клиенты (DynamoDB lock client, ZooKeeper): кастомная реализация leases концептуально проста, но тонка в корректности.
- Митигация масштаба: шардирование лидерства (DynamoDB/EBS: лидер на область данных).

## Грабли (из практики Amazon)

- **Heartbeat в фоновом потоке**: рабочий поток умер, heartbeat держит lease (недоступность); или GC-пауза между проверкой lease и работой → лидер работает без lease. Правило: проверяй остаток lease непосредственно перед каждым side-effect.
- **Двух лидеров не избежать**: гарантировать «ровно один» невозможно — проектируй на «почти один, иногда ноль или два». Системы с идемпотентной работой терпят двух лидеров дёшево. Если нужен строго один — свержение старого ДО избрания нового (сложно: отличить мёртвого от разделённого сетью).
- **Долговечность до анонса**: сначала «make work durable», потом «tell others». Новый лидер догоняет недоделанное — идемпотентность делает это безопасным.
- Метрики: сколько работы лидер МОЖЕТ vs делает; аудит-лог смен лидерства (кто был лидером в момент X).
- Формальная верификация протокола (TLA+) — ловит редкие баги допущений.
