# 8 мод отказа апокалипсиса (Jacob Gabrielson, AWS)

## Раскладка вызова

Один `board.find("pacman")` через сеть = 8 шагов, каждый падает независимо: POST REQUEST → DELIVER REQUEST → VALIDATE REQUEST → UPDATE SERVER STATE → POST REPLY → DELIVER REPLY → VALIDATE REPLY → UPDATE CLIENT STATE. Клиент, сеть и сервер **не разделяют судьбу** — на одной машине они падали бы вместе, в распределённой системе — нет.

## Пять исходов вызова

```
switch (error) {
  case POST_FAILED:  // точно не дошло — безопасно ретраить
  case RETRYABLE:    // дошло, транзиентный отказ
  case FATAL:        // дошло, принципиальный отказ — не ретраить
  case UNKNOWN:      // таймаут: МОЖЕТ выполнилось, может нет
  case SUCCESS:      // валидируй reply!
}
```

**UNKNOWN — самое тяжёлое**: «снять деньги со счёта» вернуло UNKNOWN — деньги может списались. Люди интуитивно не умеют в WHAT_THE_FARG-ветку. Ответы: идемпотентность (повтор безопасен), запросы статуса (реконсиляция), явные pending-состояния.

## Следствия

- Тест-матрица взрывается: 10 сценариев одномашинного кода → 200 в распределённом (5 исходов × вызовы × последовательности). Пиши тесты на КАЖДЫЙ исход, включая UNKNOWN посреди последовательности.
- Рекурсия: те же 8 мод — на уровне групп сервисов, зон, регионов.
- Распределённые баги латентны (месяцы до триггера) и эпидемичны (сеть — единственное, что связывает машины, — разносит баг). Кейс Amazon: каталог-сервер с полным диском стал отвечать пустым БЫСТРО → балансировщик «заметил скорость» → отдал ему весь трафик сайта.
- Практика: «не доверяй ничему» — каждая строка, потенциально делающая сетевой вызов, может не сделать то, что написано.

## Чек-лист для ревью интеграции

- [ ] Каждый вызов обрабатывает все 5 исходов (особенно UNKNOWN)
- [ ] Денежные операции: UNKNOWN → статус-запрос/реконсиляция, не «предположим»
- [ ] Тесты: POST_FAILED/RETRYABLE/FATAL/UNKNOWN на каждый вызов
- [ ] Быстрые пустые ответы не считаются здоровыми (health check смотрит содержимое)
