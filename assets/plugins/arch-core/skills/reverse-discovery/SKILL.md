# Reverse discovery

Пять из шести фреймворков проектирования решают greenfield; банк — 20–30 лет ядра. Перед высокоавтономной работой с legacy — карта системы, извлечённая из кода, с ЧЕСТНЫМИ метками уверенности (противоядие от automation bias сгенерированных описаний).

## Артефакты обследования (со сроком годности!)

1. Карта компонентов и владельцев (кто отвечает — из CODEOWNERS/коммитов).
2. Точки входа: API, джобы, очереди (consumers/producers).
3. Модель данных: ключевые сущности, владельцы записи, потоки записи/чтения.
4. Интеграции: протоколы, контракты, таймауты, ретраи (из кода, не из wiki).
5. Скрытые связи: общие таблицы, файловые обмены, планировщики.
6. Состояние тестов и наблюдаемости (чем подтвердим безопасность изменения).
7. Долг и трупы: мёртвый код, неиспользуемые флаги, deprecated-интеграции.
8. Ограничения платформы: версии, EOL, лицензии.
9. Риски изменения: хрупкие места по истории инцидентов/коммитов.

Каждый артефакт: `created_at` + `expires_at`; по истечении — пересобрать (living-spec, не разовый аудит).

## Метки уверенности

- `[confirmed]` — доказано кодом/конфигом (со ссылкой на файл:строку).
- `[inferred]` — выведено косвенно; проверить перед опорой.
- `[gap]` — пробел: информации нет, нужен владелец домена.

## Процедура

1. Быстрый обход: `glob`/`grep`/`bash` (tree, зависимости, CI, миграции).
2. Сборка карты с метками; каждый `[gap]` — с вопросом владельцу.
3. Верификация критичных для задачи `[inferred]` — точечным чтением кода.
4. Карта → в `docs/reverse/`; дельта-изменения — навык `delta-spec`.

## Антипаттерны

- Сгенерированное описание без меток — выглядит уверенно, врёт гладко.
- «Reverse-spec = истина» — заменяет владельца домена (нет, не заменяет).
- Обследование без срока годности — устарело в момент записи.
