# Дельта-спеки

Философия: fluid not rigid, iterative not waterfall, brownfield not just greenfield. Не описывай систему целиком — опиши ИЗМЕНЕНИЕ.

## Структура дельты

```
## ADDED
- Требование: оркестратор публикует событие PaymentFailed. Критерий (EARS): When проведение отклонено ядром, the оркестратор shall опубликовать PaymentFailed в топик payments.status ≤ 1 с.
## MODIFIED
- Требование PAY-3: таймаут авторизации 800 мс → 500 мс (причина: NFR-бюджет 2026-Q3).
## REMOVED
- Требование PAY-9 (синхронный статус-колбэк) — заменён событием (ADR-12).
```

## Цикл

1. **propose**: дельта + обоснование; аудиторский след намерения ДО реализации.
2. **apply**: реализация (агентная — с handoff-пакетом, навык `handoff-packaging`).
3. **archive**: дельта вливается в живой источник истины (спека системы обновляется), дельта — в архив со статусом.

## Границы применимости

- Fast/Standard Path — да. Critical Path (платежи, КИИ, необратимые миграции, смена security boundary) — полный Solutioning, дельта недостаточна (навык `significance-routing`).
- Дрейф: дельта не влита → истина расходится с кодом. Сенсор: `control sensors` + drift-check по крону (`spec-drift`).

## Антипаттерны

- Дельта от устаревшей истины (не синхронизирована с кодом).
- «Дельта-простыня»: 40 изменений одним пакетом — разбить по единицам работ.
- REMOVED без заменяющего решения и плана миграции потребителей.
