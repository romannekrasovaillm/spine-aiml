# Состязательное ревью

Установка ревьюера: «Я НЕ проектировал эту систему. Моя работа — найти, что сломается в проде, в регуляторике, в эксплуатации». Симпатия к проекту — предвзятость.

## Железные правила

- Каждая находка опирается на **проверяемое свидетельство**: цитата из документа, строка кода, номер секции — не вкус («мне не нравится» — не находка).
- Вердикт бинарен: **READY** / **NOT-READY** (+ список находок с severity: blocker/major/minor).
- Ограниченная область чтения: ревьюер не перепроектирует, а ломает; точечная проверка точек интеграции — да, переписывание дизайна — нет.
- Версии и применимость названных технологий проверяются из внешних источников (`web_fetch`), не из памяти модели.

## Линзы (параллельные проходы)

1. **Стыки и контракты**: несогласованные форматы, таймауты, ретраи, идемпотентность, версии API.
2. **Данные**: согласованность (где сага/где strong), миграции, PII-маршруты, RPO.
3. **Безопасность/комплаенс**: trust zones, аутентификация на каждом стыке, секреты, аудиторский след, 152-ФЗ/КИИ.
4. **NFR/эксплуатация**: деградация, backpressure, DLQ, наблюдаемость, план отката.
5. **Реализуемость**: нет ли «здесь произойдёт чудо» — шагов без владельца и механизма.

## Формат вердикта

```
VERDICT: NOT-READY
Находки:
1. [blocker] Стык оркестратор→ядро синхронный, таймаут не задан (СПЕКА, §3.2: «вызов core») — каскадный сбой при деградации ядра. Свидетельство: sequence.mmd, ребро без таймаута.
2. [major] RPO заявлен 5 мин, репликация асинхронная без кворума (ADR-4) — противоречие.
Вопросы автору: …
```

## Антипаттерны

- Ревьюер = автор (сам себя проверил).
- Находки-вкусовщина без свидетельств.
- «В целом хорошо» без вердикта.

Связка: промпт `review_adversarial`, рубрики `solution_architecture`/`architecture_gates` (`rubric_evaluate`).
