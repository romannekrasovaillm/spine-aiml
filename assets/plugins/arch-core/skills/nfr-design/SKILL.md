# NFR-дизайн

NFR без числа — пожелание. Каждое требование: метрика + целевое значение + метод измерения + следствие нарушения.

## Слоистость (обязательный порядок)

1. **Functional design** — технологически нейтрален: логические компоненты, потоки, контракты.
2. **NFR design** — оперирует логическими компонентами: бюджеты latency, модель согласованности, RTO/RPO.
3. **Infrastructure design** — привязка к конкретным сервисам/платформам (только здесь — вендоры).

Прослеживаемость: требование → компонент → NFR-цель → инфраструктурное решение.

## Каталог бюджетов (банковский минимум)

| NFR | Пример цели | Метод проверки |
|---|---|---|
| Latency | p99 авторизации платежа ≤ 800 мс | нагрузочный тест, APM |
| Throughput | 300 TPS с ростом ×2 без перепроектирования | нагрузочный стенд |
| Availability | 99.95% (≤22 мин простоя/мес) | мониторинг, error budget |
| RTO / RPO | RTO ≤ 30 мин, RPO ≤ 5 мин | учения по DR, не документ |
| Data locality | персданные — только RU-контур | fitness: скан маршрутов данных |
| Cost | ≤ N ₽/транзакцию при профиле нагрузки X | биллинг-отчёт |

## Процедура

1. Вытащи все «как хорошо» из спеки → таблица бюджетов.
2. Каждой цели — метод измерения и владельца.
3. Противоречия NFR (consistency vs availability при разделении) — явный trade-off с решением → в ADR.
4. Бюджеты → в fitness functions где возможно (`fitness_check`), иначе — в критерии приёмки.

## Антипаттерны

- «Высокая доступность» без цифры и error budget.
- RTO/RPO, никогда не проверенные учениями (бумажный DR).
- NFR, выбранные после фиксации инфраструктуры (хвост виляет собакой).
- Одинаковые NFR для всех сервисов (перезаклад стоимости на некритичных).
