# Readiness-гейт

Вопрос гейта: «сможет ли исполнитель (агент/разработчик) реализовать, НЕ изобретая отсутствующих решений?» Каждое изобретённое на ходу решение — будущий архитектурный долг.

## Вердикты

- **PASS** — можно в реализацию.
- **CONCERNS** — можно с оговорками; каждая оговорка адресная (где пробел, что чинит).
- **FAIL** — стоп; список пробелов с указанием чинящего навыка/артефакта.

## Процедура проверки

1. **Двусторонняя трассируемость**: каждое требование → хотя бы одна история/задача; каждая история → хотя бы одно требование. «Сироты» помечаются с обеих сторон.
2. **Критерии приёмки**: у каждого требования — проверяемый критерий. Нотация EARS (Kiro): `When <событие>, the <система> shall <реакция>` / `While <состояние>` / `If <условие>, then …` / `Where <фича>`. Без «корректно обрабатывает».
3. **Полнота NFR**: бюджеты есть и измеримы (навык `nfr-design`).
4. **Инварианты**: spine-блоки, затрагиваемые спекой, перечислены с ID (навык `spine-invariants`).
5. **Противоречия**: spec check — требования не конфликтуют (два разных SLA на один запрос).
6. **Сенсоры**: `control sensors` — required_sections, upstream_coverage (все ссылки на входы существуют).

## Формат вердикта

```
VERDICT: CONCERNS
Пробелы:
1. [CONCERN] Требование PAY-7 не покрыто историями → чинить: декомпозиция задач.
2. [FAIL] Нет RTO/RPO для платёжного контура → чинить: nfr-design.
Сироты: требования {PAY-3}; истории {US-12}.
```

## Антипаттерны

- Гейт «по вайбу» без трассируемости.
- PASS при отсутствующих критериях приёмки («договорим в спринте»).
- Резиновый штамп: гейт, который никогда не FAIL — красный флаг (approval theater).
