# Фитнес-функции

Архитектурное правило без машинной проверки — пожелание. Фитнес-функция — исполняемое утверждение о репозитории: зелёное/красное, без интерпретаций.

## Типы правил (инструмент `fitness_check`, CLI `arch-ml control check`)

- `must_contain` / `must_not_contain`: regex по файлам glob — слоистость («API не импортирует драйвер БД»), запреты (`unsafe`, `unwrap(`, `dbg!`), обязательные секции документов.
- `each_file_must_contain`: regex обязателен в КАЖДОМ файле набора — «таймаут в каждом конфиге клиента», «секция приёмки в каждой спеке». Отличие от `must_contain` («хотя бы в одном») — это и есть усиление постановки.
- `file_exists`: обязательные артефакты (spine, ADR-индекс, runbook).
- `dir_must_have_file`: обязательный файл в КАЖДОМ каталоге набора — «`openapi.yaml` у каждого сервиса `services/*`».
- `command_succeeds`: тесты, линтеры, контрактные проверки (с `timeout_secs`).
- `severity`: `error` ломает итог (exit 1 — для CI), `warn` — сигнал.

## Что превращать в фитнес-функцию, а что — в рубрику

- **Машине** (fitness): бинарно проверяемое — запрещённые зависимости, форматы id, наличие секций, зелёные тесты.
- **Судье** (рубрика, навык `rubric-judging`): качественное — полнота альтернатив, ясность обоснования, сбалансированность trade-off.
- Правило большого пальца: если на «соблюдено?» можно ответить grep'ом — это fitness.

## Авторинг правил

1. Каждое правило — от инварианта (spine `Rule:` — кандидат №1) или инцидента.
2. Формулировка сообщения — с причиной и ссылкой на AD («что нарушено и почему важно»).
3. Ложные срабатывания убивают доверие: точный glob, исключения — явно (`exclude_glob`). Glob понимает только `*`, `?` и `**` — brace-раскрытие `{yaml,yml}` не поддерживается, перечисляй отдельными правилами.
4. `must_contain`/`each_file_must_contain` матчатся против ВСЕГО файла: строчный якорь пиши с флагом `(?m)` (`"(?m)^## Секция$"`); голое `^` — начало файла, правило молча не найдёт ничего. `must_not_contain` проверяется построчно — там `^` означает начало строки.
5. Ревизия правил ежеквартально (устаревшее правило — в warn, потом удалить).
6. Exception workflow: нарушение допустимо только time-bound, с владельцем и датой пересмотра.

## Антипаттерны

- Правило, которое все обходят (exception rate растёт — правило мертво или процесс сломан).
- 200 warn-находок, которые никто не читает (шум ≥ сигнал).
- Fitness без CI-интеграции — проверяется «когда вспомнят».
