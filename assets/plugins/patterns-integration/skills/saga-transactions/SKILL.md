# Saga (Крис Ричардсон, microservices.io; Azure: Saga на Compensating Transaction)

**Проблема.** Операция охватывает несколько сервисов, у каждого своя БД (database per service); 2PC недоступен/запрещён (блокировки, единая точка отказа координатора XA).

**Решение.** Цепочка локальных транзакций T1…Tn; при сбое Ti выполняются компенсирующие транзакции C(i-1)…C1 в обратном порядке. Каждая компенсация — семантический откат (не «удалить запись», а «вернуть деньги с корр. счётом»).

## Варианты

- **Choreography**: участники слушают события и решают сами. Простые потоки (≤3 участников), нет единой точки; минус — поток читается по всему коду, циклы событий.
- **Orchestration**: оркестратор (Saga Execution Coordinator) говорит, кому что делать. Сложные потоки, видимое состояние (state machine!); минус — риск «умного центра». В банке — почти всегда оркестрация: состояние платежа должно быть явным и аудируемым.

## Изоляционные аномалии и контрмеры

Сага не даёт изоляции: между T1 и T2 данные «грязные». Контрмеры: семантические блокировки (статус `PENDING` запрещает конфликтующие операции), commutative updates, версии сущностей, чтение с учётом «подвисших» саг.

## Чек-лист проектирования

- [ ] Для каждого шага Ti есть компенсация Ci (или обоснование, почему шаг необратим — тогда он последний/точка невозврата)
- [ ] Состояние саги персистентно и видимо (таблица/state machine), не «в памяти»
- [ ] Компенсации идемпотентны (навык `idempotent-consumer`)
- [ ] Таймауты шагов + эскалация застрявших саг (для платежей — операционная очередь!)
- [ ] Деградация: что видит клиент при NOT_COMPLETE (честный статус, не 500)
- [ ] Связь с NFR: сквозной latency-бюджет саги (навык `nfr-design`)

## Антипаттерны

- Компенсация «удалить запись» — теряется аудиторский след (банк: запрещено, только сторно).
- Хореография на 8 участников — невидимый поток.
- Сага, читающая «промежуточные» данные как финальные (dirty read).
