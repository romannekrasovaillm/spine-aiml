# Transactional Outbox

**Проблема.** «Записать в БД и опубликовать событие» — не атомарно: упали между — расхождение (dual-write problem). Потерянное событие в банке = расхождение контуров.

**Решение.** В одной локальной транзакции пишем: (а) бизнес-изменение, (б) запись события в таблицу `OUTBOX`. Отдельный ретранслятор читает outbox и публикует в брокер.

## Варианты ретрансляции

- **Polling publisher**: SELECT … FOR UPDATE SKIP LOCKED по outbox. Просто, нагрузка на БД, задержка = период опроса.
- **Transaction log tailing**: чтение WAL (Debezium CDC). Нулевая задержка, нет нагрузки на запросный путь; минус — инфраструктурная сложность.

## Железные правила

- Событие в outbox — полное самодостаточное тело (не ссылка «потом дочитай»).
- Публикация at-least-once ⇒ потребитель ОБЯЗАН быть идемпотентным (`idempotent-consumer`); дедупликация по message id.
- Порядок: ключ партиции = агрегат (payment_id); глобальный порядок не гарантируй.
- Мониторинг: размер неотправленного outbox — метрика с алертом (застрявший ретранслятор = молчаливая остановка интеграции).
- Retention: отправленные записи архивируются (аудит!), не удаляются мгновенно.

## Банковский пример

Ядро проводит платёж: в той же транзакции — запись `PaymentStatus{payment_id, status, v}` в outbox; CDC-ретранслятор → топик `payments.status`; оркестратор и нотификации — идемпотентные потребители.

## Антипаттерны

- Dual write (БД, потом Kafka) — классическая причина расхождений.
- Outbox без алерта на lag.
- Событие-конверт («что-то изменилось, иди читай») — гонки читателей.
