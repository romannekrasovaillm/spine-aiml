# CQRS и API Composition

**Проблема.** Данные разнесены по сервисам (database per service) — SQL-джойн невозможен. Как строить запросы, охватывающие несколько владельцев данных?

## Вариант 1. API Composition

Запрос → композитор вызывает сервисы-владельцы параллельно → join в памяти.

- Когда: простые запросы, 2–4 владельца, умеренная нагрузка, требуется strong consistency.
- Цена: latency = max(участники) + сетевые отказы на каждом; N+1 при списках; доступность = произведение доступностей.

## Вариант 2. CQRS

Команды пишут в write-модель; события строят материализованные представления (view DB) под конкретные запросы; запросы идут только в представления.

- Когда: тяжёлые витрины, высокая нагрузка чтения, денормализация окупается, допустима eventual consistency (в банке — почти везде, кроме баланса для платежа).
- Цена: сложность (ещё одно хранилище, пайплайн проекций), лаг согласованности — ПОКАЖИ его в API (`as_of` метка), версионирование схемы событий.

## Command-side replica (гибрид)

Сервис-командист поднимает читаемую реплику чужих данных по событиям — когда API Composition к чужим сервисам не проходит по latency.

## Критерии выбора (чек-лист)

- [ ] Запрос требует актуальности «прямо сейчас»? → API Composition (или пересмотри границы).
- [ ] Чтений на порядки больше записей / тяжёлая агрегация? → CQRS.
- [ ] Лаг согласованности показан потребителю (as_of, индикатор свежести)?
- [ ] Проекции восстанавливаемы (replay из событий) при смене схемы представления?
- [ ] Персданные: маршрут в витрину согласован с data locality (навык `nfr-design`)?

## Антипаттерны

- CQRS «потому что модно» на простом CRUD — оверинжиниринг.
- API Composition по цепочке из 7 сервисов — latency-мультипликатор.
- Общая витрина «для всех» — новый монолит данных.
