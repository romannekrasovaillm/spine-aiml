# Strangler Fig + Anti-Corruption Layer

**Strangler Fig (Фаулер; Azure Patterns).** Новая система растёт вокруг старой; фасад-маршрутизатор (proxy/gateway) перенаправляет вызовы: реализованное — в новое, остальное — в legacy, пока старое не «задохнётся». Big-bang миграция в банке запрещена риск-аппетитом.

**Anti-Corruption Layer (Эванс, DDD).** Фасад/адаптер между новым доменом и legacy: транслирует модели и протоколы, НЕ пропуская концепции legacy (коды справочников, странные статусы, COBOL-структуры) в новую модель.

## Процедура миграции

1. Reverse discovery legacy (навык `reverse-discovery`): карта стыков с confidence/gaps.
2. Фасад-маршрутизатор на стыке; метрики доли трафика по веткам (новое vs старое) — это KPI миграции.
3. Первый срез — walking skeleton: один сквозной сценарий новым путём (доказывает архитектуру).
4. Перенос по вертикальным ломтям (use-case за use-case), не по слоям.
5. ACL на каждом обращении к legacy: трансляция моделей + протоколов + семантики ошибок; тесты трансляции обязательны.
6. Точка невозврата и план отката на каждый ломоть; данные — двойная запись/сверка на переходный период.
7. Удаление: погашенная ветка legacy выводится (дедактивация — отдельный шаг с аудитом).

## Чек-лист

- [ ] Фасад единственная точка маршрутизации (нет «прямых» вызовов мимо)
- [ ] ACL не торчит наружу (модель legacy не протекает в DTO/API нового)
- [ ] Доля мигрированного трафика измеряется
- [ ] Двойная запись/сверка данных на переходный период + дата отключения
- [ ] Каждый ломоть — отдельный handoff/дельта-спека (навык `delta-spec`)

## Антипаттерны

- Strangler без плана завершения — вечные две системы (дороже, чем одна).
- ACL, превратившийся в бизнес-логику (он транслятор, не сервис).
- Миграция по слоям («сначала все DAO») — ценность не видна годами.
