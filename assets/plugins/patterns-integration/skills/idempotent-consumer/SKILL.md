# Idempotent Consumer

**Проблема.** Брокеры гарантируют at-least-once (дубли при ребалансах, ретраях, повторной публикации из outbox). Клиенты ретраят таймауты. Повторная обработка команды списания без защиты = двойное списание.

**Решение.** Потребитель/обработчик безопасен при повторе: тот же вход → тот же результат, без второго эффекта.

## Приёмы

1. **Ключ идемпотентности**: бизнес-ключ (payment_id + operation) или явный `Idempotency-Key` заголовок; первичный/уникальный индекс по нему.
2. **Inbox-таблица** (зеркало outbox): `processed_messages(message_id, processed_at, result)` в ТОЙ ЖЕ транзакции, что и бизнес-изменение; дубль → вернуть сохранённый результат, не выполнять логику.
3. **Естественная идемпотентность**: PUT вместо POST-наращивания (`SET status=X` vs `balance = balance - 100`), версии/ETag для optimistic concurrency.
4. **Проверка состояния**: переходы статусной машины («уже в PAID → no-op, вернуть 200»), а не слепое выполнение.

## Чек-лист

- [ ] Каждый mutating endpoint/consumer имеет ключ идемпотентности (или обоснование)
- [ ] Дедупликация в той же транзакции, что и эффект (иначе гонка)
- [ ] Повтор возвращает ПЕРВЫЙ результат (не «уже сделано» без тела)
- [ ] Тест повторной доставки: одно сообщение ×2 → эффект ×1
- [ ] TTL хранения ключей согласован с окном ретраев канала
- [ ] Метрика дублей (аномальный рост = симптом зацикленного producer'а)

## Банковский пример

Оркестратор платежа: `POST /payments` с `Idempotency-Key: order-123`; повторный вызов при таймауте сети → тот же `payment_id` и статус, новое списание НЕ создаётся. Fitness: `fitness_check` правило — каждый handler списания содержит проверку ключа (grep по обработчикам).

## Антипаттерны

- Дедупликация «по содержимому сообщения» (два разных платежа на одну сумму — ложный дубль).
- Inbox вне транзакции бизнес-изменения.
- «У нас exactly-once в Kafka» — нет, сквозной exactly-once семантики не существует, только идемпотентность.
