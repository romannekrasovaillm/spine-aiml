# ADR-001. Миграция платёжного шлюза на нового провайдера

- Дата: 2026-08-10
- Статус: Proposed (записано до начала реализации; пересмотр — 2027-02-10
  или при изменении тарифов провайдера)

## Контекст

Интернет-магазин обрабатывает около 12 тысяч платежей в сутки через
текущий платёжный шлюз. Провайдер объявил о прекращении поддержки API v1
с 2027-03-01. Действующие силы: требования регулятора к хранению
карточных данных (нужна выделенная доверенная зона), бюджет на миграцию —
два разработчика на один квартал, пиковая нагрузка распродаж (рост в пять
раз в ноябре). Цена бездействия: с даты отключения API v1 приём платежей
остановится полностью.

## Рассмотренные варианты

1. Переход на API v2 текущего провайдера. Отклонён: тарифы вырастут на
   40 %, а двухфазный коммит провайдер не поддерживает.
2. Собственный платёжный модуль. Отклонён: потребуется сертификация, это
   год работы и постоянные аудиты, что превышает бюджет.
3. Новый провайдер с внутренним API-адаптером (выбрано).
4. Статус-кво: остаться на API v1. Отклонён: сервис отключается
   2027-03-01, приём платежей встанет; цена бездействия — вся выручка
   онлайн-канала.

## Последствия

Положительные: независимость от одного провайдера, тариф ниже на 15 %.

Отрицательные (честно):

- команда поддержки получит новый тип инцидентов (по пилоту — около двух
  обращений в неделю): митигация — runbook и обучение до запуска;
- двойная эксплуатация двух шлюзов в переходный период удвоит стоимость
  на два месяца: принято сознательно, заложено в бюджет миграции;
- откатные репетиции замедлят релизный цикл на одну неделю.

## Обратимость

Reversible with cost: адаптер скрывает провайдера за внутренним
интерфейсом; обратный переход — переключение конфигурации. Репетиция
отката проведена на стенде 2026-08-05, заняла 40 минут. Данные транзакций
не мигрируют: старый шлюз остаётся доступным на чтение 12 месяцев.
