# SPEC-0041: Мгновенное уведомление о статусе платежа маркетплейса

Образцовая спецификация изменения для сенсоров харнесса: обязательные секции
«Проблема», «Критерии приёмки», «Риски»; входы перечислены в «Контекст и входы»
(сенсор upstream-coverage проверяет ссылки на них).

## Контекст и входы

- Верхнеуровневая архитектура: `examples/specs/ARCHITECTURE-SPINE.example.md` (AD-1, AD-2).
- Гейты и маршрут: изменение затрагивает событийный стык доменов — триггер `cross_domain_integration`, маршрут Standard.
- Связанные решения: ADR-0007 «Оркестрация платежей — отдельный сервис» (Accepted).

## Проблема

Клиент маркетплейса после оплаты не видит финальный статус платежа до ночного
батча (до 8 часов). Колл-центр получает до 30% входящих «где мой платёж»,
возвраты оформляются по неподтверждённым операциям. Событие `PaymentStatus`
уже публикуется платёжным хабом в шину (AD-1), но потребителя со стороны
коммуникаций нет.

## Критерии приёмки

1. Клиент получает push-уведомление о финальном статусе платежа не позднее
   60 секунд после события `PaymentStatus` в 99% случаев (p99 ≤ 60 с).
2. При дубле события клиент получает ровно одно уведомление (дедупликация
   по `payment_id` + `status`, AD-2).
3. При недоступности шины более 5 минут статусы дозапрашиваются из платёжного
   хаба опросом; потеря события не приводит к потере уведомления.
4. Откат: отключение консьюмера фиче-флагом возвращает ночной батч
   без потери данных и без изменения схемы событий.

## Риски

- Всплеск платежей ×3 на распродажах — консьюмер отстаёт, уведомления
  опаздывают; митигация: автомасштабирование консьюмера, алерт по лагу.
- Утечка PII через текст уведомления — митигация: в событии только
  технические поля (AD-1), сумма и получатель подставляются на стороне
  коммуникаций из справочника.
- Зависимость от доступности платёжного хаба при опросе — митигация:
  окно опроса с backoff, дедлайн и эскалация в on-call при превышении.
