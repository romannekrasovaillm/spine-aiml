# ARCHITECTURE-SPINE — Платёжный контур маркетплейса (пример)

Позвоночник инвариантов: фиксируется только то, в чём независимые исполнители
могут разойтись несовместимо, что неочевидно и является компромиссом.
Тест принадлежности: «могут ли две единицы уровнем ниже, построенные
независимо, выбрать несовместимо — и будет ли это дорого?»

## AD-1: Событие PaymentStatus — единственный канал статусов платежа

- **Binds:** все потребители статусов платежей (уведомления, витрины,
  антифрод) читают событие `PaymentStatus` из топика `payments.status`;
  событие несёт только технические поля: `payment_id`, `status`,
  `occurred_at`, `schema_version`; PII в событии запрещены.
- **Prevents:** расхождение, при котором одни потребители опрашивают платёжный
  хаб, а другие читают шину с разными форматами и разным моментом истины;
  утечку PII через событийный контракт.
- **Rule:** в репозитории потребителя отсутствуют прямые вызовы API платёжного
  хаба для получения статуса; схема события версионируется полем
  `schema_version`, совместимость — backward в пределах мажорной версии 1.x.

## AD-2: Идемпотентность всех денежных операций по сквозному ключу

- **Binds:** каждая команда, двигающая деньги (списание, зачисление, возврат),
  несёт сквозной ключ `payment_id` + `operation_seq`; приёмник обязан хранить
  обработанные ключи не менее 30 суток и отвечать результатом первой обработки
  на повтор.
- **Prevents:** двойное списание при ретраях оркестратора и при повторной
  публикации события шиной (at-least-once); расхождение счетов клиента
  и процессинга при сбоях посреди цепочки.
- **Rule:** для любого консьюмера денежных команд контрактный тест «повторная
  доставка того же ключа не меняет состояние счёта» проходит в CI.

## Deferred

- **D-1:** единый формат идентификатора возврата (`refund_id`). Причина:
  контур возвратов проектируется в следующем квартале, раньше фиксации
  формат будет непроверяем. Условие возврата: старт Solutioning контура
  возвратов или появление второго потребителя событий возвратов.
