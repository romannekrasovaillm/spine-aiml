# Континуальное обучение и пост-тренинг: конвейер стадий

Скилл описывает пост-тренинг как **конвейер из шести стадий**, у каждой из которых свой объект изменения. Не путать с одноимённой темой в плагине `cpt/` (скилл `continual-learning-llm`): та — про то, как дать модели новые факты **без правки весов** (иерархия контекст/KV-кэш → файлы памяти → RAG → LoRA → SFT). Здесь наоборот: речь про **обновление весов** от базовой модели к специализированной.

Ключевая мысль конвейера — **каждая стадия меняет своё**:

| Стадия | Что меняется |
|---|---|
| CPT / mid-training | знание и распределение домена (что модель «видела») |
| SFT | формат, процедура, стиль поведения (что модель «делает») |
| RLHF | предпочтения, уместность, общая полезность (чему модель «предпочитает») |
| RL на рубриках | субъективное качество там, где нет проверяемого ответа |
| RLVR | способности/поведение по проверяемому сигналу (reasoning, tool-use) |
| Дистилляция | консолидация специалистов и режимов в один чекпоинт |

Инвариант конвейера: **качество сигнала на стадии не выше качества верификатора/reward на этой стадии.** Плохой verifier на RLVR и слабый судья на рубриках портят всё, что идёт ниже по цепочке, и это нельзя исправить следующей стадией.

## Как пользоваться (маршрутизация)

1. **Определи стадию вопроса** — по таблице выше или по таблице-маршрутизатору в §1.
2. **Проверь предпосылку «нижнего достаточного этапа»**: не запускай более дорогую и рискованную стадию, если задача решается предыдущей (см. §5, антипаттерн «прыжок в RL».
3. **Проверь gate стадии** — блок предпосылок в разделе стадии (для RL-стадий это почти всегда «есть работающий SFT-cold-start и чистый verifier»).
4. **Диагностику** веди по §4: симптом → вероятная стадия → что проверить, а не «давай ещё этап».

## 2. Стадии подробно

### 2.1 CPT / mid-training (домен-дообучение)

**Цель.** Сдвинуть распределение базы в домен (язык, терминология, длинный контекст) и подготовить её к пост-тренингу, **не меняя задачу обучения**. Mid-training — это тот же CPT, встроенный между претрейном и пост-тренингом (обзор: arXiv:2510.23081, плагин `midtraining/`).

**Данные.** Домен-корпус + **выделенная general-доля** ради обратной совместимости (backward balance): нельзя кормить модель только синтетикой домена — это ведёт к галлюцинациям и деградации general-умений. Пайплайн данных: collection → synthesis (дистилляция/извлечение/эволюция) → selection → **decontamination** → mixing. Дедуп против бенчмарков — обязателен, иначе оценка врёт.

**Лосс.** Next-token prediction — тот же, что в претрейне. Особенности: WSD/cosine-затухание LR, маскирование границ документов и EOS при упаковке (packing) — см. `cpt/eos-in-packing`; иначе модель учится склеивать несвязанные документы.

**Верификатор / reward.** Нет. Контроль — held-out домена + набор general-бенчмарков (следить за обеими сторонами: домен растёт, general не должен падать).

**Предпосылки (gate).** Есть чистый домен-корпус с правом на использование; зарезервирована general-доля; бенчмарки дедуплицированы против корпуса.

**Типовые отказы.**
- Катастрофическое забывание general-способностей — прямое следствие односторонней диеты.
- Контаминация бенчмарков домен-корпусом → завышенная оценка.
- Слишком высокий LR или отсутствие затухания → разрушение базы.
- Слепое «доливание» вместо расчета на backward balance.

### 2.2 SFT

**Цель.** Задать модели **формат, процедуру и стиль** (и засеять agentic-поведение трейсами), а не новые знания. SFT — это ещё и универсальный механизм дистилляции: трейсы учителя превращаются в CE-обучение (см. §2.6).

**Данные.** Инструкции/трейсы, отфильтрованные по корректности; качество важнее объёма. Референс: OpenThoughts3-1.2M (arXiv:2506.04178, плагин `sft/sft-openthoughts3`) — конфиги LoRA/QLoRA/full по VRAM. Для agentic-поведения — трейсы с tool-calls, а не только финальные ответы.

**Лосс.** Токеновый cross-entropy по целевым токенам, **prompt-маска** (лосс только на ответе/трейсе). Про мульти-оконные цели и contrastive-pairs — см. `effort/effort-conditioned-sft` (целевые окна как перцентили задачи, contrastive-пары 30–50%).

**Верификатор / reward.** Per-token verifier отсутствует. Гейт — на данных: фильтр по корректности ответа и/или LLM-судья до обучения, а не после.

**Предпосылки (gate).** Есть способ отфильтровать трейсы по корректности; формат промпта выверен (для chat-моделей формат критичен: неверный system prompt/plain string обваливает качество — см. `prompt-format-critical`).

**Типовые отказы.**
- Exposure bias: обучение идёт на «учительских» префиксах, а на инференсе студент видит свои — расхождение распределений (лечится online/on-policy дистилляцией, §2.6).
- Копирование личности/стиля учителя (модель называет себя именем учителя).
- Length-bias от паддинга: модель учится «набивать длину».
- Сдвиг способностей после SFT: спектральный дрейф SFT ≈ 35% против ≈ 0.01% у RLVR (arXiv:2607.19331, `rlvr/iso-rlvr-optimization`) — SFT реально двигает базовые способности, поэтому после него перемеряй general.
- Забывание режимов: SFT в один профиль убивает многомодовость, которую потом приходится возвращать дистилляцией.

### 2.3 RLHF (обучение на предпочтениях)

**Цель.** Выровнять модель на человеческие предпочтения: уместность, полезность, устойчивость, снижение нежелательного поведения. В рецептах это обычно **финальная шлифовка**, а не основной способ привить способность.

**Данные.** Парные предпочтения (chosen/rejected) для RM; либо набор принципов для **Generative Reward Model** — судья, оценивающий ответ по набору принципов (рецепт: Nemotron 3, arXiv:2604.12374 — цепочка SFT → RLVR → SWE-RL → **RLHF с principle-following GenRM**). Перекрёстная (bidirectional) преференс-пара — приём из Ling 2.6 (arXiv:2606.15079).

**Лосс.** Два уровня: (1) обучение RM — попарное ранжирование (Bradley–Terry-класс); (2) обучение политики — PPO/GRPO против RM. Альтернатива без отдельной RM — **direct preference** (DPO-семейство): лосс прямо на парах предпочтений. Выбор «RM+RL vs DPO» — компромисс между стоимостью/стабильностью (DPO проще) и потолком/онлайн-контролем (RM+RL гибче).

**Верификатор / reward.** Обучаемая модель предпочтений или GenRM — **не детерминированный** сигнал; отсюда весь класс проблем ниже.

**Предпосылки (gate).** Согласованность разметки (agreement) измерена; RM провалидирован на held-out парах; есть KL-регуляризация к референсу.

**Типовые отказы.**
- **Reward hacking / Goodhart:** политика эксплуатирует слабости RM вместо решения задачи; признак — растёт reward, падает человеческая оценка.
- **Bias RM:** оптимизация под длину/verbiage, sycophancy (поддакивание).
- Distribution shift: политика уходит из области, на которой RM обучался.
- Шум разметки: несогласованные аннотаторы → RM учит шум.

### 2.4 RL на рубриках (rubrics-as-rewards)

**Цель.** RL там, где **нет** проверяемого ответа: письмо, research, медицина, стратегия — субъективное качество. Рубрика превращает «нравится/не нравится» в набор взвешенных бинарных критериев.

**Данные.** Пары prompt ↔ рубрика, где рубрика — instance-specific, сгенерированная более сильной моделью вместе с эталонным ответом; объёмы порядка 5K–20K (Rubicon/RaR/OpenRubrics — плагины `rubrics/rubric-rl-pipeline`, `rubrics/rubric-rl-patterns`).

**Лосс.** GRPO по reward судьи; полезный сигнал — не абсолютный балл, а **разрывы** между кандидатами (score gaps) в группе. Шаг-кредит и динамические рубрики — см. `credit-assignment/draco-rubric-credit` (DRACO, arXiv:2609.04094): outcome-blind, динамические рубрики с discriminative dropout, шаговый кредит `Q_j = p_j/(p_j+f_j)`.

**Верификатор / reward.** LLM-судья по рубрике; рубрика должна быть анти-хакерской (защита от эксплуатации судьи) и по возможности динамической.

**Предпосылки (gate).** Есть сильная модель-генератор рубрик и эталоны; рубрика реально **различает** кандидатов (нет дискриминации → нет градиента).

**Типовые отказы.**
- **Взлом судьи / рубрики:** модель выучивает формулировки, которые судья любит, а не качество.
- **Seesaw-effect:** совместное обучение на верифицируемых и открытых данных роняет одну из сторон — лечится двухфазной программой (сначала верифицируемое+статичное, затем открытое+эталонное).
- Статичная рубрика не различает трейсы → нулевой advantage и «обучение ни о чём».

### 2.5 RLVR (RL с верифицируемыми наградами)

**Цель.** Оптимизировать **поведение по проверяемому сигналу**: рассуждения (математика, код), использование инструментов, успех в среде.

**Данные.** Промпты с программной проверкой (exact-match ответа, unit-тесты, результат в среде/песочнице). Фильтр too-easy (модель уже решает → нет градиента), сортировка по сложности, микширование нескольких сред. Рецепт Nemotron 3: RLVR по 21 среде, затем SWE-RL (arXiv:2604.12374).

**Лосс.** Policy gradient с group-relative advantage (GRPO/RLOO/DAPO/PPO). Обязательны: **малая ненулевая KL** к референсу (без KL — коллапс: энтропия → 0; с KL=0.01 — коллапс предотвращается полностью, см. супервизорский `grpo-kl-collapse-prevention`) и **мониторинг энтропии** (падает < 0.1 = mode collapse; здоровая 1.0–2.0).

**Верификатор / reward.** **Детерминированный verifier**: exact-match, unit-тесты, успех в среде. Требование co-location (награда должна считаться рядом с роллаутом; API-грейдеры не тянут по скорости/стоимости — `distillation/rl-vs-distillation`). Кредит на многошаговых траекториях — `credit-assignment/crest-verifier-credit-assignment` (CREST, arXiv:2608.13179): **verifier задаёт направление градиента, self-teacher — только величину**; turn-segmented advantage `A_k(i) = (R_k(i) − mean(R_k))/(std(R_k)+ε)`; entropy-gated `A_t = A_turn[t] × φ_t`.

**Предпосылки (gate).** Verifier стабилен и не флейки; есть SFT-cold-start (RLVR на «сырой» базе не стартует); среды изолированы и воспроизводимы.

**Типовые отказы.**
- **Обвал энтропии / mode collapse** без KL-регуляризации.
- **Gaming verifier:** spurious-reward — модель эксплуатирует дыры проверки, а не решает задачу.
- **Length-bias / overlong:** рост длины как прокси награды; лечится штрафом с бюджетом `P = max(0, L − B_e)/B_e` и маскированием перелимита (`effort/effort-conditioned-rlvr`), без штрафа за неверные ответы.
- **Шум/флейки verifier** (нестабильные тесты) → награда врёт, обучение дрейфует.
- **Регресс других доменов** при обучении на одной среде — нужен мульти-энв микс.
- **Кредит на мультишаге:** trajectory-level reward смазывает вклад шагов (см. CREST/DRACO выше).

### 2.6 Дистилляция (офлайн и онлайн/on-policy)

**Цель.** Перенести способности сильного учителя (или нескольких специалистов) в один студент, снизить стоимость инференса, сжать CoT/effort. Это стадия **консолидации** — ставится последней или межстадийно (Nemotron: MTP healing после RL; Ling 2.6: специалисты → дистилляция).

**Данные и лосс — два режима:**

| Режим | Данные | Лосс | Профиль |
|---|---|---|---|
| **Offline** | трейсы/текст учителя (в т.ч. tool-calls) | CE по трейсам учителя | просто, но off-policy |
| **Online / on-policy** | роллауты **студента**, размеченные учителем | reverse KL(π_θ ‖ π_teacher), **full-vocab логиты** | дороже, но без mismatch |

Online-формула (плагин `effort/effort-opd-consolidation`, OPD-линия DeepSeek V4): `L_OPD(θ) = Σ_i w_i · D_KL(π_θ ‖ π_Ei)`, где reverse KL **mode-seeking** (стягивает студента к модам учителя), а `w_i` — веса маршрутизации prompt → teacher. Ключевая деталь: дистиллировать **полный словарь логитов**, а не преподносить KL как advantage в RL-петле.

**Верификатор / reward.** Собственного verifier нет — сигнал даёт распределение учителя. Поэтому качество ограничено качеством учителя и сохранностью матрицы «домен × режим» (domain × mode matrix).

**Предпосылки (gate).** Учитель сильнее студента на целевой оси; известно, какие режимы/домены нужно сохранить; есть регрессионная матрица (домен × режим) до и после.

**Типовые отказы.**
- Distribution mismatch (offline): студент учится на чужих префиксах, на инференсе — на своих.
- **«Загадка качества учителя»:** прирост не монотонен по силе учителя — более сильный учитель не всегда даёт лучшую дистилляцию (`distillation/teacher-quality-puzzle`).
- Потеря режимов/effort: слияние усредняет моды → «policy mush»; студент теряет редкие профили.
- Слияние нескольких учителей на одной позиции даёт мусор — нужна маршрутизация (w_i), а не наивное усреднение.
- Дистилляция стоит 3 барьеров (масштаб/economics, скорость/co-location, качество/специализированный грейдер) — `distillation/rl-vs-distillation`. Data-free альтернатива консолидации — спектральное слияние (ISO-Merger, arXiv:2607.19331).

## 3. Порядок и зависимости (DAG, а не линейка)

Пользователь часто перечисляет цепочку линейно (CPT → SFT → RLHF → рубрики → RLVR → дистилляция), но на практике это **DAG с зависимостями**:

- **SFT — обязательный cold-start для любой RL-стадии.** RLVR на «сырой» базе не стартует.
- **RLVR обычно идёт ДО RLHF**, а не после: RLVR — основной этап привития способности (проверяемый сигнал, много сред), RLHF — финальная полировка (пример: Nemotron 3, arXiv:2604.12374 — SFT → RLVR → SWE-RL → RLHF). Если пользователь называет линейный порядок с RLHF раньше RLVR — предложи порядок «RLVR → RLHF», но не выдавай его за единственно верный.
- **RL на рубриках** подключается там, где RLVR неприменим (нет проверяемого сигнала), и/или как вторая фаза после верифицируемой фазы (программа «верифицируемое → открытое») для избежания seesaw-effect.
- **Дистилляция** — либо финальная консолидация (специалисты → один студент), либо межстадийный инструмент (сжатие трейсов), либо health-healing шаг. Офлайн-дистилляция по трейсам изоморфна SFT — механизм тот же, отличается источник данных.
- **CPT** ортогонален остальным по объекту (знание) и может идти один раз в начале; периодический CPT на новых корпусах — это и есть «континуальное» обучение в буквальном смысле (дообучение на новом домене без перезапуска пайплайна).

## 4. Диагностика: симптом → стадия → что проверить

| Симптом | Вероятная стадия | Что проверить |
|---|---|---|
| Упали general-бенчмарки, домен вырос | CPT | backward balance: general-доля, LR/WSD, дедуп против бенчмарков |
| Оценка домена подозрительно высокая | CPT | контаминация домен-корпусом бенчмарков |
| Модель называет себя именем учителя / копирует стиль | SFT (или дистилляция) | фильтр трейсов, примесь идентичности |
| Модель плывёт на своих префиксах, а на чужих хороша | SFT / offline-дистилляция | exposure bias → перейти на online/on-policy |
| Reward растёт, качество падает | RLHF / рубрики | reward hacking, bias RM, эксплуатация судьи |
| Энтропия → 0, ответы вырождаются | RLVR | KL к референсу и её коэффициент, мониторинг энтропии |
| Ответы растут в длину без роста качества | RLVR | length-bias, бюджет `B_e`, маскирование перелимита |
| Одна среда улучшилась, другие просели | RLVR | нет мульти-энв микса регрессии |
| Награда «дёргается», обучение нестабильно | RLVR / рубрики | флейки verifier, шумный судья |
| После слияния учителей потерялись профили/режимы | Дистилляция | маршрутизация w_i, матрица «домен × режим», data-free ISO-Merger |
| Дистилляция не дала прироста при более сильном учителе | Дистилляция | «загадка качества учителя» |

## 5. Антипаттерны конвейера

- **Прыжок в RL** без SFT-cold-start или без чистого verifier — деньги на ветер.
- **Одна стадия вместо выбора**: «давай RLHF» там, где нужен CPT/данные; «давай ещё RL» там, где проблема в данных SFT.
- **Лечение деградации следующей стадией** вместо починки сигнала предыдущей (плохой verifier не чинится ещё одним этапом).
- **Односторонняя диета** в CPT (только домен) → забывание.
- **KL=0** в RLVR → гарантированный mode collapse.
- **Наивное слияние учителей** без маршрутизации → mush.
- **Оценка без дедупа** против обучающего корпуса → завышенный результат.
- **Игнор матрицы «домен × режим»** при дистилляции → потеря профилей.
