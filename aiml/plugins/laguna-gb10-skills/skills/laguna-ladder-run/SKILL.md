# Лесенка Laguna на GB10

Лесенка — последовательность стадий для одной модели и seed'а:
`CPT → eval_base → eval_cpt → SFT → eval_sft → RL → eval_rl`. Прогон
называется `v<N>_<model>_s<seed>` (например `v12_qwen25-15b_s42`) и живёт в
`~/experiments/<run>/{logs,checkpoints,rollouts_log.jsonl}`. Главное, что
показал опыт v12: **на GB10 падения — норма, а не авария**. Прогон 1.5B
пережил 3 неудачные попытки CPT, 6 попыток SFT и 4 рестарта RL и всё равно
закрылся без участия человека — только благодаря авторезюму. Поэтому
инфраструктура здесь часть метода, а не фон.

## 0. Первым делом — статус, а не действия

Прежде чем что-то запускать/чинить, собери картину скриптом:

```bash
python3 scripts/run_status.py ~/experiments/<run> \
  --status-log ~/experiments/v12_ladder_status.log \
  --restart-log ~/gb10-shared/v12_restart.log
```

Скрипт выдаёт: какая стадия сейчас, последний чекпоинт и его шаг, сколько
рестартов и с какими rc, полнота набора артефактов, есть ли признаки
«зависания» (чекпоинт не обновлялся дольше ожидаемого интервала). Если
скрипт не находит файлов — сначала спроси у пользователя реальные пути
(имена файлов ниже — типовые для v12, у другой версии могли поменяться).

Читай статус-логи, а не только `nvidia-smi`: на UMA занятая память не
говорит о том, живой ли процесс.

## 1. Конфигурация, которая доехала (1.5B, seed 42)

| Параметр | Значение | Зачем |
|---|---|---|
| batch | 1 | единственный вариант при max_len=8192 на 128 ГБ UMA с vLLM рядом |
| max_len | 8192 | длина траекторий с tool-call'ами (RL-ответы 2.5–4k токенов) |
| vLLM gpu util | 0.32 (KV-кэш фикс. 8 ГиБ) | оставить память тренеру |
| LAGUNA_MEM_FRACTION | 0.6 | доля памяти под тренер; выше — rc=137 |
| attention | flex-attention + документное маскирование на CPT | |
| расписание | WSD, peak×0.7 | анти-форгеттинг; хвост lr до ~2e-7 |
| CPT | 4888 шагов на корпусе концепт-карточек | |
| SFT | 3 эпохи (134 847 шагов) | основной прирост качества — здесь |
| RL | GRPO, 500 шагов, группы 4 задачи × 2 роллаута | «полировка», не рост |
| судья | внешний API (GLM-5.3-flash) | флапает — см. ood-stage-eval |

Полные детали и как масштабировать на 3B — `references/gb10-config.md`.
Не меняй несколько параметров сразу: если после правки CPT снова даёт
rc=137, откатывай к этой таблице, а не крути дальше.

## 2. Падения: симптом → причина → действие

| Симптом | Причина | Действие |
|---|---|---|
| rc=137 на CPT/SFT | OOM (UMA: тренер + vLLM + кэши) | RESUME с чекпоинта; если повтор ≥3 — снизить MEM_FRACTION/util, проверить утечку через `references/failure-modes.md` |
| rc=1 на RL, в хвосте лога NVRM/driver | драйвер на UMA под долгой нагрузкой | RESUME с `rl_checkpoint_N.pt`; ничего в конфиге не менять |
| после падения бокс «не отпускает» часами | застрявшие контейнеры, сборка памяти | убить контейнеры прогона, дождаться освобождения памяти, только потом рестарт; watchdog `*/15` сводит простой к минутам |
| стадия помечена DONE, но артефактов не хватает | старый баг «DONE при неполном проходе» (фикс от 12.09.2026) | судить о завершении ТОЛЬКО по полному набору артефактов (§3), не по слову DONE |
| loss-кривая SFT «скачет назад» | несколько лёгов пишут в один файл до ротации | рисовать кривую по последнему лёгу (с шага резюма) |
| чекпоинт не обновляется > 2× ожидаемого интервала | завис, а не медленно | смотреть последние строки лога стадии, затем watchdog-цикл |

Правило: каждый рестарт — с последнего чекпоинта стадии. Если чекпоинт
битый (не грузится), брать предыдущий и явно записать потерю шагов в
статус-лог.

## 3. Что считать завершённым прогоном

Стадия закрыта, когда есть ВСЕ её артефакты:

- CPT: `checkpoint_final.pt` + `eval_results_base.json` + `eval_results_cpt.json`
- SFT: `sft_checkpoint_final.pt` + `eval_results_sft.json`
- RL: `rl_checkpoint_final.pt` + `eval_results.json` + `rollouts_log.jsonl`
  до последнего шага (500/500 или сколько задано)

Чекпоинты 1.5B весят ~9.26 ГБ каждый — следи за диском перед RL.
После закрытия прогона запусти интерпретацию: скиллы `ood-stage-eval`,
`cpt-template-check`, `rl-health-check`, затем `ladder-interpretation-report`.

## 4. Добавление модели / нового шага лесенки

1. Скопировать конфиг ближайшей по размеру модели (1.5B → 3B: смотри
   `references/gb10-config.md`, раздел «масштабирование»).
2. Сначала прогнать eval_base — база может быть сильной (qwen25-3b: 39/100 на
   OOD, лучше, чем 1.5B после всей лесенки). Сильную базу CPT может обвалить
   (3B: 39 → 2), поэтому решение о дозе CPT принимать ПОСЛЕ eval_base.
3. Включить watchdog до старта, а не после первого падения.
4. Записать в `v<N>_ladder_status.log` старт стадии с параметрами — по этому
   логу потом восстанавливаются точки крахов.

## 5. Что сообщать пользователю

Коротко: стадия, шаг/из, последний чекпоинт и его возраст, число рестартов
с rc, оценка оставшегося времени (по скорости шагов последнего лёга — RL
1.5B: ~40 шагов/3 ч на финальном леге), и один следующий шаг. Не
пересказывай логи целиком.
