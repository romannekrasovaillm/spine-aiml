# Режимы отказа лесенки на GB10 и восстановление

Порядок разбора любого падения: (1) rc и последние 50 строк лога стадии,
(2) возраст и целостность последнего чекпоинта, (3) память/контейнеры,
(4) только потом гипотезы про конфиг.

## rc=137 — SIGKILL, почти всегда OOM

Статистика v12: 3 из 3 неудачных попыток CPT и большинство из 6 попыток
SFT. Проверка:
```bash
dmesg -T | grep -iE 'killed process|out of memory' | tail
grep -n 'rc=137' ~/gb10-shared/v*_restart.log | tail
```
Решения по возрастанию агрессивности:
1. RESUME без изменений (падение могло прийтись на скачок на границе стадий).
2. Повтор ≥2 раза на одном и том же шаге → снизить LAGUNA_MEM_FRACTION на
   0.05 ИЛИ vLLM util на 0.05 (не оба).
3. Повтор на растущих шагах → утечка: логировать RSS раз в N шагов, искать
   накопление (кэш роллаутов, незакрытые tool_response, history в памяти).
4. max_len — последнее, что трогать: снижает качество траекторий с
   tool-call'ами.

## rc=1 с NVRM/driver в хвосте — RL на UMA

Все 4 рестарта RL v12. Конфиг не виноват; лечится RESUME. Если после
рестарта сразу снова rc=1 — драйвер не отпустил: убить контейнеры,
подождать, проверить `nvidia-smi` на «зависшие» процессы; в крайнем случае
перезагрузка бокса (потеря только времени, чекпоинты целы).

## Бокс не разблокируется часами

В v12 дважды: ~5 ч и ~3 ч простоя. Признаки: процесс мёртв, память не
освобождается, новый запуск не стартует. Последовательность: `docker ps -a`
→ остановить/удалить контейнеры прогона → дождаться падения занятой памяти
→ рестарт. Watchdog делает это автоматически; если он стоит, а простой
растёт — смотри его лог, вероятно, он ждёт освобождения памяти и не может
дождаться.

## Ложный DONE

До фикса 12.09.2026 стадия могла получить статус DONE при неполном проходе
(например, при обрыве эвалюации). Правило: завершение = полный набор
артефактов стадии (см. SKILL.md §3). При чтении старых статус-логов (до
12.09) DONE — гипотеза, не факт.

## Битый чекпоинт

Симптом: RESUME падает при загрузке state_dict. Взять предыдущий
`*_checkpoint_N.pt`, записать в статус-лог «потеряно шагов: N_final − N».
Никогда не удалять предпоследний чекпоинт до успешной загрузки следующего.

## Судья недоступен во время eval

Эвалюация завершается, но все вердикты `API_DOWN` (v12: BASE и SFT, 100/100).
Это не падение прогона — стадия закрыта, slug-метрика валидна. Ре-суд —
задача скилла `ood-stage-eval`, не перезапуск стадии.

## Несколько лёгов в одном loss-файле

Ранние попытки SFT писали в тот же файл до ротации. Для графиков брать
последний лег (в v12 — с шага 23 801). Ставь ротацию лога при каждом
RESUME, чтобы это не повторялось.
