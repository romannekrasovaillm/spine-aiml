# Конфигурация лесенки на GB10 (DGX Spark)

Железо: NVIDIA GB10, единая память CPU+GPU (UMA, ~128 ГБ). Это меняет
привычную логику: нет отдельной «памяти GPU», тренер, vLLM для роллаутов,
KV-кэш и системные буферы конкурируют за один пул. OOM приходит как rc=137
(kill процесса), а не как CUDA OOM внутри Python.

## Проверенный набор v12 (Qwen2.5-1.5B, seed 42)

```
batch=1
max_len=8192
vllm_gpu_memory_utilization=0.32      # KV-кэш фиксирован ~8 ГиБ
LAGUNA_MEM_FRACTION=0.6               # доля пула под тренер
attention=flex                         # + документное маскирование на CPT
schedule=WSD peak*0.7                  # хвост lr доходит до ~2e-7
cpt_steps=4888
sft_epochs=3                           # 134 847 шагов
rl_steps=500 ; rl_group=4x2            # 4 задачи x 2 роллаута = 8 роллаутов/шаг
judge=GLM-5.3-flash (внешний API)
ood_set=eval_ood_oxalpha (100 задач)
```

Хронология v12 (для оценки времени): CPT ~18 ч чистого времени (с 3
неудачными попытками до этого), SFT ~6 суток (с 6 попытками), RL ~2 суток с
4 рестартами, каждая OOD-эвалюация 20–100 мин (дольше — когда судья ждёт
API). Финальный лег RL: шаги 460→500 за 3 ч.

## Память: где она уходит

- Тренер (веса + оптимизатор + активации при 8192): основной потребитель.
  LAGUNA_MEM_FRACTION ограничивает именно его.
- vLLM: util 0.32 — это доля от общего пула, а не «от GPU»; поднять util =
  отнять у тренера.
- Дискретные скачки на границах стадий (выгрузка тренера, загрузка vLLM) —
  самые опасные моменты; часть rc=137 v12 пришлась именно на них.
- Сборка памяти после kill'а может занимать часы, если остались контейнеры.

## Масштабирование на 3B

- Веса и оптимизатор ~2×: оставить batch=1, max_len=8192; понизить
  MEM_FRACTION до 0.5–0.55 или util vLLM до 0.25 — по одному параметру за
  итерацию, наблюдая rc.
- Чекпоинты ~2× тяжелее (1.5B: 9.26 ГБ) — проверить диск на 3 финальных +
  промежуточные.
- База 3B сильная (39/100 на OOD против 2/100 у 1.5B); CPT в дозе 1.5B
  обвалил её до 2/100. Рекомендации по дозе — в скилле `cpt-template-check`.
- SFT для 3B по факту v12 — ~45k шагов на эпоху; RL-бюджет тот же 500×(4×2)
  как отправная точка.

## Watchdog

Cron `*/15`: проверяет живость процесса стадии и возраст последнего
чекпоинта; при падении — убивает остатки контейнеров, ждёт освобождения
памяти, запускает RESUME с последнего чекпоинта, пишет строку в
`~/gb10-shared/v<N>_restart.log` (время, стадия, rc, чекпоинт). Без
watchdog простой после падения составлял 3–5 ч (ручная разблокировка), с
ним — минуты.

Не ставь watchdog чаще `*/5`: проверка на UMA сама создаёт нагрузку, а
чекпоинты пишутся дольше 5 минут.
