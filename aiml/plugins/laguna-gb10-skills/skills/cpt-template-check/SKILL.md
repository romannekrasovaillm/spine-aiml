# Проверка CPT на template domination

## Что это и почему возникает

LM-цель CPT учит распределение корпуса, а не решение задачи. Если корпус
перекошен (в v12 разбор пары `grpo` / `advantage_estimation` — самая
частая траектория), то при слабом сигнале входа (в промпте нет явного
формата задачи) автодополнение опирается на макростатистику корпуса:
доля шаблона в корпусе много больше доли любой конкретной пары концептов,
и шаблон побеждает. Модель *выглядит* обученной (ppl_domain 3.6, ответы
оформлены, вызывает инструмент), но подставляет чужие сущности.

Проявления v12:
- 1.5B после CPT: slug 3/100 при «правильном виде» ответов; шаблон «The
  user asks me to explain the connection between 'grpo' and
  'advantage_estimation'…» в задачах #17, #19, #52 с совсем другими
  ожидаемыми концептами.
- SFT чинит частично: подставляет верные имена в тот же шаблон, но
  остаются утечки (#50 после SFT).
- 3B: база 39/100 → после CPT 2/100. **Чем сильнее база, тем дороже CPT.**
- Побочно: язык рассуждений сдвинулся на английский (корпус английский).

## 1. Диагностика — три числа

```bash
python3 scripts/template_dominance.py eval_results_cpt.json \
    [--base eval_results_base.json] [--corpus corpus.jsonl --corpus-field text] \
    [--ngram 6] [--top 10]
```

Скрипт выдаёт:
1. **input attribution** — доля ответов, в которых упомянут хотя бы один
   из запрошенных концептов (и доля с обоими). Здоровая модель: близко к
   1.0 даже при неверном ответе. У CPT v12 — низко: вход игнорируется.
2. **dominant template** — самые частые n-граммы по началам ответов и
   доля ответов, начинающихся с топ-1 шаблона. >20% ответов с одним
   началом при 100 разных задачах — патология.
3. **leak rate** — доля ответов, где присутствуют сущности из
   доминирующего шаблона, не входящие в ожидаемые (по умолчанию
   `grpo`, `advantage_estimation`; задай свои `--leak`).
4. **language drift** — доля латиницы/кириллицы в рассуждениях по сравнению
   с базой (если задан `--base`).
5. Если задан корпус — частота тех же n-грамм/сущностей в корпусе: это
   доказывает, что шаблон пришёл из данных.

Сравнивай с базой: у BASE-1.5B attribution низкий из-за дегенерации
(другая причина), у BASE-3B — высокий; падение attribution 3B после CPT —
прямая мера ущерба.

## 2. Решение — принимать по трём фактам

| Факт | Решение |
|---|---|
| eval_base сильный (≥ 30/100) | CPT в текущей дозе НЕ запускать; сначала аблация: 0 / ¼ / ½ шагов |
| attribution после CPT < 0.5 при базе > 0.7 | корпус перекошен — чинить данные (§3), не промпт |
| leak rate у SFT > 5% | доза CPT слишком велика ИЛИ SFT-набор мал; сначала проверить корпус |

Порядок проверки «вылечит ли SFT»: после SFT считать attribution и leak
rate заново; если leak > 0 — фиксировать список задач с утечками в отчёте.

## 3. Меры против template domination (в порядке эффективности)

1. **Данные** — перебалансировать корпус: ограничить долю любой одной
   пары/темы (напр. ≤ 2% траекторий), дедуп шаблонных начал, разнообразие
   формулировок постановки задачи (RU/EN, разные обёртки).
2. **Replay** — примешивать в CPT базовые инструкции/диалоги (5–15%) для
   удержания способности «читать вход»; это же сдерживает language drift.
3. **Доза** — меньше шагов CPT для сильных баз; WSD с peak×0.7 уже
   применяется (анти-форгеттинг), но не спасает от перекоса данных.
4. **Маскирование** — документное маскирование (уже есть); не маскировать
   постановку задачи так, чтобы модель её «не видела».
5. **Автоиндикатор** — включить input attribution в eval-цикл лесенки как
   сигнал остановки: после CPT attribution упал ниже базы на > 0.2 → стоп,
   не идти в SFT вслепую.

## 4. Как оформить в отчёте

Три живых примера с одинаковым шаблоном при разных ожидаемых концептах
(`ood-stage-eval/scripts/extract_examples.py --pick leaks`), таблица
attribution/leak по стадиям, вывод: «CPT навязывает корпусной шаблон,
SFT учит подставлять в него реальный вход». Обязательно — контраст с
соседней моделью по лесенке, если он есть.
