# Интерпретация эксперимента <run>

*Полный цикл CPT → SFT → RL на <железо> и OOD-оценка: как <модель> прошла
путь <было> → <стало> попаданий из <n>, почему так получилось и что из
этого следует для лесенки <vN>.*

Дата отчёта: <дд.мм.гггг> · прогон: <дд.мм–дд.мм.гггг> · артефакты:
<путь> · судья: <модель> · OOD-набор: <имя> (<n> задач)

# 1. Резюме (главное)

*5–7 абзацев, каждый — одна мысль с числами:*
1. Прогон завершён/не завершён; стадии и объёмы; сколько падений и как
   восстановились (участие человека — да/нет).
2. OOD-качество по стадиям: `A → B → C → D`, кратность к базе.
3. Кто сделал основной скачок и почему (одна фраза механизма).
4. Здоровье RL: энтропия, KL, clip, ppl_general — есть ли забывание.
5. Найденная патология (если есть): что, где, чинит ли следующая стадия.
6. Контраст с соседней моделью/seed'ом и главный риск.

# 2. Конфигурация и хронология

Параметры: модель, seed, batch, max_len, vLLM util, MEM_FRACTION,
attention, расписание, шаги CPT/эпохи SFT/шаги RL, группа GRPO, судья.

*Таблица 1. Стадии прогона.* Колонки: Стадия | Интервал (время бокса) |
Объём | Артефакт. Паузы внутри интервалов — краши и рестарты (рис. 1).

*Рис. 1. Хронология:* горизонтальная шкала, зелёные отрезки — успешные
леги, красные ✕ — падения с rc; подпись — откуда резюмились.

# 3. Результаты OOD

Определить метрики (slug_accuracy — основная, локальная; judge — 0–1,
только где валиден). Явно назвать стадии с сорванным судейством.

*Таблица 2. OOD-метрики по стадиям (n=<n>).* Стадия | slug-попаданий |
judge (валид.) | Вердикты.

*Рис. 2.* слева попадания по стадиям с усами 95% ДИ; справа judge там,
где отработал. *Рис. 3.* распределение вердиктов (стек), включая
соседнюю модель, если есть.

Абзацы со статистикой по переходам: «переходов мимо→попал N против M
обратных, p = …» — для каждого перехода; вывод «значимо / статистический
ноль / различие в качестве, не в попаданиях».

# 4. Живые примеры «до/после»

2–4 задачи. Для каждой: `**Пример k (задача #id): <что произошло в одной
фразе>**`, курсивом ожидаемые slug'и, затем по стадии:
`[СТАДИЯ] ✅/❌ · ВЕРДИКТ (пометка «судья упал» при API_DOWN) · score=… —
<ответ, ≤300 симв., переносы заменены на " · ">`.

После примеров — абзац про общий феномен (напр. шаблон CPT) и абзац с
примером RL-роллаута (модель сама вызывает инструмент). Контраст с
соседней моделью — отдельным абзацем.

# 5. Динамика обучения (и здоровье контура)

*Рис. 4. RL:* награда, pass-rate, длина, tool-calls, энтропия, clip по
шагам. *Рис. 5. CPT/SFT:* loss (по последнему легу; оговорить ротацию).

*Таблица 3. Сводка по RL.* Метрика | Значение | Комментарий (награда,
pass-rate, энтропия, KL, clip, ppl_general, ppl_domain).

Абзац «Надёжность»: рестарты по стадиям, rc, простои, откуда стартовал
финальный лег, «нетто-прогресс сохранён/потерян».

# 6. Почему так получилось: причинно-следственная реконструкция

6.1 Почему BASE дала <x>. *(механизм отказа: дегенерация/нет формата)*
6.2 Что сделал CPT. *(домен выучен: ppl_domain; но LM-цель ≠ задача;
    шаблон корпуса; language drift)*
6.3 Почему SFT дал скачок. *(поведенческое копирование: привязка к входу,
    tool-call, формат; остаточные дефекты)*
6.4 Почему RL добавил так. *(профиль: полировка/рост; бюджет группы и
    шагов; что ограничивает)*
6.5 Инфраструктурная причинность. *(без авторезюма результат был бы…)*
6.6 Сравнение с соседом по лесенке. *(прогноз и главный риск)*

# 7. Ограничения измерений

Список: судья (какие стадии невалидны), n и ширина ДИ, точность точек
крахов, единственность OD-набора (внутренний тест, не бенчмарк),
особенности loss-логов, что не измерено.

# 8. Выводы и что делать дальше

Упорядоченно, с приоритетом №1 первым; каждый пункт — действие с
параметрами: рецепт подтверждён/нет; меры против патологии (данные,
replay, доза); RL-бюджет; метрическая гигиена (судья); приоритетная
модель; инфраструктура.
