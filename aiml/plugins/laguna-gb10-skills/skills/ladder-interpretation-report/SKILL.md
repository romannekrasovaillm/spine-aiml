# Интерпретационный отчёт по прогону лесенки

Цель отчёта — не пересказать логи, а объяснить **почему** получились
такие числа и **что из этого следует** для следующих шагов лесенки.
Читатель — коллега, который принимает решение о конфиге следующего
прогона; он читает резюме и выводы, остальное — по необходимости.

## 0. Сначала данные, потом текст

Перед написанием получи (или запроси у пользователя) результаты трёх
скиллов-анализаторов — иначе отчёт будет умозрительным:

1. `ood-stage-eval`: `stage_compare.py --md`, `judge_health.py`,
   `extract_examples.py` (2–4 примера).
2. `cpt-template-check`: attribution / leak / доминирующий шаблон.
3. `rl-health-check`: таблица RL-метрик и профиль.
4. `laguna-ladder-run/run_status.py`: хронология, рестарты, полнота
   артефактов.

Если чего-то нет — пиши раздел с пометкой «не измерено», не додумывай.

## 1. Структура (обязательная)

Полный шаблон с подсказками по каждому разделу —
`references/report-template.md`. Кратко:

```
Заголовок: Интерпретация эксперимента <run>
Подзаголовок-курсив: одна фраза, что произошло (цифры «было → стало»)
Шапка: дата · интервал прогона · путь к артефактам · судья · OOD-набор
1. Резюме (главное)          — 5–7 абзацев, все ключевые числа
2. Конфигурация и хронология — таблица стадий + рис. хронологии с падениями
3. Результаты OOD            — таблица метрик, ДИ, МакНемар по переходам
4. Живые примеры «до/после»  — 2–4 задачи, все стадии, ✅/❌, вердикт, score
5. Динамика обучения         — loss CPT/SFT, RL-таблица, надёжность
6. Причинно-следственная реконструкция — по подразделу на стадию + инфраструктура + контраст с соседней моделью
7. Ограничения измерений
8. Выводы и что делать дальше
Приложение: артефакты и воспроизводимость
```

## 2. Принципы формулировок

- **Числа в паре «было → стало» и кратно**: «2 → 24, ×12», не «значительно».
- **Каждый скачок — с атрибуцией стадии**: «основной скачок сделал SFT
  (+19), RL добавил +2 (в шуме) и +8 PARTIAL».
- **Статистика рядом с числом**: p МакНемара и переходы там, где разница
  мала; ДИ при n=100 — ±4–8 п.п.
- **Невалидное — не ноль**: судья `API_DOWN` → «н/д», и это отдельная
  строка в ограничениях.
- **Причинность формулировать механизмом**: не «CPT не помог», а «LM-цель
  учит распределение корпуса; самый частый шаблон стал дефолтом при
  слабом сигнале входа».
- **Инфраструктура — часть метода**: сколько падений, сколько восстановлено
  авторезюмом, сколько потеряно бы без него.
- **Контраст с соседом по лесенке** (другая модель/seed) — обязателен, если
  есть: он превращает наблюдение в прогноз.
- Выводы — упорядоченный список действий с приоритетом №1 наверху.

## 3. Формат вывода

- По умолчанию — Markdown-файл (`report_<run>.md`) + отдельный каталог
  `data/` с CSV/JSON, из которых построены таблицы, и `scripts/`
  (extract_examples.py, agg_rollouts.py, build_report.py) — чтобы отчёт
  был воспроизводим.
- Если просят Word — читай `/mnt/skills/public/docx/SKILL.md`; в стиле
  ДКА — `dka-report-docx`. Рисунки (хронология, динамика попаданий с
  усами ДИ, распределение вердиктов, RL-кривые, loss) — matplotlib, PNG
  ≥ 150 dpi, подпись «Рис. N.» курсивом под рисунком, таблицы — «Таблица N.»
  над таблицей.
- Имя файла: `Отчёт_<vN>_<model>_<seed>_<стадии>_<тема>_<дд-мм-гггг>.docx`.

## 4. Чек-лист перед сдачей

- [ ] В резюме есть все числа из таблиц 2 и 3 (читатель может не листать дальше).
- [ ] У каждой невалидной метрики стоит «н/д» и причина.
- [ ] Каждый пример «до/после» помечен стадиями и вердиктами.
- [ ] В §6 есть подраздел про инфраструктуру и про соседнюю модель.
- [ ] §8 начинается с приоритета №1 и содержит конкретные параметры (шаги, группа, replay), а не «улучшить».
- [ ] Приложение содержит пути ко всем артефактам и команду быстрой проверки примеров.
