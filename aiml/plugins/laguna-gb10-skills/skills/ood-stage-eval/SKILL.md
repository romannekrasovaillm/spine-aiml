# OOD-оценка стадий лесенки

Задача OOD-набора: по паре концептов найти в библиотеке две точные
сущности (slug'и) и объяснить связь. Две метрики:

- **slug_accuracy** — доля задач, где в ответе есть ОБА ожидаемых slug'а.
  Считается локально, не зависит от внешних сервисов. **Основная метрика.**
- **judge** — балл LLM-судьи 0–1 + вердикт. Зависит от внешнего API и в
  v12 у двух стадий из четырёх был сорван (100/100 `API_DOWN`). Ноль от
  упавшего судьи — артефакт, не «нулевое качество».

Правило номер один: **сначала проверь судью, потом сравнивай стадии.**

## 1. Порядок работы

```bash
# 1. здоровье судьи по каждому файлу
python3 scripts/judge_health.py eval_results_base.json eval_results_cpt.json \
    eval_results_sft.json eval_results.json
# 2. сравнение стадий: попадания, ДИ, МакНемар, вердикты
python3 scripts/stage_compare.py \
    BASE=eval_results_base.json CPT=eval_results_cpt.json \
    SFT=eval_results_sft.json RL=eval_results.json [--md]
# 3. примеры до/после (только по задачам с переходами)
python3 scripts/extract_examples.py --stages BASE=... CPT=... SFT=... RL=... \
    --pick transitions --n 3 --maxlen 300
```

Скрипты угадывают поля (`expected_slugs`/`slugs`, `answer`/`response`/
`output`, `verdict`, `score`) — если структура другая, задай `--field`
или посмотри `--inspect`. Не пиши свой парсер, пока не посмотрел, что
скрипты выдали на `--inspect`.

## 2. Как читать результаты (уроки v12, 1.5B)

| Переход | Попадания | Что говорит статистика | Интерпретация |
|---|---|---|---|
| BASE→CPT | 2→3 | p=1.0, переходы 3 vs 2 | CPT задачу не выучил; выучил домен и оформление |
| BASE→SFT | 2→22 | p≈1e-5, 21 vs 1 | главный скачок — поведенческое копирование |
| SFT→RL | 22→24 | p=0.80, 9 vs 7 | по попаданиям неразличимы; RL — в качестве (judge 0.045→0.104, PARTIAL 1→9) |

Выводы, которые из этого следуют всегда:
- При n=100 95% ДИ ≈ ±4–8 п.п.; разницу < 8 попаданий не называй ростом
  без теста. Разницу в 10× — можно.
- Сравнивать judge можно только между стадиями с валидным судейством
  (в v12 — только CPT vs RL). Остальное — «н/д», не 0.
- Судья и slug измеряют разное: slug — «нашёл ли», judge — «объяснил ли».
  RL типично двигает второе.
- Переходы «попал→мимо» тоже важны: если их много при росте общей суммы —
  модель нестабильна, а не лучше.

## 3. Живые примеры — обязательная часть анализа

Числа не показывают механику. Для отчёта выбирай 2–4 задачи с
характерными переходами и показывай ответ каждой стадии (обрезанный до
~300 символов), с меткой ✅/❌, вердиктом и score. Хорошие кандидаты:
- «дегенерация → рабочий tool-call» (BASE циклится «#aa#aa…», RL вызывает
  `search_concepts`);
- «галлюцинация → шаблон CPT → верная пара slug'ов» (виден template
  domination, см. `cpt-template-check`);
- задачи, где RL дал PARTIAL при тех же slug'ах, что SFT — иллюстрация
  «RL полирует, а не учит».

Всегда помечай, если у стадии судья был `API_DOWN` — иначе читатель
примет score=0.0 за оценку.

## 4. Гигиена судьи

- Смотри долю `API_DOWN`/`ERROR` по файлу: >5% — судейство файла
  невалидно целиком (нельзя усреднять по выжившим — смещение).
- Ре-суд: повторить только судейство (ответы уже есть в файле), с
  ретраями и бэкоффом; при повторном флапе — альтернативная модель или
  локальный судья, и это фиксируется в отчёте как смена судьи (баллы двух
  судей не сравнимы напрямую).
- В финальных таблицах: slug — основная колонка, judge — только там, где
  валиден, иначе «н/д (API_DOWN)».

## 5. Что НЕ делать

- Не усреднять score по стадии, где часть вердиктов сорвана.
- Не объявлять SFT→RL «ростом» по +2 попаданиям.
- Не сравнивать прогоны на разных OOD-наборах или разных судьях.
- Не считать OOD-набор внешним бенчмарком: это внутренний тест рецепта
  на одном распределении (100 пар концептов); формулировки «модель
  стала лучше» ограничены этим распределением.
