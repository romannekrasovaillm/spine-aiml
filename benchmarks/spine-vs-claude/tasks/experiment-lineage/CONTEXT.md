# Контекст: происхождение экспериментов (текущее состояние)

Корпус предметной области. Одинаков для всех рук бенчмарка.

## Ландшафт «как есть»

- **Трекер экспериментов** — MLflow (self-hosted), 4 исследователя, ~600
  запусков в месяц. Логируются параметры, метрики и артефакты ноутбука.
- **Реестр моделей** — каталог `models/` в S3-совместимом хранилище, объект
  называется `<название>_<дата>.bin`, метаданных нет.
- **Датасеты** — версии в объектном хранилище, идентифицируются по дате
  выгрузки; манифесты хранятся рядом с ноутбуками, не в трекере.
- **Обучение** — скрипты `train_*.py`, запускаемые вручную; результат
  складывается в `models/`.
- **Прод** — сервис инференса читает модель по имени файла из конфигурации.

## Боли

1. Инцидент с деградацией модели: два дня ушло на выяснение, на каком срезе
   данных она обучена; ответ восстановили по переписке в мессенджере.
2. Аудит внутренний: требуется по запросу назвать источник каждой продовой
   модели за последние 6 месяцев — сейчас это ручная работа.
3. Дважды в прод попадала модель из незавершённого эксперимента.
4. Метрики трекера и фактические метрики на проде расходятся: неясно, какой
   запуск породил артефакт.

## Ограничения среды

- Команда: 4 исследователя + 1 платформенный инженер.
- Трекер менять на другой нельзя (инвестиция в MLflow, миграция не
  рассматривается).
- Ноутбуки остаются основным инструментом исследователя: требование
  «писать в трекер» не должно ломать привычный цикл.
- Горизонт: решение должно работать при 600 запусках/месяц и росте ×3.
- Нормативные рамки (справочно, не предмет задачи): внутренний регламент
  воспроизводимости экспериментов; срок хранения метаданных — 3 года.

## Словарь

- **Lineage (происхождение)** — машинно-читаемая цепочка
  «датасет → запуск → артефакт → продовая модель».
- **Run id** — идентификатор запуска в трекере.
- **Срез данных** — версия датасета, использованная в запуске.
