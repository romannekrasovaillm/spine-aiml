# Контекст: реестр моделей (текущее состояние)

Корпус предметной области. Одинаков для всех рук бенчмарка.

## Ландшафт «как есть»

- **Реестр** — самописный сервис (Python + PostgreSQL), 4 года в проде:
  таблицы `models`, `versions`, `deployments`; артефакты — файлы на локальном
  томе того же узла, путь в колонке `path`.
- **Объём**: 380 моделей, 1240 версий, 30 моделей в проде.
- **Инференс** читает модель по `model_id` → `path` из реестра; горячей
  перезагрузки нет, смена версии — рестарт пода (40–90 с).
- **Аутентификация** — общий сервисный токен; журнала обращений к моделям нет.
- **Схема** менялась аддитивно; есть колонки, не используемые с 2024 года, и
  3 разных способа указать фреймворк.

## Боли

1. Диск узла реестра заполняется: 2 инцидента за полгода, ручная чистка.
2. Нет связи «версия → кто и когда деплоил»: разбор инцидента — по логам
   сервиса, которые ротируются за 14 дней.
3. Откат версии — рестарт пода, 40–90 с простоя; при инциденте это долго.
4. Схема не даёт машинно ответить, какие версии допустимы к выкату.

## Ограничения среды

- Остановка инференса на время миграции недопустима: SLA доступности 99.5%,
  p99 ≤ 200 мс.
- Двойная запись рассматривается только как временный механизм с явно
  названным сроком снятия.
- Целевое хранилище артефактов — объектное (S3-совместимое); каталог
  метаданных — на выбор архитектора.
- Легаси-колонки удаляются только после подтверждённого отказа от них.
- Нормативные рамки (справочно, не предмет задачи): политика хранения
  артефактов моделей — 12 месяцев; внутренний регламент смены продовых
  компонентов требует плана отката.

## Словарь

- **Указатель (pointer)** — запись «какая версия обслуживает прод», отделённая
  от самого артефакта.
- **Обратимость** — возможность вернуться к предыдущему состоянию за
  ограниченное время без потери артефактов.
- **Фаза миграции** — ограниченный этап с явными критериями перехода.
