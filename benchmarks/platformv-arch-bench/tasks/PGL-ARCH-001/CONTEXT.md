## 1. Продукт: Platform V Pangolin DB `[DOC]`

### 1.1 Что это

- Реляционная СУБД промышленного уровня, **специальная сборка PostgreSQL** с
  доработками под повышенные требования к безопасности, производительности,
  надёжности и удобству эксплуатации. Производитель заявляет более 80 доработок
  относительно ванильного PostgreSQL.
- Позиционируется как замена Oracle Database, MS SQL, IBM DB2, MySQL и
  ванильного PostgreSQL.
- Продукт включён в Единый реестр российского ПО (запись №13436 от 29.04.2022)
  и прошёл сертификацию ФСТЭК; сертификат продлён до 2028 года, ранее продукт
  был сертифицирован по 4-му уровню доверия.
- Актуальная документированная версия на дату снимка — **8.2.0**; поддерживаются
  линейки документации Pangolin 8, 7, 6, 5.
- Редакции и альтернативные наименования: Standard / Enterprise, Certified
  (сертифицированная ФСТЭК сборка), варианты «для ERP-систем»; исторически
  продукт также назывался Platform V Pangolin SE.

### 1.2 Состав дистрибутива (компоненты)

| Компонент (пакет) | Назначение |
|---|---|
| `pangolin-dbms` | Сервер СУБД (серверная часть) и клиентская часть (`libpq`, `client`) |
| `Pangolin Manager` (`pangolin-manager`) | Оркестратор кластера, разработан на базе Patroni. Превращает два и более узла в высокодоступный кластер с потоковой репликацией, поддерживает контролируемое (switchover) и аварийное (failover) переключение, автоматизирует добавление/обновление/удаление реплик и одновременное изменение конфигурации на всех узлах |
| `Pangolin DCS` | Собственная реализация распределённого хранилища конфигурации (DCS), входит в состав Pangolin Manager и **может заменить etcd**. Устойчив к дисковым сбоям: операции с диском вынесены в отдельный поток, при недоступности диска сам DCS продолжает работать из памяти. Управляется через `pangolin-manager-ctl` / `pangolin-dcs-ctl` |
| `etcd` | Альтернативный DCS; ставится из стандартных репозиториев ОС; компонент **не поддерживается командой разработки Pangolin** (сторонний) |
| `Pangolin Pooler` (`pangolin-pooler`) | Пул соединений, доработанный PgBouncer. В описании продукта упоминается резервирование соединений для непривилегированных пользователей при высокой нагрузке |
| `Pangolin Backup Tools` (`pangolin-backup-tools`) | Набор утилит для создания резервных копий БД |
| `pangolin-certs-rotate` | Утилита ротации сертификатов (PKCS#12) |
| `pangolin-auth-reencrypt` | Утилита восстановления работоспособности узла кластера при смене параметров сервера (перешифрование) |
| `pangolin-security-utilities` | Набор утилит настройки средств защиты информации (СЗИ) |
| `pangolin-diagnostic-tool` | Утилиты сбора диагностической информации о СУБД |
| `pangolin-docs` | Документация продукта |
| Мета-пакеты `pangolin-full*` | Упрощают пошаговую установку полного набора компонентов |
| Папка `3rdparty` | ПО с «вирусными» лицензиями: `pangolin-citus` (распределённая БД), `pg_background` (фоновое выполнение команд), утилиты миграции `ora2pg` и `pangolin-pgloader` |

Для компонентов настраивается ротация логов через `logrotate`
(`pangolin-dbms`, `pangolin-manager`, `pangolin-pooler`, `pangolin-auth-reencrypt`,
`pangolin-certs-rotate`). Компоненты разворачиваются в каталоги вида
`/opt/pangolin-<имя-компонента>`; пользовательское табличное пространство по
умолчанию создаётся в `/pgdata/<мажорная версия>/tablespaces/`.

### 1.3 Схемы развёртывания

Документированные конфигурации:

1. **standalone** — только `pangolin-dbms`;
2. **standalone + Pangolin Pooler** — наиболее частая одиночная схема;
3. **«одноногий кластер»** — один узел СУБД + Pooler + DCS + Manager
   (используется редко);
4. **кластер с потоковой репликацией** — лидер и одна или несколько реплик,
   Pangolin Manager на узлах, DCS (etcd или Pangolin DCS, в т.ч. внешний
   «коммунальный» кластер DCS);
5. **кластер с несколькими репликами от одного лидера**;
6. **кластер с каскадными репликами** (реплика реплицируется от другой реплики);
7. **комплексный кластер**, собираемый из атомарных кластеров вышеперечисленных
   типов.

Документация содержит сценарий **реконфигурации standalone → кластер**
(установка DCS, установка Pangolin Manager, подключение реплик), чек-лист
проверки корректности работы (health-check), раздел с типовыми проблемами
(в т.ч. ошибки etcd: несоответствие идентификаторов кластера/узлов, смена
ролей узлов при сбое etcd; статус узла «Pending restart»), а также описание
**Docker-образов** СУБД.

Установка возможна вручную по шагам (standalone или cluster) либо
**автоматизированно Ansible-сценариями**, поставляемыми с продуктом: роли хостов
задаются в inventory (`leader`, `replica_N`, `replica_cascade_N`, `dcs_N`),
состав компонентов — через группы `leader_group` / `replica_group` /
`dcs_group`. Сценарии умеют включать СЗИ (TDE, защита от привилегированных
пользователей, secure config) и применять профили тюнинга **1С / OLAP / OLTP**.

### 1.4 Функции безопасности

- **Прозрачное шифрование хранимой информации (TDE)** и параметров подключения.
- **Защита от привилегированных пользователей** — механизм на принципе
  разделения ролей, предотвращающий доступ к пользовательским данным со стороны
  суперпользователя СУБД, администратора ОС, администратора безопасности
  (в части ключей TDE) и администратора резервного копирования. Включает два
  блока: защиту настроечных параметров, через которые возможно раскрытие данных,
  и защиту доступа к данным в объектах БД. Включается **с использованием
  хранилища секретов HashiCorp Vault или «KMS-заменителя»** (эмулятора).
- Под защиту помещаются: схемы, таблицы, партиции, представления и
  материализованные представления, функции, роли (функция `pm_protect_object`).
  Сведения об ограничениях хранятся в таблицах каталога безопасности.
- **Администратор безопасности** (`sec_admin_role`) — отдельная роль, не имеющая
  прав в ОС и доступа к объектам БД; несовместима с superuser у одного лица.
  Ряд операций (настройка защиты сетевых соединений, состав загружаемых
  расширений, доверенные серверы аутентификации, включение TDE, управление
  доступом к конфиденциальным объектам) по замыслу **не должен выполняться
  одним лицом**.
- Предупреждение документации: расширение `pageinspect` и подобные позволяют
  увидеть расшифрованные данные в обход защиты — их использование на защищённых
  БД опасно.
- **Secure config** — хранение конфигурационных файлов/параметров (в т.ч.
  парольных политик) в удалённом хранилище Vault; при отсутствии KMS-хостов
  используются локальные файлы.
- Гибкие **парольные политики** и управление жизненным циклом паролей;
  расширенный **аудит** действий пользователей и отчёты по истории активности;
  **маскирование параметров запросов**; **двухфакторная аутентификация**;
  сертификаты в формате **PKCS#12**, поддержка CRL, интеграция с системами
  хранения секретов. Документированы отдельные сертификаты/ключи для СУБД,
  Pangolin Manager (REST API), Pangolin Pooler, etcd и пользователя `postgres`;
  описан сценарий управления сертификатами через Secret Management System.
- Подтверждена совместимость с рядом внешних решений, включая менеджер секретов
  «ОдинКлюч» и ОС Platform V SberLinux OS Server.

### 1.5 Типовая ролевая модель

С версии 5.4.0 ролевая модель вынесена из инсталлятора и конфигурируется
опциональными скриптами из дистрибутива (могут быть изменены или заменены
собственной моделью). Типовые групповые роли:

| Роль | Смысл |
|---|---|
| `db_admin` | административная роль с superuser; владелец табличного пространства и БД |
| `as_admin` | владелец прикладной схемы; создаёт и изменяет объекты; выдаётся администраторам АС и ТУЗ автоматизации; имеет `NOINHERIT`, требуется `SET ROLE as_admin` |
| `as_admin_read` | как `as_admin`, но только чтение |
| `as_TUZ` | прикладная техническая учётная запись для DML; работает через пул соединений / Pangolin Pooler |
| `all-sa-pam-group` | группа для входа через PAM (privileged access management) |

Инфраструктурные ТУЗ: `backup_user` (интеграция с СРК), `zabbix_oasubd`
(мониторинг), `auditor`, `pangolin-pooler`, `pangolin-manager`, ТУЗ для доступа
администраторов через PAM (в т.ч. read-only вариант). Рекомендации: ручное
администрирование — только под персонализированными УЗ; минимизация прав;
типовая модель должна разворачиваться автоматически.

### 1.6 Эксплуатация и обновление

- Три документированных сценария обновления:
  - **мажорное** — через `pg_upgrade`, с обязательной локальной резервной копией
    и автоматическим откатом при ошибке; данные с лидера переносятся на реплики
    `rsync`; на время обновления внешний трафик блокируется (простой);
  - **минорное** — обновление исполняемых файлов: сначала реплика, затем
    switchover, затем бывший лидер; кластер доступен всё время (rolling);
    WAL на время недоступности узла сохраняются через `pg_receivewal`;
  - **обновление системного каталога** утилитой `inplace_upgrade` — быстро,
    как минорное, без полной резервной копии, но с простоем.
- Перед обновлением запускается «разведчик» (pre-check): состояние кластера,
  ресурсы, свободное место, deprecated-типы данных; сообщения имеют коды
  WARNING / ERROR / INFO / SUCCESS. Ведётся журнал сценариев автоматизации.
- Компоненты имеют собственные версии и в перспективе обновляются независимо.

### 1.7 Расширения и средства миграции

В состав входят расширения, обеспечивающие: автономные транзакции, планировщик
заданий, дефрагментацию таблиц, HTTP-клиент на уровне СУБД, очереди сообщений,
столбцовое хранение и организацию распределённой OLAP-БД. Документация
упоминает глобальные индексы как средство повышения производительности.
Доступны `pgvector` (ИИ-сценарии), `citus`, `pg_background`, утилиты миграции
`ora2pg` (Oracle → PostgreSQL) и `pgloader`; заявлен упрощённый переход с
ванильного PostgreSQL на Pangolin. Есть интеграции с платформами данных
(например, Selena Lakehouse).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Северный Кредитный Банк» (вымышленный, топ-30 по активам) эксплуатирует
АС «Единый реестр платёжных поручений» (ЕРПП) — систему учёта и контроля
исполнения платёжных поручений юридических лиц. ЕРПП относится к критичным
системам класса **Mission Critical**; недоступность более 15 минут в
операционное время влечёт регуляторную отчётность.

Программа импортозамещения предписывает перевести ЕРПП на отечественный стек
до конца 2027 года. Целевая СУБД утверждена: **Platform V Pangolin DB**.

### 2.2 Ландшафт AS-IS

- СУБД: **Oracle Database 19c**, RAC из 2 узлов в ЦОД-1, Data Guard
  (async) в ЦОД-2.
- Объём данных: **3,2 ТБ** (без индексов ~2,0 ТБ), рост **~1,2 ТБ/год**;
  срок хранения — 5 лет онлайн, далее архив.
- Бизнес-логика: ~40 тыс. строк PL/SQL; используются автономные транзакции,
  `DBMS_SCHEDULER` (ночные регламенты), `DBMS_AQ` (очереди уведомлений),
  `UTL_HTTP` (вызов внешнего сервиса проверки контрагентов), глобальные
  временные таблицы.
- Приложение: Java 17 / Spring Boot, **60 подов** в Kubernetes (Platform V),
  пул HikariCP **20 соединений на под** (текущая настройка), в пиках
  наблюдается до **1 100 одновременных соединений** к Oracle.
- Отчётность: 30–40 тяжёлых аналитических запросов в день, сейчас исполняются
  на Data Guard-реплике (Active Data Guard).
- Нагрузка: пик **12 000 транзакций/с** (короткие OLTP-транзакции, 70 % чтение /
  30 % запись), ночной пакет загрузки выписок **до 25 млн строк за 2 часа**.

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~45 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64, ОС **Platform V SberLinux OS Server**; в каждом ЦОД можно выделить до 4 серверов под СУБД (2×32 ядра, 512 ГБ RAM, NVMe 8 ТБ) |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, растянут между ЦОД). KMS-заменитель Pangolin использовать в промышленной среде **запрещено** политикой ИБ |
| INF-04 | Система резервного копирования (СРК) банка предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; требуется интеграция через штатные средства СУБД |
| INF-05 | Мониторинг — **Zabbix**; журналирование — централизованный SIEM; управление привилегированным доступом — **PAM-система** (все административные сессии только через PAM) |
| INF-06 | Kubernetes-кластеры приложения есть в обоих ЦОД (active/standby по приложению) |
| INF-07 | Команда сопровождения: 4 DBA (опыт PostgreSQL средний, Pangolin — базовый), 1 администратор ИБ, 2 DevOps; развёртывание — только Ansible из корпоративного репозитория |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с субботы на воскресенье, **не более 4 часов** |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность в операционное время (05:00–23:00 МСК) | ≥ 99,95 % в год |
| NFR-02 | RPO при отказе узла / стойки внутри ЦОД | **0** (подтверждённые транзакции не теряются) |
| NFR-03 | RTO при отказе узла внутри ЦОД (автоматическое переключение) | ≤ 3 мин |
| NFR-04 | RPO при полной потере ЦОД-1 | ≤ 60 с |
| NFR-05 | RTO при полной потере ЦОД-1 (допускается ручное решение о переключении) | ≤ 30 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД | ≤ 15 мс при 12 000 TPS |
| NFR-07 | Аналитические запросы не должны деградировать OLTP более чем на 5 % по p99 | — |
| NFR-08 | Ночной пакет 25 млн строк | ≤ 2 ч, без блокировки OLTP |
| NFR-09 | Ёмкость | 5 лет хранения при росте 1,2 ТБ/год + 30 % запас |
| NFR-10 | Восстановление на момент времени (PITR) | глубина 35 дней; RTO восстановления полной БД из копии ≤ 6 ч |
| NFR-11 | Плановые обновления минорных версий СУБД и компонентов | без простоя приложения |
| NFR-12 | Мажорные обновления | в окне INF-08 |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные платёжных поручений (ПДн + банковская тайна) шифруются «на диске»; ключи — во внешнем хранилище секретов банка |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен иметь возможность прочитать содержимое защищаемых таблиц |
| SEC-03 | Разделение обязанностей: включение TDE, изменение состава расширений, настройка сетевой защиты и выдача доступа к защищаемым объектам требуют участия администратора ИБ |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит DDL и всех операций с защищаемыми объектами; передача в SIEM; маскирование параметров запросов в журналах |
| SEC-06 | TLS для всех соединений (клиент ↔ пул ↔ СУБД, узлы кластера ↔ DCS, REST API оркестратора); сертификаты из корпоративного УЦ, ротация не реже раза в год без простоя |
| SEC-07 | Парольные политики для локальных УЗ (сложность, срок действия, история) |
| SEC-08 | Резервные копии не должны позволять восстановить открытые данные без ключей из хранилища секретов |
| SEC-09 | Для DBA — двухфакторная аутентификация |
| SEC-10 | Использовать сертифицированную ФСТЭК редакцию либо обосновать применение несертифицированной с компенсирующими мерами |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами.
- Решение должно быть реализуемо силами INF-07 с использованием штатной
  автоматизации продукта.
- Комитет особенно чувствителен к вопросу **размещения кворума DCS при двух
  ЦОД** и к тому, **как приложение находит нового лидера** после переключения.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Pangolin на момент внедрения — 8.2.0 или новее; базовую мажорную
  версию PostgreSQL решающий не знает из контекста и должен либо не
  использовать, либо пометить как допущение.
- Приложение допускает доработку строки подключения и параметров пула.
- Vault банка доступен из обоих ЦОД с латентностью ≤ 5 мс и имеет собственный
  RTO ≤ 5 мин.
- Все ночные регламенты можно перенести на средства планировщика СУБД или
  внешний оркестратор.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DCS | Distributed Configuration Store — хранилище состояния кластера для оркестратора (etcd или Pangolin DCS) |
| Switchover / Failover | плановое / аварийное переключение роли лидера |
| TDE | прозрачное шифрование данных на уровне хранения |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| PAM | privileged access management |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
| Secure config | хранение конфигурации СУБД в удалённом хранилище секретов |
