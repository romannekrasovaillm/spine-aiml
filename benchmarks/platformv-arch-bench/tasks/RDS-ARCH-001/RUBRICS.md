# Рубрики оценки для задачи RDS-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Radish,
   которого нет в §1 и которое не помечено допущением (или не подтверждено
   ссылкой на разрешённый домен), считается **непроверенным**; если оно
   ещё и ложно — **ложным**. Судья не «додумывает» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (NFR/SEC/INF) и обоснованное, а не за ключевое слово.
4. **Шкала 0–4:** 0 — отсутствует/ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно и обоснованно, мелкие недочёты;
   4 — образцово: полно, обоснованно, с учётом компромиссов и ловушек §4.
5. **Цитирование.** Для каждого критерия — 1–3 цитаты (≤ 25 слов) из
   ответа и указание, чего не хватает до следующего уровня.
6. **Режим прогона** — только `agentic`; учитывать `run_mode_adjustments`.
7. Стиль сверх C11 и объём не оцениваются и не поощряются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).
| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Вымышленные компоненты или функции Radish поданы как факт («Radish Manager», «Radish Proxy», «встроенный балансировщик Radish», «TDE в Radish», «встроенное маскирование ПДн») | A-05, таблица ловушек §4; механический regex — в `mechanical_checks` |
| HF-02 | Заявлена сильная консистентность или гарантированный RPO = 0 средствами Radish (`WAIT`, `min-replicas-to-write`, durability-режим), вопреки CONTEXT §1.4 | Только судья: семантика утверждений о сохранности |
| HF-03 | Промышленная топология: Sentinel менее чем из 3 экземпляров **или** кластер менее чем из 3 primary — без явного обоснования и компенсирующих мер | A-06; механический regex (частично) — в `mechanical_checks` |
| HF-04 | Предложено отключить persistence при включённом автоперезапуске экземпляров без компенсирующих мер (сценарий «пустой мастер затирает реплики», CONTEXT §1.4) | Только судья |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01; механически — `mechanical_checks.deliverables` |
| HF-06 | Предложено хранить немаскированные ПДн в кэше как целевое состояние (без минимизации/маскирования/прикладного шифрования), вопреки SEC-03 | Только судья |

## 3. Критерии

### C1. Фактическая корректность по Radish (вес 15)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md
§1; корректные наименования (`valkey-server`, `valkey-sentinel`,
`valkey-cli`, Radish Exporter, SecMan); отделение фактов от допущений.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (слоты/CRC16, кворум Sentinel, асинхронность репликации, дефолт persistence), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 помечено допущением или подтверждено ссылкой; правильно различаются Redis OSS ≤ 7.2 и Redis CE 7.4+; зоны §1.10 не используются как факт |

**Признаки сильного ответа:** корректно называет ядро Valkey и
исполняемые файлы; опирается на 16 384 слота / CRC16; цитирует дефолт
`appendonly yes` + `save ""`; не приписывает Radish TDE, «прозрачное
шардирование без клиентской поддержки» или гарантии сохранности.

**Типичные ошибки:** «кворум Sentinel выбирает новую конфигурацию»
(кворум — только обнаружение сбоя); «WAIT обеспечивает RPO = 0»;
«Radish — drop-in для любого Redis» (CE 7.4+ несовместим); выдуманные
параметры конфигурации.

### C2. Топология и шардирование (вес 13)

**Что оценивается:** D2 + D3. Выбор режима (Sentinel vs кластер) из
исходных данных, расчёт шардов/реплик, модель данных и TTL, план роста.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы, либо режим выбран без связи с нагрузкой/ёмкостью; HF-03 |
| 2 | Режим выбран и назван; шарды/узлы заявлены «с запасом» без вывода; модель данных не увязана с эвикциями и NFR-12; кластерный протокол клиента не учтён |
| 4 | Выбор обоснован числами: ёмкость ~42 ГБ (NFR-08) и ≥ 440 000 RPS (NFR-07) сопоставлены с потолком 8 I/O-потоков и цифрами вендора (0,9–1,19 млн RPS) ⇒ выведено число primary; для кластера — ≥ 3 primary, реплики на шард, размещение по серверам INF-02 без двух узлов шарда на одном сервере; префиксы `sess:/tok:/af:/rl:` с TTL по классам; учтена поддержка кластерного протокола клиентом (ASSUME про Lettuce); план роста — шарды и миграция слотов без остановки; для Sentinel-варианта честно показан предел масштабирования |

**Ловушки:** «кластер из 2 primary»; «Sentinel шардирует данные»; ручное
шардирование по классам данных вместо слотов; игнор потолка 8 I/O-потоков.

### C3. HA/DR: репликация, failover, честные RPO/RTO (вес 13)

**Что оценивается:** D4, NFR-01…NFR-05, размещение Sentinel/узлов при
двух ЦОД (INF-01), обнаружение мастера клиентами, поведение при
сетевых сбоях (SEC-08).

| Уровень | Якорь |
|---|---|
| 0 | HF-02 или HF-03; DR сведён к «восстановим из копии» без увязки с NFR-04/05 |
| 2 | Failover внутри ЦОД описан, но: RPO/RTO заявлены без связи с асинхронной репликацией; все Sentinel в ЦОД-1 (потеря ЦОД-1 останавливает failover) без обсуждения; обнаружение нового мастера клиентом не описано; «защищённый режим» не учтён |
| 4 | (a) асинхронная репликация принята осознанно: RPO ≤ 5 с / ≤ 5 мин (NFR-03/05) обоснованы через лаг реплики и, при необходимости, `min-replicas-to-write` + `min-replicas-max-lag` с оговоркой, что это снижает окно потери, а не устраняет; (b) Sentinel: ≥ 3 экземпляров, третий — в облачной зоне INF-01, разобраны потеря ЦОД-1 и потеря облачной зоны; для кластера — реплики шардов в другом ЦОД и поведение при потере ЦОД-1; (c) обнаружение мастера клиентом (Sentinel как провайдер конфигурации или кластерные редиректы) увязано с GSLB-переключением ДБО (INF-06) в RTO ≤ 20 мин; (d) учтён «защищённый режим» при сетевых сбоях; (e) возврат ЦОД-1: PSYNC/полная ресинхронизация, риск «пустого мастера» закрыт |

**Ловушки:** «синхронная репликация между ЦОД»; «RPO = 0 через WAIT»;
«по одному Sentinel в каждом ЦОД»; durability-режим подан как точная
гарантия (в документации описан общими словами — §1.4, §1.10).

### C4. Персистентность и восстановление (вес 8)

**Что оценивается:** D5, NFR-09, NFR-10, SEC-05, INF-04.

| Уровень | Якорь |
|---|---|
| 0 | Нет раздела, либо HF-04 |
| 2 | RDB/AOF названы; дефолт Radish (`appendonly yes`, `save ""`) учтён или осознанно изменён; нет сценария прогрева, копии только в одном ЦОД, нет защиты от «пустого мастера» |
| 4 | Осознанный выбор режима под кэш-профиль (AOF `everysec` на репликах при «мастере без диска» — штатный паттерн; либо полное отключение persistence с явным отключением автоперезапуска); копии в СРК обоих ЦОД (INF-04) с GPG-шифрованием (SEC-05), «не старше 24 ч + инкремент» (NFR-10); прогрев после DR (NFR-09): источник (реплики ЦОД-2, копии, ревалидация в IAM / перелогин как деградационный режим), оценка времени и hit-rate; учтено влияние bgsave/AOF-перезаписи на p99 (NFR-06); тестовые восстановления |

**Ловушки:** «RDB каждые 60 с на мастере под 440 тыс. RPS без оговорок»;
«копия = реплика»; восстановление без плана прогрева.

### C5. Память, эвикции, производительность, ёмкость (вес 12)

**Что оценивается:** D6, NFR-06…NFR-08, NFR-12, INF-02.

| Уровень | Якорь |
|---|---|
| 0 | Нет расчётов; лимиты памяти не заданы при профиле кэша |
| 2 | `maxmemory` и `allkeys-lru` названы; числа «по опыту»; NFR-12 не разведён по классам данных; 9 000 соединений не проверены против `maxclients` |
| 4 | Ёмкость: 14 ГБ × 3 = ~42 ГБ (NFR-08) + накладные ⇒ `maxmemory` на шард выведен из числа шардов и RAM серверов INF-02 с учётом ориентира ~75 % RAM; `allkeys-lru` обоснована, с пометкой, что полный перечень политик — зона §1.10; NFR-12: приоритет вытеснения счётчиков реализован в рамках подтверждённых механизмов (TTL / отдельный инстанс) — выбор обоснован; client eviction: `maxmemory-clients` + `CLIENT NO-EVICT` для критичных клиентов; 9 000 соединений сверены с `maxclients` 10 000, решение принято; 440 тыс. RPS сопоставлены с цифрами вендора и потолком 8 I/O-потоков; латентность: физические серверы 0,1 мс vs виртуализация 9–40 мс — размещение согласовано с NFR-06 |

**Ловушки:** «maxmemory не нужен, памяти хватит»; «allkeys-lru вытеснит
сессии раньше счётчиков» без механизма; расчёт на > 8 I/O-потоков.

### C6. Безопасность и защита ПДн в кэше (вес 14)

**Что оценивается:** D7, SEC-01…SEC-09.

защищены, потому что TLS».

| 4 | Обязательные альтернативы разобраны с причинами: «оставить Redis OSS» (нет поддержки вендора, лицензия CE 7.4+) и «Sentinel без шардирования» (предел ёмкости/RPS одного набора); реестр рисков с мерой: асинхронная потеря записей (принято, деградация через IAM/перелогин), потеря облачной зоны с арбитром, горячий слот, переполнение памяти, лаг реплики ЦОД-2, доступность Vault, компетенции команды; открытые вопросы к вендору по §1.10 сформулированы конкретно |

### C11. Структура, ясность, схема (вес 2)

| Уровень | Якорь |
|---|---|
| 0 | Структура не соответствует D1–D10 (HF-05), схема отсутствует |

| 4 | Все разделы; валидная Mermaid/PlantUML-схема с ЦОД, узлами, шардами, репликами, Sentinel (если есть), потоками клиентов; резюме ≤ 15 строк; лимит 4 000 слов соблюдён |

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "RDS-ARCH-001-RUB",
  "task_id": "RDS-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T5"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` — по формуле из frontmatter; `verdict = excellent` при
`total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; любой
`hard_fails[].triggered = true` ⇒ `fail`.

## 8. Калибровка и контроль качества судей

1. Подготовить три эталонных ответа (`gold`, `silver`, `fail`); медиана
   ансамбля судей должна попадать в `expected_totals`.
2. Согласованность судей по критериям: при `alpha < 0.75` — уточнить
   якоря (обычно проблема в C3 и C6).
3. Для 10 % прогонов — выборочная проверка человеком; расхождение
   > 1 балла по критерию = инцидент калибровки.
4. При обновлении Radish/документации — обновить CONTEXT §1, ловушки §4 и
   `docs_snapshot_date`, повысить `version`, перепрогнать эталоны.
5. Не показывать решающим таблицу ловушек §4 и якоря уровня 4.
