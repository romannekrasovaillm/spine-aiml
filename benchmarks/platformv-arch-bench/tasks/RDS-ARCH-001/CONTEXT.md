## 1. Продукт: Platform V Radish `[DOC]`

### 1.1 Что это

- Key-value СУБД в оперативной памяти: «масштабируемое, отказоустойчивое
  и быстрое хранение и обработка данных "ключ-значение"»; целевые задачи —
  «кеширование, обработка сессий, быстрый обмен сообщениями и хранение
  временных данных, где критически важны минимальные задержки доступа и
  высокая доступность».
- **Ядро — Valkey** (форк Redis): конфигурация `valkey.conf`, серверы
  `valkey-server` и `valkey-sentinel`, CLI `valkey-cli`. Ранние версии
  (1.1.1/1.1.4 в составе Platform V Copywala REDS) основаны на Valkey
  8.1.3/8.1.4; с релиза 2.0.0 Radish — самостоятельный продукт.
- Позиционирование: Radish «смягчает нагрузку центральной базы данных
  приложения» для данных, которые «редко меняются, к которым часто
  обращается приложение», и «не относящихся к критически важным, которые
  часто меняются». Критичные данные с жёстким требованием сохранности —
  не профиль Radish (см. §1.4).
- Добавленная ценность относительно open-source Redis/Valkey: per-slot
  метрики (горячие слоты), согласованная ACL-модель для всех режимов,
  экспериментальный RDMA-модуль, интеграция с SecMan, поддержка вендора,
  «улучшенные структуры данных для экономии памяти».

Источник: `banking/plugins/ru-data/skills/radish-kv-architecture/SKILL.md`;
`experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/rdh_documents__about__objective.html.txt`,
`rdh_about__advantages.html.txt`.

### 1.2 Совместимость с Redis/Valkey

- Совместимость «на уровне протокола и команд» с **Redis OSS ≤ 7.2** и
  **Valkey ≥ 8.0**. «Переход с любой open-source версии Redis/Valkey на
  Radish будет являться обновлением».
- **Redis CE 7.4+ не является open-source, файлы данных этих версий
  несовместимы с Radish** — миграция только через протокол
  (репликация/переливка), не копией файлов данных.
- Матрица в скачанных страницах покрывает до Radish 2.1.0; строки для
  2.2.0 нет — см. §1.10.

Источник: `references/compatibility-ops.md` (скилла radish-kv-architecture);
`txt/rdh_about__compatibility.html.txt`.

### 1.3 Топологии: standalone / Sentinel / кластер

- **Кластер (shard-mode)**: **16 384 hash-слота**, ключ → слот по
  **CRC16 (mod 16384)**; слоты перераспределяются без остановки; клиент,
  обратившийся не к тому шарду, автоматически перенаправляется. Модель
  primary–replica: у каждого primary одна или несколько реплик; при падении
  primary реплика автоматически становится новым primary. Узлы соединены
  служебным **cluster bus**. Конфиг узла: `cluster-enabled yes`,
  `cluster-config-file nodes.conf`, `cluster-node-timeout 5000`. Создание:
  `valkey-cli --cluster create … --cluster-replicas N`. **Минимум 3
  primary**, рекомендовано 3 primary + 3 реплики; масштабирование «до
  1000 узлов»; «алгоритмы управления кластером оптимизированы для быстрой
  миграции слотов». Проверка: `valkey-cli --cluster check` → `[OK] All
  16384 slots covered.`
- **Sentinel** (несегментированный набор): мониторинг, уведомления,
  автоматический failover, провайдер конфигурации клиентов. Порт **TCP
  26379** (Radish в примерах — 6379, кластер — 7000). Конфигурация:
  `sentinel monitor`, `sentinel down-after-milliseconds`,
  `sentinel failover-timeout`, `sentinel parallel-syncs`. **Кворум — только
  для обнаружения сбоя**; failover ведёт выбранный лидер Sentinel.
  Деплой: «как минимум **три экземпляра**» на независимо отказывающих
  машинах/зонах; один Sentinel — «единая точка отказа»; failover возможен
  только при связности большинства. Реплики обнаруживаются автоматически.
- Multi-DC: отдельной главы нет; документация допускает размещение хостов
  кластера «в разных зонах и регионах» и Sentinel «в разных зонах
  доступности» — растянутая на 2 ЦОД топология требует проработки (§1.10).

Источник: `references/ha-replication.md`; `txt/rdh_administration-guide__administration-scenarios-cluster.html.txt`,
`rdh_administration-guide__administration-scenarios-sentinel.html.txt`.

### 1.4 Репликация и честные гарантии консистентности

- «Лидер–последователь», **асинхронная по умолчанию**. Механизмы: поток
  команд; частичная ресинхронизация (**PSYNC**) после разрыва; полная
  синхронизация (RDB + буфер). Возможен каскад реплик. Diskless-режим:
  `repl-diskless-sync yes`. Лаг реплики возможен; влияют
  `repl-backlog-size` и `repl-diskless-sync`.
- Прямые формулировки документации: `WAIT` «**не превращает** набор
  экземпляров Radish в систему с сильной консистентностью. При выполнении
  команды подтверждённые записи могут теряться в случае отказа»; Sentinel
  «не гарантирует сохранение подтверждённых записей во время сбоев».
- Кворум на запись `min-replicas-to-write` + `min-replicas-max-lag`
  **снижает окно потери, но не устраняет его** («невозможно гарантировать
  получение репликой определённой записи»).
- **Durability-режим**: «запись считается завершённой только после
  подтверждения от заданного числа реплик… операция записи отклоняется»
  при тайм-ауте; «только полностью синхронизированные реплики могут быть
  выбраны в качестве новых основных узлов». При сбоях сети «Radish
  переводит узлы в защищённый режим… Клиентские соединения в этот момент
  разрываются».
- Реплики read-only по умолчанию; чтения на репликах — через `*_RO`
  (`EVAL_RO`, `SORT_RO`), `SUNION`/`ZINTER` вместо `*STORE`. Записываемые
  реплики (`replica-read-only no`) «не рекомендуются… из-за риска потери
  согласованности». TTL: реплики ждут `DEL` от мастера. `maxmemory` на
  репликах по умолчанию игнорируется (`replica-ignore-maxmemory`).
- **Опасная комбинация**: persistence off на мастере + автоперезапуск →
  мастер поднимается пустым → реплики реплицируют пустоту → «данные
  стираются как с основного узла, так и со всех реплик»; с Sentinel — тот
  же риск при быстрой перезагрузке мастера. Рекомендация: включить
  persistence **или** отключить автоперезапуск.
- Штатный паттерн: «мастер без persistence, реплика с AOF/снепшотами».

Источник: `references/ha-replication.md`; `txt/rdh_administration-guide__administration-scenarios-replication.html.txt`,
`rdh_about__non-functional-features.html.txt`.

### 1.5 Персистентность: RDB и AOF

- Режимы: RDB (снепшоты по интервалам/числу изменений), AOF (лог каждой
  операции записи), комбинация, полное отключение. **Дефолт Radish:
  `appendonly yes` и `save ""`**.
- Параметры: `save 3600 1` / `save 300 100` / `save 60 10000`,
  `stop-writes-on-bgsave-error`, `rdbcompression`; `appenddirname`,
  `aof-use-rdb-preamble yes`. `appendfsync`: `always` — «максимальная
  надёжность, но низкая производительность»; `everysec` — «баланс… по
  умолчанию»; `no` — «наивысшая производительность, но… риск потери
  данных».
- Рекомендации: при высоких нагрузках увеличивать интервалы сохранения;
  для кэша persistence «можно полностью отключить» — с мерой против
  «пустого мастера» (§1.4).
- Диагностика: `INFO persistence`, `CONFIG GET save/appendonly`.
- Шифрование резервных копий — **GPG**.

Источник: `references/persistence-memory.md`; `txt/rdh_administration-guide__administration-scenarios-persistence.html.txt`,
`rdh_about__use-case-rdb-aof.html.txt`, `rdh_about__non-functional-features.html.txt`.

### 1.6 Память и эвикции

- `maxmemory`: ориентир вендора «около **75%** от общей доступной
  оперативной памяти хоста»; `maxmemory 0` — без ограничения (дефолт
  64-бит). Настройка: `valkey.conf` или `CONFIG SET` + `CONFIG REWRITE`.
- Кэш-конфиг из документации: `maxmemory <лимит>` + `maxmemory-policy
  allkeys-lru` — «все ключи будут удаляться с использованием алгоритма
  LRU… пока не будет достигнут лимит памяти»; приложению EXPIRE не нужен.
  Политика LFU упоминается в контексте `valkey-cli --hotkeys`; **полный
  перечень политик в скачанных страницах не раскрыт** (§1.10).
- **Client eviction**: `maxmemory-clients` — лимит совокупной памяти
  клиентских буферов (процент от maxmemory или абсолют); при превышении
  отключаются клиенты с наибольшим потреблением; критичных исключать
  `CLIENT NO-EVICT on`. Диагностика: `evicted_clients`,
  `total_eviction_exceeded_time`, `CLIENT LIST`.
- Соединения: `maxclients` по умолчанию **10 000**; `timeout` по
  умолчанию 0 (отключён); TCP keepalive ~300 сек.
- Подготовка ОС: `vm.overcommit_memory=1`, THP `never`, swappiness 1–10.
- Пакетная загрузка: pipeline + `MULTI`/`EXEC`.

Источник: `references/persistence-memory.md`; `txt/rdh_administration-guide__administration-scenarios-memory.html.txt`,
`rdh_administration-guide__administration-scenarios-caches-settings.html.txt`,
`rdh_administration-guide__administration-scenarios-client-eviction.html.txt`,
`rdh_administration-guide__administration-scenarios-clients.html.txt`.

### 1.7 Производительность (цифры вендора)

- Отклик: GET/SET на физических серверах «стабильно **0,1 мс (100 мкс) и
  ниже**»; в виртуализированных средах с высокой нагрузкой — до 9–40 мс;
  сеть 1 Гбит/с — ~200 мкс; Unix-сокет — до 30 мкс.
- Пропускная: «от **900 000 до 1 190 000 RPS** при оптимальной настройке
  и **8 I/O потоках**»; дальше 8 потоков «масштабирование ограничено
  архитектурой (**single main thread**)» — рост только шардированием.
  I/O-потоки — lock-free ring buffer.
- НФТ-таблица (p95): авторизация до 10 000 оп/с (≤ 10 мс); подключение к
  кластеру до 5 000–10 000 (≤ 20 мс); асинхронная репликация до
  850 000–1 000 000 оп/с (≤ 70 мс); RDB/AOF 5 000–20 000 записей
  (5–20 мс); Lua/Functions API до 3 000–5 000 (≤ 50 мс).
- Доступность (заявление вендора): «99,95–99,99 % в год».
- Redlock: `SET resource unique NX PX <ttl>` на **5 независимых
  экземплярах**, успех — большинство (> N/2) в пределах TTL, освобождение
  Lua-скриптом с проверкой значения.
- Lua/Functions API: на репликах только `EVAL_RO`/`EVALSHA_RO`. RDMA —
  экспериментальный модуль `valkey-rdma.so`.

Источник: `references/compatibility-ops.md`; `txt/rdh_about__non-functional-features.html.txt`,
`rdh_about__pattern-requests.html.txt`, `rdh_administration-guide__administration-scenarios-distlock.html.txt`.

### 1.8 Безопасность

- **TLS**-шифрование соединений; `requirepass` / `primaryauth`.
- **Согласованная ACL-модель** для всех режимов (master, Sentinel,
  Cluster): единственный источник изменений; запрет локальных изменений;
  канонический хеш `acl_hash` (`acl_sha256`); автовосстановление
  рассинхронизации; **аудит с обязательным маскированием паролей**.
  Команды `ACL SETUSER_GLOBALLY` / `DELUSER_GLOBALLY` / `SAVE_GLOBALLY` —
  только на мастере (идут в поток репликации); в Sentinel — через канал
  `__sentinel__:hello`; в кластере — через cluster bus (источник —
  мастер-узел нулевого слота). Роли Admin/User.
- Управление секретами: **SecMan 1.13.0+ или HashiCorp Vault 1.7.0+**
  (опционально; есть сценарий установки «Интеграция с HashiCorp
  Vault/SecMan»).
- `MONITOR` — «только для целей диагностики в тестовых средах или
  кратковременно» (нагрузка, чувствительные данные).
- **Шифрования хранимых данных (аналог TDE) и встроенного маскирования
  значений в документации Radish нет** — защита содержимого кэша (в т.ч.
  ПДн) проектируется внешними средствами (SEC-03).

Источник: `references/compatibility-ops.md`; `txt/rdh_administration-guide__acl.html.txt`,
`rdh_administration-guide__monitoring.html.txt`, `rdh_about__system-requirements.html.txt`.

### 1.9 Мониторинг и эксплуатация

- **Radish Exporter** в составе продукта: метрики **Prometheus** на
  `/metrics` (HTTP, порт 80); собирает `INFO`, `CLUSTER INFO`, `LATENCY`,
  `SLOWLOG`, `MEMORY STATS`, `CLIENT LIST`; учётные данные — из SecMan.
  Внешние системы: Prometheus, Zabbix, Grafana.
- Метрики: `cpu.usage`, `memory.used`, `disk.*`, `network.*`,

  Histogram). Диагностика `valkey-cli`: `--stat`, `--latency`,
  `--bigkeys`, `--memkeys`, `--hotkeys`, `--scan`, `--lru-test`, `--rdb`.
- Развёртывание: вручную, Docker-образ, Kubernetes 1.20+ / OpenShift /
  Platform V DropApp; чек-листы валидации и health-check; разделы
  «Обновление» и «Откат» в руководстве по установке.

### 1.10 Системные требования и непокрытые зоны `[ТРЕБУЕТ ПРОВЕРКИ]`

Системные требования `[DOC]`: ОС — **Platform V SberLinux OS Server
8.8+** или **ALT Linux 11.1+**; опционально SecMan 1.13.0+ / Vault
1.7.0+, Kubernetes 1.20+ / Docker Engine 28+ / OpenShift 4.20+ / DropApp
2.0.0+. Железо (на элемент, компонент RADS): standalone 2 CPU / 4 ГБ /
20 ГБ; кластерный режим 4 CPU / 8 ГБ / 100 ГБ; высоконагруженные системы
8 CPU / 32 ГБ / 500 ГБ.

Непокрытые зоны — **нельзя использовать как факт**, только как открытый
вопрос к вендору:

- Вторичное индексирование (SQL-подобный синтаксис `INDEX … GLOBAL ON`) —
  нетипично для key-value, требует верификации на живой инсталляции.

- Полный перечень политик `maxmemory-policy` не раскрыт (подтверждена
  только `allkeys-lru`, упомянута LFU).
- Главы по межплощадочной (multi-DC) репликации нет.
- Встроенного шифрования «на диске» (TDE), маскирования значений и
  выгрузки аудита в SIEM не описано.

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк Северная Столица» (вымышленный, топ-20 по активам) эксплуатирует
ДБО «Мобильный банк» — **8 млн MAU**, ~2,3 млн DAU. Бэкенд — Java 17 /
Spring Boot в Kubernetes. ДБО — критичная система: недоступность более
30 минут в пиковое время — инцидент 1-й категории с регуляторной
отчётностью.

Программа импортозамещения предписывает вывести self-hosted Redis из
контура до конца 2027 года. Целевой продукт утверждён: **Platform V
Radish 2.2.0**. Отдельный драйвер: после перехода Redis на несвободную
лицензию (CE 7.4+) у банка нет поддержки вендора на текущую инсталляцию.

Radish обслуживает три класса данных:

1. **Сессии** — `sess:<sid>` → JSON-профиль (~4–6 КБ): user_id, признаки
   устройства, скоупы, **ПДн** (ФИО, телефон — сейчас немаскированные,
   признанный дефект AS-IS). TTL скользящий 20 минут.
2. **Кэш access-токенов** — `tok:<jti>` → метаданные (~1 КБ): user_id,
   scope, exp, статус отзыва. TTL 10 минут. Разгружает IAM при валидации.
3. **Антифрод- и rate-limit-счётчики** — `af:*`, `rl:*`, TTL 1–5 мин,
   интенсивная запись.

### 2.2 Ландшафт AS-IS

- **Redis OSS 7.0.15**: один мастер + 2 реплики в ЦОД-1, 3 Sentinel (все
  в ЦОД-1). В ЦОД-2 — холодный стендбай без репликации (восстановление из
  ночной RDB-копии). Шардирования нет.
- Пиковая нагрузка (замеры 2026 г.): **220 000 RPS** (87 % GET), до
  9 000 одновременных клиентских соединений; p99 GET — 3 мс.
- Горячие данные: ~**14 ГБ** (сессии ~8 ГБ, токены ~4 ГБ, счётчики
  ~2 ГБ); до ~6 млн ключей; пик активных сессий **1,1 млн**; валидных
  токенов ~3,5 млн.
- Проблемы AS-IS: единая точка отказа при потере ЦОД-1; потеря до суток
  состояния при DR; Sentinel без арбитра вне ЦОД-1; ПДн в значениях без
  маскирования; `maxmemory-policy` не задана (были OOM-инциденты);
  `MONITOR` периодически используют в проде.
- Клиенты: Java (Lettuce), 120 подов бэкенда, до 75 соединений на под в
  пике.

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (~40 км, каналы 2×10 Гбит/с, RTT 2–3 мс). Третьей площадки **нет**; есть до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64, ОС **Platform V SberLinux OS Server 9.x**; под Radish — до 6 физических серверов на ЦОД (8 CPU / 64 ГБ RAM / NVMe 1 ТБ) |
| INF-03 | Секреты — кластер **HashiCorp Vault** (3 узла, растянут между ЦОД); SecMan в банке не развёрнут |
| INF-04 | СРК банка: S3-совместимое хранилище в каждом ЦОД; копии шифруются перед выгрузкой и хранятся в обоих ЦОД |
| INF-05 | Мониторинг — **Zabbix** (основной) и **Prometheus + Grafana**; события ИБ — в централизованный SIEM |
| INF-06 | Kubernetes бэкенда ДБО в обоих ЦОД (active/standby); переключение трафика ДБО — GSLB, 5–10 минут |
| INF-07 | Команда: 3 инженера middleware (Redis — хорошо, Radish — нет), 1 администратор ИБ, 2 DevOps; прод — только через GitOps |
| INF-08 | Окно планового простоя 1 раз в квартал, ночь, **≤ 2 часов**; миграция с Redis — без полного простоя ДБО |
| INF-09 | Сегментация: доступ к портам Radish только из сегмента бэкенда ДБО; межцодовая репликация — отдельный VLAN с фильтрацией |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность кэш-контура (06:00–01:00 МСК) | ≥ 99,95 % в год |
| NFR-02 | Автоматическое переключение при отказе узла внутри ЦОД | RTO ≤ 60 с |
| NFR-03 | Потеря данных при отказе узла | RPO ≤ 5 с (допустима переаутентификация части пользователей) |
| NFR-04 | Полная потеря ЦОД-1 | RTO ≤ 20 мин (включая GSLB, INF-06) |
| NFR-05 | Потеря данных при потере ЦОД-1 | RPO ≤ 5 мин (сессии — повторный вход; токены ревалидируются в IAM) |
| NFR-06 | Латентность операций кэша (p99, внутри ЦОД) | ≤ 5 мс при пиковой нагрузке |
| NFR-07 | Пиковая нагрузка | 220 000 RPS, проектировать с запасом ×2 (≥ 440 000 RPS) |
| NFR-08 | Ёмкость | 14 ГБ горячих данных с запасом ×3 (рост MAU +15 %/год, горизонт 3 года) |
| NFR-09 | Прогрев кэша после потери ЦОД/полного рестарта | ≤ 30 мин до hit-rate ≥ 95 % для сессий |
| NFR-10 | Восстановление из резервной копии (логическая порча) | RTO ≤ 2 ч; копии не старше 24 ч + инкремент |
| NFR-11 | Плановые обновления Radish | без простоя кэш-контура либо в окне INF-08 |
| NFR-12 | Поведение при переполнении памяти | вытеснение по политике, а не ошибки записи; счётчики вытесняются первыми |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | TLS для всех соединений (клиент ↔ Radish, узлы кластера, Sentinel, репликация); сертификаты корпоративного УЦ, ротация не реже раза в год |
| SEC-02 | ACL: раздельные УЗ для бэкенда ДБО (минимум команд/префиксов ключей), мониторинга, администрирования; изменения ACL — централизованно, с аудитом |
| SEC-03 | **ПДн в кэше**: минимизировать состав; оставшиеся ПДн — маскировать/шифровать на прикладном уровне (встроенных средств у Radish нет — §1.8); немаскированные ПДн в кэше недопустимы |
| SEC-04 | Секреты (пароли ACL, ключи, сертификаты) — только в банковском Vault (INF-03) |
| SEC-05 | Резервные копии шифруются перед выгрузкой в СРК (GPG, §1.5); доступ к ключам расшифрования — «в четыре руки» |
| SEC-06 | Аудит административных операций и изменений ACL; события — в SIEM; пароли в аудите маскируются |
| SEC-07 | Запрет `MONITOR`, `KEYS` и подобных в проме — технически (ACL) и процедурно |
| SEC-08 | Сетевая сегментация по INF-09; минимум портов; поведение при сетевых сбоях не должно давать неконсистентную запись |
| SEC-09 | 152-ФЗ: учёт ПДн в кэше в реестре обработки, обоснование каждого атрибута |

### 2.6 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами (обязательно разобрать «оставить Redis OSS» и
  «Sentinel без шардирования»).
- Комитет чувствителен к: (a) честности про сохранность — недопустимо
  обещать RPO = 0 там, где продукт его не гарантирует; (b) размещению
  Sentinel/узлов при двух ЦОД; (c) судьбе ПДн в кэше.
- Решение реализуется силами INF-07.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Radish на момент внедрения — 2.2.0 или новее; точная базовая
  версия Valkey в 2.2.0 не задана — помечать как допущение.
- Клиентская библиотека Lettuce поддерживает кластерный протокол
  Redis/Valkey и Sentinel — допущение, допускающее проверку; доработка
  клиентского кода допустима.
- Полный перечень `maxmemory-policy`, вторичное индексирование, детали
  durability-режима и multi-DC — предмет запроса к вендору (§1.10).
- IAM ДБО допускает доработку инвалидации кэша токенов; повторная
  аутентификация пользователя штатна (< 30 с).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| MAU / DAU | месячная / дневная активная аудитория |
| Hash-слот | единица шардирования кластера Radish (всего 16 384, CRC16) |
| Cluster bus | служебный протокол обмена между узлами кластера |
| Sentinel | компонент Radish: мониторинг, автоматический failover, провайдинг конфигурации клиентов |
| PSYNC | частичная ресинхронизация реплики после разрыва |
| RDB / AOF | снепшоты / лог операций записи (персистентность) |
| Эвикция | вытеснение ключей при достижении `maxmemory` |
| Client eviction | отключение клиентов при превышении `maxmemory-clients` |
| Redlock | паттерн распределённых блокировок на независимых экземплярах |
| hit-rate | доля запросов, обслуженных из кэша без обращения к системе записи |
| SecMan | Secret Management System — система управления секретами Platform V |
| GSLB | глобальная балансировка трафика между ЦОД |
| ПДн | персональные данные (152-ФЗ) |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
