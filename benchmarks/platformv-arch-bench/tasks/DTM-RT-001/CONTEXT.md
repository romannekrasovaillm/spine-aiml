## 1. Продукты `[DOC]`

### 1.1 DataMarts: позиционирование и ядро

- **«DMS представляет собой OLAP СУБД»** — прямое определение раздела
  «Концептуальная модель»; «высокопроизводительная аналитическая СУБД с
  поддержкой SQL и колоночной моделью хранения данных»; целевые задачи —
  «интерактивная аналитика и построение информационных панелей», «выполнение
  онлайн-запросов с задержкой менее секунды».
- **Ядро — open source ClickHouse**; версия ядра в публичных доках не
  указана — [ТРЕБУЕТ ПРОВЕРКИ].
- Граница OLTP/OLAP в линейке: OLTP и система записи — Platform V Pangolin
  DB; витрины, отчётность, дашборды, событийная аналитика — DataMarts.
  Запись в DMS устроена как пакетные `INSERT` + фоновые **мутации**
  (UPDATE/DELETE — «частичная мутация» в метриках), а не транзакционные
  точечные записи — для OLTP-нагрузки не проектировать.
- Производительность (формулировки вендора, не гарантия): «сотни миллионов
  строк в секунду», векторная обработка, «до десятков гигабайт в секунду на
  чтение и запись».
- Паттерн «Анализ поведения пользователей в реальном времени»: «обработка
  сотен тысяч событий в секунду», данные доступны «через секунды после их
  совершения», оконные функции.
- Оговорка вендора: «использование продукта иными способами», чем описано в
  документации, — «работоспособность не гарантируется».

### 1.2 DataMarts: компонентный состав

| Компонент (RPM-пакет) | Назначение |
|---|---|
| `datamarts-server` | Сама СУБД (ClickHouse Server; systemd-юнит `clickhouse-server.service`). Рекомендовано 3+ узла; горизонтальное масштабирование — «Да» |
| `datamarts-keeper` | ClickHouse Keeper (бинарь `/usr/bin/clickhouse-keeper`, конфиг `raft_configuration`; digest-аутентификация, `superdigest` из SecMan). Допускается внешний ZooKeeper |
| `datamarts-safeguard` | REST API внешней системы управления нагрузкой (профили настроек, правила токсичности, мониторинг запросов) |
| `datamarts-rrm` + `datamarts-rrm-udf` | Исполнитель запросов на изменение ролевой модели из служебной таблицы + UDF-мост `udf_rrm` |
| `datamarts-vault-provider` | Выпуск, наблюдение и перевыпуск wrapped_token для каждого компонента DMS |
| Аудит-компонент | Чтение логов, дедупликация, запись (метрики `audit_*`); источник — `query_log`/`session_log` |

Установка — RPM-пакеты. PSQ/PostgreSQL — часть архитектуры DMS:
«используется для управления пользователями, правами доступа и ведения
аудита операций»; рекомендуемая СУБД — **Platform V Pangolin DB 5.2.2+**;
секция `[postgresql]` в config.yml с `pool_size = 10`.

### 1.3 DataMarts: кластер — keeper-кворум, шарды, реплики

- Keeper: «разверните как минимум три экземпляра datamarts-keeper на разных
  серверах», каждому — уникальный `server_id`. **RPM `datamarts-keeper`
  конфликтует с `datamarts-server`** — keeper ставится на отдельный сервер.
- Реплицированные таблицы — механизм **ReplicatedMergeTree**; на каждом узле
  — макросы («определив номера сегментов и реплик») и «параметры репликации
  и сегментирования». Документированный пример — кластер `cluster_1S_2R`
  (1 шард, 2 реплики): `internal_replication=true`, общий `<secret>`,
  `secure=1`, порт реплик 9000, keeper-порт 9181 (secure).
- Доступность **«до 99.99 %»** — при совокупности условий: минимум **три
  реплики каждого сегмента данных**; datamarts-keeper/ZooKeeper; регулярное
  резервирование и мониторинг узлов.
- Целостность: атомарные операции, контрольные суммы при чтении/записи,
  «автоматическое восстановление поврежденных сегментов данных».
- Движок Distributed и механика табличного шардирования запросов в публичных
  страницах не раскрыты (есть только `clusterAllReplicas` в safeguard) —
  [ТРЕБУЕТ ПРОВЕРКИ].
- При горизонтальном масштабировании «рекомендуется предварительно провести
  нагрузочное тестирование на целевой конфигурации конкретной инсталляции».

Источник: banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/architecture-security.md («Кластер»); corpus/pv_docs/txt/dms_administration-guide__administration-scenarios-dms-replication.html.txt

### 1.4 DataMarts: таблицы, движки, агрегации, версии

- Движки, **названные в документации**: `MergeTree`, `ReplicatedMergeTree`,
  `Kafka`, `PostgreSQL`, `Executable` (служебная).
- Ключи: «выбор правильных первичных ключей и индексация столбцов ускоряет
  доступ к данным».
- **Материализованные представления**: «автоматическое обновление агрегатов
  при добавлении новых данных», «хранение результатов в отдельной таблице»,
  «возможность настраивать триггеры и условия обновления» — основной
  механизм предрасчёта витрин.
- **Версионные таблицы**: «сохраняют историю изменений каждой строки и
  восстанавливают состояние на любой момент времени; минимальные затраты
  памяти благодаря специально реализованному механизму версионирования».
  Конкретный движок версионных таблиц не назван — [ТРЕБУЕТ ПРОВЕРКИ].
- Загрузка — `INSERT INTO`; выгрузка — `SELECT INTO OUTFILE`.
- **Партиционирование таблиц и TTL данных таблиц в публичной документации
  не раскрыты** — [ТРЕБУЕТ ПРОВЕРКИ]; TTL упоминается только для паролей
  SecMan и очистки служебной `metrics_history`.
- UPDATE/DELETE — фоновые «частичные мутации» (метрика мониторинга);
  транзакционной точечной записи нет.

### 1.5 DataMarts: интеграции (Kafka/Corax, PostgreSQL)

Белый список интеграций продукта: LDAP, SecMan, White-list («списки
доверенных адресов»), Kafka («асинхронный обмен событиями»), PostgreSQL,
IDM.

- **Kafka / Corax**: табличный движок `ENGINE = Kafka()` с параметрами
  `kafka_broker_list`, `kafka_topic_list`, `kafka_group_name`,
  `kafka_format`, `kafka_security_protocol`, `kafka_sasl_mechanism`,
  `kafka_sasl_username`, `kafka_sasl_password`; сообщения «в формате
  JSONEachRow или другом указанном формате» (перечень поддерживаемых
  форматов в публичных страницах не приведён — см. §1.10). SASL-механизмы:
  «PLAIN», «SCRAM-SHA-256», «SCRAM-SHA-512»; защищённый канал — `sasl_ssl`;
  SSL-ключи из SecMan (`ssl_key_pem`, `ssl_certificate_pem`, `ssl_ca_pem`).
  Поддержан Kerberos (GSSAPI: `sasl_kerberos_service_name=kafka`,
  `sasl_kerberos_ccache_name=KEYRING:persistent:id:kafka`). Требуемые
  версии брокеров: **Apache Kafka 0.9+** или **Platform V Corax
  12.381.1+**. Предписание: не передавать учётные данные открытым текстом.
- Kafka — также шина событий между компонентами DMS: топик
  `data_marts_events` (в примере 3 партиции, RF 1), секция `[kafka]` в
  config.yml (`bootstrap.servers`, `security.protocol`, `sasl.mechanism`,
  `ssl.enabled.protocols = TLSv1.2,TLSv1.3`).
- **PostgreSQL / Pangolin**: табличный движок `PostgreSQL` +
  `named_collections` в config.xml (`sslmode` вплоть до `verify-full`;
  ключи и сертификаты из SecMan); либо Kerberos (`gssencmode=require`).
- **FreeIPA**: «Получение актуальных keytab из FreeIPA engine» — штатная
  функция OLAP-компонента.
- **CDC как класс в публичной документации DMS не описан**: штатный входной
  паттерн потоковой загрузки — движок `Kafka`; CDC из Pangolin выполняется
  внешним CDC-инструментом (в линейке — GraDeLy/GDL) в Kafka, далее движком
  Kafka в DMS (см. §1.10).

Источник: banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/integrations-load.md («Белый список», «Kafka / Corax», «PostgreSQL / Pangolin»); corpus/pv_docs/txt/dms_administration-guide__administration-scenarios-kafka-authentification.html.txt, dms_installation-guide__installation-integration-kafka.html.txt

### 1.6 DataMarts: управление нагрузкой (datamarts-safeguard)

- Назначение: REST API для внешней системы управления нагрузкой — «правила
  токсичности», мониторинг запросов онлайн и по истории, «ручное и
  автоматическое управление токсичными запросами (блокировка
  пользователей)», «автоматическое переключение ограничений в зависимости
  от времени суток или расписания».
- Механика — профили настроек: `CREATE SETTINGS PROFILE … SETTINGS
  max_memory_usage, max_execution_time, max_threads … READONLY` + `ALTER
  USER … SETTINGS PROFILE`; readonly — «чтобы пользователи не могли
  самостоятельно обойти ограничения».
- Граница управления: safeguard управляет **только профилями с префиксом**
  `profile_prefix` (по умолчанию `beholder`); «если одна настройка задана в
  нескольких профилях, порядок ее применения не определен».
- Блокировка токсичных пользователей: предсозданная квота с минимальными
  лимитами (дословно «queries: 1, read_bytes: 1, written_bytes: 1,
  result_bytes: 1»), имя квоты — `blocked_quota_name`; исключения —
  `never_blocked_users`; запрещённые ключевые слова — `banned_sql_keywords`.
- Расписание: «в DMS **не предусмотрен встроенный механизм** автоматического
  переключения профилей настроек по расписанию» — его выполняет фоновый
  процесс safeguard (`cron.profile_schedule`); постоянные назначения
  `assign` он не трогает.
- Мониторинг запросов через API: онлайн + история (по умолчанию глубина
  168 ч); при параметре `cluster` — сбор со всех экземпляров через
  `clusterAllReplicas`. Профили логируются в `query_log`.
- Доступ к safeguard: только mTLS + ТУЗ; аутентификация по CN клиентского
  сертификата X.509 (`subject_regexp` + белый список `allowed_certs`);
  раздельные белые списки для системы управления нагрузкой и для АС
  мониторинга; healthcheck `/health` (200 / 5xx).

Источник: banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/integrations-load.md («Управление нагрузкой: datamarts-safeguard»); corpus/pv_docs/txt/dms_administration-guide__administration-scenarios-load-management.html.txt

### 1.7 DataMarts: безопасность — RBAC, аутентификация, секреты, аудит

- **RBAC**: «механизм безопасности основан на управлении доступом на основе
  ролей (RBAC)»; объекты доступа: «учетные записи пользователей, роли,
  политики строк, профили настроек и квоты». «По умолчанию в системе нет
  других ролей кроме администратора… администратор сам создает ролевую
  модель». Способы: XML-файлы в `/opt/datamarts/clickhouse/configs/
  sec.users.d/` (рекомендовано для ТУЗ) или SQL `CREATE ROLE` / `GRANT`.
  Перечень привилегий включает SELECT, INSERT, ALTER, CREATE, DROP, KILL
  QUERY, ACCESS MANAGEMENT и группу SYSTEM.
- Развёртывание ролевой модели — **datamarts-rrm**: запросы с `task_id` в
  служебную таблицу → UDF `udf_rrm` → проверка «на соответствие правилам
  ограничений» → последовательное исполнение, журнал `UDF_LOGS`; статусы
  OK / FAILED / INCOMPLETE.
- **Пароли**: при интеграции с SecMan в файлы не вписываются (KV-секрет);
  TTL паролей из секрета; предупреждения об истечении — в
  `system.text_log`; если пароль в секрете отсутствует — «работа сервиса
  останавливается». Рекомендация: «в производственных средах рекомендуется
  отключать пользователя по умолчанию после настройки».
- **Аутентификация и шифрование**: LDAP, Kerberos, внутренние схемы; TLS.
  Проверка отзыва сертификатов **OCSP** (`ocsp_enable_check`, по умолчанию
  включена) для клиентских HTTPS-соединений, PostgreSQL и Kafka; есть кеш
  ответов OCSP.
- **SecMan** (версия 01.015.03-06): секреты загружаются при старте по
  **wrapped_token** (выпуск/перевыпуск — `datamarts-vault-provider`);
  AppRole; KV- и PKI-хранилища; подстановки в конфигах вида
  `${secman:pki:cert:CN=…}`, `${vault:kv:…}`. «Все секреты (клиентские
  сертификаты, пароль ТУЗ datamarts-server, сертификаты и приватные ключи
  сервера) загружаются из Secman».
- **Аудит**: штатная «передача событий аудита» (источник — `query_log` /
  `session_log`, дедупликация, метрики `audit_*`). У safeguard — отдельный
  файл `/var/log/audit/datamarts-audit.log` (rsyslog-формат, ротация);
  события: успешная (по умолчанию ВЫКЛ) и неуспешная аутентификация,
  изменение/назначение профиля, блокировка/разблокировка УЗ.

Источник: banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/architecture-security.md («RBAC», «Аутентификация, TLS, OCSP») и references/integrations-load.md («SecMan»)

### 1.8 DataMarts: системные требования, мониторинг, трассировка

- Обязательное ПО: **Platform V SberLinux OS Server 8.7+** (единственная
  обязательная строка). Опционально: Pangolin DB 5.2.2+, Apache Kafka 0.9+
  / Corax 12.381.1+, SecMan 01.015.03-06, DevOps Tools 1.9.1+, IDM 2.3.1+,
  Ansible 2.16+, Python 3.x.
- Железо (на элемент `datamarts-server`): CPU запрос 4 ядра, RAM запрос
  8 ГБ, диски 25+ ГБ; лимиты — «зависят от нагрузки/объема данных». Стенд
  НТ вендора: 3 узла × 8 CPU / 32 ГБ RAM / 40 ГБ; НТ-показатели (p95) —
  42,5 оп/с при SLA 0,5 с.
- Мониторинг: системные таблицы `system.metrics`, `system.events`,
  `system.metric_log`, `system.query_log`, `system.latency_log`; внешние
  системы «например в формате Prometheus» (mTLS), Graphite. Ключевые
  метрики: Запрос, Слияние, **Частичная мутация**,
  `ConcurrencyControlSoftLimit`, `FilesystemMainPath*Bytes/INodes`,
  `rrm_tasks_executed/failed`, `vault_tokens_issued`, `krb_tickets_issued`;
  safeguard → таблица `metrics_history`.
- Порты: native TCP 9000 (реплики, secure), keeper 9181 (secure), HTTPS для
  safeguard API.
- **Сквозная идентификация (Correlation ID)**: приём — `SET
  tag_correlation_id = '<id>'` (префикс `tag_` задаётся в
  `custom_settings_prefixes`); сохраняется в `system.query_log`; доступен
  через REST `/safeguard/v1/observability/query-log`. Формат сегмента DMS:
  `Click_<SYSTEM_ID>_<QUERY_ID>`; сегменты разделяются `|`.

### 1.9 Corax: факты, релевантные потоковой загрузке

Platform V Corax (KFK 16.392.0) — дистрибутив Apache Kafka с
enterprise-инструментами; «все сообщения Platform V Corax хранит на диске».
Для данной задачи Corax — **существующая шина** (её проектирование вне
охвата); релевантны потребление топиков, форматы, гарантии и наблюдаемость:

- **Форматы и CDC**: для сообщений в формате **MessagePack** «должен
  использоваться отдельный топик, в который не пишутся сообщения в других
  форматах»; штатный класс чтения MessagePack — десериализатор для
  сообщений от Platform V GraDeLy
  (`--value-deserializer ru.gradely.serialization.TrailFileDeserializer`).
  GraDeLy (GDL) — CDC-инструмент линейки СберТеха, пишущий в
  MessagePack-топики.
- **Потребители**: группы (`group.id`) — каждая партиция ровно одному
  потребителю группы; любое число групп на топик без дублирования чтения;
  потребителей в группе ≤ числа партиций (лишние простаивают). Фиксация
  смещений — автоматическая (`enable.auto.commit`, дефолт 5000 мс) или
  ручная; точка восстановления после сбоя — committed position.
  `auto.offset.reset`: earliest/latest/none. При ребалансировке группы «все
  потребители приостанавливают чтение».
- **Гарантии записи** (релевантно требованиям к продюсерам CDC): `acks=all`
  — «самая надежная из доступных гарантий»; идемпотентный продюсер —
  «с at least once до exactly once», гарантия «только для сообщений,
  отправленных в одной сессии».
- **Квоты**: «встроенное квотирование пропускной способности по клиентам».
  Лимит `max.message.bytes` по умолчанию 5 МБ (брокер отклоняет
  превышающие).
- **Мониторинг потребления**: клиентская метрика consumer lag
  `records-lag-max`; координаторские `offset.metadata.group.*` и
  `timestamp.metadata.group.*` (время старейшего непрочитанного сообщения).
- **Схемы**: Corax Schema Registry (Avro, JSON Schema; Protobuf —
  расхождение вендорских страниц, [ТРЕБУЕТ ПРОВЕРКИ]). Records Policy —
  проверка соответствия схеме на стороне брокера, «НЕ ВХОДИТ в состав
  Apache Kafka и доступен только при использовании Corax».
- **Межкластерная репликация**: Corax Mirror Maker 2; «отличается от
  механизма внутрикластерной репликации в Kafka» (т.е. асинхронная);
  реплицирует сообщения, метаданные топиков, группы потребителей,
  контрольные точки смещений и ACL; есть метрики лага репликации.
- Профиль нагрузки вендорского стенда: 13 000 tps при среднем сообщении
  10 000 байт — параметры **тестового стенда**, не гарантия; вендор
  рекомендует нагрузочное тестирование.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/SKILL.md и references/dev-patterns.md, references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__administration-guide__scenarious__cluster__consumer-configuring.html.txt, kfk__documents__administration-guide__monitoring.html.txt

4. Версия ядра ClickHouse, на котором собран DMS; агрегирующие и

8. Механика резервного копирования DMS (функция «регулярное

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Ладога"» (вымышленный, топ-30 по активам) переводит отчётность
казначейства и ALM (управления ликвидностью) на **внутридневной режим**.
Сегодня платёжная позиция, остатки на корсчетах НОСТРО, использование
лимитов и обороты ДБО доступны только на утро T+1 (ночной ETL). Казначейству
и рискам нужны **intraday-витрины**: обновление каждые 15 минут, дашборды в
течение дня, регламентные внутридневные отчёты (внутридневная ликвидность
по внутренней методологии, согласованной с профильным надзором).

Решение Архитектурного комитета: не нагружать транзакционный контур,
построить отдельный аналитический контур **Platform V DataMarts** с
потоковой загрузкой CDC-событий через существующую шину **Platform V
Corax**. Запуск промышленной эксплуатации — не позднее Q3 2027.

Класс системы — **Business Critical**: недоступность intraday-витрин более
1 часа в операционный день — внутренний инцидент с докладом регулятору по
порядку 719-П (операционная надёжность); в данных присутствуют ПДн (152-ФЗ)
и сведения, составляющие банковскую тайну.

### 2.2 Ландшафт AS-IS

- Транзакционный контур: АБС и платёжные системы на **Platform V Pangolin
  DB** (3 системы-источника, суммарно ~4 ТБ операционных данных).
- CDC: в банке уже работает **Platform V GraDeLy** — изменения из Pangolin
  публикуются в топики Corax **в формате MessagePack** (используются
  другими потребителями — антифродом). Контракт этих топиков менять
  запрещено (INF-03).
- Шина **Platform V Corax 16.392.0**: кластеры в обоих ЦОД, межцодовая
  репликация доменных топиков (асинхронная), Corax Schema Registry
  развёрнут. Эксплуатируется отдельной командой middleware.
- Отчётность T+1: ночной ETL-загрузчик (самописный, Java) выгружает дельту
  в старое DWH; 25–30 тяжёлых отчётов утром.
- Пользователи intraday-контура: ~120 сотрудников (казначейство, риски,
  финансы), пик — до 40 конкурентных BI-сессий через внутренний BI-портал.
- Ночной «закрывающий» срез (22:30–01:00) — регламентная финализация дня:
  итоговые витрины дня, сверка с T+1-потоком.

### 2.3 Нагрузка и объёмы

- CDC-поток (3 системы-источника): **140 млн событий/сутки**; средний темп
  **2 400 событий/с**, пик в конце операционного дня (18:00–21:00) —
  **16 000 событий/с**; рост **+25 % в год**.
- Средний размер сообщения **1,8 КБ**; максимальный (пакетные реестры) —
  до **200 КБ** (в пределах дефолтного `max.message.bytes`).
- Доля обновлений и удалений в CDC-потоке — до **15 %** событий (остальное —
  вставки): витрины обязаны корректно отражать изменение и отмену операций.
- Intraday-витрины: 9 штук (платёжная позиция, остатки НОСТРО,
  использование лимитов, обороты ДБО по каналам и др.); регламентные
  отчёты — 25 форм каждые 15 минут (07:00–22:00).
- Детальный слой событий: **90 дней онлайн** (оценка к концу периода —
  ~8 ТБ сжатых данных); версии ключевых витрин (состояние на любой момент)
  — **3 года** (запросы ревизий и внутреннего аудита).

### 2.4 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), ~30 км, каналы 2×10 Гбит/с, RTT 1–2 мс. Третьей площадки **нет**; можно разместить до 2 лёгких ВМ (4 vCPU / 16 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | До **7 физических серверов в каждом ЦОД** под контур DataMarts (x86-64, 32 ядра, 256 ГБ RAM, NVMe 4 ТБ); ОС — только **Platform V SberLinux OS Server** совместимой версии |
| INF-03 | Шина Corax существует и эксплуатируется другой командой: формат существующих MessagePack-топиков GraDeLy менять запрещено; создание новых топиков и новых consumer-групп — согласуется с командой middleware; квоты клиентов на брокерах — в их ведении |
| INF-04 | Хранилище секретов банка — **SecMan** (версия совместима с DMS); пароли и сертификаты открытым текстом в конфигурациях запрещены политикой ИБ |
| INF-05 | Корпоративные LDAP и Kerberos (FreeIPA) доступны из обоих ЦОД; аутентификация пользователей — только через внешний каталог, локальные УЗ — только сервисные; мониторинг — Prometheus + Grafana; SIEM принимает события по rsyslog |
| INF-06 | Для служебной БД DMS (пользователи, права, аудит) предоставляется существующий кластер Pangolin DB банка |
| INF-07 | Команда: 2 инженера данных (опыт ClickHouse средний), 1 администратор ИБ, 2 DevOps; развёртывание — только Ansible из корпоративного репозитория; нагрузочное тестирование перед запуском обязательно |
| INF-08 | Окно планового обслуживания: ночь вс→пн, **≤ 6 часов**, не чаще 1 раза в месяц; в период квартальной отчётности (первые 10 рабочих дней квартала) плановые работы запрещены |

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность intraday-контура в операционный день (07:00–22:00 МСК) | ≥ 99,9 %; простой > 1 ч — инцидент 719-П |
| NFR-02 | Отказ одного узла кластера DMS | чтение витрин и потоковая загрузка не прерываются; RTO ≤ 10 мин |
| NFR-03 | Полная потеря ЦОД-1 | RTO ≤ 4 ч; RPO ≤ 30 мин (честно оценить с учётом асинхронной репликации топиков) |
| NFR-04 | Сквозная латентность «коммит в источнике → данные доступны во витрине» | p95 ≤ 60 с, p99 ≤ 120 с — в среднем темпе и в пике 16 000 соб/с |
| NFR-05 | Дашборды руководства | p95 < 2 с на предрасчитанных витринах |
| NFR-06 | Регламентные intraday-отчёты (25 форм каждые 15 мин) | формирование каждой формы ≤ 30 с; просрочка цикла — инцидент |
| NFR-07 | Изоляция нагрузки | ad-hoc запросы аналитиков не деградируют потоковую загрузку (лаг ≤ 5 мин, NFR-08) и SLA отчётов (NFR-06); тяжёлые ad-hoc — автоматическое ограничение/блокировка |
| NFR-08 | Потоковая загрузка | не отставать от потока в пике 16 000 соб/с; лаг потребления топиков ≤ 5 мин |
| NFR-09 | Хранение | детальный слой 90 дней онлайн (~8 ТБ сжатых); версии витрин 3 года |
| NFR-10 | Деградация и восстановление | при недоступности шины ≤ 30 мин витрины «замораживаются» (чтение работает на устаревших данных с явным признаком свежести), после восстановления — догонка лага ≤ 30 мин; при недоступности keeper-кворума чтение не должно прекращаться |
| NFR-11 | Наблюдаемость | лаг потребления топиков, сквозная латентность по сегментам, p95/p99 запросов, состояние реплик и keeper — в корпоративном мониторинге с алертингом; сквозная трассировка загрузки (Correlation ID) |
| NFR-12 | Масштабирование | рост +25 %/год — добавлением узлов без перестройки архитектуры; перед расширением — нагрузочное тестирование |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Все соединения — TLS (клиенты ↔ DMS, узлы кластера, keeper, интеграции Kafka/PostgreSQL, safeguard API); проверка отзыва сертификатов — OCSP |
| SEC-02 | Аутентификация пользователей — через корпоративный LDAP; сервисные взаимодействия (Kafka, PostgreSQL) — Kerberos или сертификаты; анонимный доступ запрещён |
| SEC-03 | Все секреты — только из SecMan (сертификаты, пароли ТУЗ, ключи интеграций Kafka SSL и PostgreSQL); открытых секретов в конфигурациях нет |
| SEC-04 | RBAC: роли «аналитик / инженер данных / администратор», политики строк для разграничения подразделений; изменение ролевой модели — управляемым, протоколируемым способом |
| SEC-05 | Аудит: аутентификации (успешные/неуспешные), управление профилями и блокировки, доступ к витринам — с выгрузкой в SIEM банка (rsyslog) |
| SEC-06 | Доступ к API управления нагрузкой (safeguard) — только по mTLS, раздельные белые списки для системы управления нагрузкой и мониторинга |
| SEC-07 | ПДн и банковская тайна: доступ к аналитическому контуру только из доверенных сетевых зон (white-list); в витринах — минимизация чувствительных атрибутов (маскирование на уровне модели данных) |
| SEC-08 | Технические УЗ — с минимально необходимыми привилегиями; ACCESS MANAGEMENT и SYSTEM — только у выделенных ролей администраторов; пользователь по умолчанию в проме отключён |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами; реализация силами INF-07 штатными средствами
  продуктов.
- Комитет особенно чувствителен к трём вопросам:
  1. **Формат CDC-сообщений**: существующие топики GraDeLy — MessagePack,
     а перечень форматов движка Kafka в DMS документально не раскрыт
     (§1.10, п. 1). Комитет ждёт явного решения (например, новые топики с
     документированным форматом — согласуется по INF-03) либо оформления
     открытого вопроса к вендору — а не молчаливого допущения.
  2. **Доказуемый бюджет латентности** NFR-04 — по сегментам, с числами.
  3. **Доказуемая изоляция** потоковой загрузки и регламентных отчётов от
     ad-hoc нагрузки аналитиков (NFR-07).
- Комитет предупреждён, что часть вопросов (форматы, партиционирование,
  TTL, механика резервного копирования, версия ядра) не раскрыта в публичной
  документации, и ожидает их оформления как **открытые вопросы к вендору**,
  а не бездоказательные утверждения.

### 2.8 Что можно принять допущением `[ASSUME]`

- Версия DataMarts на момент внедрения — 2.4.0 или новее; версия ядра
  ClickHouse — вопрос к вендору.
- Команда middleware может создать новые топики (в т.ч. с иным форматом
  сообщений) и новые consumer-группы в течение 10 рабочих дней; квоты на
  чтение для consumer-групп контура — по согласованию.
- Лаг асинхронной межцодовой репликации топиков Corax ≤ 2 мин (в рамках
  NFR-03); точное значение — замер на стенде.
- SecMan банка доступен из обоих ЦОД с латентностью ≤ 5 мс.
- Служебная БД DMS на Pangolin (INF-06) резервируется силами существующей
  команды Pangolin и в охват задачи не входит.
- Сетевой канал ЦОД-1 ↔ ЦОД-2 достаточен для репликации пикового потока
  с запасом ≥ 3× (подтверждается расчётом решающего: 16 000 соб/с ×
  1,8 КБ ≈ 29 МБ/с).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DMS | Platform V DataMarts — OLAP-СУБД СберТеха на ядре open source ClickHouse |
| Keeper / datamarts-keeper | ClickHouse Keeper — координация кластера (консенсус Raft) |
| ReplicatedMergeTree | механизм реплицированных таблиц DMS |
| Движок Kafka | табличный движок DMS для потокового чтения топиков Kafka/Corax |
| Мутация | фоновое изменение данных в DMS (UPDATE/DELETE — «частичная мутация» в метриках) |
| Safeguard | компонент управления нагрузкой DMS (профили настроек, правила токсичности) |
| Corax | Platform V Corax — Kafka-совместимая шина событий Platform V |
| GraDeLy (GDL) | CDC-инструмент линейки СберТеха; пишет в топики Corax в формате MessagePack |
| MessagePack | бинарный формат сериализации; в Corax — отдельный топик под формат |
| Consumer lag | отставание потребителя от конца топика (метрики `records-lag-max`, `offset.metadata.group.*`) |
| SecMan | система хранения и управления секретами Platform V |
| Correlation ID | сквозной идентификатор трассировки цепочек загрузки |
| CDC | change data capture — захват изменений из системы-источника |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
| 719-П | положение Банка России об операционной надёжности (инциденты) |
