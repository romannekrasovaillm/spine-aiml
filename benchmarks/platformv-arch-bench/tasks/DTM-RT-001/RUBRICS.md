# Рубрики оценки для задачи DTM-RT-001

## 1. Общие правила для судей

1. **Порядок:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить HF §2;
   (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из ответа;
   (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о DataMarts
   или Corax, которого нет в §1 и которое не помечено решающим как
   допущение, считается **непроверенным**; если оно ещё и ложно —
   **ложным**. Не «додумывать» за решающего.
3. **«Упомянул ≠ применил»** — балл за решение, привязанное к требованию
   (NFR/SEC/INF) и обоснованное, а не за ключевое слово.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 — образцово, с
   учётом компромиссов и ловушек §4.
5. **Цитирование:** 1–3 цитаты (≤ 25 слов) на критерий + чего не хватает до
   следующего уровня.
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`). Стиль и
   объём сверх C10 не оцениваются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
оцениваются для диагностики. «Только судья» = regex-детектор ненадёжен.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Кворум `datamarts-keeper` некорректен: 1 или чётное число узлов, либо keeper размещён на тех же серверах, что `datamarts-server` (RPM конфликтуют), — **без** явного обоснования и компенсирующих мер | Число и размещение узлов keeper в схеме/тексте; A-06. Только судья |
| HF-02 | DataMarts предложена как система транзакционной записи (OLTP), либо CDC-обновления/удаления предложено применять синхронными точечными мутациями без анализа их фоновой природы и влияния на латентность потока (CONTEXT §1.1, §1.4) | A-05; семантика. Только судья |
| HF-03 | Вымышленные компоненты/функции поданы как факт: «нативный CDC-коннектор DataMarts», «прямой CDC из Pangolin в DMS — штатная функция», «движок Kafka в DMS гарантирует exactly-once», «в DMS есть встроенный планировщик профилей», «движок Kafka документированно читает MessagePack» (без пометки «требует проверки») | A-05, ловушки §4 |
| HF-04 | Заявлен RPO = 0 при потере ЦОД-1 для аналитического контура при асинхронной межцодовой репликации топиков Corax, либо MM2 назван синхронным механизмом | A-06; CONTEXT §1.9 |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01 (механические паттерны) |

## 3. Критерии

### C1. Фактическая корректность по DataMarts и Corax (вес 14)

**Что оценивается:** соответствие утверждений о продуктах CONTEXT.md §1;
корректные наименования; отделение фактов от допущений.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-03, либо ≥ 4 ложных утверждения о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (движок Kafka, мутации, keeper, safeguard), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны; всё за пределами §1 помечено допущением или подтверждено ссылкой с разрешённых доменов; пробелы §1.10 (форматы движка Kafka, семантика дедупликации, партиционирование/TTL, движок Distributed, механика резервного копирования) оформлены как открытые вопросы к вендору, а не как факты |

**Признаки сильного ответа:** официальные имена (`datamarts-server`,
`datamarts-keeper`, `datamarts-safeguard`, `datamarts-rrm`,
`datamarts-vault-provider`, движки `Kafka`/`PostgreSQL`/`MergeTree`/
`ReplicatedMergeTree`, Corax Schema Registry, GraDeLy, SecMan); формат
MessagePack топиков GraDeLy корректно противопоставлен документированному
JSONEachRow; «13 000 tps» и «сотни миллионов строк в секунду» не поданы как
гарантии.

**Типичные ошибки:** «DMS умеет CDC из коробки»; «мутации — обычные
UPDATE»; «safeguard управляет любыми профилями»; «keeper можно поставить на
сервер СУБД»; Protobuf в Schema Registry как факт.

### C2. CDC-конвейер: потоки, форматы, семантика доставки (вес 14)

**Что оценивается:** D3. Сквозная цепочка источник → CDC → Corax →
DataMarts, решение по формату сообщений, consumer-группы, дедупликация,
упорядоченность, NFR-04, NFR-08, INF-03.

| Уровень | Якорь |
|---|---|
| 0 | Нет целостной цепочки; HF-03 по форматам |
| 2 | Цепочка названа, но: проблема MessagePack/JSONEachRow проигнорирована (молчаливое допущение); consumer-группы и число партиций не увязаны; дедупликация не спроектирована |
| 4 | (a) проблема формата решена явно: либо новые топики с документированным форматом (JSONEachRow) по согласованию с командой middleware (INF-03), либо открытый вопрос к вендору о поддержке MessagePack движком Kafka — с запасным вариантом; запрет смешения форматов в одном топике учтён; (b) consumer-группа контура отделена от существующих потребителей (антифрод), число потребителей ≤ числа партиций; (c) семантика по сегментам честно зафиксирована: идемпотентный продюсер CDC даёт exactly-once «в пределах сессии», поведение движка Kafka при сбоях документально не раскрыто ⇒ спроектирована дедупликация (версионные таблицы / ключ события / идемпотентная запись) как проектное решение, а не как функция продукта; (d) обработка update/delete (15 % потока) описана: append-only детальный слой + свёртка при чтении/предрасчёте, мутации — не основной механизм потока; (e) упорядоченность: ключ сообщения и порядок внутри партиции |

**Ловушки:** «подключим движок Kafka к существующим MessagePack-топикам»
без проверки формата; «движок Kafka гарантирует ровно один раз»; точечные
UPDATE в DMS как реакция на CDC-обновления; ретрай приложения назван
безопасным из-за идемпотентности продюсера.

| 0 | Нет бюджета; латентность «будет маленькой, это ClickHouse» |
| 2 | Сегменты перечислены, но числа не выведены; пик 16 000 соб/с не рассмотрен; p99 не отделён от p95 |

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "DTM-RT-001-RUB",
  "task_id": "DTM-RT-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0

```

Правила: `total` по формуле из frontmatter; `excellent` при `total ≥ 85`,
`pass` при `≥ 70`, иначе `fail`; при любом `hard_fails[].triggered = true`
— `fail`.
