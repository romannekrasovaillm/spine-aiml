# Рубрики оценки для задачи SEC-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по
   схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о
   продукте, которого нет в §1 и которое не помечено решающим как
   допущение или вопрос к вендору, считается **непроверенным**; если оно
   ещё и ложно — **ложным**. Судья не должен «додумывать» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие ключевого
   слова или наименования продукта.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. **Режим прогона** — только `agentic`; учитывать
   `run_mode_adjustments` во frontmatter.
7. Судья не оценивает стиль и «красоту» сверх C10 и не поощряет объём.

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| HF-01 | Продуктам категории «Сервисы безопасности» (IAM SE, IDM, SOWA, Audit SE, SecMan, OTT) приписаны **как факт** функции, отсутствующие в CONTEXT §1.1/§1.9: например «IAM SE выдаёт сертификаты», «IDM хранит секреты», «SOWA — WAF с сигнатурным анализом», «Audit SE — SIEM/корреляция инцидентов», «SecMan — аппаратный HSM», топология/HA/протоколы этих продуктов — без пометки «требует проверки у вендора» | A-05, таблица ловушек §4; только судья (regex — эвристика) |

## 3. Критерии

### C1. Фактическая корректность по продуктам и карте линейки (вес 14)

**Что оценивается:** соответствие всех утверждений о продуктах CONTEXT.md
§1; корректные наименования; отделение фактов от допущений и вопросов к
вендору.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02/HF-05, либо ≥ 4 ложных утверждений о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (редакции Pangolin, аудит DataMarts по умолчанию, дефолты Corax, pull-модель SynGX), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение/вопрос к вендору; корректно различаются: позиционирование продукта (§1.1) и документированная функция (§1.2–§1.7); редакции Pangolin Standard/Enterprise; Vault и SecMan как разные (не отождествлённые) хранилища; выводы дистиллятов и факты документации |

**Признаки сильного ответа:** использует официальные имена (Platform V
IAM SE, Keycloak SE, IAM Proxy, Platform V IDM, Platform V SOWA,
Platform V Audit SE, SecMan, `datamarts-rrm`, `datamarts-vault-provider`,
`CoraxAuthorizer`, `TsAuditProvider`/COTE, `ngx_hashicorp_vault_module`,
`audit_log`, `ACL SETUSER_GLOBALLY`); точно воспроизводит матрицу
редакций §1.2; не приписывает SOWA/Audit SE функции, отсутствующие в
§1.1.

**Типичные ошибки:** «IAM SE — это SIEM»; «Audit SE коррелирует
инциденты»; «SecMan = HSM»; «TDE есть во всех редакциях»; «LDAP в
Pangolin — во всех редакциях»; отождествление Vault и SecMan без
оговорки.

### C2. Матрица ответственности «продукт / контур ИБ / процесс» (вес 12)

**Что оценивается:** D7. Полнота покрытия доменов безопасности сценария
и корректность распределения по трём исполнителям; отсутствие «повисших»
мер.

| Уровень | Якорь |
|---|---|
| 0 | Матрицы нет, или все меры отданы продуктам (HF-03) |
| 2 | Матрица есть, но покрывает часть доменов; исполнитель указан без обоснования; процессные меры (пентест, оценка соответствия, классификация, DR-учения) не выделены |
| 4 | Матрица покрывает минимум домены: аутентификация/авторизация, секреты и сертификаты, аудит и мониторинг, сегментация, защита API, шифрование хранения, процессные меры (SEC-10), ГОСТ-СКЗИ (SEC-11); каждой мере назначен исполнитель (продукт Platform V с конкретным механизмом ИЗ CONTEXT §1 / внешний контур ИБ из INF-03–INF-04 / процесс банка) со ссылкой на источник или пометкой «требует проверки»; явно перечислены меры, которые **не закрывает ни продукт, ни контур** (процессы из единого списка §1.8); нет «повисших» мер и нет дублей (два исполнителя без разграничения) |

**Ловушки:** «продукт обеспечивает соответствие 719-П»; пентест как
функция MNC/CAP; Audit SE как замена SIEM; ответственность за
классификацию данных отдана СУБД.

### C3. Аутентификация, авторизация и учётные записи (вес 12)

**Что оценивается:** D3, SEC-01, SEC-02, SEC-06, NFR-01, NFR-02, NFR-03.

| Уровень | Якорь |
|---|---|
| 0 | Раздела нет, или централизация сведена к «везде включим LDAP» без разбора, какие продукты это документированно поддерживают |
| 2 | LDAP/Kerberos перечислены по продуктам, но без учёта редакции Pangolin (HF-05); IDM/IAM SE детализированы сверх §1.1 без пометок; блокировка уволенного (NFR-02) не прослежена по механизмам |
| 4 | Распределение по продуктам опирается на CONTEXT: Pangolin — внешняя авторизация LDAP (**только Enterprise** → связано с решением о редакции) + сквозная аутентификация Pooler ↔ СУБД + 2FA (все редакции); DataMarts — LDAP/Kerberos + RBAC + централизованное развёртывание ролевой модели через `datamarts-rrm`; Corax — Kerberos (SASL/GSSAPI) или mTLS + ACL/`CoraxAuthorizer`; Radish — согласованная ACL-модель (`ACL DELUSER_GLOBALLY` разрывает соединения на всех узлах — механика для NFR-02); SynGX — CN/SAN/JWT для внешних потребителей; централизованное управление УЗ сотрудников и JML — за IDM/IAM SE **с явной пометкой**, что детали интеграции (в т.ч. упомянутый белый список DataMarts ↔ IDM) требуют проверки у вендора; разделение обязанностей (SEC-06) — защита от привилегированных пользователей Pangolin (Enterprise) + PAM + «четыре глаза»; NFR-02 ≤ 15 мин прослежен по цепочке: событие в кадровой системе → IDM → механизмы отзыва в каждом продукте; деградация при недоступности контура аутентификации (NFR-01) описана |

**Ловушки:** «IDM сам блокирует учётные записи в Pangolin» как факт;
игнорирование, что аудит успешной аутентификации DataMarts по умолчанию
выключен; ТУЗ приложений «через LDAP сотрудников».

### C4. Управление секретами и сертификатами (вес 12)

**Что оценивается:** D4, SEC-03, SEC-04, SEC-07, NFR-06, INF-04, INF-06.

| Уровень | Якорь |
|---|---|
| 0 | HF-04; секреты «где-то в Vault» без механизмов по продуктам |
| 2 | Vault назван единой точкой, но интеграции по продуктам не показаны или показаны нештатными (самописные скрипты «забирают пароли из Vault в конфиги»); ротация сертификатов без простоя не решена для Corax/SynGX; вопрос SecMan vs Vault не замечен |
| 4 | По каждому продукту — документированная точка интеграции: SynGX — `ngx_hashicorp_vault_module` (AppRole, wrapped_token, закрытый ключ только в shared memory, автообновление) → закрывает SEC-03 для DMZ; DataMarts — `datamarts-vault-provider` + SecMan (TTL паролей, предупреждения) с явной пометкой зависимости от решения о SecMan (INF-04); Corax — шифрование паролей конфигураций (PBKDF2+AES, профиль with-auth) и/или `secman.*`/Vault Java Driver, **обязательная замена опубликованных дефолтов инсталлятора**, ротация брокерских сертификатов — SSL live update без недоступности; Pangolin — интеграция с KMS HashiCorp Vault (Enterprise) для TDE (SEC-07) и хранилище параметров подключения; Radish — SecMan/Vault опционально; единая схема выпуска x509 (УЦ банка INF-03; KACM — для контура Synapse с пометкой проверки); OCSP у DataMarts; отзыв сертификатов; явно разобрана дилемма «Vault vs SecMan» (документация не регламентирует → вопрос к вендору / решение с обоснованием); ротация без простоя увязана с NFR-06 и INF-09 |

**Ловушки:** хранение ключей TDE в файле на сервере СУБД; секреты в
Ansible-инвентаре (INF-06); «Vault в DMZ»; один сертификат на все узлы
и контуры.

### C5. Аудит и мониторинг ИБ (вес 12)

**Что оценивается:** D5, SEC-05, NFR-04, NFR-05, NFR-09.

| Уровень | Якорь |
|---|---|
| 0 | Раздела нет, или «все логи пишем в файлы» |
| 2 | SIEM назван точкой сбора, но механизмы продуктов не использованы (или выдуманы); EPS не оценён; дефолты (выключенный audit_log SynGX, выключенная успешная аутентификация DataMarts) не замечены; неизменность архива не решена |
| 4 | По каждому продукту — штатный механизм: Pangolin — аудит событий безопасности по ГОСТ Р 59548-2022 (все редакции) + маскирование запросов (Enterprise); DataMarts — аудит-компонент поверх `query_log`/`session_log` + `datamarts-audit.log` (включение аудита **успешной** аутентификации — осознанное решение); Corax — аудит-плагин, `TsAuditProvider` в COTE Platform V Monitor по HTTPS или `LogAuditProvider` + внешний форвардер, разбор `kafka.se.audit.suppress.*`; SynGX — `audit_log` (включить; файл/syslog) + учёт, что логи в Kafka напрямую не отправляются и метрики только pull; Radish — аудит ACL с маскированием паролей; Synapse — SYAL; роль Audit SE — строго по позиционированию (сбор/доставка/защищённое хранение для расследования) с пометкой проверки; **расчёт EPS** по компонентам с явной методикой (допущение) и сопоставлением с 22 000 EPS и ёмкостью SIEM 25 000 EPS (INF-03); доставка ≤ 5 мин (NFR-04) — механизм (агенты/syslog/HTTPS) и контроль потерь; архив 5 лет в неизменном виде (NFR-05) — вне SIEM, с исполнителем (продукт не гарантирует неизменность — §1.8); NFR-09 — сквозная трассировка события по УЗ |

**Ловушки:** «SynGX сам шлёт логи в SIEM/Kafka»; «Audit SE = SIEM»;
аудит без маскирования параметров; поток EPS заявлен без расчёта.

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "SEC-ARCH-001-RUB",
  "task_id": "SEC-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.

## 8. Калибровка и контроль качества судей

1. Перед запуском бенчмарка подготовить три эталонных ответа (`gold`,
   `silver`, `fail`) и убедиться, что медиана ансамбля судей попадает в
   `expected_totals`.

   C7 — там тонкая граница между «мерой продукта» и «процессом банка»).

   расхождение > 1 балла по критерию фиксируется как инцидент
   калибровки.

   очередь — при получении документации IAM SE / IDM / SOWA / Audit SE /
