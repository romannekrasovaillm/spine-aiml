# Задача SEC-ARCH-001

## 1. Роль

Вы — ведущий архитектор решений в Департаменте корпоративной архитектуры
банка. Вам поручено спроектировать **целевую (TO-BE) архитектуру контура
информационной безопасности технологического ландшафта Platform V** банка:
централизованная аутентификация и авторизация, управление секретами и
сертификатами, аудит действий, сегментация сети и защита API — и подготовить
архитектурную записку для Архитектурного комитета. Центральный вопрос
комитета: **что закрывают штатные средства продуктов Platform V, а что
должен закрывать внешний контур ИБ банка** (SIEM, PAM, УЦ, SOC, процессы).

## 2. Что нужно сделать

На основе исходных данных из `CONTEXT.md` (факты о продуктах §1, ландшафт
AS-IS, требования и ограничения §2):

1. Спроектировать **модель сегментации**: зоны безопасности ландшафта
   (DMZ, интеграционный сегмент, сегмент данных, сегмент управления ИБ),
   границы доверия и то, какие компоненты какие зоны защищают.
2. Спроектировать **централизованную идентификацию, аутентификацию и
   авторизацию** сотрудников и ТУЗ: что отдаётся контуру IAM/IDM банка,
   что исполняется встроенными механизмами продуктов (LDAP/Kerberos/RBAC/
   ACL), как обеспечивается разделение обязанностей.
3. Спроектировать **управление секретами и сертификатами** для всего
   ландшафта: хранилище секретов (HashiCorp Vault / SecMan), жизненный
   цикл сертификатов (выпуск, ротация, отзыв), исключение секретов из
   конфигурационных файлов.
4. Спроектировать **контур аудита**: какие события генерируют продукты
   (и какими штатными механизмами), как события доставляются в SIEM банка,
   где хранятся, как закрывается требование неизменности и сроков хранения.
5. Спроектировать **защиту API и каналов обслуживания**: граница между
   edge-прокси (SynGX), API Security Gateway (SOWA) и внешним периметром ИБ.
6. Построить **матрицу ответственности «продукт / внешний контур ИБ»**:
   по каждому домену безопасности явно указать исполнителя меры.
7. Выполнить **регуляторную трассировку**: меры 719-П / 683-П / 851-П →
   технический механизм продукта ИЛИ процесс/система банка, со статусом
   «подтверждено документацией / требует проверки у вендора».
8. Явно зафиксировать **компромиссы, риски и отвергнутые альтернативы**.
9. Показать **трассировку** каждого требования (INF-xx, NFR-xx, SEC-xx)
   на принятые решения.

## 4. Ограничения и правила

- Опирайтесь **только на функциональность, подтверждённую источниками из
  CONTEXT.md §1** (факты с пометкой `[DOC]`). Если используете возможность,
  отсутствующую в CONTEXT.md, — явно пометьте её как **допущение, требующее
  проверки у вендора** (`[ТРЕБУЕТ ПРОВЕРКИ]`), а не как факт. Для
  продуктов категории «Сервисы безопасности» (IAM SE, IDM, SOWA, Audit SE,
  SecMan, OTT) документация в источниках отсутствует — известны только
  однострочные позиционирования с портала (CONTEXT §1.1): любая детальная
  функция этих продуктов, заявленная как факт, — ошибка.
- Не изобретайте компоненты и не переименовывайте существующие.
  Используйте официальные наименования из CONTEXT.md: Platform V IAM SE
  (Keycloak SE, IAM Proxy), Platform V IDM, Platform V SOWA, Platform V
  Audit SE, SecMan, Pangolin DB (Pangolin Manager / DCS / Pooler),
  DataMarts (`datamarts-server`/`datamarts-keeper`/`datamarts-rrm`/
  `datamarts-safeguard`/`datamarts-vault-provider`), Corax, SynGX, Radish.
- Различайте редакции Pangolin (Standard / Enterprise): функции Enterprise
  нельзя заявлять при лицензии Standard — вопрос редакции должен быть
  явно решён в записке.
- Каждое ключевое решение должно быть привязано к требованию
  (INF/NFR/SEC) и сопровождаться кратким обоснованием «почему так, а не
  иначе».
- Числовые оценки (объёмы аудита, EPS, сроки ротации, ёмкость) должны
  быть выведены из исходных данных, а не заявлены декларативно.
- Объём ответа: не более 4000 слов без учёта кода диаграмм и таблиц.
- Язык ответа: русский; допустимы англоязычные технические термины.

## 6. Режим прохождения

Прогон выполняется **только в режиме `agentic`** (файловая система +
выполнение кода + чтение предоставленных источников). Режим фиксируется в
протоколе прогона и учитывается судьями (см. RUBRICS.md, frontmatter).

## 7. Что НЕ требуется

- Проектирование внутренней архитектуры прикладных систем банка
  (микросервисы, схемы БД, API-контракты) — продукты ландшафта заданы
  ландшафтом из CONTEXT.md §2.2.
- Проектирование внешнего периметра ИБ банка (SIEM, PAM, УЦ, SOC,
  антивирус) — он существует; требуется только интеграция с ним.
- Детальное проектирование внедрения IAM SE / IDM / SOWA / Audit SE
  (схемы развёртывания, конфигурации) — по этим продуктам доступно только
  позиционирование; конкретика — предмет вопросов к вендору.
- Сметы, лицензионные расчёты, выбор конкретных моделей серверов.
- Пошаговые инструкции установки и конфигурации «под ключ» — достаточно
  ссылок на механизмы и компоненты из CONTEXT.md.
- Сравнение с продуктами других вендоров, кроме случаев обоснования
  отвергнутых альтернатив.

## 8. Критерии приёмки (кратко)

Полные рубрики — в `RUBRICS.md`. Ключевые точки отсечения («hard fail»):

- продуктам категории «Сервисы безопасности» (IAM SE / IDM / SOWA /
  Audit SE / SecMan / OTT) приписаны как **факт** функции, отсутствующие
  в источниках (CONTEXT §1.1, §1.9), — без пометки «требует проверки у
  вендора»;
- заявлено, что TDE Pangolin **сама по себе** защищает данные от
  привилегированных пользователей (DBA, администратора ОС) без отдельного
  механизма защиты от привилегированных пользователей;
- продукт Platform V представлен как самостоятельное закрытие процессной
  меры (пентест, оценка соответствия по ГОСТ Р 57580.2, классификация
  защищаемой информации, DR-учения);
- решение оставляет пароли/секреты открытым текстом в конфигурациях
  продуктов (включая документированные дефолты инсталлятора Corax) при
  наличии штатных механизмов их исключения — без обоснования;
- функции Enterprise-редакции Pangolin заявлены при лицензии Standard
  без решения о смене редакции;
- отсутствует хотя бы один из обязательных артефактов D1–D10.
