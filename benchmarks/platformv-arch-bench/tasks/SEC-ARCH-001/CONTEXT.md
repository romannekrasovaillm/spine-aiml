### 1.3 DataMarts 2.4.0 — безопасность OLAP-контура

- Компоненты: `datamarts-server` (ClickHouse Server), `datamarts-keeper`
  (ClickHouse Keeper, Raft, минимум 3 экземпляра на разных серверах;
  digest-аутентификация с `superdigest` из SecMan), `datamarts-safeguard`,
  `datamarts-rrm` + `datamarts-rrm-udf` (исполнитель изменений ролевой
  модели), `datamarts-vault-provider` (выпуск, наблюдение и перевыпуск
  wrapped_token для каждого компонента), аудит-компонент (источник
  событий — `query_log`/`session_log`; метрики `audit_log_lines_scanned`,
  `audit_records_generated`, `audit_records_merged`).
- **RBAC**: объекты доступа — учётные записи, роли, политики строк,
  профили настроек, квоты. «По умолчанию в системе нет других ролей
  кроме администратора»; рекомендация: «в производственных средах
  рекомендуется отключать пользователя по умолчанию после настройки».
  Ролевая модель — XML-файлы (`int_roles.xml`, `int_users.xml`;
  рекомендовано для ТУЗ) или SQL (`CREATE ROLE`/`GRANT`).
  Централизованное развёртывание — через `datamarts-rrm`: запросы с
  `task_id` в служебную таблицу → UDF `udf_rrm` → проверка правил
  ограничений → исполнение, журнал `UDF_LOGS` (OK/FAILED/INCOMPLETE).
- **Аутентификация**: LDAP, Kerberos, внутренние схемы; TLS на
  соединениях; «возможна интеграция с внешними системами шифрования
  данных».
- **OCSP** (проверка отзыва сертификатов): `ocsp_enable_check` (по
  умолчанию 1) для клиентских HTTPS, PostgreSQL и Kafka; настраиваемые
  таймауты и кеш.
- **SecMan**: пароли при интеграции с SecMan в файлы не вписываются
  (KV-секрет); TTL паролей из секрета (`data.ttl`, макс. 315 532 800 с;
  `lease_duration` по умолч. 86 400 с); предупреждения об истечении
  (`PasswordExpiringWarning`/`PasswordExpiredWarning` в
  `system.text_log`); если секрет с паролем отсутствует — «работа
  сервиса останавливается».
- **Аудит safeguard**: `/var/log/audit/datamarts-audit.log` (rsyslog,
  права 0640, ротация 100 МБ × 10 архивов × 30 дней); события: успешная
  аутентификация (**по умолчанию ВЫКЛЮЧЕНА**), неуспешная
  аутентификация, назначение профиля, блокировка УЗ; события тех.
  информации и аудита безопасности — в разные файлы.
- **Белый список интеграций**: LDAP, SecMan, white-list, Kafka,
  PostgreSQL, **IDM** (упомянута как «система идентификационного
  управления»; механика интеграции в съём не вошла — [ТРЕБУЕТ
  ПРОВЕРКИ]). Системные требования (опционально): SecMan 01.015.03-06,
  IDM 2.3.1+.
- Мониторинг: системные таблицы, экспорт «например в формате
  Prometheus» (mTLS с клиентским сертификатом); метрики включают
  `vault_tokens_issued`, `krb_tickets_issued`.
- Ограничения источников: версия ядра ClickHouse, HTTP 8123/JDBC/ODBC,
  резервное копирование, движок версионных таблиц, партиционирование —
  [ТРЕБУЕТ ПРОВЕРКИ]. DataMarts — **не OLTP** (пакетные INSERT + фоновые
  мутации); система записи остаётся на Pangolin.

Источник: `banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/architecture-security.md`;
`banking/plugins/ru-data/skills/datamarts-mpp-analytics/SKILL.md`;
`banking/plugins/ru-data/skills/datamarts-mpp-analytics/references/integrations-load.md`.

### 1.4 Radish 2.2.0 — безопасность KV-кэша

- **Согласованная ACL-модель** для всех режимов (master, Sentinel,
  Cluster): единственный источник изменений; запрет локальных изменений
  вне протокола; каноническое представление с хешем `acl_sha256`;
  обнаружение и автовосстановление рассинхронизации; **аудит с
  обязательным маскированием паролей**.
- Распространение ACL: master–replica — команды `ACL SETUSER_GLOBALLY` /
  `ACL DELUSER_GLOBALLY` (удаляет УЗ и разрывает соединения на всех
  узлах) / `ACL SAVE_GLOBALLY` только на мастере, в потоке репликации
  (на репликах ACL-write запрещены), гарантия доставки — `WAIT <N>
  <timeout>`; Sentinel — через Pub/Sub-канал `__sentinel__:hello`;
  Cluster — через cluster bus, изолирован от репликации данных.
- Прочее: TLS-шифрование соединений; **шифрование резервных копий
  GPG**; `requirepass`/`primaryauth`; роли Admin/User; управление
  секретами — SecMan 1.13.0+ или HashiCorp Vault 1.7.0+ (опционально).
- Профиль: Radish — **не система записи** критичных данных (асинхронная
  репликация, `WAIT` ≠ сильная консистентность); для защищаемой
  информации — только кэш поверх системы записи (Pangolin).

Источник: `banking/plugins/ru-data/skills/radish-kv-architecture/references/compatibility-ops.md`
(«Безопасность: согласованная ACL-модель»);
`banking/plugins/ru-data/skills/radish-kv-architecture/SKILL.md`.

### 1.5 Corax 16.392.0 — безопасность событийной шины

- **Каналы**: TLS 1.2 и 1.3 (все соединения, включая ZooKeeper и Schema
  Registry), mTLS, настраиваемые cipher suites; требование документации:
  «протокол TLS не ниже 1.2 (рекомендуется 1.3)».
- **Аутентификация**: SSL/mTLS по X.509 (в т.ч.
  `FingerprintKafkaPrincipalBuilder` — по отпечатку сертификата,
  по умолчанию SHA-256); Kerberos (SASL/GSSAPI, keytab).
- **Авторизация**: ACL по ресурсам CLUSTER, GROUP, TOPIC,
  TRANSACTIONAL_ID, DELEGATION_TOKEN, USER; ALLOW/DENY; `CoraxAuthorizer`
  (метрики включают BypassCount — fallback на базовую авторизацию).
  «Restricted Authorizer» упомянут в НФТ, отдельной страницы в съёме
  нет — [ТРЕБУЕТ ПРОВЕРКИ].
- **Аудит**: встроенный плагин (создание/удаление топиков, ACL, смена
  конфигурации, перераспределение партиций, consumer-группы, квоты);
  `kafka.se.audit.enable` по умолчанию true. Провайдеры:
  `TsAuditProvider` — отправка в компонент **COTE** продукта **Platform V
  Monitor** по HTTPS (`kafka.se.audit.send=false` — только лог-файл);
  `LogAuditProvider` — `kafka-audit.log`. Фильтры-подавители
  `kafka.se.audit.suppress.*`.
- **Шифрование паролей конфигураций**: утилиты `bin/crx-encoding.sh` и
  `bin/crx-password-encrypt.sh` (PBKDF2WithHmacSHA1 + AES/CBC/
  PKCS5Padding, ключ 256 бит; дешифрование не поддерживается); профиль
  установки **with-auth** шифрует пароли в server.properties /
  zookeeper.properties / schema-registry.properties, в остальных
  профилях шифрование выключено. **Дефолтный ключ шифрования и пароль
  `qwe123` опубликованы в документации инсталлятора** — в проме замена
  обязательна (вывод дистиллята из факта публикации дефолтов).
- **Сквозное (e2e) шифрование** данных в топиках: симметричное
  (`EncryptedByteArraySerializer/Deserializer`) и асимметричное
  (`EncryptedCertByteArraySerializer/Deserializer`, RSA/ECB/PKCS1Padding,
  конфигурирование «только путём редактирования кода»); на стороне
  клиента, не зависит от настройки соединения с брокерами.
- **SecMan**: хранение секретов и выпуск сертификатов (PKI mount,
  fetch role/CN), `SecmanSslEngineFactory`, параметры `secman.*`;
  профиль установки `SSL__ZK_mTLS_WITH_AUTH__KAFKA_SSL_WITH_AUTH__SECMAN`
  — без ручной подготовки X509. Есть Vault Java Driver (интеграция с
  HashiCorp Vault, НФТ). **SSL live update**: ротация сертификатов
  брокеров без недоступности (по одному брокеру, с контролем
  репликации).
- **Schema Registry**: HTTP Basic («пароли хранятся в файле ТОЛЬКО в
  зашифрованном виде»); роли ADMIN / ADMIN_AS / USER; ACL на каждый
  запрос; неаутентифицированный доступа не имеет. Хранилище схем —
  топик `_crx_schemas` с Records Policy (брокер-сайд валидация; «НЕ
  ВХОДИТ в состав Apache Kafka и доступен только при использовании
  Corax»).
- Ограничения источников: точная версия ядра Kafka, Restricted
  Authorizer, kTLS — [ТРЕБУЕТ ПРОВЕРКИ].

Источник: `banking/plugins/ru-integration/skills/corax-event-streaming/references/security-schema-registry.md`;
`banking/plugins/ru-integration/skills/corax-event-streaming/SKILL.md`;
`banking/notes/platformv-map-20260902.md` («Пробелы волны 3», пп. 4–5).

### 1.6 SynGX 4.3.0 — безопасность edge-контура

- Промышленный **веб- и обратный прокси-сервер** на кодовой базе Nginx
  1.28.3; VM-продукт (RPM/DEB, systemd).
- **TLS** для клиент ↔ SynGX и SynGX ↔ upstream; «необходимо
  использовать версию протокола TLS не ниже 1.2»; проверка сертификата
  backend-узла (`proxy_ssl_verify` + `proxy_ssl_trusted_certificate`).
- **Контроль доступа**: ACL по адресам, HTTP Basic, подзапрос к внешнему
  сервису авторизации (auth-request), **проверка CN/SAN клиентского
  TLS-сертификата** (mTLS), модуль **nginx-auth-jwt** (проверка JWT),
  GeoIP, rate limiting (`limit_req`, `limit_req_by_node`).
- **HashiCorp Vault / SecMan** (`ngx_hashicorp_vault_module`):
  автозагрузка сертификатов и секретов; аутентификация AppRole
  (role_id + wrapped_token → secret_id → client token); публичная часть
  сертификата — на файловую систему, **закрытый ключ — только в shared
  memory**; сам запрашивает новый сертификат с перезагрузкой при его
  изменении. Ограничения: один блок `hv_pki`/`hashicorp_vault` на
  инстанс; между использованием wrapped_token и получением нового
  stop/quit/reload блокируются.
- **Аудит**: директива `audit_log` (файл или syslog UDP 514; **по
  умолчанию выключен**). События: идентификация по CN/SAN и
  логину/паролю, авторизация, изменения конфигурации, изменения
  rate limit через `limit_req_change` (управление лимитами — только с
  127.0.0.1/unix-сокета).
- **Метрики — только pull** («возможность настроить SynGX, чтобы он
  самостоятельно отправлял метрики в какую-либо систему, не
  предусмотрена»); эндпоинты метрик защищаются (TLS ≥ 1.2, имя/пароль,
  ограничение по адресам). «В SynGX нет функциональности отправки логов
  по протоколу Kafka» — только файлы/syslog через стороннее ПО.
- **WAF / ModSecurity в документации 4.3.0 не упоминается ни разу** —
  зафиксировано как отсутствие функции. `hide_syngx_name on` — скрытие
  имени сервера в ответах; уровень Debug журналирования «не
  рекомендуется в промышленных инсталляциях».

### 1.8 Регуляторная карта «продукт → линии надзора»

Базовая позиция карты: **штатные функции продукта закрывают технические
меры** (шифрование, разграничение доступа, аудит, резервирование);
**схема БД, процессы ДИТ и DR-учения остаются на уровень решения** —
продукт их не выполняет и не гарантирует.

| Регуляторная линия | Штатная функция продукта | Остаётся на уровень решения |
|---|---|---|
| Хранение защищаемой информации (719-П прил. 1 № 10 — 5 лет в неизменном виде; п. 2.2) | TDE (Pangolin Enterprise); аудит по ГОСТ Р 59548 (Pangolin); версионные таблицы + аудит `query_log`/`session_log` (DataMarts) | классификация данных, append-only-схема, retention-политика |
| Доступ — идентификация/аутентификация/авторизация (719-П прил. 1 № 1) | RBAC/LDAP (Pangolin), ACL-модель (Radish), RBAC + datamarts-rrm (DataMarts), ролевая модель + межсервисная аутентификация (Synapse) | ролевая матрица, привязка к IDM банка, периодический пересмотр прав |
| Защита обмена сообщениями / взаимная аутентификация (719-П прил. 1 № 3, № 4) | Kerberos/SASL, TLS, OCSP (DataMarts), сквозная аутентификация Pooler ↔ СУБД (Pangolin), SCT + KACM/PKI (Synapse) | выбор криптоканалов (ГОСТ-СКЗИ — GAP-C2), схема ключевого хозяйства |
| Резервирование/восстановление (719-П прил. 1 № 11) | Patroni HA (Pangolin), Sentinel/кластер (Radish), ReplicatedMergeTree + keeper-Raft (DataMarts), GEOH (Synapse) | DR-учения (фактические RTO/RPO), runbook failover, частота проверок |

Единый список «что остаётся на уровень решения» (дословно):

1. **Классификация защищаемой информации** (719-П п. 2.2; 683-П п. 1).
2. **Схема БД и append-only-дисциплина** (719-П прил. 1 № 10,
   «неизменный вид», retention 5 лет).
3. **Ежегодный pentest / анализ уязвимостей** (851-П пп. 3.2; 683-П
   п. 2; 719-П п. 1.1) — процесс, продукт не проводит.
4. **Оценка соответствия по ГОСТ Р 57580.2** (уровень ≥ 4, не реже раза
   в 2 года — 719-П п. 2.4; 851-П п. 13; 683-П п. 9) — проверяющая
   организация, не продукт.
5. **Сертификация ПО** (719-П п. 2.5, уровни доверия 4/5; 851-П пп. 4.1;
   683-П п. 4.1) — вопрос вендора/сертификации, не решается в проекте.
6. **Уровень защиты по ГОСТ Р 57580.1** (усиленный/стандартный — 851-П
   пп. 3.1; 683-П п. 3.1) — определяется статусом банка, не продуктом.
7. **DR-учения и фактические RTO/RPO** (719-П прил. 1 № 11).

Гипотезы карты (обязательств не создают): **ГОСТ-СКЗИ каналов** (851-П
п. 6, приказ ФСБ № 378) — закрывается ли штатным TLS/Kerberos продуктов
или требуется ГОСТ-TLS-прокси (GAP-C2) — [ТРЕБУЕТ ПРОВЕРКИ];
**редакция Pangolin Enterprise** как условие TDE/LDAP — зависимость
лицензии, фиксируется в ADR; **прямой CDC в DataMarts** — не описан,
[ТРЕБУЕТ ПРОВЕРКИ]. Правило карты: ссылаться на неё как «какая мера уже
есть в продукте»; **не декларировать соответствие — только механизмы**.

поданное как факт, — ошибка; легитимное оформление — «[ТРЕБУЕТ

6. **ГОСТ-СКЗИ**: применимость штатного TLS продуктов к требованиям

7. **Synapse (AM/SEI)**: детальная механика фильтрации трафика и

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Искра"» (вымышленный, топ-30 по активам, ~3,8 млн клиентов
физических лиц, ~90 тыс. корпоративных клиентов) эксплуатирует ландшафт
из ~340 АС. Ключевые слои переведены на продукты Platform V (§2.2).
Внешний контур ИБ банка (SIEM, PAM, УЦ/PKI, SOC, антивирус, сканер
уязвимостей) существует и развивается отдельной программой.

Внешний аудит ИБ (2026 г.) зафиксировал системные проблемы ландшафта
Platform V:

- локальные учётные записи в СУБД, брокере и прокси не связаны с
  корпоративным каталогом; блокировка уволенного сотрудника занимает до
  2 рабочих дней;
- пароли ТУЗ хранятся открытым текстом в конфигурационных файлах и
  Ansible-инвентарях; ротация — «по инцидентам»;
- TLS-сертификаты выпускаются вручную, файлы закрытых ключей лежат на
  ВМ, в т.ч. в DMZ;
- события аудита продуктов пишутся локально и в SIEM попадают с
  задержкой до 6 часов (часть не попадает вовсе);
- нет формальной матрицы «кто отвечает за меру защиты»: продукт,
  внешний контур ИБ или процесс — при проверке 719-П ряд мер «повис в
  воздухе».

Архитектурный комитет инициировал программу **«Единый контур доверия»**;
первый этап — целевая архитектура безопасности ландшафта Platform V.
Решение о внедрении продуктов категории «Сервисы безопасности» линейки
(IAM SE, IDM, SOWA, Audit SE) — в стадии pre-sale: **документация
вендора на них банку недоступна** (INF-05); допустимо оперировать
только их позиционированием из §1.1 и формулировать вопросы к вендору.

| SEC-11 | Вопрос применимости ГОСТ-СКЗИ к каналам ландшафта (851-П п. 6) явно разрешён в архитектуре (подтверждение у вендора либо внешнее СКЗИ-решение); замалчивание не допускается |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами.
- Комитет особенно чувствителен к трём вопросам: (1) **матрица
  ответственности** «продукт / внешний контур ИБ / процесс» — без
  «повисших» мер; (2) **обоснование редакции Pangolin** (Standard →
  Enterprise?) с перечнем функций, ради которых меняется лицензия;
  (3) честность по продуктам без доступной документации (IAM SE / IDM /
  SOWA / Audit SE): что именно будет запрошено у вендора.
- Решение реализуемо силами команды INF-08 штатными механизмами
  продуктов и GitOps.

### 2.8 Что можно принять допущением `[ASSUME]`

- Vault банка (INF-04) доступен из обоих ЦОД с латентностью ≤ 5 мс; его
  HA/DR — зона ответственности команды ИБ-платформ.
- Корпоративный каталог LDAP предоставляет атрибуты ролей, достаточные
  для маппинга на ролевые модели продуктов.
- SIEM (INF-03) принимает события по syslog и через HTTPS-агентов;
  превышение 25 000 EPS согласуется отдельно.
- Кадровая система публикует события увольнения в шину (Corax) с
  задержкой ≤ 1 мин.
- Оценку EPS по компонентам (NFR-04) решающий выполняет сам как
  допущение с явной методикой.
