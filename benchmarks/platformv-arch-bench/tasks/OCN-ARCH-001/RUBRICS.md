# Рубрики оценки для задачи OCN-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о продукте,
   которого нет в §1 и которое не помечено решающим как допущение или вопрос
   к вендору, считается **непроверенным**; если оно ещё и ложно — **ложным**.
   Судья не должен «додумывать» за решающего.
3. **Нейтральность к выбору.** Выбор Ocean DB или Pangolin DB сам по себе не
   является правильным или неправильным. Оцениваются качество критериев (C3),
   честность о последствиях выбора (C5, C7, C10) и обоснованность. Одинаково
   штрафуются и «маркетинговый» выбор Ocean DB без учёта пробелов §1.9, и
   «консервативный» выбор Pangolin без анализа масштаба данных NFR-06.
4. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (NFR/SEC/INF) и обоснованное, а не за наличие ключевого слова.
5. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/поверхностно;
   2 — базово корректно, есть пробелы; 3 — полно и обоснованно, мелкие
   недочёты; 4 — образцово: полно, обоснованно, с учётом компромиссов и
   ловушек §4. Промежуточные уровни (1, 3) — интерполяция между якорями.
6. **Цитирование доказательств.** Для каждого критерия судья приводит 1–3
   коротких цитаты (≤ 25 слов) из ответа и указывает, чего не хватает до
   следующего уровня.
7. Судья не оценивает стиль и «красоту» сверх C11 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Топология Ocean DB без кворума: предложено **менее 3 зон/реплик** (или чётный состав Paxos-группы) без явного обоснования и компенсирующих мер; либо **большинство зон размещено в одном ЦОД** и при этом заявлена автоматическая доступность при потере этого ЦОД | Найти число зон/узлов и их размещение; A-06; mechanical_checks |
| HF-02 | Вымышленные или переименованные компоненты поданы как факт («Ocean Manager», «Ocean Pooler», «Ocean DCS», «Ocean Vault», «OCP-кластер» и т.п.) вместо официальных OBSERVER / OBAGENT / OBPROXY / OBCLIENT / RootService / Resource Unit | A-05, таблица ловушек §4, mechanical_checks |
| HF-03 | Недокументированные возможности Ocean DB 1.1.0 (CONTEXT §1.9) поданы как **факт**: Oracle-режим арендаторов, сертификация ФСТЭК/ФСБ, ГОСТ-криптография, CDC в Kafka, межкластерная/standby-репликация — без пометки «требует проверки у вендора» | A-05, mechanical_checks (частично); требует LLM-подпроверки семантики |
| HF-04 | Заявлен **RPO = 0 при полной потере ЦОД-1** для топологии, где большинство зон (2 из 3) находится в одном ЦОД, без описания механизма сохранения кворума | A-06; сверка с CONTEXT §1.4; только судья |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01, mechanical_checks |

## 3. Критерии

### C1. Фактическая корректность по Ocean DB (вес 12)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md §1;
корректные наименования компонентов; отделение фактов от допущений; корректная
работа с расхождением вендора по RTO (<30 с vs <8 с).

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-02 или HF-03, либо ≥ 4 ложных утверждения о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (Paxos-группы, OBProxy, Resource Unit, обязательная ОС), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение/вопрос к вендору; расхождение RTO зафиксировано и заложено консервативное значение 30 с; корректно используются порты 2883/2881, формат `user@tenant#cluster`, типы арендаторов |

**Признаки сильного ответа:** использует официальные имена (OBSERVER, OBAGENT,
OBPROXY, OBCLIENT, RootService, Resource Unit, арендатор); знает, что протокол
MySQL-совместимый (не PostgreSQL); помнит про обязательную ОС SberLinux OS
Server **9.6.2** (а не «любой SberLinux»); не приписывает Ocean DB функции
Pangolin (TDE, защита от привилегированных пользователей) и наоборот.

**Типичные ошибки:** «Ocean DB — PostgreSQL-совместимый»; «OBSERVER =
Patroni-подобный оркестратор»; «OBProxy — аналог PgBouncer с пулами сессий»
(он stateless-маршрутизатор партиций); приписывание Pangolin-возможностей
(автопартиционирование, ora2pg) Ocean DB.

### C2. Позиционирование Ocean DB vs Pangolin и решение (вес 14)

**Что оценивается:** D2 + D3. Корректность сравнительной матрицы по CONTEXT
§1.11 и полнота её адаптации к сценарию; итоговое решение и его обоснование.

| Уровень | Якорь |
|---|---|
| 0 | Сравнения нет, или решение заявлено без матрицы и критериев |
| 2 | Матрица скопирована из CONTEXT §1.11 без привязки к сценарию; решение названо, но обоснование декларативно («Ocean DB современнее» / «Pangolin привычнее») |
| 4 | Матрица сопоставляет продукты по осям, выведенным из требований сценария: объём данных (NFR-06: ~250 ТБ сырых → масштабирование/сжатие), сезонность (NFR-05 → эластичность Ocean / запас мощности Pangolin), латентность (NFR-02 → НФТ обоих классов), HA-модель (NFR-03/04 → Paxos 3 зоны против Patroni leader+standby), протокол и компетенции (INF-07), HTAP-антифрод (NFR-07), безопасность/сертификация (SEC-01/SEC-06 → пробелы §1.9 у Ocean, TDE/Certified у Pangolin); решение единственное и обосновано «почему так, а не иначе»; последствия выбора (что теряем) зафиксированы |

**Ловушки:** выбор Ocean DB «потому что 300 000 TPS» без сопоставления с
реальным профилем 3000 TPS; выбор Pangolin без анализа, влезает ли 250+ ТБ в
один-лидер топологию; игнорирование того, что у Ocean DB нет документированной
миграции с Oracle (в сценарии не нужна — greenfield — и это корректно
отметить, а не драматизировать).

### C4. Целевая топология и кворум (вес 14)

**Что оценивается:** D4. Схема размещения выбранного решения по ЦОД/зонам,
состав компонентов, точки подключения приложения, соответствие INF-01/INF-02.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы, или схема без размещения по ЦОД/зонам; HF-01 |
| 2 | Схема есть, но: размещение зон при двух ЦОД не объяснено (почему так, что будет при потере каждого ЦОД); точка подключения приложения не показана; число узлов не связано с нагрузкой |
| 4 | Для **Ocean DB**: ≥3 зон доступности с явным размещением по ЦОД (например, 2 зоны в ЦОД-1 + 1 в ЦОД-2) и **честным разбором**, что теряется при потере каждого ЦОД (потеря ЦОД с 2 зонами = потеря кворума = NFR-04 не выполняется автоматически → риск/вопрос, а не замалчивание); обосновано, почему облачная зона INF-01 (2 ВМ 4vCPU/8ГБ) **не годится** под зону OBServer (минимальная конфигурация 8 CPU/16 ГБ/200 ГБ SSD, зона полнокопийна); OBProxy-ферма за балансировщиком (INF-06) в каждом ЦОД; OBAGENT на узлах; число узлов связано с C6. Для **Pangolin**: лидер+реплики с кворумным DCS (нечётный состав, третий голос — облачная зона INF-01), пулеры, standby в ЦОД-2. В обоих случаях: показано, как приложение находит точку записи; учтён лимит INF-02 (≤9 серверов на ЦОД) |

**Ловушки:** «3 зоны» без привязки к ЦОД; арбитр в облачной зоне для Ocean DB
(в документации нет понятия witness-зоны — это допущение, требующее проверки);
Paxos-группа из 2 реплик; применение механики Patroni/DCS к Ocean DB.

### C5. HA/DR: сценарии отказов и RPO/RTO (вес 12)

**Что оценивается:** D5, соответствие NFR-01, NFR-03, NFR-04.

| Уровень | Якорь |
|---|---|
| 0 | Сценариев отказов нет; HF-04 |
| 2 | Описан отказ узла/зоны со ссылкой на RPO=0/RTO<30 с, но: сценарий потери ЦОД не разобран или заявлен RPO=0 при потере ЦОД для конфигурации 2+1; обратное восстановление ЦОД не описано |
| 4 | Три сценария с числами: (a) отказ узла/зоны → перевыборы лидера партиций, RPO=0, RTO ≤ 30 с (консервативно, не 8 с) → NFR-03; (b) потеря ЦОД-1 → честная оценка достижимости NFR-04 (для 2+1: кворум теряется, RTO/RPO определяются ручной процедурой или недокументированной межкластерной репликацией → вопрос к вендору, компенсирующие меры: PITR из архива S3/NFS в ЦОД-2 с оценкой RTO); (c) возврат ЦОД-1 → реинтеграция узлов/реплик. Для Pangolin-варианта: failover внутри ЦОД и переключение на standby-кластер в ЦОД-2 с режимами репликации, увязанными с RPO |

**Ловушки:** RPO=0 при потере ЦОД «потому что Paxos»; RTO <8 с заложено как
гарантия; «приложение само переключится» без механизма (OBProxy перенаправляет
к новому лидеру — документировано; для Pangolin механизм надо спроектировать).

|---|---|

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "OCN-ARCH-001-RUB",
  "task_id": "OCN-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` считается по формуле из frontmatter; `verdict = excellent`
при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.
