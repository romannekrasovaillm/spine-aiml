## 1. Продукт: Platform V Ocean DB `[DOC]`

### 1.1 Что это и позиционирование

- **Platform V Ocean DB (код OCN, актуальная версия документации 1.1.0)** —
  распределённая СУБД, объединяющая OLTP и OLAP в едином движке (**HTAP**),
  на архитектуре **Shared-Nothing**.
- Класс задач по вендору (портал Platform V): системы с транзакционным
  изменением данных и требованиями к консистентности; высоконагруженные
  системы, **шардирующие нагрузку** между инстансами реляционной БД; системы
  с плохо предсказуемой или **сезонной нагрузкой**; сверхбольшие объёмы
  данных.
- Правило выбора из дистиллята: **Pangolin** — классический OLTP банка,
  PostgreSQL-совместимость, миграция с Oracle, зрелая эксплуатация;
  **Ocean DB** — сверхбольшие объёмы (сотни ТБ на кластер), шардинг нагрузки,
  непредсказуемая/сезонная нагрузка, гибрид OLTP+аналитика без отдельного
  DWH, консолидация множества БД через multi-tenancy, встроенный семантический
  поиск.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.2 Архитектура и компоненты

Архитектура семейства OceanBase; имена компонентов совпадают напрямую:

| Компонент | Назначение |
|---|---|
| **OBSERVER** | Ядро СУБД: SQL Engine; Storage Engine (**LSM-Tree**, многоуровневое сжатие, авторебалансировка); Transaction Engine (распределённые транзакции на **Paxos**, изоляция Read-Committed и Serializable); **RootService** (метаданные, топология, восстановление) |
| **OBAGENT** | Агент мониторинга, соразмещён с OBSERVER на каждом узле (1 CPU / 2 ГБ / 20 ГБ на узел) |
| **OBPROXY** | **Stateless** прокси доступа: маршрутизация к узлу с данными, балансировка, сокрытие топологии; отслеживает расположение лидеров партиций и перенаправляет запросы к новому лидеру |
| **OBCLIENT** | Драйверы JDBC/ODBC/C и CLI |

Каждая партиция данных — **группа Paxos** из нескольких реплик в разных зонах
доступности; коммит — после подтверждения большинством.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md;
banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md

### 1.3 Подключение и мультиарендность

- Протокол: **MySQL-совместимый**. Поддерживается штатный `mysql`-клиент.
- Через OBProxy (рекомендуется): порт **2883**, пользователь в формате
  `user@tenant#cluster`; напрямую к OBServer — порт **2881**, `user@tenant`.
- Проверка контекста подключения:
  `SELECT effective_tenant_id(), user(), database();`
- С версии ядра 4.0 — три типа арендаторов: **системный (sys)**,
  **пользовательский** и **мета**. Системный арендатор совместим с
  MySQL-протоколом, управляет кластером и арендаторами.
- Мультиарендность: **Resource Unit** = квоты CPU/память/IO на арендатора;
  вертикальное масштабирование арендатора без перезапуска; перемещение
  ресурсных единиц между узлами; онлайн-изменение квот.
- OBProxy stateless — масштабируется любым числом экземпляров за обычным
  балансировщиком; кэш расположения партиций минимизирует межузловые
  обращения.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md;
banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.4 Отказоустойчивость (HA/DR)

- **RPO = 0** при сбое узла или целой зоны (коммит после подтверждения
  большинством Paxos-группы партиции).
- **RTO**: страница «Преимущества» заявляет **< 30 с** при отказе узла или
  целой зоны; паттерн надёжности заявляет **< 8 с** (перевыборы лидера без
  администратора). Это **расхождение вендора**; в ADR закладывать
  консервативные **30 с**.
- Топологии: **3+ зоны доступности** в одном или нескольких ЦОД; «горячая»
  замена узлов и роллинговые обновления без остановки.
- OBProxy перенаправляет запросы к новому лидеру партиции — failover
  прозрачен для приложений.
- Автобалансировка в фоне: объём данных, интенсивность запросов, правила
  locality, приоритеты зон.

### 1.6 HTAP и изоляция нагрузок

- Аналитические запросы выполняются **на актуальных транзакционных данных,
  без выгрузки и ETL**.
- Механизмы: направление аналитики на реплики-подписчики (не нагружая
  лидера); оптимизатор выбирает план под тип нагрузки; параллельное
  выполнение сложных запросов на нескольких узлах.
- Изоляция: транзакционная и аналитическая нагрузки — в **разных арендаторах
  с квотами Resource Unit**.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md

### 1.7 Масштабирование и сжатие

- Shared-Nothing: каждый OBServer хранит и обрабатывает свою часть данных;
  **добавление узла — SQL-командами административного интерфейса, без
  остановки**; узел доступен для размещения Resource Unit арендаторов.
- Авторебалансировка партиций после изменения топологии, в фоне; скорость
  миграции данных управляется параметрами кластера.
- «Поддерживаются кластеры, объединяющие **сотни узлов** с объёмами данных на
  уровне **петабайт**».
- Сжатие: SSTable + кодирование при Major Compaction; алгоритмы **zstd, lz4,
  snappy, zlib**; экономия **70–80 %** (страница «Преимущества») / **70–90 %**
  (паттерн горизонтального масштабирования) дискового объёма.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md

### 1.8 Долговечность, резервное копирование, PITR

- **ACID полностью**; изоляция Read-Committed и Serializable (нет грязного
  чтения, неповторяемого чтения, фантомов).
- Долговечность: **синхронный WAL на нескольких репликах (по умолчанию три)**.
- Архивирование на **NFS / S3-совместимые хранилища** по расписанию или по
  требованию.
- **PITR с точностью до секунды**.

### 1.11 Сравнение с Platform V Pangolin DB (из дистиллята)

| Ось | Pangolin DB (PSQ 8.2.0) | Ocean DB (OCN 1.1.0) |
|---|---|---|
| Класс | OLTP-сборка PostgreSQL, «для задач аналитики — специализированные продукты» | HTAP: OLTP+OLAP в одном движке, без ETL во внешнее хранилище |
| Масштабирование | Вертикальное + read-реплики; **один лидер** | Горизонтальное: добавление узлов без остановки, авторебаланс партиций; «сотни узлов, петабайты» |
| HA/DR | Manager (Patroni) + DCS (Raft): RPO=0, RTO<6 мин/год; **standby-кластер, N-ЦОД** | Paxos-группы на партицию, 3+ зоны: RPO=0, RTO<30 с (в паттерне — <8 с) |
| Протокол/совместимость | PostgreSQL-протокол, миграция с Oracle/MS SQL (ora2pg, orafce, FDW) | MySQL-протокол; матрица совместимости клиентов в доках 1.1.0 — незаполненный шаблон |
| Изоляция нагрузок | Ресурсные ограничения PostgreSQL | Мультиарендность: Resource Units (квоты CPU/RAM/IO на арендатора), онлайн-изменение |
| Доп. возможности | TDE, автопартиционирование, глобальные индексы (Enterprise) | Встроенный векторный поиск и AI-функции SQL |
| Целевая ОС | Шире (см. PSQ) | Только SberLinux OS Server 9.6.2 (обязательно) |

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Прибрежный Банк» (вымышленный, топ-20 по активам, ~9 млн держателей карт)
в рамках программы «Собственный процессинг» строит **новую** систему — АС
«Фронт авторизационного процессинга» (АС ФАП): приём и обработка
авторизационных запросов по картам банка (эквайринг и эмиссия), ведение
авторизационного журнала, онлайн-контроль лимитов, передача событий в
антифрод.

АС ФАП относится к **системам общебанковского процессинга**; недоступность
более 10 минут влечёт обязательный инцидент-репорт в регулятора, а деградация
в пиковые даты — прямые репутационные потери. Это **greenfield**: миграции
данных нет; внешний процессинг работает параллельно до конца 2028 года.

СУБД-слой выбирается внутри контура вендора банка (Platform V): кандидаты —
**Ocean DB 1.1.0** и **Pangolin DB 8.2.0**. Архитектурный комитет ждёт одно
рекомендуемое решение с критериями выбора и целевой топологией.

### 2.2 Профиль нагрузки и данные

- Транзакция авторизации: 3–6 коротких SQL-операторов (проверка статуса
  карты, лимитов, запись авторизации); **70 % чтение / 30 % запись**, доступ
  преимущественно по первичному ключу.
- Нагрузка: средняя **800 TPS**, пиковая **3000 TPS** (вечерние часы,
  распродажи), сезонный пик до **3× от пиковой (≈9000 TPS)** на срок до
  10 дней (новогодний период).
- Объём на транзакцию: запись авторизации + 2–3 записи журнала ≈ **2 КБ**;
  оценка роста данных **~50 ТБ/год сырых данных**.
- Хранение: **5 лет онлайн** (требование к доступности истории авторизаций и
  спорных операций), далее архив.
- Аналитика: антифрод и отчётность выполняют запросы по **свежим данным**
  (допустимый лаг ≤ 5 минут), несколько десятков тяжёлых запросов в час.
- Приложение: Java 21 / Spring Boot, **40 подов на ЦОД** в Kubernetes
  (Platform V DropApp), active-active по приложению в двух ЦОД; пул
  соединений **25 на под** (настраиваемо).

### 2.3 Ландшафт банка AS-IS

- СУБД-стандарт банка для учётных систем: **Pangolin DB** (несколько
  промышленных инсталляций, опыт 3 года); Ocean DB в банке **не
  эксплуатируется**.
- Аналитическая платформа: **Platform V DataMarts** (ClickHouse-ядро) —
  витрины кормятся через CDC из учётных СУБД.
- Хранилище секретов: **HashiCorp Vault** (3 узла, растянут между ЦОД).
- СРК банка: S3-совместимое и NFS-хранилище в каждом ЦОД.
- Мониторинг: Zabbix + Prometheus/Grafana; SIEM; PAM для административных
  сессий.

### 2.4 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~40 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64: до **9 серверов в каждом ЦОД** под СУБД-слой (2×24 ядра, 384 ГБ RAM, NVMe 6×3,84 ТБ) |
| INF-03 | Стандарт ОС банка — **Platform V SberLinux OS Server** (эксплуатируются ветки 9.x и 10.x; выбор редакции согласуется с ОТБ) |
| INF-04 | СРК предоставляет S3-совместимое и NFS-хранилище в **каждом** ЦОД; требуется интеграция штатными средствами СУБД |
| INF-05 | Мониторинг Zabbix обязателен для промышленных систем; Prometheus/Grafana допустимы как дополнительный контур; аудит — в SIEM |
| INF-06 | Kubernetes-кластеры приложения (Platform V DropApp) в обоих ЦОД, приложение active-active; балансировщики L4/L7 банка доступны в обоих ЦОД |
| INF-07 | Команда сопровождения: 5 DBA (PostgreSQL/Pangolin — уверенно, MySQL — базово, Ocean DB — **нет опыта**), 1 администратор ИБ, 2 DevOps; контракт поддержки вендора 24×7 доступен |
| INF-08 | Окна плановых работ: ночь, не более 2 часов, не чаще раза в квартал; **приём авторизаций при этом не прерывается** |

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность АС ФАП (круглосуточно, 7×24×365) | ≥ 99,95 % в год |
| NFR-02 | Латентность транзакции на стороне СУБД (p99) при пике 3000 TPS | ≤ 10 мс |
| NFR-03 | Отказ одного узла или одной зоны доступности | RPO = 0; RTO ≤ 60 с, автоматически |
| NFR-04 | Полная потеря ЦОД-1 | RPO ≤ 5 мин; RTO ≤ 60 мин (допускается ручное решение) |
| NFR-05 | Сезонный пик ≈9000 TPS до 10 дней | без изменения аппаратного состава; допустимая деградация p99 ≤ 25 мс |
| NFR-06 | Ёмкость | 5 лет онлайн при ~50 ТБ/год + 30 % запас |
| NFR-07 | Антифрод/отчётность по свежим данным (лаг ≤ 5 мин) | без деградации OLTP более чем на 5 % по p99 |
| NFR-08 | PITR | глубина 35 дней; RTO восстановления полной БД из копии ≤ 8 ч |
| NFR-09 | Плановые обновления СУБД (минорные и в рамках линейки) | без остановки приёма авторизаций |
| NFR-10 | Одновременные подключения от приложения | до 2 500 |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные авторизаций (банковская тайна, PCI DSS) шифруются «на диске»; ключи — во внешнем хранилище секретов банка (Vault) |
| SEC-02 | TLS 1.2+ для всех соединений (клиент ↔ прокси ↔ узлы, межузловые); сертификаты корпоративного УЦ, ротация без простоя |
| SEC-03 | Разделение обязанностей: ни один администратор (DBA, ОС, ИБ) в одиночку не должен иметь возможность читать содержимое защищаемых таблиц |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит DDL и операций с защищаемыми объектами с передачей в SIEM |
| SEC-06 | АС ФАП находится в периметре ГОП/КИИ: предпочтительно ПО с сертификацией ФСТЭК; при её отсутствии — явное риск-решение с компенсирующими мерами |
| SEC-07 | Соответствие PCI DSS: сегментация CDE, минимизация хранения PAN (маскирование/токенизация на уровне приложения — вне скоупа СУБД, но должно быть учтено) |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами; «выбрать обе» не принимается, но допускается
  комбинация (например, разные СУБД для разных контуров) с обоснованием.
- Комитет особенно чувствителен к трём вопросам:
  1. как выбранное решение выполняет NFR-03/NFR-04 при наличии **только двух
     ЦОД** (INF-01);
  2. честный статус **безопасности и сертификации** Ocean DB (§1.9) и его
     влияние на SEC-01/SEC-06;
  3. готовность **команды** (INF-07) к эксплуатации выбранного продукта.
- Решение должно быть реализуемо силами INF-07 с поддержкой вендора.

### 2.8 Что можно принять допущением `[ASSUME]`

- Версии: Ocean DB 1.1.0, Pangolin DB 8.2.0 (или новее в рамках линейки).
- Приложение допускает доработку слоя доступа к данным (драйвер, диалект
  SQL, строка подключения) — система новая, legacy-кода нет.
- Vault банка доступен из обоих ЦОД с латентностью ≤ 5 мс.
- Оценка «~50 ТБ/год» дана бизнесом как верхняя граница; решающий обязан
  пересчитать ёмкость из исходных цифр §2.2 и показать вывод.
- Любая недокументированная возможность (§1.9) может быть включена в
  решение только как открытый вопрос к вендору с планом проверки (POC).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| Paxos-группа | набор реплик одной партиции данных; коммит — после подтверждения большинством |
| Зона доступности | изолированный домен отказа внутри топологии Ocean DB; 3+ зоны могут размещаться в одном или нескольких ЦОД |
| Арендатор (tenant) | логическая изолированная БД в кластере Ocean DB со своими Resource Unit |
| Resource Unit | квота CPU/память/IO, выделяемая арендатору |
| HTAP | гибридная транзакционно-аналитическая обработка в одном движке |
| PITR | восстановление на момент времени |
| TPS | транзакций в секунду |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| CDE | cardholder data environment (периметр PCI DSS) |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
