### 1.1 Роли продуктов в контуре и базовые факты

- **Platform V Pangolin DB (PSQ) 8.2.0** — специальная сборка PostgreSQL
  с доработками под безопасность, доступность, надёжность и эксплуатацию.
  Это **OLTP-СУБД, не MPP**; класс задач из документации —
  высоконагруженные OLTP и хранилища ПДн/критичных данных
  («безопасность банковского уровня»). Редакции: Standard / Standard для
  ERP / Enterprise / Enterprise для ERP; ключевые архитектурные функции
  (TDE, защита от привилегированных пользователей, глобальные индексы,
  нативное автопартиционирование, pgloader, pgcopydb, внешняя
  авторизация LDAP) — только Enterprise.
- **Platform V Corax (KFK) 16.392.0** — «программный брокер сообщений…
  распределенная, отказоустойчивая, реплицированная и легко
  масштабируемая система передачи сообщений», принцип «публикация —
  доставка»; **все сообщения Corax хранит на диске**. Состав компонента:
  Apache Kafka (обязателен), Apache ZooKeeper (в таблице «Назначение»
  помечен обязательным, но см. KRaft в §1.5), Corax Schema Registry,
  Corax UI, Corax Mirror Maker 2 (последние три опциональны). Ядро —
  Apache Kafka, в разделе «Нефункциональные особенности» указано
  «наследуя архитектуру Apache Kafka 3.9».
- **Platform V SynGX (SNX) 4.3.0** — продукт для промышленной
  эксплуатации в качестве высокопроизводительного и безопасного **веб- и
  обратного прокси-сервера** на кодовой базе **Nginx 1.28.3**. VM-продукт
  (RPM/DEB, systemd-юнит `syngx.service`), не K8s-оператор. Документация
  фиксирует ровно два паттерна применения: веб-сервер и обратный
  прокси-сервер (маршрутизация и балансировка запросов с учётом отказов
  инсталляций сервиса).

### 1.2 Pangolin DB: HA-кластер (внутри площадки)

- HA-кластер = 2+ сервера с экземплярами одной БД, связанные потоковой
  физической репликацией. Компоненты: **Pangolin Manager** (оркестратор;
  в поставляемой документации «Архитектура компонентов» — Patroni 4.1.1
  целиком; утилита `pangolin-manager-ctl` — patronictl-подобный CLI),
  **Pangolin DCS** (распределённое хранилище конфигурации на базе Raft;
  поддерживается и etcd/ZooKeeper/Consul из Patroni-наследия),
  **Pangolin Pooler** (доработанный форк PgBouncer).
- Заявленные целевые показатели кластера для mission critical:
  **RPO = 0** (нет потери данных при программном/аппаратном сбое) и
  **RTO = 6 минут в год** простоя; достигается горячим резервированием
  двух экземпляров в разных ЦОД (Active/StandBy) + автоматическим
  failover средствами Manager + пулер. Внимание: это показатель
  **суммарного годового простоя кластера**, а не бюджет времени
  DR-переключения между площадками.
- Репликация однопоточная → один лидер, остальные — реплики. Manager
  хранит запись о лидере в DCS (пара ключ-значение с TTL); при истечении
  TTL узлы проверяют доступность лидера, сравнивают позиции журнала
  транзакций, первый записавший себя в DCS становится лидером.
- Управление: CLI `pangolin-manager-ctl` и REST API (REST используют
  балансировщики типа HAProxy для health-check, мониторинга и
  автоматики). Операции: `list`, `pause`/`resume` (режим обслуживания),
  `reload`, `restart`, **`switchover`** (плановое переключение,
  гарантия нулевых потерь даже в асинхронном режиме), `failover`,
  `reinit` (пересоздание реплики с pg_basebackup). При работающем
  Manager управлять экземплярами как одиночными (`pg_ctl`, `systemctl`)
  — только в режиме `pause`, иначе кластер воспримет действия как сбой.
- **DCS failsafe mode** (Patroni): при полной недоступности DCS кластер
  продолжает работать, если все узлы видят лидера через его REST API.
- В дистрибутиве 8.2.0: pangolin-manager 4.2.0, pangolin-pooler 3.2.0.

Источник: `spine-bank/banking/plugins/ru-data/skills/pangolin-db-architecture/references/ha.md` (разделы «Состав HA-кластера», «DCS», «Pangolin Manager ↔ Patroni»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/psq_documents__administration-guide__administration-pangolin-manager__cluster.html.txt`, `psq_documents__architecture-components__patroni__dcs_failsafe_mode.html.txt`.

### 1.3 Pangolin DB: режимы репликации (trade-off доступность/сохранность)

- **Асинхронный (дефолт, `synchronous_mode: false`)**: максимум
  производительности; при сбое лидера теряются транзакции в пределах
  `maximum_lag_on_failover` байт WAL + записи за последние `ttl` секунд
  (в среднем `loop_wait` = 2 с).
- **Стандартная синхронная PostgreSQL** (`synchronous_commit: on` +
  `synchronous_standby_names`): коммит ждёт записи на реплику;
  рекомендовано ≥ 2 реплик, иначе сбой единственной реплики блокирует
  запись; при одновременной потере лидера и синхронной реплики Manager
  поднимет асинхронную — с потерей данных.
- **Нестрогий синхронный Manager (`synchronous_mode: true`)**: при
  недоступности реплики лидер переводится в standalone-режим (async) —
  доступность на запись сохраняется; failover только на реплику со всеми
  зафиксированными транзакциями, иначе кластер недоступен на запись до
  ручного `failover` (с потерями).
- **Строгий синхронный (`synchronous_mode_strict: true`)**: failover
  только на синхронную реплику; перевод в async запрещён — максимум
  сохранности ценой доступности (при потере синхронной реплики —
  недоступность на запись).
- Выбор режима — явный trade-off доступность/сохранность, фиксируется в
  архитектурном решении.

Источник: `spine-bank/banking/plugins/ru-data/skills/pangolin-db-architecture/references/ha.md` (раздел «Режимы репликации»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/psq_documents__administration-guide__administration-pangolin-manager__replication.html.txt`.

### 1.4 Pangolin DB: DR — standby-кластер и правила мульти-ЦОД

- **Standby-кластер** (механизм от Patroni): «standby leader»
  реплицируется с удалённого первичного кластера, каскадные реплики — с
  него; блокировка лидера — в СВОЁМ DCS; пространства имён (scope)
  основного и резервного кластеров **должны различаться**; кластеры не
  знают друг о друге ничего, кроме репликации; standby не виден в
  `patronictl list` основного. Настройка — секция `standby_cluster` в
  конфигурации при бутстрапе; слот репликации на первичном создаётся
  вручную (или постоянные слоты).
- **Правило 2 ЦОД**: при наличии только двух ЦОД документация прямо
  рекомендует **два независимых DCS + standby-кластер во втором ЦОД**,
  а не растянутый синхронный кластер. **Автоматическое повышение
  (promote) standby-кластера невозможно** — DC2 не может отличить сбой
  DC1 от сетевого разделения. Повышение выполняется **вручную удалением
  секции `standby_cluster` из динамической конфигурации** (НЕ
  `pg_ctl promote`). Перед promote — **STONITH** основного сайта, иначе
  split-brain. Возврат основного сайта: `pg_rewind` (требует
  `--data-checksums` и/или `wal_log_hints=on`) или пересоздание standby
  с нуля.
- **Правило 3+ ЦОД**: синхронный мульти-ЦОД кластер: минимум 3 узла
  СУБД; DCS растянут по ЦОД, **нечётное число узлов — 3 или 5**;
  `synchronous_mode: true`; переживает падение одной зоны.
- **Имена узлов должны быть уникальны** во всех связанных кластерах:
  совпадение application_name с узлом основного кластера молча ломает
  синхронную репликацию (ложные «синхронные» коммиты → риск потери
  данных без ошибок в логах).

Источник: `spine-bank/banking/plugins/ru-data/skills/pangolin-db-architecture/references/ha.md` (разделы «Standby-кластер (DR на 2 ЦОД)», «Мульти-ЦОД (HA на 3+ ЦОД и правило 2 ЦОД)»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/psq_documents__architecture-components__patroni__standby_cluster.html.txt`, `psq_documents__architecture-components__patroni__ha_multi_dc.html.txt`.

### 1.5 Pangolin Pooler: N-ЦОД и защита от записи «не в тот» ЦОД

- N-ЦОД — логическое объединение кластеров: все данные потребителя
  синхронизируются между ЦОД любым инструментом межкластерной
  репликации; устойчивость — резервированием.
- Пулер как точка enforce'а записи в правильный ЦОД: режимы
  `NDC_ALLOWED` / `NDC_DISALLOWED`; команда **`NDC_SUSPEND`** — рвёт все
  клиентские и БД-соединения (кроме админ-консоли pgbouncer) и запрещает
  новые; **`NDC_KEEPALIVE`** — возобновляет приём и запоминает время;
  параметр `ndc_suspending_timeout` (сек, 0 = выкл.) — без регулярного
  keepalive пулер **сам переходит в suspend**. Т.е. внешний арбитр ЦОД
  обязан периодически слать `NDC_KEEPALIVE` — мёртвый арбитр = закрытый
  вход в БД (fail-closed).
- Pangolin Pooler — доработанный PgBouncer: сквозная аутентификация
  (вкл. LDAP и аудит), prepared statements в транзакционном режиме,
  PKCS#12/SecMan, многопоточная версия (только SberLinux).

Источник: `spine-bank/banking/plugins/ru-data/skills/pangolin-db-architecture/references/ha.md` (раздел «N-ЦОД в Pangolin Pooler»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/psq_documents__administration-guide__administration-pangolin-pooler__support-data-center-topology.html.txt`.

### 1.6 Pangolin DB: CDC — источник событий для шины

- Логическая репликация (публикация/подписка) + плагин **wal2json**
  (JSON на транзакцию или на кортеж; параметры include-*/filter-*/add-*;
  `wal_level = 'logical'` + рестарт) — база для CDC-контуров; есть также
  плагин `test_decoding`; поддержана работа со смещением LSN «для
  облегчения работы с логической репликацией и CDC-решениями».
- Отдельный CDC-продукт линейки — **Platform V GraDeLy (GDL)**:
  «логическая репликация с захватом изменений на клиенте или из журнала
  БД»; GDL пишет в Corax в MessagePack-топики (см. §1.9).

### 1.7 Corax: кластер и HA внутри площадки

- **Два режима метаданных**: ZooKeeper-ансамбль или KRaft-контроллеры
  (шаг 2 Ansible-установки — «Установка контроллера (kraft controller
  или zookeeper) и брокера (kafka)»). НФТ: «метаданные кластера хранятся
  в отказоустойчивом хранилище (ZooKeeper-ансамбль или KRaft-
  контроллеры), что исключает единую точку отказа». Детальных страниц
  конфигурации KRaft в съёме документации нет — **[ТРЕБУЕТ ПРОВЕРКИ]**.
- **ZooKeeper**: ансамбль, минимальное число узлов — **3**, только
  нечётное количество, работоспособен при живом строгом большинстве;
  standalone-конфигурация «не рекомендован для использования в
  промышленной эксплуатации»; порты clientPort 2181, кворумные
  2888/3888; «устаревшие версии файлов транзакционных логов и снепшотов
  не удаляются с диска сервером ZooKeeper — эта задача полностью ложится
  на администратора».
- **Доступность 99,9 %** при условиях: каждый компонент на отдельном
  хосте, фактор репликации ≥ 3, `min.insync.replicas` ≥ 2; rolling
  update без простоя; в тестовой конфигурации
  `unclean.leader.election.enable=false`. При отказе брокера
  ZooKeeper/контроллер переназначает лидеров из ISR; вернувшийся брокер
  догоняет репликацией и возвращается в ISR.
- **Ребалансировка лидеров**: `auto.leader.rebalance.enable=true` по
  умолчанию; Corax-специфичный параметр
  **`auto.leader.rebalance.on.not.isr.broker.enable`** (false — брокер с
  несинхронизированными репликами не участвует в выборах лидера;
  меняется только на весь кластер) — защита от «дискового шторма» после
  возврата брокера, когда он становится лидером синхронизированных
  партиций, пока остальные ещё реплицируются.
- **Auto Data Balancer** — утилита автоматического распределения
  партиций: режимы `--generate`/`--execute`/`--auto`; автоматический
  режим — **только в технологическое окно** (cron-параметр
  `ru.sbrf.kafka.balancer.operational-period`); поддержаны throttle и
  rack-awareness.
- Профиль нагрузки вендора: **13 000 tps** записи при среднем сообщении
  10 000 байт на стенде из 3 брокеров; «включение SSL значительно
  увеличивает утилизацию процессора»; рекомендация вендора — нагрузочное
  тестирование на целевой конфигурации. ВНИМАНИЕ: стенд НФТ использовал
  `min.insync.replicas=1` и `acks=1` — это параметры производительного
  теста, а не рекомендация для промышленного контура.

### 1.8 Corax: гарантии доставки (ключ к согласованности при DR)

- **acks**: 0 (буфер сокета, без гарантий) / 1 (лидер) / all=-1 (все
  ISR — «самая надежная из доступных гарантий»). При `acks=1` запись
  будет потеряна, если лидер упал до репликации.
- **Идемпотентный продюсер** (`enable.idempotence=true`, начиная с
  Corax 5.272.0): «усиливает семантику доставки… с at least once до
  exactly once»; обязательные условия — `acks=all`,
  `max.in.flight.requests.per.connection ≤ 5`, `retries > 0`; гарантия —
  «только для сообщений, отправленных в одной сессии»; повторные
  отправки на уровне приложения идемпотентность не отменяют.
  `retries > 0` без идемпотентности «может привести к задвоению
  данных» и без `max.in.flight.requests.per.connection=1` меняет порядок
  записей.
- **Транзакционный продюсер** (`transactional.id`): атомарная запись в
  несколько партиций/топиков; для топиков в транзакциях —
  `replication.factor ≥ 3` + `min.insync.replicas = 2` («оптимальная для
  большинства случаев»); потребитель для полных гарантий —
  `isolation.level=read_committed` (чтение до LSO).
- **Потребитель**: auto-commit или ручной `commitSync()/commitAsync()`;
  `auto.offset.reset` earliest/latest/none; рекомендация вендора —
  выносить обработку в отдельный поток с ручным коммитом и `pause`
  партиции (иначе зафиксированные смещения опередят фактическую позицию
  обработки).

### 1.9 Corax: межкластерная репликация (Mirror Maker 2) и бэкап в S3

- **Corax Mirror Maker 2** — «инструмент для репликации данных и
  метаданных между кластерами Platform V Corax/Apache Kafka», на
  платформе Kafka Connect; «отличается от механизма внутрикластерной
  репликации в Kafka». Компоненты: Source Connector/Task (чтение из
  исходного кластера), Sink Connector/Task (запись в целевой),
  **Checkpoint Connector/Task** (контрольные точки offsets —
  синхронизация смещений групп потребителей, топик `MirrorOffsetSyncs`),
  **Heartbeat Connector/Task** (проверка доступности удалённых
  кластеров), Config Connector/Task.
- MM2 реплицирует: сообщения, метаданные топиков, группы потребителей,
  контрольные точки смещений и **права доступа (ACL)**. Функции:
  динамическое обнаружение новых топиков/партиций, checkpoints для
  восстановления, метрики лага репликации, топологии
  **Active-Active / Active-Standby**. Сценарии из документации:
  репликация между удалёнными кластерами, **аварийное восстановление**,
  объединение кластеров, изоляция (пром/тест), миграция.
- Репликация MM2 — **асинхронная** (через коннекторы чтения/записи):
  сквозной RPO = 0 между кластерами Corax она не даёт; фактический
  RPO шины определяется лагом репликации, который нужно измерять и
  контролировать (метрики лага репликации MM2 заявлены).
- **Бэкап в S3**: Kafka Connect + доработанный плагин Lenses Stream
  Reactor: sink-коннектор (`S3SinkConnector`, выгрузка топиков в S3) и
  source-коннектор (`S3SourceConnector`, восстановление в топик),
  правила KCQL, конвертеры `EncryptedByteArrayConverter`, SecMan,
  управление через REST API. НФТ: «архивирование и восстановление данных
  выходят за рамки функций Corax… Исключение — облачные хранилища S3».

### 1.11 SynGX: поведение в аварийных сценариях и границы продукта

- **Active healthcheck** (модули `nginx_upstream_check_module` L7 и
  `ngx_stream_upstream_check_module` L4): директива `check` в upstream
  (`interval` умолч. 10000 мс и должен быть > `timeout`; `timeout`
  3000 мс; `fall` 5; `rise` 2; `default_down` true). Секции `match`
  задают условия работоспособности; `match_drain` (stream) — состояние
  **DRAIN**: новые соединения не устанавливаются, существующие доживают.
  Узел в статусе недоступен исключается из балансировки.
- При выпадении всех узлов группы: `send_rst` (http) и модули
  `ngx_http_rst_send_module`/`ngx_stream_rst_send_module` разрывают
  клиентские соединения — узел SynGX «закрывает» точку входа, пока
  upstream мёртв (fail-closed).
- **reload**: master проверяет синтаксис, запускает новые workers,
  старые доживают текущие запросы (без разрыва установленных
  соединений); **stop** — все соединения сбрасываются. Master
  перезапускает упавшие рабочие процессы.
- **Межинстансовая кластеризация SynGX** (VRRP/keepalived, синхронизация
  состояния между ВМ) в документации **НЕ описана**; горизонтальное
  масштабирование заявлено, но схема — за внешним балансировщиком.
  Состояние лимитов (`limit_req_zone`) и sticky-привязок живёт в shared
  memory каждого инстанса и между узлами не реплицируется (вывод из
  архитектуры продукта).
- Конфигурация SynGX — файлы (`/opt/syngx/conf/syngx.conf`), т.е.
  DR-восстановление узла SynGX = развёртывание ВМ + применение
  конфигурации из системы управления конфигурациями; состояния данных у
  узла нет.
- TLS-сертификаты — из **HashiCorp Vault** (`ngx_hashicorp_vault_module`,
  один блок `hv_pki`/`hashicorp_vault` на инстанс): публичная часть на
  ФС, **закрытый ключ — только в shared memory**. Подводный камень:
  между использованием wrapped_token и получением нового токена
  stop/quit/reload блокируются; `systemctl restart` скрипта-обхода не
  имеет. Метрики Vault: `vault_certificate_expiration_days`,
  `vault_fetch_errors_total`.
- Метрики — **только pull** (HTTP GET → JSON/Prometheus); «возможность
  настроить SynGX, чтобы он самостоятельно отправлял метрики в
  какую-либо систему, не предусмотрена». Логи — файлы/syslog через
  внешних агентов; «в SynGX нет функциональности отправки логов по
  протоколу Kafka».
- WAF, API-management, авторизационный сервер OAuth2 — в составе продукта
  отсутствуют.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (разделы «HA и отказоустойчивость», «Терминация TLS и сертификаты», «Эксплуатация в периметре банка», «WAF — НЕ обнаружен»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__use-case-syngx-active-healthcheck.html.txt`, `snx__documents__about__use-case-syngx-hashicorp-vault.html.txt`.

### 1.12 Мониторинг DR-готовности: что отдают продукты

- **Corax**: HTTPReporter (`ru.sbrf.kafka.HttpReporter`) — HTTP-сервер с

- **SynGX**: pull-метрики по HTTP (модули nginx-module-vts,

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Опорный"» (вымышленный, топ-30 по активам) завершил
импортозамещение платёжного контура на продукты Platform V. Контур
обрабатывает платежи юридических и физических лиц: приём платёжных
поручений по API и из ДБО, валидация, антифрод-проверка (через события
шины), проведение по счетам, выписки и статусы.

Архитектура потока данных (упрощённо):

1. Внешние и внутренние клиенты → **SynGX** (обратный прокси, терминация
   TLS, маршрутизация на платёжные сервисы).
2. Платёжные сервисы (микросервисы, вне scope задачи) пишут
   транзакционные данные в **Pangolin DB** (кластер платёжного ядра) и
   публикуют платёжные события в **Corax** (топики платежей, антифрода,
   уведомлений, выписок).
3. Часть событий попадает в шину из БД через CDC (транзакционный outbox
   → wal2json → топики Corax).
4. Потребители событий: антифрод, уведомления, витрины отчётности,
   интеграция с учётной системой.

Регуляторный контекст: контур подпадает под требования Положения
719-П (операционная надёжность операторов услуг платёжной
инфраструктуры) и внутренний стандарт банка по катастрофоустойчивости;
Архитектурный комитет требует ежегодного подтверждения DR-готовности
учениями.

### 2.2 Ландшафт AS-IS

- Два ЦОД (ЦОД-1 «Восточный», ЦОД-2 «Западный»), расстояние ~40 км,
  каналы 2×10 Гбит/с, RTT < 1 мс.
- **Pangolin DB 8.2.0 Enterprise**: HA-кластер из 3 узлов (1 лидер + 2
  реплики) — все в ЦОД-1; Pangolin Pooler перед кластером. В ЦОД-2
  развёрнут «холодный» одноузловой экземпляр, обновляемый вручную из
  архива WAL раз в сутки (историческая схема, не документирована,
  фактический RPO неизвестен, учения не проводились).
- **Corax 16.392.0**: один кластер в ЦОД-1 (5 брокеров, ZooKeeper-
  ансамбль из 3 узлов, RF = 3, `min.insync.replicas = 2`); в ЦОД-2 —
  кластер из 3 брокеров, развёрнутый «про запас», репликация между
  кластерами не настроена, топики резервного кластера пусты.
- **SynGX 4.3.0**: по 2 ВМ в DMZ каждого ЦОД за L4-балансировщиками с
  VIP; внешняя балансировка между ЦОД — существующий GSLB (DNS);
  конфигурация — в корпоративном GitOps (Ansible); сертификаты — из
  кластера HashiCorp Vault банка (внутренний контур).
- Регламент DR формально существует (документ 2023 года), под
  текущий ландшафт не адаптирован; учения по платёжному контуру не
  проводились более 2 лет.

### 2.3 Нагрузка и данные `[BENCH]`

- Платёжное ядро (Pangolin): пик **3 500 TPS** записи, ~80 ТБ данных,
  WAL-поток в пике ~1,2 ГБ/мин.
- Шина (Corax): пик **5 000 сообщений/с**, средний размер сообщения
  2 КБ; ~45 платёжных сервисов-продюсеров/потребителей; 120 топиков;
  ретенция платёжных топиков 7 суток.
- Точка входа (SynGX): пик 6 000 RPS суммарно; соединения stateless
  (REST).
- Профиль «длинный хвост»: до 15 % платёжных поручений требуют
  асинхронного подтверждения (статусы приходят через события шины) —
  потеря или дублирование таких событий при DR приводит к «зависшим»
  платежам, требующим ручной разборки.

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Классы критичности и целевые RTO/RPO: **класс А** — платёжное ядро (БД): RTO ≤ 30 мин, RPO = 0; **класс Б** — шина событий: RTO ≤ 30 мин, RPO ≤ 5 мин; **класс В** — точка входа (edge): RTO ≤ 15 мин, потеря состояния сессий/лимитов допустима, конфигурация RPO = 0 | подтверждать учениями |
| NFR-02 | Сквозная согласованность после DR: ни одна операция, подтверждённая клиенту до отказа, не должна быть потеряна; «зависшие» платежи после переключения должны автоматически выявляться и разбираться по процедуре ≤ 4 ч | обязательно |
| NFR-03 | Доступность платёжного контура в операционное время (04:00–01:00 МСК) | ≥ 99,95 % в год |
| NFR-04 | Обнаружение отказа ЦОД и решение о переключении | детекция ≤ 5 мин; решение по процедуре эскалации ≤ 10 мин после детекции |
| NFR-05 | Отказоустойчивость внутри ЦОД (узел БД, брокер, узел edge) | автоматически, без участия дежурной смены, RTO ≤ 5 мин |
| NFR-06 | Контроль лага репликации между ЦОД (БД и шина) | SLO лага шины ≤ 60 с в штатном режиме; алерт при превышении; фактический RPO шины должен быть измерим в каждый момент |
| NFR-07 | Плановый возврат на основной ЦОД после устранения аварии | без потери данных, в плановое окно, с подтверждением целостности |
| NFR-08 | DR-учения: полномасштабные (переключение контура) — ≥ 2 раз в год; компонентные (отказ узла/брокера) — ежеквартально; проверка процедур «на бумаге» (tabletop) — ежеквартально | фиксация результатов и актуализация плана |
| NFR-09 | Наблюдаемость DR-готовности: в любой момент дежурная смена видит, что резервный ЦОД способен принять контур | дашборд + алерты в Prometheus/Grafana банка |
| NFR-10 | Документация DR-плана актуализируется после каждого учения и каждого инцидента | версии в GitOps, review ДКА |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Все межЦОД-каналы репликации (БД, шина) — TLS не ниже 1.2; взаимная аутентификация сертификатами корпоративного УЦ |
| SEC-02 | Закрытые TLS-ключи edge-контура не хранятся файлами на ВМ в DMZ (источник — Vault, INF-04) |
| SEC-03 | Все ручные операции DR (promote, переключение направления репликации, изменение маршрутизации) — персонализированные, через PAM, с журналированием в SIEM |
| SEC-04 | Доступность секретов при DR: потеря одного ЦОД не должна лишить резервный ЦОД доступа к Vault/УЦ (INF-04) |
| SEC-05 | Аудит событий всех трёх продуктов (включая события авторизации Corax и аудит изменений конфигурации SynGX) доставляется в SIEM ≤ 5 мин |
| SEC-06 | Пароли в конфигурациях Corax — только в зашифрованном виде (штатные утилиты шифрования паролей); открытые пароли в GitOps запрещены |

### 2.7 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами.
- Комитет особенно чувствителен к трём вопросам: (1) **кто и как принимает
  решение о promote** при потере ЦОД (практика банка — ручные решения
  для платёжного контура, автоматика — только внутри площадки);
  (2) **согласованность БД и шины** после переключения — история банка
  знает инцидент с дублированием платёжных событий при аварийном
  переключении в старом ландшафте; (3) **измеримость**: все RTO/RPO
  должны подтверждаться учениями, а не декларироваться.
- Решение должно быть реализуемо силами команды INF-08 на
  документированных механизмах продуктов и существующем GitOps.

### 2.8 Что можно принять допущением `[ASSUME]`

- GSLB банка корректно исключает недоступный ЦОД за время ≤ 5 мин
  (TTL/health-check на стороне GSLB); детали — вне scope.
- Платёжные сервисы (микросервисы) разворачиваются в обоих ЦОД и их
  контракты позволяют реализовать идемпотентных потребителей (по
  бизнес-ключу платежа); доработка сервисов — отдельный проект, DR-план
  может на него опираться как на зависимость.
- Пропускной способности каналов 2×10 Гбит/с достаточно для потоков
  репликации БД (пик 1,2 ГБ/мин) и шины параллельно с прикладным
  трафиком; точный расчёт полосы — предмет нагрузочного тестирования.
- Время подъёма «холодных» ВМ из образов и применения конфигурации из
  GitOps — ≤ 15 мин (проверено на учениях смежных контуров).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DR (disaster recovery) | восстановление контура после катастрофического отказа (потеря ЦОД) |
| RTO | целевое время восстановления работоспособности после отказа |
| RPO | целевая точка восстановления: максимально допустимый объём потери данных во времени |
| standby-кластер | резервный кластер Pangolin, реплицирующий с основного и не связанный с ним общим DCS; повышается только вручную |
| promote | вывод standby-кластера из-под репликации в роль основного |
| STONITH | принудительное гарантированное отключение основного сайта перед promote (защита от split-brain) |
| split-brain | ситуация двух одновременно пишущих лидеров |
| ISR | in-sync replicas — синхронизированные реплики партиции Kafka |
| MM2 | Corax Mirror Maker 2 — межкластерная репликация данных и метаданных |
| checkpoint (MM2) | контрольная точка смещений групп потребителей для продолжения обработки на другом кластере |
| exactly-once | семантика «ровно один раз» (идемпотентный/транзакционный продюсер + read_committed потребитель) |
| GSLB | глобальная балансировка между площадками через DNS |
| DRAIN | состояние узла: новые соединения не принимаются, существующие доживают |
| fail-closed | при недоступности зависимости точка входа закрывается (отказ в обслуживании вместо записи «не туда») |
| NDC | режим N-ЦОД в Pangolin Pooler (NDC_ALLOWED/NDC_DISALLOWED, NDC_SUSPEND/NDC_KEEPALIVE) |
| CDC | захват изменений данных (Change Data Capture) из журнала БД |
| tabletop-учения | прогон процедур DR «на бумаге» без реального переключения |
