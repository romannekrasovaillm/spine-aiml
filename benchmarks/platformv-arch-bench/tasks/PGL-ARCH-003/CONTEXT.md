## 1. Продукт: Platform V Pangolin DB 8.2.0 `[DOC]`

### 1.1 Что это; редакции; поддержка 1С

- СУБД Pangolin (код продукта PSQ, вендор АО «СберТех», линейка Platform V) —
  **специальная сборка PostgreSQL** с доработками под безопасность,
  доступность, надёжность и эксплуатацию. Это **OLTP-СУБД, не MPP**: один
  ведущий узел на запись + потоковая физическая репликация; для аналитических
  нагрузок вендор прямо рекомендует специализированные продукты. Зарегистрирован
  в РРПО (№13436 от 29.04.2022).
- Редакции 8.2.0: **Standard**, **Standard для ERP-систем**, **Enterprise**,
  **Enterprise для ERP-систем**. Для Enterprise-only функциональностей в
  документации стоит пометка «Доступно только для редакций Enterprise и
  Enterprise для ERP-систем». Редакция — вопрос лицензии, фиксируется до
  проектирования схемы.
- Из матрицы функциональности по редакциям (выборочно):
  - **только Enterprise**: TDE (прозрачное защитное преобразование данных,
    4.1.0); защита данных от привилегированных пользователей (4.1.0); защита
    параметров конфигурации (4.3.0); интеграция с KMS HashiCorp Vault (4.3.0);
    хранилище параметров подключения (4.4.0); маскирование запросов (5.2.1);
    **внешняя авторизация через LDAP** (6.6.0); нативное интервальное
    партиционирование; глобальные индексы; pgloader; pgcopydb; отчёты
    детального анализа истории активности; **оптимизация работы с временными
    таблицами (7.1.0)**;
  - **все редакции**: аудит событий безопасности по ГОСТ Р 59548-2022 (3.2.0);
    управление парольными политиками (3.3.0); сквозная аутентификация
    Pooler ↔ СУБД (4.4.0); двухфакторная аутентификация (5.2.0);
    **«Поддержка совместной работы с 1C» (5.3.2)** и **«Повышение
    производительности для использования совместно с 1С» (5.3.2)**.
- **Поддержка 1С** — документированный отдельный **отключаемый** режим СУБД:
  включение активирует оптимизации планировщика запросов, изменения в работе
  внутренних алгоритмов СУБД и дополнительные расширения. Поведение продукта
  с включённой и выключенной поддержкой 1С различается; оптимизации **могут
  приводить к построению планов с деградацией производительности при
  использовании без 1С**. Рекомендация вендора: включать только при реальной
  работе совместно с 1С. Подробности — в разделе «Поддержка 1С» Руководства
  администратора (в съём не вошёл, см. §1.11).
- Целевые сценарии из раздела «Преимущества»: OLTP; работа с
  «1С:Предприятие» (включая высоконагруженные системы с тысячами
  пользователей); time-series через адаптированное расширение TimescaleDB из
  дистрибутива; хранение ПДн/критичных данных; масштабирование чтения
  репликами.
- Жёсткие ограничения ядра: размер БД не ограничен; отношение ≤ 32 ТБ
  (BLCKSZ 8192); ≤ 1 600 колонок на таблицу; поле ≤ 1 ГБ (TOAST); ≤ 32
  колонки на индекс; ≤ 32 ключей партиционирования. Документация сравнивает
  системы хранения LOB: Oracle BLOB/CLOB vs PostgreSQL Large Object vs TOAST;
  защита таблиц со ссылками на LOB/BFILE не распространяется на сами объекты.

### 1.2 Компоненты и HA-кластер

- Кластер высокой доступности — 2+ сервера с экземплярами одной БД,
  связанные потоковой физической репликацией. Компоненты: **Pangolin
  Manager** (оркестратор, доработанный Patroni; в комплекте документация
  Patroni 4.1.1), **Pangolin DCS** (распределённое хранилище конфигурации на
  базе Raft: состояние кластера, кворум, блокировка лидера с TTL; альтернатива
  из Patroni-наследия — etcd/ZooKeeper/Consul), **Pangolin Pooler**.
- Заявленные целевые показатели для mission critical: **RPO = 0** при
  программном/аппаратном сбое и **RTO < 6 минут в год** простоя (горячее
  резервирование Active/StandBy + автоматический failover + Pooler). Это
  целевые показатели продукта, а не гарантия для конфигурации заказчика.
- Репликация однопоточная → в кластере один лидер, остальные — реплики.
  Выборы: при истечении записи о лидере в DCS узлы сравнивают позиции WAL;
  узел с наиболее актуальной позицией, первым записавший себя в DCS, становится
  лидером.
- Управление: CLI `pangolin-manager-ctl` (`list`, `pause`/`resume`, `reload`,
  `restart`, `switchover`, `failover`, `reinit`, `edit-config`) и REST API
  (health-check балансировщиками типа HAProxy, мониторинг). `switchover`
  гарантирует применение всех транзакций лидера на репликах до передачи роли
  (нулевые потери даже в async); `reinit` пересоздаёт реплику через
  pg_basebackup. Управлять экземплярами напрямую (`pg_ctl`, `systemctl`) при
  активном Manager — только в режиме `pause`.
- **Режимы репликации** (по умолчанию асинхронная):
  1. **Асинхронная** (`synchronous_mode: false`): потери при сбое лидера
     ограничены `maximum_lag_on_failover` (байты WAL) плюс записи за последние
     `ttl` секунд (в среднем `loop_wait` ≈ 2 с); `check_timeline: true`
     запрещает выбирать лидером реплику с другой временной шкалой.
  2. **Стандартная синхронная PostgreSQL** (`synchronous_commit: on` +
     `synchronous_standby_names`): коммит ждёт записи на реплику; Manager
     трактует кластер как асинхронный; рекомендуется ≥ 2 реплик, иначе сбой
     единственной реплики блокирует запись.
  3. **Нестрогий синхронный Manager** (`synchronous_mode: true`): при
     недоступности реплики лидер переводится в async (запись сохраняется); при
     сбое лидера failover только на реплику со всеми зафиксированными
     транзакциями, иначе кластер недоступен на запись до ручного `failover`.
  4. **Строгий синхронный** (`synchronous_mode_strict: true`): failover только
     на синхронную реплику; при её одновременной потере с лидером
     автопереключения нет вообще; перевод в async запрещён.
- Тег `nosync: true` исключает узел из кандидатов в синхронные реплики;
  `synchronous_node_count` (по умолчанию 1) — число синхронных standby.
- **DCS failsafe mode**: при полной недоступности DCS кластер продолжает
  работать, если все узлы видят лидера через его REST API; включается через
  глобальную динамическую конфигурацию (ключ `/config` в DCS).
- Дистрибутив 8.2.0: pangolin-manager 4.2.0, pangolin-pooler 3.2.0.

### 1.3 DR: standby-кластер и правило двух ЦОД

- **Standby-кластер**: «standby leader» реплицируется с первичного кластера и
  ведёт за собой каскадные реплики; удерживает блокировку лидера в
  **собственном DCS**; scope основного и резервного кластеров должны
  различаться. Кластеры не знают друг о друге, кроме канала репликации;
  standby не виден в `list` основного. Настройка — секция `standby_cluster`
  при бутстрапе; слот репликации на первичном создаётся вручную.
  `standby_cluster.host` может быть списком хостов с
  `target_session_attrs=read-write`.
- **Имена узлов должны быть уникальны во всех связанных кластерах**:
  совпадение `application_name` с узлом основного кластера молча ломает
  синхронную репликацию (ложные «синхронные» коммиты, риск потери данных без
  ошибок в логах).
- **Мульти-ЦОД**: синхронный мульти-ЦОД кластер — минимум 3 узла СУБД, DCS
  растянут по ЦОД с **нечётным числом узлов (3 или 5)**,
  `synchronous_mode: true` — переживает падение одной зоны.
- **Правило двух ЦОД**: при наличии только двух ЦОД документация предписывает
  два независимых DCS и standby-кластер во втором ЦОД. **Автоматическое
  повышение невозможно** (ЦОД-2 не может отличить сбой ЦОД-1 от сетевого
  разделения): повышение — **только вручную** удалением секции
  `standby_cluster` из динамической конфигурации (НЕ `pg_ctl promote`); перед
  повышением — STONITH основного, иначе split-brain. Возврат: `pg_rewind`
  (требует `--data-checksums` и/или `wal_log_hints = on`) или пересоздание
  standby с нуля.
- **N-ЦОД в Pangolin Pooler**: пулер — точка контроля записи «в правильный
  ЦОД»: режимы `NDC_ALLOWED`/`NDC_DISALLOWED`; команда `NDC_SUSPEND` рвёт
  клиентские и БД-соединения (кроме админ-консоли pgbouncer) и запрещает
  новые; `NDC_KEEPALIVE` возобновляет приём; параметр `ndc_suspending_timeout`
  — без регулярного keepalive от внешнего арбитра пулер **сам** переходит в
  suspend (fail-closed).

### 1.4 Pangolin Pooler: доработки, расчёт пула, предупреждения вендора

- Pangolin Pooler — доработанный PgBouncer (в 8.2.0: Pooler 3.2.0, ядро
  PgBouncer 1.24.0). Порт по умолчанию 6544, админ-консоль — БД `pgbouncer`.
  Доработки: **сквозная аутентификация пользователей** (включая LDAP и аудит
  действий пользователя в лог пулера, команда `RESET_AUTH`); **поддержка
  подготовленных запросов (prepared statements) в транзакционном режиме**
  кластера высокой доступности; сертификаты PKCS#12 + SecMan; топология N-ЦОД;
  вывод `SHOW POOLS` в лог; **многопоточная версия**.
- **Многопоточный Pooler** (пакет `pangolin-pooler-mt`, версия компонента
  1.5.5): классический пулер однопоточен → потолок одного ядра CPU, деградация
  при росте подключений; многопоточный вариант распределяет соединения по
  воркерам с мониторингом утилизации потоков. **Доступен только на ОС
  SberLinux.** Не допускается одновременная установка/запуск однопоточной и
  многопоточной версий на одном стенде; «обновления» однопоточной на
  многопоточную нет.
- Рекомендации вендора по настройке:
  - `max_connections` определяется **нагрузочным тестированием**; стартовая
    формула `max_connections = GREATEST(5 × CPU cores, 100)`; после
    формирования конфигурации проверять через **Pangolin Tuner**;
  - **`max_connections` не универсален для всех профилей**: «Для профилей, при
    которых приложение создаёт большое количество клиентских подключений,
    может потребоваться ручное изменение параметра. **Например, такая ситуация
    возможна для профиля 1C**»;
  - **одинаковое `max_connections` на Primary и StandBy** — иначе после
    failover часть клиентов не получит подключение;
  - пулер рекомендуется, когда `max_client_conn > max_connections`; правила:
    `max_db_connections <= max_connections - superuser_reserved_connections - 30`;
    `min_pool_size = default_pool_size`; пример сбалансированной конфигурации
    (одна ТУЗ / одна БД): `max_client_conn=1000`, `pool_mode=transaction`,
    `min_pool_size=default_pool_size=max_db_connections=max_user_connections=200`;
  - `default_pool_size` задаётся **на пару пользователь/БД**: потенциально
    открывается `default_pool_size × (число БД) × (число пользователей)`
    соединений — при нескольких БД/пользователях ограничивать `pool_size` в
    секции `databases`;
  - эффективность пулера — когда `max_db_connections` значительно меньше
    `max_client_conn`; если значения близки или равны, либо
    `pool_mode = session`, пулер становится лишним звеном; **работа через
    пулер замедляет отклик БД в среднем на ~5 %**;
  - не увеличивать `max_connections` без оценки RAM/CPU (риск OOM killer);
    изменение требует **перезапуска** СУБД;
  - связка с HikariCP: если пул приложения меньше `max_connections` —
    подключаться напрямую; иначе HikariCP + Pooler, `max_client_conn` больше
    суммы всех пулов (`hosts × maximumPoolSize`), тайм-аут подключения на
    клиенте выше, чем на пулере.
- **Pangolin Pooler не рекомендуется использовать** (дословный список
  вендора): когда ядро CPU пулера нагружено более чем на 70 %; в режимах
  `pool_mode = session/statement`; **в режиме `pool_mode = transaction` при
  OLTP-нагрузках с требованиями более 1000–10000 TPS и длительностью операции
  менее 1–10 мс** (накладные расходы на сокет, диагностируется ростом
  `sys_time` на CPU); когда число клиентских подключений в пределе достигает
  числа подключений к БД; для OLAP-нагрузок с большим трафиком.

### 1.5 Партиционирование, глобальные индексы, сжатие

- Декларативное партиционирование: RANGE/LIST/HASH, ключ до 32 полей;
  вложенное партиционирование; отсечение партиций
  (`enable_partition_pruning`, статическое и динамическое) + доработка
  `pruning_fields` для композитного ключа (Enterprise).
- **Нативное интервальное (авто-) партиционирование** (только Enterprise):
  `AUTO PARTITION BY RANGE (key) PERIOD (p) [OFFSET (o)]` / `BY HASH ...
  MODULUS` / `BY LIST`; партиции создаются автоматически при вставке данных,
  не попадающих в существующие; пустые партиции при удалении данных **не
  удаляются**; **схему автопартиционирования для уже созданной таблицы
  изменить нельзя** — период и ключ проектируются до наполнения; для RANGE —
  типы INTEGER/NUMERIC/DATE/TIMESTAMP/TIMESTAMPTZ (float не поддерживается);
  параметры `autpartition.enable_shift` / `autopartition.default_timezone` —
  границы партиций по 00:00:00 заданной таймзоны.
- **Глобальные индексы и ограничения** (только Enterprise): `CREATE [UNIQUE]
  INDEX ... GLOBAL`, `PRIMARY KEY/UNIQUE (...) GLOBAL` — единый B-Tree поверх
  всех партиций, уникальность по полям, **не включающим ключ
  партиционирования** (в ванильном PostgreSQL UNIQUE на партиционированной
  таблице обязан включать ключ). Ограничения: только B-Tree; нет
  exclusion-ограничений, субпартиционирования, deduplication; при
  `REINDEX INDEX CONCURRENTLY` на автопартиционированной таблице невозможен
  INSERT, создающий новую партицию; ATTACH таблицы с существующим PK к таблице
  с `PRIMARY KEY GLOBAL` запрещён. Созданные индексы продолжают работать при
  понижении лицензии, новые создавать нельзя.
- **Сжатие данных на уровне страниц** (Enterprise): `compresstype` =
  pglz | lz4 | zstd на таблицу, партицию, матпредставление, индекс или
  табличное пространство; включается `enable_page_compression` (reload).
  Подход: сжимать исторические партиции, не трогая горячие.
- **Оптимизация работы с временными таблицами** (Enterprise, с 7.1.0) и
  хранение метаданных временных объектов в памяти — релевантно 1С-профилю,
  интенсивно использующему временные таблицы.
- `pg_pathman` исключён из состава продукта и не поддерживается с версии
  7.1.0; операции EXCHANGE PARTITION (Oracle) нет — используются DETACH +
  RENAME + ATTACH в одной транзакции.

### 1.7 Подключения, блокировки, ресурсы (паттерн «Надёжная эксплуатация высоконагруженных систем»)

- **Резервирование подключений для ролей**: в ядре ванильного PostgreSQL
  резерв подключений есть только у суперпользователя; в Pangolin в каждой БД
  создаётся файл **`pg_quota.conf`** с записями для ролей, которым нужно
  зарезервировать соединения, — гарантированный доступ служебных УЗ при
  исчерпании пула.
- **Контроль и квотирование потребления ресурсов** (CPU/RAM/диск) с
  завершением ресурсоёмких сессий (`psql_resources_consumption_limits`,
  `psql_quotolin`, Enterprise).
- **Управление лёгкими блокировками (LWLock)**: расширенные параметры под
  сценарии — частое чтение/редкая запись; запросы с большим числом таблиц
  (партиции, JOIN, много индексов); интенсивная работа буферного кэша.
- **Управление планами запросов**: фиксация и подмена плана на сервере без
  изменения текста запроса (`pg_hint_plan`, `pg_dbms_stats`,
  `pg_store_plans`).
- **64-битные XID** снимают wraparound-проблему ванильного PostgreSQL
  (в документации пример: ваниль встаёт при 50k TPS с 13-часовым
  OLAP-запросом).
- Пользовательские блокировки: расширение **`pg_dbms_lock`** (аналог
  DBMS_LOCK из Oracle).
- SIMD-оптимизации (по умолчанию off, контекст USERSET, включаются точечно и
  проверяются нагрузочным тестированием): `enable_fast_sort`,
  `enable_fast_pattern_matching`, сжатие FSM, `enable_wal_locking_reduction`.
- Аварийное завершение СУБД при отключении СХД; режим Read Only экземпляра;
  параллельный ANALYZE; быстрая остановка walsender логической репликации.
- **Pangolin Tuner** — утилита тюнинга параметров из дистрибутива, стартовая
  точка конфигурации под профиль нагрузки (затем подтверждать НТ).

### 1.8 Миграция с Oracle и CDC

| Инструмент | Версия | Источник | Редакция | Назначение |
|---|---|---|---|---|
| `ora2pg` | 23.0 | Oracle | любая (поставка в `migration_tools`) | миграция БД Oracle → Pangolin |
| `orafce` | 4.4.0 | Oracle (код) | любая | функции/пакеты Oracle для PL/pgSQL (dbms_alert, dbms_output, dbms_pipe, dbms_random, dbms_utility, utl_file и др.) |
| `oracle_fdw` | 2.5.0 | Oracle | любая | FDW к Oracle: WHERE и списки колонок пробрасываются в Oracle, DML, IMPORT FOREIGN SCHEMA; пароль — из защищённого `pg_auth_config` |
| `tds_fdw` | 2.0.3 | MS SQL, Sybase | любая | FDW по протоколу TDS (FreeTDS) |
| `pgloader` | 3.6.9 | **MS SQL, MySQL, SQLite** | Enterprise | перенос данных через COPY |
| `pgcopydb` | 0.14 | **PostgreSQL** | Enterprise | полная копия БД + CDC-follow |

- **ora2pg в 8.2.0 не установлен по умолчанию**; поставляется в каталоге
  `migration_tools/ora2pg` дистрибутива (ora2pg 23.0, DBD::Oracle 1.80,
  DBD::Pg 3.15, Oracle Instant Client 18.5). Позиционирование вендора: «один
  из возможных вариантов и инструментов миграции; окончательный выбор
  инструмента и его использование — в зоне ответственности продуктовой
  команды». Официальной «кнопки миграции» нет — закладывать оценку и пилот.
- orafce покрывает «некоторые функции из СУБД Oracle, отсутствующие или
  ведущие себя иначе в PostgreSQL»; по умолчанию не установлен. Раздел
  «Портирование из Oracle PL/SQL» описывает различия: конфликт имён
  переменная/колонка (`plpgsql.variable_conflict = use_column`), тело функции
  — строковый литерал, `varchar2`→`varchar`/`text`, `number`→`numeric`,
  пакетов нет (схемы), переменных уровня пакета нет (временные таблицы).
- **pgloader не мигрирует с Oracle** (источники: MS SQL/MySQL/SQLite);
  **pgcopydb работает только PostgreSQL → Pangolin**, причём его CDC-follow
  падает при перезапуске любой из БД, требует суперпользователя на приёмнике и
  **не работает с TDE**; набор расширений и GUC источника и приёмника должен
  быть идентичен.
- Вендорская рамка процесса миграции (из раздела pgloader, применима широко):
  архитектурное планирование → планирование схемы (DDL под диалект целевого
  сервера) → подготовка схемы (сначала DDL-таблиц, затем индексы и связи) →
  перенос данных → перенос кода → валидация полноты. Рекомендация: перенос в
  неиндексированную структуру с последующей индексацией; на время загрузки —
  минимум ограничений.
- **CDC**: логическая репликация (публикация/подписка), плагин **wal2json**
  (JSON на транзакцию или на кортеж; требуется `wal_level = logical` +
  перезапуск сервера), `test_decoding`; поддержка смещения LSN для логической
  репликации и CDC-решений. Отдельный CDC-продукт линейки — **Platform V
  GraDeLy (GDL)**: «логическая репликация с захватом изменений на клиенте или
  из журнала БД»; в Pangolin заявлена нативная поддержка GraDeLy (поддержка
  Oracle-источника в съёме не зафиксирована, см. §1.11).
- Обновление самой СУБД: `pg_upgrade` (мажорные переходы) и
  `pangolin-inplace-upgrade` (обновление системных каталогов без миграции
  данных, значительно быстрее классического pg_upgrade); автоматизированные
  сценарии обновления через Pangolin Installer (с 8.2.0 — с GUI-режимом).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Байкал-Инвест Банк» (вымышленный, топ-50 по активам) эксплуатирует АС
«ХозУчёт» — учётную систему внутрибанковского учёта (учёт основных средств,
НМА, МБП, хозяйственных договоров, казначейских лимитов и внутрибанковских
операций) на платформе **«1С:Предприятие 8.3.24.1690»** с собственной
конфигурацией (доработанная отраслевая, ~12 лет развития). АС «ХозУчёт»
относится к системам класса **Business Critical**: недоступность более 2 часов
в операционное время останавливает закрытие операционного дня по хозяйственной
деятельности и блокирует часть регламентной отчётности.

Программа импортозамещения предписывает вывод Oracle Database из контура
АС «ХозУчёт» до конца 2027 года. Целевая СУБД утверждена: **Platform V
Pangolin DB 8.2.0**. Кластер серверов 1С остаётся без изменений (только
перенастройка подключений); рядом с продуктивным контуром живут две тестовые
информационные базы, обновляемые копиями продуктива.

### 2.2 Ландшафт AS-IS

- СУБД: **Oracle Database 19c Enterprise Edition**, один узел в ЦОД-1 +
  физический standby (Data Guard, async) в ЦОД-2.
- Объём БД: **4,6 ТБ** (данные ~3,0 ТБ без индексов), рост **~0,9 ТБ/год**;
  срок хранения — 5 лет онлайн, далее архив.
- Три самые большие таблицы-аккумулятора (регистры накопления/сведений) — по
  300–450 ГБ каждая; запросы 1С к ним идут преимущественно по периоду и
  измерениям; в Oracle они секционированы по месяцу с локальными индексами;
  уникальность ряда регистров обеспечивается по набору полей, **не
  включающему период**.
- Бизнес-логика в СУБД минимальна (1С-специфика): ~3 тыс. строк PL/SQL
  написаны поверх платформы — триггеры внешнего аудита и две витрины обмена;
  схема БД полностью управляется конфигуратором 1С (реструктуризация).
- Платформа 1С: активно использует **подготовленные запросы (prepared
  statements)** и **временные таблицы** (пакетные запросы, менеджеры временных
  таблиц); управляемые блокировки реализованы на уровне платформы 1С;
  регламентные задания исполняются планировщиком кластера 1С (не СУБД).
- Кластер серверов 1С: **6 рабочих серверов** в ЦОД-1; пик — **2 800
  одновременных сеансов** пользователей; кластер 1С держит до **3 400
  одновременных соединений с СУБД** (рабочие процессы + пулы соединений
  платформы). Текущий Oracle обслуживает их напрямую (max sessions поднят
  вручную, в пиках — проблемы с PGA-памятью).
- Информационные базы: **3 продуктивные ИБ** (основная «хозучёт»,
  зарплатно-кадровая, архивная) + 2 тестовые. На каждую ИБ — **одна
  технологическая учётная запись СУБД** (владелец схемы, полные права на свою
  БД), как требует типовая схема развёртывания 1С.
- Нагрузка: пик **4 500 транзакций/с** (короткие OLTP-транзакции,
  длительность операции 2–8 мс, 65 % чтение / 35 % запись); **закрытие
  месяца** — пакетное перепроведение ~40 млн записей за ночное окно; 20–30
  тяжёлых отчётных запросов в день (сейчас исполняются на standby Data Guard).
- Двухфакторная аутентификация пользователей 1С — на уровне платформы 1С (вне
  контура СУБД).

### 2.3 Инфраструктура и ограничения `INF-xx`

| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault 1.15.x** (3 узла, растянут между ЦОД). SecMan в банке не развёрнут. Сторонние KMS-эмуляторы в промышленной среде запрещены политикой ИБ |
| INF-04 | СРК банка предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; требуется интеграция через штатные средства СУБД |
| INF-05 | Мониторинг — **Zabbix**; журналирование — централизованный SIEM; управление привилегированным доступом — **PAM-система** (все административные сессии только через PAM) |
| INF-06 | Кластер серверов 1С: 6 рабочих серверов в ЦОД-1 (active), 3 резервных сервера 1С в ЦОД-2 (standby, включаются при DR). Лицензии 1С на обе площадки имеются |
| INF-07 | Команда сопровождения: 3 DBA (опыт PostgreSQL средний, Pangolin базовый), 2 администратора 1С, 1 администратор ИБ, 2 DevOps; развёртывание — только Ansible 8.7.0 из корпоративного репозитория |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с субботы на воскресенье, **не более 6 часов**. Одноразовое миграционное окно переключения — **не более 12 часов** (выходные) |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс 1–2
  отвергнутые альтернативы с причинами.
- Решение должно быть реализуемо силами INF-07 с использованием штатной
  автоматизации продукта.
- Комитет особенно чувствителен к двум вопросам: (а) **как 3 400 соединений
  кластера 1С лягут на Pangolin** без деградации (опыт Oracle показывает
  чувствительность к числу сессий); (б) **не «залипнет» ли закрытие месяца**
  из-за планировщика/блокировок после переезда.
- Вопрос совместимости версии платформы 1С 8.3.24.1690 с Pangolin 8.2.0
  поднят в рабочей группе; комитет ожидает, что архитектор **явно зафиксирует
  статус этой проверки** (см. CONTEXT §1.11), а не проигнорирует её.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Pangolin на момент внедрения — 8.2.0 или новее; базовую мажорную
  версию PostgreSQL решающий не знает из контекста и должен либо не
  использовать, либо пометить как допущение.
- Кластер серверов 1С допускает перенастройку параметров соединения с СУБД
  (количество соединений в пулах рабочих процессов, тайм-ауты, строка
  подключения).
- Vault банка доступен из обоих ЦОД с латентностью ≤ 5 мс и имеет собственный
  RTO ≤ 5 мин.
- Нагрузочное тестирование на копии продуктивного контура будет проведено до
  переключения; результаты НТ могут скорректировать параметры пула и
  `max_connections`.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DCS | Distributed Configuration Store — хранилище состояния кластера для оркестратора (Pangolin DCS или etcd/ZooKeeper/Consul) |
| Standby-кластер | резервный кластер Patroni-архитектуры с собственным DCS, каскадно реплицирующий с первичного |
| Switchover / Failover | плановое / аварийное переключение роли лидера |
| STONITH | принудительное отключение узлов прежнего лидера перед повышением standby (защита от split-brain) |
| TDE | прозрачное защитное преобразование (шифрование) данных на уровне хранения |
| ТУЗ | технологическая учётная запись |
| ИБ | информационная база 1С |
| СРК | система резервного копирования |
| PAM | privileged access management |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
| НТ | нагрузочное тестирование |
| LWLock | лёгкие (разделяемые в памяти) блокировки ядра PostgreSQL |
