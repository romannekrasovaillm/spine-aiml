# Рубрики оценки для задачи CRX-ARCH-001

## 1. Общие правила для судей

1. **Порядок:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить HF §2;
   (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из ответа;
   (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Corax,
   которого нет в §1 и которое не помечено решающим как допущение, считается
   **непроверенным**; если оно ещё и ложно — **ложным**. Не «додумывать» за
   решающего.
3. **«Упомянул ≠ применил»** — балл за решение, привязанное к требованию
   (NFR/SEC/INF) и обоснованное, а не за ключевое слово.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 — образцово, с
   учётом компромиссов и ловушек §4.
5. **Цитирование:** 1–3 цитаты (≤ 25 слов) на критерий + чего не хватает до
   следующего уровня.
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`). Стиль и
   объём сверх C10 не оцениваются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
оцениваются для диагностики. «Только судья» = regex-детектор ненадёжен.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Координационный слой без кворума: ZK-ансамбль или кворум KRaft из 1 или чётного числа узлов, либо весь кворум в одном ЦОД/зоне — **без** явного обоснования и компенсирующих мер | Число и размещение узлов ZK/KRaft в схеме/тексте; A-06. Только судья |
| HF-02 | Для платёжных топиков предложены `acks=0`/`acks=1` или `min.insync.replicas=1` без обоснования компромисса, либо exactly-once заявлен «по умолчанию» без конфигурации идемпотентности/транзакций | A-05, A-06; CONTEXT §1.4 |
| HF-03 | Вымышленные компоненты/функции Corax поданы как факт (например: «Records Policy входит в Apache Kafka», «встроенный балансировщик Corax для клиентов», «синхронная межкластерная репликация штатна») | A-05, ловушки §4 |
| HF-04 | Заявлен RPO = 0 при потере ЦОД-1 при асинхронной межкластерной репликации (MM2), либо MM2 назван синхронным механизмом | A-06; CONTEXT §1.8 |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01 (механические паттерны) |

## 3. Критерии

### C1. Фактическая корректность по Corax (вес 15)

**Что оценивается:** соответствие утверждений о продукте CONTEXT.md §1;
корректные наименования; отделение фактов от допущений.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-03, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (доставка, Records Policy, MM2, аудит), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны; всё за пределами §1 помечено допущением или подтверждено ссылкой с разрешённых доменов; различаются внутрикластерная репликация и MM2, SecMan и Vault, тестовый профиль нагрузки и пром-рекомендации; пробелы съёма (KRaft, sr-migration, mm2-scenarious) честно помечены как вопросы к вендору |

**Признаки сильного ответа:** официальные имена (Apache Kafka, Apache
ZooKeeper, Corax Schema Registry, Corax UI, Corax Mirror Maker 2, Auto Data
Balancer, Records Policy); версия ядра Kafka не заявлена как факт; «13 000
tps» не подан как гарантия; аномальный «p99 = 1375 с» не использован.

**Типичные ошибки:** «ZooKeeper обязателен всегда»; «идемпотентность
устраняет дубли от ретраев приложения»; Protobuf как факт без оговорки;
аудит в COTE вопреки INF-05.

### C2. Топология кластеров, кворум координации, HA/DR (вес 15)

**Что оценивается:** D2 + D3. Схема, число брокеров и RF, выбор и размещение
ZK/KRaft при двух ЦОД (INF-01), сценарии отказа, NFR-01…NFR-05.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы или схема без координационного слоя; HF-01 или HF-04 |
| 2 | RF ≥ 3 и `min.insync.replicas=2` есть, координация есть, но: потеря ЦОД-1 останавливает управление без объяснения; выбор ZK vs KRaft не обоснован; потеря облачной зоны не разобрана |
| 4 | (a) явный выбор ZK vs KRaft с учётом пробелов документации (§1.2, §1.12); (b) нечётный кворум, переживающий потерю одного ЦОД (например, 2+2+1 с узлом в облачной зоне INF-01), с разбором потери ЦОД-1 и потери облачной зоны; (c) решение «один растянутый кластер vs кластер в каждом ЦОД» принято и увязано с NFR-01…06 (sync-запись между ЦОД при RTT 2–4 мс конфликтует с NFR-06); (d) `unclean.leader.election.enable=false`, auto-leader-rebalance и защита от «дискового шторма»; (e) отказ брокера увязан с RTO ≤ 5 мин; (f) условия доступности вендора (отдельные хосты, RF ≥ 3, mis ≥ 2) посчитаны против бюджета хостов INF-02 |

**Ловушки:** кворум ZK из 2 узлов; весь кворум в ЦОД-1; «растянутый
синхронный кластер без влияния на latency»; брокер + KRaft-контроллер на
одном хосте вопреки рекомендации.

### C3. Гарантии доставки, ordering, exactly-once (вес 14)

**Что оценивается:** D4, NFR-02, NFR-07, NFR-08.

| Уровень | Якорь |
|---|---|
| 0 | Нет конфигурации гарантий; HF-02 |
| 2 | `acks=all`, идемпотентность, транзакции названы, но без привязки к топикам; границы гарантий не зафиксированы; порядок «обеспечивается партициями» без ключей |
| 4 | Профили по критичности: платёжные — `acks=all` + RF 3 + `min.insync.replicas=2` + `enable.idempotence=true` (с требованиями `max.in.flight.requests.per.connection ≤ 5`, `retries > 0`); финансовые подтверждения — транзакционный продюсер + потребитель `read_committed`; границы зафиксированы (сессия; ретраи приложения дают дубли ⇒ дедупликация по бизнес-ключу — прикладное требование); ordering: ключ = счёт/операция, порядок только внутри партиции, влияние retries/max.in.flight учтено, потребителей ≤ партиций; коммит потребителя ручной после обработки (+`pause` при фоновой обработке); auto-commit для платёжных отключён |

**Ловушки:** «exactly-once из коробки»; `retries>0` без идемпотентности;
auto-commit в финансовом контуре; ordering «по всему топику».

### C5. Безопасность (вес 12)

**Что оценивается:** D6, SEC-01…SEC-08 с учётом INF-05/INF-06.

| Уровень | Якорь |
|---|---|
| 0 | Безопасность сведена к «включить SSL» |
| 2 | TLS, ACL, аудит перечислены без привязки к SEC-xx; аудит в COTE вопреки INF-05; SecMan вопреки INF-06; нет e2e-шифрования при SEC-05 |
| 4 | TLS 1.3 (≥1.2) на всех связках, включая брокер↔брокер и SR/UI → SEC-01; mTLS с принципалом на сервис (`FingerprintKafkaPrincipalBuilder`) или Kerberos (выбор обоснован) → SEC-02; ACL с минимальными правами по TOPIC/GROUP/CLUSTER/TRANSACTIONAL_ID через Corax UI/CLI → SEC-03; аудит: `kafka.se.audit.enable` + **LogAuditProvider → `kafka-audit.log` → агенты SIEM** (COTE недоступен — INF-05), фильтры `suppress` → SEC-04; e2e-шифрование ПДн `EncryptedByteArraySerializer` (соль ≥ 16 байт), ключи вне платформы → SEC-05; пароли конфигов — `crx-password-encrypt.sh`/ConfigProvider, профиль with-auth, замена `qwe123`, секреты в Vault (Vault Java Driver; SecMan исключён по INF-06) → SEC-06; ротация сертификатов SSL live update → SEC-07 + NFR-11; JMX закрыт или с аутентификацией; SSL-надёгрузка на CPU учтена в сайзинге |

**Ловушки:** «SecMan решит всё» (нет в банке); аудит «в COTE» без

аутентификации.

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "CRX-ARCH-001-RUB",
  "task_id": "CRX-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` по формуле из frontmatter; `excellent` при `total ≥ 85`,
`pass` при `≥ 70`, иначе `fail`; при любом `hard_fails[].triggered = true`
— `fail`.

## 9. Механические проверки (для детерминированного раннера)

Блок ниже парсится раннером. Включены только детекторы, реально ловящиеся
regex'ом; остальные HF — «только судья» (§2): HF-01 (число и размещение
узлов кворума требует понимания схемы), HF-04 и основная часть HF-02/HF-03
(контекст и семантика). HF-05 выводится из отсутствия deliverables.

```yaml
mechanical_checks:
  max_words: 4000
  deliverables:        # наличие разделов-артефактов в ответе (regex по тексту ответа)
    - {id: D1,  pattern: '(?im)^#{1,3}.*резюме'}
    - {id: D2,  pattern: '(?im)^#{1,3}.*схема\s+разв'}
    - {id: D3,  pattern: '(?im)^#{1,3}.*топологи'}
    - {id: D4,  pattern: '(?im)^#{1,3}.*(доставк|exactly|гарантии)'}
    - {id: D5,  pattern: '(?im)^#{1,3}.*(схемам?\w*\s+сообщен|schema\s*registry|контракт\w*\s+данных)'}
    - {id: D6,  pattern: '(?im)^#{1,3}.*безопасност'}
    - {id: D7,  pattern: '(?im)^#{1,3}.*(квот|производительност|ёмкост)'}
    - {id: D8,  pattern: '(?im)^#{1,3}.*(репликац|архив|восстановлен|mirror)'}
    - {id: D9,  pattern: '(?im)^#{1,3}.*трассировк'}
    - {id: D10, pattern: '(?im)^#{1,3}.*(допущен|риск|альтернатив)'}
  hard_fails:          # детекторы-кандидаты; итоговое решение — за судьёй
    - {id: HF-02, pattern: '(?im)acks\s*=\s*[01]\b', note: 'кандидат: acks=0/1; судья проверяет контекст платёжных топиков и обоснование'}
```
