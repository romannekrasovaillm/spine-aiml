## 1. Продукт: Platform V Corax `[DOC]`

### 1.1 Что это и состав

- «Программный брокер сообщений… распределенная, отказоустойчивая,
  реплицированная и легко масштабируемая система передачи сообщений»;
  «все сообщения Platform V Corax хранит на диске».
- Состав компонента Corax (KFKA): **Apache Kafka** (обязателен), **Apache
  ZooKeeper** (по таблице состава обязателен — но см. KRaft в §1.2),
  **Corax Schema Registry**, **Corax UI**, **Corax Mirror Maker 2**
  (трое последних опциональны).
- Ядро — Apache Kafka; «наследуя архитектуру **Apache Kafka 3.9**»
  поддерживает exactly-once транзакции. Точная версия ядра в дистрибутиве
  16.392.0 — [ТРЕБУЕТ ПРОВЕРКИ].
- Java: OpenJDK/SberJDK 17 и 21; с 16.392.0 OpenJDK 11 не поддерживается.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/SKILL.md; corpus/pv_docs/txt/kfk__documents__about__objective.html.txt

### 1.2 Координационный слой: ZooKeeper-ансамбль или KRaft

- Два режима метаданных: ZooKeeper-ансамбль или KRaft-контроллеры (шаг 2
  Ansible-установки — «kraft controller или zookeeper»). НФТ: «метаданные
  кластера хранятся в отказоустойчивом хранилище (ZooKeeper-ансамбль или
  KRaft-контроллеры), что исключает единую точку отказа». Совмещение
  допустимо, но «брокер и KRaft-контроллер рекомендуется разворачивать на
  отдельных хостах».
- ZooKeeper: «минимальное число узлов… — 3», «для каждого ансамбля
  предполагается только нечетное количество узлов»; ансамбль работоспособен,
  пока «строгое большинство узлов остается в рабочем состоянии».
  Standalone-конфигурация «не рекомендован для использования в промышленной
  эксплуатации».
- Конфиг ансамбля: `server.N=ip:2888:3888`, `clientPort=2181`,
  обязательные `tickTime`/`initLimit`/`syncLimit`; поддерживаются
  **иерархические кворумы** (`group.x=nnnn[:nnnn]` + `weight.x`; группы не
  должны пересекаться). Устаревшие транзакционные логи и снепшоты ZooKeeper
  с диска не удаляет — чистка на администраторе.
- Страниц конфигурации KRaft (`process.roles`, `controller.quorum.voters`)
  в съёме нет — [ТРЕБУЕТ ПРОВЕРКИ]. Расхождение источников (ZooKeeper
  «обязателен» vs KRaft-режим) трактовать как «ZooKeeper обязателен в
  ZK-режиме».

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__about__conceptual-model.html.txt

### 1.3 Брокеры, ISR, отказ внутри ЦОД

- **Ожидаемая доступность 99,9 %** при условиях: каждый компонент на
  отдельном хосте, фактор репликации ≥ 3, `min.insync.replicas` ≥ 2;
  rolling update без простоя; `unclean.leader.election.enable=false`.
- При отказе брокера ZooKeeper/контроллер переназначает лидеров партиций
  из ISR; вернувшийся брокер догоняет репликацией и возвращается в ISR.
- Corax-специфичный `auto.leader.rebalance.on.not.isr.broker.enable=false`
  — брокер с несинхронизированными репликами не участвует в выборах лидера
  (защита от «дискового шторма» при возврате брокера).
- Партиция делится на сегменты; удаление по retention
  (`log.retention.hours`) — целыми сегментами.
- **Auto Data Balancer**: режимы `--generate`/`--execute`/`--auto`;
  в `--auto` применение **только в технологическое окно**; throttle
  (Байт/с) и rack-awareness.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__about__non-functional-features.html.txt

### 1.4 Гарантии доставки (для оценки RPO)

- **acks**: `0` — retries не работают; `1` — при отказе лидера до
  репликации на ISR «запись будет потеряна»; `all` — подтверждение всех
  ISR, «самая надежная из доступных гарантий».
- **Идемпотентный продюсер** (`enable.idempotence=true`) и
  **транзакционный продюсер** — с Corax 5.272.0; рекомендация вендора:
  «replication.factor = 3 и min.insync.replicas = 2 является оптимальной
  для большинства случаев». Границы: идемпотентность — «только для
  сообщений, отправленных в одной сессии».
- **Важно для DR:** все эти гарантии — **внутрикластерные**. Они ничего не
  говорят о судьбе подтверждённых сообщений при потере всего ЦОД до их
  репликации MM2 (см. §1.7): межкластерная репликация «отличается от
  механизма внутрикластерной репликации в Kafka».

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/dev-patterns.md; corpus/pv_docs/txt/kfk__documents__dev-guide__instructions__producer__usage-examples.html.txt

### 1.5 Потребители: смещения, группы, восстановление позиции

- Две позиции: **position** (offset следующей записи) и **committed
  position** (последняя надёжно сохранённая; «точка восстановления после
  сбоя»). Фиксация — автоматически (`enable.auto.commit=true`, дефолт
  `auto.commit.interval.ms` = 5000 мс) или вручную
  `commitSync()`/`commitAsync()`.
- `auto.offset.reset`: earliest / latest / none — поведение потребителя,
  **у которого нет сохранённого смещения** в кластере (критично при
  переключении на резервный кластер, куда offsets группы не перенеслись).
- Смещения групп хранятся в служебном топике `__consumer_offsets`
  исходного кластера (см. также §1.7 про Checkpoint Connector).
- Группы: каждая партиция — ровно одному потребителю группы; потребителей
  в группе больше партиций бесполезно (лишние простаивают). При
  непредсказуемом времени обработки вендор рекомендует: автофиксация
  выключена, ручной коммит после обработки, `pause` партиции.

### 1.6 Corax Schema Registry при DR

- «Работает по принципу **Active-Active**, что обеспечивает его
  георезервирование и масштабирование»; все узлы идентичны, конфликты
  разрешаются через Kafka-топик; разворачивается отдельно от брокеров.
- Хранение — топик **`_crx_schemas`** (создаётся автоматически, 1 партиция,
  `cleanup.policy=compact`): «**Параметры менять запрещено**». Это лог
  предзаписи всех схем/субъектов/версий/настроек совместимости; судьба
  этого топика при потере ЦОД (репликация MM2, восстановление из архива)
  в документации съёма не описана — [ТРЕБУЕТ ПРОВЕРКИ] у вендора.
- ID схемы пишется в заголовок сообщения; субъект по умолчанию
  `<топик>-value` / `<топик>-key`; режим совместимости по умолчанию —
  BACKWARD. Serdes — **только Java**.
- **Records Policy** — проверка соответствия сообщений схеме на стороне
  брокера; «НЕ ВХОДИТ в состав Apache Kafka и доступен только при
  использовании Corax».

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/security-schema-registry.md; corpus/pv_docs/txt/kfk__documents__schema-registry__sr-architecture.html.txt

### 1.7 Corax Mirror Maker 2 (межкластерная репликация)

- «Инструмент для репликации данных и метаданных между кластерами Platform
  V Corax/Apache Kafka», основан на платформе **Kafka Connect**; «упрощает
  процесс настройки и масштабирования репликации, обеспечивая
  синхронизацию разделов, смещений и секций между кластерами». «Mirror
  Maker это инструмент межкластерной репликации, и он **отличается от
  механизма внутрикластерной репликации в Kafka**».
- Компоненты: **Source Connector** (читает данные из исходного кластера;
  MirrorSourceTask передаёт их MirrorSinkTask), **Sink Connector/Task**
  (запись в целевой кластер через Kafka Producer; «поддерживает
  параллельную запись в несколько партиций, что позволяет масштабировать
  процесс репликации»), **Checkpoint Connector/Task** (контрольные точки
  offsets; контрольные точки сохраняются в специальном топике
  `__consumer_offsets` исходного кластера), **Heartbeat Connector/Task**
  (сигналы в удалённые кластеры «чтобы убедиться в их доступности»),
  **Config Connector/Task** (динамическое изменение конфигурации
  репликации «без необходимости перезапуска процесса репликации»).
  **MirrorOffsetSyncs** — «синхронизирует смещения потребителей между
  кластерами… помогает поддерживать соответствие между смещениями
  потребителей в исходном и целевом кластерах».
- Концептуальная модель: «прозрачная репликация всех элементов: сообщения;
  метаданные топиков; группы потребителей; контрольные точки смещения;
  **права доступа (ACL)**».
- Функции: «Динамическое обнаружение изменений — автоматически обнаруживает
  новые топики и партиции, и синхронизирует их с целевыми кластерами»;
  «Checkpoints — сохранение позиций (offsets) для восстановления после
  сбоев»; «Покрытие метриками — …данные о задержках (лаг) репликации на
  кластерах или объединении кластеров»; «Топологии Active-Active/
  Active-Standby»; «Масштабируемость … благодаря использованию Kafka
  Connect»; «Отказоустойчивость — …за счет автоматического восстановления
  соединений и обработки ошибок».
- Сценарии применения: репликация между удалёнными кластерами; **аварийное
  восстановление**; организация единого кластера из нескольких; изоляция
  (пром/тест); облачная/гибридная миграция. Архитектурные блоки: исходный
  кластер, Kafka Connect Cluster (обработка), целевой кластер; служебные
  топики (mm2-configs, `__consumer_offsets` и др.).
- **Чего в съёме нет** ([ТРЕБУЕТ ПРОВЕРКИ]): страницы сценариев настройки
  MM2 (mm2-scenarious), параметры потоков, переименование топиков
  (remote-topic-префиксы), точная семантика перевода смещений при
  переключении, гарантии упорядоченности/дедупликации при репликации.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__mm2__introduction.html.txt; corpus/pv_docs/txt/kfk__documents__mm2__architecture.html.txt

### 1.8 Бэкап топиков в S3 и восстановление

- «Corax поддерживает сохранение и восстановление топиков в S3 хранилища.
  Функциональность реализуется с помощью механизма **Kafka Connect** и
  доработанного плагина **Lenses Stream Reactor**». В примере документации
  используется AWS S3; поддерживается кастомный endpoint
  (`connect.s3.custom.endpoint`).
- Два коннектора: **sink** (`io.lenses.streamreactor.connect.aws.s3.sink.
  S3SinkConnector`, выгрузка топиков в S3) и **source** (`...s3.source.
  S3SourceConnector`, восстановление данных в топик). Путь к плагину —
  `plugin.path`.
- Правила экспорта/импорта — **KCQL**: `insert into <bucket> select * from
  <topic> STOREAS BYTES`; `flush.count` (пример: `'flush.count'=1` —
  «немедленная запись при получении сообщения»).
- Конвертеры `ru.sbrf.kafka.connect.EncryptedByteArrayConverter` для
  key/value/header (каждому — `*.converter.password` для дешифровки),
  `schemas.enable=true`.
- Служебные топики коннекторов в примере документации: `connect-offsets`,
  `connect-configs`, `connect-status` — **в примере с
  `replication.factor=1`** (учебное значение, для прода повышать).
- Обработка ошибок: DLQ (`errors.deadletterqueue.topic.name`),
  `errors.tolerance` (none/fail/all), `errors.log.include.messages=true`.
- SSL к брокеру в примере — через
  `ru.sbrf.kafka.secman.SecmanSslEngineFactory` + параметры
  `consumer/producer.secman.*` (endpoint, namespace, role_id/secret_id
  закодированы `${decode:...}`). **Внимание:** это пример под SecMan;
  при отсутствии SecMan в контуре способ подключения SSL к брокеру —
  отдельный вопрос конфигурации (стандартные SSL-параметры либо иной
  механизм — увязать с имеющимся контуром сертификатов банка).
- В примере source-коннектора пароль truststore указан открытым текстом
  (`qwe123`) — это дефолт инсталлятора, в проме заменяется обязательно
  (см. §1.9).
- Запуск: `bin/connect-distributed.sh connect.properties`; управление —
  через REST API.
- НФТ: «**архивирование и восстановление данных выходят за рамки функций
  Corax**… Исключение — облачные хранилища S3». Т.е. S3 — единственная
  документированная цель архивирования.
- **Чего в съёме нет** ([ТРЕБУЕТ ПРОВЕРКИ]): страницы sink/source-options
  (полный список опций), поведение source-коннектора при восстановлении
  (сохранение ключей/партиционирования/смещений исходного топика не
  описано), производительность коннекторов.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__administration-guide__scenarious__s3__usage.html.txt

### 1.9 Безопасность, применимая к DR-контуру

- **Каналы**: TLS 1.2/1.3, mTLS, настраиваемые cipher suites — на всех
  связках, включая брокеры↔брокеры и Schema Registry/Corax UI/ZooKeeper.
  Требование: TLS ≥ 1.2, рекомендуется 1.3.
- **Аутентификация**: X.509 (в т.ч. `FingerprintKafkaPrincipalBuilder`),
  Kerberos (SASL/GSSAPI, keytab).
- **ACL**: ресурсы CLUSTER, GROUP, TOPIC, TRANSACTIONAL_ID и др.;
  ALLOW/DENY; управление через Corax UI и CLI. MM2 реплицирует ACL между
  кластерами (§1.7).
- **Аудит**: встроенный плагин (`kafka.se.audit.enable`, дефолт true):
  топики, ACL, конфигурации, перераспределение партиций, группы, квоты.
  Провайдеры: `TsAuditProvider` — в компонент **COTE** продукта Platform V
  Monitor по HTTPS; `LogAuditProvider` — файл `kafka-audit.log` (INFO).
- **Сквозное (e2e) шифрование**: «данные шифруются и расшифровываются на
  стороне клиента, поэтому механизм не зависит от настройки соединения с
  брокерами». Симметричное — `EncryptedByteArraySerializer` (секретная
  фраза + соль ≥ 16 байт; соль и ключ потребителя совпадают с продюсером).
- **Пароли в конфигурациях**: `crx-encoding.sh` /
  `crx-password-encrypt.sh` (PBKDF2WithHmacSHA1 + AES-256; «дешифрование
  пароля не поддерживается»); ConfigProvider `${имя:пароль}`. Дефолтный
  пароль инсталлятора `qwe123` опубликован в документации — в проде
  заменить обязательно.
- **SecMan** (СберТех): хранение секретов, выпуск сертификатов из PKI.
  Заявлен Vault Java Driver — «интеграция с HashiCorp Vault для
  динамического получения секретов».
- **SSL live update**: ротация сертификатов без недоступности — по одному
  брокеру, после запуска ждать полной репликации
  (`--under-replicated-partitions` = 0).

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/security-schema-registry.md; corpus/pv_docs/txt/kfk__documents__administration-guide__audit.html.txt

### 1.10 Мониторинг лага и здоровья

- **HTTPReporter** (`ru.sbrf.kafka.HttpReporter`): метрики Prometheus,
  порт 7011 (HTTP) / 7012 (HTTPS).
- «Здоровые» значения кластера: `ActiveControllerCount` = 1,
  `OfflinePartitionsCount` = 0, `UnderReplicatedPartitions` = 0,
  `UncleanLeaderElectionsPerSec` = 0 (ненулевое = потеря данных).
- Consumer lag: клиентская `records-lag-max`; координаторские метрики
  `offset.metadata.group.*` и `timestamp.metadata.group.*` (возраст
  старейшего непрочитанного сообщения).
- MM2: «широкий спектр метрик, таких как данные о задержках (лаг)
  репликации на кластерах» (§1.7). Конкретные имена метрик MM2 в съём не
  вошли — [ТРЕБУЕТ ПРОВЕРКИ].

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__administration-guide__monitoring.html.txt

### 1.11 Системные требования и профиль нагрузки вендора

- Минимум (пром): брокер 4 CPU / 16 ГБ RAM / 200 ГБ; ZooKeeper или
  KRaft-контроллер 4 CPU / 4 ГБ / 64 ГБ; Schema Registry и Corax UI по
  2 CPU / 1 ГБ heap / 32 ГБ. «Для обеспечения отказоустойчивости…
  рекомендуется каждый компонент разворачивать на отдельном хосте»;
  диски RAID10 + XFS; «максимальная производительность… при использовании
  SSD-дисков и сетевых интерфейсов 10 Гбит/с».
- ОС: CentOS 8.7+, Astra Linux SE 1.7.3+, Альт СП 8+, SberLinux OS Server
  9.7.0+/8.10.4+. Опционально: SecMan 1.7.0, Platform V Monitor 6.0.200+
  (аудит в COTE).
- Профиль нагрузки вендора: **13 000 tps** при среднем сообщении 10 000

- Масштабирование: брокеры и партиции добавляются без простоя. Установка —

  идемпотентны; критерий успеха `unreachable=0 failed=0`).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Окский Капитал"» (вымышленный, топ-30 по активам) год назад
ввёл в пром **событийную платформу процессинга** на Platform V Corax
16.392.0: события карточных авторизаций, клиринговые сообщения, клиентские
уведомления, фрод-мониторинг, выгрузка в DWH. Платформа развёрнута **только
в ЦОД-1**, DR-контура нет. Внешний аудит катастрофоустойчивости (контекст
Положения Банка России № 719-П: процессы экосистемы карточных платежей —
критичные) указал на неприемлемый риск: полная потеря ЦОД-1 останавливает
событийный контур и делает невосстановимой историю событий. Архитектурному
комитету нужен проект георезервирования с **честными RPO/RTO по классам
топиков** — без деклараций «нулевых потерь», которые комитет заведомо
отклонит.

### 2.2 Ландшафт AS-IS

- Кластер Corax «CRX-PROD» в ЦОД-1: 6 брокеров (16 CPU / 64 ГБ / RAID10
  NVMe 4 ТБ), ZooKeeper-ансамбль из 3 узлов — **все узлы в ЦОД-1**;
  Corax Schema Registry (2 узла), Corax UI. Всё развёрнуто Ansible-ролью,
  профиль безопасности с mTLS.
- Топики: RF = 3, `min.insync.replicas` = 2, `acks=all`, идемпотентные
  продюсеры на финансово значимых потоках; онлайн-retention **14 дней**.
- Потребители (Java 17 / Spring Boot): фрод-сервис (группа из 12
  инстансов), процессинг-адаптеры, сервис уведомлений, DWH-загрузчик,
  ночные сверки. Kubernetes банка есть в обоих ЦОД (active/standby).
- **Отсутствует**: второй кластер, межкластерная репликация,
  архивирование в S3, runbook'и DR, учения.
- ЦОД-2 «Резервный» введён в строй и пустует под платформу.

### 2.3 Классы топиков и нагрузка

| Класс | Состав | Топиков | Целевые RPO/RTO (ожидание бизнеса) |
|---|---|---|---|
| A — финансово значимые | авторизации, клиринговые сообщения, подтверждения списаний | 8 | RPO ≤ 60 с, RTO ≤ 30 мин при потере ЦОД |
| B — операционные | статусы операций, клиентские уведомления | 15 | RPO ≤ 15 мин, RTO ≤ 2 ч |
| C — аналитические | события для DWH, витрины, поисковый индекс | 20 | RPO ≤ 24 ч, RTO ≤ 24 ч |
| S — служебные | `_crx_schemas`, connect-*, mm2-* | — | отдельный разбор (см. §1.6–§1.8) |

Нагрузка и объёмы (суммарно по классам):

- Средний поток **3 000 событий/с**, вечерний/зарплатный пик **12 000
  событий/с**; средний размер сообщения **2 КБ**; реестровые файлы сверок —
  до **4 МБ** на сообщение.
- Рост нагрузки **+25 % в год**, горизонт планирования 5 лет.
- Онлайн-хранение 14 дней; **регуляторный архив — 5 лет** с возможностью
  восстановления топика на произвольную дату.
- Потребители класса A должны после переключения продолжить с позиции,
  удовлетворяющей RPO класса; повторная обработка уже прочитанных сообщений
  допустима, но её окно должно быть оценено и зафиксировано.

| SEC-02 | Аутентификация всех клиентов платформы, включая коннекторы MM2 и S3; персональный принципал на сервис; анонимный доступ запрещён |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами (например: один растянутый на два ЦОД кластер
  с синхронной записью vs два кластера + MM2; актив-актив vs актив-стенбай).
- Особая чувствительность комитета: **роль третьей площадки в кворуме
  координации** (что происходит при потере каждой из трёх площадок) и
  **честный RPO класса A** (комитет знает, что межкластерная репликация
  асинхронна, и ждёт оценки лага из нагрузки и канала, а не декларации).
- Выбор ZooKeeper vs KRaft — явно, с оценкой зрелости документации
  (см. §1.2, §1.12).
- Судьба служебного топика Schema Registry `_crx_schemas` при DR должна
  быть разобрана явно (реплицировать ли MM2, что грозит) — при пробелах
  документации зафиксировать вопрос к вендору.

### 2.8 Что можно принять допущением `[ASSUME]`

- Точная версия ядра Apache Kafka в 16.392.0 не задана — не использовать
  или пометить как допущение (§1.1).
- Клиентские приложения допускают доработку (стратегии фиксации смещений,
  поведение при переключении).
- Клиенты платформы — Java-сервисы (serdes Schema Registry — только Java,
  §1.6).
- Vault доступен из обоих ЦОД с латентностью ≤ 5 мс; секреты коннекторов
  допустимо выдавать через Vault-интеграцию либо штатное шифрование
  конфигураций Corax (§1.9) — выбор обосновать.
- Межцодового канала хватает для репликации пикового потока с запасом
  ≥ 3× (подтверждается расчётом решающего).
- Производительность MM2 и S3-коннекторов документацией не нормирована
  ([ТРЕБУЕТ ПРОВЕРКИ]) — оценки делать из нагрузки и подтверждать
  нагрузочным тестированием (INF-07).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| RPO / RTO | Допустимая потеря данных по времени / допустимое время восстановления |
| ISR / RF | In-Sync Replicas / replication.factor (внутрикластерная репликация) |
| MM2 | Corax Mirror Maker 2 — межкластерная репликация на Kafka Connect |
| Checkpoint Connector | Компонент MM2: контрольные точки смещений между кластерами |
| MirrorOffsetSyncs | Компонент MM2 синхронизации смещений потребителей между кластерами |
| `__consumer_offsets` | Служебный топик смещений групп потребителей |
| `_crx_schemas` | Служебный топик Schema Registry (параметры менять запрещено) |
| KCQL | Язык правил коннекторов Lenses Stream Reactor (S3) |
| DLQ | Dead Letter Queue — топик для сообщений, которые коннектор не обработал |
| 719-П | Положение Банка России об операционной надёжности (контекст сценария) |
| Кворум | Строгое большинство узлов ансамбля ZooKeeper / контроллеров KRaft |
