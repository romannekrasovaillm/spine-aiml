# Задача PGL-MIG-001

## 1. Роль

Вы — ведущий архитектор решений в Департаменте корпоративной архитектуры банка.
Вам поручено спроектировать **архитектуру поэтапной миграции** крупной
автоматизированной системы «Реестр гарантий и аккредитивов» (АС РГА,
12 ТБ, режим 24/7) с **Oracle Database 19c** на **Platform V Pangolin DB**
и подготовить архитектурную записку для Архитектурного комитета. Записка
должна покрыть весь жизненный цикл миграции: инвентаризацию, конвертацию
схемы и кода, канал данных с CDC-досинхронизацией, параллельную эксплуатацию,
cutover и обратимый откат.

## 2. Что нужно сделать

На основе исходных данных из `CONTEXT.md` (факты о продукте §1, ландшафт
AS-IS, нефункциональные требования, требования ИБ, инфраструктурные
ограничения §2):

1. Провести **инвентаризацию объектов миграции** AS-IS: классифицировать
   объекты БД и механизмы Oracle по категориям переноса (переносится
   инструментом / переносится с переработкой / не переносится — требует
   замены решения).
2. Предложить **стратегию и этапность миграции** (волны/этапы,
   критерии входа и выхода каждого этапа, контрольные точки), удовлетворяющую
   требованию непрерывности приёма операций (NFR-07) и обратимости (NFR-09).
3. Спроектировать **конвертацию схемы и кода**: таблица соответствия
   механизмов Oracle средствам Pangolin (или переработке), оценка доли
   ручной доработки, выбор инструментов из дистрибутива с учётом их
   документированных ограничений и редакционных границ.
4. Спроектировать **канал данных**: начальную загрузку 12 ТБ и
   непрерывную CDC-досинхронизацию Oracle → Pangolin с обоснованием выбора
   механизма и честным учётом его ограничений (включая стык с TDE).
5. Спроектировать **параллельную эксплуатацию и верификацию данных**:
   сверка полноты и консистентности, мосты коэкзистенции, критерии
   готовности к cutover.
6. Спроектировать **cutover и откат**: чек-лист переключения с evidence,
   точку невозврата, обратный канал синхронизации на окно отката, оценку
   укладывания в ограничения NFR-07/NFR-09.
7. Описать **целевой контур Pangolin** в объёме, необходимом для приёма
   мигрируемой нагрузки: топология HA/DR на два ЦОД, пул соединений,
   партиционирование, ёмкость, контур безопасности (TDE, ключи, роли) —
   как условия готовности приёмника, без детальной проработки
   эксплуатации (это отдельная задача).
8. Явно зафиксировать **компромиссы, риски, открытые вопросы к вендору
   и отвергнутые альтернативы**.
9. Показать **трассировку** каждого требования (NFR-xx, SEC-xx, INF-xx)
   на принятые решения.

## 4. Ограничения и правила

- Опирайтесь **только на функциональность, подтверждённую документацией
  Pangolin** (факты приведены в CONTEXT.md §1 с пометкой `[DOC]`). Если
  используете возможность, отсутствующую в CONTEXT.md, — явно пометьте её
  как **допущение, требующее проверки**, а не как факт. Это особенно важно
  для миграционного инструментария: у части инструментов документированы
  жёсткие ограничения (источники, редакции, совместимость с TDE), нарушение
  которых делает план несостоятельным.
- Не изобретайте компоненты и не переименовывайте существующие. Используйте
  официальные наименования: `ora2pg`, `orafce`, `oracle_fdw`, `pgloader`,
  `pgcopydb`, `wal2json`, `test_decoding`, Platform V GraDeLy, Pangolin
  Manager, Pangolin DCS, Pangolin Pooler и т.д.
- Каждое ключевое решение должно быть привязано к требованию (NFR/SEC/INF)
  и сопровождаться кратким обоснованием «почему так, а не иначе».
- Числовые оценки (время начальной загрузки, требуемая пропускная
  способность канала и CDC, ёмкость дисков, длительность прерывания записи
  при cutover) должны быть выведены из исходных данных, а не заявлены
  декларативно.
- Объём ответа: не более 4000 слов без учёта кода диаграмм и таблиц.
- Язык ответа: русский; допустимы англоязычные технические термины.

## 6. Режим прохождения

Прогон выполняется **только в режиме `agentic`** (web_fetch по разрешённым
доменам документации + файловая система + выполнение кода): проверяется
способность агента самостоятельно собирать доказательства о продукте и
подтверждать расчёты (окна загрузки, пропускная способность, ёмкость).
Режим фиксируется в протоколе прогона и учитывается судьями
(см. RUBRICS.md, `run_mode_adjustments`).

## 7. Что НЕ требуется

- Детальное проектирование целевой эксплуатационной архитектуры Pangolin
  (полный контур безопасности, сценарии обновления СУБД, runbook-и) — это
  профиль смежной задачи; здесь целевой контур описывается в объёме
  «условия готовности приёмника миграции» (D8).
- Проектирование прикладной архитектуры АС РГА (микросервисы, API, UI).
- Переписывание конкретных PL/SQL-процедур — достаточно классификации,
  оценки трудоёмкости и демонстрации подхода на классах объектов.
- Сметы, лицензионные расчёты стоимости, выбор конкретных моделей серверов.
- Пошаговые инструкции (команды, конфиги целиком) — достаточно ссылок на
  соответствующие разделы документации.

## 8. Критерии приёмки (кратко)

Полные рубрики — в `RUBRICS.md`. Ключевые точки отсечения («hard fail»):

- `pgloader` предложен как инструмент миграции **с Oracle** (он
  документирован только для MS SQL Server / MySQL / SQLite);
- `pgcopydb` предложен как CDC-канал с источника Oracle, либо
  `pgcopydb follow` — при включённом TDE на приёмнике, подано как рабочее
  решение без оговорки о документированной несовместимости;
- вымышленные компоненты или функции Pangolin поданы как факт (например,
  «Pangolin нативно исполняет PL/SQL», «встроенный CDC-коннектор
  Oracle → Pangolin»);
- предложена миграция «big bang»: полная перекладка 12 ТБ в квартальное
  окно 4 часа без предварительной загрузки и CDC-досинхронизации — при
  действующем требовании непрерывности приёма (NFR-07);
- заявлен RPO = 0 на DR-контуре или CDC-канале при асинхронной репликации,
  либо автоматический promote резервного кластера при двух ЦОД без разбора
  документированного ограничения;
- отсутствует хотя бы один из обязательных артефактов D1–D10.

## 9. Примечания для составителей бенчмарка

Варианты порождения задач из этого шаблона (для расширения набора):

- **Вариация A (MS SQL):** заменить источник на MS SQL Server — проверить
  корректное применение pgloader/tds_fdw и отсутствие автоматического
  переноса T-SQL.
- **Вариация B (PostgreSQL-источник):** источник — ванильный PostgreSQL —
  проверить применение pgcopydb с follow и честный учёт его ограничений
  (рестарты, TDE, права суперпользователя, идентичность расширений).
- **Вариация C (без внешнего CDC):** запретить закупку Platform V GraDeLy —
  проверить, что решающий перестроит стратегию (снапшот ora2pg + окно
  досинхронизации) и честно пересчитает прерывание записи вместо подмены
  требований.
- **Вариация D (тестовые данные):** добавить требование обфускации ПДн на
  миграционных стендах — проверить знание pg_anon.

Рекомендуется хранить каждую вариацию как отдельный `task_id` с суффиксом
(`PGL-MIG-001-A`, `-B`, …) и общим `CONTEXT.md` с параметризованным §2.
