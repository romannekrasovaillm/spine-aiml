## 1. Продукт: Platform V Pangolin DB `[DOC]`

### 1.1 Позиционирование, редакции, линейка

- Реляционная СУБД, **специальная сборка PostgreSQL** (код продукта PSQ,
  вендор — АО «СберТех», линейка Platform V) с доработками под безопасность,
  доступность, надёжность и эксплуатацию. Это **OLTP-СУБД, не MPP**:
  для аналитических нагрузок вендор прямо рекомендует специализированные
  продукты (аналитический профиль линейки — Platform V DataMarts).
- Диалект — PostgreSQL (полная совместимость синтаксиса и протокола с
  базовой версией ядра); процедурный язык — **PL/pgSQL**. Недоверенные языки
  (PL/Perl, PL/Python3, PL/Tcl и др.) поставляются отдельным «untrusted»
  архивом дистрибутива, их использование контролируется механизмом
  «контроль использования процедурных языков».
- Продукт зарегистрирован в Реестре российского ПО (запись №13436 от
  29.04.2022). Актуальная версия линейки документации на дату снимка —
  **8.2.0**; поддержка версии 8.2 (выход патчей) — до выхода версии 11.1.0.
- Редакции: **Standard**, **Standard для ERP-систем**, **Enterprise**,
  **Enterprise для ERP-систем**. Ключевые для миграции и промышленной
  эксплуатации функции — **только Enterprise**: TDE, защита данных от
  привилегированных пользователей, защита параметров конфигурации,
  интеграция с KMS HashiCorp Vault, маскирование запросов, внешняя
  авторизация LDAP, нативное интервальное партиционирование, глобальные
  индексы, pgloader, pgcopydb. Во всех редакциях: парольные политики,
  двухфакторная аутентификация, аудит событий безопасности по
  ГОСТ Р 59548-2022, сквозная аутентификация Pooler ↔ СУБД.
- Поддерживаемые ОС: Platform V SberLinux OS Server 9/10, Astra Linux
  SE 1.8 (в т.ч. установка на «Смоленск»), РЕД ОС 7.3/8, Альт СП 10,
  Альт Сервер 10.
- Политика расширений: поддерживаются только расширения из официальной
  таблицы поставки; собранные или модифицированные вне поставки — не
  поддерживаются.
- Версии компонентов дистрибутива 8.2.0: pangolin-manager 4.2.0,
  pangolin-pooler 3.2.0.

### 1.2 Инструментарий миграции: что из чего переносит

Сводка инструментов миграции из дистрибутива и экосистемы (версии — из
документации 8.2.0):

| Инструмент | Версия | Источник данных | Редакция | Назначение |
|---|---|---|---|---|
| ora2pg | 23.0 | Oracle | любая (поставка в `migration_tools`) | Миграция БД Oracle → Pangolin |
| orafce | 4.4.0 | Oracle (код) | любая | Функции Oracle для PL/pgSQL (dbms_* и др.) |
| oracle_fdw | 2.5.0 | Oracle | любая | FDW к Oracle (поэтапная коэкзистенция) |
| tds_fdw | 2.0.3 | MS SQL, Sybase | любая | FDW по протоколу TDS (FreeTDS ≥ 1.1.20) |
| pgloader | 3.6.9 | MS SQL, MySQL, SQLite | Enterprise | Перенос данных через COPY |
| pgcopydb | 0.14 | PostgreSQL | Enterprise | Полная копия БД + CDC-follow |

Ключевые факты и ограничения:

- **ora2pg 23.0 отсутствует в продукте в версии 8.2.0** (не установлен по
  умолчанию): поставляется в каталоге `migration_tools/ora2pg`
  дистрибутива (ora2pg-23.0, модули DBD::Oracle 1.80, DBD::Pg 3.15,
  rpm Oracle Instant Client 18.5 — basic/jdbc/sqlplus/devel). Установка
  требует `sudo all`. Конфигурация — `ora2pg.conf` (DSN к Oracle); состав —
  Perl-скрипт `ora2pg` + модуль `Ora2Pg.pm`. Позиция вендора: ora2pg —
  «один из возможных вариантов и инструментов миграции. Окончательный выбор
  инструмента и его использование — в зоне ответственности продуктовой
  команды». Официальной «кнопки» миграции нет — оценку и пилот закладывать
  в план.
- **orafce 4.4.0** — «некоторые функции из СУБД Oracle, отсутствующие или
  ведущие себя иначе в PostgreSQL»: пакеты dbms_alert, dbms_output,
  dbms_pipe, dbms_random, dbms_utility, utl_file и др. По умолчанию не
  установлен. orafce покрывает **часть** функций/пакетов — ручная
  адаптация кода остаётся на проект.
- Комплекс «Для простоты миграции с Oracle Database» (заявлен в разделе
  «Основные функциональности»): orafce, **pg_dbms_lock** (аналог
  DBMS_LOCK), **pg_dbms_stats** (аналог DBMS_STATS; для Enterprise —
  функции экспорта), **psql_bfile** (составной тип bfile для доступа к
  внешнему файлу — аналог BFILE), **oracle_fdw**, ora2pg (в 3rd-party
  `migration_tools`), Platform V **GraDeLy** (CDC, нативная поддержка).
- **pgloader 3.6.9** (установлен по умолчанию, но функциональность — только
  Enterprise) — перенос данных **MS SQL Server / MySQL / SQLite** →
  PostgreSQL через COPY; загрузка из файлов. Доработки вендора: тип
  datetime2, скрытый запрос пароля MS SQL, маппинг
  datetimeoffset→timestamptz, перенос uuid. **Oracle не входит в список
  источников.** Автоматический перенос процедурного кода T-SQL не
  предусмотрен — только данные; DDL готовится отдельно
  (liquibase/flyway-подход).
- **pgcopydb 0.14** (3rd-party часть дистрибутива; Enterprise) — полная
  миграция БД **PostgreSQL → Pangolin** (кластер-кластер): clone/fork,
  follow (CDC через логическое декодирование, совместим с test_decoding и
  wal2json, дефолт — test_decoding), snapshot, compare schema/data, copy
  (db, roles, extensions, schema, data, table-data, blobs, sequences,
  indexes, constraints), dump/restore schema (pre-data/post-data/roles).
  **Ограничения (дословно из документации):** не запрашивает пароль для
  части команд (передавать параметром или беспарольная аутентификация по
  сертификату); не работает с хранилищем паролей; при полной миграции
  набор расширений (версии + GUC) источника и приёмника должен быть
  идентичен; **follow падает при перезапуске любой из БД**; follow требует
  суперпользователя на приёмнике (`SET session_replication_role`);
  **follow не работает с TDE**.
- Для миграции **с оригинального PostgreSQL** вендор предоставляет
  доработанную **pg_upgrade** («Инструмент миграции с оригинального
  PostgreSQL»; с версии 6.1.0 — миграция данных с PostgreSQL 15) — к
  данному сценарию (источник Oracle) неприменимо.
- После переноса БД через pg_dump/pg_restore доступна поддержка смещения
  LSN — важно для продолжения работы логической репликации/CDC на новом
  экземпляре.

### 1.3 Методология миграции (стадии, из документации)

Вендорская рамка процесса смены SQL-сервера (раздел pgloader, применима
широко как чек-лист миграционного проекта):

1. Архитектурное планирование (требования к сервису, DataFlow, SLA);
2. Планирование схемы данных (DDL под диалект целевого сервера, обычно
   liquibase/flyway);
3. Подготовка схемы: сначала DDL таблиц, затем индексы и связи;
4. Перенос данных;
5. Перенос кода (опционально: хранимые процедуры, триггеры, регламентные
   процедуры);
6. Валидация полноты данных (опционально).

Ключевые рекомендации по массовой загрузке: перенос в **неиндексированную
структуру** с последующей индексацией быстрее и не фрагментирует индексы;
на время загрузки — минимум ограничений целостности (PK, партиционирование),
после — довести БД до продуктивного состояния. Для pgloader рекомендуется
выделенная роль с правами на создание/наполнение объектов; на источнике —
пользователь с доступом ко всем переносимым объектам.

### 1.4 CDC: логическая репликация и декодирование

- Модель **публикация/подписка** (транзакционная логическая репликация):
  снапшот + поток изменений в порядке коммитов; поддерживается
  каскадирование; репликация между мажорными версиями и платформами.
  Доработка Pangolin — параметр `drop_repl_sync_slots_only_after_restart`
  (управление удалением неописанных в DCS слотов синхронизации логической
  реплики).
- Плагин логического декодирования **wal2json** входит в состав продукта:
  JSON на транзакцию (format-version 1) или на кортеж (2); опции
  include-xids, include-timestamp, include-schemas/types/typmod/type-oids,
  filter-tables/add-tables (по схемам с экранированием), include-pk,
  include-lsn. Требуется `wal_level = 'logical'` — **нужен перезапуск
  сервера** при включении. Изменения доступны через слоты логической
  репликации или SQL API. Доступ к старым версиям строк UPDATE/DELETE —
  по REPLICA IDENTITY.
- **test_decoding** — тестовый SQL-модуль вывода логического декодирования
  WAL (используется pgcopydb по умолчанию).
- Поддержка **смещения значения LSN** для облегчения работы с логической
  репликацией и CDC-решениями (расширение psql_logical_slot_rewind — слот
  со сдвигом в прошлое; актуально и после переноса БД через
  pg_dump/pg_restore).
- Механизм быстрой остановки walsender логической репликации; контроль
  целостности передачи WAL на реплику.
- Внешний CDC-продукт линейки: **Platform V GraDeLy (GDL 3.0.0)** —
  «логическая репликация данных с захватом изменений на клиенте или из
  журнала БД»; заявлена нативная поддержка GraDeLy в Pangolin.
- Важное негативное знание: штатных коннекторов к **Kafka, S3, HDFS** и
  аналогов PXF в документации Pangolin 8.2.0 **не описано**. Типовой
  паттерн обмена с такими системами — CDC через логическое декодирование
  (wal2json/GraDeLy) во внешний конвейер, либо FDW к реляционным
  источникам, либо файловый обмен через COPY/psql_bfile. Шина линейки —
  Platform V Corax.
- Направление каналов: wal2json читает журнал **Pangolin/PostgreSQL** —
  пригоден для **исходящих** из Pangolin каналов (обратная репликация,
  выгрузка в витрины). Захват изменений **на стороне Oracle** требует
  внешнего CDC (в линейке вендора — GraDeLy); собственного механизма
  чтения журналов Oracle у Pangolin нет.

### 1.5 FDW и параллельная эксплуатация (коэкзистенция)

- **oracle_fdw 2.5.0** — доступ к таблицам и представлениям Oracle
  (включая материализованные) как к сторонним таблицам: отображение WHERE
  и списка столбцов на сторону Oracle, поддержка EXPLAIN, DML
  (INSERT/UPDATE/DELETE) по сторонним таблицам, IMPORT FOREIGN SCHEMA.
  Из значимых параметров: `isolation_level` (предупреждение документации о
  повторном сканировании в транзакции и ошибке ORA-08177), `readonly`,
  `prefetch` (по умолчанию 200 строк за round-trip; **не работает с
  BLOB/CLOB/BFILE**), `key` для DML. Пароль можно брать из защищённого
  хранилища **pg_auth_config**; для Enterprise — использование хранилища
  параметров подключения.
- **tds_fdw 2.0.3** — FDW по протоколу Tabular Data Stream (MS SQL Server,
  Sybase), FreeTDS ≥ 1.1.20. Доработка Pangolin: пароль сторонней БД — в
  защищённом хранилище `pg_auth_config` (в оригинале — обязательный
  открытый логин/пароль в user mapping). Опция DSN со списком серверов
  через запятую — автопереключение при недоступности.
- Декларативное партиционирование допускает **смешение локальных партиций
  со сторонними (foreign) таблицами** через FDW — механизм, пригодный для
  поэтапного переноса доменов/периодов.
- Позиция скилла-дистиллята по стратегиям (вывод для ADR): разовая
  перекладка Oracle — ora2pg (схема+данные) + orafce (код) + ручная
  доработка по разделу портирования; FDW — как **временный мост**;
  параллельная эксплуатация (strangler) — oracle_fdw/tds_fdw для чтения
  «из старой» СУБД на время поэтапного переноса доменов.

### 1.6 Портирование кода PL/SQL → PL/pgSQL (документированные различия)

Из документа «Портирование PL/pgSQL» (руководство по программированию):

- Конфликт имён «переменная vs колонка»: PL/SQL трактует имя как колонку,
  PL/pgSQL выдаёт ошибку неоднозначности; лечение —
  `plpgsql.variable_conflict = use_column` (практично для больших объёмов
  кода).
- Тело функции — строковый литерал (долларовое цитирование).
- Типы: `varchar2` → `varchar`/`text`, `number` → `numeric`.
- **Пакетов нет** → схемы; **переменных уровня пакета нет** → временные
  таблицы.
- REVERSE-циклы целых чисел: границы инвертированы; FOR по запросу требует
  явного объявления целевых переменных; курсоры — другой синтаксис.

Прямого аналога **автономных транзакций** (PRAGMA AUTONOMOUS_TRANSACTION)
в перечне документированных расширений не найдено — помечать как
`[ТРЕБУЕТ ПРОВЕРКИ]` у вендора либо проектировать переработку (например,
вынос журналирующих вызовов на отдельное соединение; фоновое выполнение —
pg_background из дистрибутива — семантику автономной транзакции в общем
случае не воспроизводит).

Источник: banking/plugins/ru-data/skills/pangolin-db-architecture/references/migration-cdc.md; <KNOWLEDGE>/architecture/sber-stack/pangolin_sql_dialect.md

### 1.7 Партиционирование и соответствие механизмам Oracle

- **Декларативное партиционирование** (стратегии RANGE/LIST/HASH) — во
  всех версиях Pangolin; автоматическая маршрутизация INSERT; UPDATE с
  перемещением записей между партициями (**аналог Oracle ENABLE ROW
  MOVEMENT**); отсечение партиций в ядре (`enable_partition_pruning`,
  статическое и динамическое — PREPARE-параметры, nested loop, подзапросы).
- **Нативное интервальное автопартиционирование** (только Enterprise):
  `AUTO PARTITION BY RANGE (key) PERIOD (p) [OFFSET (o)]` — аналог Oracle
  PARTITION BY RANGE INTERVAL; партиции создаются автоматически при вставке
  данных, не попадающих в существующие партиции; поддерживается вложенное
  автопартиционирование. Ограничения: **схему автопартиционирования для уже
  созданной таблицы изменить нельзя** (решение о ключе/периоде принимается
  до наполнения); пустые партиции при удалении/перемещении данных не
  удаляются; не поддерживаются типы с плавающей точкой в ключе RANGE;
  пересечение ручных партиций с автосоздаваемыми — на совести
  проектировщика; для недельных интервалов задавать OFFSET (границы по
  умолчанию от эпохи 2000-01-01 — суббота).
- **Глобальные индексы и ограничения** (только Enterprise):
  `CREATE [UNIQUE] INDEX ... GLOBAL`, `PRIMARY KEY/UNIQUE ... GLOBAL` —
  физически единый B-Tree над партициями, уникальность по набору атрибутов,
  **не включающему ключ партиционирования** (главное функциональное
  отличие от ванильного PostgreSQL). Ограничения: только B-Tree; нет
  exclusion-ограничений и субпартиций; при `REINDEX INDEX CONCURRENTLY`
  глобального индекса на автопартиционированной таблице невозможен INSERT,
  создающий новую партицию; ATTACH таблицы с существующим PK к таблице с
  PRIMARY KEY GLOBAL запрещён.
- Операции Oracle **EXCHANGE PARTITION нет**: используется
  **DETACH + RENAME + ATTACH в одной транзакции**. Автоматического
  объединения/расщепления партиций нет — выполняется вручную в транзакции
  (создать заготовку SELECT-ом, удалить объединяемые, ATTACH).
- ATTACH готовой таблицы: `CREATE TABLE ... (LIKE ... INCLUDING DEFAULTS
  INCLUDING CONSTRAINTS)`, загрузить данные, `ALTER TABLE ... ATTACH
  PARTITION ... FOR VALUES ...` — механизм переиспользует готовые
  ограничения/индексы.
- **pg_pathman исключён из состава продукта и не поддерживается с версии
  7.1.0** — требуется переход на декларативное партиционирование
  (физические форматы данных у обоих подходов одинаковы, миграция в
  основном логическая).
- Ключ партиционирования: до 32 полей; для RANGE — INTEGER/NUMERIC/DATE/
  TIMESTAMP/TIMESTAMPTZ (не float). Для композитного ключа — параметр
  хранения `pruning_fields`, чтобы отсечение учитывало не только первый
  столбец (Enterprise).
- **Сжатие на уровне страниц** (Enterprise): `compresstype` =
  pglz | lz4 | zstd на таблицу, партицию, матпредставление, индекс или
  табличное пространство; включается `enable_page_compression` (reload).
  Типовой подход: сжимать исторические партиции, не трогая горячие.

### 1.8 HA/DR целевого контура (в объёме, нужном для приёмника миграции)

- Кластер высокой доступности = 2+ сервера с экземплярами одной БД,
  связанные **потоковой физической репликацией** (однопоточной, один
  лидер). Компоненты: **Pangolin Manager** (оркестратор; в комплекте
  документация Patroni 4.1.1 — вендорская сборка этого стека, CLI
  `pangolin-manager-ctl`, REST API), **Pangolin DCS** (распределённое
  хранилище конфигурации на базе **Raft**: кворум, блокировка лидера с
  TTL — `loop_wait`, `retry_timeout`, `ttl`), **Pangolin Pooler**.
  Заявляемые целевые показатели mission critical: **RPO = 0** и
  **RTO < 6 минут в год** простоя (Active/StandBy в разных ЦОД +
  автоматический failover + пулер).
- Операции `pangolin-manager-ctl`: `list`, `pause`/`resume` (режим
  обслуживания — иначе ручные действия кластер воспримет как сбой),
  `reload`, `restart`, `switchover` (плановое, **гарантия нулевых потерь
  даже в асинхронном режиме**), `failover`, `reinit` (пересоздание реплики
  с pg_basebackup, в т.ч. с узла с меткой clonefrom), `edit-config`.
- Режимы репликации (выбор — явный trade-off доступность/сохранность):
  **асинхронный** (дефолт; потери в пределах `maximum_lag_on_failover`
  байт WAL + записи за последние `ttl` секунд, в среднем `loop_wait` ≈ 2 с;
  `check_timeline: true` — не выбирать лидером реплику с другой временной
  шкалой); **стандартная синхронная PostgreSQL** (`synchronous_commit: on`
  + `synchronous_standby_names`; рекомендовано ≥ 2 реплик); **нестрогий
  синхронный Manager** (`synchronous_mode: true`: при недоступности реплики
  лидер деградирует в async — запись сохраняется; failover только на
  реплику со всеми зафиксированными транзакциями); **строгий синхронный**
  (`synchronous_mode_strict: true`: без синхронной реплики лидер блокирует
  запись). Тег `nosync: true` исключает узел из кандидатов в синхронные;
  `synchronous_node_count` (по умолчанию 1).
- **Правило двух ЦОД**: синхронный мульти-ЦОД кластер требует минимум
  3 узла СУБД и растянутый по ЦОД DCS с **нечётным числом узлов (3 или
  5)** — переживает падение одной зоны. Если ЦОД только два, документация
  прямо рекомендует **standby-кластер** во втором ЦОД вместо растянутого
  синхронного: «standby leader» реплицируется с первичного кластера,
  каскадные реплики — с него; у кластеров **разные scope DCS**, связей
  кроме репликации нет, standby не виден в `list` первичного.
  **Автоматическое повышение standby невозможно** (DC2 не отличает сбой
  DC1 от сетевого разделения) → **ручной promote** удалением секции
  `standby_cluster` из динамической конфигурации (**НЕ** `pg_ctl promote`);
  перед promote — **STONITH** основного, иначе split-brain. Возврат ЦОД-1:
  `pg_rewind` (требует `--data-checksums` и/или `wal_log_hints=on`) или
  пересоздание standby с нуля. Слот репликации на первичном создаётся
  вручную (или постоянные слоты Patroni).
- **Имена узлов уникальны** во всех связанных кластерах: совпадение
  application_name с узлом основного кластера молча ломает синхронную
  репликацию (ложные «синхронные» подтверждения → риск потери данных без
  ошибок в логах).
- **DCS failsafe mode**: при полной недоступности DCS кластер продолжает
  работать, если все узлы видят лидера через его REST API.
- **N-ЦОД в Pangolin Pooler**: режимы `NDC_ALLOWED`/`NDC_DISALLOWED`;
  команда `NDC_SUSPEND` — рвёт все клиентские и БД-соединения (кроме
  админ-консоли) и запрещает новые; `NDC_KEEPALIVE` — возобновляет приём;
  параметр `ndc_suspending_timeout` (сек, 0 = выкл.): без регулярного
  keepalive от внешнего арбитра пулер **сам** переходит в suspend
  (fail-closed — мёртвый арбитр = закрытый вход в БД).
- Резервное копирование: агент **CopyWala**, **pg_probackup** с
  инкрементальным копированием в режиме **ptrack**; выгрузка данных в дамп
  при включённых СЗИ (Enterprise) — для защищённых контуров.

### 1.9 Пулер и производительность (рекомендации, важные для приёма нагрузки)

- **Pangolin Pooler** — форк PgBouncer (в 8.2.0: версия 3.2.0, ядро
  PgBouncer 1.24.0). Порт по умолчанию 6544, админ-консоль — БД
  `pgbouncer`. Доработки: сквозная аутентификация пользователей (включая
  LDAP + аудит в лог пулера, команда `RESET_AUTH`), **поддержка
  подготовленных запросов в транзакционном режиме HA-кластера**,
  **сохранение контекста сессий (SET ROLE, search_path)** — доработки,
  снимающие классические ограничения PgBouncer; сертификаты PKCS#12;
  топология N-ЦОД; вывод `SHOW POOLS` в лог.
- Рекомендации вендора: `max_connections` определяется нагрузочным
  тестированием; стартовая эвристика `max_connections = GREATEST(5 × CPU
  cores, 100)`; **одинаковое значение на всех узлах, способных стать
  Primary** — иначе после failover часть клиентов не получит подключение;
  изменение требует перезапуска СУБД. Правила пулера:
  `max_db_connections <= max_connections - superuser_reserved_connections
  - 30`; `min_pool_size = default_pool_size`; пример сбалансированной
  конфигурации (одна ТУЗ / одна БД): `max_client_conn=1000`,
  `pool_mode=transaction`, `min_pool_size=default_pool_size=
  max_db_connections=max_user_connections=200`.
- **Когда пулер НЕ рекомендуется** (документировано): ядро CPU пулера
  загружено > 70 %; pool_mode=session/statement; **OLTP > 1 000–10 000 TPS
  с операциями < 1–10 мс в transaction-режиме** (накладные расходы на
  сокет, рост sys_time); OLAP с большим трафиком. Через пулер отклик в
  среднем на ~5 % медленнее. Эффективность пулера — когда
  `max_db_connections` значительно меньше `max_client_conn`.
- HikariCP: если пул приложения меньше `max_connections` — подключаться
  напрямую; иначе HikariCP + Pooler, `max_client_conn` > суммы всех пулов
  (hosts × maximumPoolSize), тайм-аут подключения на клиенте выше, чем на
  пулере.
- Резервирование подключений для ролей (файл `pg_quota.conf` в каждой
  БД) — гарантированный доступ служебных УЗ при исчерпании пула
  (в ванильном PostgreSQL резерв только для суперпользователя).
- **64-битные XID** — снимают проблему wraparound для систем с десятками
  тысяч TPS.
- Управление планами: фиксация и подмена планов на стороне сервера без
  изменения текста запроса в приложении (**pg_hint_plan**, **pg_dbms_stats**,
  **pg_store_plans**) — для стабилизации SLA критичных запросов после
  миграции.
- Диагностика: pg_profile (анализ исторической нагрузки), psql_diagpack,
  Performance Insights; борьба с раздуванием таблиц: autovacuum +
  pg_repack / pg_squeeze / pgcompacttable; причины bloat — скачки
  UPDATE/DELETE, долгие транзакции, незавершённые prepared-транзакции,
  **зависшие слоты репликации** (актуально для CDC-контура).
- Прочие расширения, релевантные замене механизмов Oracle: **pg_cron**
  (планировщик заданий), **pg_background** (фоновое выполнение команд),
  **pg_variables**, **pgq/pgq_coop/pgqd** (очереди сообщений: монопольные
  и кооперативные очереди, менеджер очередей), **http/pgsql_http**
  (HTTP-клиент на уровне СУБД), **TimescaleDB** (time-series, адаптирован
  к механизмам безопасности Pangolin), **external_authorize** (LDAP),
  **pg_anon** (обфускация/анонимизация данных).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Уральский Объединённый Банк» (вымышленный, топ-20 по активам)
эксплуатирует АС «Реестр гарантий и аккредитивов» (АС РГА) — систему
учёта и сопровождения документарных операций: банковские гарантии
(включая гарантии по 44-ФЗ/223-ФЗ с обязательной регистрацией в едином
реестре), аккредитивы, обязательства по внешнеторговым контрактам.
Система работает в режиме **24/7** (интеграции с торговыми площадками,
банками-корреспондентами в других часовых поясах, ночные сверки
реестров); недоступность более 15 минут фиксируется как инцидент с
регуляторными последствиями.

Программа импортозамещения предписывает вывод Oracle из контура до конца
2027 года. Целевая СУБД утверждена: **Platform V Pangolin DB**.
Миграция признана проектом повышенного риска: объём БД **12 ТБ**,
бизнес требует непрерывности приёма операций и гарантированной
обратимости.

### 2.2 Ландшафт AS-IS

- СУБД-источник: **Oracle Database 19c Enterprise Edition**, RAC из
  2 узлов в ЦОД-1, Data Guard (async) в ЦОД-2. Включены опции:
  **TDE** (Oracle Wallet), Advanced Compression (холодные партиции),
  Partitioning.
- Объём БД: **12 ТБ** (данные ~7 ТБ, индексы ~5 ТБ), рост **~1,8 ТБ/год**;
  срок хранения операций онлайн — **7 лет** (документарный контур).
- Документы: ~1,5 ТБ сканов и вложений хранятся как **BFILE** (файловое
  хранилище ЦОД-1, ссылки в БД); внутри БД LOB-ов немного (~200 ГБ BLOB).
- Процедурный код: **~120 тыс. строк PL/SQL**: ~900 пакетов, ~2 400
  процедур и функций, 180 триггеров; активно используются переменные
  уровня пакета (сессионный контекст журналирования).
- Проприетарные механизмы Oracle в промышленном использовании:
  - автономные транзакции (`PRAGMA AUTONOMOUS_TRANSACTION`) — журналирование
    ошибок и аудит, ~35 мест;
  - `DBMS_SCHEDULER` — 45 регламентных заданий (ночные сверки, расчёт
    комиссий, архивация);
  - `DBMS_AQ` — 6 очередей уведомлений площадкам и внутренним системам;
  - `UTL_HTTP` — 3 интеграции (внешний реестр гарантий, сервис
    банков-корреспондентов, антифрод-вызов);
  - `DBMS_LOCK` — 2 критических места (взаимное исключение регламентов);
  - `DBMS_STATS` — регламентный сбор статистики;
  - глобальные временные таблицы (GTT) — 40 штук в отчётных процедурах;
  - INTERVAL-партиционирование — 12 крупнейших таблиц (операции, журналы
    аудита, статусы документов); регламент архивации использует
    `ALTER TABLE ... EXCHANGE PARTITION`; `ENABLE ROW MOVEMENT` включён;
  - представления с `ROWNUM`-пагинацией и `CONNECT BY` — в справочных
    подсистемах (объём небольшой).
- Приложение: Java 17 / Spring Boot, **48 подов** в Kubernetes,
  HikariCP **25 соединений на под** (текущая настройка) ⇒ до **1 200**
  одновременных соединений, в пиках наблюдалось **1 400** (ручное
  увеличение пулов на инциденты).
- Отчётность: 25–35 тяжёлых аналитических запросов в день исполняются на
  реплике Active Data Guard.
- Нагрузка: пик **8 500 транзакций/с** (короткие OLTP-транзакции,
  65 % чтение / 35 % запись, медианная длительность транзакции ~3 мс),
  ночной пакет загрузки реестров — **до 30 млн строк за 3 часа**.
- Оба ЦОД живут в модели приложения active/standby (Kubernetes в обоих
  ЦОД).

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |

| NFR-01 | Доступность АС РГА (24/7) в период миграции и после | ≥ 99,95 % в год |
| NFR-02 | RPO целевого контура при отказе узла внутри ЦОД | **0** |
| NFR-03 | RTO целевого контура при отказе узла (автоматическое переключение) | ≤ 3 мин |
| NFR-04 | RPO при полной потере ЦОД-1 | ≤ 60 с |
| NFR-05 | RTO при полной потере ЦОД-1 (допускается ручное решение) | ≤ 60 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД | ≤ 20 мс при 8 500 TPS |
| NFR-07 | **Непрерывность миграции**: остановки приёма операций нет; прерывание записи на cutover | ≤ 15 мин (INF-08) |
| NFR-08 | **Полнота переноса**: расхождения данных Oracle ↔ Pangolin на момент cutover | 0 по бизнес-ключам и контрольным суммам |
| NFR-09 | **Обратимость**: окно отката на Oracle после cutover без потери операций, принятых в Pangolin; время возврата | окно ≥ 30 дней; возврат ≤ 60 мин |
| NFR-10 | Ночной пакет загрузки реестров на целевом контуре | ≤ 3 ч, без блокировки OLTP |
| NFR-11 | Ёмкость целевого контура | 7 лет хранения при росте 1,8 ТБ/год + 30 % запас |
| NFR-12 | PITR на целевом контуре | глубина 35 дней; восстановление полной БД ≤ 8 ч |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные АС РГА (ПДн + банковская тайна) шифруются «на диске» на целевом контуре; ключи — во внешнем хранилище секретов банка (INF-03). TDE целевого контура включается **до начала** перелива продуктивных данных |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен иметь возможность прочитать содержимое защищаемых таблиц |
| SEC-03 | Разделение обязанностей: включение TDE, изменение состава расширений, выдача доступа к защищаемым объектам — с участием администратора ИБ |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной и миграционный доступ — ТУЗ с минимальными правами |
| SEC-05 | Аудит событий безопасности по ГОСТ Р 59548-2022 с выгрузкой в SIEM; маскирование параметров запросов в журналах |
| SEC-06 | TLS для всех соединений миграционного и целевого контуров (клиенты, репликация, CDC-канал, FDW-мосты); сертификаты из корпоративного УЦ |
| SEC-07 | Данные в миграционном контуре (стенды, промежуточные выгрузки, CDC-трафик) защищены не слабее продуктивных; тестовые стенды — только с обфусцированными данными (INF-06) |
| SEC-08 | Используемая редакция Pangolin должна покрывать все задействованные функции; выбор редакции обосновать |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одну рекомендуемую стратегию** плюс
  1–2 отвергнутые альтернативы с причинами.
- Комитет особенно чувствителен к трём вопросам: (a) как обеспечивается
  непрерывный перенос изменений Oracle → Pangolin при включённом TDE на
  приёмнике; (b) как устроен обратный канал на окно отката и где точка
  невозврата; (c) сколько PL/SQL-кода будет перенесено автоматически, а
  сколько потребует ручной переработки — с оценкой в человеко-месяцах
  (допустимо в диапазонах, с методикой оценки).
- Решение должно быть реализуемо силами INF-07; любой внешний продукт
  (включая CDC) требует закупки и согласования — это время и риск,
  которые нужно явно показать в плане.
- Допускается изменение настроек приложения (строки подключения, пулы,
  маршрутизация чтения) без смены архитектуры приложения.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Pangolin на момент миграции — 8.2.0 или новее; базовую мажорную
  версию PostgreSQL решающий не знает из контекста и должен либо не
  использовать, либо пометить как допущение.
- Бюджет на закупку редакции Enterprise и одного внешнего продукта
  (например, CDC) при обосновании имеется; срок согласования закупки —
  до 4 месяцев, это нужно учесть в этапности.
- Oracle Instant Client для миграционного инструментария уже есть в
  дистрибутиве (§1.2) и может быть установлен на выделенный миграционный
  сервер.
- Производительность CDC-захвата GraDeLy на стороне Oracle, поддержка им
  Oracle RAC/TDE-источника и направление Pangolin → Oracle **в контексте
  не подтверждены** — помечать как `[ТРЕБУЕТ ПРОВЕРКИ]` у вендора.
- Приложение в период параллельной эксплуатации может читать из обеих БД
  (маршрутизация чтения по доменам — допустимая доработка).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| CDC | Change Data Capture — захват и доставка изменений данных |
| Cutover | момент переключения записи прикладной системы с источника на целевую СУБД |
| Reverse-replication | обратный канал синхронизации Pangolin → Oracle на окно отката |
| DCS | Distributed Configuration Store — хранилище состояния кластера для оркестратора (Pangolin DCS на Raft) |
| Switchover / Failover / Promote | плановое / аварийное переключение лидера / повышение standby-кластера |
| TDE | прозрачное шифрование данных на уровне хранения |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| PAM | privileged access management |
| GTT | глобальные временные таблицы Oracle |
| FDW | foreign data wrapper — обёртка сторонних данных |
| Strangler pattern | поэтапный перенос доменов с коэкзистенцией старой и новой систем |
| Expand-migrate-contract | этапность изменения схемы: расширение → перенос → сжатие |
