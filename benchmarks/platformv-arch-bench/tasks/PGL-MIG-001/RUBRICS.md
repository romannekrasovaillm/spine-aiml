# Рубрики оценки для задачи PGL-MIG-001

## 1. Общие правила для судей

1. **Порядок:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить HF §2;
   (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из ответа;
   (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Pangolin,
   которого нет в §1 и которое не помечено решающим как допущение,
   считается **непроверенным**; если оно ещё и ложно — **ложным**.
   Не «додумывать» за решающего.
3. **«Упомянул ≠ применил»** — балл за решение, привязанное к требованию
   (NFR/SEC/INF) и обоснованное, а не за ключевое слово. Название
   инструмента без учёта его документированных ограничений (редакция,
   источник, TDE, рестарты) — не решение.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 — образцово, с
   учётом компромиссов и ловушек §4.
5. **Цитирование:** 1–3 цитаты (≤ 25 слов) на критерий + чего не хватает до
   следующего уровня.
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`). Стиль и
   объём сверх C10 не оцениваются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
оцениваются для диагностики. «Только судья» = regex-детектор ненадёжен.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | `pgloader` предложен как инструмент миграции **с Oracle** (схема или данные), подано как факт/решение. В документации источники pgloader — только MS SQL Server / MySQL / SQLite | A-05, A-08; CONTEXT §1.2; механический regex — кандидат, знак утверждения проверяет судья |
| HF-02 | `pgcopydb` предложен как канал миграции/CDC **с источника Oracle**, либо `pgcopydb follow` — при включённом TDE на приёмнике без явной оговорки о документированной несовместимости — подано как рабочее решение | A-05, A-08; CONTEXT §1.2; SEC-01 требует TDE до перелива |
| HF-03 | Вымышленные компоненты/функции поданы как факт: «Pangolin нативно исполняет PL/SQL», «встроенный CDC-коннектор Oracle → Pangolin в составе Pangolin», «wal2json читает журналы Oracle», «Pangolin GoldenGate», вымышленные пакеты/утилиты | A-05, ловушки §4; механический regex — частично |
| HF-04 | Стратегия «big bang»: полная перекладка 12 ТБ в квартальное окно 4 часа (или аналогичное) **без** предварительной загрузки и CDC-досинхронизации — при действующем NFR-07 | Только судья: оценка плана целиком; ориентир — 12 ТБ за 4 ч = ≥ 0,83 ГБ/с только на копирование, без индексов/сверки, что при NFR-07 несостоятельно и должно быть разобрано |
| HF-05 | Заявлен RPO = 0 на DR-контуре (между ЦОД) или на CDC-канале при асинхронной репликации без оговорок; либо предложен **автоматический** promote standby-кластера при двух ЦОД без разбора документированного ограничения (DC2 не отличает сбой DC1 от разделения; promote — ручной, со STONITH) | A-06; CONTEXT §1.4, §1.8 |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01 (механические паттерны) |

## 3. Критерии

### C1. Фактическая корректность по Pangolin (вес 12)

**Что оценивается:** соответствие утверждений о продукте CONTEXT.md §1;
корректные наименования и версии инструментов; отделение фактов от
допущений; честная маркировка пробелов (`[ТРЕБУЕТ ПРОВЕРКИ]`).

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02/HF-03, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности (версии инструментов, редакционные границы, «установлен по умолчанию» для ora2pg и т.п.), не разрушающие план; допущения помечены частично |
| 4 | Все утверждения верны; всё за пределами §1 помечено допущением или подтверждено ссылкой с разрешённых доменов; корректно различаются: ora2pg (в `migration_tools`, не установлен по умолчанию) vs pgloader (по умолчанию, но не Oracle) vs pgcopydb (только PostgreSQL); Enterprise-функции отделены от общих; неподтверждённые параметры GraDeLy (производительность захвата, поддержка Oracle RAC/TDE, направление Pangolin → Oracle) честно помечены как вопросы к вендору |

**Признаки сильного ответа:** официальные имена и версии (ora2pg 23.0,
orafce 4.4.0, oracle_fdw 2.5.0, pgloader 3.6.9, pgcopydb 0.14, GraDeLy
GDL 3.0.0, wal2json, test_decoding); позиция вендора «выбор инструмента —
зона ответственности продуктовой команды» учтена в рисках; базовая версия
PostgreSQL не заявлена как факт.

**Типичные ошибки:** «ora2pg входит в стандартную установку»; «pgloader
перенесёт с Oracle»; «pgcopydb даст CDC из Oracle»; «orafce покрывает весь
PL/SQL»; выдуманные версии и флаги.

**Что оценивается:** D2 + D3. Полнота инвентаризации AS-IS, выбор
стратегии, этапы с критериями входа/выхода, увязка с ограничениями
(INF-07, INF-08, сроки, закупка CDC).

| Уровень | Якорь |
|---|---|
| 0 | Нет стратегии или HF-04 |
| 2 | Этапы «оценка → конвертация → тест → переключение» названы, но без критериев выхода; инвентаризация неполна (забыты BFILE, GTT, автономные транзакции, регламенты); срок закупки внешнего CDC (ASSUME: до 4 месяцев) не учтён в плане |
| 4 | Полная инвентаризация с количественной оценкой (900 пакетов, 120 тыс. строк, 45 заданий, 6 очередей, 35 мест автономных транзакций, 12 interval-таблиц, 1,5 ТБ BFILE); стратегия поэтапная (например, expand-migrate-contract / волны по доменам) с критериями входа-выхода и контрольными точками; пилот на копии до CDC; этапность учитывает закупку CDC-продукта, обучение команды (INF-07), квартальные окна (INF-08); явно зафиксировано, почему big-bang отклонён (расчёт, а не лозунг) |

**Ловушки:** стратегия «перельём всё за квартальное окно»; пилот без
критериев; игнорирование BFILE-контента (файлы вне БД).

### C3. Конвертация схемы и кода (вес 14)

**Что оценивается:** D4. Таблица соответствия механизмов Oracle средствам
Pangolin/переработке, оценка ручной доработки.

| Уровень | Якорь |
|---|---|
| 0 | Нет таблицы соответствия; заявлена нативная совместимость с PL/SQL (HF-03) |
| 2 | Названы ora2pg и orafce; 2–4 механизма сопоставлены; оценки ручной доработки нет; особенности портирования (пакеты, переменные пакета, автономные транзакции) не разобраны |
| 4 | Таблица соответствия по всем механизмам AS-IS: DBMS_SCHEDULER → pg_cron (или внешний оркестратор — выбор обоснован); DBMS_AQ → pgq/pgq_coop/pgqd; UTL_HTTP → http/pgsql_http (с оговоркой ИБ про исходящие вызовы); DBMS_LOCK → pg_dbms_lock; DBMS_STATS → pg_dbms_stats; BFILE → psql_bfile (с учётом, что защита таблиц не распространяется на внешние объекты, и планом переноса 1,5 ТБ файлов); пакеты → схемы, переменные пакета → временные таблицы; автономные транзакции — честно: прямого аналога в перечне нет ⇒ `[ТРЕБУЕТ ПРОВЕРКИ]` у вендора + дизайн-переработка ~35 мест; типы (varchar2→varchar/text, number→numeric), variable_conflict=use_column, курсоры/REVERSE-циклы; INTERVAL → AUTO PARTITION BY RANGE (Enterprise), с учётом «схему автопартиционирования потом не изменить»; EXCHANGE PARTITION → DETACH+RENAME+ATTACH в одной транзакции; GTT → временные таблицы с учётом пулинга; оценка доли автоконвертации и ручной доработки с методикой (пилот на выборке пакетов → экстраполяция) |

**Ловушки:** «ora2pg перенесёт код без правок»; «pg_pathman»; игнор
ограничения неизменяемости схемы автопартиционирования; GTT без учёта
транзакционного пулинга.

### C4. Канал данных: начальная загрузка и CDC (вес 14)

**Что оценивается:** D5. Выбор инструментов перелива и досинхронизации,
учёт их ограничений, расчёты окон и пропускной способности, стык CDC с
TDE (SEC-01).

| Уровень | Якорь |
|---|---|
| 0 | HF-01/HF-02, либо канал данных отсутствует как конструкция |
| 2 | ora2pg для снапшота + «какой-то CDC» названы, но: производительность и поддержка GraDeLy приняты на веру без пометки `[ТРЕБУЕТ ПРОВЕРКИ]`; расчёта пропускной способности нет; вопрос TDE-на-приёмнике × CDC не разобран; план Б при недоступности CDC отсутствует |
| 4 | Начальная загрузка — ora2pg (схема+данные) с учётом документированных рекомендаций (загрузка в неиндексированную структуру, минимум ограничений на время загрузки, индексы — после); расчёт: 7 ТБ данных при реалистичной скорости COPY-перелива ⇒ часы/сутки, укладывается вне окна INF-08; CDC — внешний захват журнала Oracle (Platform V GraDeLy) с явной пометкой неподтверждённых характеристик как вопросов к вендору (ASSUME §2.7); обосновано, почему НЕ pgloader (нет Oracle в источниках) и НЕ pgcopydb (источник — только PostgreSQL; follow несовместим с TDE, требует superuser на приёмнике, падает при рестартах); расчёт CDC-трафика из нагрузки (8 500 TPS × 35 % записи ⇒ порядок величины WAL/с) и увязка с каналом; стык SEC-01: TDE включается до перелива, инструментальный конфликт разобран; предусмотрено включение `wal_level='logical'` на приёмнике с плановым рестартом (для исходящих каналов) до cutover; план Б: FDW-мосты / повторная дельта-выгрузка с окном |

**Ловушки:** pgloader для Oracle (HF-01); pgcopydb с Oracle/при TDE
(HF-02); «CDC не требует оценки пропускной способности»; TDE «потом
включим» вопреки SEC-01.

**Что оценивается:** D7, NFR-07, NFR-09.

| Уровень | Якорь |
|---|---|
| 0 | Нет раздела; откат «восстановим из бэкапа» без оценки потерь |

| 4 | Чек-лист cutover с evidence на каждый шаг: остановка записи в Oracle (очередь интеграционного слоя, INF-08), доводка CDC-хвоста до нулевого лага, финальная сверка (NFR-08), переключение строк подключения/пулов (48 × 25), прикладные смоук-тесты, решение «go»; оценка укладывания в ≤ 15 мин прерывания записи; обратный канал на окно отката ≥ 30 дней: исходящий CDC из Pangolin (wal2json, `wal_level='logical'`) → конвейер в Oracle, при этом направление Pangolin → Oracle и совместимость GraDeLy честно помечены `[ТРЕБУЕТ ПРОВЕРКИ]` у вендора, либо предложен альтернативный механизм с обоснованием; точка невозврата (закрытие окна, отключение обратного канала) определена с владельцем и критериями стабилизации; возврат ≤ 60 мин (NFR-09) — ручная операция по чек-листу; REPLICA IDENTITY для UPDATE/DELETE учтён; разобрано, что происходит с данными, принятыми в Pangolin, при откате (0 потерь — через обратный канал, а не «заново введём») |

**Ловушки:** «обратная репликация штатна и тривиальна»; откат через
pg_dump 12 ТБ; окно отката без даты закрытия; «RPO=0 между СУБД при
асинхронном CDC» (HF-05).

```json
{
  "rubric_id": "PGL-MIG-001-RUB",
  "task_id": "PGL-MIG-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",

```

Правила: `total` по формуле из frontmatter; `excellent` при `total ≥ 85`,
`pass` при `≥ 70`, иначе `fail`; при любом `hard_fails[].triggered = true`
— `fail`.
