### 1.1 Методология комплаенс-маппинга: позиция карты

- **Штатные функции продукта закрывают технические меры** (шифрование,
  разграничение доступа, аудит, резервирование); **схема БД, процессы ДИТ и
  DR-учения остаются на уровень решения** — продукт их не выполняет и не
  гарантирует. Правило использования карты: **не декларировать
  соответствие — только механизмы**. Гипотезы помечены conditional
  `[ТРЕБУЕТ ПРОВЕРКИ]` и обязательств не создают.

### 1.3 Pangolin DB (PSQ 8.2.0) — система записи / OLTP: комплаенс-функции

Закрывается штатно:

- **Хранение (719-П прил. 1 № 10, п. 2.2):** TDE (**только редакция
  Enterprise**, с версии 4.1.0) шифрует данные и индексы на диске; аудит
  событий безопасности по **ГОСТ Р 59548-2022** — **все редакции** (с 3.2.0).
- **Доступ (719-П прил. 1 № 1):** RBAC; внешняя авторизация **LDAP —
  редакция Enterprise**; сквозная аутентификация Pooler ↔ СУБД — **все
  редакции**; двухфакторная аутентификация (с версии 5.2.0).
- **Резервирование (719-П прил. 1 № 11):** HA-кластер Pangolin Manager
  (Patroni 4.1.1) + DCS (Raft-кворум): целевые RPO = 0, RTO < 6 мин/год;
  standby-кластер для DR на 2 ЦОД; N-ЦОД-политика пулера — fail-closed
  защита от записи «не в тот» ЦОД.
- **Защита обмена (719-П прил. 1 № 3/4):** PKCS#12 + SecMan в пулере,
  Kerberos/SASL в логической репликации; интеграция с HashiCorp Vault —
  редакция Enterprise.

Остаётся решению (§1.8): классификация данных; append-only-дисциплина
схемы; фактические RTO/RPO доказываются DR-учениями, а не паспортом
продукта. **Редакционная зависимость** (не гипотеза, а зависимость
лицензии): без Enterprise меры TDE, LDAP, глобальные индексы недоступны.

Источник: `banking/compliance/platformv-reg-map.md`

### 1.4 Radish (RDH 2.2.0) — in-memory KV (кэш/сессии)

- Key-value СУБД в памяти **на ядре Valkey** (форк Redis). Гипотеза «Radish
  = MPP-профиль линейки» **опровергнута документацией**: аналитический
  профиль линейки — DataMarts и OLAP Analytics, распределённая
  транзакционная — Ocean DB.
- **Доступ (прил. 1 № 1):** согласованная ACL-модель для всех режимов,
  интеграция с SecMan. **Резервирование (прил. 1 № 11):** кластер (16384 hash-слотов,
  минимум 3 primary + 3 реплики) или Sentinel (минимум 3 экземпляра);
  persistence RDB/AOF (дефолт `appendonly yes`).
- **Ограничение продукта:** Radish — **не система записи** критичных данных:
  репликация асинхронна, `WAIT` не даёт сильной консистентности, Sentinel
  не гарантирует подтверждённые записи. Для защищаемой информации (719-П
  п. 2.2) Radish применим только как кэш поверх Pangolin — хранение
  остаётся на Pangolin. Выбор Radish vs SessionsData (SUS) — ADR.

Источники: `banking/compliance/platformv-reg-map.md`,
`banking/notes/platformv-map-20260902.md`

### 1.5 DataMarts (DMS 2.4.0) — OLAP / витрины (ClickHouse)

- Аналитическая СУБД на базе open source ClickHouse; **не OLTP**: запись
  пакетными INSERT + фоновые мутации. Система записи остаётся на Pangolin;
  отчётность надзору (719-П гл. 7) проектируется как витрины решения.
- Компоненты: `datamarts-server`, `datamarts-keeper` (Raft-кворум, минимум
  3 узла), `datamarts-safeguard`, `datamarts-rrm`, `datamarts-vault-provider`.
- **Хранение (719-П прил. 1 № 10):** версионные таблицы (история строк,
  состояние на любой момент) + аудит (`query_log`/`session_log`,
  `datamarts-audit.log` через rsyslog). Движок версионных таблиц не назван
  `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **Доступ (719-П прил. 1 № 1):** RBAC + datamarts-rrm (роли, политики
  строк, профили настроек, квоты); safeguard: профили `READONLY` и правила
  токсичности против ad-hoc запросов.
- **Защита обмена (719-П прил. 1 № 3/4):** Kerberos (GSSAPI) и SASL для
  Kafka, TLS, **OCSP**, SecMan для секретов.
- **Резервирование (719-П прил. 1 № 11):** ReplicatedMergeTree, доступность
  99.99% при ≥ 3 репликах сегмента + keeper (Raft, минимум 3 узла).
- Загрузка: табличный движок Kafka (SASL/Kerberos), named collections к
  Pangolin, материализованные представления. Пробелы `[ТРЕБУЕТ ПРОВЕРКИ]`:
  партиционирование/TTL, движок Distributed, версия ядра ClickHouse,
  резервное копирование. Прямого CDC в DataMarts в публичных доках нет;
  штатный входной паттерн — внешний CDC (GraDeLy/GDL) в Kafka → движок
  Kafka.

Источники: `banking/compliance/platformv-reg-map.md`,
`banking/notes/platformv-map-20260902.md`

### 1.6 Synapse (AM 2.5.0 / SEI 6.8.0 / SCT 6.7.0 / SNX 4.3.0) — интеграционный слой

- **Доступ и межсервисная аутентификация (719-П прил. 1 № 1, № 4):**
  ролевая модель разграничения доступа, аутентификация/авторизация
  межсервисных взаимодействий; KACM — интеграция с PKI потребителя,
  авто-выпуск и ротация x509.
- **Защита обмена (719-П прил. 1 № 3):** SCT (защищённая отправка/приём
  сообщений с аудитом и ролевой моделью), SWA SOWA (API Security Gateway),
  SynGX SNX (промышленный proxy на Nginx).
- **Резервирование (719-П прил. 1 № 11):** GEOH Geohealthcheck
  (балансировка трафика между ЦОД); горизонтальное масштабирование
  (K8s/OpenShift). **Аудит (прил. 1 № 10, частично):** SYAL (логи), GATM
  (метрики).
- **Остаётся решению:** политики доступа и маршрутизации; шина не
  классифицирует трафик и не решает, где ГОСТ-криптоканал (GAP-C2 —
  открытая СКЗИ-линия). SynGX: TLS ≥1.2, Vault/SecMan; **WAF в
  документации 4.3.0 отсутствует** — API-security закрывает SWA SOWA;
  межинстансовая HA-кластеризация не описана `[ТРЕБУЕТ ПРОВЕРКИ]`.

Источники: `banking/compliance/platformv-reg-map.md`,
`banking/notes/platformv-map-20260902.md`

### 1.7 Corax (KFK 16.392.0) — событийная платформа

- Ядро Apache Kafka (точная версия `[ТРЕБУЕТ ПРОВЕРКИ]`): брокеры +
  ZooKeeper (ансамбль ≥ 3 узла, только нечётный состав) или KRaft;
  опциональные Schema Registry / Corax UI / Mirror Maker 2. Доступность
  99,9% при RF≥3 + min.insync.replicas≥2. **Records Policy — брокер-сайд
  валидация, только в Corax, не в Apache Kafka**.
- Безопасность: TLS 1.2/1.3 + mTLS, Kerberos, ACL + CoraxAuthorizer, аудит
  (`kafka-audit.log`), e2e-шифрование, SecMan. Паттерн (рекомендация
  дистиллята): outbox из Pangolin по CDC wal2json → Corax → DataMarts.
  Риск: **дефолтный пароль инсталлятора `qwe123` опубликован в
  документации** — смена обязательна.

Источник: `banking/notes/platformv-map-20260902.md`

### 1.8 Единый список «остаётся на уровень решения» и гипотезы карты

Остаётся на уровень решения (единый список карты):

1. **Классификация защищаемой информации** (719-П п. 2.2; 683-П п. 1).
2. **Схема БД и append-only дисциплина** (719-П прил. 1 № 10 «неизменный
   вид», retention 5 лет).
3. **Ежегодный pentest / анализ уязвимостей** (851-П пп. 3.2; 683-П п. 2;
   719-П п. 1.1) — процесс, продукт не проводит.
4. **Оценка соответствия** по ГОСТ Р 57580.2 (уровень ≥ 4, не реже раза в
   2 года — 719-П п. 2.4; 851-П п. 13; 683-П п. 9) — проверяющая организация.
5. **Сертификация ПО** (719-П п. 2.5, ФСТЭК-131; 851-П пп. 4.1 ОУД 4;
   683-П п. 4.1) — вопрос вендора/сертификации.
6. **Уровень защиты по ГОСТ Р 57580.1** (усиленный/стандартный — 851-П пп.
   3.1) — определяется статусом банка, не продуктом.
7. **DR-учения и фактические RTO/RPO** (719-П прил. 1 № 11) — runbook,
   периодичность, владелец.

Гипотезы (conditional, обязательств не создают):

- **ГОСТ-СКЗИ каналов** (851-П п. 6 — СКЗИ по приказу ФСБ № 378):
  закрывается ли штатным TLS/Kerberos продуктов Platform V или требуется
  ГОСТ-TLS-прокси (GAP-C2) — `[ТРЕБУЕТ ПРОВЕРКИ]`.
- **Редакция Pangolin Enterprise** как условие TDE/LDAP/глобальных
  индексов — не гипотеза, а зависимость лицензии (см. §1.3).
- **Прямой CDC в DataMarts** — `[ТРЕБУЕТ ПРОВЕРКИ]` (см. §1.5).

### 1.9 Карта 719-П (платёжный контур)

- Реквизиты: Положение Банка России от 04.06.2020 № 719-П, регистрация
  Минюст 23.09.2020 № 59991; правовая база — ч. 3 ст. 27 161-ФЗ; субъект
  задачи — ОПДС (банк). **Акт не отменён (проверено 2026-08-31).**
- **п. 2.1:** отсылает к 683-П как обязательному для ОПДС. **Открытый
  вопрос:** 683-П утратил силу (заменён 851-П), а fetched-редакция 719-П
  всё ещё ссылается на 683-П; наличие поправки, обновляющей ссылку на
  851-П, — `[ТРЕБУЕТ ПРОВЕРКИ]`. Для антифрод-маппинга использовать 851-П.
- **п. 2.2 (расширенный состав защищаемой информации):** состав 683-П +
  остатки денежных средств на счетах клиентов, остатки электронных
  денежных средств, конфигурация, определяющая параметры работы объектов
  информационной инфраструктуры и технических средств защиты информации.
- **п. 2.3/2.4:** оценка соответствия — **не реже одного раза в два года**;
  уровень **не ниже четвёртого** по ГОСТ Р 57580.2-2018.
- **п. 2.5 (контринтуитивно):** сертификация прикладного ПО по приказу
  ФСТЭК № 131: **системно значимые КО и КО, значимые на рынке платёжных
  услуг — не ниже 4 уровня доверия**; остальные ОПДС — **не ниже 5
  уровня доверия**.
- **п. 2.6:** порядок информирования об инцидентах защиты информации;
  сведения об инцидентах — в ЦБ по запросу.
- **п. 2.7–2.10:** ограничения операций по заявлениям клиентов; техмеры
  интернет-канала (2FA, взаимная аутентификация, защита сообщений).
- **п. 2.12:** показатель переводов без согласия клиента — **≤ 0,005 %**
  ежеквартально.
- **Глава 7 (контроль ЦБ):** запросы документов, включая ПДн (7.1.2),
  проверки (7.1.3–7.2). Evidence-bundle проекта: реестр мер ГОСТ Р 57580.1,
  отчёты оценки по 57580.2 (уровень ≥ 4), отчёты pentest, сертификаты/ОУД
  ПО, документы о контроле третьих лиц, данные показателя 2.12, журналы.
- **Приложение 1 — 11 технологических мер.** Ключевые для ландшафта:
  № 1 (идентификация/аутентификация/авторизация), № 3 (защита электронных
  сообщений от искажения, фальсификации, ложной авторизации и др.), № 4
  (взаимная аутентификация участников обмена), № 10 (хранение защищаемой
  информации, событий регистрации и инцидентов **5 лет в неизменном
  виде**), № 11 (восстановление при разрушении/искажении). Меры № 2
  (2FA клиентов), № 5–6 (ЭП по 63-ФЗ), № 7–9 (подтверждение права, сверка,
  двойной контроль) — клиентский/прикладной контур, вне продуктов
  ландшафта.
- **п. 3 прил. 1 (компенсирующие меры):** при невозможности технической
  реализации отдельных мер (с учётом экономической целесообразности)
  субъекты «в рамках системы управления операционным риском» могут
  разрабатывать **иные (компенсирующие) меры** — нейтрализацию актуальных
  угроз.
- Граница контуров: 719-П/683-П (НПС/антифрод) и 187-ФЗ (КИИ) — разные
  нормативные ветки (683-П п. 10; у 851-П — п. 14).

### 1.11 Карта 851-П (действующий антифрод-акт)

- Реквизиты: Положение Банка России от 30.01.2025 № 851-П, регистрация
  Минюст 06.03.2025 № 81462; предшественник 683-П признан утратившим силу
  (п. 16).
- **Переходные сроки:** с 01.10.2025, с 01.01.2027, до 31.12.2026 (по

- **пп. 3.1 — уровни защиты по ГОСТ Р 57580.1-2017:** системно значимые и

- **пп. 3.2:** ежегодное тестирование на проникновение и анализ
  уязвимостей (наследует 683-П п. 2 и 719-П п. 1.1).
- **пп. 4.1:** прикладное ПО и ПО интернет-каналов — оценка по требованиям
  к оценочному уровню доверия **не ниже ОУД4** (ГОСТ Р ИСО/МЭК 15408-3)
  либо сертификация ФСТЭК.
- **пп. 5:** целостность электронных сообщений — усиленная ЭП (63-ФЗ) или
  СКЗИ с имитозащитой.
- **п. 6:** СКЗИ по 63-ФЗ/152-ФЗ/ПП 1119/ПКЗ-2005/приказу ФСБ № 378; СКЗИ
  российского производства — подтверждение ФСБ.
- **п. 13:** оценка соответствия по ГОСТ Р 57580.2-2018 проверяющими
  организациями — **не реже одного раза в два года**, отчёт ≥ 5 лет,
  уровень ≥ 4; расчёт показателя — по Указанию 6406-У (форма 0409071).
- **п. 14:** граница с 187-ФЗ (КИИ) сохранена. Правило использования:
  карта собрана по официальному скану ЦБ (OCR); дословные цитаты — после
  сверки по читаемой копии.

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк „Стрежень"» (вымышленный, топ-30 по активам) — ОПДС; по решению
ЦБ отнесён к кредитным организациям, **значимым на рынке платёжных услуг**
(не системно значимый, не филиал иностранного банка).

Программа импортозамещения переводит платёжный контур (процессинг платёжных
поручений, ДБО-бэкенд, обмен с внешними системами, надзорная отчётность) на
ландшафт из продуктов Platform V; ввод в пром — **IV квартал 2026**, полный
переход — до **01.01.2027** (переходные сроки 851-П). АК поручил ДКА
заключение: что ландшафт закрывает штатными функциями продуктов, что
остаётся решению/процессам, где пробелы и какие компенсирующие меры нужны.

### 2.2 Ландшафт AS-IS и целевой ландшафт TO-BE `[BENCH]`

AS-IS: платёжный хаб — Oracle Database 19c (RAC + Data Guard async в
ЦОД-2), IBM MQ, самописная ESB; ДБО-бэкенд — Java 17 / Spring Boot, сессии
в самописном Redis; надзорная отчётность — витрины на том же Oracle (ODS).

TO-BE (закуплено и разворачивается):

| Слой | Продукт Platform V | Роль в контуре |
|---|---|---|
| Система записи платёжного контура | **Pangolin DB 8.2.0, редакция Standard** (лицензия закуплена до решения по TDE) | учёт платёжных поручений, остатки, реестры |
| Кэш сессий ДБО | **Radish 2.2.0** | кэш сессий; план ИТ: хранить в Radish также токены авторизации и историю входов «для быстрого доступа» |
| Аналитика и надзорная отчётность | **DataMarts 2.4.0** | витрины отчётности ЦБ (гл. 7 719-П), история операций |
| Событийная платформа | **Corax 16.392.0** | событийная шина платёжного контура |
| CDC | **GraDeLy 3.0.0** | захват изменений из Pangolin → Corax |
| Интеграционный слой | **Synapse AM 2.5.0, SEI 6.8.0, SCT 6.7.0, SynGX 4.3.0** | шина, защищённый обмен, API-шлюз |
| Резервное копирование | **CopyWala 1.3.1** | РК СУБД Pangolin |
| ОС | **SberLinux OS Server 10.2.1.ai1** | все узлы контура |

Поток данных TO-BE: Pangolin (запись) → GraDeLy (CDC) → Corax →
DataMarts (витрины); ДБО ↔ Synapse (SCT/SynGX) ↔ Pangolin; сессии ДБО —
Radish.

### 2.7 Организационные ожидания `[BENCH]`

- АК ожидает **одно заключение** с однозначной классификацией каждого
  требования: «продукт / решение / процесс / пробел / компенсирующая мера».
- Особо чувствительные вопросы АК: (а) редакция Pangolin Standard против

  токенов и истории входов в Radish (SEC-06 против ограничений Radish);
  (в) закрытие ГОСТ-СКЗИ каналов (SEC-04 против открытой линии GAP-C2).
- Заключение — evidence-артефакт для запросов ЦБ (гл. 7 719-П): ссылки на
  пункты актов и продуктовые механизмы, без деклараций соответствия.

### 2.8 Что можно принять допущением `[ASSUME]`

- Версии продуктов на момент ввода — не ниже указанных в §2.2.
- Vault банка доступен из обоих ЦОД; SIEM и PAM покрывают все узлы контура.
- Клиентские каналы ДБО (мобильное приложение, интернет-банк) в scope
  задачи не входят — входит только серверный контур и его продукты.
- Уровни доверия и сертификаты конкретных продуктов Platform V — предмет
  запроса к вендору (в картах актов не раскрыты).
