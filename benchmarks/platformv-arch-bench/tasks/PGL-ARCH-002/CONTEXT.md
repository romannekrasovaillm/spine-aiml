## 1. Продукт: Platform V Pangolin DB `[DOC]`

### 1.1 Назначение, позиционирование, версии

- СУБД Pangolin (код PSQ, линейка Platform V, АО «СберТех») —
  реляционная СУБД, **специальная сборка PostgreSQL** с доработками под
  повышенные требования к безопасности, доступности, надёжности и
  удобству эксплуатации; в т.ч. для «построения кластеров высокой
  доступности, резервирования данных и снятия/восстановления резервных
  копий».
- Это **OLTP-СУБД, не MPP**: «полностью совместим с ACID и идеально
  подходит для OLTP-нагрузок… Для решения задач аналитики рекомендуется
  использовать специализированные продукты». Базовая модель — один
  ведущий узел на запись + физические реплики; чтение масштабируется
  репликами.
- Заявленное преимущество: «автоматическое переключение при сбое,
  полное резервирование с получением практически нулевого времени
  простоя».
- Регистрация в РРПО № 13436 от 29.04.2022. Поддержка версии 8.2:
  «выход патчей до выхода версии 11.1.0».
- Версия ядра: в релизе 8.1 «выполнен переход на версию **18.3** ядра
  СУБД PostgreSQL». Версии компонентов 8.2.0: `pangolin-manager`
  **4.2.0** («основан на Patroni версии **4.1.1**»), `pangolin-pooler`
  **3.2.0**. В релизе 8.1 «интегрирована утилита **CopyWala** версии
  1.2.3» и «выполнен полный переход на использование утилиты **Pangolin
  Installer** для процессов автоматизации СУБД». Новое в 8.2.0, в т.ч.:
  механизм Shared Pool (переиспользование планов запросов между
  сессиями), поддержка SberLinux OS Server 10.
- Поддерживаемые ОС: РЕД ОС 7.3/8, Альт СП 10 версия 2, Альт Сервер 10,
  Platform V SberLinux OS Server 9/10, Astra Linux SE 1.8. Архитектуры:
  x86-64, ARM64.

### 1.3 Кластер высокой доступности: состав и механика

- Кластер высокой доступности — «группа из двух и более серверов с
  экземплярами одной БД, взаимодействующими по протоколу **потоковой
  физической репликации**». Компоненты: **Pangolin Manager**
  (оркестратор), **Pangolin DCS** (распределённое хранилище
  конфигурации), **Pangolin Pooler**.
- Заявленные целевые показатели для mission critical: «отсутствие потери
  данных в случае программного или аппаратного сбоя (**RPO = 0**); время
  простоя сервиса в случае сбоя менее 6 минут в год (**RTO = 6**)».
  Достигается: горячее резервирование двух экземпляров БД в разных ЦОД
  (Active и StandBy), автоматический failover средствами Manager, пулы
  соединений через Pooler. **Примечание составителей:** сопоставляйте это
  заявление с правилом двух ЦОД из §1.7 (при двух ЦОД автоматическое
  повышение невозможно) — согласование этих положений для конкретной
  топологии является частью задачи.
- Репликация однопоточная: «в кластере всегда есть один ведущий узел
  (лидер), а все остальные узлы имеют статус реплики».
- Выборы лидера: Manager хранит запись о лидере в DCS (пара
  ключ-значение с TTL). При отсутствии/истечении записи каждый Manager
  проверяет доступность лидера и узлов; узлы сравнивают позиции журнала
  транзакций; «узел, который первым успешно выполнит запись [в DCS],
  становится новым лидером кластера».
- Управление: CLI `pangolin-manager-ctl` и REST API. REST API используют:
  внутренние компоненты кластера (выборы, failover); **балансировщики
  нагрузки (к примеру, HAProxy) для проверок работоспособности**;
  мониторинг; внешние скрипты.
- Команды: `list` (роли Leader / Sync Standby / Replica, LSN, lag),
  `pause`/`resume` (режим обслуживания), `reload`, `restart`,
  `switchover`, `failover`, `reinit`, `edit-config`.
- **switchover**: плановое переключение; «гарантирует, что все
  завершённые на лидере транзакции будут применены на всех подключённых
  к нему репликах и потеря данных будет нулевой, **даже в асинхронном
  режиме репликации**».
- **failover**: обычно автоматически при потере лидера; ручной — когда
  лидер потерян при существенно отстающих асинхронных репликах; в строгом
  синхронном режиме потеряны лидер и синхронная реплика одновременно;
  лидер нестабилен. Прежний лидер откатывается (pg_rewind) или обновляется
  копией нового лидера и возвращается репликой.
- **reinit**: пересоздание реплики через `pg_basebackup` с лидера или
  узла с меткой `clonefrom`.
- При активном Manager управлять экземплярами как одиночными
  (`pg_ctl`, `systemctl … postgresql`) — только в режиме `pause`, иначе
  кластер воспримет действия как сбой.
- Среди документированных инструкций по восстановлению есть
  «**Пересоздание узла арбитра**» и «Пересоздание узла реплики» (из
  дистрибутива или средствами автоинсталляции).

### 1.4 Pangolin DCS и Raft

- Pangolin Manager работает с двумя типами хранилищ конфигурации:
  **etcd** и **Pangolin DCS** (часть компонента Pangolin Manager; пакет
  `pangolin-manager-dcs`).
- «Pangolin Manager использует распределённое хранилище конфигураций
  Pangolin DCS на базе **Raft** алгоритма для хранения информации о
  состоянии кластера, реализации механизма **кворума** и обеспечения
  идентичности значений параметров на всех узлах кластера».
- Raft: мастер выбирается большинством голосов; запись считается успешной
  после подтверждения **большинством узлов**. Следствие: кластер из N
  узлов переживает отказ не более ⌊(N−1)/2⌋ узлов; чётное число узлов не
  добавляет отказоустойчивости.
- Параметры DCS в `postgres.yml` (секция `pangolin_dcs`): `self_addr`,
  `partner_addrs`, `data_dir` (журнал Raft), `dump_dir`/`dump_interval`
  (по умолчанию 300 с), `heartbeat_interval` (мс; как часто мастер
  DCS-кластера сообщает о себе), `election_timeout` (мс; тайм-аут до
  нового голосования при отсутствии heartbeat), TLS-параметры
  (`certfile/keyfile/cafile/crlfile`, `verify_client`, `verify_server`,
  `no_tls1_3`). В примерах документации: `heartbeat_interval: 1000`,
  `election_timeout: 5000`; адреса Raft `<host>:2481`, REST DCS
  `<host>:8009`.
- Управление DCS: утилита `pangolin-dcs-ctl` (в примерах — `member list`,
  `endpoint status`, `endpoint health` по списку эндпоинтов); в разделе
  администрирования заявлены команды аутентификации/пользователей/ролей,
  операций с KV-хранилищем, мониторинга, **управления участниками
  DCS-кластера** и **резервного копирования** (страницы в съём не вошли —
  [ТРЕБУЕТ ПРОВЕРКИ]).
- Из документации Patroni в составе продукта: «Следует запускать
  **нечётное количество узлов** etcd, ZooKeeper или Consul: **3 или
  5**!»; «DCS должен работать с 3 или 5 узлами для обеспечения
  правильного консенсуса и отказоустойчивости»; один кластер DCS может
  обслуживать множество кластеров через namespace/scope.

### 1.5 Узел арбитра (документированная роль)

- Руководство по установке («Реконфигурация Pangolin из standalone в
  кластерное решение») оперирует тремя ролями: «узел мастера», «узел
  реплики», «**узел арбитра** `{arbiter_host}`».
- «**На арбитре не требуется наличие установленной СУБД**» — ставятся
  только `pangolin-manager` (+ `pangolin-manager-venv`); в связке с etcd
  на арбитре ставится пакет `etcd`.
- В примере `postgres.yml` арбитра: «**секция postgresql отсутствует для
  арбитра, так как он не имеет установленного экземпляра СУБД**»;
  присутствуют `restapi`, `pangolin_dcs` (собственный `self_addr`,
  `partner_addrs`, `data_dir` для журнала Raft) и теги
  `nofailover: true`, `nosync: true`.
- Примеры алиасов администратора опрашивают DCS по трём узлам:
  `{master_host}:8009, {replica_host}:8009, {arbiter_host}:8009`.
- Документирована операция «Пересоздание узла арбитра» (§1.3).

### 1.6 Режимы репликации

Документ «Репликация» (Руководство администратора → Pangolin Manager) и
страница Patroni «Режимы репликации»:

- **Асинхронный** (`synchronous_mode: false`, по умолчанию): максимум
  производительности; при сбое лидера теряются транзакции, не успевшие
  примениться на реплике. Потери ограничивает `maximum_lag_on_failover`
  (байты WAL) плюс данные за последние `ttl` секунд (в среднем
  `loop_wait` ≈ 2 с). `check_timeline: true` запрещает выбирать лидером
  узел с отличающейся временной шкалой.
- **Стандартная синхронная СУБД** (`synchronous_commit: on` +
  `synchronous_standby_names`): коммит ждёт записи на реплику; **Manager
  трактует кластер как асинхронный**. Рекомендовано ≥ 2 реплик; при
  одновременной потере лидера и синхронной реплики Manager выдвинет
  асинхронную — с потерей отсутствовавших на ней транзакций.
- **Нестрогий синхронный Manager** (`synchronous_mode: true`): Manager
  сам управляет `synchronous_standby_names`. При недоступности реплики
  лидер переводится в асинхронный/standalone-режим — **доступность на
  запись сохраняется** (при аварийном сбое реплики фиксация может
  блокироваться до перевода лидера в standalone — худшая задержка `ttl`
  секунд). При сбое лидера переключение только на реплику со всеми
  зафиксированными транзакциями; если такой нет — кластер недоступен на
  запись до ручного `failover` (с потерями). «Позволяет использовать
  синхронную репликацию на двух узлах». Если хост бывшего лидера
  возвращается после сбоя и ручного переключения не было — он
  автоматически возвращается в роли лидера.
- **Строгий синхронный** (`synchronous_mode: true` +
  `synchronous_mode_strict: true`): «любое изменение данных должно быть
  сохранено на двух узлах (как минимум)»; без доступной синхронной
  реплики лидер **недоступен на запись** (обход — только асинхронный
  коммит приложением); failover только на синхронную реплику.
  Документированные остаточные риски потери даже в строгом режиме:
  одновременная потеря лидера и реплики; асинхронный коммит приложением;
  сбой фонового процесса в момент ожидания подтверждения репликации.
- **Тег `nosync: true`** исключает узел из кандидатов в синхронные
  реплики — «рекомендуется для резервных узлов за медленными сетевыми
  соединениями».
- **`synchronous_node_count`** (по умолчанию 1) — число синхронных
  standby; Manager корректирует DCS и `synchronous_standby_names` по
  мере присоединения/отключения участников; значение выше числа доступных
  узлов автоматически уменьшается.
- Переключение режимов — `pangolin-manager-ctl edit-config`
  (динамическая конфигурация в DCS), без пересоздания кластера.
- Стоимость синхронной репликации: «повышенная задержка и снижение
  пропускной способности при записи… полностью зависит от
  производительности сети».

### 1.7 Standby-кластер и мульти-ЦОД (правило двух ЦОД)

Страницы Patroni «Резервный кластер» и «Высокая доступность с несколькими
ЦОД» (в составе продукта; переведены нейросетью GigaChat — пометка в
источнике):

- **Standby-кластер**: «лидер standby» реплицируется с удалённого узла и
  ведёт каскадные реплики; удерживает блокировку лидера в **своём** DCS.
  Кластеры «не знают ничего друг о друге, кроме информации о репликации»,
  **не должны делить scope DCS**; резервный не виден в `list`/`topology`
  первичного. Настройка — секция `standby_cluster` (`host`, `port`,
  `primary_slot_name`, `create_replica_methods`) при бутстрапе; слот на
  первичном создаётся вручную (или постоянные слоты). Список хостов в
  `standby_cluster.host` → используется `target_session_attrs=read-write`.
- **Имена узлов уникальны** во всех связанных кластерах: совпадение
  имени (application_name) приводит к тому, что требование синхронной
  репликации может удовлетворяться соединением резервного кластера —
  **тихий сбой без ошибок в логах с риском потери данных**.
- **Синхронный мульти-ЦОД**: «чтобы иметь мульти-дата-центровый кластер,
  способный автоматически выдерживать падение зоны, требуется минимум
  **3 узла**»; «развернуть кластер etcd, ZooKeeper или Consul через
  разные дата-центры, с минимум 3 узлами — по одному в каждой зоне»; для
  PostgreSQL — минимум 2 узла в разных дата-центрах и
  `synchronous_mode: true`.
- **Только два ЦОД**: «лучше иметь два независимых кластера etcd и
  запускать Patroni резервный кластер во втором дата-центре»; повышение —
  **только ВРУЧНУЮ**. «**Автоматическое повышение невозможно, потому что
  DC2 никогда не сможет определить состояние DC1**».
- «**Не следует использовать `pg_ctl promote`**, нужно "вручную повысить"
  здоровый кластер, **удалив раздел `standby_cluster` из динамической
  конфигурации**».
- Перед повышением — «вручную убедиться, что исходный кластер недоступен
  (**STONITH**)», иначе **split-brain**. Возврат: добавить раздел
  `standby_cluster` обратно (запустится `pg_rewind` — требует
  `--data-checksums` при initdb и/или `wal_log_hints = on`; «всё ещё есть
  вероятность, что pg_rewind может завершиться ошибкой») либо пересоздать
  резервный кластер с нуля.

### 1.8 Режим отказоустойчивости DCS (failsafe mode)

- Узел может быть первичным, только пока обновляет блокировку лидера в
  DCS; при сбое обновления Postgres «немедленно понижается и запускается
  в режиме только для чтения». Разделение сети и недоступность DCS с
  точки зрения узла неразличимы — предполагается худшее.
- **failsafe_mode** включается только через глобальную динамическую
  конфигурацию (ключ `/config`; `edit-config -s failsafe_mode=true` или
  REST API `PATCH /config`). При сбое обновления блокировки Postgres
  **может продолжать работать первичным, если доступны ВСЕ известные
  участники кластера через REST API** (постоянный ключ `/failsafe` со
  списком участников; опрос `POST /failsafe`; не отвечает хотя бы один —
  первичный понижается).
- Кандидатом в лидеры при недоступном DCS может стать только участник из
  ключа `/failsafe`. Реплики считают запросы `POST /failsafe` индикатором
  живости первичного (кэш на `ttl`).
- FAQ: на кворум здесь полагаться нельзя («представление о кворуме может
  различаться с точки зрения DCS и Patroni»); если узел завершён, пока
  DCS недоступен, проверка не пройдёт и Postgres останется пониженным до
  восстановления DCS.

### 1.9 Pangolin Pooler: настройка, ограничения, N-ЦОД

- Pangolin Pooler — «доработанная версия утилиты PgBouncer»: минимизация
  издержек установления подключений. Доработки: сквозная аутентификация
  (включая LDAP) с аудитом; **поддержка подготовленных запросов для
  транзакционного режима кластера высокой доступности** (и сохранение
  контекста сессий — SET ROLE, search_path); PKCS#12 / Secret Management
  System (SecMan); **поддержка топологии N-ЦОД**; вывод `SHOW POOLS` в
  лог; команда `RESET_AUTH`.
- `max_connections` определяется на нагрузочном тестировании; стартовая
  формула `GREATEST(5 × CPU cores, 100)`; **одинаковое значение на всех
  узлах, которые могут стать Primary** (иначе после failover часть
  клиентов не подключится); изменение требует перезапуска; проверять
  после формирования конфигурации **Pangolin Tuner**.
- Пулер рекомендуется, когда `max_client_conn > max_connections`.
  Правила: `max_db_connections <= max_connections −
  superuser_reserved_connections − 30`; `min_pool_size =
  default_pool_size`; `default_pool_size` задаётся на пару
  пользователь/БД (потолок `pool_size × БД × пользователей`,
  ограничивать `pool_size` в секции `databases`). Пример сбалансированной
  конфигурации (1 ТУЗ / 1 БД): `max_client_conn = 1000`,
  `pool_mode = transaction`, пулы по 200.
- Эффективность — когда `max_db_connections` **значительно меньше**
  `max_client_conn`; при близких значениях пулер — «промежуточное звено,
  замедляющее работу». «Работа через Pangolin Pooler замедляет отклик от
  БД в среднем на 5 %».
- **Когда Pooler НЕ рекомендуется**: ядро CPU пулера загружено > 70 %;
  `pool_mode = session/statement`; **OLTP-нагрузки с требованиями более
  1000–10000 TPS и длительностью операции менее 1–10 мс в
  транзакционном режиме** (накладные расходы на сокет, рост sys_time);
  OLAP с большим трафиком; когда клиентских подключений не больше, чем
  соединений с БД. Pooler однопоточен — следить за утилизацией его ядра.
- Связка с HikariCP: если пул приложения меньше `max_connections` —
  подключаться напрямую; иначе HikariCP + Pooler, `max_client_conn` >
  суммы всех пулов (`hosts × maximumPoolSize`), тайм-аут подключения на
  клиенте выше, чем на пулере.
- **Многопоточный Pangolin Pooler** (пакет `pangolin-pooler-mt`, версия
  1.5.5; **только ОС SberLinux**): потоки-воркеры (`worker_count`, по
  умолчанию 2, до 128), `so_reuseport` включён без возможности
  отключения, мониторинг `SHOW THREADS`; одновременная установка с
  однопоточной версией недопустима, «обновления» однопоточной до
  многопоточной нет; не рекомендуется для передачи значимых объёмов
  данных в потоковом режиме (COPY).
- **Топология N-ЦОД в Pooler**: N-ЦОД — «логическое объединение
  кластеров, содержащее все множество синхронизируемых данных,
  обрабатываемых одним потребителем во всех ЦОД»; синхронизация — «любым
  из инструментов межкластерной репликации». Для сценариев HA/DR Pooler
  дополнен:
  - режимы приёма соединений `NDC_ALLOWED` / `NDC_DISALLOWED`;
  - команда `NDC_SUSPEND` (админ-консоль): прерывает все соединения к БД
    и клиентские (кроме админ-консоли) и запрещает новые;
  - команда `NDC_KEEPALIVE`: переводит в `NDC_ALLOWED`, возобновляет
    приём; момент получения запоминается;
  - параметр `ndc_suspending_timeout` (секунды, **по умолчанию 0 =
    проверка отключена**): если с момента старта/последнего
    `NDC_KEEPALIVE` прошло больше интервала, Pooler **сам** разрывает все
    соединения и приостанавливает приём (fail-closed: для непрерывной
    работы keepalive обязан поступать регулярно). Изменение параметра не
    требует перезапуска Pooler.
  - В том же разделе описан плагин логического декодирования **wal2json**
    (в составе продукта; требует `wal_level = 'logical'` и перезапуск).

### 1.12 Производительность и жёсткие ограничения

- **64-битные идентификаторы транзакций** снимают проблему исчерпания
  32-битного XID: пример документации — при ~50 000 TPS 13-часовой
  OLAP-запрос с 32-битным счётчиком привёл бы к отказу OLTP-записи
  примерно через 12 часов (горизонт транзакций, autovacuum).
- Управление лёгкими блокировками (LWLock) для сценариев: частое
  чтение/редкая запись; запросы с большим числом таблиц; интенсивная
  работа буферного кэша.
- Резервирование подключений для ролей (файл `pg_quota.conf` в каждой
  БД) — гарантированные подключения служебных ролей при исчерпании пула.
- Контроль и квотирование потребления ресурсов (CPU/RAM/диск) с
  завершением ресурсоёмких сессий.
- `pangolin-inplace-upgrade` — обновление системных каталогов без
  миграции данных («значительно быстрее» полного pg_upgrade-сценария);
  мажорные обновления — через `pg_upgrade`.
- Жёсткие лимиты (наследованы от PostgreSQL): размер отношения 32 ТБ,
  колонок на таблицу 1600, размер поля 1 ГБ (TOAST) и др.
- Партиционирование: декларативное RANGE/LIST/HASH; нативное интервальное
  автопартиционирование `AUTO PARTITION BY` (Enterprise; схему
  автопартиционирования существующей таблицы изменить нельзя); глобальные
  индексы `CREATE INDEX ... GLOBAL` (Enterprise, только B-Tree).
- Сжатие данных при записи на диск (Enterprise): `compresstype` =
  pglz | lz4 | zstd для таблиц, партиций, матпредставлений, индексов,
  табличных пространств — экономия диска и I/O.

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Горизонт Финанс Банк» (вымышленный, топ-40 по активам) создаёт
АС «Платёжный конвейер» (АС ПК) — новую систему приёма, проведения и
учёта внутрибанковских платежей и платёжных поручений юридических лиц.
Система проектируется «с нуля» (миграции данных нет), целевая СУБД
утверждена: **Platform V Pangolin DB 8.2.0**.

АС ПК относится к системам класса **Mission Critical**: режим работы
**24×7**, недоступность более 10 минут влечёт регуляторные последствия и
штрафы по SLA с корпоративными клиентами. Требование совета по
непрерывности бизнеса: система обязана переживать **полную потерю любой
одной площадки** без потери подтверждённых платежей.

### 2.2 Площадки и профиль нагрузки

Площадки (ограничения — в INF-01):

- **ЦОД-1 «Восток»** — основная площадка (все продуктивные мощности).
- **ЦОД-2 «Запад»** — равноправная резервная площадка (полный профиль
  мощностей, приложение в горячем резерве).
- **Площадка-3 «Арбитр»** — лёгкая технологическая площадка (стойка в
  головном офисе, отдельный сетевой сегмент и инженерия, независимые от
  обоих ЦОД).

Нагрузка (целевые значения, подтверждены профилем пилота):

- Пик **9 000 транзакций/с**, короткие OLTP-транзакции (60 % чтение /
  40 % запись), средняя длительность операции 2–3 мс.
- Приложение: Java 21 / Spring Boot, **45 подов** в Kubernetes, пул
  HikariCP **30 соединений на под** (настройка пилота), суммарно до
  **1 350 одновременных клиентских соединений** к СУБД.
- Объём данных на старте **2,8 ТБ**, рост **~1,5 ТБ/год**; хранение
  онлайн — 5 лет, далее выгрузка в архивный контур (вне рамок задачи).
- Ночной клиринг: пакетная загрузка до **40 млн строк за 3 часа**.
- Отчётность/выписки: ~25 тяжёлых аналитических запросов в день.

| INF-04 | СРК банка предоставляет S3-совместимое хранилище в каждом из двух ЦОД; на площадке-3 хранилище отсутствует |
| INF-05 | Мониторинг — **Zabbix**; журналирование — централизованный SIEM; административный доступ — только через **PAM** |
| INF-06 | Kubernetes-кластеры приложения в обоих ЦОД (приложение active/standby); доработка строки подключения, параметров пула и health-check'ов приложения допустима; в банке эксплуатируется балансировщик **Platform V SynGX** |
| INF-07 | Команда сопровождения: 3 DBA (опыт PostgreSQL средний, Pangolin — базовый), 1 администратор ИБ, 2 DevOps; развёртывание — только штатной автоматизацией (Pangolin Installer / Ansible из корпоративного репозитория) |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с субботы на воскресенье, **не более 6 часов** |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность (24×7) | ≥ 99,98 % в год |
| NFR-02 | RPO при отказе узла / стойки внутри ЦОД | **0** |
| NFR-03 | RTO при отказе узла внутри ЦОД (автоматически) | ≤ 2 мин |
| NFR-04 | RPO при полной потере любого основного ЦОД | **0** (подтверждённые платежи не теряются) |
| NFR-05 | RTO при полной потере основного ЦОД, **автоматическое** переключение (без решения дежурной смены) | ≤ 10 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД | ≤ 10 мс при пике 9 000 TPS |
| NFR-07 | Потеря площадки-3 «Арбитр» | без влияния на запись (RPO = 0, RTO = 0) и без риска split-brain |
| NFR-08 | Аналитические запросы не деградируют OLTP более чем на 5 % по p99 | — |
| NFR-09 | Ёмкость | 5 лет хранения при росте 1,5 ТБ/год + 30 % запас |
| NFR-10 | PITR | глубина 30 дней; RTO восстановления полной БД из копии ≤ 8 ч |
| NFR-11 | Минорные обновления СУБД и компонентов | без простоя приложения |
| NFR-12 | Мажорные обновления | в окне INF-08 |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные платежей (банковская тайна + ПДн) шифруются «на диске»; ключи — во внешнем хранилище секретов банка (INF-03); доступность СУБД при недоступности хранилища секретов должна быть спроектирована |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен читать содержимое защищаемых таблиц |
| SEC-03 | TLS для всех соединений: клиент ↔ пул ↔ СУБД, узлы кластера ↔ DCS (включая трафик на площадку-3), REST API оркестратора; сертификаты из корпоративного УЦ; поддержка CRL; ротация не реже раза в год без простоя |
| SEC-04 | Все административные подключения — персонализированные, через PAM, с двухфакторной аутентификацией; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит событий безопасности по ГОСТ Р 59548-2022 с передачей в SIEM |
| SEC-06 | На площадке-3 не должно быть пользовательских данных и секретов, достаточных для их расшифрования; компрометация площадки-3 не должна давать доступа к данным платежей |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами.
- Комитет заранее сформулировал три «контрольных вопроса»:
  (a) почему кворум DCS переживает потерю любой площадки — показать
  расклад голосов по каждому сценарию;
  (b) чем платим за RPO = 0 между ЦОД в единицах латентности коммита и
  как это согласуется с NFR-06;
  (c) что происходит с записью при потере **второго** ЦОД (не того, где
  лидер) — зависит ли она от выбора строгого/нестрогого режима.
- Решение должно быть реализуемо силами INF-07 штатной автоматизацией.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Pangolin на момент внедрения — 8.2.0 или новее в рамках линейки
  8.x; номера версий компонентов — по §1.1.
- Приложение допускает доработку строки подключения, health-check'ов и
  логики повторных подключений.
- Служба эксплуатации может выполнять документированные ручные операции
  (`failover`, изменение динамической конфигурации) по регламенту;
  требование NFR-05 относится к штатному автоматическому сценарию.
- Бюджет на две ВМ на площадке-3 и на лицензию редакции Enterprise
  согласован, если решение того требует.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DCS | Distributed Configuration Store — распределённое хранилище конфигурации кластера (Pangolin DCS на Raft или etcd) |
| Узел арбитра | документированная роль узла кластера с Pangolin Manager + DCS **без экземпляра СУБД** (теги `nofailover`/`nosync`) |
| Switchover / Failover | плановое / аварийное переключение роли лидера |
| Standby-кластер | резервный кластер с каскадной репликацией из другого ЦОД, отдельный scope DCS, только ручное повышение |
| Нестрогий / строгий синхронный режим | режимы Manager `synchronous_mode` / `synchronous_mode_strict`: деградация в async при потере реплики vs блокировка записи |
| N-ЦОД | топология логического объединения кластеров в нескольких ЦОД; в Pooler — `NDC_SUSPEND`/`NDC_KEEPALIVE`, `ndc_suspending_timeout` |
| failsafe mode | режим отказоустойчивости DCS: первичный продолжает работу при недоступном DCS, если видит всех участников по REST API |
| STONITH | принудительное гарантированное отключение узлов проигравшей площадки перед повышением резервной |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
