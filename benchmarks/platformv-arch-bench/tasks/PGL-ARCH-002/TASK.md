# Задача PGL-ARCH-002

## 1. Роль

Вы — ведущий архитектор решений в Департаменте корпоративной архитектуры
банка. Вам поручено спроектировать **целевую (TO-BE) архитектуру слоя
хранения данных** новой платёжной системы АС «Платёжный конвейер» (АС ПК)
на СУБД **Platform V Pangolin DB** в топологии **«два основных ЦОД +
третья площадка-арбитр»** и подготовить архитектурную записку для
Архитектурного комитета.

## 2. Что нужно сделать

На основе исходных данных из `CONTEXT.md` (описание продукта, ландшафт
и требования сценария, инфраструктурные ограничения):

1. Спроектировать **топологию развёртывания Pangolin на трёх площадках**:
   размещение узлов СУБД, узлов Pangolin DCS (включая документированный
   «узел арбитра» без экземпляра СУБД), экземпляров Pangolin Pooler —
   так, чтобы кворум DCS и запись переживали **потерю любой одной
   площадки** (NFR-04, NFR-05, NFR-07).
2. Спроектировать **режимы репликации между тремя сайтами**: выбор
   синхронного/асинхронного режима на каждом плече (внутри ЦОД и между
   ЦОД) с явным компромиссом «RPO при потере ЦОД vs латентность коммита»
   (NFR-04 vs NFR-06), параметры `synchronous_mode`,
   `synchronous_mode_strict`, `synchronous_node_count`, теги `nosync`,
   `maximum_lag_on_failover`, `check_timeline`.
3. Описать **поведение решения при потере каждой площадки** (матрица
   сценариев: ЦОД-1, ЦОД-2, площадка-3, а также сетевое разделение):
   судьба кворума DCS, доступность записи, RPO/RTO, действия эксплуатации,
   возврат площадки в строй (включая требования к `pg_rewind`).
4. Спроектировать **подключение приложения**: пулы соединений, роль и
   режимы Pangolin Pooler (включая топологию N-ЦОД: `NDC_SUSPEND`,
   `NDC_KEEPALIVE`, `ndc_suspending_timeout`), обнаружение нового лидера
   после переключения, защита от записи «не в тот» ЦОД (split-brain на
   уровне приложений).
5. Спроектировать **контур безопасности** трёхплощадочного решения:
   редакция продукта, TDE и ключи, защита от привилегированных
   пользователей, TLS на всех каналах (клиент↔пул↔СУБД, узлы↔DCS,
   REST API оркестратора), аудит, персонализированный доступ.
6. Спроектировать **резервное копирование и восстановление**, включая
   PITR, размещение копий по площадкам и восстановление узла арбитра.
7. Обосновать **решения по производительности и ёмкости**: расчёт
   соединений и пула, оценка латентности синхронного коммита через
   межцодовый канал, ёмкость с учётом роста и сроков хранения, WAL-трафик
   между площадками.
8. Описать **модель эксплуатации**: обновления без простоя (где
   возможно), мониторинг лага репликации и состояния кворума, ротация
   сертификатов, диагностика.
9. Явно зафиксировать **компромиссы, риски и отвергнутые альтернативы**
   (в т.ч. standby-кластер vs растянутый кластер; строгий vs нестрогий
   синхронный режим).
10. Показать **трассировку** каждого требования (NFR-xx, SEC-xx, INF-xx)
    на принятые решения.

## 4. Ограничения и правила

- Опирайтесь **только на функциональность, подтверждённую документацией
  Pangolin** (факты приведены в CONTEXT.md §1 с пометкой `[DOC]`). Если
  используете возможность, отсутствующую в CONTEXT.md, — явно пометьте её
  как **допущение, требующее проверки**, а не как факт. Пункты CONTEXT.md
  с пометкой `[ТРЕБУЕТ ПРОВЕРКИ]` нельзя подавать как подтверждённый факт.
- Не изобретайте компоненты и не переименовывайте существующие.
  Используйте официальные наименования: `pangolin-dbms`, `Pangolin Manager`
  (`pangolin-manager`), `Pangolin DCS` (`pangolin-manager-dcs`), `etcd`,
  `Pangolin Pooler` (`pangolin-pooler`, `pangolin-pooler-mt`),
  `pangolin-manager-ctl`, `pangolin-dcs-ctl`, `Pangolin Backup Tools`,
  `pangolin-certs-rotate`, `pangolin-inplace-upgrade` и т.д.
  «Узел арбитра» — документированная роль узла без экземпляра СУБД,
  а не отдельный продукт.
- Каждое ключевое решение должно быть привязано к требованию (NFR/SEC/INF)
  и сопровождаться кратким обоснованием «почему так, а не иначе».
- Числовые оценки (число узлов, размер пула, RPO/RTO, латентность,
  ёмкость) должны быть выведены из исходных данных, а не заявлены
  декларативно.
- Объём ответа: не более 4000 слов без учёта кода диаграмм и таблиц.
- Язык ответа: русский; допустимы англоязычные технические термины.

## 6. Режим прохождения

Прогон выполняется **только в режиме `agentic`** (web_fetch по разрешённым
доменам документации + файловая система + выполнение кода): проверяется
способность агента самостоятельно собирать доказательства и подтверждать
расчёты (кворум, латентность, ёмкость). Режим фиксируется в протоколе
прогона и учитывается судьями (см. RUBRICS.md, `run_mode_adjustments`).

## 7. Что НЕ требуется

- Проектирование прикладной архитектуры АС ПК (микросервисы, API,
  бизнес-логика проведения платежа, интеграции с платёжными рельсами).
- Миграция данных с действующей СУБД (система создаётся «с нуля»).
- Сметы, лицензионные расчёты, выбор конкретных моделей серверов.
- Пошаговые инструкции установки (команды, конфиги целиком) — достаточно
  ссылок на соответствующие сценарии документации.
- Сравнение с другими СУБД, кроме случаев обоснования отвергнутых
  альтернатив.

## 8. Критерии приёмки (кратко)

Полные рубрики — в `RUBRICS.md`. Ключевые точки отсечения («hard fail»):

- кворум DCS не переживает потерю одной площадки (1 узел, чётное число
  узлов, либо все голоса в пределах двух ЦОД без независимого арбитра) —
  без явного обоснования и компенсирующих мер;
- предложено автоматическое повышение standby-кластера при потере ЦОД
  либо ручной promote без обязательного STONITH исходной площадки;
- заявлен RPO = 0 при потере ЦОД при асинхронной межплощадочной
  репликации (или без указания режима репликации между ЦОД вообще);
- вымышленные компоненты/функции Pangolin, представленные как факт
  (например, «Pangolin Witness», «Pangolin Proxy», «автоматический
  promote standby-кластера средствами Manager»);
- размещение узла с данными (экземпляра СУБД) на неаттестованной
  площадке-3 вопреки INF-01;
- отсутствует хотя бы один из обязательных артефактов D1–D10.

## 9. Примечания для составителей бенчмарка

Задача является реализацией **вариации B («три ЦОД»)** из примечаний к
PGL-ARCH-001: добавлена третья площадка-арбитр; проверяется корректное
размещение кворума DCS и режимы репликации между тремя сайтами. Сценарий
намеренно построен так, чтобы:

- требование RPO = 0 при потере ЦОД (NFR-04) вступало в противоречие с
  латентностью (NFR-06) и с рекомендацией документации «при двух ЦОД —
  standby-кластер с ручным promote»;
- запрет размещать данные на площадке-3 (INF-01) исключал «полноценный
  третий узел СУБД» и делал документированный «узел арбитра» ключевым
  элементом решения;
- требование автоматического переключения при потере ЦОД (NFR-05)
  исключало вариант «два независимых кластера + ручной promote» как
  единственный ответ без явной оговорки;
- документированное ограничение Pooler для коротких OLTP-операций
  (CONTEXT §1.9) вступало в противоречие с расчётным числом соединений.

Возможные дальнейшие вариации: `-A` (заменить NFR-04 на RPO ≤ 30 с —
проверить переход к standby-кластеру), `-C` (профиль 1С), `-D`
(добавить OLAP-контур).
