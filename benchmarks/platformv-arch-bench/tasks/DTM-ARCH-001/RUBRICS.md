# Рубрики оценки для задачи DTM-ARCH-001

## 1. Общие правила для судей

1. **Порядок:** прочитать TASK.md и CONTEXT.md → проверить HF §2 → оценить
   критерии §3 (0–4, с цитатами) → вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о DataMarts
   вне §1 и без пометки «допущение» — **непроверенное**; если ложно —
   **ложное**. Позиции §1.9 заведомо не раскрыты в документации: их подача
   как факт без пометки «требует проверки у вендора» — ошибка фактологии.
3. **«Упомянул ≠ применил»** — балл за решение, привязанное к требованию
   (NFR/SEC/INF) и обоснованное, а не за ключевое слово.
4. **Шкала 0–4:** 0 — отсутствует/ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 — образцово
   (полнота + компромиссы + ловушки §4).
5. Для каждого критерия — 1–3 цитаты (≤ 25 слов) и «чего не хватает до
   следующего уровня».
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`).
   Стиль сверх C10 и объём не оцениваются.

## 2. Правила hard-fail (HF)

Срабатывание любого правила: итог ≤ 39; критерии оцениваются для диагностики.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Кворум keeper нарушен: 1–2 экземпляра `datamarts-keeper` или keeper совмещён с `datamarts-server` на одних серверах — без явного обоснования и компенсирующих мер | Только судья (regex в mechanical_checks — подсветка); CONTEXT §1.3 |
| HF-02 | DataMarts спроектирована как система транзакционной записи (OLTP) / система-источник транзакционного контура | Только судья; CONTEXT §1.1 |
| HF-03 | Вымышленные/недокументированные возможности поданы как факт: штатный CDC DMS, «балансировщик/прокси DataMarts», движок Distributed, порт 8123, JDBC/ODBC, партиционирование/TTL, версия ядра ClickHouse — без пометки «требует проверки у вендора» (§1.9) | A-05, ловушки §4, regex-детекторы |
| HF-04 | Заявлена доступность «до 99.99 %» при < 3 репликах сегмента или без keeper — без оговорки, что условия вендора не выполняются | Только судья; CONTEXT §1.3 |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01, mechanical_checks.deliverables |

## 3. Критерии

### C1. Фактическая корректность по DataMarts (вес 15)

Соответствие утверждений CONTEXT §1, корректные наименования, отделение
фактов от допущений, работа с §1.9.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-03, либо ≥ 4 ложных утверждения о продукте |
| 2 | 2–3 неточности или одна ложная о ключевом механизме (keeper-кворум, ReplicatedMergeTree, условия 99.99 %, префикс safeguard, отсутствие встроенного scheduler'а), не разрушающая решение |
| 4 | Все утверждения верны и корректно названы; всё вне §1 помечено допущением или подтверждено ссылкой; позиции §1.9 оформлены вопросами к вендору; различаются keeper/ZooKeeper, server/keeper (RPM-конфликт), граница OLTP Pangolin / OLAP DataMarts |

**Сильный ответ:** официальные имена (`datamarts-server`, `datamarts-keeper`,
`datamarts-safeguard`, `datamarts-rrm`, `datamarts-vault-provider`, SecMan,
Corax, Pangolin DB); не утверждает версию ядра ClickHouse как факт.
**Типичные ошибки:** «DMS — ClickHouse версии X»; «штатный CDC-коннектор»;
«встроенный планировщик профилей»; «keeper на тех же серверах».

|---|---|

## 8. Калибровка и контроль качества судей

1. Подготовить эталоны (`gold`, `silver`, `fail`); медиана ансамбля — в
   `expected_totals`.
2. При `alpha < 0.75` по критерию — уточнить якоря (обычно C2 и C5).
3. 10 % прогонов — проверка человеком; расхождение > 1 балла — инцидент.
4. При обновлении DataMarts/документации — обновить CONTEXT §1/§1.9, ловушки
   §4, `docs_snapshot_date`; повысить `version`; перепрогнать эталоны.
5. Не показывать решающим ловушки §4 и якоря уровня 4.
