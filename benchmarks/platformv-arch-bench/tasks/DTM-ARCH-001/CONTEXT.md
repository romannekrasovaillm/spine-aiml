## 1. Продукт: Platform V DataMarts `[DOC]`

### 1.1 Позиционирование и ядро

- **«DMS представляет собой OLAP СУБД»** — прямое определение раздела
  «Концептуальная модель»; «высокопроизводительная аналитическая СУБД с
  поддержкой SQL и колоночной моделью хранения данных»; целевые задачи —
  «интерактивная аналитика и построение информационных панелей», «выполнение
  онлайн-запросов с задержкой менее секунды».
- **Ядро — open source ClickHouse**; версия ядра в публичных доках не указана
  (см. §1.9).
- Граница OLTP/OLAP в линейке СберТеха: OLTP и система записи — Platform V
  Pangolin DB; витрины, отчётность, дашборды, событийная аналитика —
  DataMarts. Прямого запрета OLTP в доках DMS нет, но запись устроена как
  пакетные `INSERT` + фоновые **мутации** (UPDATE/DELETE — «частичная
  мутация» в метриках), а не транзакционные точечные записи.
- Производительность (формулировки вендора): «сотни миллионов строк в
  секунду», «петабайты данных на обычных жестких дисках», векторная обработка,
  «до десятков гигабайт в секунду на чтение и запись». Оговорка вендора:
  «использование продукта иными способами», чем описано в документации, —
  «работоспособность не гарантируется».

Источник: `datamarts-mpp-analytics/SKILL.md` («Позиционирование»,
«Антипаттерны»).

### 1.2 Компонентный состав

| Компонент (RPM-пакет) | Назначение |
|---|---|
| `datamarts-server` | Сама СУБД (ClickHouse Server; systemd-юнит `clickhouse-server.service`; каталоги `/opt/datamarts/{clickhouse,keeper,safeguard}`). Рекомендовано 3+ узла; горизонтальное масштабирование — «Да» |
| `datamarts-keeper` | ClickHouse Keeper (бинарь `/usr/bin/clickhouse-keeper`, конфиг `raft_configuration`; digest-аутентификация с `superdigest` из SecMan). Допускается внешний ZooKeeper |
| `datamarts-safeguard` | REST API внешней системы управления нагрузкой (профили настроек, правила токсичности, мониторинг запросов) |
| `datamarts-rrm` + `datamarts-rrm-udf` | Исполнитель запросов на изменение ролевой модели из служебной таблицы + UDF-мост `udf_rrm` |
| `datamarts-vault-provider` | Выпуск, наблюдение и перевыпуск wrapped_token для каждого компонента DMS |
| Аудит-компонент | Чтение логов, дедупликация, запись (метрики `audit_*`); источник — `query_log`/`session_log` |

Установка — RPM-пакеты. PSQ/PostgreSQL — часть архитектуры DMS: «используется
для управления пользователями, правами доступа и ведения аудита операций»;
рекомендуемая СУБД — **Platform V Pangolin DB 5.2.2+**.

Источник: `datamarts-mpp-analytics/references/architecture-security.md`
(«Компонентный состав»).

### 1.3 Кластер: keeper-кворум, шарды, реплики

- Keeper: «разверните как минимум три экземпляра datamarts-keeper на разных
  серверах», каждому — уникальный `server_id`. **RPM `datamarts-keeper`
  конфликтует с `datamarts-server`** — keeper ставится на отдельный сервер.
- Реплицированные таблицы — механизм **ReplicatedMergeTree**; на каждом узле —
  макросы («определив номера сегментов и реплик») и «параметры репликации и
  сегментирования». Документированный пример — кластер `cluster_1S_2R`
  (1 шард, 2 реплики): `internal_replication=true`, общий `<secret>`,
  `secure=1`, порт реплик 9000, keeper-порт 9181.
- Доступность **«до 99.99 %»** — при совокупности условий: минимум **три
  реплики каждого сегмента данных**; datamarts-keeper/ZooKeeper; регулярное
  резервирование и мониторинг узлов.
- Надёжность (формулировки вендора): MTBF «более 1 года непрерывной работы при
  правильной конфигурации», Failure Rate «менее 0.1 % в год»; атомарные
  операции, контрольные суммы при чтении/записи, «автоматическое
  восстановление поврежденных сегментов данных».
- При горизонтальном масштабировании «рекомендуется предварительно провести
  нагрузочное тестирование на целевой конфигурации конкретной инсталляции».

Источник: `datamarts-mpp-analytics/references/architecture-security.md`
(«Кластер: keeper-кворум, шарды, реплики»).

### 1.4 Таблицы, движки, агрегации, версии

- Движки, **названные в документации**: `MergeTree`, `ReplicatedMergeTree`,
  `Kafka`, `PostgreSQL`, `Executable` (служебная).
- Ключи: «выбор правильных первичных ключей и индексация столбцов ускоряет
  доступ к данным».
- **Материализованные представления**: «автоматическое обновление агрегатов
  при добавлении новых данных», «хранение результатов в отдельной таблице»,
  «возможность настраивать триггеры и условия обновления» — основной механизм
  предрасчёта витрин и регулярных ресурсоёмких отчётов.
- **Версионные таблицы**: «сохраняют историю изменений каждой строки и
  восстанавливают состояние на любой момент времени; минимальные затраты
  памяти благодаря специально реализованному механизму версионирования».
  Конкретный движок версионных таблиц не назван (см. §1.9).
- Загрузка — `INSERT INTO`; выгрузка — `SELECT INTO OUTFILE`.
- **Партиционирование таблиц и TTL данных в публичной документации не
  раскрыты** (см. §1.9); TTL упоминается только для паролей SecMan и очистки
  служебной `metrics_history`.

Источник: `datamarts-mpp-analytics/references/architecture-security.md`
(«Таблицы и движки»).

### 1.5 Загрузка и интеграции

Белый список интеграций продукта: LDAP, SecMan, White-list («списки доверенных
адресов»), Kafka («асинхронный обмен событиями»), PostgreSQL («подключение к
внешним базам данных PostgreSQL»), IDM.

- **Kafka / Corax**: табличный движок `ENGINE = Kafka()` (параметры
  `kafka_broker_list`, `kafka_topic_list`, `kafka_group_name`, `kafka_format`
  и др.); сообщения «в формате JSONEachRow или другом указанном формате».
  SASL-механизмы (дословно): «PLAIN», «SCRAM-SHA-256», «SCRAM-SHA-512»;
  защищённый канал — `sasl_ssl`. Поддержан Kerberos (GSSAPI); SSL-ключи из
  SecMan. Требуемые версии брокеров: **Apache Kafka 0.9+** или **Platform V
  Corax 12.381.1+**. Kafka — также шина событий между компонентами DMS
  (топик `data_marts_events`). Предписание: не передавать учётные данные
  открытым текстом.
- **PostgreSQL / Pangolin**: табличный движок `PostgreSQL` +
  `named_collections` в config.xml (`host`, `port`, `user`, `database`,
  `schema`, `sslmode` вплоть до `verify-full`; ключи и сертификаты из
  SecMan); либо Kerberos (`gssencmode=require`). Секция `[postgresql]` в
  config.yml с `pool_size = 10`.
- **FreeIPA**: «Получение актуальных keytab из FreeIPA engine» — штатная
  функция OLAP-компонента.
- **CDC как класс в публичной документации DMS не описан** (см. §1.9):
  штатный входной паттерн потоковой загрузки — движок Kafka; CDC из Pangolin
  выполняется внешним CDC-инструментом (в линейке СберТеха — GraDeLy/GDL) в
  Kafka, далее движком Kafka в DMS.
- HTTP-интерфейс (порт 8123), JDBC/ODBC в публичной документации не описаны
  (см. §1.9).

Источник: `datamarts-mpp-analytics/references/integrations-load.md` («Белый
список интеграций», «Kafka / Corax», «PostgreSQL / Pangolin»).

### 1.6 Управление нагрузкой (datamarts-safeguard)

- Назначение: REST API для внешней системы управления нагрузкой — «правила
  токсичности», мониторинг запросов онлайн и по истории, «ручное и
  автоматическое управление токсичными запросами (блокировка пользователей)»,
  «автоматическое переключение ограничений в зависимости от времени суток или
  расписания».
- Механика — профили настроек: `CREATE SETTINGS PROFILE … SETTINGS
  max_memory_usage, max_execution_time, max_threads … READONLY` + `ALTER USER
  … SETTINGS PROFILE`; readonly — «чтобы пользователи не могли самостоятельно
  обойти ограничения».
- Граница управления: safeguard управляет **только профилями с префиксом**
  `profile_prefix` (по умолчанию `beholder`); «если одна настройка задана в
  нескольких профилях, порядок ее применения не определен».
- Блокировка токсичных пользователей: предсозданная квота с минимальными
  лимитами (дословно «queries: 1, read_bytes: 1, written_bytes: 1,
  result_bytes: 1»), имя квоты — `blocked_quota_name`; исключения —
  `never_blocked_users`; запрещённые ключевые слова — `banned_sql_keywords`.
- Расписание: «в DMS **не предусмотрен встроенный механизм** автоматического
  переключения профилей настроек по расписанию» — его выполняет фоновый
  процесс safeguard (`cron.profile_schedule`) по таблице
  `settings_profiles_schedule`; постоянные назначения `assign` он не трогает.
- Мониторинг запросов через API: онлайн + история (по умолчанию глубина
  168 ч); при параметре `cluster` — сбор со всех экземпляров через
  `clusterAllReplicas`. Профили логируются в `query_log`.
- Доступ к safeguard: только mTLS + ТУЗ; аутентификация по CN клиентского
  сертификата X.509 (`subject_regexp` + белый список `allowed_certs`);
  раздельные белые списки для системы управления нагрузкой и для АС
  мониторинга; healthcheck `/health` (200 / 5xx).

Источник: `datamarts-mpp-analytics/references/integrations-load.md`
(«Управление нагрузкой: datamarts-safeguard»).

### 1.7 Безопасность: RBAC, аутентификация, секреты, аудит

- **RBAC**: «механизм безопасности основан на управлении доступом на основе
  ролей (RBAC)»; объекты доступа: «учетные записи пользователей, роли,
  политики строк, профили настроек и квоты». «По умолчанию в системе нет
  других ролей кроме администратора… администратор сам создает ролевую
  модель». Способы задания: XML-файлы в
  `/opt/datamarts/clickhouse/configs/sec.users.d/` (рекомендовано для ТУЗ)
  или SQL `CREATE ROLE` / `CREATE USER` / `GRANT`. Перечень привилегий
  включает SELECT, INSERT, ALTER, CREATE, DROP, TRUNCATE, KILL QUERY,
  ACCESS MANAGEMENT и группу SYSTEM (включая REPLICATION QUEUES,
  SYNC REPLICA, RESTART REPLICA).
- Развёртывание ролевой модели — **datamarts-rrm**: запросы с `task_id` в
  служебную таблицу → UDF `udf_rrm` → проверка «на соответствие правилам
  ограничений» → последовательное исполнение, журнал `UDF_LOGS`; статусы
  OK / FAILED / INCOMPLETE.
- **Пароли**: при интеграции с SecMan в файлы не вписываются (KV-секрет);
  TTL паролей из секрета; предупреждения об истечении — в `system.text_log`;
  если пароль в секрете отсутствует — «работа сервиса останавливается».
  Рекомендация: «в производственных средах рекомендуется отключать
  пользователя по умолчанию после настройки».
- **Аутентификация и шифрование**: LDAP, Kerberos, внутренние схемы; TLS.
  Проверка отзыва сертификатов **OCSP** (`ocsp_enable_check`, по умолчанию
  включена) предусмотрена для клиентских HTTPS-соединений, PostgreSQL и
  Kafka; есть кеш ответов OCSP.
- **SecMan** (версия 01.015.03-06): секреты загружаются при старте по
  **wrapped_token** (выпуск/перевыпуск — `datamarts-vault-provider`);
  AppRole-аутентификация; KV- и PKI-хранилища; подстановки в конфигах вида
  `${secman:pki:cert:CN=…}`, `${vault:kv:…}`. «Все секреты (клиентские
  сертификаты, пароль ТУЗ datamarts-server, сертификаты и приватные ключи
  сервера) загружаются из Secman».
- **Аудит**: штатная «передача событий аудита» (источник — `query_log` /
  `session_log`, дедупликация, метрики `audit_*`). У safeguard — отдельный
  файл `/var/log/audit/datamarts-audit.log` (rsyslog-формат, ротация);
  события: успешная (по умолчанию ВЫКЛ) и неуспешная аутентификация,
  изменение/назначение профиля, блокировка/разблокировка УЗ.

Источник: `datamarts-mpp-analytics/references/architecture-security.md`
(«RBAC, ролевая модель, пароли», «Аутентификация, TLS, OCSP») и
`references/integrations-load.md` («SecMan»).

### 1.8 Системные требования, мониторинг, трассировка

- Обязательное ПО: **Platform V SberLinux OS Server 8.7+** (единственная
  обязательная строка). Опционально: Pangolin DB 5.2.2+, Apache Kafka 0.9+ /
  Corax 12.381.1+, SecMan 01.015.03-06, DevOps Tools 1.9.1+, IDM 2.3.1+,
  Ansible 2.16+, Python 3.x.
- Железо (на элемент `datamarts-server`): CPU запрос 4 ядра, RAM запрос 8 ГБ,
  диски 25+ ГБ; лимиты — «зависят от нагрузки/объема данных».
- Мониторинг: системные таблицы `system.metrics`, `system.events`,
  `system.asynchronous_metrics`, `system.metric_log`, `system.query_log`,
  `system.latency_log`; внешние системы «например в формате Prometheus»
  (mTLS с клиентским сертификатом), Graphite. Ключевые метрики: Запрос,
  Слияние, Частичная мутация, `ConcurrencyControlSoftLimit`,
  `FilesystemMainPath*Bytes/INodes`, `rrm_tasks_executed/failed`,
  `vault_tokens_issued`, `krb_tickets_issued`; safeguard → `metrics_history`.
- Порты: native TCP 9000 (реплики, secure), keeper 9181 (secure), HTTPS для
  safeguard API. HTTP 8123/JDBC/ODBC в публичных страницах не описаны (§1.9).
- **Сквозная идентификация (Correlation ID)**: приём — `SET
  tag_correlation_id = '<id>'` или `SELECT … SETTINGS tag_correlation_id`;
  префикс тегов `tag_` задаётся в `custom_settings_prefixes`; сохраняется в
  колонке Settings `system.query_log`; доступен через REST
  `/safeguard/v1/observability/query-log`. Формат сегмента DMS в цепочке:
  `Click_<SYSTEM_ID>_<QUERY_ID>`; сегменты разделяются `|`. Передача в
  downstream PostgreSQL — через движок PostgreSQL командой `SET LOCAL
  <parameter>=<Correlation ID>` в транзакции (параметры
  `forward_correlation_id`, `correlation_id_parameter_name`).

Источник: `datamarts-mpp-analytics/references/architecture-security.md`
(«Системные требования и мониторинг») и `references/integrations-load.md`
(«Сквозная идентификация (Correlation ID)»).

### 1.9 Что заведомо НЕ раскрыто в публичной документации DMS 2.4.0

Следующие позиции в публичной документации на дату снимка **не раскрыты**.
Использование их в решении допустимо только с явной пометкой «допущение,
требует проверки у вендора»:

1. Версия ядра ClickHouse, на котором собран продукт.
2. Движок Distributed и механика табличного шардирования запросов (в публичных
   страницах есть только `clusterAllReplicas` в safeguard).
3. Партиционирование таблиц и TTL данных таблиц.
4. HTTP-интерфейс (порт 8123), JDBC/ODBC-интерфейсы.
5. Конкретный движок версионных таблиц и агрегирующие варианты
   MergeTree-семейства.
6. CDC как класс интеграции (потоковый вход — только движок Kafka).
7. Пошаговая настройка LDAP и IDM.
8. Состав событий аудита компонента аудита (за пределами метрик `audit_*` и
   событий `datamarts-audit.log`).
9. Механика резервного копирования (функция «регулярное резервирование»
   заявлена как условие доступности 99.99 %, механика не описана).

Источник: `datamarts-mpp-analytics/SKILL.md` (пометки «[ТРЕБУЕТ ПРОВЕРКИ]»)
и `references/integrations-load.md` («CDC и прочие пробелы»).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Западный Региональный Банк» (вымышленный, топ-50 по активам) формирует
обязательную отчётность в Банк России (~120 регламентных форм в месяц, включая
ежедневные) из данных транзакционного контура. Сегодня отчётность собирается
ночными регламентными заданиями непосредственно на транзакционной СУБД, что
приводит к деградации OLTP-нагрузки и срывам окон сдачи отчётности в пиковые
периоды (последние 3 рабочих дня месяца).

Программа «Данные-2028» предписывает выделить **отдельный аналитический
контур витрин данных** на **Platform V DataMarts** с загрузкой из
транзакционного контура и изоляцией аналитической нагрузки. Запуск
промышленной эксплуатации — не позднее Q2 2027.

### 2.2 Ландшафт AS-IS

- Транзакционный контур: АБС и учётные системы на **Platform V Pangolin DB**
  (кластер, версия 5.2.2+), суммарно ~6 ТБ операционных данных.
- Отчётность: ночные пакетные задания на той же Pangolin; 30–40 тяжёлых
  аналитических запросов в день конкурируют с OLTP; p99 OLTP-транзакций в
  отчётный период деградирует до 4 раз.
- Поток событий для аналитики: существующая шина **Platform V Corax**
  (Kafka-совместимая, 12.381.1+), топики доменных событий с SASL_SSL
  (SCRAM-SHA-512); **~400 млн событий/сутки** (средний размер 2 КБ), пик до
  **50 000 событий/с**.
- Справочники (клиенты, счета, продукты): ~40 справочников, 300 ГБ,
  актуализируются в Pangolin; требуется чтение из аналитического контура.
- История: восстановление состояния витрин **на любой момент времени** в
  пределах 5 лет (запросы ревизий и надзора).
- Аналитики: ~300 пользователей, ad-hoc SQL через внутренний BI-портал;
  дашборды руководства — онлайн, целевой отклик < 1 с.

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), ~40 км, каналы 2×10 Гбит/с, RTT 2–3 мс. Третьей площадки **нет**; можно разместить до 2 лёгких ВМ (4 vCPU / 16 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | До **6 физических серверов в каждом ЦОД** (x86-64, 32 ядра, 256 ГБ RAM, NVMe 4 ТБ); ОС — только **Platform V SberLinux OS Server** совместимой версии |
| INF-03 | Шина Corax в обоих ЦОД (межцодовая репликация топиков, retention доменных топиков 7 суток); изменение форматов сообщений потребителем не допускается |
| INF-04 | Хранилище секретов банка — **SecMan** (версия совместима); пароли и сертификаты открытым текстом в конфигах **запрещены** политикой ИБ |
| INF-05 | Корпоративные LDAP и Kerberos (FreeIPA) доступны из обоих ЦОД; аутентификация пользователей — только через внешний каталог, локальные УЗ — только сервисные |
| INF-06 | Для служебной БД DMS (пользователи, права, аудит) предоставляется существующий кластер Pangolin DB банка |
| INF-07 | Мониторинг — корпоративный Prometheus + Grafana; аудит — централизованный SIEM (приём по rsyslog) |
| INF-08 | Команда: 2 инженера данных (опыт ClickHouse средний), 1 администратор ИБ, 2 DevOps; развёртывание — только Ansible из корпоративного репозитория |
| INF-09 | Окно планового обслуживания: ночь сб/вс, **≤ 6 часов**, не чаще 1 раза в месяц; в отчётный период (последние 3 рабочих дня месяца) плановые работы запрещены |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность контура в отчётный период (последние 3 рабочих дня месяца, 06:00–22:00 МСК) | ≥ 99,95 %; ориентир — заявленные вендором «до 99.99 %» |
| NFR-02 | Отказ одного узла кластера | без прерывания отчётных запросов; RTO ≤ 5 мин |
| NFR-03 | RPO при отказе узла/шарда | ≤ 15 мин (допускается до-загрузка из шины/источника) |
| NFR-04 | Полная потеря ЦОД-1 | RTO ≤ 4 ч, RPO ≤ 1 ч |
| NFR-05 | Регламентные формы ЦБ | сформированы к 08:00 МСК в отчётный день; просрочка = регуляторный инцидент |
| NFR-06 | Изоляция нагрузки | ad-hoc запросы не срывают SLA отчётности (NFR-05) и дашбордов; тяжёлые ad-hoc — автоматическое ограничение/блокировка |
| NFR-07 | Потоковая загрузка | не отставать от потока 50 000 событий/с в пике; лаг потребления ≤ 5 мин |
| NFR-08 | Дашборды руководства | p95 < 1 с на предрасчитанных витринах |
| NFR-09 | Хранение истории | 5 лет, состояние витрин на любой момент времени; детальный слой — 40 ТБ сжатых к концу 5-го года |
| NFR-10 | Сквозная трассировка | каждая форма и поток загрузки трассируются сквозным идентификатором от источника до витрины |
| NFR-11 | Масштабирование | рост +30 %/год — добавлением узлов без перестройки архитектуры; перед расширением — нагрузочное тестирование |
| NFR-12 | Наблюдаемость | p95/p99 запросов, лаг загрузки, состояние репликации и keeper — в корпоративном мониторинге с алертингом |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Все соединения — TLS (клиенты ↔ СУБД, узлы кластера, keeper, интеграции Kafka/PostgreSQL, safeguard API); проверка отзыва сертификатов — OCSP |
| SEC-02 | Аутентификация аналитиков и администраторов — через корпоративный LDAP; сервисные взаимодействия (Kafka, PostgreSQL) — Kerberos или сертификаты |
| SEC-03 | Все секреты — только из SecMan; открытых секретов в конфигах нет; секреты интеграций (Kafka SSL, PostgreSQL sslkey/sslcert) — из SecMan |
| SEC-04 | RBAC: роли «аналитик-читатель / инженер данных / администратор», политики строк для разграничения подразделений; изменение ролевой модели — управляемым, протоколируемым способом |
| SEC-05 | Аудит: события аутентификации (успешные и неуспешные), управление профилями и блокировки, доступ к витринам — с выгрузкой в SIEM |
| SEC-06 | Доступ к API управления нагрузкой (safeguard) — только по mTLS с раздельными белыми списками для системы управления и мониторинга |
| SEC-07 | Пользователь по умолчанию в проме отключён; сервисные УЗ — с TTL паролей и предупреждениями об истечении |
| SEC-08 | Доступ к аналитическому контуру — только из доверенных сетевых зон (white-list) |
| SEC-09 | Пароли и учётные данные не передаются открытым текстом ни в одной интеграции (включая Kafka) |
| SEC-10 | Технические УЗ — с минимально необходимыми привилегиями; ACCESS MANAGEMENT и SYSTEM — только у выделенных ролей администраторов |

### 2.6 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами.
- Решение должно быть реализуемо силами INF-08 штатными средствами продукта.
- Комитет особенно чувствителен к двум вопросам: **размещение кворума keeper
  при двух ЦОД** и **доказуемое выполнение SLA регламентной отчётности**
  (NFR-05) в присутствии ad-hoc нагрузки аналитиков.
- Комитет предупреждён, что часть вопросов (партиционирование, TTL, механика
  резервного копирования, версия ядра) не раскрыта в публичной документации, и
  ожидает их оформления как **открытые вопросы к вендору**, а не
  бездоказательные утверждения.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия DataMarts на момент внедрения — 2.4.0 или новее; версия ядра
  ClickHouse — вопрос к вендору.
- Шина Corax выдерживает дополнительные группы потребителей; выделение
  отдельных топиков для аналитического контура согласуется с источником.
- Лаг межцодовой репликации топиков Corax ≤ 1 мин (в рамках NFR-04).
- SecMan банка доступен из обоих ЦОД с латентностью ≤ 5 мс.
- Служебная БД DMS на Pangolin (INF-06) резервируется силами существующей
  команды Pangolin и в охват задачи не входит.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DMS | Platform V DataMarts — OLAP-СУБД СберТеха на ядре open source ClickHouse |
| Keeper / datamarts-keeper | ClickHouse Keeper — координация кластера (консенсус Raft); заменяет ZooKeeper |
| ReplicatedMergeTree | механизм реплицированных таблиц DMS |
| Шард / сегмент | часть данных кластера; реплики сегмента хранят одинаковые данные |
| Safeguard | компонент управления нагрузкой (профили настроек, правила токсичности, мониторинг запросов) |
| Профиль настроек | именованный набор ограничений запросов с режимом READONLY |
| Правила токсичности | правила автоматической блокировки пользователей, создающих избыточную нагрузку |
| SecMan | система хранения и управления секретами Platform V |
| PSQ | Platform V Pangolin DB — OLTP-СУБД линейки; в DMS — для пользователей, прав и аудита |
| Corax | Kafka-совместимая шина событий Platform V |
| Correlation ID | сквозной идентификатор трассировки цепочек загрузки |
| ТУЗ | техническая учётная запись |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
| CDC | change data capture — захват изменений из системы-источника |
