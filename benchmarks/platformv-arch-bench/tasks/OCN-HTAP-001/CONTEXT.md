## 1. Продукт: Platform V Ocean DB `[DOC]`

### 1.1 Что это и позиционирование

- **Platform V Ocean DB (код OCN, актуальная версия документации 1.1.0)** —
  распределённая СУБД, объединяющая OLTP и OLAP в едином движке (**HTAP**),
  на архитектуре **Shared-Nothing**.
- Класс задач по вендору (портал Platform V): системы с транзакционным
  изменением данных и требованиями к консистентности; высоконагруженные
  системы, **шардирующие нагрузку** между инстансами реляционной БД; системы
  с плохо предсказуемой или **сезонной нагрузкой**.
- Правило выбора из дистиллята: **Ocean DB** — сверхбольшие объёмы (сотни ТБ
  на кластер), шардинг нагрузки, непредсказуемая/сезонная нагрузка, **гибрид
  OLTP + аналитика без отдельного DWH**, консолидация множества БД через
  multi-tenancy, встроенный семантический поиск.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.2 Архитектура и компоненты

Архитектура семейства OceanBase; имена компонентов совпадают напрямую:

| Компонент | Назначение |
|---|---|
| **OBSERVER** | Ядро СУБД: SQL Engine; Storage Engine (**LSM-Tree**, многоуровневое сжатие, авторебалансировка); Transaction Engine (распределённые транзакции на **Paxos**, изоляция Read-Committed и Serializable); **RootService** (метаданные, топология, восстановление) |
| **OBAGENT** | Агент мониторинга, соразмещён с OBSERVER на каждом узле (1 CPU / 2 ГБ / 20 ГБ на узел) |
| **OBPROXY** | **Stateless** прокси доступа: маршрутизация к узлу с данными, балансировка, сокрытие топологии; отслеживает расположение лидеров партиций и перенаправляет запросы к новому лидеру |
| **OBCLIENT** | Драйверы JDBC/ODBC/C и CLI |

Каждая партиция данных — **группа Paxos** из нескольких реплик в разных зонах
доступности; коммит — после подтверждения **большинством**.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md;
banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md

### 1.3 Подключение и мультиарендность

- Протокол: **MySQL-совместимый**. Поддерживается штатный `mysql`-клиент.
- Через OBProxy (рекомендуется): порт **2883**, пользователь в формате
  `user@tenant#cluster`; напрямую к OBServer — порт **2881**, `user@tenant`.
- Проверка контекста подключения:
  `SELECT effective_tenant_id(), user(), database();`
- С версии ядра 4.0 — три типа арендаторов: **системный (sys)**,
  **пользовательский** и **мета**. Системный арендатор совместим с
  MySQL-протоколом, управляет кластером и арендаторами.
- Мультиарендность: **Resource Unit** = квоты CPU/память/IO на арендатора;
  вертикальное масштабирование арендатора без перезапуска; перемещение
  ресурсных единиц между узлами; **онлайн-изменение квот**.
- OBProxy stateless — масштабируется любым числом экземпляров за обычным
  балансировщиком; кэш расположения партиций минимизирует межузловые
  обращения.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md;
banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.4 Отказоустойчивость (HA/DR)

- **RPO = 0** при сбое узла или целой зоны (коммит после подтверждения
  большинством Paxos-группы партиции).
- **RTO**: страница «Преимущества» заявляет **< 30 с** при отказе узла или
  целой зоны; паттерн надёжности заявляет **< 8 с** (перевыборы лидера без
  администратора). Это **расхождение вендора**; в ADR закладывать
  консервативные **30 с**.
- Топологии: **3+ зоны доступности** в одном или нескольких ЦОД; «горячая»
  замена узлов и роллинговые обновления без остановки.
- OBProxy перенаправляет запросы к новому лидеру партиции — failover
  прозрачен для приложений.
- Автобалансировка в фоне: объём данных, интенсивность запросов, правила
  locality, приоритеты зон.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md;
banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.5 HTAP и изоляция нагрузок

- Аналитические запросы выполняются **на актуальных транзакционных данных,
  без выгрузки и ETL**.
- Механизмы: направление аналитики на **реплики-подписчики** (не нагружая
  лидера); оптимизатор выбирает план под тип нагрузки; **параллельное
  выполнение** сложных запросов на нескольких узлах.
- Изоляция: транзакционная и аналитическая нагрузки — в **разных арендаторах
  с квотами Resource Unit**.

Внимание (тонкость для проектирования): арендатор — логически изолированная
БД кластера со своими Resource Unit (см. глоссарий). Каким образом
аналитический арендатор получает актуальные данные OLTP-арендатора, в
скачанных страницах не раскрыто; механизм «аналитика на репликах-подписчиках»
описан в рамках данных, обслуживаемых кластером. Способ совмещения изоляции
и актуальных данных — предмет проектного решения (и, при необходимости,
вопроса к вендору).

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md

### 1.6 Производительность (заявленные НФТ)

Целевая конфигурация стенда вендора: **3 узла × 8 CPU / 16 ГБ RAM / 200 ГБ
SSD**:

| Операция | op/s | SLA p95, мс |
|---|---|---|
| OLTP INSERT (однострочный) | 50 000 | 5 |
| OLTP SELECT по PK | 100 000 | 3 |
| OLTP UPDATE по PK | 50 000 | 5 |
| OLTP DELETE по PK | 50 000 | 5 |
| Аналитика (скан 1 млн строк) | 50 | 1000 |
| Смешанная нагрузка, всего | 300 000 | — |

### 1.7 Масштабирование и сжатие

- Shared-Nothing: каждый OBServer хранит и обрабатывает свою часть данных;
  **добавление узла — SQL-командами административного интерфейса, без
  остановки**; узел доступен для размещения Resource Unit арендаторов.
- Авторебалансировка партиций после изменения топологии, в фоне; скорость
  миграции данных управляется параметрами кластера.
- «Поддерживаются кластеры, объединяющие **сотни узлов** с объёмами данных на
  уровне **петабайт**».
- Сжатие: SSTable + кодирование при **Major Compaction**; алгоритмы **zstd,
  lz4, snappy, zlib**; экономия **70–80 %** (страница «Преимущества») /
  **70–90 %** (паттерн горизонтального масштабирования) дискового объёма.

Источник: banking/plugins/ru-data/skills/ocean-db-positioning/references/ha-htap.md;
banking/plugins/ru-data/skills/ocean-db-positioning/SKILL.md

### 1.8 Долговечность, резервное копирование, PITR

- **ACID полностью**; изоляция Read-Committed и Serializable (нет грязного
  чтения, неповторяемого чтения, фантомов).
- Долговечность: **синхронный WAL на нескольких репликах (по умолчанию
  три)**.
- Архивирование на **NFS / S3-совместимые хранилища** по расписанию или по
  требованию.
- **PITR с точностью до секунды**.

### 1.12 Сравнение с Platform V Pangolin DB (из дистиллята)

| Ось | Pangolin DB (PSQ 8.2.0) | Ocean DB (OCN 1.1.0) |
|---|---|---|
| Класс | OLTP-сборка PostgreSQL, «для задач аналитики — специализированные продукты» | HTAP: OLTP+OLAP в одном движке, без ETL во внешнее хранилище |
| Масштабирование | Вертикальное + read-реплики; один лидер | Горизонтальное: добавление узлов без остановки, авторебаланс партиций; «сотни узлов, петабайты» |
| HA/DR | Manager (Patroni) + DCS (Raft): RPO=0, RTO<6 мин/год; standby-кластер, N-ЦОД | Paxos-группы на партицию, 3+ зоны: RPO=0, RTO<30 с (в паттерне — <8 с) |
| Протокол/совместимость | PostgreSQL-протокол, миграция с Oracle/MS SQL | MySQL-протокол; матрица совместимости клиентов — незаполненный шаблон |
| Изоляция нагрузок | Ресурсные ограничения PostgreSQL | Мультиарендность: Resource Units (квоты CPU/RAM/IO на арендатора), онлайн-изменение |
| Целевая ОС | Шире (см. PSQ) | Только SberLinux OS Server 9.6.2 (обязательно) |

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Верхневолжский Клиринговый Банк» (вымышленный, топ-40 по активам,
~5 млн держателей карт) модернизирует антифрод карточных операций. Строится
**новая** система — АС «Антифрод-контур карточных операций» (АС АФ-КО):

- **транзакционный журнал авторизаций**: запись каждой авторизации с
  вектором признаков (устройство, геолокация, MCC, сумма, скоростные
  счётчики) и следом срабатывания правил;
- **оперативная аналитика по свежим данным**: ad-hoc запросы антифрод-
  аналитиков и регулярные скоринговые агрегаты по данным с лагом не более
  минуты;
- **онлайн-проверки в пути авторизации**: часть правил (точечные lookups)
  исполняется синхронно до решения об одобрении.

Программа утвердила **Ocean DB 1.1.0** как целевую СУБД контура (пилот HTAP
в банке); выбор пересмотру не подлежит, но архитектор обязан честно
зафиксировать его риски. АС АФ-КО относится к системам **Mission Critical**:
недоступность более 15 минут влечёт обязательный инцидент-репорт регулятору;
потеря подтверждённых записей авторизаций недопустима (спорные операции,
chargeback).

### 2.2 Профиль нагрузки и данные

- Объём: ~**60 млн авторизаций/сутки** → средняя нагрузка ≈ **700 TPS**.
- Пиковая нагрузка (вечерние часы, распродажи): **4 200 TPS**.
- Сезонный пик (новогодний период, до 7 дней): **2,5× от пиковой
  (≈ 10 500 TPS)**.
- Транзакция записи авторизации: 4–7 коротких SQL-операторов (INSERT
  авторизации, INSERT признаков, UPDATE скоростных счётчиков, запись следа
  правил); **≈ 65 % запись / 35 % чтение**, доступ преимущественно по
  первичному ключу.
- Итоговый объём данных на транзакцию (авторизация + вектор признаков +
  след правил): **≈ 5 КБ**.
- Бизнес-оценка роста: «**~120 ТБ/год сырых данных**» — заявлена как верхняя
  граница (см. §2.8: решающий обязан пересчитать).
- Хранение: **3 года онлайн** (спорные операции и chargeback), далее архив.
- Оперативная аналитика: **40–60 тяжёлых запросов в час** (сканы 0,5–5 млн
  строк по свежим данным, допустимое время ответа ≤ 30 с), плюс ad-hoc
  запросы 8–12 аналитиков в дневное время; требуемая **свежесть данных
  ≤ 60 с**.
- Онлайн-проверки в пути авторизации: ~70 правил, сводимых к точечным
  lookups по ключу; СУБД-бюджет на проверки — **p99 ≤ 5 мс** внутри общего
  бюджета авторизации.
- Приложение: Java 21 / Spring Boot, **50 подов в каждом ЦОД** в Kubernetes
  (Platform V DropApp), active-active; пул соединений **30 на под**
  (настраиваемо).

### 2.3 Ландшафт AS-IS и проблемы

- Антифрод-журнал сейчас — кластер **Pangolin DB** (ЦОД-1 + standby в
  ЦОД-2); ночной ETL выгружает данные в корпоративное хранилище банка
  (вне скоупа задачи), витрины антифрода строятся там.
- Проблема 1: **лаг данных до 24 часов** — мошеннические цепочки видны
  постфактум; оперативные правила работают по вчерашним агрегатам.
- Проблема 2: ad-hoc запросы аналитиков к боевой БД **деградировали OLTP**
  (инциденты с превышением бюджета авторизации); введён запрет ad-hoc в
  дневное время — аналитики работают ночью по ночным данным.
- Проблема 3: рост объёмов упёрся в вертикальное масштабирование; шардинг
  средствами приложения признан тупиковым.
- Корпоративное хранилище и его витрины **остаются** (долгосрочная история,
  отчётность регулятору, обучение ML-моделей); механизм кормления витрин из
  нового контура — часть границ HTAP (см. §1.11 п. 4).
- Хранилище секретов банка — **HashiCorp Vault** (3 узла, растянут между
  ЦОД).
- СРК банка: S3-совместимое и NFS-хранилище в **каждом** ЦОД.
- Мониторинг: Zabbix (обязателен) + Prometheus/Grafana (допустимы); аудит —
  централизованный SIEM; административные сессии — через PAM.

### 2.4 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~35 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 **лёгких ВМ (4 vCPU / 8 ГБ)** в «облачной зоне» банка, сетево независимой от обоих ЦОД. Выделение полноценного сервера вне двух ЦОД — изменение ограничения, требует отдельного решения ИТ-инфраструктуры (срок 3–4 месяца) |
| INF-02 | Серверы x86-64: до **6 серверов в каждом ЦОД** под СУБД-слой (2×32 ядра, 512 ГБ RAM, NVMe 6×3,84 ТБ ≈ 23 ТБ на сервер) |
| INF-03 | Стандарт ОС банка — **Platform V SberLinux OS Server** (эксплуатируются ветки 9.x и 10.x; выбор редакции согласуется с ОТБ) |
| INF-04 | Хранилище секретов — HashiCorp Vault (3 узла, растянут между ЦОД), латентность из обоих ЦОД ≤ 5 мс |
| INF-05 | СРК предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; требуется интеграция штатными средствами СУБД |
| INF-06 | Мониторинг Zabbix обязателен для промышленных систем; Prometheus/Grafana допустимы как дополнительный контур; аудит — в SIEM |
| INF-07 | Kubernetes-кластеры приложения (Platform V DropApp) в обоих ЦОД, приложение active-active; балансировщики L4/L7 банка доступны в обоих ЦОД |
| INF-08 | Команда сопровождения: 4 DBA (PostgreSQL/Pangolin — уверенно, MySQL — базово, Ocean DB — **нет опыта**), 1 администратор ИБ, 2 DevOps; контракт поддержки вендора 24×7 доступен |
| INF-09 | Окно плановых работ: ночь, не более 2 часов, не чаще раза в квартал; **приём авторизаций при этом не прерывается** |

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность АС АФ-КО (круглосуточно, 7×24×365) | ≥ 99,95 % в год |
| NFR-02 | Латентность записи авторизации на стороне СУБД (p99) при пике 4 200 TPS | ≤ 10 мс |
| NFR-03 | Отказ одного узла или одной зоны доступности | **RPO = 0**; RTO ≤ 60 с, автоматически |
| NFR-04 | Полная потеря ЦОД-1 | **RPO = 0**; RTO ≤ 15 мин (допускается ручное решение о переключении) |
| NFR-05 | Оперативная аналитика антифрода по свежим данным (лаг ≤ 60 с) | без деградации OLTP более чем на 5 % по p99 |
| NFR-06 | Синхронные онлайн-проверки в пути авторизации (точечные lookups) | СУБД-бюджет p99 ≤ 5 мс |
| NFR-07 | Сезонный пик ≈ 10 500 TPS до 7 дней | без изменения аппаратного состава; допустимая деградация p99 ≤ 25 мс |
| NFR-08 | Ёмкость | 3 года онлайн + 30 % запас |
| NFR-09 | Восстановление на момент времени (PITR) | глубина 30 дней; RTO восстановления полной БД из копии ≤ 6 ч |
| NFR-10 | Плановые обновления СУБД и плановые работы | без прерывания приёма авторизаций |
| NFR-11 | Одновременные подключения от приложения | до 3 000 |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные авторизаций (банковская тайна, PCI DSS) шифруются «на диске»; ключи — во внешнем хранилище секретов банка (Vault). Документированный статус шифрования хранимых данных у Ocean DB — см. §1.11 п. 3 |
| SEC-02 | TLS 1.2+ для всех соединений (клиент ↔ OBPROXY ↔ узлы, межузловые); сертификаты корпоративного УЦ, ротация без простоя |
| SEC-03 | Разделение обязанностей: ни один администратор (DBA, ОС, ИБ) в одиночку не должен иметь возможность читать содержимое защищаемых таблиц |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит DDL и операций с защищаемыми объектами с передачей в SIEM |
| SEC-06 | АС АФ-КО в периметре КИИ/ГОП: предпочтительно ПО с сертификацией ФСТЭК; при её отсутствии — явное риск-решение с компенсирующими мерами |
| SEC-07 | PCI DSS: сегментация CDE, минимизация хранения PAN (маскирование/токенизация на уровне приложения — вне скоупа СУБД, но должно быть учтено) |
| SEC-08 | Резервные копии не должны позволять восстановить открытые данные без ключей из хранилища секретов |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** по топологии и модели
  HTAP плюс 1–2 отвергнутые альтернативы с причинами.
- Комитет особенно чувствителен к трём вопросам:
  1. как обеспечивается **RPO = 0 при наличии только двух ЦОД** (INF-01) —
     и что произойдёт при потере ЦОД-1, если большинство зон окажется в нём;
  2. **граница HTAP**: что именно исполняется на актуальных данных внутри
     Ocean DB, что выносится из пути транзакции и что остаётся в
     корпоративном хранилище — и как изолируются нагрузки (повторение
     проблемы AS-IS недопустимо);
  3. честный статус **безопасности и сертификации** Ocean DB (§1.11) и его
     влияние на SEC-01/SEC-06.
- Решение должно быть реализуемо силами INF-08 с поддержкой вендора.

### 2.8 Что можно принять допущением `[ASSUME]`

- Версия Ocean DB на момент внедрения — 1.1.0 или новее в рамках линейки.
- Приложение новое: слой доступа к данным (драйвер, диалект SQL, строка
  подключения) проектируется без legacy-ограничений.
- Бизнес-оценка «~120 ТБ/год» дана как верхняя граница; решающий обязан
  пересчитать ёмкость из исходных цифр §2.2 (TPS × КБ × горизонт) и показать
  вывод, включая фактор репликации и эффект сжатия.
- Недокументированная возможность (§1.11) может быть включена в решение
  только как открытый вопрос к вендору с планом проверки (POC).
- Срок поставки полноценного сервера в «облачную зону» (INF-01) — 3–4
  месяца, если такое решение будет принято.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| HTAP | гибридная транзакционно-аналитическая обработка в одном движке |
| Paxos-группа | набор реплик одной партиции данных; коммит — после подтверждения большинством |
| Зона доступности | изолированный домен отказа внутри топологии Ocean DB; 3+ зоны могут размещаться в одном или нескольких ЦОД |
| Арендатор (tenant) | логическая изолированная БД в кластере Ocean DB со своими Resource Unit |
| Resource Unit | квота CPU/память/IO, выделяемая арендатору |
| Реплика-подписчик | не-лидерная реплика партиции; механизм направления аналитики, не нагружающий лидера |
| Major Compaction | фоновая компакция LSM-Tree (SSTable + кодирование), дающая основной эффект сжатия |
| PITR | восстановление на момент времени |
| TPS | транзакций в секунду |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| CDE | cardholder data environment (периметр PCI DSS) |
| КИИ / ГОП | критическая информационная инфраструктура / общебанковский процессинг |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
