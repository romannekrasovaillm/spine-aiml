## 1. Продукт: Platform V Radish KV `[DOC]`

### 1.1 Что это и позиционирование

- **Key-value СУБД в оперативной памяти**: «масштабируемое,
  отказоустойчивое и быстрое хранение и обработка данных "ключ-значение"»;
  целевые задачи — «кеширование, обработка сессий, быстрый обмен
  сообщениями и хранение временных данных, где критически важны минимальные
  задержки доступа и высокая доступность».
- **Ядро — Valkey** (форк Redis): конфигурация `valkey.conf`, сервер
  `valkey-server` / `valkey-sentinel`, CLI `valkey-cli`. С релиза 2.0.0
  Radish — «самостоятельное продуктовое решение» (ранее — компонент
  Platform V Copywala).
- Граница применимости: Radish «смягчает нагрузку центральной базы данных
  приложения» для данных, которые «редко меняются, к которым часто
  обращается приложение», и «не относящихся к критически важным, которые
  часто меняются». **Критичные данные с требованием сохранности — не
  профиль Radish** (см. §1.4: репликация асинхронна, подтверждённые записи
  могут теряться).
- Добавленная ценность относительно open-source Redis/Valkey: per-slot
  метрики, согласованная ACL-модель для всех режимов, экспериментальный
  RDMA-модуль, интеграция с SecMan, поддержка вендора.

Источник: `radish-kv-architecture/SKILL.md` («Позиционирование и границы»);
корпус: `rdh_documents__about__objective.html.txt`,
`rdh_about__compatibility.html.txt`, `rdh_about__advantages.html.txt`.

### 1.2 Совместимость с Redis/Valkey

- «Radish совместим с open-source продуктом Redis OSS версии 7.2 и более
  ранними версиями, а также с open-source продуктом Valkey версии 8.0 и
  выше. Переход с любой open-source версии Redis/Valkey на Radish будет
  являться обновлением». Совместимость с Redis — «на уровне протокола и
  команд».
- **Redis CE 7.4+ несовместим**: «начиная с версии 7.4 и выше, продукт
  Redis Community Edition (CE) не является open-source, поэтому файлы
  данных для этих версий несовместимы с Radish» — миграция с CE 7.4+
  только по протоколу (репликация/переливка), не копией дампа.
- Матрица совместимости в снимке покрывает версии до Radish 2.1.0;
  **строки для 2.2.0 нет** — [ТРЕБУЕТ ПРОВЕРКИ].

Источник: `radish-kv-architecture/references/compatibility-ops.md`
(«Совместимость»); корпус: `rdh_about__compatibility.html.txt`.

### 1.3 Топологии: standalone, Sentinel, кластер

- **Кластерный режим (shard-mode)**: **16 384 hash-слота**, ключ → слот по
  **CRC16 (mod 16384)**; слоты перераспределяются без остановки кластера;
  при обращении не к тому шарду клиент перенаправляется автоматически.
  Модель primary–replica; при падении primary реплика автоматически
  становится новым primary. Узлы соединены служебным протоколом
  **cluster bus**. Конфиг узла: `port 7000`, `cluster-enabled yes`,
  `cluster-config-file nodes.conf`, `cluster-node-timeout 5000`,
  `appendonly yes`. Создание: `valkey-cli --cluster create …
  --cluster-replicas N`. «Минимальное количество первичных узлов для
  рабочего кластера — 3, рекомендуемое — 3 первичных узла и 3 реплики»;
  масштабируется «до 1000 узлов в кластере». Проверка:
  `valkey-cli --cluster check` → `[OK] All 16384 slots covered.`
- **Sentinel** — для несегментированного набора данных: мониторинг,
  уведомления, автоматический failover, провайдер конфигурации клиентов
  (подробности §1.5).
- **Multi-DC**: прямой главы по межплощадочной репликации в снимке **нет**;
  документация допускает размещение хостов кластера «в разных зонах и
  регионах» и Sentinel «в разных зонах доступности». Растянутые на два
  ЦОД топологии — [ТРЕБУЕТ ПРОВЕРКИ] у вендора.

Источник: `radish-kv-architecture/references/ha-replication.md` («Кластер»);
корпус: `rdh_administration-guide__administration-scenarios-cluster.html.txt`,
`rdh_about__advantages.html.txt`, `rdh_about__non-functional-features.html.txt`.

### 1.4 Репликация и честные гарантии сохранности

- Тип — «лидер–последователь». Механизмы доставки: поток команд при
  надёжной связи; частичная ресинхронизация (**PSYNC**) после разрыва;
  полная синхронизация (RDB-снимок + буфер команд), когда частичная
  невозможна. Идентификация: Replication ID + offset.
- **Асинхронная по умолчанию.** Про опциональный `WAIT` документация
  говорит прямо: WAIT «обеспечивает наличие указанного числа
  подтвержденных копий в других экземплярах Radish, но **не превращает
  набор экземпляров Radish в систему с сильной консистентностью. При
  выполнении команды подтвержденные записи могут теряться в случае
  отказа**… Тем не менее… вероятность потери записи после сбоя значительно
  снижается».
- **Кворум на запись**: `min-replicas-to-write <N>` (мастер отклоняет
  запись, если синхронизировано меньше N реплик) + `min-replicas-max-lag
  <сек>`. При этом «невозможно гарантировать получение репликой
  определенной записи, что может приводить к потере данных» — окно потери
  снижается, но не устраняется.
- Реплики **read-only по умолчанию** (`replica-read-only yes`); чтение на
  репликах — `EVAL_RO`/`EVALSHA_RO`, `SORT_RO`, `SUNION`/`ZINTER` вместо
  `*STORE`. Записываемые реплики «не рекомендуются для обычной эксплуатации
  из-за риска потери согласованности»; повышать такую реплику в мастер
  нельзя.
- **TTL и репликация**: реплики не удаляют истёкшие ключи сами — ждут `DEL`
  от мастера (в т.ч. при вытеснении по LRU); логически истёкшие ключи
  реплика скрывает при чтении собственным таймером; во время Lua-скрипта
  время на мастере «заморожено».
- **Каскад**: «реплики могут подключаться к другим репликам каскадной
  структуры»; репликация не блокирует мастер; загрузка нового набора
  данных на реплике «произойдет в основном потоке и заблокирует реплику».
- Diskless: `repl-diskless-sync yes`, `repl-diskless-sync-delay`; на лаг
  влияют `repl-backlog-size`, `repl-diskless-sync`. Лаг: «возможна
  небольшая задержка (replica lag)».
- Прочее: maxmemory на репликах по умолчанию игнорируется (включить —
  `replica-ignore-maxmemory no`); аутентификация реплики на мастере —
  `primaryauth`; NAT/Docker — `replica-announce-ip/-port`.
- **Durability-режим** (раздел нефункциональных характеристик): «запись
  считается завершенной только после подтверждения от заданного числа
  реплик… операция записи отклоняется» при тайм-ауте; «только полностью
  синхронизированные реплики могут быть выбраны в качестве новых основных
  узлов». При сбоях сети: «Radish переводит узлы в защищенный режим…
  Клиентские соединения в этот момент разрываются». Доступность:
  «вероятность безотказной работы может достигать 99,95—99,99 % в год».
  Детальной главы по настройке режима в снимке нет — [ТРЕБУЕТ ПРОВЕРКИ].

Источник: `radish-kv-architecture/references/ha-replication.md`
(«Репликация», «Durability-режим»); корпус:
`rdh_administration-guide__administration-scenarios-replication.html.txt`,
`rdh_about__non-functional-features.html.txt`.

### 1.5 Sentinel: конфигурация, кворум, границы

- Запуск: `valkey-sentinel /path/to/sentinel.conf` (или `valkey-server …
  --sentinel`); файл конфигурации обязателен и должен быть доступен на
  запись (Sentinel хранит в нём состояние). Порт по умолчанию **TCP
  26379** (экземпляр Radish в примерах — 6379, кластер — 7000).
- Конфиг: `sentinel monitor mymaster {IP} 6379 2`,
  `sentinel down-after-milliseconds mymaster 60000`,
  `sentinel failover-timeout mymaster 180000`,
  `sentinel parallel-syncs mymaster 1`.
- **Кворум — только для обнаружения сбоя**; failover ведёт один Sentinel,
  ставший лидером. Реплики в конфиге не указываются — обнаруживаются
  автоматически.
- Деплой: «Подготовьте **как минимум три экземпляра Sentinel**» на
  независимо отказывающих машинах/зонах доступности; один Sentinel —
  «единая точка отказа»; failover возможен только при связности
  большинства Sentinel.
- **Граница гарантий (цитата)**: «система распределенных вычислений
  Valkey Sentinel не гарантирует сохранение подтвержденных записей во
  время сбоев в связи с использованием асинхронной репликации».
- Диагностика: `SENTINEL masters`, `SENTINEL replicas <master-name>`;
  runtime-изменение: `SENTINEL SET`, `SENTINEL CONFIG SET`.

Источник: `radish-kv-architecture/references/ha-replication.md`
(«Sentinel»); корпус:
`rdh_administration-guide__administration-scenarios-sentinel.html.txt`.

### 1.6 Persistence: RDB, AOF и ловушка автоперезапуска

- Режимы: **RDB** (снепшоты по интервалам/числу изменений), **AOF** (лог
  каждой операции записи), комбинация, полное отключение. **Дефолт Radish:
  `appendonly yes` и `save ""`** (регулярные RDB отключены).
- Параметры RDB: `save 3600 1` / `save 300 100` / `save 60 10000`, `dir`,
  `dbfilename dump.rdb`, `stop-writes-on-bgsave-error`, `rdbcompression`.
  AOF: `appenddirname`, `appendfilename`, смешанный формат
  `aof-use-rdb-preamble yes`.
- `appendfsync`: `always` — «максимальная надежность, но низкая
  производительность»; `everysec` — «баланс… вариант используется по
  умолчанию»; `no` — «наивысшая производительность, но существует риск
  потери данных».
- Рекомендации: «при высоких нагрузках увеличьте интервалы сохранения»;
  для кэша, где «потеря данных не критична, можно полностью отключить
  сохранение данных на диск».
- **Ловушка (прямой сценарий потери из документации)**: persistence
  выключен на мастере + автоперезапуск → мастер поднимается пустым →
  реплики реплицируют пустоту → «данные стираются как с основного узла,
  так и со всех реплик». С Sentinel — тот же риск при перезагрузке мастера
  быстрее, чем Sentinel обнаружит сбой. Рекомендация: «включите режим
  постоянного хранения как на основном узле, так и на репликах. В случае,
  если это невозможно, настройте экземпляры Radish на избегание
  автоматического перезапуска после перезагрузки системы».
- Штатный паттерн «мастер без диска, реплика с диском»: мастер без
  persistence, реплика с периодическим сохранением или AOF.
- Проверка: `INFO persistence`, `CONFIG GET save/appendonly`.

Источник: `radish-kv-architecture/references/persistence-memory.md`
(«Persistence»); корпус:
`rdh_administration-guide__administration-scenarios-persistence.html.txt`,
`rdh_administration-guide__administration-scenarios-replication.html.txt`.

### 1.7 Память, эвикции и подготовка ОС

- `maxmemory` — обязательная настройка кэш-профиля (`valkey.conf` или
  `CONFIG SET` + `CONFIG REWRITE`); ориентир вендора — «около 75 % от
  общей доступной оперативной памяти хоста»; `maxmemory 0` — без лимита
  (дефолт 64-бит).
- **Кэш-конфигурация из документации**: `maxmemory <лимит>` +
  `maxmemory-policy allkeys-lru` — «все ключи будут удаляться с
  использованием алгоритма LRU до тех пор, пока не будет достигнут лимит
  памяти»; приложению «не требуется устанавливать время жизни ключей».
  Политика LFU упомянуется в контексте `valkey-cli --hotkeys`. **Полный
  перечень политик эвикции в снимке не раскрыт** — [ТРЕБУЕТ ПРОВЕРКИ].
- **Client eviction**: `maxmemory-clients` — лимит совокупной памяти
  клиентских буферов (в процентах от maxmemory, напр. `5%`, или абсолютно);
  при превышении отключаются клиенты с наибольшим потреблением; критичных
  исключать — `CLIENT NO-EVICT on`. Метрики: `evicted_clients`,
  `total_eviction_exceeded_time`.
- Подготовка ОС: `vm.overcommit_memory=1`; THP `never` («может негативно
  влиять на задержки и производительность»); swap со `swappiness` 1–10.
- Клиенты: `maxclients` по умолчанию 10 000; `timeout` по умолчанию 0
  (отключён); TCP keepalive включён, интервал ~300 с.
- Пакетная загрузка: pipeline + `MULTI`/`EXEC` для атомарности.

Источник: `radish-kv-architecture/references/persistence-memory.md`
(«Память», «Эвикции», «Client eviction»); корпус:
`rdh_administration-guide__administration-scenarios-memory.html.txt`,
`rdh_administration-guide__administration-scenarios-caches-settings.html.txt`,
`rdh_administration-guide__administration-scenarios-client-eviction.html.txt`.

### 1.8 Распределённые блокировки (Redlock) — что документировано, а что нет

**Документировано** (сценарий «Распределённые блокировки»):

- Захват — установкой ключа с уникальным значением и сроком жизни:
  **`SET resource_name unique_value NX PX <ttl>`** (`NX` — только при
  отсутствии ключа, гарантия взаимного исключения; `PX <ttl>` — срок жизни
  в миллисекундах, «окно, в течение которого гарантируется взаимное
  исключение»; `unique_value` — уникальный идентификатор клиента).
- Автоматическое освобождение по TTL: «в случае, если клиент не успевает
  освободить блокировку вручную, она автоматически снимается после
  истечения времени жизни, что предотвращает блокировки при сбоях».
- Алгоритм Redlock: «подготовьте N **независимых экземпляров** Radish
  (рекомендуемое количество — 5), расположенных на разных серверах или
  виртуальных машинах»; клиент параллельно выполняет `SET … NX PX` на
  каждом из N; блокировка считается захваченной, если захвачена **на
  большинстве (> N/2)** и суммарное время захвата не превышает TTL.
- Неудачный захват: отозвать частичные блокировки (Lua-скриптом на все
  экземпляры), подождать **рандомизированный интервал**, повторить.
- Безопасное освобождение — **Lua-скриптом** с проверкой значения:
  `if redis.call("get", KEYS[1]) == ARGV[1] then return
  redis.call("del", KEYS[1]) else return 0 end`.
- Клиент «должен завершить работу с ресурсом и освободить блокировку до
  истечения времени TTL, чтобы избежать её автоматического снятия».
- Предусловия: синхронизация времени между узлами; настроенные политики
  тайм-аутов и автоснятия блокировок.

**НЕ документировано в снимке** (зона проектных решений и допущений):

- **Fencing-токены** (монотонный номер захвата, проверяемый защищаемым
  ресурсом) в снимке **не упоминаются** — механизм проектируется
  самостоятельно и помечается как допущение.
- **Продление блокировки (renewal/watchdog)** при операции длиннее TTL —
  не описано; документация требует завершить работу до истечения TTL.
- Поведение Redlock при перезапуске независимых экземпляров (перезахват
  до истечения TTL на восстановившемся узле) — не описано; увязывать с
  persistence-конфигурацией lock-экземпляров самостоятельно.
- Keyspace-уведомления (`notify-keyspace-events`) как механизм реакции на
  истечение/удаление ключей в снимке **не упоминаются**.

Источник: `radish-kv-architecture/SKILL.md` («Паттерны использования»),
`references/compatibility-ops.md` («Redlock и RDMA»); корпус:
`rdh_administration-guide__administration-scenarios-distlock.html.txt`.

### 1.9 Производительность и пределы масштабирования

- Отклик: «большинство команд за микросекунды… GET/SET на физических
  серверах стабильно 0,1 миллисекунды (100 микросекунд) и ниже»; в
  виртуализированных средах с высокой нагрузкой — до 9–40 мс; сеть
  1 Гбит/с — около 200 мкс; Unix-сокет — до 30 мкс.
- Пропускная способность: «от 900 000 до 1 190 000 запросов в секунду
  (RPS) при оптимальной настройке и использовании 8 I/O потоков»; «рост
  пропускной способности при увеличении числа потоков до 8, после чего
  дальнейшее масштабирование ограничено архитектурой (single main
  thread)» — дальше только шардирование.
- Многопоточность: main-поток + I/O-потоки с lock-free ring buffer;
  «атомарные операции для синхронизации доступа к структурам клиентов».
- НФТ-таблица (p95): авторизация до 10 000 оп/с (≤ 10 мс); подключение к
  кластеру до 5000–10 000 (≤ 20 мс); асинхронная репликация до
  850 000–1 000 000 оп/с (≤ 70 мс); RDB/AOF 5000–20 000 записей
  (5–20 мс); Lua/Functions API до 3000–5000 (≤ 50 мс).
- Lua/Functions API — атомарные составные операции; на репликах только
  `EVAL_RO`/`EVALSHA_RO`.

Источник: `radish-kv-architecture/references/compatibility-ops.md`
(«Производительность (НФТ)»); корпус:
`rdh_about__non-functional-features.html.txt`,
`rdh_about__pattern-requests.html.txt`.

### 1.10 Безопасность: ACL, TLS, секреты

- **Согласованная ACL-модель** для всех режимов (master, Sentinel,
  Cluster): единственный источник изменений; запрет локальных изменений
  вне протокола; детерминированность; канонический хеш `acl_hash`
  (`acl_sha256`); обнаружение и автовосстановление рассинхронизации; аудит
  с обязательным маскированием паролей.
- Master–replica: `ACL SETUSER_GLOBALLY`, `ACL DELUSER_GLOBALLY` (удаляет
  и разрывает соединения на всех узлах), `ACL SAVE_GLOBALLY` — только на
  мастере, в поток репликации; на репликах ACL-write запрещены; гарантия
  доставки — `WAIT`; `*_GLOBALLY` выполняются «с задержкой в несколько
  секунд».
- Sentinel: распространение ACL через канал `__sentinel__:hello`; операции
  принимает любой Sentinel, применяет лидер (минимальный sentinel_id);
  состояние — только полным снепшотом (`fullacl,<event_id>,<acl_payload>`)
  с дедубликацией по `event_id`.
- Cluster: ACL — только через cluster bus, изолированно от репликации
  данных; источник изменений — мастер нулевого слота; снепшот
  `CLUSTERMSG_TYPE_FULLACL`; сверка хешем через gossip.
- Прочее: TLS-шифрование соединений; шифрование резервных копий GPG;
  `requirepass`/`primaryauth`; роли Admin/User; управление секретами —
  SecMan 1.13.0+ или HashiCorp Vault 1.7.0+ (опционально).

Источник: `radish-kv-architecture/references/compatibility-ops.md`
(«Безопасность: ACL-модель»); корпус: `rdh_administration-guide__acl.html.txt`.

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Ильмень-Банк» (вымышленный, топ-40 по активам) модернизирует
автоматизированную банковскую систему **АБС «Кредо-Ядро»** (вымышленная;
учёт договоров, проводки, продуктовая параметрика). Ядро АБС работает на
реляционном кластере (Platform V Pangolin DB, вне рамок этой задачи).
Два смежных контура переводятся на **Platform V Radish KV**:

1. **Кэш «горячих» справочников** — данные, которые «редко меняются, к
   которым часто обращается приложение»: курсы валют и котировки,
   тарифные и лимитные матрицы, продуктовая параметрика, справочник
   подразделений и БИК, календари расчётов. Сейчас справочники читаются
   напрямую из АБС-БД, что создаёт до 60 % её read-нагрузки и деградирует
   OLTP-латентность проводок в утренние пики.
2. **Распределённые блокировки регламентных операций** — в АБС
   ~180 регламентных процедур (загрузка курсов ЦБ, внутридневная
   переоценка, закрытие операционного дня, выгрузки регуляторной
   отчётности), которые должны выполняться **строго в одном экземпляре**
   на весь кластер подов. Сейчас единственность обеспечивается таблицей
   блокировок в АБС-БД; при разрывах и переключениях БД наблюдались
   «зависшие» блокировки и (однажды, 2024 г.) двойное выполнение загрузки
   курсов, приведшее к ошибочной переоценке и финансовому инциденту.
   Из 180 операций **12 класса P0** (в т.ч. закрытие операционного дня):
   их двойное выполнение недопустимо; для классов P1–P2 двойное выполнение
   идемпотентно или безвредно.

Программа импортозамещения предписывает вывод self-hosted Redis 7.2
(pilot-кэш одного модуля АБС) до конца 2027 года. Целевой продукт
утверждён: **Platform V Radish KV 2.2.0**.

### 2.2 Ландшафт AS-IS

- Система записи справочников: схема `spr` в кластере АБС-БД (Pangolin),
  ~420 справочников, суммарный объём ~24 ГБ в сериализованном виде;
  ~95 млн записей. Обновления: дельта-загрузки до 5 000 записей/с
  короткими всплесками (курсы валют — каждые 15–60 с в сессию торгов);
  ночная полная перезагрузка части справочников.
- Доступ к справочникам: Java 17 / Spring Boot, **48 подов** сервиса
  справочников в Kubernetes в каждом ЦОД (active/active по приложению);
  чтение: среднее 25 000 RPS, утренний пик **120 000 RPS** (09:30–10:30),
  99,5 % чтений — точечные по ключу.
- Pilot-кэш: self-hosted Redis 7.2 (master + replica в ЦОД-1, без
  Sentinel), 8 ГБ данных, обслуживает один модуль АБС; инвалидация —
  только по TTL (5 мин для всех классов). Известные проблемы: устаревшие
  курсы до 5 минут (жалобы Казначейства), «гром стада» после рестарта
  (пик нагрузки на АБС-БД ×4 за 10 минут).
- Блокировки AS-IS: таблица `job_locks` в АБС-БД (SELECT FOR UPDATE +
  heartbeat); типичное удержание 5–60 с, максимум **до 20 минут**
  (переоценка портфеля); частота захватов до 600/мин в пике регламентов.
  Известные проблемы: зависшие записи после падения пода; конкуренция
  блокировок с OLTP-проводками за ресурсы АБС-БД.

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~30 км, каналы 2×10 Гбит/с, RTT 2–4 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Под контуры Radish можно выделить до 6 серверов в каждом ЦОД (x86-64, 8 vCPU, 128 ГБ RAM, NVMe 500 ГБ, ОС Platform V SberLinux OS Server 8.8+) плюс лёгкие ВМ облачной зоны из INF-01 |
| INF-03 | Система записи — кластер АБС-БД (Pangolin) в двух ЦОД; её редизайн вне рамок задачи; Radish — кэш/координационный контур рядом с ней |
| INF-04 | Хранилище секретов банка — HashiCorp Vault (3 узла между ЦОД); допустим SecMan 1.13.0+; секреты в конфигурационных файлах запрещены |

| ID | Требование |
|---|---|

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс 1–2
  отвергнутые альтернативы с причинами (как минимум: блокировки на
  системе записи/АБС-БД вместо Redlock; кластерный режим вместо Sentinel
  для кэша или наоборот).
- Комитет особенно чувствителен к двум вопросам: (а) **что происходит со
  взаимным исключением P0-операции, если её выполнение длиннее TTL
  блокировки** (исторический инцидент 2024 г.); (б) **как обеспечивается
  staleness ≤ 60 с для курсов** без ручного TTL-шаманства на каждый
  справочник.
- Решение должно быть реализуемо силами INF-07 без доработки продукта.

### 2.7 Что можно принять допущением `[ASSUME]`

- Клиентские библиотеки Java с поддержкой протокола Redis/Valkey и
  Sentinel доступны; конкретный выбор библиотеки — допущение решающего.
- NTP-синхронизация всех узлов банка в пределах 50 мс — выполнена
  (предусловие документации к Redlock).
- Сервис справочников допускает доработку: версионирование записей
  (монотонная версия/метка времени от системы записи) может быть
  добавлено в payload значений кэша.
- Регламентные процедуры допускают доработку: передача и проверка
  токена/версии при записи результатов в АБС-БД — реализуемо.
- Облачная зона из INF-01 доступна из обоих ЦОД с RTT ≤ 15 мс; её
  собственная доступность — 99,9 %.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| Redlock | документированный в Radish алгоритм распределённой блокировки на N независимых экземплярах с большинством > N/2 |
| Fencing (fencing token) | монотонный номер захвата блокировки, проверяемый защищаемым ресурсом; **в снимке документации Radish не описан** — проектный механизм |
| Sentinel | компонент мониторинга и автоматического failover несегментированного набора Radish |
| PSYNC | частичная ресинхронизация реплики после разрыва |
| AOF / RDB | журнальный / снепшотный режимы persistence |
| Эвикция | вытеснение ключей при достижении `maxmemory` по политике (`allkeys-lru` и др.) |
| Staleness | устаревание данных кэша относительно системы записи |
| Класс P0 | регламентные операции, двойное выполнение которых недопустимо |
| ТУЗ | техническая учётная запись |
| RTO | допустимое время восстановления |
