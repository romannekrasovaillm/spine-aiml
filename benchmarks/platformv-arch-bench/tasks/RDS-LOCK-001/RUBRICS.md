# Рубрики оценки для задачи RDS-LOCK-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Radish,
   которого нет в §1 и которое не помечено решающим как допущение,
   считается **непроверенным**; если оно ещё и ложно — **ложным**. Судья
   не должен «додумывать» за решающего. Особое внимание — §1.8 и §1.12:
   там зафиксировано, чего в документации **нет**; подать отсутствующее
   как факт продукта — ошибка фактологии.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (NFR/SEC/INF) и обоснованное, а не за наличие ключевого
   слова или команды.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. Режим прогона фиксирован: `agentic`. Утверждения за пределами
   CONTEXT.md §1 должны быть помечены как допущения либо подтверждены
   ссылкой на документацию Radish 2.2.0.
7. Судья не оценивает стиль и «красоту» сверх C12 и не поощряет объём.

| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (WAIT, кворум Sentinel, эвикции, TTL-репликация), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение или «[ТРЕБУЕТ ПРОВЕРКИ] у вендора»; правильно различаются: независимые экземпляры Redlock и реплики одного мастера; кворум Sentinel (обнаружение) и лидер failover; документированный Redlock и недокументированные fencing/renewal |

**Признаки сильного ответа:** использует официальные имена
(`valkey-server`, `valkey-sentinel`, `valkey-cli`, `valkey.conf`,
Radish Exporter, SecMan, `SET … NX PX`, `min-replicas-to-write`,
`min-replicas-max-lag`, `maxmemory-policy allkeys-lru`,
`CLIENT NO-EVICT`, `ACL SETUSER_GLOBALLY`); не заявляет как факт
политики эвикции кроме подтверждённых (§1.12); не приписывает Sentinel
роль кворума failover.

**Типичные ошибки:** «Sentinel гарантирует сохранность»; «Redlock на 5
репликах одного кластера»; «в Radish есть fencing-токены»; «продление
блокировки — штатная функция»; изобретение параметров; уверенные
утверждения о multi-DC-репликации.

### C2. Топология Sentinel/кластер, размещение в двух ЦОД (вес 11)

**Что оценивается:** D2 + D3. Выбор режима для кэш-контура и
lock-контура, размещение Sentinel и lock-экземпляров при двух ЦОД
(INF-01, INF-02), сценарии отказов, NFR-01, NFR-08.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; один Sentinel или все три в одном ЦОД без обоснования; HF-02 |
| 2 | Sentinel ×3 и Redlock ×5 названы, но: размещение по ЦОД не увязано с кворумом (например, 2 Sentinel в ЦОД-1 + 1 в ЦОД-2 → потеря ЦОД-1 оставляет minority и failover невозможен, а последствие не разобрано); выбор Sentinel vs кластер для кэша декларативен |
| 4 | (a) выбор режима обоснован: кэш справочников — несегментированный набор ~24 ГБ, влезает в один шард (≤ 96 ГБ maxmemory на сервер 128 ГБ из INF-02) → Sentinel-топология «мастер + реплики» достаточна, кластерный режим отвергнут с причиной (избыточен до роста за пределы сервера / усложняет lock-контур); (b) Sentinel ×3 на независимо отказывающих площадках с честным разбором: при двух ЦОД третий Sentinel — в облачной зоне (INF-01), поведение при потере ЦОД-1 (большинство живёт → failover в ЦОД-2) и при потере облачной зоны (2 Sentinel остаются, но большинство из 3 — 2 → работает) разобрано явно; (c) кворум назван кворумом обнаружения, failover — решением лидера; (d) lock-экземпляры Redlock — 5 независимых, размещение 2+2+1 (облачная зона) или иное с обоснованием; (e) NFR-08 (≤ 10 мин на lock-контур при потере ЦОД-1) увязан с тем, что из 5 экземпляров большинство (3) доступно без ЦОД-1 |

**Ловушки:** Sentinel ×2; «Sentinel хранит данные»; lock-экземпляры =
реплики одного мастера; растянутый кластер на 2 ЦОД подан как
документированная схема (CONTEXT §1.3: multi-DC-главы нет).

### C3. Распределённые блокировки (Redlock) (вес 12)

**Что оценивается:** D4 (часть Redlock), NFR-06, NFR-07, NFR-08,
SEC-02 (разделение УЗ lock-контура).

| Уровень | Якорь |
|---|---|
| 0 | Блокировки на одном экземпляре Radish или на репликах одного мастера; HF-02/HF-03 |
| 2 | Redlock по документации (5 независимых, `SET … NX PX`, большинство > N/2, Lua-освобождение) воспроизведён, но: TTL выбран «из воздуха» (не увязан с длительностью операций 5 с–20 мин из CONTEXT §2.2); обработка неудачных захватов и рандомизированная задержка не описаны; NFR-07 (≤ 500 мс на захват) не проверен против 5 последовательных/параллельных SET и RTT |
| 4 | (a) N = 5 независимых экземпляров на разных серверах/ВМ (не реплики!), размещение по площадкам обосновано; (b) TTL выведен из профиля операций: TTL ≥ max(длительность операции) с запасом ИЛИ явно принято разделение классов (для P0 с удержанием до 20 мин — TTL ~25–30 мин с fencing, для P1/P2 — короткий TTL) с разбором цены «зависшей» блокировки на TTL; (c) время захвата оценено: параллельные SET на 5 экземпляров, время = max(RTT), а не 5×RTT — и увязано с NFR-07; (d) неудачный захват: отзыв частичных блокировок на всех экземплярах, рандомизированная задержка, повтор; (e) освобождение — Lua-скриптом с проверкой unique_value на каждом экземпляре; (f) для классов P1–P2 (идемпотентных) честно рассмотрен упрощённый вариант с обоснованием; (g) persistence lock-экземпляров увязан с §1.6/§1.8 (перезапуск независимого экземпляра и перезахват до истечения TTL — разобран) |

**Ловушки:** «TTL = 30 с для всех» при 20-минутной переоценке; «TTL
бесконечный + ручное снятие» (потеря автоснятия при сбое клиента);
lock-ключи в кэш-инстансе под allkeys-lru (HF-02).

### C4. Fencing и границы взаимного исключения (вес 9)

**Что оценивается:** D4 (часть fencing), NFR-06, честность границ.

| Уровень | Якорь |
|---|---|
| 0 | HF-03: взаимное исключение «гарантировано Redlock» без оговорок |
| 2 | Сценарий истечения TTL при живом держателе (GC-пауза, длинная операция) назван, но fencing не спроектирован («приложение должно следить за временем») или подан как функция Radish |
| 4 | (a) явно зафиксировано: fencing-токены в документации Radish отсутствуют (CONTEXT §1.8) — механизм является проектным допущением/[ТРЕБУЕТ ПРОВЕРКИ]; (b) предложен монотонный токен захвата (например, счётчик `INCR` на отдельном экземпляре или версия в системе записи) с **проверкой на стороне защищаемого ресурса**: АБС-БД при фиксации результатов P0-операции отвергает записи с устаревшим токеном (допущение §2.7 это разрешает); (c) честно записано: Redlock гарантирует взаимное исключение только в пределах TTL и при корректных часах, а fencing закрывает остаточный риск двойного выполнения (NFR-06); (d) продление блокировки (renewal) помечено как недокументированное допущение с риском; (e) разобран сценарий: перезапуск lock-экземпляра → повторный захват той же блокировки до истечения TTL → fencing на ресурсе всё равно защищает |

### C5. Кэш справочников: модель, TTL, инвалидация, прогрев (вес 11)

**Что оценивается:** D5, NFR-02, NFR-03, NFR-04, NFR-05, NFR-09.

| Уровень | Якорь |
|---|---|
| 0 | Кэш не отделён от lock-контура (HF-02); «инвалидация не нужна» при NFR-04 ≤ 60 с |
| 2 | `maxmemory` + `allkeys-lru` названы; TTL по классам справочников заданы, но: стратегия активной инвалидации при дельта-загрузках отсутствует или опирается на недокументированные keyspace-уведомления как на факт; прогрев не рассчитан; холодный старт после потери ЦОД не разобран |
| 4 | (a) модель «система записи — АБС-БД, Radish — кэш» зафиксирована явно (граница профиля из §1.1); (b) ключевая модель и классы справочников с разной стратегией: курсы (NFR-04 ≤ 60 с) — активная инвалидация `DEL` с мастера при дельта-загрузке (документировано: DEL реплицируется, §1.4) + TTL-страховка; прочие (NFR-05 ≤ 5 мин) — TTL по классам + `allkeys-lru` без EXPIRE на приложении; (c) Pub/Sub-шина инвалидации, если предложена, помечена допущением (§1.12: главы по Pub/Sub в снимке нет); (d) прогрев рассчитан: 24 ГБ / 95 млн ключей pipeline-загрузкой из системы записи с ограничением скорости, чтобы не деградировать АБС-БД > 20 % (NFR-03), оценка ≤ 30 мин выведена, а не заявлена; (e) «гром стада» из AS-IS адресован (прогрев до переключения трафика, лимиты на систему записи, чтение из ЦОД-2 при холодном ЦОД-1); (f) `cache.hit_rate` — в мониторинг (§1.11); (g) версионирование значений (допущение §2.7) для защиты от гонки «старая дельта затирает новую» рассмотрено |

**Ловушки:** инвалидация через `KEYS *` + DEL в проде (SEC-05); TTL 5 мин
на курсы (нарушение NFR-04); «кэш всегда консистентен с БД» (ложно при
асинхронной доставке DEL).

**Что оценивается:** D6, NFR-03, NFR-08, INF-08.

| Уровень | Якорь |
|---|---|
| 0 | HF-06; или заявлен RPO = 0 для контуров Radish |

| 4 | (a) конфигурация разведена по контурам с обоснованием: кэш — допустимо `appendonly yes` + `everysec` (или RDB-снепшоты) ради быстрого прогрева, либо persistence off + заявка на отключение автоперезапуска по INF-08 с явным разбором ловушки §1.6; lock-экземпляры — осознанный выбор (persistence on, чтобы перезапущенный экземпляр не «забыл» и не «воскресил» состояние некорректно — с увязкой к §1.8 про перезахват); (b) честно зафиксировано: сохранность содержимого кэша не гарантируется и не требуется (система записи — АБС-БД), гарантии для блокировок ограничены TTL+fencing; (c) WAIT и `min-replicas-to-write`/`min-replicas-max-lag`, если используются, описаны корректно — «снижают вероятность потери, но не гарантируют» (§1.4); (d) штатный паттерн «мастер без диска, реплика с AOF» рассмотрен |

**Ловушки:** `appendfsync always` на кэше при 120 000 RPS без разбора

```json
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],

```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.
