# Рубрики оценки для задачи CAP-ARCH-001

## 1. Общие правила для судей

1. **Порядок:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить HF §2;
   (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из ответа;
   (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о продукте,
   которого нет в §1 и которое не помечено решающим как допущение, считается
   **непроверенным**; если оно ещё и ложно — **ложным**. Не «додумывать» за
   решающего.
3. **«Упомянул ≠ применил»** — балл за решение/расчёт, привязанный к
   требованию (NFR/SEC/INF) и выведенный из исходных данных, а не за
   ключевое слово или пересказ таблицы контекста.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 — образцово, с
   учётом компромиссов и ловушек §4.
5. **Цитирование:** 1–3 цитаты (≤ 25 слов) на критерий + чего не хватает до
   следующего уровня.
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`). Стиль и
   объём сверх C10 не оцениваются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
оцениваются для диагностики. «Только судья» = regex-детектор ненадёжен.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Вендорские НФТ выданы за **гарантированную** производительность на целевой конфигурации банка (например, «Corax выдержит 42 500 соб/с — вендор подтверждает 13 000 tps» или «Pangolin выдержит 35 000 TPS» как факт) — вопреки оговорке документации о необходимости НТ на целевой конфигурации | A-06, семантика; поиск «гарантир» рядом с числами НФТ. Только судья |
| HF-02 | Аномальное значение «p99 = 1375 с» из НФТ Corax принято как валидный норматив/SLA **без** пометки «требует проверки у вендора» | A-05, A-06 (regex `1375` + проверка контекста) |
| HF-03 | Вымышленные компоненты/функции/числа продуктов поданы как факт (например: «Pangolin Proxy», «встроенный шардировщик Radish в один клик», несуществующие НФТ-таблицы Pangolin, «DataMarts штатно партиционирует таблицы по TTL» — последнее в съёме не раскрыто) | A-05, ловушки §4 |
| HF-04 | Хотя бы для одного из четырёх слоёв (Pangolin / Radish / Corax / DataMarts) отсутствует **численный расчёт ёмкости** (есть только декларации вида «масштабируется горизонтально») | Судья: проверить D4–D7 на наличие выведенных чисел. Только судья |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01 (механические паттерны) |

## 3. Критерии

### C1. Фактическая корректность по продуктам ландшафта (вес 14)

**Что оценивается:** соответствие утверждений обо **всех четырёх** продуктах
CONTEXT.md §1; корректные наименования; отделение фактов от допущений;
правильная трактовка вендорских НФТ (стенд ≠ гарантия).

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-02 или HF-03, либо ≥ 4 ложных утверждений о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (потолок I/O-потоков Radish, тестовый профиль Corax, конфликт RPM keeper/server, формула max_connections), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; различаются: НФТ-стенд вендора и пром-рекомендации (Corax: acks=1/mis=1 — тест, а не норма; RF ≥ 3 + mis ≥ 2 — условие 99,9 %); «горизонтальное масштабирование: Нет» для отдельного экземпляра Radish и шардирование кластера; пробелы съёма (НФТ Pangolin, версия ClickHouse, Distributed/TTL в DMS, CDC в DMS) честно помечены как вопросы к вендору |

**Признаки сильного ответа:** официальные имена (`pangolin-dbms`, Pangolin
Manager, Pangolin DCS, Pangolin Pooler, `datamarts-server`, `datamarts-keeper`,
`datamarts-safeguard`, Apache Kafka, Apache ZooKeeper, Corax Schema Registry,
Corax Mirror Maker 2); «13 000 tps» назван профилем конкретного стенда;
«42,5 оп/с» DMS назван профилем двух типов запросов на стенде 3×8 CPU;
аномалия «1375 с» помечена [ТРЕБУЕТ ПРОВЕРКИ]; версия ядра Kafka не
заявлена как факт.

**Типичные ошибки:** «Radish масштабируется вертикально без ограничений»;
«Pangolin имеет опубликованный TPS»; «keeper и server DMS на одном хосте»;
«99.99 % DMS с двумя репликами»; «MM2 синхронен».

| Уровень | Якорь |

| 4 | Для каждого слоя выведены свои ведущие метрики из §2.3: Pangolin — пик 35 000 TPS, 12 000 соединений, 17,4 ТБ; Radish — пик 700 000 RPS, 5,5 млн сессий × 5 КБ + справочники + счётчики, 3 000 Lua-оп/с; Corax — пик 42 500 соб/с × 2 КБ ≈ 85 МБ/с (пик) / 28 МБ/с (средний), сверки отдельным потоком, реестры 3 МБ; DMS — 19,8 ТБ витрин, 300 тяжёлых запросов/час, 120 пользователей. Сайзинг ведётся от пиков (NFR-02) с запасом 30 % (NFR-09); рост показан по годам (вход для календарного плана D8); арифметика воспроизводима (A-06) |

**Ловушки:** сайзинг по средней нагрузке; «×5 всем» без разбора
непропорциональностей (память Radish растёт от MAU и сессий, диски Corax —
от retention × поток × RF, а не от TPS Pangolin напрямую).

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "CAP-ARCH-001-RUB",
  "task_id": "CAP-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` по формуле из frontmatter; `excellent` при `total ≥ 85`,
`pass` при `≥ 70`, иначе `fail`; при любом `hard_fails[].triggered = true`
— `fail`.
