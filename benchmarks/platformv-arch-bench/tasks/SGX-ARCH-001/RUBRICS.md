# Рубрики оценки для задачи SGX-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о SynGX,
   которого нет в §1 и которое не помечено решающим как допущение,
   считается **непроверенным**; если оно ещё и ложно — **ложным**. Судья
   не должен «додумывать» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие ключевого
   слова или директивы.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. Режим прогона фиксирован: `agentic`. Утверждения за пределами
   CONTEXT.md §1 должны быть помечены как допущения либо подтверждены
   ссылкой на документацию SynGX 4.3.0.
7. Судья не оценивает стиль и «красоту» сверх C10 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | SynGX представлен как API-шлюз/API-management: ему как **встроенные факты продукта** приписаны функции, которых нет в документации, — портал разработчика, каталог API, авторизационный сервер OAuth2 (выдача токенов), WAF, биллинг | Только судья: семантическая проверка по CONTEXT §1.9 и таблице ловушек T1–T4 (частично ловится regex mechanical_checks: упоминание WAF/OAuth2-сервера/портала в контексте «встроенный/штатный/в составе SynGX») |
| HF-02 | Заявлено, что SynGX **сам** отправляет метрики во внешние системы (push) или пишет логи напрямую в Kafka «из коробки» | Только судья + regex mechanical_checks (характерные формулировки); сверка с CONTEXT §1.7 |
| HF-03 | HA решён «встроенной кластеризацией SynGX» (межинстансовый VRRP/keepalived/синхронизация состояния как функция продукта) без явной пометки, что это внешнее решение; либо топология с единственной точкой отказа на уровне edge при NFR-01 | Только судья: сверка с CONTEXT §1.6; проверить наличие внешнего балансировщика (GSLB/L4 VIP из INF-01) в схеме |
| HF-04 | Закрытые TLS-ключи edge-контура хранятся файлами на ВМ в DMZ при наличии документированного потока Vault (ключи только в shared memory) — без явного обоснования отказа и компенсирующих мер (нарушение SEC-04) | Только судья: раздел безопасности, сверка с CONTEXT §1.4 и SEC-04 |
| HF-05 | Эндпоинт горячего управления лимитами (`limit_req_change`) выставлен за пределы loopback/unix-сокета (нарушение документированного ограничения и SEC-06) | Только судья: проверить, где размещён location управления лимитами и кто к нему обращается |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 | Механическая проверка (mechanical_checks.deliverables) + A-01 |

## 3. Критерии

### C1. Фактическая корректность по SynGX (вес 15)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md
§1; корректные наименования компонентов и директив; отделение фактов от
допущений; корректная работа с «отрицательными» фактами §1.9.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02/HF-03, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (Vault-поток, limit_req_change, active healthcheck, pull-модель метрик), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение или «проверить у вендора»; правильно различаются: факты документации и выводы дистиллята; OSS Nginx и доработки SynGX; роль SynGX (прокси) и внешних систем (IdP, каталог, биллинг) |

**Признаки сильного ответа:** использует официальные имена и директивы
(`limit_req_zone`/`limit_req`, `limit_req_by_node`, `limit_req_monitor`,
`limit_req_change`, `check`, `sticky cookie`, `ngx_hashicorp_vault_module`,
`hv_pki`/`hashicorp_vault`, `nginx-auth-jwt`, `audit_log`, `send_rst`);
упоминает кодовую базу Nginx 1.28.3; явно фиксирует, что кластеризации
между инстансами в продукте нет; не заявляет WAF/портал/каталог/OAuth2-сервер
как функции SynGX.

**Типичные ошибки:** «SynGX — API-шлюз со встроенным OAuth2»; «SynGX
отправляет метрики в Prometheus»; «ноды SynGX объединяются в кластер»;
изобретение директив; уверенные утверждения о функциях, отсутствующих в
CONTEXT.md.

### C2. Топология DMZ, внешняя балансировка, DR (вес 13)

**Что оценивается:** D2 + D3 (топологическая часть). Размещение узлов
SynGX в DMZ двух ЦОД, использование существующих GSLB и L4 VIP (INF-01),
сценарии отказа узла SynGX, всего edge-контура ЦОД и потери ЦОД (NFR-01,
NFR-02), расчёт числа узлов (NFR-03), масштабирование (NFR-10).

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; одна ВМ SynGX на контур; HF-03 |
| 2 | По паре ВМ SynGX в каждом ЦОД за L4-балансировщиком, GSLB между ЦОД; но: число узлов не выведено из нагрузки, поведение при потере ЦОД описано декларативно, SPOF где-то остались |
| 4 | (a) схема: ≥ 2 ВМ SynGX в DMZ каждого ЦОД за L4 VIP (INF-01, INF-02 — одна ВМ = один СПО), GSLB распределяет партнёрский трафик между ЦОД, исключение ЦОД при отказе через GSLB (допущение §2.9) с увязкой к RTO ≤ 15 мин (NFR-02); (b) **расчёт числа узлов из нагрузки**: пик 3 000 RPS на ЦОД в штате / 6 000 RPS + 30 % при потере ЦОД против замера вендора 3 800 оп/с проксирования (ответ 100 КБ, ≤ 50 % CPU) — с корректной оговоркой, что замер вендора для ответа 100 КБ, а профиль банка (8 КБ) требует **собственного нагрузочного тестирования** (документированная рекомендация вендора), и с выводом по числу ВМ в пределах лимита INF-02 (3 ВМ/ЦОД) или явным риском при его недостаточности; (c) разбор отказа одной ВМ SynGX (L4 VIP + health-check балансировщика), отказа всех ВМ ЦОД (GSLB), возврата ЦОД; (d) горизонтальное масштабирование «добавить ВМ за VIP» под NFR-10 |

**Ловушки:** «две ноды SynGX в кластере с плавающим IP» (кластеризации в
продукте нет); VRRP/keepalived, поданный как функция SynGX; цифра
«3 800 оп/с» применена к профилю 8 КБ без оговорки о нагрузочном
тестировании; DR «переключим вручную конфиги» вместо GSLB.

### C3. Безопасность: TLS/mTLS/JWT/Vault/ACL (вес 15)

**Что оценивается:** D4, покрытие SEC-01…SEC-10.

| Уровень | Якорь |
|---|---|
| 0 | HF-04/HF-05, либо безопасность сведена к «включим HTTPS» |
| 2 | Перечислены TLS, mTLS, JWT, Vault, но без привязки к SEC-xx; реестр CN/SAN не связан с INF-07; служебные эндпоинты не изолированы; ротация сертификатов декларативна |
| 4 | TLS ≥ 1.2 на всех стыках, к backend — `proxy_ssl_verify` + доверенный сертификат (SEC-01); mTLS партнёров через проверку CN/SAN клиентского сертификата из УЦ банка, реестр поставляется GitOps (SEC-02, INF-07); проверка JWT на edge через `nginx-auth-jwt` и/или auth-request к внешнему сервису авторизации **до** проксирования, выдача токенов явно вынесена на IdP (SEC-03, INF-06); сертификаты и ключи из Vault через `ngx_hashicorp_vault_module` (`hv_pki`/`hashicorp_vault`), закрытые ключи только в shared memory (SEC-04, INF-03), TLS к Vault обязателен; `audit_log` в syslog → SIEM, покрыты события идентификации/авторизации и изменения конфигурации (SEC-05, NFR-09); эндпоинты метрик/лимитов/ИИ-агента — loopback или внутренний контур + TLS + ACL (SEC-06); автообновление сертификатов `update_expiring_cert_interval` + метрика `vault_certificate_expiration_days` для контроля (SEC-07); `hide_syngx_name on` + манипуляция заголовками против раскрытия деталей (SEC-08); запрет debug-логов в проме (SEC-09); учтены подводные камни Vault-потока (блокировка stop/reload при ротации wrapped_token, один блок hv_pki, reload не запрашивает новые сертификаты без изменения hv_pki) и поведение при недоступности Vault |

**Ловушки:** «сертификаты положим файлами, так проще» (HF-04);
проверка JWT «где-то на backend» при SEC-03; два блока `hv_pki` с
разными role_id (не поддерживается); WAF от SynGX при INF-05 (HF-01);
`limit_req_change` на внешнем интерфейсе (HF-05).

### C4. Лимиты и квоты партнёров (вес 13)

**Что оценивается:** D5, NFR-04, NFR-05, NFR-06.

| Уровень | Якорь |
|---|---|
| 0 | Нет модели лимитов; «поставим один общий лимит» (повторение ошибки AS-IS) |
| 2 | `limit_req_zone`/`limit_req` названы; лимит на партнёра есть, но ключ зоны не выведен из идентификатора партнёра (CN сертификата/JWT-claim); нет пер-узлового лимитирования; NFR-06 решён «reload конфигурации» |
| 4 | Зоны лимитов с ключом по идентификатору партнёра (например, переменная из CN/SAN клиентского сертификата или claim JWT) и сопоставление тарифам «Старт» 50 / «Стандарт» 300 / «Премиум» 1 000 r/s (NFR-04); код отказа 429 через `limit_req_status`; dry-run для новых партнёров через `limit_req_dry_run`; `limit_req_by_node` для защиты backend-узлов при деградации группы с обоснованием (NFR-05); `limit_req_monitor` для наблюдаемости по партнёрам (NFR-08); NFR-06 решён через `limit_req_change` (PATCH с `duration` → автоматический возврат, DELETE — отмена) **только с loopback/unix-сокета**, обёрнутого в GitOps/внутренний сервис, с аудитом изменений в audit.log; ёмкость зон посчитана (200 партнёров ≪ 8–16 тыс. состояний на МБ); учтена ловушка «смена ключа/имени зоны не применяется reload'ом» (нужен stop+start ⇒ плановое окно INF-09) |

**Ловушки:** лимит по `$binary_remote_addr` как «лимит партнёра» (у
партнёра много IP); отсутствие 429 (молчаливый дефолт); «меняем лимиты
редактированием конфига и reload» при NFR-06; `limit_req_change` на
публичном listen (HF-05).

| 4 | Автоматическая ротация через Vault (`update_expiring_cert_interval`, reload при смене сертификата) + контроль сроков метриками (SEC-07); плановые изменения — reload без разрыва установленных соединений (старые workers доживают запросы, NFR-07), откат на старую конфигурацию при ошибке применения; явно перечислены случаи, когда reload недостаточен, и они уводятся в окно INF-09: смена ключа/имени `limit_req_zone`, включение healthcheck в группе с `resolve`, добавление healthcheck туда, где его не было; описаны риски Vault-потока (блокировка stop/reload при ротации wrapped_token; у `systemctl restart` нет скрипта-обхода; потеря сертификатов при reload с неверным `get_cert`) и runbook на них; все изменения только через GitOps с review (INF-08); порядок обновления версии SynGX — по одной ВМ за L4 VIP, без простоя контура |

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "SGX-ARCH-001-RUB",
  "task_id": "SGX-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.

## 8. Калибровка и контроль качества судей

1. Перед запуском бенчмарка подготовить три эталонных ответа (`gold`,
   `silver`, `fail`) и убедиться, что медиана ансамбля судей попадает в
   `expected_totals`.
2. Считать согласованность судей по каждому критерию; при
   `alpha < 0.75` — уточнить якоря критерия (ожидаемо проблемные: C2 и
   C3 — там тонкая граница между «фактом продукта» и «внешним решением»).
3. Для 10 % прогонов проводить выборочную проверку человеком;
   расхождение > 1 балла по критерию фиксируется как инцидент
   калибровки.
4. При обновлении версии SynGX или документации — обновить CONTEXT §1,
   таблицу ловушек §4 и `docs_snapshot_date`; повысить `version` рубрик
   и перепрогнать эталоны.
5. Не показывать решающим таблицу ловушек §4 и якоря уровня 4 — они
   предназначены только для судей и составителей.
