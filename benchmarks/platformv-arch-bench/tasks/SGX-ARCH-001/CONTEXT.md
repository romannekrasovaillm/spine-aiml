## 1. Продукт: Platform V SynGX (SNX) 4.3.0 `[DOC]`

### 1.1 Позиционирование и состав

- SynGX — продукт для промышленной эксплуатации в качестве
  высокопроизводительного и безопасного **веб- и обратного
  прокси-сервера** на кодовой базе **Nginx 1.28.3** при обработке сетевых
  запросов к критически важным для бизнеса веб-ресурсам.
- Цель создания — альтернатива коммерческим **Nginx PLUS** и **HAProxy
  Enterprise** (недоступны в РФ) для пользователей OSS Nginx, которым
  нужны дополнительная функциональность и коммерческая поддержка.
  Продукт — полностью отечественная разработка, входит в Реестр
  российского ПО; вендор декларирует ежегодный переход на актуальную
  стабильную версию Nginx.
- Документация фиксирует ровно два паттерна применения: **веб-сервер**
  (отдача статического контента) и **обратный прокси-сервер**
  (маршрутизация и балансировка запросов с учётом отказов инсталляций
  сервиса и изменений инфраструктуры).
- SynGX — **VM-продукт** (поставка zip-архивом с RPM/DEB-пакетами,
  управление через systemd-юнит `syngx.service`), а не K8s-оператор.
- Поддерживаемые ОС (x86_64): SberLinux OS Server 8.10
  (**рекомендовано**), SberLinux 9.3, Альт 10 СП, RHEL 8.7, RedOS 8.0
  (RPM); Ubuntu 20.04/22.04/24.04, Debian 12.0, AstraLinux SE 1.8 (DEB).
- Системные требования: минимальная ВМ — 2 CPU / 2 ГБ RAM / 10 ГБ диск /
  NIC ≥ 1000 Мбит/с; горизонтальное масштабирование заявлено («Да»);
  «не рекомендуется размещение двух и более СПО на одной ВМ»; для
  промышленной эксплуатации оптимальную конфигурацию определять
  нагрузочным тестированием.
- Бинарь `syngx`; конфигурация по умолчанию `/opt/syngx/conf/syngx.conf`;
  журналы по умолчанию `/opt/syngx/logs/`; управление сигналами
  `syngx -s stop|quit|reload|debug|nodebug`; ротация журналов —
  logrotate.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (разделы «Позиционирование», «Режимы применения», «Эксплуатация в периметре банка»); `references/operations.md` (раздел «Дистрибутив и установка»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__objective.html.txt`, `snx__documents__about__system-requirements.html.txt`, `snx__documents__installation-guide__sostav-distributiva.html.txt`.

### 1.2 Доработки относительно OSS Nginx 1.28.3

- Расширенные метрики работоспособности, в т.ч. формат **Prometheus**,
  подключаемые несколькими директивами в конфигурации.
- **Active health checks** для TCP, UDP, HTTP, HTTPS, TCP TLS.
- **Lua** и **JavaScript (njs)** для собственной логики обработки
  запросов; модули манипуляции HTTP-заголовками, sticky session,
  **GeoIP**, туннелирование TLS.
- **slow start** — плавная подача нагрузки на узел, введённый в
  балансировку; улучшенная проверка конфигурации с большим числом групп
  балансировки.
- Автозагрузка TLS-сертификатов и секретов из **HashiCorp Vault**
  (модуль `ngx_hashicorp_vault_module`); поддерживается также Secret
  Management System (SecMan): «упоминание HashiCorp Vault считать
  аналогичным интеграции с SecMan».
- **sticky route** и **sticky learn**; периодическое обновление IP узлов
  группы балансировки **по DNS** без перезагрузки; отклонение входящих
  TCP-соединений при выпадении всех узлов группы балансировки.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Доработки SynGX относительно OSS Nginx 1.28.3»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__advantages.html.txt`.

### 1.3 Балансировка, sticky, динамический upstream

- Алгоритмы балансировки в секции `upstream`: **(Weighted) Round Robin**
  (по умолчанию), **(Weighted) Least Connections** (`least_conn`),
  **IP Hash** (`ip_hash`, только HTTP), **Hash по ключу** (`hash`),
  **Random** (`random`). `weight` опционален (по умолчанию 1); с
  hash/ip_hash нельзя параметр `backup`.
- Sticky-сессии: `sticky cookie` (cookie выставляет SynGX;
  предпочтительный синтаксис; `sticky name=` объявлен устаревшим и «в
  следующих версиях поддерживаться не будет»), `sticky route` (маршрут
  из cookie/URI), `sticky learn` (cookie выставляет upstream-узел, SynGX
  запоминает привязку в shared memory zone). Со sticky нельзя
  использовать `backup`. Если узел выведен healthcheck — выбор идёт по
  алгоритму балансировки, как будто привязки нет. `no_fallback` → 502,
  если узел из cookie недоступен.
- Динамический upstream по DNS: параметр `resolve` у `server` +
  `resolver` + `zone` обновляют IP без перезагрузки;
  `server_auto_resolver` управляет всеми серверами группы;
  `service=http` — SRV-записи. Изменения применяются в памяти без
  reload; добавление/удаление серверов логируется. Если в группе с
  `resolve` не был включён active healthcheck, для его включения
  требуется **остановка и запуск** SynGX (не reload). Для предотвращения
  DNS-спуфинга рекомендуется использовать DNS-серверы в защищённой
  доверенной локальной сети.
- `slow_start=<time>` у `server` — плавный рост веса от 0 до номинала
  при возврате узла; только http; несовместим с hash/ip_hash/random.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/references/patterns-config.md` (разделы «Балансировка», «Sticky (прилипание)», «Динамический upstream по DNS», «Active healthcheck»).

### 1.4 Терминация TLS, mTLS, контроль доступа, Vault

- TLS для соединений клиент ↔ SynGX и SynGX ↔ upstream-узел; «необходимо
  использовать версию протокола TLS не ниже 1.2».
- Контроль доступа: по сетевым адресам (ACL), HTTP Basic Authentication,
  **подзапрос к внешнему сервису авторизации** (auth-request), **проверка
  Common Name в клиентском TLS-сертификате** (CN/SAN).
- В дистрибутиве есть модуль **nginx-auth-jwt** (пакет `auth-jwt`) —
  проверка JWT в запросах; заявлены «проверки токенов в запросах» через
  собственную логику.
- Проверка сертификата backend-узла: `proxy_ssl_verify on` +
  `proxy_ssl_trusted_certificate` (+ `proxy_ssl_protocols`,
  `proxy_ssl_ciphers`). Параметр `sn` у `server` в upstream
  переопределяет имя узла для проверки сертификата и SNI (приоритетнее
  `proxy_ssl_name`); `sn` и `tag` совместно запрещены.
- **Интеграция с HashiCorp Vault** (`ngx_hashicorp_vault_module`,
  директива `delayed_load_cert;` + ОДИН блок `hv_pki <имя>` для
  PKI-движка или `hashicorp_vault <имя>` для KV-движка): аутентификация
  по AppRole (role_id + wrapped_token → unwrap → secret_id → client
  token → fetch). Публичная часть сертификата пишется на файловую
  систему, **закрытый ключ — только в shared memory** (доступ у master и
  privileged-агента). SynGX следит за сроком действия и сам запрашивает
  новый сертификат с перезагрузкой при его изменении
  (`update_expiring_cert_interval`). Сертификаты из Vault заменяют
  директивы `ssl_certificate*`/`proxy_ssl_certificate*` в http и stream.
  TLS-подключение к Vault рекомендовано обязательно (`hv_ssl_verify on`,
  `hv_ssl_protocols TLSv1.2`).
- Подводные камни Vault-интеграции: между использованием wrapped_token и
  получением нового **stop/quit/reload блокируются** (проверяется файл
  wrapped_token; «остановка SynGX приведет к невозможности его старта
  после остановки»); `systemctl stop syngx` обходит это скриптом с
  повторными попытками, для `systemctl restart` такого скрипта НЕТ;
  `reload` использует ранее полученные сертификаты, новые запрашиваются
  только при изменении секций `hv_pki`; поддерживается только ОДИН блок
  `hv_pki`/`hashicorp_vault` на инстанс (два блока с разными role_id не
  поддерживаются); при reload с неверными параметрами `get_cert` текущие
  сертификаты теряются.
- **kTLS** (kernel TLS) при отдаче статики/кеша: скорость отдачи более
  чем на 60 % выше для файлов > 1 МБ; требует ядро ≥ 5.2 (CONFIG_TLS) и
  openssl ≥ 3.0 — из поддерживаемых ОС подходит только SberLinux 9; на
  файлах < 16 КБ возможно замедление.
- В дистрибутиве — модуль `sslkeylog` (запись TLS-сессионных ключей для
  диагностики трафика).
- Директива `hide_syngx_name on` — скрыть имя сервера в заголовках и теле
  стандартных 3xx/4xx/5xx-ответов.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Терминация TLS и сертификаты»); `references/patterns-config.md` (раздел «TLS и HashiCorp Vault»); `references/operations.md` (раздел «Подводные камни Vault-интеграции»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__use-case-syngx-hashicorp-vault.html.txt`.

### 1.5 Rate limiting и квоты

- Базовый модуль `ngx_http_limit_req_module`: `limit_req_zone` +
  `limit_req` (алгоритм leaky bucket, ключ зоны — произвольная
  переменная, параметры `burst`/`nodelay`/`delay`, `limit_req_status`,
  `limit_req_dry_run`). Оценка памяти: 1 МБ зоны ≈ 16 тыс. состояний по
  64 Б (8 тыс. по 128 Б).
- Добавлены пороги уведомлений `notify_info`/`notify_warn`/`notify_err`
  (проценты от лимита → сообщения в error.log) и переменная
  `$limit_req_status` (PASSED/DELAYED/REJECTED/DELAYED_DRY_RUN/
  REJECTED_DRY_RUN).
- **`limit_req_by_node`** — SynGX-специфичное квотирование «на каждый
  узел в группе балансировки» (http/upstream): «позволяет предотвращать
  каскадный отказ серверов при уменьшении количества работающих узлов»;
  свой код ответа (`limit_req_status_by_node`, по умолчанию 503),
  dry-run, уровень логирования.
- **Мониторинг лимитов**: `limit_req_monitor` отдаёт по зонам JSON или
  Prometheus (счётчики зон, keys_count, requests_delayed/rejected,
  гистограмма средних скоростей по ключам, EMA).
- **Горячее управление**: location с `limit_req_change;` — PATCH-запросом
  временно менять `rate` зоны без reload (с `duration`; по истечении
  duration возврат к значению из конфигурации; повторный PATCH отменяет
  предыдущий), DELETE — вернуть исходный rate. Доступ **только с
  127.0.0.1 / unix-сокета** — иначе `[emerg] insecure server ... The
  "limit_req_change" directive can only be used for the ip address
  127.0.0.1 or a unix socket`. События изменения лимитов пишутся в
  audit.log.
- В Lua-пакете дистрибутива — библиотека `lua-resty-limit-traffic`.
- Известная ловушка: изменение ключа/имени зоны `limit_req_zone` через
  reload **не применяется** (reload «успешен синтаксически», но SynGX
  остаётся на старой конфигурации; диагностика — `Failed to reload
  SynGX` в error.log/audit.log; для вступления в силу нужен stop+start).

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Rate limiting»); `references/patterns-config.md` (раздел «Rate limiting»); `references/operations.md` (раздел «FAQ администратора»).

### 1.6 Отказоустойчивость и HA

- **Active healthcheck** (модули `nginx_upstream_check_module` для L7 и
  `ngx_stream_upstream_check_module` для L4): директива `check` в
  upstream (`interval` умолч. 10000 мс и должен быть > `timeout`;
  `timeout` 3000 мс; `fall` 5; `rise` 2; `default_down` true; `port`;
  `type`; `mandatory`; `persistent`). Типы проверок http: tcp,
  tls_handshake (ssl_hello устарел с 3.4.0), http, https; stream: udp,
  tcp, http, ssl_hello, tcp_tls. Секции `match` задают условия
  работоспособности по ответу; `match_drain` (stream) — состояние
  **DRAIN**: новые соединения не устанавливаются, существующие доживают.
- **Составные проверки**: исключение узла по произвольной комбинации
  активных/пассивных проверок ДРУГИХ узлов через Lua-модули
  (`ngx.upstream.get_primary_peers` и др.) в privileged-агенте.
- При выпадении всех узлов группы: `send_rst` (http) и модули
  `ngx_http_rst_send_module`/`ngx_stream_rst_send_module` (через
  iptables, `depending_server`) разрывают клиентские соединения — узел
  SynGX «закрывает» точку входа, пока upstream мёртв (fail-closed).
- Отказоустойчивость самого процесса: master поддерживает заданное число
  рабочих процессов и перезапускает упавшие; распределение соединений по
  workers — на уровне ядра ОС. При деградации ресурсов SynGX «сначала
  начинает увеличивать среднее время обработки запросов, а затем
  начинает отказывать в обработке новых запросов», при снижении нагрузки
  сам восстанавливается.
- **reload**: master проверяет синтаксис, запускает новые workers,
  старые доживают текущие запросы на старой конфигурации (без разрыва
  установленных соединений); при невозможности применить — откат на
  старую конфигурацию. **stop** — все соединения сбрасываются.
- **Межинстансовая кластеризация SynGX** (VRRP/keepalived, синхронизация
  состояния между ВМ) в документации **НЕ описана**; горизонтальное
  масштабирование заявлено, но схема — за внешним балансировщиком.
- Вертикальное масштабирование — workers по ядрам CPU.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «HA и отказоустойчивость»); `references/patterns-config.md` (раздел «Active healthcheck», «Жизненный цикл конфигурации»); `references/operations.md` (раздел «Нефункциональные рамки»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__use-case-syngx-active-healthcheck.html.txt`.

### 1.7 Мониторинг, журналы, аудит, трассировка

- Метрики — **только pull**: SynGX отдаёт метрики по HTTP GET (JSON /
  Prometheus / HTML); «возможность настроить SynGX, чтобы он
  самостоятельно отправлял метрики в какую-либо систему, не
  предусмотрена». Вендор требует защищать эндпоинты метрик: TLS ≥ 1.2,
  имя/пароль, ограничение по сетевым адресам.
- Модули-источники метрик: nginx-module-vts (трафик и состояния
  серверов), ngx_http_extstatus (`snx_http_extstatus_json`,
  `snx_http_certificates_status_json` и др.), upstream_check
  (`check_upstream_*`), stream (`l4check_upstream_*`), sts
  (`nginx_sts_*`), hashicorp_vault (`vault_certificate_expiration_days`,
  `vault_last_fetch_time_seconds`, `vault_fetch_errors_total`).
  Prometheus-метрики семейства `syngx_mtx_*`,
  `syngx_http_requests_total{code}`, `syngx_ssl_handshakes_total`,
  `syngx_ssl_verify_failures{name}` и др.
- В дистрибутиве — готовая **Grafana Dashboard** (SynGX Status,
  Connections, HTTP Requests, TLS, Cache Usage, Shared Memory Usage).
- Журналы: error.log (уровни emerg…debug; директива `required` запрещает
  переопределение ниже по иерархии; «включение уровня Debug не
  рекомендуется в промышленных инсталляциях»), access.log (настраиваемый
  формат `log_format`), backtrace.log при аварийном завершении worker.
  Отправка: файлы, syslog, внешние RSYSLOG/fluentbit; «в SynGX нет
  функциональности отправки логов по протоколу Kafka» — только через
  стороннее ПО.
- **Аудит**: директива `audit_log` (файл или `syslog:server=...`, UDP
  514 по умолчанию; по умолчанию выключен). События: идентификация по
  CN/SAN TLS-сертификата и логину/паролю, авторизация (basic, подзапрос,
  deny, CN/SAN), изменения конфигурации при старте/reload, изменения
  rate limit через `limit_req_change`.
- **Трассировка**: доработанный динамический модуль `nginx-otel` —
  клиентские сертификаты для mTLS к коллектору спанов
  (`client_certificate`/`client_key` в `otel_exporter`).
- ИИ-агент (динамический модуль `ngx_http_ai_agent_module`): принимает
  вопросы администратора на естественном языке (POST `{"message": ...}`),
  сам запрашивает метрики и возвращает анализ состояния с
  рекомендациями; провайдеры LLM — OpenAI-совместимый API или GigaChat
  API V2 (в примерах — GigaChat-2-Max); ключ — явно («только для
  тестирования») или из Vault; поддержан mTLS к провайдеру LLM.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (разделы «Эксплуатация в периметре банка», «ИИ-агент»); `references/operations.md` (разделы «Журналы», «Аудит», «Метрики и мониторинг»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__administration-guide__monitoring.html.txt`, `snx__documents__administration-guide__system-log.html.txt`, `snx__documents__administration-guide__audit-log-events.html.txt`.

### 1.8 Производительность (замер вендора)

- Замер вендора (SberLinux 8.8, утилизация ≤ 50 % CPU, ответ 100 КБ):
  статика HTTP(S) — **4000 оп/с**, проксирование HTTP(S) — **3800 оп/с**,
  SLA отклика 0,1 с.
- Доступность: 24×7 без участия администратора при корректной настройке
  и достаточных ресурсах (включая место под логи).

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/references/operations.md` (раздел «Нефункциональные рамки»); `experiments/0909-platformv-arch-benchmark/corpus/pv_docs/txt/snx__documents__about__non-functional-features.html.txt`.

### 1.9 Чего в продукте НЕТ (важно для границ решения)

- **WAF / ModSecurity**: в документации SNX 4.3.0 не упоминается ни
  разу. Защитные функции ограничены: ACL по адресам, Basic Auth,
  auth-request к внешнему сервису, проверка CN/SAN клиентского
  сертификата, rate limiting, GeoIP-фильтрация, проверка JWT
  (nginx-auth-jwt).
- **API-management**: портал разработчика, каталог API, управление
  жизненным циклом API, авторизационный сервер OAuth2 (выдача токенов),
  биллинг/тарификация — в составе SynGX отсутствуют; это прокси/
  балансировщик, а не API-шлюз. В линейке СберТеха смежные функции
  позиционируются за другими продуктами семейства Synapse (SNE API Mesh,
  SWA SOWA — API Security Gateway) — в данной задаче они не входят в
  scope поставки, их упоминание допустимо только как внешних систем.
- Межинстансовая кластеризация (см. §1.6), push-отправка метрик и
  запись логов в Kafka напрямую (см. §1.7).

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (разделы «WAF — НЕ обнаружен», «Антипаттерны и риски решений», «HA и отказоустойчивость»).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Меридиан"» (вымышленный, топ-20 по активам) реализует
программу «Открытый контур»: публикацию **партнёрского Open API** для
финтех-интеграций. Через API партнёры (платёжные агрегаторы, сервисы
онлайн-бухгалтерии, маркетплейсы, финтех-стартапы) получают доступ к
операциям: запрос информации по счетам (с согласия клиента), инициация
платежей, выписки, справочные данные (курсы валют, реквизиты), статусы
онбординга.

- Целевой масштаб: **~200 партнёров** к концу 2027 года (на старте 60).
- API монетизируется по тарифам (см. NFR-04): превышение тарифного
  лимита — отказ в обслуживании, а не платный овердрафт.
- Простой партнёрского API в операционное время — репутационный риск и
  штрафные санкции по договорам с крупными партнёрами.
- Программа импортозамещения предписывает вывод OSS Nginx из DMZ и
  перевод edge-контура на поддерживаемый вендором продукт. Целевой
  продукт утверждён: **Platform V SynGX 4.3.0**.

### 2.2 Ландшафт AS-IS

- Точки входа партнёров: **OSS Nginx 1.24** (open source), по одной паре
  ВМ в DMZ каждого ЦОД, конфигурация ведётся вручную по заявкам.
- Единые «общие» лимиты на весь контур; лимитов на партнёра нет. Был
  инцидент: один партнёр ошибочным циклом запросов перегрузил backend
  онбординга, что вызвало каскадный отказ смежных сервисов.
- TLS-сертификаты и закрытые ключи хранятся файлами на ВМ в DMZ; ротация
  — вручную, раз в квартал, с простоем в окне.
- Проверка партнёрских токенов выполняется каждым backend-сервисом
  самостоятельно (неоднородно).
- Логи — локальные файлы на ВМ, в SIEM попадают с задержкой до часа.
- Нет каталога API и портала: документация рассылается партнёрам PDF-ами;
  подключение нового партнёра занимает до 3 недель.
- Мониторинг: zabbix-агент на ВМ (CPU/RAM/диск), прикладных метрик
  прокси нет.

### 2.3 Топология и нагрузка `[BENCH]`

- Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~60 км,
  каналы 2×10 Гбит/с. В каждом ЦОД — изолированная DMZ-зона для
  внешних интеграций.
- Внешний трафик партнёров распределяется между ЦОД существующим
  **GSLB (DNS)** банка; внутри каждого ЦОД — существующие
  **L4-балансировщики DMZ** с VIP.
- Нагрузка (целевые значения на конец 2027):
  - суммарный пик **6 000 RPS** по всем партнёрам (распределяется GSLB
    примерно 50/50 между ЦОД в штатном режиме);
  - средний размер ответа **8 КБ**; короткие HTTP/JSON-запросы;
  - топ-5 партнёров дают ~60 % трафика; хвост — сотни мелких партнёров
    по 1–10 RPS;
  - прогноз роста **+30 % трафика в год**;
  - соединения stateless (REST, без «прилипания» на уровне приложения);
    backend-сервисы — внутренние ВМ/поды в каждом ЦОД.
- Backend-сервисы API разворачиваются в обоих ЦОД (active/active);
  внутренняя маршрутизация между ними — вне scope задачи.

### 2.4 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД с DMZ; внешняя балансировка — только существующий GSLB (DNS) и L4-балансировщики DMZ; новых сетевых механизмов (anycast, stretched L2) не вводить |
| INF-02 | Виртуальные машины: 8 vCPU / 16 ГБ RAM / 100 ГБ диск, ОС **SberLinux OS Server 8.10**; под edge-контур выделяется до **3 ВМ на ЦОД**; правило банка: один СПО на ВМ |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, внутренний контур); доступ из DMZ — через межсетевой экран по заявке; SecMan в банке не используется |
| INF-04 | Мониторинг банка — **Prometheus + Grafana** (pull-модель); журналирование — централизованный **SIEM**, приём по syslog; шина Kafka есть, но форвардинг в неё выполняют внешние агенты (RSYSLOG/fluentbit) |
| INF-05 | Перед DMZ уже работает **существующий WAF-контур** банка (отдельное решение); функции WAF от SynGX не требуются и не должны дублироваться |
| INF-06 | **Авторизационный сервер банка** (OAuth2/OIDC, выдача JWT access token партнёрам) существует и эксплуатируется отдельной командой; его доработка вне scope задачи |
| INF-07 | Клиентские сертификаты партнёров выдаёт **УЦ банка**; реестр допущенных CN/SAN ведёт ИБ (поставляется в конфигурацию через корпоративный GitOps) |
| INF-08 | Все изменения конфигурации — только через корпоративный GitOps-репозиторий (Ansible) с code review; ручной доступ к ВМ DMZ — через PAM |
| INF-09 | Окно плановых работ в DMZ: ночь 02:00–04:00 МСК, не чаще раза в месяц |
| INF-10 | Команда сопровождения edge-контура: 2 инженера DMZ/сети, 1 инженер ИБ, 1 DevOps; компетенции по Nginx — средние, по SynGX — отсутствуют |

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность партнёрского API в операционное время (05:00–01:00 МСК) | ≥ 99,95 % в год |
| NFR-02 | Полная потеря ЦОД: переключение трафика партнёров на второй ЦОД | автоматически через GSLB, RTO ≤ 15 мин |
| NFR-03 | Пиковая нагрузка на edge-контур | 6 000 RPS суммарно + 30 % запас; добавочная латентность прокси p99 ≤ 20 мс |
| NFR-04 | Лимиты по тарифам партнёра: «Старт» 50 r/s, «Стандарт» 300 r/s, «Премиум» 1 000 r/s | превышение → отказ с кодом 429; для новых партнёров первый месяц — режим «только наблюдение» (dry-run) |
| NFR-05 | Защита backend-узлов от каскадного отказа при деградации группы (часть узлов выведена healthcheck) | лимит нагрузки на каждый узел группы |
| NFR-06 | Изменение лимита конкретного партнёра (например, временное повышение на маркетинговую кампанию) | без перезагрузки и разрыва соединений, ≤ 5 мин, с автоматическим возвратом к исходному значению |
| NFR-07 | Плановые изменения конфигурации edge-контура | без разрыва установленных соединений клиентов |
| NFR-08 | Наблюдаемость по каждому партнёру: RPS, коды ответов, срабатывания лимитов | задержка данных ≤ 1 мин, выгрузка в Prometheus/Grafana банка |
| NFR-09 | Доставка access-логов и событий аудита в SIEM | ≤ 5 мин |
| NFR-10 | Масштабирование под рост +30 %/год | горизонтально, без перепроектирования схемы |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | TLS для всех соединений: партнёр ↔ edge, edge ↔ backend, edge ↔ Vault; версии протокола не ниже 1.2, для внешнего контура предпочтительно 1.3 |
| SEC-02 | Аутентификация партнёров на edge по **mTLS**: проверка CN/SAN клиентского сертификата из УЦ банка по реестру ИБ |
| SEC-03 | Проверка OAuth2 access token (JWT) на edge **до** проксирования к backend: подпись, срок действия, scope; выдача токенов — внешний авторизационный сервер (INF-06) |
| SEC-04 | Закрытые TLS-ключи edge-контура **не должны храниться файлами на ВМ в DMZ**; источник сертификатов — Vault банка (INF-03) |
| SEC-05 | Аудит событий идентификации/авторизации и изменений конфигурации; выгрузка в SIEM |
| SEC-06 | Служебные эндпоинты (метрики, управление лимитами, ИИ-агент) — только из внутреннего контура банка / loopback, с TLS и ограничением по адресам |
| SEC-07 | Ротация TLS-сертификатов автоматически, без остановки обслуживания; контроль сроков действия с оповещением |
| SEC-08 | В ответах наружу не раскрываются технические детали (имя и версия прокси-сервера, внутренние имена backend-узлов) |
| SEC-09 | Запрет debug-уровня журналирования в промышленном контуре |
| SEC-10 | Весь административный доступ к ВМ — персонализированный, через PAM (INF-08) |

### 2.7 Модель монетизации `[BENCH]`

- Тарифы «Старт» (бесплатный), «Стандарт», «Премиум» — платная
  подписка; превышение лимита тарифа → отказ 429 (овердрафта нет).
- Для биллинга (внешняя система финансового контура, вне scope задачи)
  ежемесячно требуются: число запросов по каждому партнёру, число и
  длительность превышений лимита, распределение кодов ответов.
- Маркетинговые кампании: временное повышение лимита партнёра на срок до
  нескольких дней с автоматическим возвратом (NFR-06).

### 2.8 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами.
- Решение должно быть реализуемо силами команды INF-10 с использованием
  документированных механизмов продукта и корпоративного GitOps.
- Комитет особенно чувствителен к двум вопросам: (1) **не приписаны ли
  SynGX функции, которых в продукте нет** (API-management, WAF,
  кластеризация); (2) как решение выполняет NFR-06 (горячее изменение
  лимитов) без ущерба SEC-06.

### 2.9 Что можно принять допущением `[ASSUME]`

- GSLB банка корректно исключает недоступный ЦОД за время ≤ 5 мин
  (TTL/health-check на стороне GSLB); детали — вне scope.
- Backend-сервисы выдерживают пиковую нагрузку при исправном
  edge-контуре; их ёмкость — вне scope.
- Авторизационный сервер (INF-06) предоставляет JWKS/ключи проверки
  подписи JWT по защищённому каналу; формат интеграции — предмет
  отдельного согласования.
- Каталог API / портал разработчика банк планирует внедрять отдельным
  проектом; в рамках этой задачи требуется только не блокировать его
  появление и определить интеграционные границы.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| Edge-контур | слой обратного прокси на границе периметра банка (DMZ), принимающий внешние запросы партнёров |
| upstream | группа backend-узлов, на которую SynGX проксирует запросы |
| mTLS | взаимная аутентификация TLS: клиент предъявляет сертификат |
| JWT / JWKS | формат access token OAuth2 / набор открытых ключей проверки подписи |
| leaky bucket | алгоритм ограничения скорости запросов (limit_req) |
| DRAIN | состояние узла: новые соединения не принимаются, существующие доживают |
| GSLB | глобальная балансировка между площадками через DNS |
| fail-closed | при недоступности всех backend-узлов точка входа разрывает соединения |
| pull-модель метрик | система мониторинга сама опрашивает эндпоинты SynGX |
| dry-run (limit_req) | режим, в котором превышения только фиксируются, но не отклоняются |
