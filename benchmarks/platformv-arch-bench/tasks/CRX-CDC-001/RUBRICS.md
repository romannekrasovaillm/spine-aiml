# Рубрики оценки для задачи CRX-CDC-001

## 1. Общие правила для судей

1. **Порядок:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить HF §2;
   (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из ответа;
   (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Pangolin
   или Corax, которого нет в §1 и которое не помечено решающим как
   допущение, считается **непроверенным**; если оно ещё и ложно —
   **ложным**. Не «додумывать» за решающего.
3. **«Упомянул ≠ применил»** — балл за решение, привязанное к требованию
   (INF/NFR/SEC) и обоснованное, а не за ключевое слово.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 —
   базово корректно, есть пробелы; 3 — полно, мелкие недочёты; 4 —
   образцово, с учётом компромиссов и ловушек §4.
5. **Цитирование:** 1–3 цитаты (≤ 25 слов) на критерий + чего не хватает
   до следующего уровня.
6. Режим прогона фиксирован: `agentic` (см. `run_mode_adjustments`).
   Стиль и объём сверх C10 не оцениваются.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
оцениваются для диагностики. «Только судья» = regex-детектор ненадёжен.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | pgcopydb `follow` предложен как промышленный CDC-механизм вопреки документированным ограничениям: заявлено, что follow переживает рестарт БД, работает с TDE (в сценарии TDE включена), либо не требует superuser на приёмнике; либо follow назначен основным CDC без явной огласки этих ограничений | Сверка с CONTEXT §1.5; regex-кандидаты в §9. Только судья |
| HF-02 | Строгий **глобальный** порядок событий (по всему топику / всем счетам) заявлен как штатно достижимый, либо требование ordering по счёту «закрыто» без ключей сообщений и партиционирования | Семантика раздела D4; CONTEXT §1.8. Только судья |
| HF-03 | Заявлен RPO = 0 при потере ЦОД-1 для событийного контура при асинхронной межкластерной репликации (MM2), либо MM2 назван синхронным механизмом | A-06, regex-кандидаты в §9; CONTEXT §1.11 |

| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01 (механические паттерны) |

## 3. Критерии

### C1. Фактическая корректность по Pangolin CDC и Corax (вес 15)

**Что оценивается:** соответствие утверждений о продуктах CONTEXT.md §1;
корректные наименования; отделение фактов от допущений и вопросов к
вендору.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01 или HF-04, либо ≥ 4 ложных утверждений о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (wal2json, слоты, идемпотентность, Records Policy, MM2), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами §1 помечено допущением или подтверждено ссылкой с разрешённых доменов; различаются логическая репликация (подписка) и логическое декодирование (слот + плагин вывода), test_decoding и wal2json, внутрикластерная репликация и MM2; пробелы съёма (судьба слотов при failover, GDL, wal2json+TDE, имя LSN-rewind-расширения) честно помечены как вопросы к вендору |

**Признаки сильного ответа:** официальные имена (`pangolin-dbms`, Pangolin
Manager/DCS/Pooler, wal2json, test_decoding, pgcopydb, Platform V GraDeLy,
Apache Kafka, Apache ZooKeeper, Corax Schema Registry, Corax UI, Corax
Mirror Maker 2, Records Policy); версия ядра Kafka не заявлена как факт;
«13 000 tps» не подан как гарантия; GraDeLy не наделён выдуманными
характеристиками.

**Типичные ошибки:** «pgcopydb follow — штатный промышленный CDC»;
«test_decoding рекомендован для прода»; «wal2json включается без
рестарта»; «слот переживает failover сам»; «GraDeLy поставляется с Corax».

### C2. Архитектура CDC-захвата из Pangolin (вес 15)

**Что оценивается:** D3. Выбор и обоснование механизма захвата, слоты и их
жизненный цикл, REPLICA IDENTITY, включение `wal_level=logical` в условиях
INF-08, поведение при failover/рестарте СУБД, права ТУЗ.

| Уровень | Якорь |
|---|---|
| 0 | Нет раздела или выбран pgcopydb follow без огласки ограничений (HF-01) |
| 2 | Механизм выбран (например, wal2json + коннектор), но: REPLICA IDENTITY для UPDATE/DELETE не учтён; путь включения `wal_level=logical` в проме не увязан с INF-08 (рестарт лидера); судьба слота при failover проигнорирована (не помечена даже как вопрос); права ТУЗ не описаны |
| 4 | (a) осознанный выбор одного механизма с отвергнутыми альтернативами: pgcopydb follow отвергнут по документированным ограничениям (TDE, рестарт, superuser — §1.5), test_decoding отвергнут как тестовый модуль (§1.4), GDL отложен как отдельный продукт без документации и лицензии (§1.6, INF-09) — оформлен вопросом к вендору/бюджетным запросом; (b) конфигурация wal2json привязана к сценарию: `format-version` выбран (с учётом TRUNCATE при v1), `filter-tables`/`add-tables` под 40 таблиц, `include-xids`/`include-lsn`/`include-pk` для дедупликации и ordering; (c) REPLICA IDENTITY для старых версий строк UPDATE/DELETE; (d) включение `wal_level='logical'` спланировано через квартальное окно/регламентный switchover (INF-08), а не «перезапустим когда-нибудь»; (e) судьба слота при failover лидера — явный риск с runbook-ом (пересоздание слота, LSN-rewind как кандидат с пометкой [ТРЕБУЕТ ПРОВЕРКИ]) и вопросом к вендору; (f) ТУЗ CDC с минимальными правами (SEC-03) |

**Ловушки:** «pgcopydb follow решит CDC»; «включим wal_level=logical на
ночь» без окна; «слот репликации отработает failover как в физической
репликации»; CDC-ТУЗ = postgres.

### C3. Гарантии доставки и сквозной ordering (вес 14)

**Что оценивается:** D4, NFR-02, NFR-03, NFR-06, NFR-07.

| Уровень | Якорь |
|---|---|
| 0 | Нет конфигурации гарантий; HF-02 |
| 2 | `acks=all`, идемпотентность, ключи названы, но: границы гарантий end-to-end не зафиксированы; дедупликация отсутствует; стыковка «порядок коммитов в слоте → порядок в партиции» не описана |
| 4 | Продюсер CDC-звена: `acks=all` + RF 3 + `min.insync.replicas=2` + `enable.idempotence=true` (с требованиями `max.in.flight.requests.per.connection ≤ 5`, `retries > 0`); явно зафиксировано, что идемпотентность действует в пределах сессии продюсера, поэтому end-to-end дедупликация — на потребителе по бизнес-ключу из события (xid/LSN из wal2json — §1.3) → NFR-07 с честной границей; ordering: ключ сообщения = счёт/договор, порядок гарантируется внутри партиции, ретраи с идемпотентностью порядок не ломают, потребителей ≤ партиций, при ребалансировке обработка завершается до коммита (ручной коммит, `pause` при фоновой обработке) → NFR-06; транзакционный продюсер + `read_committed` там, где события одной БД-транзакции должны читаться атомарно; глобальный порядок явно отвергнут как нетребуемый (NFR-06) |

**Ловушки:** «exactly-once end-to-end из коробки»; `retries>0` без
идемпотентности; auto-commit в контуре антифрода; «порядок по топику».

### C5. Деградация звеньев и DR (вес 12)

**Что оценивается:** D6, NFR-04, NFR-05, NFR-10.

| Уровень | Якорь |
|---|---|
| 0 | Нет матрицы сбоев; HF-03 |
| 2 | Сценарии перечислены, но бюджет WAL не посчитан; failover лидера Pangolin сведён к «Manager сам переключит» без судьбы слота; DR-переключение потребителей не описано |

**Ловушки:** «MM2 синхронный»; «слот бесконечно подождёт»; RTO ЦОД «5
минут» с ручным promote и пересозданием слота внутри; догон 4-часового
накопленного без ограничения скорости.
