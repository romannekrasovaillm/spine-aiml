## 1. Продукты `[DOC]`

### 1.1 Pangolin DB: позиционирование, редакции, HA-контур

- **Platform V Pangolin DB** — «специальная сборка PostgreSQL» с
  доработками под безопасность, доступность, надёжность и эксплуатацию;
  OLTP-СУБД, не MPP: «для задач аналитики рекомендуется использовать
  специализированные продукты» (аналитический профиль линейки — Platform V
  DataMarts).
- Редакции: **Standard / Standard для ERP / Enterprise / Enterprise для
  ERP**. Только Enterprise (и «для ERP»): **TDE** (прозрачное защитное
  преобразование данных), защита данных от привилегированных пользователей,
  интеграция с KMS HashiCorp Vault, глобальные индексы, нативное
  интервальное партиционирование, **pgloader**, **pgcopydb**.
- HA-кластер: **Pangolin Manager** (оркестратор; в документации
  поставляется Patroni 4.1.1, `pangolin-manager-ctl` — patronictl-подобный
  CLI) + **Pangolin DCS** (распределённое хранилище конфигурации на базе
  Raft) + **Pangolin Pooler** (форк PgBouncer). Заявленные целевые
  показатели: RPO = 0, RTO = 6 минут простоя в год.
- Репликация физическая, потоковая, однопоточная; один лидер. Режимы:
  асинхронный (дефолт), стандартная синхронная PostgreSQL, нестрогий
  синхронный Manager (`synchronous_mode: true`, деградация в async при
  потере реплики), строгий синхронный (`synchronous_mode_strict: true`).
  Операции `pangolin-manager-ctl`: `switchover` (плановое, «гарантия
  нулевых потерь даже в async»), `failover`, `reinit`, `pause`/`resume`.
- DR на 2 ЦОД: standby-кластер (секция `standby_cluster` при бутстрапе).
  Автоматическое повышение standby при двух ЦОД **невозможно** (DC2 не
  отличает сбой DC1 от сетевого разделения) → ручной promote удалением
  секции `standby_cluster` из динамической конфигурации (НЕ
  `pg_ctl promote`), перед promote — STONITH основного. **Слот репликации
  на первичном кластере для standby-кластера необходимо создать вручную —
  «это не будет сделано автоматически»** (допустимы постоянные слоты
  Patroni). **DCS failsafe mode**: при полной недоступности DCS кластер
  продолжает работать, если все узлы видят лидера через его REST API.

### 1.2 Pangolin DB: логическая репликация (публикация/подписка) и слоты

- Логическая репликация — репликация объектов данных и их изменений на
  основе идентичности реплики (обычно первичного ключа); модель
  «публикация/подписка» с каскадированием. При старте — снимок таблицы на
  подписчик, далее поток изменений. **«Подписчик применяет данные в том же
  порядке, что и издатель, что гарантирует транзакционную согласованность
  для публикаций в рамках одной подписки»** (транзакционная репликация).
  Поддерживается репликация между разными мажорными версиями и платформами.
- **Доработки Pangolin** — параметры управления слотами синхронизации
  логической реплики для оркестратора (Pangolin Manager):
  - `drop_repl_sync_slots_only_after_restart` (boolean, default `true`):
    не описанные в DCS-конфигурации слоты синхронизации удаляются только
    после рестарта СУБД; настройка через `pangolin-manager-ctl edit-config`;
  - `forbid_create_pg_sync_slots_by_user` (boolean, default `false`): при
    `on` запрещает пользователю создавать слоты с именем по шаблону
    `pg_N_sync_N_N`.
- Судьба **пользовательских** слотов логического декодирования при failover
  лидера (перенос на нового лидера, потеря позиции) в съёме документации
  **не описана** — [ТРЕБУЕТ ПРОВЕРКИ] у вендора.

### 1.3 Pangolin DB: плагин логического декодирования wal2json

- «Для реализации возможности логической репликации в формате JSON в состав
  продукта дополнительно включен плагин вывода для логического
  декодирования — **wal2json**».
- Плагин имеет доступ к кортежам INSERT и UPDATE; «доступ к UPDATE/DELETE
  старым версиям строк (row) возможен в зависимости от настроенного
  идентификатора реплики» (REPLICA IDENTITY). Изменения применяются через
  протокол потока изменений (слоты логической репликации) или через
  специальный SQL API.
- Два формата вывода (`format-version`): **1** — объект JSON на транзакцию
  (все новые/старые кортежи в одном объекте); **2** — объект JSON на
  кортеж. Ограничение: при `format-version = 1` действие TRUNCATE не
  включается в поток («для поддержания обратной совместимости»).
- Параметры плагина при подключении к слоту (выборка): `include-xids`,
  `use-xid32` (32-битный xid; доработка Pangolin), `include-timestamp`,
  `include-schemas`, `include-types`, `include-pk`, `include-lsn`,
  `include-transaction`, `write-in-chunks`, `filter-tables` / `add-tables`
  (по умолчанию — все таблицы всех схем), `actions` (INSERT/UPDATE/DELETE/
  TRUNCATE).
- **Требование: `wal_level = 'logical'`; «после смены значения этого
  параметра требуется перезапустить сервер Pangolin»**.

Источник: corpus/pv_docs/txt/psq_documents__administration-guide__administration-pangolin-pooler__support-data-center-topology.html.txt; banking/plugins/ru-data/skills/pangolin-db-architecture/references/migration-cdc.md

### 1.4 Pangolin DB: модуль test_decoding

- Модуль `test_decoding` — **«пример модуля вывода логического
  декодирования»**, «отправная точка для разработки собственного модуля
  вывода»; в исходном дистрибутиве установлен по умолчанию.
- Работа: получение WAL через логическое декодирование → текстовое
  представление операций (BEGIN/INSERT/DELETE/COMMIT с lsn, xid).
  Интерфейс — SQL, например `pg_logical_slot_get_changes('slot', NULL,
  NULL, 'include-xids', '0')`. Доработка Pangolin: параметр `use-xid32`.
- Ограничение: `wal_level` должен быть `logical`, иначе ошибка
  `ERROR: logical decoding requires wal_level >= logical`.

### 1.5 Pangolin DB: pgcopydb и его CDC-режим follow

- **pgcopydb 0.14** — 3rd Party часть дистрибутива; функциональность
  **только для редакций Enterprise**. Назначение: полная миграция БД между
  PostgreSQL-совместимыми кластерами + клиент логического декодирования
  (CDC-режим `follow` после снапшота; совместим с test_decoding и wal2json,
  дефолтный модуль — test_decoding).
- **Документированные ограничения (раздел «Ограничения»):**
  - «утилита не запрашивает пароль для части команд» — пароль параметром
    или беспарольная аутентификация; **работа с хранилищем паролей не
    поддерживается**;
  - при полной миграции набор расширений источника и приёмника должен быть
    **абсолютно идентичен в части версий и настроек GUC**;
  - **«заявленная возможность follow, позволяющая реализовать CDC, упадет
    в ошибку, если одна из БД по какой-либо причине будет перезапущена»**;
  - follow требует **прав суперпользователя в БД-приёмнике** (выполняется
    `SET session_replication_role`);
  - **«заявленная возможность follow не работает с TDE»**.
- Последовательности логическим декодированием не обрабатываются —
  синхронизируются отдельно в конце операции.

### 1.7 Corax: состав, ядро, координационный слой, HA

- «Программный брокер сообщений… распределенная, отказоустойчивая,
  реплицированная и легко масштабируемая система передачи сообщений»;
  «все сообщения Platform V Corax хранит на диске».
- Состав (KFKA): **Apache Kafka** (обязателен), **Apache ZooKeeper**,
  **Corax Schema Registry**, **Corax UI**, **Corax Mirror Maker 2** (трое
  последних опциональны). Добавленная ценность против ванильного Kafka:
  Schema Registry, Corax UI, **Auto Data Balancer**, мониторинг (consumer
  lag, Prometheus exporter), Ansible-роль, функции безопасности данных,
  патчи без CVE, поддержка; заявлены kTLS и SecMan.
- Ядро — Apache Kafka; «наследуя архитектуру **Apache Kafka 3.9**»
  поддерживает exactly-once транзакции. Точная версия ядра в 16.392.0 —
  [ТРЕБУЕТ ПРОВЕРКИ]. Идемпотентный и транзакционный продюсер — начиная с
  Corax 5.272.0. Java: OpenJDK/SberJDK **17 и 21**; OpenJDK 11 с 16.392.0
  не поддерживается.
- Координация: ZooKeeper-ансамбль **или** KRaft-контроллеры (шаг 2
  Ansible-установки — «kraft controller или zookeeper»). ZooKeeper:
  «минимальное число узлов… — 3», «только нечетное количество узлов».
  Детальные страницы конфигурации KRaft в съём не вошли —
  [ТРЕБУЕТ ПРОВЕРКИ].
- **Ожидаемая доступность 99,9 %** при условиях: каждый компонент на
  отдельном хосте, фактор репликации ≥ 3, `min.insync.replicas` ≥ 2;
  rolling update без простоя; `unclean.leader.election.enable=false`.
  При отказе брокера лидеры партиций переназначаются из ISR.
  Corax-специфичный `auto.leader.rebalance.on.not.isr.broker.enable=false`
  — брокер с несинхронизированными репликами не участвует в выборах лидера
  (защита от «дискового шторма»). **Auto Data Balancer**: режимы
  `--generate`/`--execute`/`--auto`; авто — только в технологическое окно.

### 1.8 Corax: гарантии доставки (продюсер и потребитель)

- **acks**: `0` — без подтверждения, retries не работают; `1` — лидер
  записал локально, при его отказе до репликации на ISR «запись будет
  потеряна»; `all` (=-1) — все ISR, «самая надежная из доступных
  гарантий»; для идемпотентности обязателен `acks=all`.
- **retries**: повторы без `max.in.flight.requests.per.connection=1`
  могут изменить порядок записей; «включение параметра retries может
  привести к задвоению данных».
- **Идемпотентный продюсер** (`enable.idempotence=true`): «усиливает
  семантику доставки… с at least once до exactly once». Требования:
  `max.in.flight.requests.per.connection ≤ 5`, `retries > 0`, `acks=all`.
  Оговорки: гарантия «только для сообщений, отправленных в одной сессии»;
  **повторные отправки на уровне приложения идемпотентность не отменяют**.
- **Транзакционный продюсер** (`transactional.id`, идемпотентность
  включается автоматически): атомарная запись в несколько партиций/топиков.
  Рекомендация вендора: `replication.factor = 3` и
  `min.insync.replicas = 2` — «оптимальная для большинства случаев»;
  транзакции по умолчанию требуют ≥ 3 брокеров.
- **Потребитель**: `isolation.level=read_committed` — чтение только
  зафиксированных транзакционных сообщений до LSO. Фиксация смещений: авто
  (`enable.auto.commit=true`, дефолт 5000 мс) или вручную
  `commitSync()`/`commitAsync()`; точка восстановления после сбоя —
  committed position. При ребалансировке «все потребители приостанавливают
  чтение». Рекомендация вендора при непредсказуемом времени обработки:
  обработка в отдельном потоке, автофиксация выключена, ручной коммит
  после обработки, `pause` партиции. Группы: партиция — ровно одному
  потребителю группы; потребителей в группе ≤ числа партиций (лишние
  простаивают); групп на топик любое число.

### 1.9 Corax: Schema Registry и Records Policy

- Централизованное хранилище схем + serdes. Форматы: по `sr-overview` —
  Avro, JSON Schema, Protobuf; по `sr-concepts` — Avro и JSON (расхождение
  зафиксировано; Protobuf — [ТРЕБУЕТ ПРОВЕРКИ]). **Serdes — только Java**.
- «Работает по принципу Active-Active», георезервирование; ставится
  отдельно от брокеров. Хранение — топик **`_crx_schemas`** (1 партиция,
  `cleanup.policy=compact`): «Параметры менять запрещено».
- **Records Policy** — проверка соответствия сообщений схеме **на стороне
  брокера**; «НЕ ВХОДИТ в состав Apache Kafka и доступен только при
  использовании Corax».
- Совместимость: **BACKWARD** (дефолт, не транзитивный; порядок обновления
  «сначала потребители»), BACKWARD_TRANSITIVE, FORWARD, FORWARD_TRANSITIVE,
  FULL, FULL_TRANSITIVE, NONE (без проверок). В не-TRANSITIVE режимах
  совместно работают версии схемы, различающиеся не более чем на 1. При
  несовместимом изменении — одновременное обновление всех клиентов или
  новый топик («предпочтительный вариант»).
- Серверная валидация JSON-схем **по умолчанию отключена** (включается
  `schema.registry.rest.schemas.custom.checks=true`; отказ — HTTP 422).
- Безопасность SR: HTTP Basic (пароли только зашифрованные); ACL, роли
  ADMIN / ADMIN_AS / USER. Рекомендация вендора: «всегда начинайте с
  Schema Registry».

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/security-schema-registry.md; corpus/pv_docs/txt/kfk__documents__schema-registry__sr-architecture.html.txt

### 1.10 Corax: топики MessagePack и Platform V GraDeLy

- **«Для обмена сообщениями в формате MessagePack должен использоваться
  отдельный топик, в который не пишутся сообщения в других форматах. Иначе
  сообщения будут некорректно десериализованы потребителем»** (прямое
  ограничение документации).
- По умолчанию поставляется класс-десериализатор для сообщений от
  **Platform V GraDeLy**: `ru.gradely.serialization.TrailFileDeserializer`
  (опция `--value-deserializer` у `kafka-console-consumer.sh`). Т.е. штатный
  формат CDC-событий GDL в Corax — MessagePack-топики.

### 1.11 Corax: MM2, S3-архив, квоты, лимиты, мониторинг

- **Corax Mirror Maker 2 (MM2)** — репликация данных и метаданных между
  кластерами на платформе Kafka Connect; **«отличается от механизма
  внутрикластерной репликации в Kafka»** (т.е. асинхронная). Коннекторы:
  Source/Sink, Checkpoint (синхронизация offsets между кластерами),
  Heartbeat, Config. Реплицирует сообщения, метаданные топиков, группы
  потребителей, контрольные точки смещений, **ACL**. Топологии
  Active-Active / Active-Standby; есть метрики лага репликации. Детальные
  сценарии MM2 в съём не вошли — [ТРЕБУЕТ ПРОВЕРКИ].
- **Бэкап в S3**: Kafka Connect + доработанный плагин Lenses Stream
  Reactor: sink-коннектор (выгрузка) и source-коннектор (восстановление),
  правила KCQL, `EncryptedByteArrayConverter`, DLQ, управление через REST
  API. НФТ: «архивирование и восстановление данных выходят за рамки функций
  Corax… Исключение — облачные хранилища S3».
- **Quota Management**: «встроенное квотирование пропускной способности по
  клиентам». Лимиты: `max.message.bytes` по умолчанию 5 МБ (брокер
  отклоняет превышающие), `max.request.size` 1 МБ, `fetch.max.bytes` 50 МБ,
  `max.partition.fetch.bytes` 1 МБ.
- Минимальное железо (пром): брокер 4 CPU / 16 ГБ / 200 ГБ; контроллер
  ZK/KRaft 4 / 4 ГБ / 64 ГБ; Schema Registry и Corax UI по 2 CPU / 1 ГБ
  heap / 32 ГБ. Каждый компонент — отдельный хост; диски RAID10 + XFS.
  «Включение SSL значительно увеличивает утилизацию процессора».
- Профиль нагрузки вендора: **13 000 tps** при среднем сообщении 10 000
  байт на тестовом стенде (3 брокера, топик 20 партиций, RF 3, `acks=1`,
  `min.insync.replicas=1` — параметры **теста**, не рекомендация для
  прода). Вендор рекомендует нагрузочное тестирование.
- Мониторинг: **HTTPReporter** (`ru.sbrf.kafka.HttpReporter`), метрики
  Prometheus, порт 7011 (HTTP) / 7012 (HTTPS). «Здоровые» значения:
  `ActiveControllerCount` = 1, `OfflinePartitionsCount` = 0,
  `UnderReplicatedPartitions` = 0, `UncleanLeaderElectionsPerSec` = 0.
  Consumer lag: клиентская `records-lag-max`; координаторские
  `offset.metadata.group.*` и `timestamp.metadata.group.*`. JMX по
  умолчанию выключен; в PROD — только с аутентификацией.
- Установка — штатной **Ansible-ролью** (инвентарь `inv/stand-corax.yml`,
  профили безопасности, критерий успеха `unreachable=0 failed=0`).

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/cluster-ha.md; corpus/pv_docs/txt/kfk__documents__mm2__architecture.html.txt

### 1.12 Corax: безопасность

- **Каналы**: TLS 1.2/1.3, mTLS, настраиваемые cipher suites (все связки,
  включая брокеры↔брокеры и Schema Registry/Corax UI/ZooKeeper).
  Требование: TLS ≥ 1.2, рекомендуется 1.3.
- **Аутентификация**: X.509 (в т.ч. `FingerprintKafkaPrincipalBuilder`,
  принципал по отпечатку сертификата); Kerberos (SASL/GSSAPI, keytab).
- **ACL**: ресурсы CLUSTER, GROUP, TOPIC, TRANSACTIONAL_ID,
  DELEGATION_TOKEN, USER; ALLOW/DENY; управление через Corax UI и CLI;
  JMX-метрики авторайзера `ru.sbrf.kafka.authorizer:type=CoraxAuthorizer`.
- **Аудит**: встроенный плагин (`kafka.se.audit.enable`, дефолт true):
  топики, ACL, конфигурации, перераспределение партиций, группы, квоты.
  Провайдеры: `TsAuditProvider` — в компонент **COTE** продукта Platform V
  Monitor по HTTPS; `LogAuditProvider` — файл `kafka-audit.log`. Фильтры
  `kafka.se.audit.suppress.*`.
- **Сквозное (e2e) шифрование** — на клиенте, «не зависит от настройки
  соединения с брокерами»: симметричное (`EncryptedByteArraySerializer`,
  ключ + соль ≥ 16 байт) и асимметричное (`EncryptedCertByteArraySerializer`,
  RSA/ECB/PKCS1Padding, только кодом). Сериализаторы — Java (см. §1.9).
- **Пароли в конфигурациях**: `crx-encoding.sh` /
  `crx-password-encrypt.sh` (PBKDF2WithHmacSHA1 + AES-256); ConfigProvider
  `${имя:пароль}`. Дефолтный пароль инсталлятора `qwe123` — заменить
  обязательно.
- **SecMan** (СберТех): хранение секретов, выпуск сертификатов из PKI;
  заявлен Vault Java Driver. kTLS — [ТРЕБУЕТ ПРОВЕРКИ].
- **SSL live update**: ротация сертификатов без недоступности — по одному
  брокеру, после запуска ждать `--under-replicated-partitions` = 0.

Источник: banking/plugins/ru-integration/skills/corax-event-streaming/references/security-schema-registry.md; corpus/pv_docs/txt/kfk__documents__administration-guide__audit.html.txt

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Окский Вектор"» (вымышленный, топ-30 по активам) переводит
карточный контур на потоковую модель данных. Система-источник — АС
«Карт-Процессинг» (авторизация и клиринг по картам, лимиты, справочники
договоров) на СУБД **Platform V Pangolin DB 8.2.0 (редакция Enterprise,
включена TDE)**. Изменения из ~40 бизнес-таблиц должны потоково попадать в:

1. **Антифрод-систему «Сокол»** — скоринг авторизаций в near-real-time;
   критичны задержка и порядок событий по счёту/договору (история операций
   счёта читается последовательно).
2. **DWH-витрины** (операционная витрина, витрина лимитов) — загрузка
   потоком; допустим лаг до 10 минут; не должна деградировать антифрод.
3. **Контур аудита операций** — неизменяемый поток всех изменений для
   внутреннего расследования инцидентов и регуляторных запросов.

Поток классифицирован как критичный: сбой публикации событий > 30 минут —
инцидент с регуляторными последствиями (ориентир — 719-П); события
содержат ПДн и данные карт (часть полей передаётся в открытом виде внутри
контура). Целевой брокер утверждён: **Platform V Corax 16.392.0**.

### 2.2 Ландшафт AS-IS

- АС «Карт-Процессинг»: кластер Pangolin 8.2.0 Enterprise (ЦОД-1: лидер +
  синхронная реплика; ЦОД-2: standby-кластер из 2 узлов), под управлением
  Pangolin Manager + Pangolin DCS + Pangolin Pooler. `wal_level` сейчас
  `replica`.
- БД: **14 ТБ**, ~1 800 таблиц; CDC-контур — 40 таблиц (операции, лимиты,
  договоры, справочники статусов), из них 6 «тяжёлых» (до 900 млн строк).
- Сегодня: ночные файловые выгрузки (ETL) в DWH и пакетная передача в
  антифрод каждые 15 минут; дубли при ретраях выгрузок; порядок событий по
  счёту не гарантирован; повторное проигрывание невозможно.
- CDC-звена нет; команда middleware эксплуатирует Corax для другого
  контура (уведомления ДБО) — кластер из 3 брокеров в ЦОД-1 без
  межкластерной репликации (подлежит перепроектированию или замене новым
  контуром — решение архитектора).

### 2.3 Нагрузка и объёмы

- АС «Карт-Процессинг»: средняя OLTP-нагрузка **4 800 TPS**, вечерний пик
  **12 000 TPS** (по кластеру целиком).
- CDC-события по 40 таблицам: среднее **2 200 событий/с**, пик
  **8 500 событий/с**; рост **+30 % в год** на 5 лет.
- Средний размер CDC-события **3 КБ**; ночной клиринг генерирует всплески
  до **40 000 событий/с в течение 20 минут**.
- Топики: ~15 доменных (группы таблиц), до 50 с учётом окружений и
  служебных (DLQ).
- Потребители: антифрод (p99 доставки «коммит в Pangolin → событие у
  потребителя» ≤ 5 с), DWH (лаг ≤ 10 мин), аудит (лаг ≤ 60 мин, но без
  потерь и с доказуемой полнотой).
- Онлайн-хранение в топиках — **7 дней**; регуляторный архив событий
  аудита — **5 лет** с восстановлением потока на дату.

### 2.5 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность сквозного pipeline (захват → топик → потребитель) | ≥ 99,9 % в год (24×7) |
| NFR-02 | Потеря подтверждённых CDC-событий при отказе брокера/СУБД-узла внутри ЦОД | 0 |
| NFR-03 | Сквозная задержка «коммит в Pangolin → событие у антифрода» | p99 ≤ 5 с при пике |
| NFR-04 | RPO при полной потере ЦОД-1 (событийный контур) | ≤ 5 мин (честно оценить и обосновать) |
| NFR-05 | RTO при полной потере ЦОД-1: pipeline восстановлен, включая возобновление CDC-захвата | ≤ 60 мин (ручные действия допустимы, runbook обязателен) |
| NFR-06 | Упорядоченность | строгий порядок событий в пределах счёта/договора, включая ретраи коннектора и ребалансировки потребителей; глобальный порядок не требуется |
| NFR-07 | Дубли у потребителей | финансовые эффекты применяются потребителями не более одного раза; границы гарантий зафиксированы явно |
| NFR-08 | Изоляция нагрузки | DWH- и аудит-контуры не деградируют доставку в антифрод более чем на 5 % |
| NFR-09 | Хранение | 7 дней онлайн в топиках; архив аудита 5 лет; восстановление потока на дату ≤ 24 ч |
| NFR-10 | Деградация при недоступности Corax | при недоступности брокера до 4 ч события не теряются, OLTP-контур АС «Карт-Процессинг» не останавливается и не деградирует (оценить бюджет WAL) |
| NFR-11 | Обновления и ротация сертификатов звеньев pipeline | без простоя (rolling) |
| NFR-12 | Ёмкость | 5 лет роста нагрузки +30 %/год + 30 % запас на дисках брокеров |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | TLS не ниже 1.2 (рекомендовано 1.3) на всех каналах pipeline: Pangolin ↔ CDC-звено, CDC-звено ↔ Corax, брокеры ↔ брокеры, Schema Registry/UI, мониторинг |
| SEC-02 | Аутентификация всех участников; персональный принципал на сервис; анонимный доступ запрещён (включая Schema Registry и Corax UI) |
| SEC-03 | Минимальные права: ТУЗ CDC-захвата на Pangolin — без superuser (либо явное обоснование и компенсирующие меры); ACL в Corax с минимальными правами на топики/группы; wildcard-административные ACL для сервисов запрещены |
| SEC-04 | Аудит всех административных операций над pipeline (топики, ACL, конфигурации, квоты, схемы) с выгрузкой в SIEM банка |
| SEC-05 | ПДн и данные карт в событиях защищаются сквозным шифрованием: администратор платформы и обладатель архива S3 не читают содержимое без ключей |
| SEC-06 | Пароли/секреты в конфигурациях — только зашифрованные; ключи — в Vault банка; дефолтные пароли инсталляторов заменяются |
| SEC-07 | Ротация сертификатов не реже раза в год, без недоступности pipeline |
| SEC-08 | Доступ администраторов персонализированный; их действия попадают в аудит (SEC-04) |

### 2.7 Организационные ожидания `[BENCH]`

- Комитет ожидает **одно рекомендуемое решение** плюс 1–2 отвергнутые
  альтернативы с причинами; реализация силами INF-07 штатной
  Ansible-автоматизацией.
- Особая чувствительность: **выбор CDC-механизма против документированных
  ограничений** (pgcopydb follow при включённой TDE; рестарт СУБД для
  `wal_level=logical` в условиях INF-08) и **честные границы гарантий**
  end-to-end (комитет знает, что идемпотентность продюсера ограничена
  сессией, и ждёт механизм дедупликации, а не слово «exactly-once»).
- Вопросы, не закрытые документацией (см. §1.13), должны быть
  сформулированы как явный список к вендору — это часть ожидаемого
  результата, а не признак неполноты.

### 2.8 Что можно принять допущением `[ASSUME]`

- Точная версия ядра Apache Kafka в Corax 16.392.0 не задана — не
  использовать или пометить как допущение (§1.7).
- CDC-коннектор — новый компонент контура: выбор его реализации
  (самописный на слотах wal2json, Kafka Connect-стек, профильный продукт)
  — предмет проектирования; язык реализации не задан (но serdes Schema
  Registry и e2e-сериализаторы Corax — только Java, §1.9, §1.12).
- Приложение-потребитель допускает доработку: ключи сообщений, стратегии
  фиксации смещений, дедупликация по бизнес-ключу.
- Механика слотов логической репликации (удержание WAL неподтверждённым
  слотом) — общеизвестная механика PostgreSQL; её подтверждение и
  предельные параметры для Pangolin — [ТРЕБУЕТ ПРОВЕРКИ] у вендора, но
  проектировать защиту от роста WAL требуется в любом случае (NFR-10).
- Межцодового канала хватает для репликации пикового потока с запасом
  ≥ 3× (подтверждается расчётом решающего).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| CDC | Change Data Capture — захват изменений из журнала/слотов СУБД |
| Слот (логической репликации) | именованная точка потока логического декодирования WAL с подтверждаемой позицией |
| LSN | Log Sequence Number — позиция в журнале WAL |
| wal2json | плагин вывода логического декодирования Pangolin (JSON на транзакцию/кортеж) |
| ISR / RF | In-Sync Replicas / replication.factor |
| `min.insync.replicas` | минимум ISR для подтверждения записи при `acks=all` |
| LSO | Last Stable Offset — граница чтения при `read_committed` |
| Records Policy | проверка сообщений схеме на стороне брокера (только Corax) |
| MM2 | Corax Mirror Maker 2 — межкластерная репликация на Kafka Connect |
| COTE | компонент аудита продукта Platform V Monitor |
| GDL | Platform V GraDeLy — CDC-продукт линейки СберТеха (не лицензирован в сценарии) |
| ПДн | персональные данные; PAN — номер карты |
| DCS | Pangolin DCS — распределённое хранилище конфигурации кластера (Raft) |
