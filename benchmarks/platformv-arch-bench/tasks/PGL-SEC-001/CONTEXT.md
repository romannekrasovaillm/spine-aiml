## 1. Продукт: Platform V Pangolin DB 8.2.0 `[DOC]`

### 1.1 Позиционирование, поставка, поддерживаемые ОС

- СУБД Pangolin (код продукта PSQ, вендор АО «СберТех», линейка Platform V) —
  реляционная СУБД, **специальная сборка PostgreSQL** с доработками под
  повышенные требования к безопасности хранимых данных, доступности,
  надёжности и удобству эксплуатации.
- Это **OLTP-СУБД, не MPP и не форк Greenplum**: базовая модель — один
  ведущий узел на запись с потоковой физической репликацией. Для
  аналитических (OLAP) нагрузок вендор прямо рекомендует использовать
  специализированные продукты (аналитический профиль линейки — Platform V
  DataMarts). Классы задач из документации: высоконагруженные OLTP,
  «1С:Предприятие» (отдельный отключаемый режим оптимизаций), time-series
  через адаптированный TimescaleDB из дистрибутива, хранилища
  ПДн/критичных данных («безопасность банковского уровня»),
  масштабирование чтения репликами.
- Продукт зарегистрирован в Реестре российского ПО (запись №13436 от
  29.04.2022). Дистрибутив поставляется с разным набором доступной
  функциональности — редакции Standard и Enterprise (см. §1.2).
- Поддерживаемые ОС (x86_64): РЕД ОС 7.3/8, Альт СП 10 версия 2,
  Альт Сервер 10, Platform V SberLinux OS Server 9.7.0+ / 10.0.0+,
  Astra Linux Special Edition 1.8. В релизе 8.2 добавлена поддержка
  установки на ОС **Astra Linux «Смоленск»** и поддержка SberLinux OS
  Server 10.
- Состав: `pangolin-dbms` (серверная часть, клиентские пакеты, libpq),
  Pangolin Manager, Pangolin DCS, Pangolin Pooler, средства резервного
  копирования (`pangolin-backup-tools`, агент CopyWala, `pg_probackup`,
  инкрементальное копирование в режиме ptrack), утилиты (Pangolin
  Installer — автоматическое развёртывание/обновление, с 8.2.0 — с GUI;
  Pangolin Tuner — тюнинг параметров под профиль нагрузки;
  `pangolin-inplace-upgrade`; диагностические утилиты; утилиты
  безопасности — TDE, защита от привилегированных пользователей,
  засекречивание параметров подключения), расширения. Поставляются
  Docker-образы (в т.ч. кластерной конфигурации 1 лидер + N реплик +
  Pooler) и debug-пакеты для расследования инцидентов.
- Интеграции экосистемы Platform V: Kintsugi (графическая консоль
  управления СУБД), SynGX, GraDeLy (CDC-решение, нативная поддержка),
  Data Protector (мониторинг резервного копирования), Pangolin
  CloudNative (`pcloudn`, оператор для Kubernetes, в 3rd-party части
  дистрибутива).

### 1.3 Регуляторный контур (привязка продуктов Platform V к требованиям)

Факты из верифицированных карт соответствия (выдержки из актов
проверены по цитатам составителями карт):

- **719-П, п. 2.3**: оценка соответствия защиты информации — «не реже
  одного раза в два года».
- **719-П, п. 2.4**: уровень соответствия — «не ниже четвёртого» в
  соответствии с ГОСТ Р 57580.2-2018.
- **719-П, п. 2.5**: сертификация прикладного ПО по приказу ФСТЭК России
  от 30.07.2018 № 131 (рег. Минюст 14.11.2018 № 52686). Операторы,
  являющиеся системно значимыми кредитными организациями или признанные
  Банком России значимыми на рынке платёжных услуг, — сертификация **не
  ниже 4 уровня доверия**; остальные операторы — не ниже 5 уровня
  доверия (контринтуитивно: «обычные» ОПДС — 5-й уровень, системно
  значимые — 4-й).
- **683-П, п. 4.1**: клиентское ПО и ПО приёма электронных сообщений из
  интернета — «сертифицированных в системе сертификации ФСТЭК… включая
  требования по анализу уязвимостей и контролю отсутствия
  недекларированных возможностей», либо анализ уязвимостей по требованиям
  к оценочному уровню доверия **не ниже ОУД 4** (ГОСТ Р ИСО/МЭК
  15408-3-2013).
- **851-П, пп. 4.1**: прикладное ПО и ПО интернет-каналов — оценка
  соответствия по требованиям к ОУД не ниже ОУД4 (п. 7.6 раздела 7 ГОСТ Р
  ИСО/МЭК 15408-3), либо сертификация ФСТЭК (ПП № 608). **851-П, пп.
  3.2**: ежегодное тестирование на проникновение и анализ уязвимостей.
  **851-П, п. 6**: СКЗИ по 63-ФЗ/152-ФЗ/ПП 1119/ПКЗ-2005/приказу ФСБ
  № 378.
- Карта соответствия фиксирует принцип: **штатные функции продукта
  закрывают технические меры** (шифрование, разграничение доступа, аудит,
  резервирование); **схема БД, процессы ДИТ и DR-учения остаются на
  уровень решения** — продукт их не выполняет и не гарантирует.
- По карте «остаётся на уровень решения» (т.е. НЕ закрывается покупкой
  продукта): классификация защищаемой информации (719-П п. 2.2);
  append-only-дисциплина схемы и retention (719-П прил. 1 № 10 — 5 лет в
  неизменном виде); ежегодный pentest/анализ уязвимостей; оценка
  соответствия по ГОСТ Р 57580.2 (уровень ≥ 4, не реже раза в 2 года) —
  выполняется проверяющей организацией, не продуктом; **сертификация ПО
  (719-П п. 2.5, ФСТЭК-131 уровни доверия 4/5; 851-П пп. 4.1 ОУД 4;
  683-П п. 4.1) — уровень доверия продуктов Platform V является вопросом
  вендора/сертификации и не решается в проекте ДИТ**; уровень защиты по
  ГОСТ Р 57580.1 определяется статусом банка, а не продуктом; фактические
  RTO/RPO доказываются DR-учениями, а не паспортом продукта.
- **Гипотеза (conditional, обязательств не создаёт)**: закрываются ли
  требования ГОСТ-СКЗИ каналов (851-П п. 6, приказ ФСБ № 378) штатным
  TLS/Kerberos продуктов Platform V или требуется ГОСТ-TLS-прокси —
  `[ТРЕБУЕТ ПРОВЕРКИ]`, зависит от конкретного контура банка.

### 1.4 TDE, хранилище параметров, управление ключами и сертификатами

- **TDE** — прозрачное защитное преобразование данных (шифрование данных
  и индексов на диске). Только редакции Enterprise / Enterprise для ERP
  (с 4.1.0). Данные глобальных индексов подпадают под TDE.
- **Интеграция с KMS HashiCorp Vault** — только Enterprise (с 4.3.0).
  Хранилища секретов, зафиксированные в материалах продукта: HashiCorp
  Vault (KMS) и система «ОдинКлюч»; применяются в т.ч. для параметров
  подключения FDW.
- **Хранилище параметров подключения** (засекречивание параметров
  подключения, в т.ч. для FDW: `pg_auth_config`, защищённое хранилище
  паролей сторонних БД) — только Enterprise (с 4.4.0).
- **Защита параметров конфигурации** — только Enterprise (с 4.3.0).
- Сертификаты: хранение в защищённом виде (PKCS#12), использование
  сертификатов из системы хранения секретов и их ротация, поддержка CRL в
  компонентах кластера — всё только Enterprise (5.3.0/5.4.0).
- В составе утилит безопасности заявлены: TDE, защита от
  привилегированных пользователей, засекречивание параметров подключения.
- В разделе «Основные функциональности»: «сокрытие парольной информации в
  конфигурационных файлах», «хранение сертификатов в формате PKCS#12 и
  возможность интеграции с системой хранения секретов», «очистка
  высвобождаемого дискового пространства в процессе работы СУБД»
  (в матрице редакций — все редакции, с 6.2.0).
- При включённом TDE **логическое CDC-сопровождение недоступно**:
  pgcopydb follow не работает с TDE (см. §1.10) — порядок «миграция →
  включение TDE» является следствием документированного ограничения.
- При включённых СЗИ (Enterprise) документация описывает выгрузку данных
  в дамп для защищённых контуров.

### 1.5 Защита от привилегированных пользователей

- Функция «Защита данных от привилегированных пользователей» — только
  Enterprise (с 4.1.0). В разделе «Основные функциональности» заявлены
  отдельно: «защита объектов от привилегированных пользователей» и
  «защита параметров от привилегированных пользователей».
- В документации упоминается утилита **initprotection** — инициализация
  защиты данных от привилегированных пользователей.
- TDE и защита от привилегированных пользователей — **разные строки
  матрицы** функциональности (4.1.0, обе Enterprise): TDE отвечает за
  шифрование данных на диске, защита от привилегированных — за
  разграничение доступа привилегированных ролей к данным и параметрам.
- Состав защищаемых объектов, ролевая механика (роли администраторов,
  порядок включения, совместимость с конкретными расширениями) в снятых
  источниках НЕ детализированы — см. §1.13.
- Связанные механизмы контроля: «контроль загрузки динамических библиотек
  с проверкой контрольных сумм» (по разрешённому списку), «контроль
  использования процедурных языков», «контроль целостности конфигурации и
  объектов БД» (6.2.0, Enterprise), «механизм сбора информации о движении
  данных» (Data Lineage).

### 1.7 HA/DR: кластер, режимы репликации, DCS, standby-кластер, N-ЦОД

- Кластер высокой доступности = 2+ сервера с экземплярами одной БД,
  связанные потоковой физической репликацией. Компоненты: **Pangolin
  Manager** (оркестратор, вендорская сборка Patroni; в 8.2.0 —
  pangolin-manager 4.2.0, в комплекте документация Patroni 4.1.1),
  **Pangolin DCS** (распределённое хранилище конфигурации на Raft:
  состояние кластера, кворум, лидерская блокировка с TTL), **Pangolin
  Pooler**. Из Patroni-наследия поддерживаются и etcd/ZooKeeper/Consul.
- Заявленные целевые показатели mission critical: **RPO = 0** (без потери
  данных при программном/аппаратном сбое), **RTO < 6 минут в год**
  простоя — через горячее резервирование Active/StandBy в разных ЦОД,
  автоматический failover средствами Manager и пулер.
- Репликация однопоточная → один лидер. При потере записи о лидере в DCS
  узлы сравнивают позиции WAL; первый записавший себя в DCS становится
  лидером. Управление: CLI `pangolin-manager-ctl` (`list`, `pause`/
  `resume`, `reload`, `restart`, `switchover`, `failover`, `reinit`,
  `edit-config`) и REST API (health-check балансировщиками, мониторинг,
  автоматика). `switchover` — плановое переключение с нулевой потерей
  данных даже в асинхронном режиме; `reinit` — пересоздание реплики через
  pg_basebackup. При активном Manager ручное управление экземплярами
  (`pg_ctl`, systemctl) — только в режиме `pause`.
- Режимы репликации:
  - **асинхронный** (дефолт, `synchronous_mode: false`): потери в
    пределах `maximum_lag_on_failover` + записи за `ttl` (в среднем
    `loop_wait` = 2 с); `check_timeline: true` запрещает выбирать лидером
    узел с другой временной шкалой;
  - **стандартная синхронная PostgreSQL** (`synchronous_commit: on` +
    `synchronous_standby_names`): коммит ждёт записи на реплику; Manager
    трактует кластер как асинхронный; рекомендовано ≥ 2 реплик;
  - **нестрогий синхронный Manager** (`synchronous_mode: true`): при
    недоступности реплики лидер деградирует в async (запись сохраняется);
    failover — только на реплику со всеми зафиксированными транзакциями;
    позволяет работать с двумя узлами;
  - **строгий синхронный** (`synchronous_mode_strict: true`): без
    доступной синхронной реплики лидер блокирует запись; автопереключения
    при одновременной потере лидера и синхронной реплики нет.
- **DCS failsafe mode**: при полной недоступности DCS кластер продолжает
  работать, если все узлы видят лидера через его REST API.
- **Standby-кластер (паттерн DR при двух ЦОД)**: «standby leader»
  реплицируется с первичного кластера и ведёт каскадные реплики;
  пространства имён (scope) DCS основного и резервного кластеров ДОЛЖНЫ
  различаться; кластеры не знают друг о друге ничего, кроме канала
  репликации; слот репликации на первичном создаётся вручную (или
  постоянные слоты). При двух ЦОД документация предписывает **два
  независимых DCS + standby-кластер во втором ЦОД**; автоматическое
  повышение standby невозможно (DC2 не отличает сбой DC1 от сетевого
  разделения) → **ручной promote** удалением секции `standby_cluster` из
  динамической конфигурации (НЕ `pg_ctl promote`); перед promote —
  **STONITH** основного, иначе split-brain; возврат — `pg_rewind`
  (требует `--data-checksums` и/или `wal_log_hints=on`) или пересоздание
  standby с нуля. Имена узлов должны быть уникальны во всех связанных
  кластерах — иначе синхронная репликация может «тихо» подтверждаться
  через чужое соединение (риск потери данных без ошибок в логах).
- При 3+ ЦОД: синхронный мульти-ЦОД кластер, нечётное число узлов DCS
  (3 или 5), минимум 3 узла СУБД для пережития падения зоны.
- **N-ЦОД в Pangolin Pooler**: режимы `NDC_ALLOWED`/`NDC_DISALLOWED`,
  команды `NDC_SUSPEND` (рвёт клиентские и БД-соединения, кроме
  админ-консоли, и запрещает новые) / `NDC_KEEPALIVE`, таймер
  `ndc_suspending_timeout` — без регулярного keepalive от внешнего
  арбитра пулер САМ переходит в suspend (fail-closed защита от записи
  «не в тот» ЦОД).

### 1.8 Pangolin Pooler

- Доработанный форк PgBouncer (в 8.2.0 — Pangolin Pooler 3.2.0; ядро
  PgBouncer 1.24.0). Порт по умолчанию 6544, админ-консоль — БД
  `pgbouncer`. Доработки: сквозная аутентификация (вкл. LDAP и аудит),
  prepared statements в транзакционном режиме HA-кластера, сохранение
  контекста сессий (SET ROLE, search_path), PKCS#12/SecMan, топология
  N-ЦОД, вывод `SHOW POOLS` в лог.
- **Многопоточная версия** пулера существует, но **только для SberLinux**
  (классический пулер однопроцессный → потолок одного ядра CPU);
  распределяет соединения по воркерам с мониторингом утилизации потоков.
- Рекомендации вендора: `max_connections` определяется нагрузочным
  тестом; стартовая формула `GREATEST(5 × CPU cores, 100)`; одинаковое
  значение на Primary и StandBy (иначе после failover часть клиентов не
  подключится); пулер нужен, когда `max_client_conn > max_connections`;
  `max_db_connections <= max_connections - superuser_reserved_connections
  - 30`; `min_pool_size = default_pool_size`. Пример сбалансированной
  конфигурации (одна ТУЗ / одна БД): `max_client_conn=1000`,
  `pool_mode=transaction`, пул по 200.
- Когда пулер НЕ рекомендуется: ядро CPU пулера загружено > 70 %;
  OLTP > 1000–10000 TPS с операциями < 1–10 мс в transaction-режиме
  (накладные расходы на сокет, рост sys_time; через пулер отклик в
  среднем ~5 % медленнее); OLAP с большим трафиком. HikariCP: если пул
  приложения меньше `max_connections` — подключаться напрямую, иначе
  HikariCP + Pooler, `max_client_conn` больше суммы всех пулов.
- Резервирование подключений для ролей (файл `pg_quota.conf` в каждой
  БД) — гарантированный доступ служебных УЗ при исчерпании пула.

### 1.10 Миграция с PostgreSQL и ограничения при TDE

- **PostgreSQL → Pangolin**: доработанная `pg_upgrade` («Инструмент
  миграции с оригинального PostgreSQL»; с версии 6.1.0 — миграция данных
  с PostgreSQL 15) — штатный сценарий вендора; раздел «Миграция с
  оригинального PostgreSQL на Pangolin» в документации. Также —
  **pgcopydb 0.14** (Enterprise, 3rd-party часть дистрибутива):
  clone/fork + follow (CDC через test_decoding по умолчанию, совместим с
  wal2json), snapshot, compare schema/data.
- Ограничения pgcopydb (дословно из документации): не запрашивает пароль
  для части команд (передавать параметром или беспарольная
  аутентификация); не работает с хранилищем паролей; при полной миграции
  набор расширений (версии + GUC) источника и приёмника должен быть
  идентичен; **follow падает при перезапуске любой из БД**; **follow
  требует суперпользователя на приёмнике** (`SET
  session_replication_role`); **follow не работает с TDE**.
- Следствие для защищённых контуров: при включённом TDE логическое
  CDC-сопровождение (pgcopydb follow) недоступно — планировать
  даунтайм-миграцию или иной канал; порядок «перенос данных → включение
  TDE».
- Прочие инструменты дистрибутива: ora2pg 23.0 (в 8.2.0 НЕ установлен по
  умолчанию; поставляется в `migration_tools/ora2pg`), orafce 4.4.0,
  oracle_fdw 2.5.0, tds_fdw 2.0.3 (пароль сторонней БД — в защищённом
  `pg_auth_config`), pgloader 3.6.9 (Enterprise; MS SQL/MySQL/SQLite,
  транспорт COPY).
- Внешний CDC-продукт линейки — Platform V GraDeLy (GDL).
- Обновление самого Pangolin: `pangolin-inplace-upgrade` (обновление
  системных каталогов без миграции данных, значительно быстрее
  классического pg_upgrade-сценария); сценарий standalone → кластер;
  автоматизированные сценарии через Pangolin Installer; поддержка
  обновления кластера с предустановленными сторонними расширениями
  (с 6.7.0).

### 1.11 Партиционирование, сжатие, ёмкость

- **Нативное интервальное (авто-) партиционирование** (только
  Enterprise): `AUTO PARTITION BY RANGE/HASH/LIST`, партиции создаются
  при вставке; вложенность поддерживается; пустые партиции не удаляются;
  **схему автопартиционирования для уже созданной таблицы изменить
  нельзя** — ключ и период проектируются до наполнения. Ключ
  партиционирования — до 32 полей; для RANGE — INTEGER/NUMERIC/DATE/
  TIMESTAMP/TIMESTAMPTZ. `pruning_fields` для композитных ключей
  (Enterprise).
- **Глобальные индексы и ограничения** (только Enterprise): `CREATE
  [UNIQUE] INDEX ... GLOBAL` / `PRIMARY KEY/UNIQUE ... GLOBAL` — B-Tree
  над всеми партициями, уникальность по полям ВНЕ ключа
  партиционирования. Ограничения: только B-Tree; без
  exclusion-ограничений и субпартиционирования; при `REINDEX INDEX
  CONCURRENTLY` на автопартиционированной таблице невозможен INSERT,
  создающий новую партицию. Созданные глобальные индексы продолжают
  работать при понижении лицензии, новые создавать нельзя. Данные
  глобального индекса подпадают под TDE.
- **Сжатие данных на уровне страниц** (Enterprise): `compresstype` =
  pglz | lz4 | zstd на таблицу, партицию, матпредставление, индекс или
  табличное пространство; включается `enable_page_compression` (reload).
  Подход из рекомендаций: сжимать исторические (холодные) партиции, не
  трогая горячие.
- Жёсткие пределы ядра: размер отношения ≤ 32 ТБ (BLCKSZ 8192), поле ≤ 1
  ГБ (TOAST), ≤ 1600 колонок на таблицу. Декларативное партиционирование
  допускает смешение локальных партиций со сторонними (foreign)
  таблицами через FDW.
- Прочее для нагрузок: 64-битные XID (снимают wraparound-проблему);
  управление планами (pg_hint_plan, pg_dbms_stats, pg_store_plans);
  контроль и квотирование ресурсов (CPU/RAM/диск) с завершением
  ресурсоёмких сессий (Enterprise); pg_repack/pg_squeeze/pgcompacttable
  против раздувания таблиц; режим поддержки 1С — отключаемый, без 1С
  может деградировать планы.
- Диагностика: Performance Insights, pg_profile, psql_diagpack,
  трассировка сессий.

### 1.13 Что источники НЕ подтверждают — помечать `[ТРЕБУЕТ ПРОВЕРКИ]`

Решающий ОБЯЗАН оформлять приведённое ниже как открытый вопрос к вендору
или допущение, а не как факт:

1. **Редакция «Certified»**: в матрице редакций документации 8.2.0 —
   только Standard / Standard для ERP / Enterprise / Enterprise для ERP.
   Отдельная сертифицированная сборка («Certified») в предоставленных
   источниках не зафиксирована. Существование такой сборки для 8.2.0, её
   состав, действующий сертификат ФСТЭК и уровень доверия конкретной
   сборки — `[ТРЕБУЕТ ПРОВЕРКИ]` у вендора (запрос в СберТех, проверка
   реестра сертифицированных средств). При этом сам по себе сертификат на
   продукт не заменяет аттестацию системы и оценку соответствия
   (§1.3 — «остаётся на уровень решения»).
2. **Криптография TDE**: алгоритмы шифрования TDE (ГОСТ или нет), длины
   ключей, соответствие конкретным классам СКЗИ в снятых источниках не
   описаны — `[ТРЕБУЕТ ПРОВЕРКИ]`.
3. **ГОСТ-СКЗИ каналов**: закрывают ли штатные TLS/Kerberos продукта
   требования по приказу ФСБ № 378 — гипотеза карты соответствия,
   `[ТРЕБУЕТ ПРОВЕРКИ]` (возможен ГОСТ-TLS-прокси на границах).
4. **Детали механизма защиты от привилегированных пользователей**:
   состав защищаемых объектов, ролевая механика, порядок включения (кроме
   упоминания утилиты initprotection), совместимость с расширениями —
   `[ТРЕБУЕТ ПРОВЕРКИ]` по документации 8.2.0.
5. **Базовая мажорная версия PostgreSQL**, на которой собран Pangolin
   8.2.0, в снятых источниках не зафиксирована (задокументировано лишь,
   что миграция данных с оригинального PostgreSQL 15 поддерживается с
   версии 6.1.0).
6. **Параметры CopyWala/pg_probackup**: политики ретенции, PITR-окно,
   шифрование копий и порядок получения ключей при восстановлении —

7. Поведение TDE при недоступности Vault (старт экземпляра, переключение)

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Заволжский Торговый Банк» (вымышленный, топ-40 по активам, признан
Банком России **значимым на рынке платёжных услуг**) по государственным
контрактам выполняет роль агента по выплате социальных пособий и
компенсаций. АС «Реестр социальных выплат» (АС РСВ) ведёт реестры
получателей (ФИО, СНИЛС, реквизиты счетов — **персональные данные**),
назначения и исполнение выплат (суммы — **банковская тайна**). Сбой
системы в дни массовых выплат — репутационный и регуляторный риск.

По внутренней классификации ИБ банка АС РСВ отнесена к **аттестуемому
контуру с требованиями ФСТЭК**: планируется аттестация АС силами
аккредитованной лаборатории; ввод в эксплуатацию нового слоя хранения
возможен только после успешной аттестации.

Программа импортозамещения предписывает перевести АС РСВ на
отечественный стек до конца 2027 года. Целевая СУБД утверждена:
**Platform V Pangolin DB 8.2.0**. ИБ банка в исходном задании просит
«сертифицированную ФСТЭК редакцию Certified» — требуется архитектурная
проверка этого запроса (CONTEXT §1.13, п. 1).

### 2.2 Ландшафт AS-IS

- СУБД: **ванильный PostgreSQL 15**, кластер Patroni (1 лидер + 2
  реплики) в ЦОД-1, асинхронная реплика в ЦОД-2; etcd из 3 узлов.
  Шифрования на уровне СУБД нет; диски шифруются средствами СХД — ИБ
  признала это недостаточным (нет защиты от администратора ОС/СХД, ключи
  на серверах площадки, нет разграничения для привилегированных ролей
  СУБД).
- Объём данных: **6,8 ТБ** (без индексов ~4,3 ТБ), рост **~0,9 ТБ/год**;
  срок хранения реестров — **5 лет онлайн** (719-П прил. 1 № 10), далее
  архив.
- Приложение: Java 21 / Spring Boot, **40 подов** в Kubernetes (Platform
  V), пул HikariCP **25 соединений на под** (до 1 000 клиентских
  соединений к СУБД в пике).
- Нагрузка: пик **4 500 транзакций/с** (короткие OLTP, ~80 % чтение);
  ночная загрузка реестров выплат — **до 8 млн строк за 90 минут**;
  месячная отчётность в органы — 15–20 тяжёлых аналитических запросов в
  день.
- Аутентификация прикладных ТУЗ — локальные пароли; интеграции с IDM/LDAP
  банка на уровне СУБД нет; аудит действий — штатный `log_statement`,
  не соответствует ГОСТ Р 59548-2022.

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~55 км, выделенные каналы 2×10 Гбит/с, RTT 3–4 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64; в каждом ЦОД можно выделить до 4 серверов под СУБД (2×24 ядра = 48 ядер, 384 ГБ RAM, NVMe 12 ТБ). Стандарт банка — Platform V SberLinux OS Server 10; для аттестуемого контура ИБ **требует Astra Linux Special Edition («Смоленск»)** |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, растянут между ЦОД, доступен из обоих ЦОД с латентностью ≤ 5 мс, собственный RTO ≤ 5 мин). Локальное хранение ключей и секретов на серверах СУБД **запрещено** политикой ИБ |
| INF-04 | СРК банка предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; копии аттестуемого контура должны храниться в обоих ЦОД |
| INF-05 | Мониторинг — Zabbix; журналирование — централизованный SIEM; все административные сессии — только через PAM-систему банка; IDM/LDAP — корпоративный |
| INF-06 | Аттестуемый контур изолирован: выход в интернет запрещён; внешние взаимодействия — только через утверждённые ИБ точки обмена; состав ПО контура фиксируется в аттестационном пакете, изменение состава/версий ПО требует согласования с ИБ и актуализации аттестационного пакета (срок согласования — до 15 рабочих дней) |
| INF-07 | Команда сопровождения: 3 DBA (опыт PostgreSQL хороший, Pangolin — базовый), 1 администратор ИБ, 2 DevOps; развёртывание — только автоматизированное, из корпоративного репозитория |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с воскресенья на понедельник, **не более 3 часов** |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность в операционное время (06:00–22:00 МСК) | ≥ 99,9 % в год |
| NFR-02 | RPO при отказе узла внутри ЦОД | **0** (подтверждённые транзакции не теряются) |
| NFR-03 | RTO при отказе узла внутри ЦОД (автоматическое переключение) | ≤ 3 мин |
| NFR-04 | RPO при полной потере ЦОД-1 | ≤ 60 с |
| NFR-05 | RTO при полной потере ЦОД-1 (допускается ручное решение) | ≤ 30 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД | ≤ 12 мс при 4 500 TPS |
| NFR-07 | Ночная загрузка реестров (8 млн строк) | ≤ 90 мин, без блокировки OLTP |
| NFR-08 | Ёмкость | 5 лет хранения при росте 0,9 ТБ/год + 30 % запас |
| NFR-09 | Восстановление на момент времени (PITR) | глубина 35 дней; RTO восстановления полной БД из копии ≤ 6 ч |
| NFR-10 | Установка критических патчей безопасности вендора | не позднее 30 дней с момента публикации патча |
| NFR-11 | Плановые минорные обновления СУБД и компонентов | без простоя приложения |
| NFR-12 | Мажорные обновления | в окне INF-08 |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Данные реестров (ПДн + банковская тайна) шифруются средствами СУБД «на диске»; ключи — только в Vault банка (INF-03) |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен иметь возможность прочитать содержимое защищаемых таблиц |
| SEC-03 | Разделение обязанностей: включение TDE, изменение состава расширений и настройка защитных параметров требуют участия администратора ИБ |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только ТУЗ с минимальными правами; аутентификация сквозная от приложения к СУБД |
| SEC-05 | Аудит событий безопасности по ГОСТ Р 59548-2022; выгрузка в SIEM; маскирование параметров запросов в журналах |
| SEC-06 | TLS для всех соединений (клиент ↔ пул ↔ СУБД, узлы кластера ↔ DCS, REST API оркестратора); сертификаты из корпоративного УЦ; поддержка CRL; ротация сертификатов не реже раза в год без простоя |
| SEC-07 | Парольные политики для локальных УЗ (сложность, срок действия, история); ротация паролей ТУЗ без недоступности сервиса |
| SEC-08 | Внешняя авторизация администраторов через корпоративный LDAP/IDM |
| SEC-09 | Двухфакторная аутентификация для административных УЗ |
| SEC-10 | Сертификация прикладного ПО контура по приказу ФСТЭК № 131 на уровень доверия не ниже требуемого для статуса банка (719-П п. 2.5); успешная аттестация АС до ввода в эксплуатацию; обоснованный выбор редакции СУБД |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами.
- ИБ настаивает на «редакции Certified»; комитет ждёт от архитектора
  проверки этого запроса по источникам и корректной формулировки вопроса
  к вендору, а не слепого следования или слепого отказа.
- Комитет особенно чувствителен к: разграничению «требования к редакции /
  к среде / к процессам»; конфликту окна патчирования (NFR-10) с
  аттестационным согласованием (INF-06); порядку включения TDE
  относительно миграции.
- Решение должно быть реализуемо силами INF-07.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версия Pangolin на момент внедрения — 8.2.0 или новее (патчи вендора в
  пределах линейки 8.2).
- Приложение допускает доработку строки подключения, параметров пула
  HikariCP и отказ от сессионных фич, несовместимых с транзакционным
  пулингом.
- Vault банка (INF-03) считается эталонной зависимостью; его внутреннее
  устройство не проектируется.
- Ночные регламенты можно перенести на планировщик заданий СУБД или
  внешний оркестратор банка.
- Оценочный коэффициент сжатия холодных партиций (pglz/lz4/zstd) решающий
  вправе принять как допущение, явно пометив его и подтвердив планом
  нагрузочного тестирования.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| DCS | Distributed Configuration Store — хранилище состояния кластера для оркестратора (Pangolin DCS на Raft; альтернативы из Patroni-наследия — etcd/ZooKeeper/Consul) |
| Switchover / Failover | плановое / аварийное переключение роли лидера |
| Standby-кластер | резервный кластер в другом ЦОД, реплицирующийся с первичного; повышение — только вручную |
| STONITH | принудительное изолирование/выключение потерянного узла перед повышением резервного |
| TDE | прозрачное защитное преобразование (шифрование) хранимых данных |
| KMS | система управления ключами (в сценарии — HashiCorp Vault банка) |
| ТУЗ | техническая учётная запись |
| СРК | система резервного копирования |
| PAM | privileged access management |
| УЗ | учётная запись |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
| ОУД | оценочный уровень доверия (ГОСТ Р ИСО/МЭК 15408) |
| ГОСТ Р 59548-2022 | стандарт на состав событий аудита безопасности (требования ФСТЭК) |
| ГОСТ Р 57580.1/.2 | уровни защиты / оценка соответствия защиты информации в финансовых организациях |
| Приказ ФСТЭК № 131 | требования по уровням доверия к средствам защиты информации |
