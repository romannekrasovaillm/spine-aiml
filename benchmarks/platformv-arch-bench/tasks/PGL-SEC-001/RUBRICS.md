# Рубрики оценки для задачи PGL-SEC-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`) и указанные там источники.
   Утверждение о Pangolin, которого нет в §1 и которое не помечено решающим
   как допущение или `[ТРЕБУЕТ ПРОВЕРКИ]`, считается **непроверенным**; если
   оно ещё и ложно — **ложным**. Судья не должен «додумывать» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие ключевого слова.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/поверхностно;
   2 — базово корректно, есть пробелы; 3 — полно и обоснованно, мелкие
   недочёты; 4 — образцово: полно, обоснованно, с учётом компромиссов и
   ловушек §4. Промежуточные уровни (1, 3) — интерполяция между якорями.
5. **Цитирование доказательств.** Для каждого критерия судья приводит 1–3
   коротких цитаты (≤ 25 слов) из ответа, подтверждающих оценку, и указывает,
   чего не хватает до следующего уровня.
6. Режим прогона — только `agentic`; учитывается `run_mode_adjustments`.
7. Судья не оценивает стиль и «красоту» сверх C11 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Выбрана редакция Standard / Standard для ERP при сохранённых требованиях SEC-01 (TDE), SEC-02 (защита от привилегированных пользователей), SEC-08 (LDAP) — без явного отказа от этих требований и согласования этого отказа; **либо** редакция «Certified» для версии 8.2.0 заявлена как существующий факт (в матрице редакций 8.2.0 её нет, CONTEXT §1.2/§1.13) без пометки «требует проверки у вендора» | Только судья: семантическая проверка раздела D2 по CONTEXT §1.2, §1.13 (частично ловится regex mechanical_checks: «Certified» в утвердительной форме) |
| HF-02 | Заявлено, что сертификат ФСТЭК на продукт/редакцию **сам по себе** заменяет аттестацию АС или освобождает от оценки соответствия по ГОСТ Р 57580.2 (CONTEXT §1.3: сертификация ПО — вопрос вендора; оценка соответствия и аттестация остаются на уровне решения) | Только судья + regex mechanical_checks (характерные формулировки); сверка с CONTEXT §1.3 |
| HF-03 | Заявлено, что TDE **сама по себе** защищает данные от суперпользователя СУБД или администратора ОС (CONTEXT §1.5: TDE и защита от привилегированных пользователей — разные механизмы) | Только судья + regex mechanical_checks; сверка с CONTEXT §1.4/§1.5 |
| HF-04 | Миграция спланирована через pgcopydb follow при уже включённом TDE (документировано: follow не работает с TDE, CONTEXT §1.10) без осознанной оговорки; либо порядок «сначала TDE, потом CDC-миграция» подан как рабочий план | Только судья + regex mechanical_checks (pgcopydb/follow рядом с TDE); сверка с CONTEXT §1.10 |
| HF-05 | Вымышленные компоненты, редакции или функции Pangolin поданы как факт (например, «Pangolin Vault», «Pangolin CryptoGateway», «встроенный HSM Pangolin», «редакция Certified в составе 8.2.0», «нативная поддержка PL/SQL») | Только судья, таблица ловушек §4; частично regex mechanical_checks |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 | Механическая проверка (mechanical_checks.deliverables) + A-01 |

## 3. Критерии

### C1. Фактическая корректность по Pangolin 8.2.0 (вес 15)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md
§1; корректные наименования компонентов и редакций; отделение фактов от
допущений и от вопросов `[ТРЕБУЕТ ПРОВЕРКИ]`.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-05, либо ≥ 4 ложных утверждения о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (матрица редакций, standby-кластер, pgcopydb+TDE, многопоточный Pooler), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение или `[ТРЕБУЕТ ПРОВЕРКИ]`; правильно различаются: четыре редакции матрицы 8.2.0 и неподтверждённая «Certified»; факты документации и выводы дистиллятов; функции «все редакции» (аудит ГОСТ Р 59548-2022, 2FA, парольные политики, сквозная аутентификация Pooler) и Enterprise-only |

**Признаки сильного ответа:** использует официальные имена
(`pangolin-dbms`, Pangolin Manager, Pangolin DCS, Pangolin Pooler,
`pangolin-backup-tools`, CopyWala, `pg_probackup`, pgcopydb,
`pangolin-inplace-upgrade`, initprotection, `external_authorize`);
версии компонентов 8.2.0 (manager 4.2.0, pooler 3.2.0) не приписывает
выдуманных; темы §1.13 CONTEXT (криптография TDE, детали защиты от
привилегированных, ГОСТ-СКЗИ каналов, параметры CopyWala) оформлены как
вопросы к вендору.

**Типичные ошибки:** «в 8.2.0 есть редакция Certified»; «TDE по ГОСТ»
без пометки проверки; «pgcopydb работает при включённом TDE»;
«многопоточный Pooler на Astra Linux»; изобретение параметров и утилит.

### C2. Выбор редакции и разграничение редакция/среда/процесс (вес 15)

**Что оценивается:** D2 целиком. Матрица «требование → функция →
редакция», выбор редакции, разбор запроса на «Certified», реестр
«продукт / среда / процесс», соответствие SEC-10.

| Уровень | Якорь |
|---|---|
| 0 | HF-01/HF-02; редакция не выбрана вообще |
| 2 | Enterprise выбрана, но без матрицы функция→редакция; «Certified» отвергнута или принята без проверки источников; реестр «продукт/среда/процесс» формален |
| 4 | (a) матрица покрывает минимум: TDE (Ent, 4.1.0) → SEC-01; защита от привилегированных (Ent, 4.1.0) → SEC-02/03; маскирование запросов (Ent, 5.2.1) → SEC-05; PKCS#12/сертификаты из хранилища секретов/ротация/CRL (Ent, 5.3.0–5.4.0) → SEC-06; LDAP (Ent, 6.6.0) → SEC-08; аудит ГОСТ Р 59548-2022 (все, 3.2.0) → SEC-05; 2FA (все, 5.2.0) → SEC-09; парольные политики (все, 3.3.0) → SEC-07; сквозная аутентификация Pooler (все, 4.4.0) → SEC-04; (b) выбрана Enterprise (или Enterprise для ERP — с обоснованием, что контур не 1С); (c) «Certified»: явно зафиксировано, что в матрице редакций 8.2.0 её нет, сформулирован конкретный вопрос вендору (существование сборки для 8.2.0, действующий сертификат, уровень доверия) и решение не блокируется этим вопросом; (d) реестр разграничения: продукт (функции матрицы) / среда (ОС Astra «Смоленск», Vault, PAM, SIEM, изоляция контура INF-06) / процессы (аттестация лабораторией, оценка соответствия ГОСТ Р 57580.2 не реже раза в 2 года, DR-учения, pentest ежегодный); (e) уровень доверия по 719-П п. 2.5 выведен из статуса банка («значимый на рынке платёжных услуг» → не ниже 4 уровня доверия) |

**Ловушки:** «возьмём Certified, раз ИБ просит»; «сертифицированная
редакция снимает необходимость аттестации»; Standard «с компенсирующими
мерами» при SEC-01/02/08; матрица скопирована без вывода.

### C3. TDE и управление ключами (вес 12)

**Что оценивается:** части D3/D5/D6 про TDE, ключи, Vault; SEC-01,
SEC-06, INF-03.

| Уровень | Якорь |
|---|---|
| 0 | HF-03; TDE отсутствует при SEC-01 |
| 2 | TDE + Vault названы; ключи «где-то в Vault»; поведение при недоступности Vault не разобрано; сертификаты компонентов (Manager REST API, Pooler, DCS) не учтены; тема криптографии TDE заявлена фактом вместо проверки |
| 4 | TDE включён с интеграцией KMS HashiCorp Vault (Ent, 4.3.0) → SEC-01, INF-03 (локальное хранение ключей запрещено соблюдено); Vault признан критической зависимостью (старт экземпляра, переключение, восстановление) с мерой/допущением и пометкой §1.13 п. 7; сертификаты: PKCS#12, получение из системы хранения секретов, ротация без простоя, CRL в компонентах кластера (Ent, 5.3.0–5.4.0) → SEC-06; алгоритмы/ГОСТ-соответствие TDE и ГОСТ-СКЗИ каналов корректно помечены `[ТРЕБУЕТ ПРОВЕРКИ]` (§1.13 п. 2–3), а не заявлены фактом; данные глобальных индексов учтены как подпадающие под TDE; связь с D6: копия без ключей не раскрывает данные |

**Ловушки:** «TDE по ГОСТ Р 34.12» как факт; ключи «в файле на сервере,
но под защитой ОС» (нарушение INF-03); Vault упомянут, но его
недоступность при старте/восстановлении не рассмотрена.

### C4. Защита от привилегированных пользователей и разделение обязанностей (вес 12)

**Что оценивается:** D5 (соответствующая часть); SEC-02, SEC-03, SEC-04.

| Уровень | Якорь |
|---|---|
| 0 | HF-03; защита сведена к «отнимем superuser у DBA» |
| 2 | Функция защиты от привилегированных включена, initprotection упомянут, но распределение полномочий между DBA/ИБ/ОС/РК не расписано; детали механизма выдуманы вместо пометки `[ТРЕБУЕТ ПРОВЕРКИ]` |
| 4 | Защита данных И параметров от привилегированных пользователей (Ent, 4.1.0) включена через initprotection → SEC-02; разделение обязанностей расписано по ролям банка (DBA / администратор ИБ / администратор ОС / администратор РК): кто инициирует, кто авторизует включение TDE и изменение состава расширений → SEC-03; административный доступ только персонализированный через PAM, прикладной — ТУЗ минимальных прав со сквозной аутентификацией через Pooler (все редакции, 4.4.0) → SEC-04; задействованы смежные механизмы контроля: контроль загрузки динамических библиотек по разрешённому списку, контроль процедурных языков, контроль целостности конфигурации и объектов БД (6.2.0); недетализированные в источниках аспекты механизма (состав защищаемых объектов, ролевая механика) помечены `[ТРЕБУЕТ ПРОВЕРКИ]` |

**Ловушки:** «TDE закроет SEC-02»; выдуманные названия ролей/функций
защиты, поданные как факт; superuser у прикладной ТУЗ; pgcopydb follow с
постоянным суперпользователем на приёмнике без оговорки о миграционном
окне (см. C7).

### C5. Топология HA/DR в защищённом контуре (вес 10)

**Что оценивается:** D3 + D4; NFR-01…NFR-05, INF-01, INF-02.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; растянутый синхронный кластер на 2 ЦОД с автоматическим failover подан как рекомендация документации |
| 2 | Кластер + standby нарисованы, но: режим репликации не связан с RPO; ручной promote standby не описан (или описан `pg_ctl promote`); DCS без кворум-рассуждения; уникальность имён узлов не учтена |
| 4 | (a) ЦОД-1: кластер Manager + ≥ 2 реплик, нестрогий или строгий синхронный режим с обоснованием trade-off → NFR-02/03; (b) ЦОД-2: standby-кластер с отдельным DCS-scope, асинхронная каскадная репликация → NFR-04 с контролем лага; (c) явно зафиксировано документированное ограничение: при двух ЦОД автоматическое повышение standby невозможно → ручной promote удалением секции `standby_cluster`, STONITH основного, оценка укладывания в RTO ≤ 30 мин (NFR-05), возврат через `pg_rewind` (data-checksums) или пересоздание; (d) DCS: два независимых DCS с разными scope, нечётное число узлов, арбитраж через лёгкие ВМ облачной зоны (INF-01) с разбором её потери; упомянут DCS failsafe mode; (e) N-ЦОД-политика пулера (`NDC_SUSPEND`/`NDC_KEEPALIVE`, fail-closed по `ndc_suspending_timeout`) как защита от записи «не в тот» ЦОД; (f) ограничение ОС контура (Astra «Смоленск», INF-02) увязано с поддержкой 8.2 |

**Ловушки:** «автоматический failover между ЦОД»; общий DCS на оба
кластера; promote через `pg_ctl promote`; «синхронная репликация между
ЦОД без влияния на latency» при RTT 3–4 мс и NFR-06.

### C6. Резервное копирование в зашифрованном контуре (вес 8)

**Что оценивается:** D6; NFR-09, SEC-01/02 (следствие для копий), INF-04.

| Уровень | Якорь |
|---|---|
| 0 | Нет раздела; копии только в одном ЦОД при INF-04 |
| 2 | CopyWala/pg_probackup названы; глубина PITR 35 дней указана; нет вывода RTO восстановления, нет темы ключей при восстановлении |
| 4 | Штатные средства (CopyWala, pg_probackup, ptrack-инкременты) + архив WAL; копии в обоих ЦОД (INF-04); политика под PITR 35 дней; **выведен RTO**: ~6,8 ТБ за ≤ 6 ч ⇒ требуемая полоса ≥ ~0,3 ГБ/с и проверка СРК; явно описано, что восстановление зашифрованной БД требует доступа к ключам Vault (следствие SEC-01/02) и как это организовано процедурно (доступ к ключам по runbook с участием ИБ); регулярные тестовые восстановления (доказательство RTO/RPO — «остаётся на уровень решения», CONTEXT §1.3); недетализированные параметры CopyWala помечены `[ТРЕБУЕТ ПРОВЕРКИ]` |

### C7. Миграция с PostgreSQL 15 с учётом TDE (вес 8)

**Что оценивается:** D8; INF-06, INF-08.

| Уровень | Якорь |
|---|---|
| 0 | HF-04; нет раздела |
| 2 | pgcopydb назван; этапы «копия → дельта → переключение» без учёта TDE и ограничений follow |
| 4 | Рассмотрены оба документированных пути: доработанная `pg_upgrade` (штатная миграция с PostgreSQL 15, с 6.1.0) и pgcopydb (Enterprise, clone/fork + follow); **явно выведен порядок «миграция данных → затем включение TDE»** из ограничения «follow не работает с TDE»; ограничения follow учтены: перезапуск любой БД обрывает follow (риск-менеджмент окна), суперпользователь на приёмнике — оформлен как временная мера миграционного окна с отзывом прав (увязка с SEC-02/03), идентичный набор расширений и GUC, пароли параметром/сертификат; окно переключения сопоставлено с INF-08 (3 ч) и согласованием INF-06; план отката; валидация compare schema/data |

### C8. Производительность и ёмкость (вес 8)

**Что оценивается:** D7; NFR-06, NFR-07, NFR-08, INF-02.

| Уровень | Якорь |
|---|---|
| 0 | Нет расчётов; ёмкость не пересчитана |
| 2 | Pooler и партиционирование названы; размеры заданы «по опыту»; конфликт пулера с профилем нагрузки не замечен |

```json
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.
