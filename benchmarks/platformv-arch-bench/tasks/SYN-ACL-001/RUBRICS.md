# Рубрики оценки для задачи SYN-ACL-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о Synapse,
   которого нет в §1 и которое не помечено решающим как допущение или
   вопрос к вендору, считается **непроверенным**; если оно ещё и ложно —
   **ложным**. Судья не должен «додумывать» за решающего. Раздел §1.11
   CONTEXT.md («чего в источниках нет») — часть фактической базы: темы из
   него легитимны только как `[ASSUME]` / «проверить у вендора» /
   нагрузочное тестирование.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие кодов
   компонентов.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. Режим прогона фиксирован: `agentic`.
7. Судья не оценивает стиль и «красоту» сверх C11 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Использованы **вымышленные компоненты или функции** Synapse, поданные как факт (например, «Synapse API Portal», «встроенный CDC-коннектор Synapse», «REST-шлюз ASGT», «Synapse Workflow Engine»), либо компоненту приписана функция другого компонента (например, «ASGT трансформирует форматы сообщений», «KFGT вызывает хранимые процедуры») | Только судья: сверка с CONTEXT §1 и таблицей ловушек §4; частично — regex mechanical_checks |
| HF-02 | Заявлено как **документированный факт**, что шлюз **ASGT подключается к очередям IBM MQ** АБС (в CONTEXT §1.11 это явно «[ТРЕБУЕТ ПРОВЕРКИ]»; IBM MQ есть только у генераторов/заглушек SYTE) | Судья + regex mechanical_checks (смежность ASGT и IBM MQ в утвердительной форме) |
| HF-03 | В **целевом** состоянии (не на переходный период волны) потребители сохраняют прямые подключения к АБС мимо контура: прямой JDBC к БД АБС, прямой доступ к очередям IBM MQ, прямые файловые шары | Только судья: семантическая проверка D2/D3 и раздела миграции |
| HF-04 | SDTM приписаны сквозные XA-транзакции «потребитель ↔ БД АБС» либо SDTM назначен «для всех взаимодействий» / «для всего контура» без разбора границ применимости (документированы только XA и XA-запись в несколько Kafka через KFGT) | Судья + regex mechanical_checks (эвристика) |
| HF-05 | Квоты потребителей решены **самописным** механизмом (свой rate limiter, счётчики в RDSH/Redis, Lua-скрипты) при наличии профильного компонента SRLS — без явного обоснованного отказа от SRLS | Судья + regex mechanical_checks (эвристика) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D11 | Механическая проверка (mechanical_checks.deliverables) + A-01 |

## 3. Критерии

### C1. Фактическая корректность по Synapse (вес 15)

**Что оценивается:** соответствие всех утверждений о продуктах CONTEXT.md
§1; корректные коды и наименования компонентов; отделение фактов от
допущений; корректная работа с «отрицательным» знанием §1.11.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02, либо ≥ 4 ложных утверждений о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом компоненте (ASGT, KFGT, JDBC, SDTM, SRLS, GEOH, SMBX), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы (официальные коды: ASGT, KFGT, JDBC, SDTM, SRLS, GEOH, IGEG, SVPX, POLM, KACM, GATM, SYAL, SYTE, SMBX, FSGW, EVPC, EVTA); всё за пределами CONTEXT §1 помечено допущением или «проверить у вендора»; правильно различаются: AM (шина-зонтик CloudESB) и SEI (продукт интеграции + миграция с ESB); шлюзы и компоненты; факты документации и проектные решения |

**Признаки сильного ответа:** ссылки на код компонента, а не только на
продукт (компоненты входят в оба состава); ASGT назван «Шлюз ActiveMQ
Artemis»; SMBX — «Синапс.Брокер сообщений» на Apache ActiveMQ Artemis;
явно зафиксировано, что поддержка IBM MQ шлюзом ASGT не документирована
и требует проверки; производительность шлюзов отведена в НТ (SYTE), а не
заявлена цифрой.

**Типичные ошибки:** «ASGT подключится к IBM MQ напрямую» (HF-02);
«SMBX — это Kafka»; «SDTM даст сквозные транзакции до БД АБС» (HF-04);
«GEOH сам переключает трафик»; выдуманные числа производительности;
путаница AM ↔ SEI.

### C2. Карта интеграционных паттернов и выбор шлюзов (вес 14)

**Что оценивается:** D3 + паттерн-часть D2. Для каждого класса K1–K5 из
CONTEXT §2.3 выбран sync/async паттерн и компонент, с обоснованием.

| Уровень | Якорь |
|---|---|
| 0 | Карты паттернов нет; шлюзы выбраны произвольно («всё через ASGT») |
| 2 | Таблица «класс → компонент» есть, но: sync/async выбраны без связи с требованиями к согласованности; K4 (файлы) оставлен без решения или решён «по старинке»; K3 (события) без Corax/KFGT; буферизация K2 не привязана к SMBX |
| 4 | Для каждого класса K1–K5 выбран и обоснован паттерн: K1 — sync-чтение через фасадные сервисы/JDBC Gateway (gRPC/HTTP → процедуры БД АБС), с рассмотрением кэширования повторных запросов (35 % повторов — данные §2.3; например, RDSH как InMemory KV — с пометкой о допущении); K2 — гарантированный async с буферизацией в очередях SMBX (Artemis) + вызов процедур АБС, либо sync с отказом в НОП — выбор обоснован через NFR-05/NFR-06; K3 — события через CDC → Corax (допущение §2.9) с доступом потребителей через KFGT или прямое чтение топиков; K4 — файловый класс решён компонентами FSGW/FXIA (документированные) либо явным допущением; K5 — статусы async через SMBX с корреляционным ID; для каждого класса указано, какой контракт видит потребитель (gRPC/Proto, очередь Artemis, топик) и почему это изолирует АБС |

**Ловушки:** «ASGT заберём сообщения из IBM MQ АБС» (HF-02); файлы K4
«переведём в топики Kafka» без обоснования объёмов (1,2 ТБ/сутки, файлы
до 2 ГБ); sync-вызовы JDBC Gateway для записи проводок в НОП без
буферизации; игнорирование K5.

### C3. Изоляция АБС и модель контрактов ACL (вес 12)

**Что оценивается:** D2 (топологическая часть) + D4. Граница контура,
точки входа, стабильные контракты, NFR-07, SEC-03, SEC-06.

| Уровень | Якорь |
|---|---|
| 0 | HF-03; изоляции нет — потребители продолжают видеть устройство АБС |
| 2 | Контур нарисован, точки входа потребителей есть, но: контракты не описаны (непонятно, что именно видит потребитель); внутренние детали АБС протекают в контракты; SEC-03 (технологические УЗ контура в АБС) не закрыт |
| 4 | Потребители обращаются только к точкам входа контура (IGEG на границе проекта K8s, SVPX между сервисами; политики — POLM; фильтрация на границах namespace — SEC-06); стабильные контракты ACL: gRPC/Proto-интерфейсы фасадных сервисов и шлюзов, очереди SMBX, топики Corax, объекты S3 — без имён таблиц/очередей IBM MQ/файловых форматов АБС (NFR-07); со стороны АБС — технологические УЗ контура с минимальными правами, чтение через фасадные представления/процедуры, запись только через процедуры K2 (SEC-03); политика версионирования контрактов определена как проектное решение (платформа её не даёт — CONTEXT §1.11); описано, что маппинг/трансформация бизнес-данных — зона LIND/SEI-логики или фасадных сервисов, а не шлюзов (шлюзы преобразуют интерфейсы/протоколы — факт §1.2, §1.11) |

**Ловушки:** контракты «та же очередь IBM MQ, но теперь через шлюз»;
маппинг приписан ASGT/KFGT; версионирование контрактов приписано
платформе.

### C4. Транзакционная согласованность (SDTM/XA) (вес 10)

**Что оценивается:** D5, NFR-05, NFR-06, границы применимости SDTM.

| Уровень | Якорь |
|---|---|
| 0 | HF-04; вопрос согласованности не поднят |
| 2 | SDTM упомянут «для транзакций»; границы не разобраны; идемпотентность K2 решена декларативно; связь с документированным сценарием «XA-запись в несколько Kafka через KFGT» отсутствует |
| 4 | Явно разведены зоны: (a) где XA/SDTM применим и нужен — по документированным функциям (XA-транзакции между клиентскими сервисами; XA-запись в несколько Kafka через KFGT — релевантно для связки K2/K5 или дублирования событий K3); (b) где согласованность осознанно ослаблена (K1 — кэш, K3 — at-least-once по данным §2.3); (c) недопущение потери/дублирования проводок K2 решено композицией: буфер в SMBX + идемпотентность по бизнес-ключу (на стороне процедур АБС или фасада) + трекинг по корреляционному ID (K5); состав ресурсов XA SDTM и его поведение при отказе явно вынесены в «проверить у вендора» (CONTEXT §1.11); рассмотрен и обоснован отказ/принятие SDTM как вендорского lock-in (см. дистиллят: антипаттерн «саги вручную поверх имеющегося DTM» или наоборот) |

**Ловушки:** «SDTM свяжет потребителя и Oracle АБС в одну транзакцию»
(HF-04); XA «на всякий случай везде»; идемпотентность «обеспечит брокер»
без механизма (в источниках не описана — §1.11).

### C5. Квоты потребителей (SRLS) (вес 10)

**Что оценивается:** D6, NFR-04, NFR-10 (частично), SEC-10 (частично).

| Уровень | Якорь |
|---|---|
| 0 | HF-05; квот нет или они «общие на контур» (повторение ошибки AS-IS) |
| 2 | SRLS назван; но паттерн подсчёта не выбран, расписания и режим NЦОД не использованы, привязка квот к потребителю не определена |
| 4 | Квоты — на SRLS с осознанным выбором паттерна: централизованный подсчёт vs подсчёт в точке применения квот (оба документированы), с аргументом (точность vs накладные расходы; два ЦОД ⇒ режим NЦОД с разделением квот между ЦОД — документированный сценарий); лимиты NFR-04 разложены по потребителям (200/400/50 RPS), НОП-ужесточение ×0,5 — через **расписание применения квот** (документированный сценарий); включение квотирования потребителя/ресурса — в релизном цикле, что увязано с GitOps (INF-08) и волнами перевода; единицы квот и идентификатор потребителя честно помечены как нераскрытые в источниках (§1.11) и выведены проектным решением (например, идентификатор из mTLS-сертификата — допущение); поведение при превышении (отказ потребителю без влияния на остальных) связано с NFR-04 и 719-П (SEC-10) |

**Ловушки:** самописный rate limiter (HF-05); квоты «на IP-адрес» при
многих узлах потребителя; применение SRLS к ASGT/SMBX-потокам без
пометки, что SRLS работает для сервисов в Synapse Service Mesh
(ограничение из определения SRLS — «защищаемые сервисы, исполняемые в
рамках Synapse Service Mesh»).

### C6. Отказоустойчивость и DR (вес 10)

| Уровень | Якорь |
|---|---|
| 0 | Раздела нет; один кластер на контур; потеря ЦОД = потеря контура |
| 2 | Компоненты в обоих кластерах; GEOH упомянут; но поведение при переключении АБС (INF-02) не описано, HA брокера SMBX заявлено фактом (не раскрыто в источниках), расчёт буфера K2 отсутствует |
| 4 | Развёртывание в кластерах OpenShift обоих ЦОД (INF-01), GEOH как источник health-ответов для внешнего балансировщика (агрегированный/по группе/по префиксу — документированные сценарии) с корректной оговоркой: GEOH отвечает на опросы балансировщика, а не «сам переключает трафик»; сценарии отказа разобраны: под/узел (горизонтальное масштабирование — НФО продукта), кластер/ЦОД (NFR-02, RTO контура ≤ 15 мин), АБС (контур живёт на буфере SMBX; sync-классы деградируют контролируемо), переключение АБС active/standby без перенастройки потребителей (INF-02); расчёт буфера K2 выведен: 250 TPS × 4 ч ≈ 3,6 млн сообщений (NFR-05), догруз ≤ 45 мин ⇒ требуемая скорость сброса ~1 300+ msg/s — число выведено, а не заявлено; HA SMBX и гарантии доставки честно в «проверить у вендора» (§1.11) с компенсирующими мерами; производительность — в план НТ на SYTE, не выдумана |

**Ловушки:** «GEOH переключит трафик на второй ЦОД» (он — healthcheck для
балансировщика); «SMBX кластеризован active-active» как факт; RTO
контура, превышающий RTO самой АБС, без объяснения; буфер «4 часа»
принят без пересчёта в сообщения/ёмкость.

### C7. Поэтапный перевод потребителей (вес 10)

| Уровень | Якорь |

```json

  "run_id": "string",
  "run_mode": "agentic",

      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T2"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.

## 8. Калибровка и контроль качества судей

1. Перед запуском бенчмарка подготовить три эталонных ответа (`gold`,
   `silver`, `fail`) и убедиться, что медиана ансамбля судей попадает в
   `expected_totals`.
2. Считать согласованность судей по каждому критерию; при
   `alpha < 0.75` — уточнить якоря (ожидаемо проблемные: C4 — граница
   между «документированным XA» и «проектным решением»; C5 — что считать
   обоснованным отказом от SRLS).
3. Для 10 % прогонов проводить выборочную проверку человеком;
   расхождение > 1 балла по критерию фиксируется как инцидент
   калибровки.
4. При обновлении версий AM/SEI или документации — обновить CONTEXT §1,
   таблицу ловушек §4 и `docs_snapshot_date`; повысить `version` рубрик
   и перепрогнать эталоны.
5. Не показывать решающим таблицу ловушек §4 и якоря уровня 4 — они
   предназначены только для судей и составителей.
