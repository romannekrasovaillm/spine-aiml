## 1. Продукт: Platform V SynGX (SNX) 4.3.0 `[DOC]`

### 1.1 Позиционирование и состав

- SynGX — продукт для промышленной эксплуатации в качестве
  высокопроизводительного и безопасного **веб- и обратного
  прокси-сервера** на кодовой базе **Nginx 1.28.3** при обработке сетевых
  запросов к критически важным для бизнеса веб-ресурсам.
- Цель создания — альтернатива коммерческим **Nginx PLUS** и **HAProxy
  Enterprise** (недоступны в РФ) для пользователей OSS Nginx, которым
  нужны дополнительная функциональность и коммерческая поддержка.
  Продукт — полностью отечественная разработка, входит в Реестр
  российского ПО; вендор декларирует ежегодный переход на актуальную
  стабильную версию Nginx.
- Документация фиксирует ровно два паттерна применения: **веб-сервер**
  (отдача статического контента) и **обратный прокси-сервер**
  (маршрутизация и балансировка запросов с учётом отказов инсталляций
  сервиса и изменений инфраструктуры: активные healthcheck,
  автообновление IP экземпляров по DNS, sticky, разрыв клиентских
  соединений при выпадении всех узлов группы).
- SynGX — **VM-продукт** (поставка zip-архивом с RPM/DEB-пакетами,
  управление через systemd-юнит `syngx.service`), а не K8s-оператор.
- Поддерживаемые ОС (x86_64): SberLinux OS Server 8.10
  (**рекомендовано**), SberLinux 9.3, Альт 10 СП, RHEL 8.7, RedOS 8.0
  (RPM); Ubuntu 20.04/22.04/24.04, Debian 12.0, AstraLinux SE 1.8 (DEB).
- Системные требования: минимальная ВМ — 2 CPU / 2 ГБ RAM / 10 ГБ диск /
  NIC ≥ 1000 Мбит/с; горизонтальное масштабирование заявлено («Да»);
  «не рекомендуется размещение двух и более СПО на одной ВМ»; для
  промышленной эксплуатации оптимальную конфигурацию определять
  нагрузочным тестированием.
- Бинарь `syngx`; конфигурация по умолчанию `/opt/syngx/conf/syngx.conf`;
  журналы по умолчанию `/opt/syngx/logs/`; управление сигналами
  `syngx -s stop|quit|reload|debug|nodebug`; ротация журналов —
  logrotate. Временная диагностика «на лету»: `syngx -s debug`
  (директива `detailed_log`, по умолчанию debug на 30 с), возврат —
  `nodebug`, без reload.

### 1.2 Доработки относительно OSS Nginx 1.28.3

- Расширенные метрики работоспособности, в т.ч. формат **Prometheus**,
  подключаемые несколькими директивами в конфигурации.
- **Active health checks** для TCP, UDP, HTTP, HTTPS, TCP TLS.
- **Lua** и **JavaScript (njs)** для собственной логики обработки
  запросов; модули манипуляции HTTP-заголовками, sticky session,
  **GeoIP**, туннелирование TLS-соединений.
- **slow start** — плавная подача нагрузки на узел, введённый в
  балансировку; улучшенная проверка конфигурации с большим числом групп
  балансировки.
- Автозагрузка TLS-сертификатов и секретов из **HashiCorp Vault**
  (модуль `ngx_hashicorp_vault_module`); поддерживается также Secret
  Management System (SecMan): «упоминание HashiCorp Vault считать
  аналогичным интеграции с SecMan».
- **sticky route** и **sticky learn**; периодическое обновление IP узлов
  группы балансировки **по DNS** без перезагрузки; отклонение входящих
  TCP-соединений при выпадении всех узлов группы балансировки.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Доработки SynGX относительно OSS Nginx 1.28.3»); `corpus/pv_docs/txt/snx__documents__about__advantages.html.txt`.

### 1.3 Балансировка, динамический upstream, L4/stream

- Алгоритмы балансировки в секции `upstream`: **(Weighted) Round Robin**
  (по умолчанию), **(Weighted) Least Connections** (`least_conn`),
  **IP Hash** (`ip_hash`, только HTTP), **Hash по ключу** (`hash`),
  **Random** (`random`); протоколы: Round Robin / Least Conn / Hash /
  Random — HTTP, TCP, UDP. `weight` опционален (по умолчанию 1); с
  hash/ip_hash нельзя параметр `backup`. Директивы keepalive upstream —
  строго ПОСЛЕ настроек балансировки.
- Sticky-сессии: `sticky cookie` (cookie выставляет SynGX;
  предпочтительный синтаксис; `sticky name=` объявлен устаревшим и «в
  следующих версиях поддерживаться не будет»), `sticky route` (маршрут
  из cookie/URI), `sticky learn` (cookie выставляет upstream-узел, SynGX
  запоминает привязку в shared memory zone). Со sticky нельзя
  использовать `backup`. Если узел выведен healthcheck — выбор идёт по
  алгоритму балансировки, как будто привязки нет. `no_fallback` → 502,
  если узел из cookie недоступен.
- Динамический upstream по DNS: параметр `resolve` у `server` +
  `resolver` + `zone` (~16 КБ shared memory на server с `resolve`)
  обновляют IP без перезагрузки; `server_auto_resolver` управляет всеми
  серверами группы; `service=http` — SRV-записи. Изменения применяются в
  памяти без reload; добавление/удаление серверов логируется. Если в
  группе с `resolve` не был включён active healthcheck, для его включения
  требуется **остановка и запуск** SynGX (не reload). Для предотвращения
  DNS-спуфинга рекомендуется использовать DNS-серверы в защищённой
  доверенной локальной сети.
- `slow_start=<time>` у `server` — плавный рост веса от 0 до номинала
  при возврате узла; только http; несовместим с hash/ip_hash/random.
- **L4/stream-режим**: проксирование TCP/UDP; активные проверки stream —
  типы `udp`, `tcp`, `http`, `ssl_hello`, `tcp_tls`; `match_drain`
  (stream) — состояние **DRAIN**: новые соединения не устанавливаются,
  существующие доживают. Метрики L4: `nginx_sts_*`, `l4check_upstream_*`.
  Интеграция с Vault действует и в stream (сертификаты заменяют
  директивы `ssl_certificate*`/`proxy_ssl_certificate*` в http и
  stream). В дистрибутиве есть директива `grpc_ssl_certificate` в
  перечне заменяемых Vault-потоком (http).

### 1.4 TLS и mTLS на обоих стыках, HashiCorp Vault

- TLS для соединений клиент ↔ SynGX и SynGX ↔ upstream-узел; «необходимо
  использовать версию протокола TLS не ниже 1.2».
- Контроль доступа: по сетевым адресам (ACL), HTTP Basic Authentication,
  **подзапрос к внешнему сервису авторизации** (auth-request), **проверка
  Common Name в клиентском TLS-сертификате** (CN/SAN).
- В дистрибутиве есть модуль **nginx-auth-jwt** (пакет `auth-jwt`) —
  проверка JWT в запросах; заявлены «проверки токенов в запросах» через
  собственную логику.
- Проверка сертификата backend-узла: `proxy_ssl_verify on` +
  `proxy_ssl_trusted_certificate` (+ `proxy_ssl_protocols`,
  `proxy_ssl_ciphers`). Клиентский сертификат шлюза к backend —
  `proxy_ssl_certificate` / `proxy_ssl_certificate_key`. Параметр `sn` у
  `server` в upstream переопределяет имя узла для проверки сертификата и
  SNI (приоритетнее `proxy_ssl_name`; действует и для healthcheck);
  `sn` и `tag` совместно запрещены.
- **Интеграция с HashiCorp Vault** (`ngx_hashicorp_vault_module`,
  директива `delayed_load_cert;` + ОДИН блок `hv_pki <имя>` для
  PKI-движка или `hashicorp_vault <имя>` для KV-движка): аутентификация
  по AppRole (role_id + wrapped_token → unwrap → secret_id → client
  token → fetch). Публичная часть сертификата пишется на файловую
  систему, **закрытый ключ — только в shared memory** (доступ у master и
  privileged-агента); в сырой странице документации: «SynGX сохраняет
  сертификаты на файловую систему, а ключи сертификатов в оперативную
  память». SynGX следит за сроком действия и сам запрашивает новый
  сертификат с перезагрузкой при его изменении
  (`update_expiring_cert_interval`). Сертификаты из Vault заменяют
  директивы `ssl_certificate*` / `proxy_ssl_certificate*` /
  `grpc_ssl_certificate*` / `snx_ahc_ssl_certificate*` в http и stream —
  т.е. поток покрывает и серверный сертификат шлюза, и **клиентский
  сертификат шлюза к backend (второй стык mTLS)**. TLS-подключение к
  Vault рекомендовано обязательно (`hv_ssl_verify on`,
  `hv_ssl_protocols TLSv1.2`).
- Подводные камни Vault-интеграции: между использованием wrapped_token и
  получением нового **stop/quit/reload блокируются** (проверяется файл
  wrapped_token; «остановка SynGX приведет к невозможности его старта
  после остановки»); `systemctl stop syngx` обходит это скриптом с
  повторными попытками, для `systemctl restart` такого скрипта НЕТ;
  `reload` использует ранее полученные сертификаты, новые запрашиваются
  только при изменении секций `hv_pki`; поддерживается только ОДИН блок
  `hv_pki`/`hashicorp_vault` на инстанс (два блока с разными role_id не
  поддерживаются; внутри блока — несколько секций `get_cert` под разные
  сертификаты); при reload с неверными параметрами `get_cert` текущие
  сертификаты теряются; обновление role_id — только с остановленным
  SynGX.
- **kTLS** (kernel TLS) при отдаче статики/кеша: требует ядро ≥ 5.2
  (CONFIG_TLS) и openssl ≥ 3.0 — из поддерживаемых ОС подходит только
  SberLinux 9; на файлах < 16 КБ возможно замедление.
- В дистрибутиве — модуль `sslkeylog` (запись TLS-сессионных ключей для
  диагностики трафика).
- Директива `hide_syngx_name on` — скрыть имя сервера в заголовках и теле
  стандартных 3xx/4xx/5xx-ответов.

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Терминация TLS и сертификаты»); `references/patterns-config.md` (раздел «TLS и HashiCorp Vault»); `references/operations.md` (раздел «Подводные камни Vault-интеграции»); `corpus/pv_docs/txt/snx__documents__about__use-case-syngx-hashicorp-vault.html.txt`, `snx__documents__about__non-functional-requirements.html.txt`, `snx__documents__administration-guide__administration-scenarios-syngx.html.txt`.

### 1.5 Rate limiting и квоты

- Базовый модуль `ngx_http_limit_req_module`: `limit_req_zone` +
  `limit_req` (алгоритм leaky bucket, **ключ зоны — произвольная
  переменная**, параметры `burst`/`nodelay`/`delay`, `limit_req_status`,
  `limit_req_dry_run`). Оценка памяти: 1 МБ зоны ≈ 16 тыс. состояний по
  64 Б (8 тыс. по 128 Б).
- Добавлены пороги уведомлений `notify_info`/`notify_warn`/`notify_err`
  (проценты от лимита → сообщения в error.log) и переменная
  `$limit_req_status` (PASSED/DELAYED/REJECTED/DELAYED_DRY_RUN/
  REJECTED_DRY_RUN).
- **`limit_req_by_node`** — SynGX-специфичное квотирование «на каждый
  узел в группе балансировки» (http/upstream): «позволяет предотвращать
  каскадный отказ серверов при уменьшении количества работающих узлов»;
  свой код ответа (`limit_req_status_by_node`, по умолчанию 503),
  dry-run, уровень логирования.
- **Мониторинг лимитов**: `limit_req_monitor` отдаёт по зонам JSON или
  Prometheus (счётчики зон, keys_count, requests_delayed/rejected,
  гистограмма средних скоростей по ключам, EMA).
- **Горячее управление**: location с `limit_req_change;` — PATCH-запросом
  временно менять `rate` зоны без reload (с `duration`; по истечении
  duration возврат к значению из конфигурации; повторный PATCH отменяет
  предыдущий), DELETE — вернуть исходный rate. Доступ **только с
  127.0.0.1 / unix-сокета** — иначе `[emerg] insecure server ... The
  "limit_req_change" directive can only be used for the ip address
  127.0.0.1 or a unix socket`. События изменения лимитов пишутся в
  audit.log.
- В Lua-пакете дистрибутива — библиотека `lua-resty-limit-traffic`.
- Известная ловушка: изменение ключа/имени зоны `limit_req_zone` через
  reload **не применяется** (reload «успешен синтаксически», но SynGX
  остаётся на старой конфигурации; диагностика — `Failed to reload
  SynGX` в error.log/audit.log; для вступления в силу нужен stop+start).

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (раздел «Rate limiting»); `references/patterns-config.md` (раздел «Rate limiting»); `references/operations.md` (раздел «FAQ администратора»); `corpus/pv_docs/txt/snx__documents__administration-guide__administration-scenarios-syngx.html.txt`.

### 1.6 Отказоустойчивость и HA

- **Active healthcheck** (модули `nginx_upstream_check_module` для L7 и
  `ngx_stream_upstream_check_module` для L4): директива `check` в
  upstream (`interval` умолч. 10000 мс и должен быть > `timeout`;
  `timeout` 3000 мс; `fall` 5; `rise` 2; `default_down` true; `port`;
  `type`; `mandatory`; `persistent`). Типы проверок http: tcp,
  tls_handshake (ssl_hello устарел с 3.4.0), http, https; stream: udp,
  tcp, http, ssl_hello, tcp_tls. Секции `match` задают условия
  работоспособности по ответу. JSON-статистика:
  `active_healthcheck_status` (ON/OFF/DRAIN/UNDEFINE), счётчики
  rise/fall.
- **Составные проверки**: исключение узла по произвольной комбинации
  активных/пассивных проверок ДРУГИХ узлов через Lua-модули
  (`ngx.upstream.get_primary_peers` и др.) в privileged-агенте; для
  синхронизации между workers обязателен `zone` в upstream.
- При выпадении всех узлов группы: `send_rst` (http) и модули
  `ngx_http_rst_send_module`/`ngx_stream_rst_send_module` (через
  iptables, `depending_server`) разрывают клиентские соединения — узел
  SynGX «закрывает» точку входа, пока upstream мёртв (fail-closed).
- Отказоустойчивость самого процесса: master поддерживает заданное число
  рабочих процессов и перезапускает упавшие; распределение соединений по
  workers — на уровне ядра ОС. При деградации ресурсов SynGX «сначала
  начинает увеличивать среднее время обработки запросов, а затем
  начинает отказывать в обработке новых запросов», при снижении нагрузки
  сам восстанавливается.
- **reload**: master проверяет синтаксис, запускает новые workers,
  старые доживают текущие запросы на старой конфигурации (без разрыва
  установленных соединений); при невозможности применить — откат на
  старую конфигурацию. **stop** — все соединения сбрасываются.
- **Межинстансовая кластеризация SynGX** (VRRP/keepalived, синхронизация
  состояния между ВМ) в документации **НЕ описана**; горизонтальное
  масштабирование заявлено, но схема — за внешним балансировщиком.
- Вертикальное масштабирование — workers по ядрам CPU.

### 1.7 Мониторинг, журналы, аудит, трассировка

- Метрики — **только pull**: SynGX отдаёт метрики по HTTP GET (JSON /
  Prometheus / HTML); «возможность настроить SynGX, чтобы он
  самостоятельно отправлял метрики в какую-либо систему, не
  предусмотрена». Вендор требует защищать эндпоинты метрик: TLS ≥ 1.2,
  имя/пароль, ограничение по сетевым адресам.
- Модули-источники метрик: nginx-module-vts (трафик и состояния
  серверов), ngx_http_extstatus (`snx_http_extstatus_json`,
  `snx_http_certificates_status_json` и др.), upstream_check
  (`check_upstream_*`), stream (`l4check_upstream_*`), sts
  (`nginx_sts_*`), hashicorp_vault (`vault_certificate_expiration_days`,
  `vault_last_fetch_time_seconds`, `vault_fetch_errors_total`).
  Prometheus-метрики семейства `syngx_mtx_*`,
  `syngx_http_requests_total{code}`, `syngx_ssl_handshakes_total`,
  `syngx_ssl_verify_failures{name}` и др.
- В дистрибутиве — готовая **Grafana Dashboard** (SynGX Status,
  Connections, HTTP Requests, TLS, Cache Usage, Shared Memory Usage).
- Журналы: error.log (уровни emerg…debug; директива `required` запрещает

  Отправка: файлы, syslog, внешние RSYSLOG/fluentbit; «в SynGX нет

  рекомендациями; провайдеры LLM — OpenAI-совместимый API или GigaChat
  API V2 (модель GigaChat-2-Max в системных требованиях); ключ — явно

### 1.9 Чего в продукте НЕТ (важно для границ решения)

- **Service mesh**: sidecar-прокси, control plane (централизованное
  распространение политик и идентичностей), автоматическая выдача и
  ротация сертификатов сервисов, декларативные политики mTLS «между
  всеми» — в документации SNX 4.3.0 **не описаны**. SynGX — VM-продукт
  (обратный прокси/веб-сервер), а не mesh. В линейке СберТеха east-west
  Service Mesh в K8s позиционируется за отдельным продуктом семейства
  Synapse (SSM) — вывод дистиллята по карте семейства, не факт вендора;
  в данной задаче SSM вне scope поставки.
- **WAF / ModSecurity**: в документации SNX 4.3.0 не упоминается ни
  разу. Защитные функции ограничены: ACL по адресам, Basic Auth,
  auth-request к внешнему сервису, проверка CN/SAN клиентского
  сертификата, rate limiting, GeoIP-фильтрация, проверка JWT
  (nginx-auth-jwt).
- **API-management**: портал разработчика, каталог API, управление
  жизненным циклом API, авторизационный сервер OAuth2 (выдача токенов),
  биллинг/тарификация — в составе SynGX отсутствуют.
- **ГОСТ-криптография TLS**: поддержка ГОСТ-шифрования/ГОСТ-TLS в
  скачанных страницах документации SNX 4.3.0 **не упоминается**
  `[ТРЕБУЕТ ПРОВЕРКИ]` — легитимный открытый вопрос к вендору, а не факт
  в любую сторону.
- Межинстансовая кластеризация (см. §1.6), push-отправка метрик и
  запись логов в Kafka напрямую (см. §1.7).

Источник: `spine-bank/banking/plugins/ru-integration/skills/syngx-api-gateway/SKILL.md` (разделы «Место в семействе Synapse», «WAF — НЕ обнаружен», «Антипаттерны и риски решений», «HA и отказоустойчивость»); проверка отсутствия упоминаний — полнотекстовый поиск по `corpus/pv_docs/txt/snx__*.txt` (service mesh, sidecar, ГОСТ — 0 совпадений на дату снимка).

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "ТерраКапитал"» (вымышленный, топ-30 по активам) реализует
программу **«Доверенный контур»** — переход внутренних взаимодействий на
модель **zero-trust**. Драйверы:

- Аудит ИБ показал: значительная часть east-west трафика между АС идёт по
  HTTP без шифрования внутри «доверенного» периметра; на половине АС
  используется единый wildcard-сертификат `*.svc.terracapital.local`;
  лимитов между системами нет.
- Инцидент (Q2 2026): АС отчётности из-за ошибочного цикла вызовов
  создала шторм ~4 000 RPS на АС ДБО-ядра; каскадный отказ вывел
  интернет-банк на 40 минут.
- Регуляторный контекст: контур обрабатывает данные, подпадающие под
  требования ГОСТ Р 57580.1-2017 (защита финансовых операций) и
  внутренний стандарт ИБ банка «Сегментация и взаимная аутентификация
  сервисов» (вступает в силу 01.01.2027).
- Целевое состояние: весь межсистемный синхронный API-трафик проходит
  через **сегментные шлюзы** на базе **Platform V SynGX 4.3.0**
  (продукт утверждён советом по импортозамещению; лицензии закуплены).

### 2.2 Ландшафт AS-IS

- **40 АС**, ~120 задокументированных синхронных интеграционных потоков
  «потребитель → поставщик» (точечные связи напрямую, без шлюзов).
- Подключения разнородны: ~60 % потоков — HTTPS с проверкой сертификата,
  ~25 % — plain HTTP внутри периметра, ~15 % — собственные TCP-протоколы
  поверх TLS (казначейство).
- Аутентификация потребителей: где-то по API-ключам в заголовках, где-то
  по IP-адресам, где-то отсутствует. Единого реестра идентичностей АС
  нет; wildcard-сертификат `*.svc.terracapital.local` установлен на
  ~20 АС.
- Лимитов между системами нет (см. инцидент §2.1).
- Логи — локальные файлы на серверах АС, в SIEM попадают с задержкой до
  часа; сквозной трассировки вызовов между АС нет.
- Внедрён пилот OSS Nginx как «внутренний прокси» в 2 сегментах —
  конфигурация вручную, без healthcheck, без лимитов на потребителя.

### 2.3 Топология и нагрузка `[BENCH]`

- Два ЦОД (ЦОД-1 «Северный», ЦОД-2 «Южный»), ~40 км между площадками,
  каналы 2×10 Гбит/с; АС развёрнуты active/active в обоих ЦОД.
- Внутренний контур разделён на **6 контуров безопасности (сегментов)**,
  изолированных межсетевыми экранами (МЭ):
  | # | Сегмент | Примеры АС | Пик входящего API-трафика (RPS) |
  |---|---------|-----------|-------------------------------|
  | 1 | ДБО-ядро | интернет-банк, мобильный бэкенд | 3 000 |
  | 2 | Карточный процессинг | авторизации, токенизация | 2 600 |
  | 3 | Кредитный конвейер | скоринг, андеррайтинг | 2 200 |
  | 4 | DWH/аналитика | отчётность, витрины | 1 600 |
  | 5 | Казначейство/рынки | ликвидность, дилинг (часть — TCP/TLS) | 1 400 |
  | 6 | Общесервисный | справочники, нотификации | 1 200 |
- Суммарный пик east-west API: **12 000 RPS** (штатно распределяется
  ~50/50 между ЦОД); средний размер ответа **12 КБ**; короткие
  HTTP/JSON-запросы; ~10 % потоков карточного сегмента — gRPC; в
  казначействе 3 АС общаются собственным протоколом **TCP поверх TLS**.
- Топ-5 пар «потребитель → поставщик» дают ~45 % трафика; хвост — пары
  по 1–20 RPS. Соединения stateless (REST/gRPC, без «прилипания»).
- Прогноз роста **+25 % трафика в год**; число АС к концу 2028 — до 60.
- Каждая АС-поставщик развёрнута кластером из 2–6 узлов (ВМ) в каждом
  ЦОД; состав кластеров меняется при релизах, узлы регистрируются во
  внутреннем DNS банка.

| NFR-02 | Полная потеря ЦОД: переключение внутреннего трафика на второй ЦОД | автоматически (DNS/L4), RTO ≤ 15 мин для критичных сегментов |

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | TLS для всех соединений: АС-потребитель ↔ шлюз, шлюз ↔ АС-поставщик, шлюз ↔ Vault, шлюз ↔ коллектор трассировки; версии протокола не ниже 1.2, предпочтительно 1.3; plain HTTP между системами выводится из эксплуатации |
| SEC-02 | **Взаимная** аутентификация на обоих стыках: потребитель предъявляет клиентский сертификат своей АС; шлюз предъявляет клиентский сертификат АС-поставщику; АС-поставщик проверяет сертификат шлюза |
| SEC-03 | Идентичность АС = уникальный сертификат на систему (CN/SAN = системный идентификатор); проверка по реестру ИБ (INF-05); wildcard- и «общие» сертификаты на группу АС **запрещены** |
| SEC-04 | Закрытые TLS-ключи шлюзов **не должны храниться файлами на ВМ**; источник сертификатов — Vault банка (INF-03) |
| SEC-05 | Аудит событий идентификации (какая АС вызывала), авторизации и изменений конфигурации; выгрузка в SIEM |
| SEC-06 | Служебные эндпоинты (метрики, управление лимитами, ИИ-агент) — только из внутреннего контура управления / loopback, с TLS и ограничением по адресам |
| SEC-07 | Ротация TLS-сертификатов шлюзов автоматически, без остановки обслуживания; контроль сроков действия с оповещением |
| SEC-08 | В ответах не раскрываются технические детали (имя и версия прокси-сервера, внутренние имена узлов АС) — требование zero-trust действует и внутри периметра |
| SEC-09 | Запрет debug-уровня журналирования в промышленном контуре (допускается только штатная кратковременная диагностика) |
| SEC-10 | Весь административный доступ к ВМ шлюзов — персонализированный, через PAM (INF-06) |

### 2.7 Модель лимитов между системами `[BENCH]`

- Профили пар «потребитель → поставщик» (NFR-04): «Базовый» 50 r/s
  (умолчание для новых пар), «Повышенный» 200 r/s, «Критичный» 500 r/s
  (топ-5 пар). Превышение — отказ 429, платного овердрафта нет.
- Матрица профилей ведётся ИБ совместно с владельцами АС и поставляется
  через GitOps (INF-06).
- Инцидентные изменения: дежурная смена может временно (до 24 часов)
  изменить лимит пары с автоматическим возвратом (NFR-06); каждое такое
  изменение должно попадать в аудит (SEC-05).
- Ожидаемое число ключей лимитирования: до ~500 активных пар
  «потребитель × поставщик» на сегментный шлюз.

### 2.8 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами; обязательная альтернатива к
  разбору — «полноценный service mesh» (см. INF-07: 34 из 40 АС — не
  K8s).
- Комитет особенно чувствителен к трём вопросам: (1) **не приписаны ли
  SynGX функции, которых в продукте нет** (service mesh, API-management,
  WAF, кластеризация); (2) как выполняется NFR-06 (горячее изменение
  лимитов) без ущерба SEC-06; (3) как решение покрывает **второй стык
  mTLS** (шлюз → АС-поставщик), а не только входящий.
- Открытый вопрос ИБ, который комитет ожидает увидеть в записке:
  применимость **ГОСТ-криптографии TLS** для части потоков казначейства
  (в документации SynGX не описана — см. §1.9; оформить как
  `[ТРЕБУЕТ ПРОВЕРКИ]` у вендора, не как факт).

### 2.9 Что можно принять допущением `[ASSUME]`

- Внутренний DNS банка корректно исключает недоступный ЦОД/узел за время
  ≤ 5 мин; детали — вне scope.
- АС-поставщики выдерживают пиковую нагрузку при исправных шлюзах; их
  ёмкость — вне scope.
- МЭ банка могут ограничивать потоки «АС → шлюз» и «шлюз → АС» на уровне
  L3/L4 по заявке; политики МЭ согласуются отдельным процессом ИБ.
- Коллектор OpenTelemetry банка принимает спаны по TLS и поддерживает
  mTLS; детали версии — вне scope.
- Для 5 устаревших АС (INF-08) допустимы временные компенсирующие меры
  с явным сроком вывода (конец 2027).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| East-west трафик | обращения между внутренними системами банка (в отличие от north-south — входящего извне) |
| Сегментный шлюз | пара/тройка ВМ SynGX на границе контура безопасности, принимающая весь входящий API-трафик сегмента |
| АС | автоматизированная система банка |
| upstream | группа узлов АС-поставщика, на которую SynGX проксирует запросы |
| mTLS | взаимная аутентификация TLS: обе стороны предъявляют сертификаты |
| zero-trust | модель «не доверять периметру»: каждый вызов аутентифицируется и авторизуется независимо от сетевого положения |
| service mesh | инфраструктурный слой (sidecar-прокси + control plane) для east-west трафика; **не** функция SynGX |
| leaky bucket | алгоритм ограничения скорости запросов (limit_req) |
| DRAIN | состояние узла: новые соединения не принимаются, существующие доживают |
| fail-closed | при недоступности всех узлов АС-поставщика шлюз разрывает соединения, а не обслуживает «вслепую» |
| pull-модель метрик | система мониторинга сама опрашивает эндпоинты SynGX |
| dry-run (limit_req) | режим, в котором превышения только фиксируются, но не отклоняются |
| МЭ | межсетевой экран |
