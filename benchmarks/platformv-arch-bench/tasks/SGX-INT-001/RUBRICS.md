# Рубрики оценки для задачи SGX-INT-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о SynGX,
   которого нет в §1 и которое не помечено решающим как допущение,
   считается **непроверенным**; если оно ещё и ложно — **ложным**. Судья
   не должен «додумывать» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие ключевого
   слова или директивы.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. Режим прогона фиксирован: `agentic`. Утверждения за пределами
   CONTEXT.md §1 должны быть помечены как допущения либо подтверждены
   ссылкой на документацию SynGX 4.3.0.
7. Судья не оценивает стиль и «красоту» сверх C10 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | SynGX представлен как **service mesh** или API-шлюз/API-management: ему как **встроенные факты продукта** приписаны функции, которых нет в документации, — sidecar-прокси, control plane (централизованная выдача идентичностей/политик), автоматический mTLS «между всеми сервисами», портал разработчика, каталог API, авторизационный сервер OAuth2, WAF, биллинг | Только судья: семантическая проверка по CONTEXT §1.9 и таблице ловушек T1–T4 (частично ловится regex mechanical_checks: упоминание service mesh/sidecar/WAF/OAuth2-сервера в контексте «встроенный/штатный/в составе SynGX») |
| HF-02 | Заявлено, что SynGX **сам** отправляет метрики во внешние системы (push) или пишет логи напрямую в Kafka «из коробки» | Только судья + regex mechanical_checks (характерные формулировки); сверка с CONTEXT §1.7 |
| HF-03 | HA решён «встроенной кластеризацией SynGX» (межинстансовый VRRP/keepalived/синхронизация состояния как функция продукта) без явной пометки, что это внешнее решение; либо топология с единственной точкой отказа на уровне сегментного шлюза при NFR-01 | Только судья: сверка с CONTEXT §1.6; проверить наличие внешнего балансировщика (L4 VIP из INF-01) в схеме |
| HF-04 | Закрытые TLS-ключи шлюзов хранятся файлами на ВМ при наличии документированного потока Vault (ключи только в shared memory) — без явного обоснования отказа и компенсирующих мер (нарушение SEC-04) | Только судья: раздел идентичности/mTLS, сверка с CONTEXT §1.4 и SEC-04 |
| HF-05 | Эндпоинт горячего управления лимитами (`limit_req_change`) выставлен за пределы loopback/unix-сокета (нарушение документированного ограничения и SEC-06) | Только судья: проверить, где размещён location управления лимитами и кто к нему обращается |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 | Механическая проверка (mechanical_checks.deliverables) + A-01 |

## 3. Критерии

### C1. Фактическая корректность по SynGX (вес 15)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md
§1; корректные наименования компонентов и директив; отделение фактов от
допущений; корректная работа с «отрицательными» фактами §1.9.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02/HF-03, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (Vault-поток, limit_req_change, active healthcheck, pull-модель метрик), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение или «проверить у вендора»; правильно различаются: факты документации и выводы дистиллята; OSS Nginx и доработки SynGX; роль SynGX (обратный прокси) и внешних систем (УЦ, Vault, SIEM, IdP/сервис авторизации); ГОСТ-TLS подан как открытый вопрос, а не факт |

**Признаки сильного ответа:** использует официальные имена и директивы
(`limit_req_zone`/`limit_req`, `limit_req_by_node`, `limit_req_monitor`,
`limit_req_change`, `check`, `resolve`, `send_rst`, `proxy_ssl_verify`/
`proxy_ssl_certificate`, `ngx_hashicorp_vault_module`,
`hv_pki`/`hashicorp_vault`, `audit_log`, `nginx-otel`); упоминает кодовую
базу Nginx 1.28.3; явно фиксирует, что service-mesh-функций и
межинстансовой кластеризации в продукте нет; не заявляет WAF/портал/
каталог/OAuth2-сервер/ГОСТ-TLS как функции SynGX.

**Типичные ошибки:** «SynGX обеспечит service mesh для east-west
трафика»; «SynGX отправляет метрики в Prometheus»; «ноды SynGX
объединяются в кластер»; «SynGX поддерживает ГОСТ-шифрование» как факт;
изобретение директив.

### C2. Топология сегментных шлюзов, балансировка, DR (вес 12)

**Что оценивается:** D2 + D3 (топологическая часть). Размещение узлов
SynGX по 6 сегментам и 2 ЦОД, использование существующих L4 VIP и
внутреннего DNS (INF-01), сценарии отказа узла SynGX, всех узлов
сегментного шлюза ЦОД и потери ЦОД (NFR-01, NFR-02), расчёт числа узлов
(NFR-03), масштабирование (NFR-10).

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; одна ВМ SynGX на сегмент; HF-03 |
| 2 | По паре ВМ SynGX на сегмент за L4 VIP в каждом ЦОД; но: число узлов не выведено из нагрузки по сегментам, поведение при потере ЦОД описано декларативно, SPOF где-то остались |
| 4 | (a) схема: ≥ 2 ВМ SynGX на сегментный шлюз в каждом ЦОД за L4 VIP (INF-01, INF-02 — одна ВМ = один СПО), внутренний DNS распределяет вызовы между ЦОД и исключает площадку при отказе (допущение §2.9) с увязкой к RTO ≤ 15 мин (NFR-02); (b) **расчёт числа узлов из нагрузки по сегментам**: крупнейший сегмент 3 000 RPS в штате / 3 000 × 1,3 = 3 900 RPS при потере ЦОД против замера вендора 3 800 оп/с проксирования (ответ 100 КБ, ≤ 50 % CPU) — с корректной оговоркой, что замер вендора для ответа 100 КБ, а профиль банка (12 КБ) требует **собственного нагрузочного тестирования** (документированная рекомендация вендора), и с выводом по числу ВМ в пределах лимита INF-02 (3 ВМ/ЦОД для критичных сегментов, 2 ВМ — для остальных) или явным риском при его недостаточности; (c) разбор отказа одной ВМ SynGX (L4 VIP + health-check балансировщика), отказа всех ВМ сегмента в ЦОД (DNS/L4), возврата ЦОД; (d) горизонтальное масштабирование «добавить ВМ за VIP / добавить сегментный шлюз» под NFR-10 (до 60 АС) |

**Ловушки:** «ноды SynGX объединены в кластер с плавающим IP»
(кластеризации в продукте нет); VRRP/keepalived, поданный как функция
SynGX; цифра «3 800 оп/с» применена к профилю 12 КБ без оговорки о
нагрузочном тестировании; единый шлюз на все 6 сегментов (сводит
zero-trust сегментацию на нет и создаёт SPOF/megablast radius);
DR «переключим вручную конфиги» вместо DNS/L4.

### C3. Идентичность АС и mTLS на обоих стыках, Vault (вес 15)

**Что оценивается:** D4, покрытие SEC-01, SEC-02, SEC-03, SEC-04,
SEC-07, INF-03, INF-05, INF-08.

| Уровень | Якорь |
|---|---|
| 0 | HF-04, либо mTLS заявлен только на входящем стыке, а к АС-поставщикам — plain HTTP без обоснования (нарушение SEC-01/SEC-02), либо общий/wildcard-сертификат на все АС подан как решение (нарушение SEC-03) |
| 2 | mTLS на обоих стыках назван, но: идентичность потребителя не связана с реестром CN/SAN (INF-05); клиентский сертификат шлюза к backend не привязан к Vault-потоку; ротация декларативна; 5 устаревших АС (INF-08) не учтены |
| 4 | TLS ≥ 1.2 (предпочтительно 1.3) на всех четырёх стыках SEC-01; входящий стык: проверка CN/SAN клиентского сертификата АС из УЦ банка по реестру ИБ, поставляемому GitOps (SEC-02, SEC-03, INF-05); исходящий стык: `proxy_ssl_verify on` + `proxy_ssl_trusted_certificate` + клиентский сертификат шлюза (`proxy_ssl_certificate*`) — источник обоих — Vault через `ngx_hashicorp_vault_module` (один блок `hv_pki` на инстанс, отдельные `get_cert` под серверный и клиентский сертификаты; Vault заменяет `ssl_certificate*`/`proxy_ssl_certificate*` в http и stream — покрывает и TCP/TLS-потоки казначейства), закрытые ключи только в shared memory (SEC-04); автообновление сертификатов `update_expiring_cert_interval` + метрика `vault_certificate_expiration_days` (SEC-07); для 5 устаревших АС (INF-08) — явное временное исключение с компенсирующими мерами (отдельный listen/локейшн + ACL по адресам + усиленный аудит) и сроком вывода (конец 2027), а не молчаливое послабление для всех; учтены подводные камни Vault-потока (блокировка stop/reload при ротации wrapped_token, один блок hv_pki, reload не запрашивает новые сертификаты без изменения hv_pki) и поведение при недоступности Vault |

**Ловушки:** «сертификаты положим файлами, так проще» (HF-04); mTLS
только на входе, к backend — «доверенная сеть» (сводит zero-trust на
нет); два блока `hv_pki` с разными role_id (не поддерживается);
wildcard-сертификат `*.svc.terracapital.local` сохранён «на переходный
период без срока»; проверка идентичности АС только по IP-адресу при
SEC-03.

### C4. Zero-trust сегментация и контроль доступа (вес 10)

**Что оценивается:** D5, SEC-03 (авторизационная часть), SEC-06,
SEC-08, INF-01 (МЭ-граница).

| Уровень | Якорь |
|---|---|
| 0 | Сегментация сведена к «МЭ всё разрулит», шлюз — пассивный прокси без проверок; либо HF-01 (segmentation приписана «встроенному mesh») |
| 2 | Матрица потребитель → поставщик названа, enforcement на шлюзе есть, но механизм не конкретизирован (как именно CN/SAN отображается на разрешённые upstream/location); граница ролей SynGX и МЭ размыта |
| 4 | Модель: весь трафик в сегмент проходит только через его шлюз (МЭ ограничивает L3/L4 потоки: АС → шлюз, шлюз → АС; прямые связи запрещены — допущение §2.9), на шлюзе — enforcement по идентичности АС: доступ пары «потребитель (CN/SAN) → поставщик/ресурс» проверяется на каждый вызов (переменные клиентского сертификата + map/ACL и/или auth-request к внешнему сервису авторизации), отказ логируется в audit.log (SEC-05); явно проведена граница: МЭ — сетевой уровень (L3/L4), шлюз — прикладной (L7: идентичность, лимиты, аудит), ни один не дублирует другого; служебные эндпоинты (метрики, limit_req_change, ИИ-агент) — loopback/контур управления + TLS + ACL (SEC-06); `hide_syngx_name on` и минимизация раскрытия деталей (SEC-08); нигде не заявлено, что SynGX «сам» строит mesh/политики (HF-01); рост числа АС до 60 (NFR-10) не требует смены модели (добавление записи реестра + GitOps) |

**Ловушки:** «внутренний контур безопасен, поэтому достаточно ACL по
IP»; политика авторизации заявлена как встроенная функция «service mesh
SynGX»; служебные эндпоинты на общем listen сегмента.

### C5. Лимиты между системами (вес 12)

**Что оценивается:** D6, NFR-04, NFR-05, NFR-06, NFR-08.

| Уровень | Якорь |
|---|---|
| 0 | Нет модели лимитов; «поставим один общий лимит на сегмент» (повторение ошибки AS-IS) |
| 2 | `limit_req_zone`/`limit_req` названы; лимит на потребителя есть, но ключ зоны не выведен из идентификатора АС (CN/SAN клиентского сертификата); нет пер-узлового лимитирования; NFR-06 решён «reload конфигурации» |
| 4 | Зоны лимитов с ключом по идентификатору АС-потребителя (переменная из CN/SAN клиентского сертификата) и сопоставление профилям «Базовый» 50 / «Повышенный» 200 / «Критичный» 500 r/s (NFR-04, §2.7); код отказа 429 через `limit_req_status`; dry-run для новых потребителей (2 недели) через `limit_req_dry_run`; `limit_req_by_node` для защиты узлов АС-поставщика при деградации группы с обоснованием (NFR-05) и корректным кодом (по умолчанию 503 или явно заданный `limit_req_status_by_node`); `limit_req_monitor` для наблюдаемости по парам (NFR-08); NFR-06 решён через `limit_req_change` (PATCH с `duration` ≤ 24 ч → автоматический возврат, DELETE — отмена) **только с loopback/unix-сокета**, обёрнутого во внутренний сервис/GitOps-процедуру дежурной смены, с аудитом изменений в audit.log (SEC-05); ёмкость зон посчитана (~500 активных пар на шлюз ≪ 8–16 тыс. состояний на МБ); учтена ловушка «смена ключа/имени зоны не применяется reload'ом» (нужен stop+start ⇒ плановое окно INF-09) |

**Ловушки:** лимит по `$binary_remote_addr` как «лимит АС» (у АС много
узлов/IP — счётчик размазывается); отсутствие 429 (молчаливый дефолт);
«меняем лимиты редактированием конфига и reload» при NFR-06;
`limit_req_change` на listen сегмента (HF-05).

### C6. Наблюдаемость, аудит, трассировка (вес 10)

**Что оценивается:** D7, NFR-08, NFR-09, SEC-05, INF-04.

| Уровень | Якорь |
