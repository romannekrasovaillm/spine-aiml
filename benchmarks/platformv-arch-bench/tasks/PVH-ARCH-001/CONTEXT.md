## 1. Продукт: Platform V Works::Architect Hub (MET) 2.0.0 `[DOC]`

### 1.1 Позиционирование и состав

- Заявленное назначение (титул документации MET 2.0.0): «Организация
  архитектурного репозитория и реестров в соответствии с архитектурным
  фреймворком предприятия».
- Фактическое назначение по документации: **инструмент для создания
  архитектурных реестров** — «позволяет конфигурировать реестры путем
  настройки сущностей и операций для них, поддерживает наследование
  свойств для дочерних объектов».
- Продукт состоит из **одного компонента: Конфигуратор архитектурного
  репозитория (BECF)** — клиентская библиотека (SDK), Maven-артефакты
  `ru.sbt.met.hub:met-configurator-all:2.0.0` и
  `ru.sbt.met.hub:met-configurator-db-liquibase` (DDL-скрипты системных
  таблиц). Расположение в дистрибутиве:
  `./sdk/mvn/met-configurator-all/2.0.0/met-configurator-all-2.0.0.jar`;
  PURL `pkg:maven/ru.sbt.met.hub/met-configurator-core@2.0.0`.
- «Продукт представляет собой **SDK, который не требует отдельной
  установки и запуска**» — подключается как зависимость к проекту
  пользователя.
- Цикл работы по документации: подключить BECF → сконфигурировать типы
  объектов (сущности) → сконфигурировать операции → **скомпилировать
  приложение-реестр** → запустить (Java 17, Spring Boot, `java -jar`).
- Потребитель функций по матрице функций продукта — **«прикладной
  разработчик»**, а не архитектор, работающий в готовом UI.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/SKILL.md` (раздел «Что это по документации»); `spine-bank/banking/notes/platformv-wave4-20260902.md` (§1); `corpus/pv_docs/txt/MET__2.0.0__common__documents__about__objective.html.txt`, `MET__2.0.0__common__documents__about__functions.html.txt`, `MET__2.0.0__common__documents__developer-guide-BECF__about.html.txt`, `MET__2.0.0__common__documents__installation-guide__installation.html.txt`.

### 1.2 Чем продукт НЕ является (важно для границ решения)

- **Не modeling-инструмент**: ни C4, ни ArchiMate, ни какой-либо
  графической нотации в документации нет; диаграммы, viewpoints,
  визуальное моделирование не описаны. Единственная страница
  «концептуальная модель предметной области» — заглушка с картинкой без
  текста.
- **Не готовый EA-репозиторий**: метамодель предприятия (capability,
  процессы, прикладной/технический слои), импорт/экспорт (ArchiMate Open
  Exchange и т.п.), коллаборация архитекторов, порталы и дашборды в
  документации отсутствуют. Реестр получается **только разработкой** на
  BECF: сущности, операции, права, DDL — всё кодом на Java.
- **Не путать с Platform V Works::Architect (ART 1.8.0)** — смежный
  продукт линейки: «создавать хорошо структурированные системы и
  контролировать соответствие кода заложенной бизнес-логике» — это
  контроль code-architecture conformance, другой класс задачи.
- К ISO/IEC/IEEE 42010 продукт отношения не имеет: понятий
  stakeholder/concern/viewpoint/view в документации нет — есть «объекты
  управления» и «реестры». Заявка «в соответствии с архитектурным
  фреймворком предприятия» означает, что банк **сам** зашьёт свой
  фреймворк (свою метамодель реестров) в конфигурацию BECF.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/SKILL.md` (разделы «Чем это НЕ является», «Соотношение с C4 / ArchiMate / ISO 42010»); `spine-bank/banking/notes/platformv-map-20260902.md` (строка ART в категории «Инструменты разработчика»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__about__conceptual-model.html.txt`.

### 1.3 Типы объектов управления (ОУ)

- Тип объекта — **класс, реализующий интерфейс `IObjectType`** (методы
  `getName()`, `getTableName()`, `getIdAttributeType()`,
  `getNameAttribute()`); атрибуты задаются через
  `SettingObjectAttributeDTO` (name/type/column).
- Типы атрибутов: `AttributeType.TEXT` и др.; признаки атрибутов —
  например, `AttributeFeature.MULTI_WITH_DATE` (множественный атрибут с
  датой).
- Класс типа объекта — Spring-сервис (`@Service`); тип объекта
  **маппится на таблицу БД**.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/references/becf-configuring.md` (раздел «Тип объекта (ОУ)»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__developer-guide-BECF__instruction-type-configuring.html.txt`.

### 1.4 Операции и жизненный цикл объектов

- Операция над объектом — **класс, наследующий
  `AbstractObjectOperation`** (пример `CustomTypeCreateOperation`);
  задаются `getObjectType()`, `getOperationName()`,
  `getSecurityFilter()`, `getAllowedAttribute()`, хуки
  `preUpdateRequest(...)`.
- По матрице функций продукта конфигурируются операции **просмотра,
  создания, редактирования и перевода статуса ЖЦ объекта**.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/references/becf-configuring.md` (раздел «Операции над объектами»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__developer-guide-BECF__instruction-operation-configuring.html.txt`, `MET__2.0.0__common__documents__about__functions.html.txt`.

### 1.5 Разграничение прав (RBAC)

- Контроль доступа — интерфейс **`IObjectOperationSecurityFilter`**
  (пакет `ru.sber.meta.base.configurator.common.domain.operation.security`),
  метод `filter(request, oldVersion)` → `OperationSecurityInfo` (флаги
  `isUserAllowed`, `isAdminAllowed`).
- Базовая реализация **`RoleObjectOperationSecurityFilter`**: роль из
  токена сравнивается со списками пользовательских и административных
  ролей; пререквизит — реализация
  `ru.sber.meta.base.configurator.security.auth.CredentialsProvider`.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/references/becf-configuring.md` (раздел «Разграничение прав (RBAC)»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__developer-guide-BECF__access-rights-differentiation.html.txt`.

### 1.6 Наследование атрибутов

- Ключевой интерфейс — **`InheritanceStrategy`**; базовые стратегии:
  - `RewriteInheritanceStrategy` — перезапись атрибутов потомков
    значениями родителя;
  - `RewriteFillEmptyInheritanceStrategy` — перезапись, только если у
    потомка значение не задано;
  - `UpdateInheritanceStrategy` — обновление, если текущее значение
    потомка совпадает со старым значением родителя;
  - `UpdateFillEmptyInheritanceStrategy` — то же, либо null у потомка.
- Кастомная стратегия — наследование `AbstractInheritanceStrategy`,
  методы `applyForPlain` / `applyForMulti` / `applyForMultiWithDate`,
  режим в `getPropagationMode()`, ответ — `InheritanceResult`.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/references/becf-configuring.md` (раздел «Наследование атрибутов»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__developer-guide-BECF__inheritance.html.txt`.

### 1.7 Сборка, DDL и запуск

- DDL генерируется **тестом**: `SqlGenerator.createChangeset("<path>")`
  в `MigratorITCase` (Spring Boot Test, профиль `test`); команда
  `mvn clean verify` создаёт скрипты новых таблиц.
- Для тестов — embedded PostgreSQL
  (`com.opentable.components.otj-pg-embedded`) или TestContainers.
- Запуск собранного приложения: `java -jar
  target/met-configurator-quick-start-app-*.jar`; проверка —
  REST-запросом на создание объекта.
- Сторонние зависимости минимальной архитектуры проекта:
  `org.postgresql:postgresql:42.7.10`,
  `org.liquibase:liquibase-core:4.8.0`, `net.ttddyy:datasource-proxy:1.5.1`,
  `spring-boot-starter-web`, `spring-boot-starter-security`,
  `spring-boot-starter-oauth2-resource-server`.

Источник: `spine-bank/banking/plugins/ru-architecture/skills/pv-architect-hub/references/becf-configuring.md` (разделы «Подключение», «Сборка и DDL»); `corpus/pv_docs/txt/MET__2.0.0__common__documents__developer-guide-BECF__quick-start.html.txt`, `MET__2.0.0__common__documents__developer-guide-BECF__configuration.html.txt`.

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк "Взморье"» (вымышленный, топ-30 по активам, универсальный
коммерческий банк) реализует программу ДКА «Прозрачная архитектура» —
внедрение инструмента управления корпоративной архитектурой. Драйверы:

- Регуляторный контекст: банк субъект КИИ (часть АС), обработка ПДн
  (152-ФЗ), требования к процессам ИБ по ГОСТ Р 57580.1; при
  надзорных проверках банк обязан предъявлять актуальный учёт АС, их
  владельцев, состава ПО и интеграционных взаимодействий.
- В 2025 году при подготовке ответа на запрос надзорного органа выгрузка
  «перечень АС с владельцами и критичностью» собиралась вручную **11
  рабочих дней** из Confluence и Excel; в выгрузке нашлось 17 %
  устаревших записей.
- Правление утвердило целевое видение «единый архитектурный реестр как
  источник правды об ИТ-ландшафте» и выделило финансирование.
- Банк ранее приобрёл контур **Platform V** (в т.ч. лицензию на
  Works::Architect Hub 2.0.0). По результатам предпроектного обследования
  вендор подтвердил модель поставки «SDK для сборки собственного
  реестра»; ИТ-стратегия банка предписывает максимальное использование
  уже купленной линейки.
- Архитектурный комитет принял принципиальное решение «реестр как
  продукт»: своя метамодель, свои жизненные циклы объектов, глубокая
  интеграция с процессами банка (вендорская аргументация: готовые
  реестры «не позволяют гибко подстраиваться под процессы компании»).

### 2.2 Ландшафт AS-IS

- Архитектурные описания ведутся в **Confluence**: ~1 800 страниц в 6
  пространствах (архитектурные решения, ADR-подобные протоколы комитета,
  описания АС, интеграционные контракты, стандарты, паспорта релизов);
  навигация поиском, структура не регламентирована, ~30 % страниц не
  обновлялись более года.
- Реестры — **14 Excel-файлов** на сетевой папке ДКА: реестр АС
  (~420 строк), реестр ИТ-сервисов (~1 100 строк), реестр интеграций
  (~2 300 строк), реестр ПО и лицензий (~2 800 строк), реестр технологий
  и стандартов (~650 строк), прочие; самый большой файл — 9 500 строк,
  периодические конфликты одновременного редактирования.
- **CMDB банка «Атлант-CMDB»** (вымышленная, сторонний вендор):
  содержит ~60 000 инфраструктурных объектов (серверы, ВМ, кластеры,
  СХД-ресурсы) и ~40 000 экземпляров ПО с привязкой к серверам; есть
  REST API (чтение), данные актуализируются автодискаверингом
  ежесуточно; связи «АС ↔ инфраструктура» в CMDB **не ведутся**.
- Репозитории кода: **Works::GitVerse** (все ~1 900 репозиториев
  прикладных команд); CI/CD — **Works::Pipeliner**; артефакты —
  **Works::Artifactory**. Манифесты зависимостей (Maven/Gradle) и
  dockerfile'ы — в репозиториях, централизованного учёта технологического
  стека АС нет: сведения о технологиях вносятся в Excel вручную раз в
  квартал.
- Пользователи будущего реестра: 12 архитекторов ДКА, 33 доменных и
  проектных архитектора (итого **45 архитекторов**), ~180 прикладных
  команд разработки (чтение своих АС, актуализация атрибутов по
  заявкам), до **600 читателей** (руководители, ИБ, риски, аудит,
  надзорные выгрузки).
- Процессы согласования: статусный перевод АС («пилот → пром → вывод»)
  сейчас фиксируется протоколом комитета в Confluence и вручную
  переносится в Excel; средний срок отражения изменения в реестре — 3
  недели.

### 2.3 Целевая модель данных и нагрузка `[BENCH]`

Предметная область реестра (типы ОУ, оценка объёма на старте после
миграции):

| Тип объекта | Кол-во на старте | Источник миграции |
|---|---|---|
| Автоматизированная система (АС) | ~420 | Excel-реестр АС + Confluence |
| ИТ-сервис | ~1 100 | Excel-реестр сервисов |
| Интеграционное взаимодействие (поток) | ~2 300 | Excel-реестр интеграций |
| Продукт/версия ПО | ~2 800 | Excel-реестр ПО |
| Экземпляр ПО (привязка к серверу) | ~40 000 | CMDB (автозагрузка) |
| Инфраструктурный объект (сервер/ВМ/кластер) | ~60 000 | CMDB (автозагрузка) |
| Технология/стандарт | ~650 | Excel-реестр технологий |
| Архитектурный документ (ADR, решение комитета) | ~15 000 | Confluence (парсинг страниц) |

Итого порядка **120 тыс. объектов управления** на старте; рост **+20 %
в год**; среднее число атрибутов на объект — 25–40.

Нагрузочный профиль:

- Пиковая интерактивная нагрузка: **120 одновременных пользователей**
  (комитеты, массовые актуализации в период надзорных запросов);
  типовая — 30–50 сессий.
- Автозагрузка из CMDB: ежесуточная дельта до **5 000 изменённых
  объектов**; первичная загрузка ~100 000 объектов — ночное окно.
- Сканирование репозиториев: ~1 900 репозиториев, обход раз в сутки
  ночью; актуализация технологических атрибутов АС (связь АС ↔
  репозиторий задаётся атрибутом).
- Отчётные выгрузки для надзорных органов: до 4 раз в месяц, полная
  выборка по АС с владельцами и критичностью — формирование ≤ 10 мин.

### 2.4 Инфраструктура и ограничения `INF-xx`

### 2.6 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | Аутентификация всех пользователей — только через корпоративный IAM (Keycloak SE, INF-03); локальных учётных записей нет |
| SEC-02 | Ролевая модель минимум из ролей: «читатель», «архитектор домена» (редактирование своего домена), «администратор реестра» (управление типами, статусами, справочниками), «аудитор» (чтение всего + история); доменный архитектор не должен редактировать чужие домены |
| SEC-03 | Все операции изменения данных — с персональной атрибуцией и аудитом; события аудита выгружаются в SIEM (INF-09) |
| SEC-04 | TLS ≥ 1.2 на всех стыках: пользователь ↔ SynGX, SynGX ↔ приложение, приложение ↔ БД/брокер/IAM/CMDB |
| SEC-05 | Секреты интеграций (токены CMDB API, ключи брокера, credentials БД) — только в корпоративном Vault; в коде и конфигурационных файлах GitVerse секретов быть не должно |
| SEC-06 | Разделение контуров test/prom; в test — только обфусцированные данные (владельцы АС — персональные данные: ФИО, табельные номера) |
| SEC-07 | Доступ администраторов к инфраструктуре — через PAM; прямой доступ к БД — только учётной записи приложения и штатной ТУЗ мониторинга (INF-02) |
| SEC-08 | В атрибутах реестра минимизируются ПДн: ФИО владельцев хранятся как ссылки на штатное расписание (ID сотрудника), отображение по требованию |

### 2.7 Метрики внедрения (ожидания программы) `[BENCH]`

Программа «Прозрачная архитектура» считается внедрённой, когда:

- ≥ 95 % АС (по актуальному перечню) заведены в реестр с полным
  обязательным атрибутным составом и назначенным владельцем;
- ≥ 90 % АС имеют актуальную связь «АС ↔ инфраструктура» (через
  экземпляры ПО из CMDB) и «АС ↔ репозиторий»;
- средний срок отражения решения комитета в реестре ≤ 3 рабочих дней
  (AS-IS: 3 недели);
- надзорная выгрузка формируется self-service ≤ 10 мин (AS-IS: 11
  рабочих дней);
- Excel-реестры ДКА выведены из обращения (режим «только чтение»),
  Confluence-пространства архитектуры переведены в архив со ссылками на
  реестр;
- доля записей с признаком «не актуализировалась > 90 дней» ≤ 10 %
  (контрольная метрика качества данных).

### 2.8 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами (в частности, комитет просит
  явно разобрать альтернативу «приобрести готовый EA-инструмент класса
  Archi/ARIS вместо разработки на BECF»).
- Решение должно быть реализуемо командой INF-08 и эксплуатироваться
  штатной дежурной сменой (INF-09) без выделенного администратора
  реестра.
- Комитет особенно чувствителен к двум вопросам: (1) **не продан ли
  банку «готовый репозиторий» под видом SDK** — все функции, которые
  потребуют разработки (UI, импорт, отчётные выгрузки), должны быть
  явно названы разработкой с оценкой; (2) реальна ли оценка трудозатрат
  команды 4+1+0,5 на горизонте 9 месяцев до промышленной эксплуатации.

### 2.9 Что можно принять допущением `[ASSUME]`

- Доступность инфраструктурных компонентов (DropApp, Pangolin, Corax,
  IAM SE, SynGX, GitVerse/Pipeliner/Artifactory, Vault, SIEM)
  обеспечивается их владельцами по корпоративным SLA; их
  проектирование — вне scope задачи.
- Реализация `CredentialsProvider` (см. §1.5) для интеграции ролевой
  модели BECF с токенами Keycloak SE технически достижима; объём —
  предмет оценки решающего.
- Характер использования брокера приложением-реестром (какие события
  публикуются/потребляются, требуемый профиль топиков) в документации
  MET 2.0.0 не раскрыт (§1.10) — решающий вправе предложить модель
  событийного взаимодействия как своё проектное решение, пометив
  предположения о поведении продукта как `[ТРЕБУЕТ ПРОВЕРКИ]`.
- Confluence банка предоставляет REST API выгрузки страниц; Excel-
  реестры доступны как файлы; инструменты преобразования в целевую
  модель — разработка банка (см. §1.10: штатный импорт в продукте не
  описан).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| ОУ (объект управления) | сущность архитектурного реестра (АС, ИТ-сервис, интеграция, сервер и т.д.); в BECF — тип, реализуемый классом `IObjectType` |
| BECF | Конфигуратор архитектурного репозитория — единственный компонент Works::Architect Hub, Java-библиотека (SDK) |
| «реестр как продукт» | подход: архитектурный реестр — собственное приложение банка (своя метамодель, ЖЦ, интеграции), разрабатываемое и сопровождаемое внутренней командой |
| Метамодель | набор типов ОУ, их атрибутов, связей и правил; в случае BECF зашивается в Java-код приложения-реестра |
| ЖЦ объекта | статусная модель объекта (например, «пилот → пром → вывод»); переводы статусов — операции `AbstractObjectOperation` |
| Двойное ведение | переходный период миграции, когда данные параллельно ведутся в старом (Confluence/Excel) и новом контуре |
| Домен (архитектурный) | предметная область ответственности доменного архитектора (например, «платежи», «кредиты») |
| CMDB | база данных управления конфигурациями: учёт инфраструктурных объектов и экземпляров ПО |
| ADR | Architecture Decision Record — документ фиксации архитектурного решения |
| self-service выгрузка | формирование отчётной выгрузки уполномоченным пользователем без участия ИТ |
