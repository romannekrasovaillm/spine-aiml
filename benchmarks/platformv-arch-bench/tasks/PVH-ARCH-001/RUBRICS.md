# Рубрики оценки для задачи PVH-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   правила hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с
   цитатами-доказательствами из ответа; (d) сформировать вердикт по §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о
   Works::Architect Hub (MET), которого нет в §1 и которое не помечено
   решающим как допущение, считается **непроверенным**; если оно ещё и
   ложно — **ложным**. Судья не должен «додумывать» за решающего.
3. **«Упомянул ≠ применил».** Балл ставится за решение, привязанное к
   требованию (INF/NFR/SEC) и обоснованное, а не за наличие ключевого
   слова или имени интерфейса.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно/
   поверхностно; 2 — базово корректно, есть пробелы; 3 — полно и
   обоснованно, мелкие недочёты; 4 — образцово: полно, обоснованно, с
   учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия судья приводит
   1–3 коротких цитаты (≤ 25 слов) из ответа и указывает, чего не
   хватает до следующего уровня.
6. Режим прогона фиксирован: `agentic`. Утверждения за пределами
   CONTEXT.md §1 должны быть помечены как допущения либо как «требует
   проверки у вендора» — это легитимный элемент ответа, а не ошибка.
7. Судья не оценивает стиль и «красоту» сверх C10 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами, критерии
всё равно оцениваются (для диагностики).

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Architect Hub представлен как готовый EA-репозиторий «из коробки»: ему как **встроенные факты продукта** приписаны готовый UI/портал для архитекторов, дашборды, штатный импорт из Excel/Confluence/ArchiMate или предконфигурированная метамодель/набор реестров | Только судья: семантическая проверка по CONTEXT §1.2 и §1.10 (частично ловится regex mechanical_checks) |
| HF-02 | Продукту приписаны функции визуального моделирования (диаграммы, нотации C4/ArchiMate, viewpoints, графическая коллаборация) как факт | Только судья: сверка с CONTEXT §1.2 |
| HF-03 | Вымышленные компоненты, Maven-артефакты или классы BECF поданы как факт (например, «Architect Hub Server», `met-configurator-ui`, `met-import-tool`, «консоль администратора Architect Hub») | Только судья + regex mechanical_checks (характерные имена); сверка с CONTEXT §1.1–§1.7 |
| HF-04 | Решение обещает внедрение реестра «настройкой/конфигурированием без разработки»: типы ОУ, операции, права или DDL предлагается ввести без Java-кода, компиляции и релиза приложения — вопреки документированной модели SDK | Только судья: сверка с CONTEXT §1.1, §1.3–§1.7 |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | Механическая проверка (mechanical_checks.deliverables) + A-01 |

## 3. Критерии

### C1. Фактическая корректность по Works::Architect Hub (вес 15)

**Что оценивается:** соответствие всех утверждений о продукте CONTEXT.md
§1; корректные наименования компонентов, артефактов, интерфейсов;
отделение фактов от допущений; корректная работа с пробелами §1.10.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01/HF-02/HF-03/HF-04, либо ≥ 4 ложных утверждений о продукте |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (SDK-модель, генерация DDL, RBAC-фильтры, обязательность брокера/IAM), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 явно помечено как допущение или «проверить у вендора»; правильно различаются: MET и ART, факты документации и проектные решения банка, документированные механизмы BECF и разработка, которую предстоит выполнить банку |

**Признаки сильного ответа:** использует официальные имена
(`ru.sbt.met.hub:met-configurator-all:2.0.0`,
`met-configurator-db-liquibase`, `IObjectType`,
`SettingObjectAttributeDTO`, `AbstractObjectOperation`,
`IObjectOperationSecurityFilter`, `RoleObjectOperationSecurityFilter`,
`CredentialsProvider`, `InheritanceStrategy` и четыре базовые стратегии,
`SqlGenerator.createChangeset`, `MigratorITCase`); явно фиксирует, что
продукт — SDK и потребитель функций — «прикладной разработчик»; не
заявляет UI/импорт/предконфигурированные реестры как факт; пробел по
назначению брокера помечает `[ТРЕБУЕТ ПРОВЕРКИ]`.

**Типичные ошибки:** «развернём Architect Hub как готовый сервер»;
«архитекторы будут работать в портале Architect Hub»; путаница
MET ↔ ART; изобретение классов/параметров конфигурации; уверенные
утверждения о функциях, отсутствующих в CONTEXT.md.

### C2. Целевой контур и размещение (вес 12)

**Что оценивается:** D2. Топология: приложение-реестр на BECF и всё
обязательное окружение по матрице §1.8, размещение в DropApp двух ЦОД
(INF-01), интеграция с корпоративными компонентами, NFR-01, NFR-07.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; контур не включает обязательные компоненты матрицы (БД, брокер, IAM, веб-точка входа) |
| 2 | Приложение-реестр размещено в Kubernetes, БД/IAM/брокер показаны, но: часть обязательного окружения (SynGX, Keycloak, Corax) отсутствует или не связана с матрицей §1.8; доступность/RTO заявлены декларативно; один ЦОД без обоснования |
| 4 | (a) схема: приложение-реестр (Spring Boot на BECF, Java 17) в DropApp обоих ЦОД, веб-точка входа SynGX (INF-05), БД на корпоративном кластере Pangolin 8.2.0 (INF-02, удовлетворяет 6.5.0+), Corax (INF-04, удовлетворяет 9.340.2+), IAM SE/Keycloak (INF-03, удовлетворяет 23.0.0+), CI/CD GitVerse/Pipeliner/Artifactory (INF-06), CMDB, SIEM/Prometheus (INF-09); (b) для каждого компонента окружения показана увязка с матрицей системных требований MET; (c) модель доступности: активная работа в ЦОД-1, восстановление в ЦОД-2 под RPO ≤ 15 мин / RTO ≤ 4 ч (NFR-07) — конкретный механизм (резервное копирование БД средствами контура Pangolin, повторное развёртывание из GitOps) как проектное решение банка; (d) разделение контуров test/prom (INF-01, SEC-06) |

**Ловушки:** «установим Architect Hub на отдельные ВМ» (INF-01); контур
без брокера («Kafka не нужна») при обязательности по §1.8; собственная
аутентификация приложения при INF-03/SEC-01.

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "PVH-ARCH-001-RUB",
  "task_id": "PVH-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` считается по формуле из frontmatter; `verdict =
excellent` при `total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.

## 8. Калибровка и контроль качества судей

1. Перед запуском бенчмарка подготовить три эталонных ответа (`gold`,
   `silver`, `fail`) и убедиться, что медиана ансамбля судей попадает в
   `expected_totals`.
2. Считать согласованность судей по каждому критерию; при
   `alpha < 0.75` — уточнить якоря критерия (ожидаемо проблемные: C3 и
   C7 — там тонкая граница между «документированным механизмом BECF» и
   «разработкой банка»).
3. Для 10 % прогонов проводить выборочную проверку человеком;
   расхождение > 1 балла по критерию фиксируется как инцидент
   калибровки.
4. При обновлении версии MET или документации — обновить CONTEXT §1,
   таблицу ловушек §4 и `docs_snapshot_date`; повысить `version` рубрик
   и перепрогнать эталоны.
5. Не показывать решающим таблицу ловушек §4 и якоря уровня 4 — они
   предназначены только для судей и составителей.
