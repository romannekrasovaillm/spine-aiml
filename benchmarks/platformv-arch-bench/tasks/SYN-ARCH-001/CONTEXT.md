### 1.3 Компоненты-шлюзы: семантика взаимодействий

- **ASGT**: приём gRPC-вызова от микросервиса, преобразование интерфейса
  gRPC ↔ транспортная библиотека провайдера MQ; маршрутизация; отправка/чтение
  MQ-сообщения в/из очереди внешней АС; ответное Proto-сообщение.
  Документированы **4 сценария**: асинхронный и синхронный запрос/ответ в обе
  стороны («Внешняя АС ↔ Микросервис»).
- **KFGT**: преобразование интерфейса gRPC/REST ↔ Kafka; отправка/чтение
  сообщений в/из топиков внешней АС. Документированный сценарий — синхронный
  запрос от микросервиса во внешнюю АС.
- **JDBC Gateway**: приём gRPC или HTTP вызова; вызов хранимой
  процедуры/функции внешней БД; ответ в формате Proto или текст; шифрование
  данных. Документированный сценарий — **только синхронный запрос/ответ**
  от микросервиса во внешнюю БД.
- **SAPG**: преобразование gRPC ↔ RFC, вызов функциональных модулей SAP,
  обработка вызовов из AC SAP, маршрутизация к микросервису.
- **OCPL**: регистрация изменений прикладных объектов в 1С, приём/выполнение
  HTTP GET/POST, описание изменений в JSON.
- **FSGW**: загрузка/получение/удаление/копирование объектов S3 с вычислением
  хеша, наложением и проверкой подписи, шифрованием (режимы FSGW-TR,
  FSGW-TSE-KEY), multipart upload, операции с bucket.
- **FXIA**: передача файла из ресурса-источника в ресурсы-получатели.
- **MICR**: HTTP и gRPC в обе стороны, очереди брокеров по AMQP 1.0 и
  AMQP 0.9, публикация/чтение Kafka, таймеры, SFTP, SMTP, фильтрация и
  валидация сообщений языковыми выражениями, установка тела и заголовков.

### 1.4 Брокеры сообщений

**SMBX (Синапс.Брокер сообщений, продукт SMB):**

- Очереди сообщений на базе технологий **Apache ActiveMQ Artemis**; модели
  «точка-точка» (point-to-point) и «публикация-подписка» (pub-sub);
  протоколы CORE, JMS, STOMP, MQTT, AMQP.
- Хранение и получение секретов и получение сертификатов из HashiCorp Vault.
- Эксплуатация кластера: поузловое обновление версии и сертификатов **без
  недоступности**, scale-up/scale-down брокеров, ограничение числа сессий на
  клиента, архивные копии по cron, перешифрование паролей в конфигурациях.
- В оглавлении есть разделы «Механизмы балансировки нагрузки внутри кластера
  SMB», «Отказоустойчивость», «Адресная модель», «Совместимость с выпущенными
  клиентами» — содержимое в корпус не вошло (см. §1.8).

**Platform V Corax (KFK) 16.392.0:**

- «Распределенная, отказоустойчивая, реплицированная и легко масштабируемая
  система передачи сообщений»; все сообщения хранятся на диске. Дистрибутив
  на базе **Apache Kafka** (в нефункциональных особенностях упомянуто ядро
  «Apache Kafka 3.9»; точную версию ядра проверить у вендора).
- Состав: Apache Kafka (обязателен), Apache ZooKeeper **или**
  KRaft-контроллеры (KRaft поддержан в Ansible-установке как альтернатива);
  опциональные Corax Schema Registry, Corax UI, Corax Mirror Maker 2.
- **ZooKeeper-ансамбль**: минимум 3 узла, только нечётное количество,
  работоспособен при живом строгом большинстве; standalone-конфигурация не
  рекомендована для промышленной эксплуатации.
- **Доступность 99,9%** заявлена при условиях: каждый компонент на отдельном
  хосте, фактор репликации ≥ 3, `min.insync.replicas` ≥ 2; rolling update
  без простоя; `unclean.leader.election.enable=false`.
- **Гарантии доставки**: `acks` = 0/1/all; идемпотентный продюсер
  (`enable.idempotence=true`; требования `acks=all`,
  `max.in.flight.requests.per.connection ≤ 5`, `retries > 0`) «усиливает
  семантику доставки с at least once до exactly once» — в пределах одной
  сессии; транзакционный продюсер (`transactional.id`) — атомарная запись в
  несколько партиций/топиков (рекомендованы RF ≥ 3,
  `min.insync.replicas = 2`; потребитель — `isolation.level=read_committed`).
  Прямое предупреждение документации: `retries > 0` без идемпотентности
  может привести к задвоению данных и нарушению порядка записей.
- **Corax Schema Registry**: хранилище схем (Avro, JSON Schema; Protobuf
  упомянут на одной из страниц — расхождение, требует проверки); режим
  Active-Active, узлы равноправны; хранение в топике `_crx_schemas`
  (параметры топика менять запрещено); режимы совместимости BACKWARD
  (дефолт, не транзитивный) / BACKWARD_TRANSITIVE / FORWARD(_TRANSITIVE) /
  FULL(_TRANSITIVE) / NONE. **Records Policy** — проверка входящих данных на
  соответствие схеме **на стороне брокера**; «НЕ ВХОДИТ в состав Apache
  Kafka и доступен только при использовании Corax».
- **Corax Mirror Maker 2**: репликация данных и метаданных между кластерами
  (на базе Kafka Connect): сообщения, метаданные топиков, группы
  потребителей, контрольные точки (offsets), ACL; топологии Active-Active и
  Active-Standby; сценарии — DR, консолидация, изоляция пром/тест, миграция.
- **Безопасность Corax**: TLS 1.2/1.3, mTLS, Kerberos (SASL/GSSAPI); ACL по
  ресурсам CLUSTER/GROUP/TOPIC/TRANSACTIONAL_ID/DELEGATION_TOKEN/USER;
  аудит (встроенный плагин включён по умолчанию; события в Platform V
  Monitor COTE или лог-файл); сквозное (e2e) шифрование сообщений на клиенте
  (симметричное и асимметричное); шифрование паролей в конфигурациях;
  SecMan; SSL live update — ротация сертификатов по брокеру без
  недоступности кластера; JMX по умолчанию выключен (в PROD — только с
  аутентификацией); HTTPReporter — экспорт метрик в Prometheus.
- Минимальное железо (пром): брокер 4 CPU / 16 ГБ RAM / 200 ГБ; контроллер
  ZooKeeper/KRaft 4/4/64. Профиль нагрузки вендора: 13 000 tps записи при
  среднем сообщении 10 КБ (стенд из 3 брокеров).
- ОС: CentOS 8.7+, Astra Linux SE 1.7.3+, Альт СП 8+, SberLinux OS Server
  9.7.0+/8.10.4+; OpenJDK/SberJDK 17 и 21 (поддержка OpenJDK 11 прекращена
  с версии 16.392.0).

### 1.5 Надёжность, балансировка и распределённые транзакции

- **GEOH (Geohealthcheck, SEI)**: балансировка трафика **между кластерами**
  (ЦОД). Сценарии: опрос работоспособности хоста; работоспособность сервиса
  из группы (в т.ч. по префиксу); агрегированный ответ о группе сервисов;
  ответ от каждого сервиса; валидация конфигурации. GEOH отвечает
  балансировщику.
- **SRLS (Synapse Rate Limiter, SEI)**: ограничение прикладной нагрузки со
  стороны потребителя на защищаемые сервисы в Synapse Service Mesh; два
  паттерна — централизованный подсчёт запросов и подсчёт в точке применения
  квот. Сценарии: квоты на ресурс/потребителя, расписания квотирования, сбор
  метрик и **режим NЦОД** — запуск в режиме нескольких ЦОД и разделение квот
  между ЦОД (перевод endpoint в режим NЦОД в рамках релизного цикла).
- **SDTM**: реализация XA-транзакций, в том числе XA-транзакции для записи в
  несколько Kafka при помощи KFGT.
- **EVPC**: фильтрация, трансформация, слияние, порождение, агрегация потоков
  событий. **SAI (SynAI)**: ML-управление трафиком (моделирование).

### 1.6 Функции безопасности AM и SEI

- Авторизация доступа пользователей на основе ролей и атрибутов доступа.
- Безопасность и фильтрация входящего/исходящего трафика между приложениями
  и на границах namespace; логирование событий.
- Аутентификация и авторизация межсервисных взаимодействий (нефункциональные
  особенности AM и SEI, формулировки совпадают).
- **KACM** — выпуск и ротация x509 из PKI потребителя (§1.2). **POLM** —
  централизованная рассылка политик на IGEG/SVPX. **MPSM** — авторизация
  пользователей портала по OIDC.
- Безопасность Corax — см. §1.4 (TLS/mTLS, Kerberos, ACL, аудит, e2e-
  шифрование, SecMan, SSL live update).

### 1.7 Эксплуатация, наблюдаемость, тестирование

- **GATM**: сбор метрик пользовательского namespace, метрик istiod
  контрольной панели, системных метрик; агрегация; сбор событий.
- **SYAL**: сбор, отправка и хранение логов (приложения synapse-logs-agent /
  -insert / -select / -storage); удалённое хранилище — Kafka напрямую или
  через KFGT, либо локальное краткосрочное хранилище.
- **VISL**: граф сетевого трафика, метрики, трейсы, логи, правила
  маршрутизации, процент нагрузки (панель для Istio SE).
- **SYTE (SyTester)**: нагрузочное и интеграционное тестирование, заглушки;
  протоколы HTTP/HTTPS, gRPC (HTTP/2), Kafka, Active MQ, Artemis MQ, IBM MQ;
  синхронный и асинхронный режимы; пошаговые сценарии (например: отправить в
  очередь Artemis MQ → прочитать ответ из топика Kafka → вызов gRPC);
  debug-режим для взаимодействий сервисов в k8s с Istio; авторизация в GUI
  через KeyCloak.
- **SXEI (Syndex)**: ИИ-помощник — консультации по документации и генерация
  конфигураций компонентов.
- **LIND + MPSM + SEI**: low-code проектирование интеграций и маппинга;
  «преобразование протоколов API и форматов данных, маппинг, любая
  бизнес-логика на языках JavaScript и C#»; автоматическая проверка
  конфигураций; интегрированные инструменты нагрузочного тестирования.
- Установка компонентов AM — через **SYOP** (Helm Charts, порядок установки,
  параметры в CRD, чек-листы проверки, сценарии обновления и отката по
  каждому компоненту); для сервисов **вне** Kubernetes — **SYAP** (Ansible).
- Нефункциональные особенности AM и SEI (формулировки совпадают):

  требованиях» руководств по установке); стек на базе Open Source; ролевая

## 2. Сценарий заказчика `[BENCH]`

### 2.1 Бизнес-контекст

АО «Банк “Полюс-Кредит”» (вымышленный, топ-40 по активам) эксплуатирует
централизованный интеграционный слой на legacy ESB, через который проходят
интеграции ~90 автоматизированных систем: АБС, процессинг, ДБО, CRM,
SAP ERP, 1С:ЗУП, антифрод, внешние контрагенты (ФНС, бюро кредитных
историй, SWIFT-шлюз), файловый обмен с клиентами-юрлицами.

Стратегия технологического суверенитета предписывает вывод иностранной ESB
из эксплуатации до конца 2027 года. Целевая платформа утверждена:
**Platform V Synapse** (линейка, см. §1.1). Архитектурный комитет требует
**поэтапную миграцию потоков** с сохранением работоспособности и
возможностью отката каждого потока; «big bang» запрещён (INF-07).

### 2.2 Ландшафт AS-IS

**Интеграционная платформа (выводится):**

- ESB: IBM App Connect Enterprise (ACE) 12 — 4 узла в ЦОД-1, 4 узла в ЦОД-2
  (active/standby по потокам).
- Очереди: IBM MQ 9.3 — 2 кластера очередей (по одному в ЦОД), ~600 очередей;
  часть внешних АС (АБС, процессинг) подключены напрямую к MQ.
- Событийная шина: Confluent Platform (Kafka) 7.x — кластер 5 брокеров в
  ЦОД-1 и 3 брокера в ЦОД-2, репликация Confluent Replicator; ~180 топиков;
  потребители: ДБО, антифрод, витрины данных.
- Файловый обмен: файловый шлюз на FTP/SFTP-серверах и самописных
  регламентах (cron + shell).

**Потоки ESB (всего 240):**

| Тип потока | Кол-во | Примеры |
|---|---|---|
| MQ синхронный запрос/ответ | 70 | АБС ↔ карточный процессинг, АБС ↔ ДБО |
| MQ асинхронный | 60 | уведомления, журналирование операций, антифрод |
| SOAP/REST синхронный | 55 | CRM, БКИ, ФНС, внутренние справочники |
| Файловый (FTP/SFTP, сверки, реестры) | 30 | клиенты-юрлица, SWIFT-реестры, регуляторные выгрузки |
| DB-адаптеры (вызов хранимых процедур Oracle) | 15 | legacy-модули АБС, казначейство |
| SAP RFC | 10 | SAP ERP: бухгалтерия, кадры |

**Нагрузка:**

- MQ: среднее 850 сообщений/с, пик **3 200 сообщений/с**; средний размер
  сообщения 8 КБ, максимум 2 МБ.
- Kafka: среднее 12 000 событий/с, пик 40 000 событий/с; средний размер 5 КБ;
  retention критичных топиков 7 суток.
- SOAP/REST: пик 600 RPS, p99 ≤ 800 мс end-to-end.
- Файлы: ~4 ТБ/месяц, файлы до 2 ГБ; ~120 регламентных обменов в сутки.

**Классы критичности потоков:**

| Класс | Кол-во потоков | Критерий | Примеры |
|---|---|---|---|
| A (критичные) | 45 | платёжные и клиентские операции; недоступность влечёт регуляторные последствия | АБС ↔ процессинг, ДБО-платежи |
| B (важные) | 110 | деградация сервиса без прямых регуляторных последствий | CRM, справочники, уведомления |
| C (фоновые) | 85 | пакетные и аналитические обмены | выгрузки, сверки, витрины |

### 2.3 Инфраструктура и ограничения `INF-xx`

| ID | Ограничение |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), ~38 км, каналы 2×10 Гбит/с, RTT ≤ 2 мс. Третьей площадки нет; доступны до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД (пригодны, например, для кворумных узлов) |
| INF-02 | В каждом ЦОД — два продуктивных кластера Kubernetes (совместимость с Platform V подтверждена пилотом), ОС узлов SberLinux OS Server. Под Synapse выделяется до 40 worker-узлов (16 vCPU / 64 ГБ) на кластер. Corax по системным требованиям разворачивается на отдельных хостах/ВМ (не в K8s) |
| INF-03 | PKI банка: корпоративный УЦ, выпуск x509; хранилище секретов — кластер HashiCorp Vault (3 узла, растянут между ЦОД) |
| INF-04 | Мониторинг: Prometheus + Zabbix; логи — централизованный сбор в SIEM; трейсинг — корпоративный Jaeger |
| INF-05 | Внешние потребители и партнёры подключаются через DMZ: L4/L7-балансировщики с health-check, DNS/GSLB для переключения между ЦОД |
| INF-06 | Команда: 3 интеграционных архитектора, 6 инженеров сопровождения (Kubernetes — средний уровень, Synapse — без опыта), 2 специалиста ИБ. Внедрение — только через корпоративный CI/CD и IaC |
| INF-07 | Миграционные окна — ночи выходных дней; для потоков класса A перевод только с подтверждённой процедурой отката ≤ 30 минут; одновременный перевод всех потоков («big bang») запрещён |
| INF-08 | Legacy-платформа (ACE + IBM MQ + Confluent) эксплуатируется до конца миграции; лицензии позволяют параллельную работу старого и нового контуров до 18 месяцев. Общий срок программы — 18 месяцев |

### 2.4 Нефункциональные требования `NFR-xx`

| ID | Требование | Целевое значение |
|---|---|---|
| NFR-01 | Доступность интеграционного слоя для потоков класса A | ≥ 99,95 % в операционное время (04:00–01:00 МСК) |
| NFR-02 | Пропускная способность MQ-канала | пик 3 200 сообщений/с, p99 доставки через шлюз ≤ 500 мс |
| NFR-03 | Пропускная способность событийного канала | среднее 12 000, пик 40 000 событий/с; retention критичных топиков ≥ 7 суток |
| NFR-04 | Потеря сообщений класса A | подтверждённые сообщения не теряются при отказе одного узла/пода (RPO = 0 внутри ЦОД); при потере ЦОД — RPO ≤ 30 с для событий, для MQ-потоков класса A — по регламенту DR (обосновать) |
| NFR-05 | RTO при потере ЦОД | класс A ≤ 15 мин, класс B ≤ 60 мин |
| NFR-06 | Файловый обмен | файлы до 2 ГБ, 4 ТБ/мес, подпись и контроль целостности |
| NFR-07 | Квотирование внешних потребителей | ограничение нагрузки от каждого внешнего потребителя; при потере ЦОД квоты не должны «схлопываться» или удваиваться |
| NFR-08 | Масштабирование | рост числа потоков +50 % за 2 года без перепроектирования топологии |
| NFR-09 | Миграция без остановки | перевод каждого потока без недоступности для его участников; откат потока ≤ 30 мин |
| NFR-10 | Тестирование | автоматизированная регрессия каждого мигрируемого потока до перевода; нагрузочное тестирование по профилю NFR-02/03 |

### 2.5 Требования информационной безопасности `SEC-xx`

| ID | Требование |
|---|---|
| SEC-01 | TLS для всех каналов; mTLS для межсервисных и межкомпонентных взаимодействий; сертификаты из корпоративного УЦ; ротация не реже раза в год без простоя |
| SEC-02 | Файлы с ПДн и банковской тайной — подпись и шифрование при передаче и хранении в промежуточном объектном хранилище |
| SEC-03 | Секреты подключений (пароли, ключи к внешним АС) — только во внешнем хранилище секретов банка (Vault); открытые пароли в конфигурациях запрещены |
| SEC-04 | Разграничение доступа к интеграциям и порталам по ролям; доступ разработчиков/администраторов — через корпоративный IdP (OIDC) |
| SEC-05 | Аудит операций с интеграциями и доступа к сообщениям; логи интеграционного слоя передаются в SIEM; администраторы слоя не могут изменить переданные журналы |
| SEC-06 | Изоляция интеграций по доменам банка (отдельные namespace/проекты); политики трафика на границах доменов — централизованные |
| SEC-07 | События с ПДн в событийном канале — сквозное шифрование (потребитель расшифровывает самостоятельно) |
| SEC-08 | Межсервисная аутентификация и авторизация во всех взаимодействиях интеграционного слоя |

### 2.6 Организационные ожидания `[BENCH]`

- Архитектурный комитет ожидает **одно рекомендуемое решение** плюс
  1–2 отвергнутые альтернативы с причинами (включая «оставить Confluent
  вместо Corax» и «прямые Kafka/MQ-клиенты в микросервисах вместо шлюзов»).
- Решение должно быть реализуемо силами команды INF-06 с использованием
  штатной автоматизации продуктов.
- Комитет особенно чувствителен к: (a) размещению кворумов контроллеров при
  двух ЦОД; (b) поведению потоков класса A при потере ЦОД; (c) отсутствию
  «разрыва гарантий» на стыке шлюз ↔ брокер ↔ внешняя АС; (d) откату потока
  без остановки соседних.

### 2.7 Что можно принять допущением `[ASSUME]`

- Версии целевых продуктов на момент внедрения — не ниже зафиксированных в
  §1.1 (AM 2.5.0, SEI 6.8.0, SMB 4.1.1, Corax 16.392.0).
- Микросервисы ДБО (cloud-native, в Kubernetes) могут быть доработаны под
  gRPC/REST-контракты шлюзов Synapse; legacy-системы (АБС, процессинг, SAP,
  1С) свои протоколы **не меняют** — остаются MQ, Kafka, RFC, файлы,
  БД-процедуры.
- Внешние АС-потребители Kafka способны работать с любым Kafka-совместимым
  брокером (клиентский API 0.10.0+); S3-совместимое хранилище банка доступно
  в обоих ЦОД.
- Регламент DR для IBM MQ AS-IS (ручное переключение, RTO 60 мин) может быть
  воспроизведён на целевом контуре как стартовая точка.

## 3. Глоссарий

| Термин | Значение |
|---|---|
| CloudESB | позиционирование Synapse App Mesh: корпоративная сервисная шина поверх Kubernetes/OpenShift |
| Шлюз (ASGT/KFGT/JDBC/SAPG) | компонент-переходник между микросервисами (gRPC/REST) и внешними АС (MQ/Kafka/БД/SAP); не хранит сообщения как брокер |
| Брокер | SMBX (Apache ActiveMQ Artemis) для очередей MQ; Platform V Corax (Apache Kafka) для событий |
| GEOH | компонент балансировки трафика между кластерами (ЦОД) по health-check |
| SRLS | rate limiter для сервисов в Synapse Service Mesh, включая режим NЦОД |
| SDTM | менеджер распределённых (XA) транзакций |
| MM2 | Corax Mirror Maker 2 — межкластерная репликация Kafka |
| DLQ | dead letter queue; семантика в источниках Synapse не описана — только как допущение/вопрос вендору |
| exactly-once | в Corax — идемпотентный/транзакционный продюсер в пределах сессии, не сквозная гарантия «из коробки» |
| RPO / RTO | допустимая потеря данных / допустимое время восстановления |
