# Задача SYN-ARCH-001

## 1. Роль

Вы — ведущий архитектор решений в Департаменте корпоративной архитектуры банка.
Вам поручено спроектировать **целевую (TO-BE) архитектуру интеграционного слоя**
банка на продуктах линейки **Platform V Synapse** и подготовить архитектурную
записку для Архитектурного комитета. Интеграционный слой переводится с
действующей legacy ESB (см. CONTEXT.md §2.2); миграция должна быть поэтапной,
без остановки бизнес-операций, с возможностью отката каждого потока.

## 2. Что нужно сделать

На основе исходных данных из `CONTEXT.md` (факты о продукте §1, ландшафт AS-IS,
нефункциональные требования, требования ИБ, инфраструктурные ограничения §2):

1. Спроектировать **целевую топологию** интеграционного слоя в двух ЦОД:
   кластеры Kubernetes, размещение компонентов Synapse App Mesh / Synapse
   Enterprise Integration, брокеров (SMBX, Corax), смежных продуктов линейки.
2. Построить **карту интеграционных потоков AS-IS → TO-BE**: для каждого
   класса потоков выбрать шаблон интеграции (message queue / event streaming /
   синхронный API / файлы / вызов БД / SAP / 1С) и профильный компонент
   Synapse с обоснованием.
3. Спроектировать **модель надёжности доставки** по классам критичности:
   гарантии доставки (at-least-once / exactly-once), идемпотентность,
   распределённые транзакции, поведение при отказе компонентов и потере ЦОД.
4. Спроектировать **катастрофоустойчивость**: межкластерная балансировка
   трафика, репликация событий между ЦОД, размещение кворумов, сценарии
   переключения и RPO/RTO по классам потоков.
5. Разработать **план поэтапной миграции потоков** с legacy ESB: волны,
   критерии перевода потока, параллельная работа старого и нового контуров,
   тестирование, процедура отката потока.
6. Спроектировать **контур безопасности**: TLS/mTLS, управление сертификатами,
   секреты, ролевая модель, аудит, шифрование файлов и событий с ПДн.
7. Описать **наблюдаемость и тестирование**: метрики, логи, трассировка,
   нагрузочное и интеграционное тестирование штатными инструментами.
8. Показать **трассировку** каждого требования (INF-xx / NFR-xx / SEC-xx) на
   принятые решения и явно зафиксировать **компромиссы, риски, допущения и
   отвергнутые альтернативы**.

## 4. Ограничения и правила

- Опирайтесь **только на функциональность, подтверждённую документацией**
  продуктов линейки Synapse (факты приведены в CONTEXT.md §1 с пометкой
  `[DOC]`). Если используете возможность, отсутствующую в CONTEXT.md, —
  явно пометьте её как **допущение, требующее проверки у вендора**, а не
  как факт.
- Не изобретайте компоненты и не переименовывайте существующие. Используйте
  официальные наименования и коды: Platform V Synapse App Mesh, Synapse
  Enterprise Integration, ASGT, KFGT, JDBC Gateway, SAPG, OCPL, FSGW, FXIA,
  MICR, GEOH, SRLS, SDTM, EVPC, EVTA, IGEG, SVPX, POLM, KACM, KBLT, GATM,
  SYAL, SYTE, LIND, MPSM, VISL, SYOP, SYAP, SMBX, RDSH Verdis, Platform V
  Corax, Corax Schema Registry, Corax Mirror Maker 2 и т.д.
- Различайте роли: **шлюз ≠ брокер**. ASGT/KFGT/JDBC — шлюзы, убирающие
  логику провайдера из микросервисов; брокеры — SMBX (Apache ActiveMQ
  Artemis) и Platform V Corax (Apache Kafka).
- Каждое ключевое решение должно быть привязано к требованию (INF/NFR/SEC)
  и сопровождаться кратким обоснованием «почему так, а не иначе».
- Числовые оценки (число экземпляров, RPO/RTO, объёмы, волны миграции)
  должны быть выведены из исходных данных, а не заявлены декларативно.
- Объём ответа: не более 4000 слов без учёта кода диаграмм и таблиц.
- Язык ответа: русский; допустимы англоязычные технические термины.

## 6. Режим прохождения

Задача прогоняется **только в режиме `agentic`**: у решающего есть доступ к
файловой системе (CONTEXT.md и корпус документации), выполнению кода и
web_fetch по разрешённым доменам документации (см. CONTEXT.md §1.9). Ожидается,
что агент самостоятельно сверяет факты с источниками и подтверждает расчёты.

## 7. Что НЕ требуется

- Проектирование прикладной архитектуры микросервисов банка (внутреннее
  устройство ДБО, АБС и т.п.) — только их интеграционные взаимодействия.
- Сметы, лицензионные расчёты, выбор моделей серверов.
- Пошаговые инструкции установки компонентов (манифесты, значения CRD) —
  достаточно ссылок на компоненты и разделы документации.
- Сравнение Synapse с конкурирующими ESB, кроме случаев обоснования
  отвергнутых альтернатив (включая «оставить legacy ESB»).

## 8. Критерии приёмки (кратко)

Полные рубрики — в `RUBRICS.md`. Ключевые точки отсечения («hard fail»):

- вымышленные компоненты или функции Synapse/Corax поданы как факт;
- шлюз (ASGT/KFGT/JDBC) назван брокером сообщений или наоборот;
- заявлен RPO = 0 при потере ЦОД на каналах с асинхронной межкластерной
  репликацией без оговорок и компенсирующих мер;
- план миграции — «big bang»: без волн, без критериев перевода и отката
  отдельного потока;
- отсутствует хотя бы один из обязательных артефактов D1–D10.

## 9. Примечания для составителей бенчмарка

Варианты порождения задач из этого шаблона (для расширения набора):

- **Вариация A (только события):** сузить сценарий до событийной шины
  (миграция Confluent → Corax + KFGT/EVD) — проверить глубину знаний
  гарантий Kafka-совместимого брокера.
- **Вариация B (один ЦОД):** убрать второй ЦОД — проверить, что решающий
  честно зафиксирует невозможность выполнить NFR по потере ЦОД, а не
  «натянет» GEOH/MM2 на один ЦОД.
- **Вариация C (файловый профиль):** увеличить долю файловых интеграций —
  проверить выбор между FSGW, FXIA и FEX.
- **Вариация D (внешние партнёры):** добавить открытый API партнёрам —
  проверить подключение SNE / SWA / SNX и SRLS.

Рекомендуется хранить каждую вариацию как отдельный `task_id` с суффиксом
(`SYN-ARCH-001-A`, `-B`, …) и общим `CONTEXT.md` с параметризованным §2.
