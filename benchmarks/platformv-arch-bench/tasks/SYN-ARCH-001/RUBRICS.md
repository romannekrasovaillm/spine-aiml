# Рубрики оценки для задачи SYN-ARCH-001

## 1. Общие правила для судей

1. **Порядок работы:** (a) прочитать TASK.md и CONTEXT.md; (b) проверить
   hard-fail §2; (c) оценить каждый критерий §3 по шкале 0–4 с цитатами из
   ответа; (d) сформировать вердикт по схеме §6.
2. **Фактическая база** — CONTEXT.md §1 (`[DOC]`). Утверждение о продуктах
   Synapse/Corax, которого нет в §1 и которое не помечено решающим как
   допущение («требуется проверить у вендора»), считается **непроверенным**;
   если оно ещё и ложно — **ложным**. Судья не «додумывает» за решающего.
3. **«Упомянул ≠ применил».** Балл — за решение, привязанное к потоку или
   требованию (INF/NFR/SEC) и обоснованное, а не за код компонента в тексте.
4. **Шкала 0–4:** 0 — отсутствует или ошибочно; 1 — фрагментарно; 2 — базово
   корректно, есть пробелы; 3 — полно и обоснованно, мелкие недочёты;
   4 — образцово: полно, обоснованно, с учётом компромиссов и ловушек §4.
5. **Цитирование доказательств.** Для каждого критерия — 1–3 коротких цитаты
   (≤ 25 слов) из ответа и указание, чего не хватает до следующего уровня.
6. Судья не оценивает стиль сверх C11 и не поощряет объём.

## 2. Правила hard-fail (HF)

При срабатывании любого правила итог ограничивается 39 баллами; критерии
оцениваются для диагностики.

| ID | Правило | Как обнаружить |
|---|---|---|
| HF-01 | Вымышленные компоненты/функции Synapse/Corax поданы как факт (например, «Synapse ESB», «Synapse Queue Manager», «встроенный DLQ-движок ASGT») | A-05, таблица ловушек §4; детектор-кандидат — подтверждает судья |
| HF-02 | Путаница ролей: шлюз (ASGT/KFGT/JDBC/SAPG) назван брокером или хранилищем сообщений, либо брокер (SMBX/Corax) назван шлюзом | Детектор-кандидат (regex) + проверка судьёй |
| HF-03 | Заявлен RPO = 0 («нулевая потеря сообщений») при потере ЦОД на каналах с асинхронной межкластерной репликацией (MM2) без оговорок и компенсирующих мер | Детектор-кандидат `RPO = 0` + проверка контекста судьёй; A-06 |
| HF-04 | План миграции — «big bang»: все 240 потоков одной волной, нет критериев перевода и отката отдельного потока (нарушение INF-07/NFR-09) | Только судья |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 | A-01, механически через `deliverables` (см. §9) |

## 3. Критерии

### C1. Фактическая корректность по Synapse/Corax (вес 15)

**Что оценивается:** соответствие утверждений о продуктах CONTEXT.md §1;
корректные коды компонентов; отделение фактов от допущений.

| Уровень | Якорь |
|---|---|
| 0 | Сработал HF-01 или HF-02, либо ≥ 4 ложных утверждений о продуктах |
| 2 | 2–3 неточности или одно ложное утверждение о ключевом механизме (GEOH, SRLS, SDTM, MM2, гарантии Corax), не разрушающее решение; допущения помечены частично |
| 4 | Все утверждения верны и корректно названы; всё за пределами CONTEXT §1 помечено как допущение (или подтверждено ссылкой на документацию); правильно различаются продукты (AM/SEI/SMB/Corax) и компоненты (шлюз vs брокер); пробелы источников (§1.8) названы вопросами к вендору |

**Признаки сильного ответа:** официальные коды (ASGT, KFGT, JDBC, SAPG,
FSGW/FXIA, GEOH, SRLS, SDTM, SYOP/SYAP, SYTE, GATM, SYAL, KACM, POLM, SMBX,
Corax Schema Registry, Corax Mirror Maker 2); SMBX — на базе Apache ActiveMQ
Artemis, Corax — на базе Apache Kafka; шлюзам не приписывается хранение
сообщений; сквозной exactly-once «из коробки» не заявлен; непокрытые
источниками вопросы (производительность шлюзов, аппаратные требования, DLQ,
межЦОД-схема AM/SEI) помечены «требуется проверить».

**Типичные ошибки:** «ASGT — брокер очередей»; «KFGT делает маппинг
бизнес-данных»; «JDBC Gateway для асинхронной репликации»; «GEOH балансирует
поды внутри кластера»; «Corax — не Kafka»; «Records Policy есть в Apache
Kafka».

### C2. Карта потоков и выбор шаблонов/компонентов (вес 14)

**Что оценивается:** D3. Полнота покрытия шести типов потоков AS-IS
(CONTEXT §2.2), корректность выбора шаблона и компонента, обоснование.

| Уровень | Якорь |
|---|---|
| 0 | Карта отсутствует или покрывает < половины типов потоков |
| 2 | Все типы потоков перечислены, но выбор компонентов частично ошибочен (файлы — «через Kafka», DB-процедуры — «через KFGT») или без обоснований; судьба 600 очередей IBM MQ и 180 топиков не рассмотрена |
| 4 | Таблица «тип потока → шаблон → компонент → обоснование» полная: MQ синхронный/асинхронный → SMBX (брокер) + ASGT (шлюз для микросервисов), 4 сценария ASGT увязаны с типами; события → Corax (+KFGT для микросервисов без Kafka-клиента, +Schema Registry для контрактов); SOAP/REST → синхронные API через IGEG/SVPX (при необходимости SNE/SWA — с пометкой «проверить у вендора»); файлы → FSGW/FXIA (и/или FEX — с пометкой); DB-процедуры → JDBC Gateway (с оговоркой о синхронности); SAP RFC → SAPG; 1С → OCPL; явно описано, какие потоки остаются «точка-точка» и почему; показано отличие роли брокера от роли шлюза |

**Ловушки:** «весь трафик через один компонент»; MICR как ответ на все
потоки без разбора; шлюз вместо брокера для хранения очередей.

| Уровень | Якорь |
|---|---|
| 0 | Нет схемы; или единый контур в одном ЦОД при NFR-01/NFR-05 |
| 2 | Схема с двумя ЦОД есть, компоненты названы, но: кворум ZooKeeper/KRaft в одном ЦОД или из чётного числа узлов без обоснования; не различаются контуры K8s (Synapse) и хосты Corax; не показаны шлюзы относительно микросервисов, внешние АС и DMZ (INF-05) |
| 4 | (a) компоненты AM/SEI развёрнуты в кластерах Kubernetes обоих ЦОД (active-active или active-standby — с выбором и обоснованием; stretch-кластер помечен «проверить у вендора»); (b) Corax — отдельные хосты по INF-02, кластеры в обоих ЦОД, ансамбль ZooKeeper/KRaft из нечётного числа ≥ 3 узлов с обоснованным размещением (например, облачная зона INF-01) и разбором его потери; (c) SMBX-кластеры по ЦОД с учётом документированных механизмов (scale-up/down, обновление без недоступности); (d) показаны GEOH, DMZ, внешние АС, S3, Vault, PKI; (e) схема Mermaid/PlantUML читаема: ЦОД, кластеры, коды компонентов, направления потоков |

**Ловушки:** Corax внутри K8s вопреки INF-02; кворум из 2 узлов;
stretch-кластер K8s на два ЦОД подан как факт (в источниках не описан —
только как допущение).

### C4. Надёжность доставки и гарантии (вес 12)

**Что оценивается:** D4, NFR-04. Гарантии по классам критичности,
идемпотентность, распределённые транзакции, поведение при сбоях.

| Уровень | Якорь |
|---|---|
| 0 | Гарантии не определены; или заявлен сквозной exactly-once «платформа обеспечивает» |
| 2 | Названы acks=all и идемпотентный продюсер без привязки к классам потоков; не разобран стык шлюз ↔ брокер ↔ внешняя АС («разрыв гарантий»); DLQ заявлен как документированная функция (в источниках не описана) |
| 4 | Для каждого класса (A/B/C) определён профиль доставки: для событий класса A — `acks=all`, RF ≥ 3, `min.insync.replicas ≥ 2`, идемпотентный продюсер (с требованиями `retries > 0`, `max.in.flight.requests.per.connection ≤ 5`), ручной коммит смещений после обработки, `isolation.level=read_committed` где нужны транзакции; учтено предупреждение «retries без идемпотентности = задвоение»; честно описано, что exactly-once в Corax — в пределах сессии, а сквозная семантика — комбинация механизмов + идемпотентность потребителей; для MQ-потоков — персистентность SMBX с пометкой пробелов (DLQ/redelivery — проверить у вендора); для «записи в несколько Kafka» — SDTM (XA) с оговоркой о lock-in либо осознанный отказ с причиной |

**Ловушки:** «сквозные JMS-транзакции через ASGT» (в источниках не
описано); EVTA как средство трансформации (он — «без трансформации»).

## 6. Формат вердикта {#verdict-schema}

```json
{
  "rubric_id": "SYN-ARCH-001-RUB",
  "task_id": "SYN-ARCH-001",
  "run_id": "string",
  "run_mode": "agentic",
  "judge": {"type": "llm-judge | agent-judge | human", "model": "string", "ensemble_index": 0},
  "hard_fails": [{"id": "HF-01", "triggered": false, "evidence": "string"}],
  "criteria": [
    {
      "id": "C1",
      "score": 0,
      "evidence": ["цитата ≤ 25 слов", "..."],
      "missing_for_next_level": "string",
      "traps_hit": ["T1"]
    }
  ],
  "checks": [{"id": "A-01", "status": "pass | fail | skipped", "details": "string"}],
  "total": 0,
  "verdict": "excellent | pass | fail",
  "summary": "3–5 предложений: сильные стороны, главные пробелы, рекомендация",
  "confidence": 0.0
}
```

Правила: `total` — по формуле из frontmatter; `verdict = excellent` при
`total ≥ 85`, `pass` при `≥ 70`, иначе `fail`; при любом
`hard_fails[].triggered = true` — `fail`.

   `fail`) и убедиться, что медиана ансамбля судей попадает в

   уточнить якоря критерия (обычно проблема в C2 и C4).

   по критерию фиксируется как инцидент калибровки.

   таблицу ловушек §4 и `docs_snapshot_date`; повысить `version` рубрик и
